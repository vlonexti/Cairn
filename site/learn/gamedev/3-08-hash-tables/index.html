Hash Tables

lesson 3.088 of 10 in milestone 37 min1 practice task

A hash table finds a value by its key in about the same time however many entries it holds. A hash function turns the key into a number that picks a bucket, and the table only has to look in that one place. This lesson explains hashing, collisions and load factor, compares std::unordered_map with std::map, and shows where games use them.

The problem

A game has 5,000 item definitions and looks them up by name: "iron_sword", "health_potion". Searching a vector of them means comparing names one by one, up to 5,000 comparisons per lookup. A sorted vector with binary search needs about 13. A hash table usually needs one or two.

The idea: compute where it goes

A hash function turns a key into a number, its hash. The table keeps an array of buckets and stores each entry in bucket number hash % bucketCount. To find a key, compute its hash, go straight to that bucket, and look only there.

A good hash function has two properties:

  • Deterministic: the same key always gives the same hash.
  • Well spread: similar keys give very different hashes, so entries scatter evenly over the buckets.

Here is a simple, widely used string hash, FNV-1a. It mixes each byte in with an XOR, then multiplies by a carefully chosen prime to spread the bits:

C++
#include <cstdint>
#include <format>
#include <iostream>
#include <string_view>

std::uint32_t fnv1a(std::string_view text)
{
    std::uint32_t hash{ 2166136261u };          // the FNV "offset basis"
    for (unsigned char c : text)
    {
        hash ^= c;
        hash *= 16777619u;                        // the FNV prime
    }
    return hash;
}

int main()
{
    for (const char* key : { "iron_sword", "iron_swore", "health_potion", "" })
        std::cout << std::format("{:>14} -> 0x{:08X}  bucket {}\n", key, fnv1a(key), fnv1a(key) % 8);
    return 0;
}
Output
    iron_sword -> 0xAB515E15  bucket 5
    iron_swore -> 0xAA515C82  bucket 2
 health_potion -> 0xA92D125F  bucket 7
               -> 0x811C9DC5  bucket 5

A change in the last letter moves the key to a different bucket. Notice, though, that iron_sword and iron_swore share some hex digits: FNV-1a is simple and fast, and the last byte it sees is only mixed in lightly. Hash tables that need better spreading run a short final "mixing" step over the result, like the hash function in this lesson's practice task. Games often hash asset names once, at build time, and refer to assets by the 32-bit hash at run time: comparing two numbers is much cheaper than comparing two strings.

Collisions

Different keys can land in the same bucket: there are endlessly many possible keys and only so many buckets. This is a collision, and every hash table has a strategy for it.

Strategy How it works Used by
Separate chaining Each bucket holds a small linked list of the entries that landed there std::unordered_map
Open addressing Entries live directly in the bucket array; on a collision, try the next bucket (or another probe sequence) until a free one is found Many fast game-engine and third-party hash maps

A lookup computes the hash, goes to the bucket, then compares keys until it finds a match. With a good hash and enough buckets, that is one or two comparisons.

Load factor and rehashing

The load factor is entries divided by buckets. As it rises, collisions become common and lookups slow down. So when the load factor passes a limit (1.0 for std::unordered_map by default), the table rehashes: it allocates more buckets and reinserts every entry, because hash % bucketCount changes when bucketCount does. Like vector growth, this is expensive once and cheap on average, and reserve(n) avoids it if you know the size in advance.

std::unordered_map and std::map

C++
#include <iostream>
#include <map>
#include <string>
#include <unordered_map>

int main()
{
    std::unordered_map<std::string, int> prices{ { "rope", 5 }, { "lantern", 12 }, { "sword", 40 } };
    prices["shield"] = 30;                         // insert
    if (auto it{ prices.find("lantern") }; it != prices.end())
        std::cout << "lantern costs " << it->second << '\n';
    std::cout << "contains torch: " << prices.contains("torch") << '\n';

    std::map<std::string, int> sorted{ prices.begin(), prices.end() };
    for (const auto& [name, price] : sorted) std::cout << name << ' ';   // always in key order
    std::cout << '\n';
    return 0;
}
Output
lantern costs 12
contains torch: 0

Pick unordered_map for fast lookup, map when you need the keys in order. Both allocate a node per entry, so neither is especially cache friendly; performance-sensitive engines often use open-addressing tables instead.

Where games use hashing

  • Asset and string lookup by name or by precomputed hash.
  • Spatial hashing: hash a grid cell's (x, y) to find the objects near a point without a grid for the whole world.
  • Caches: remember the result of an expensive calculation keyed by its inputs.
  • Detecting change: hash a save file or a block of data and compare hashes. (Hashes for this need to be strong; FNV-1a is fine for spotting accidents, not for detecting deliberate tampering.)

Common mistakes

[!warning] Relying on unordered_map iteration order It can differ between runs, compilers and sizes. Sort the keys, or use std::map, when order matters, such as when writing a save file.

[!warning] Using operator[] to check whether a key exists m[key] inserts a default value if the key is missing. Use find or contains.

Keeping pointers or iterators across a rehash

Rehashing invalidates iterators (though unordered_map keeps pointers to elements valid, since each lives in its own node).
