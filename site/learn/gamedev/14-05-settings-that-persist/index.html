Settings That Persist

lesson 14.055 of 6 in milestone 145 min1 practice task

A tool that forgets its window positions, open panels and last connection every time it starts is tiring to use. ImGui saves window layout itself to an .ini file; your tool saves its own settings alongside. This lesson covers both, where to store them, versioning them, and the classic bug of windows restored onto a monitor that is no longer connected.

What ImGui saves for you

ImGui remembers each window's position, size, collapsed state and (with docking) its docked layout, keyed by window title, and writes them to imgui.ini in the current directory every few seconds and on exit. Two adjustments make that robust:

C++
static std::string g_iniPath;          // must outlive the ImGui context: ImGui keeps the pointer
g_iniPath = (settingsFolder() / "layout.ini").string();
io.IniFilename = g_iniPath.c_str();
  • Store it in the user's settings folder (Local AppData, lesson 5.04), not the current directory, which may be read-only or change with how the tool was started.
  • Window titles are ids: renaming a window loses its saved layout. "Monsters###monsters" shows "Monsters" but uses the stable id monsters, so the visible title can change (with a count, say) without forgetting the layout.

Your own settings

Everything else the tool needs to remember is yours to save:

Setting Example
Which panels are open show.monsters = true
Preferences refresh.ms = 100, theme = dark, font.size = 16
Recent things Last connected process name, recent files
Table state Sorted column (ImGui can also save table column widths and order itself, with ImGuiTableFlags_Reorderable, _Hideable)

Lesson 10.08's INI format is ideal: readable, easy to edit by hand when something goes wrong, tolerant of new and missing keys. Save on exit and whenever a setting changes (debounced, for example at most once per second), so a crash does not lose them, using lesson 5.04's write-to-temporary-then-replace.

Versioning settings

As with saves (lesson 10.07), include a version, and handle:

  • Missing keys (an older settings file): use the default.
  • Unknown keys (a newer one): ignore them, and preserve them when writing back if you can, so switching between tool versions does not destroy settings.
  • Invalid values (hand-edited): validate and fall back to the default, with a log message, never crash on bad settings.

Restoring windows safely

The classic bug: a tool remembers that its main window was at x = 2600 on the second monitor. The user unplugs that monitor, starts the tool, and the window opens off-screen where it cannot be seen or dragged back. Before restoring a saved window rectangle:

  1. Get the work areas of the monitors currently connected (on Windows, EnumDisplayMonitors / GetMonitorInfoW; with SDL, SDL_GetDisplayUsableBounds).
  2. If the saved rectangle does not overlap any of them enough to grab its title bar, move it onto the primary monitor.
  3. If it is larger than the monitor, shrink it to fit.

The practice task implements this clamping, which applies equally to the main window of a game.

Common mistakes

[!warning] imgui.ini in the current directory Point io.IniFilename at the user's settings folder, with a string that outlives the context.

Renaming windows and losing their layout

Use ###id for a stable id with a changing title.

Restoring a window off-screen

Check the saved position against the monitors that exist now.
