Versioning the Interface Between a Game and Its Tools

lesson 12.066 of 7 in milestone 125 min1 practice task

The game will change: new fields in the telemetry, new commands on the pipe. Tools built for last month's game should keep working, and new tools should cope with old games. This lesson designs for that: append-only layouts with a size field, version and capability checks, feature flags, and the rules that let both sides evolve without breaking each other.

Why interfaces need versions

A tool and a game are built separately, often by different people, and updated at different times. Every shared structure and message format is an interface, and like lesson 4.05's DLL interfaces, changing it carelessly breaks whoever is on the other side:

  • Insert a field in the middle of the telemetry struct, and every older tool reads the wrong offsets: health shows the floor number.
  • Rename a pipe command, and old tools send commands the game no longer understands.

The goal is compatibility in both directions:

Situation Should
New tool, old game Read what the old game provides; hide features it lacks
Old tool, new game Keep working with the fields it knows; ignore new ones
Truly incompatible change Be detected and reported clearly, never misread

Rule 1: append, never insert or reorder

Add new fields only at the end of a structure. Then every field keeps its offset forever, and an older tool reading the beginning of a newer block reads exactly what it expects.

C++
struct TelemetryV2                // version 2 = version 1 + new fields at the end
{
    // ---- version 1: never change these ----
    std::uint32_t magic, version, size;
    std::atomic<std::uint32_t> sequence;
    std::uint64_t frame;
    float frameMs;
    std::int32_t floor, playerX, playerY, playerHp, playerMaxHp, monstersAlive;
    std::uint32_t turn;
    // ---- added in version 2 ----
    std::uint32_t features;       // capability flags, below
    float cpuMs;                  // time spent in update
    std::int32_t itemsOnFloor;
};

Removing a field becomes "stop updating it" (leave it in place, write 0), never actually deleting it.

Rule 2: the size field tells the reader what exists

The header's size is the size of the struct the writer used. A reader then knows exactly which fields are present:

  • A field whose end offset is within size exists and is valid.
  • A field beyond size does not exist in this game: show "not available".
C++
bool has(const TelemetryHeader& h, std::size_t fieldOffset, std::size_t fieldSize)
{
    return fieldOffset + fieldSize <= h.size;
}
// has(header, offsetof(TelemetryV2, cpuMs), sizeof(float))  -> is CPU time published?

The reader copies min(h.size, sizeof(its own struct)) bytes and zero-fills the rest, so an old tool reading a new game copies only what it knows, and a new tool reading an old game gets zeros it knows not to trust.

Rule 3: major and minor versions

Some changes cannot be made compatible (a field's meaning changes, units change from pixels to tiles). Split the version into major and minor:

Change Version
Fields added at the end Minor + 1: compatible, nothing breaks
Meaning or layout of existing data changed Major + 1: incompatible; tools for the old major must refuse

A tool accepts any minor version of the majors it supports, and clearly reports "this game uses telemetry format 3.x; this tool supports 2.x" otherwise. The practice task implements this decision.

Rule 4: feature flags for optional things

Not everything is "present or not" by version. A features bit field (lesson 1.02's bits) says which optional parts the game actually provides right now: 0x1 "AI debug data", 0x2 "physics counters". Tools show panels only for set flags. It also lets a shipping build publish less than a development build of the same version.

Messages on pipes

The same rules apply to messages (lesson 12.01's pipes):

  • Every message starts with a type and a length, so a reader can skip types it does not know.
  • New message types get new numbers; old numbers are never reused for different meanings.
  • On connecting, each side sends a hello with its version and features, and both use the common subset.

Common mistakes

Inserting a field in the middle "where it belongs"

Every later field moves, and every older tool misreads them. Append.

Reading fields beyond the writer's size

They contain whatever is in memory there, or nothing. Check against size.

Silently accepting an unknown major version

Refuse with a clear message; misread data is worse than none.
