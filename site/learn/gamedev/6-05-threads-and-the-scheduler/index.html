Threads and the Scheduler

lesson 6.055 of 9 in milestone 66 min1 practice task

A thread is a path of execution with its own registers and its own stack, running inside a process and sharing everything else. The scheduler decides which threads run on which cores and for how long. This lesson creates threads with std::thread and the Windows API, splits work between them, and explains what the scheduler does with them.

What a thread has of its own

All threads of a process share its address space, its heap, its globals and its handles. Each thread has only a few things of its own:

Per thread Why
Registers, including rip and rsp So it can be paused and resumed exactly where it was
A stack (1 MB reserved by default) For its own calls and locals (lessons 1.05, 2.01)
Thread-local storage Variables declared thread_local
A thread id, a priority, a last-error value GetLastError is per thread

Because memory is shared, threads can work on the same data with no copying. That is their great advantage and, as the next lesson shows, their great danger.

Creating threads

The portable way is std::thread (or std::jthread in C++20, which joins itself automatically):

C++
#include <iostream>
#include <numeric>
#include <thread>
#include <vector>

int main()
{
    std::vector<long long> values(10'000'000);
    std::iota(values.begin(), values.end(), 1);           // 1, 2, 3, ... 10,000,000

    const unsigned parts{ 4 };
    std::vector<long long> partial(parts, 0);             // one result slot per thread: no sharing
    std::vector<std::thread> workers;
    const std::size_t chunk{ values.size() / parts };
    for (unsigned t{ 0 }; t < parts; ++t)
    {
        const std::size_t begin{ t * chunk };
        const std::size_t end{ t == parts - 1 ? values.size() : begin + chunk };
        workers.emplace_back([&values, &partial, t, begin, end] {
            long long sum{ 0 };
            for (std::size_t i{ begin }; i < end; ++i) sum += values[i];
            partial[t] = sum;
        });
    }
    for (std::thread& w : workers) w.join();              // wait for every thread to finish

    std::cout << "total " << std::accumulate(partial.begin(), partial.end(), 0LL) << '\n';
    return 0;
}
Output
total 50000005000000

The pattern is the simplest safe one: each thread works on its own slice and writes its own result slot; the main thread waits with join and combines the results. Nothing is written by two threads, so nothing needs locking.

A std::thread must be joined (waited for) or detached (left to run on its own) before it is destroyed; destroying a joinable thread calls std::terminate. std::jthread joins in its destructor, which is why it is usually the better choice.

Underneath, on Windows, std::thread calls CreateThread (through the C runtime). The direct form:

C++
DWORD WINAPI worker(void* parameter)
{
    auto* job{ static_cast<Job*>(parameter) };
    job->run();
    return 0;                                   // the thread's exit code
}

HANDLE thread{ CreateThread(nullptr, 0, &worker, &job, 0, nullptr) };
WaitForSingleObject(thread, INFINITE);          // like join()
CloseHandle(thread);

The thread function is a callback (lesson 3.04) taking one void*, through which you pass whatever the thread needs.

How many threads?

std::thread::hardware_concurrency() reports how many threads the processor can run truly at once: cores, doubled on processors with simultaneous multithreading (Hyper-Threading). Creating more threads than that for CPU-heavy work does not make it faster: the extra threads just take turns.

Games usually create a fixed set of worker threads at start-up, about one per core minus one or two, and feed them small jobs through a queue (a job system). Creating a thread costs tens of microseconds and a megabyte of address space, far too much to do per task.

The scheduler

Windows decides, many times a second, which ready thread runs on each core:

  • Each thread has a priority. The highest-priority ready threads run first.
  • Threads of equal priority take turns in time slices (quanta) of a few milliseconds.
  • A thread that waits (for input, a file, a lock, Sleep) leaves the core straight away, and another thread runs.
  • Switching from one thread to another, a context switch, saves one thread's registers and loads another's. It costs a few microseconds.
flowchart LR
    R["Ready<br/>(wants a core)"] -->|"scheduler picks it"| X["Running"]
    X -->|"time slice used up, or a higher priority thread wakes"| R
    X -->|"waits: Sleep, a lock, I/O"| W["Waiting"]
    W -->|"the thing it waited for happens"| R

Things this explains in games:

  • Sleep(1) sleeps for at least a millisecond, often up to 15.6 ms with the default timer resolution. A frame limiter built on Sleep is imprecise (chapter 10).
  • A game whose main thread spins in a busy loop takes a core at 100% for nothing.
  • Raising a thread's priority rarely helps and can starve other threads, including Windows' own; leave priorities alone unless you have measured a reason.

Common mistakes

[!warning] Destroying a std::thread without joining it The program terminates. Join it, detach it, or use std::jthread.

Capturing locals by reference in a thread that outlives them

The thread reads a dead stack frame. Join before the locals go out of scope, as the example does.

One thread per task

Creating threads is expensive. Create a few workers once and give them jobs.

[!warning] Expecting Sleep(1) to sleep for exactly one millisecond It sleeps for at least that, often much longer.

    So no two threads write the same memory, and no locking is needed Separate outputs, combined after join, is the simplest safe pattern.

    The thread leaves the core, and the scheduler runs another ready thread A waiting thread gives up the core immediately.
