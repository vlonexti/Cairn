Time Steps and Frame Rates

lesson 10.022 of 9 in milestone 105 min1 practice task

How much time does each update simulate? Using the real frame time (a variable time step) is simple but makes physics behave differently on fast and slow machines. Most games run the simulation at a fixed time step, consuming real time from an accumulator, and smooth the picture with interpolation. This lesson builds that loop and covers frame limiting and vsync.

Variable time step

The simplest loop measures how long the last frame took and updates by that much:

C++
while (running)
{
    const double now{ clock() };
    const double dt{ now - previous };
    previous = now;
    update(dt);
    render();
}

It works, and many small games use it. Its problems show up at the edges:

  • Physics depends on dt. Integrating motion in bigger steps gives different results: a jump reaches a different height at 30 fps than at 144 fps, collisions can be missed when a fast object moves past a wall in one big step ("tunnelling").
  • One slow frame (a disk read, a hitch) produces a huge dt that throws objects across the level.
  • Nothing is reproducible: the same input gives different results on different machines, which breaks replays and networked games that must agree exactly.

Fixed time step

The standard solution: the simulation always advances in the same small step (for example 1/60 s), and the loop runs as many of those steps as real time requires.

C++
#include <iostream>

int main()
{
    const double step{ 1.0 / 60.0 };            // the simulation always moves in 1/60 s steps
    double accumulator{ 0.0 };
    int updates{ 0 };

    // Real frame times, in seconds: a fast frame, normal frames, and one slow hitch.
    const double frames[]{ 0.008, 0.016, 0.017, 0.050, 0.016 };
    for (double frameTime : frames)
    {
        accumulator += frameTime;                // real time owed to the simulation
        int thisFrame{ 0 };
        while (accumulator >= step)
        {
            // update(step);                     // always the same step
            accumulator -= step;
            ++thisFrame;
        }
        updates += thisFrame;
        const double alpha{ accumulator / step };  // how far we are into the next step, 0 to 1
        std::cout << "frame of " << frameTime * 1000 << " ms: " << thisFrame << " update(s), alpha " << static_cast<int>(alpha * 100) << "%\n";
    }
    std::cout << "total updates " << updates << '\n';
    return 0;
}
Output
frame of 8 ms: 0 update(s), alpha 48%
frame of 16 ms: 1 update(s), alpha 44%
frame of 17 ms: 1 update(s), alpha 46%
frame of 50 ms: 3 update(s), alpha 46%
frame of 16 ms: 1 update(s), alpha 42%
total updates 6

Real time flows into the accumulator; the simulation takes it out in fixed bites. A fast frame may run no update at all; a slow frame runs several to catch up. The simulation always sees the same step, so it behaves identically on every machine, and with the same inputs, it produces the same results every time.

The spiral of death

If one update takes longer than step to compute, each frame owes more updates than the last, and the game grinds to a halt trying to catch up. Guard against it by capping how much time one frame may add:

C++
accumulator += std::min(frameTime, 0.25);    // never try to catch up more than a quarter of a second

The game then runs in slow motion under extreme load instead of freezing.

Interpolation: smooth pictures between steps

With a 60 Hz simulation on a 144 Hz monitor, several frames are rendered between two updates. Drawing the latest state each time would make movement stutter. Instead, keep the previous and current state of each object and draw a blend, using alpha from the loop above:

drawn position = previous + (current − previous) × alpha

What is drawn lags the simulation by up to one step (about 16 ms), which players do not notice, in exchange for perfectly smooth motion. The practice task computes these numbers.

Frame rate, vsync and limiting

Technique Effect
Vsync on The GPU waits for the monitor's refresh before showing a frame: no tearing, frame rate capped at the refresh rate, slightly more input latency
Vsync off Frames shown as soon as ready: lowest latency, possible tearing (top and bottom of the screen from different frames)
Variable refresh (G-Sync, FreeSync) The monitor refreshes when a frame is ready: no tearing, low latency
A frame limiter The game waits until a target frame time has passed: saves power and heat; must wait precisely (Sleep is coarse, lesson 6.05), typically sleeping most of the remaining time and spinning briefly at the end

Common mistakes

[!warning] Feeding a variable dt straight into physics Use a fixed step for anything that must be stable or reproducible.

No cap on the accumulator

One long stall leads to a spiral of catch-up updates.

Interpolating game logic

Interpolation is only for drawing. Game rules always use the simulated state.
