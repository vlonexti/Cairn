Instrumenting Functions in Your Own Program

lesson 13.055 of 8 in milestone 135 min1 practice task

Instrumentation means adding observation points to a program: measuring how long functions take, counting calls, recording events, letting plugins react to what happens. The cleanest way is to design the points in from the start: scoped timers, an event bus that plugins and tools subscribe to, and indirection through function pointers where behaviour should be replaceable. This lesson builds those, and looks at compiler-assisted instrumentation for your own builds.

Observation points you design in

Code becomes observable and extensible when it announces what it does at well-chosen places. Three patterns cover nearly everything:

Pattern Use Example
Scoped timers How long did this take? PROFILE_SCOPE("ai") at the top of the AI system
Events Something happened; whoever cares can react "monster died", "level loaded", "item picked up"
Replaceable functions Let a plugin or test change one behaviour A damage formula stored in a function pointer the plugin can replace

Scoped timers

Lesson 8.08's ScopedTimer, wrapped in a macro so it can be compiled out:

C++
#ifdef DELVE_PROFILE
#  define PROFILE_SCOPE(name) ProfileScope profileScope_##__LINE__{ name }
#else
#  define PROFILE_SCOPE(name) ((void)0)
#endif

void updateMonsters(World& w)
{
    PROFILE_SCOPE("monsters");
    // ...
}

Each ProfileScope records a start and end time into a per-thread buffer; once a frame the samples are summarised (lesson 8.08's practice task) and published through the telemetry channel (lesson 12.04), where the stats panel graphs them. That is a complete profiling pipeline built from this course's pieces.

An event bus

Hard-wiring "when a monster dies, update the quest, play a sound, drop loot, notify plugins" into the combat code makes it grow without end. An event bus decouples them: the combat code publishes "monster died", and any number of systems, plugins and tools subscribe to it.

flowchart LR
    C["Combat system"] -->|"publish('monster_died', id)"| B["Event bus"]
    B --> Q["Quest system"]
    B --> S["Sound system"]
    B --> L["Loot drops"]
    B --> P["Plugins (lesson 13.03's subscribe)"]
    B --> T["Telemetry / logging"]

Design details that matter:

  • Subscriptions return a handle used to unsubscribe, which is essential for plugins being unloaded (lesson 13.04).
  • Priorities decide the order handlers run in, when it matters (the quest system before the "you win" check).
  • Unsubscribing during dispatch (a handler that removes itself) must be safe: mark the handler removed and clean up after the dispatch finishes, rather than erasing from the list being iterated (lesson 3.07).
  • A handler that throws must not stop the others, and must be reported (lesson 13.07).

The practice task builds this bus.

Replaceable functions

Where you want behaviour to be swappable, put a function pointer at the decision point, with a default:

C++
using DamageFn = int (*)(const Attack&, const Defence&, Random&);
DamageFn g_damageFormula{ &defaultDamage };        // plugins may set this through the host API

int resolveHit(const Attack& a, const Defence& d, Random& rng) { return g_damageFormula(a, d, rng); }

Tests use the same indirection to substitute a fixed formula. It costs one indirect call (lesson 3.04), which is nothing outside the hottest loops.

Compiler-assisted instrumentation

For deeper investigation of your own builds, MSVC can insert a call at the start and end of every function: compile with /Gh (calls a function named _penter on entry) and /GH (_pexit on exit), which you write yourself, for example to record a call trace or count calls per function. It slows the program considerably, so it belongs in a special build configuration, but it instruments every function without touching the source.

For instrumenting functions of your own program at run time in test builds, Microsoft's open-source Detours library intercepts calls to chosen functions (including Windows API functions your program calls) and redirects them to your own code, which can record the call and pass it on. It is useful for testing how your program behaves when, say, file writes fail. As with the rest of this chapter, it is for your own programs and your own test builds.

Common mistakes

Hard-coding every reaction at the source of an event

Publish events and let systems subscribe; the source stays small.

Erasing handlers while dispatching

Mark them and remove them after the dispatch.

Leaving profiling in shipping builds by accident

Compile it out with a macro.
