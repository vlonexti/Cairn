Levels and Saving

lesson 11.066 of 8 in milestone 115 min1 practice task

Delve gets several floors connected by stairs, and the ability to save and continue. This lesson handles level transitions (what persists between floors and what is rebuilt), designs Delve's save format using lesson 10.07's header, version and checksum, and writes it safely, so a crash or power cut never costs the player their run.

Moving between floors

When the player steps onto the stairs (lesson 11.03's Descend), the game:

  1. Keeps what belongs to the player: health, inventory, experience.
  2. Discards everything belonging to the old floor: its map, monsters, items on the ground, its distance map.
  3. Loads the next level file (lesson 11.02) and spawns its monsters.
  4. Places the player at the new level's start and shows "Floor 2" in the message log.

Making that split explicit (a PlayerState that survives levels, a FloorState that does not) keeps the transition simple and is exactly the line the save format follows.

C++
struct PlayerState
{
    int health{ 20 }, maxHealth{ 20 };
    int power{ 3 }, armour{ 1 };
    Inventory inventory{ 10, itemStackLimits() };
};

struct FloorState
{
    int floor{ 1 };
    TileMap map;
    std::vector<MonsterInstance> monsters;      // kind, position, health, AI state
    std::vector<ItemOnFloor> items;
    std::vector<bool> openedDoors;
};

What a Delve save contains

Lesson 10.07's principle: save the minimum from which everything else can be rebuilt.

Saved Rebuilt on load
The floor number The map: reload data/levels/NN.txt
Changes to the map: doors opened Distance maps, rendering state
Each surviving monster: kind, position, health, state Monster stats: from monsters.ini by kind
Items on the floor: id, count, position Item names and effects: from items.ini by id
The player's position, health and inventory
The random generator's state

Saving the random generator's state means a reloaded game continues exactly as it would have, which makes bugs that happen after loading reproducible.

The format

A text body inside lesson 10.07's binary header is a practical choice: easy to read while developing, protected by the checksum.

Output
SAVE  version 1  length 214  crc 0x9A3C11F0         (16-byte binary header)
floor 2
player 7 4 hp 14 20 power 4 armour 1
inv potion 3
inv dagger 1
door 12 5
monster g 9 4 hp 6 chasing
monster g 15 2 hp 9 idle
item gold 40 3 7
rng 2463534242

Each line starts with a keyword, so loading is a loop over lines with a switch on the first word, and an old save missing a newer keyword still loads with defaults. The version in the header decides which keywords exist (lesson 10.07's migrations).

Saving safely

Following lesson 5.04:

  1. Build the whole save in memory as a string.
  2. Compute the CRC-32 (lesson 10.07) and write the header and body to slot1.sav.tmp in the Saved Games folder.
  3. Flush and close it, then replace slot1.sav with it atomically, keeping the previous file as slot1.sav.bak.

On loading, check the magic, the version and the checksum before reading a single line; if anything fails, offer the backup.

Delve saves automatically on each new floor and when quitting, so a run can always be continued, and the practice task writes the save and load of the player's part.

Common mistakes

Saving the level map wholesale

The map comes from the level file; save only what changed (opened doors).

Forgetting the random generator's state

A reloaded game then diverges from the original, and bugs after loading cannot be reproduced.

Saving during a monster's turn

Save only between turns, when the state is consistent.
