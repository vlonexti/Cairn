How Structs and Classes Are Laid Out

lesson 2.066 of 11 in milestone 27 min1 practice task

A class in memory is only its data members, laid out by the alignment rules. Member functions, static members and access specifiers take no space in the object. Inheritance puts the base class's members first, and a class with virtual functions gains a hidden pointer at the front. Knowing this lets you read any object's bytes in a debugger.

What is, and is not, inside an object

Here is a class that looks large:

C++
#include <iostream>
#include <string>

class Character
{
public:
    static int s_count;                 // one shared copy, in static storage

    Character(int hp, float x, float y) : m_health{ hp }, m_x{ x }, m_y{ y } { ++s_count; }

    void move(float dx, float dy) { m_x += dx; m_y += dy; }
    int health() const { return m_health; }
    bool alive() const { return m_health > 0; }

private:
    int m_health;
    float m_x;
    float m_y;
};

int Character::s_count{ 0 };

int main()
{
    Character hero{ 100, 2.0f, 3.5f };
    hero.move(1.0f, 0.0f);
    std::cout << "sizeof(Character) = " << sizeof(Character) << '\n';
    std::cout << "characters made   = " << Character::s_count << '\n';
    return 0;
}
Output
sizeof(Character) = 12
characters made   = 1

Twelve bytes: just m_health, m_x and m_y. The rest is not stored in objects at all:

Part of the class Where it lives
Non-static data members In every object, laid out by the rules of lesson 2.05
Member functions Once, in the program's .text section, like any function
static data members Once, in static storage (lesson 2.03)
public, private, protected Nowhere. They are checked by the compiler and leave no trace in the program

How does move know which object to change, then? It receives the object's address as a hidden first argument called this. hero.move(1.0f, 0.0f) compiles to roughly Character::move(&hero, 1.0f, 0.0f), and inside, m_x means this->m_x: "the float 4 bytes after the address in this". On x64 Windows, this arrives in rcx like any first argument. You will see this in chapter 7.

struct and class are the same thing

The only difference between struct and class is the default access: public for struct, private for class. Their layout rules are identical. This course uses struct for plain bundles of data and class for types that guard their data, but the memory looks the same.

Inheritance: the base comes first

A derived class contains a complete copy of its base class's members, called the base subobject, at the start, followed by its own members.

C++
#include <cstdint>
#include <iostream>

struct Entity
{
    int id;
    float x, y;
};

struct Monster : Entity
{
    int health;
    std::uint8_t level;
};

template <typename T, typename M>
std::ptrdiff_t offsetIn(const T& object, const M& member)
{
    return reinterpret_cast<const char*>(&member) - reinterpret_cast<const char*>(&object);
}

int main()
{
    Monster m{};
    std::cout << "id     " << offsetIn(m, m.id) << '\n';
    std::cout << "x      " << offsetIn(m, m.x) << '\n';
    std::cout << "y      " << offsetIn(m, m.y) << '\n';
    std::cout << "health " << offsetIn(m, m.health) << '\n';
    std::cout << "level  " << offsetIn(m, m.level) << '\n';
    std::cout << "size   " << sizeof(Monster) << '\n';

    Entity* asEntity{ &m };   // a Monster* converts to an Entity* with no adjustment
    std::cout << "same address: " << (static_cast<void*>(asEntity) == static_cast<void*>(&m)) << '\n';
    return 0;
}
Output
id     0
x      4
y      8
health 12
level  16
size   20
same address: 1

Because the Entity part sits at offset 0, a Monster* and the Entity* made from it hold the same address. Code that only knows about Entity can work with a Monster without knowing anything else about it. That is what makes inheritance-based designs work at the machine level.

With multiple inheritance, each base gets its own region, one after the other. Converting to the second base then changes the address: the compiler adds that base's offset. It is one reason game code tends to avoid deep or multiple inheritance.

Virtual functions add a hidden pointer

As soon as a class has a virtual function, every object of it carries one extra hidden member: a pointer, called the vptr, at offset 0. It points to a table of function addresses for that object's actual type, the vtable. Lesson 3.05 is about exactly this; for now, watch the size change:

C++
#include <iostream>

struct Plain
{
    int health;
    void hurt(int n) { health -= n; }
};

struct WithVirtual
{
    int health;
    virtual void hurt(int n) { health -= n; }
    virtual ~WithVirtual() = default;
};

int main()
{
    std::cout << sizeof(Plain) << ' ' << sizeof(WithVirtual) << '\n';
    return 0;
}
Output
4 16

Eight bytes for the vptr, then the int, then 4 bytes of tail padding to keep the size a multiple of 8. If you look at an object of a class with virtual functions in the Memory window, its first 8 bytes always look like an address inside the program's image: that is the vptr.

Empty classes

A class with no data members still has sizeof 1, because every object must have a distinct address. But when an empty class is used as a base, the compiler may give it no space at all (the empty base optimisation). Since C++20, the attribute [[no_unique_address]] (spelled [[msvc::no_unique_address]] for MSVC) lets an empty member take no space either.

Reading an object in the debugger

Put it together and you can decode objects by hand. Suppose a Monster from above shows this in the Memory window:

Output
07 00 00 00  00 00 20 41  00 00 a0 c0  3c 00 00 00  05 cc cc cc
Bytes Member Value
07 00 00 00 id 7
00 00 20 41 x 10.0 (the bit pattern of a float; lesson 2.11)
00 00 a0 c0 y −5.0
3c 00 00 00 health 60
05 level 5
cc cc cc tail padding (Debug fill)

This is the core skill behind using memory views, and later behind chapter 9's work of reconstructing the layout of a type from compiled code.

Common mistakes

Thinking member functions make objects bigger

They do not. Only data members (and a vptr, if there are virtual functions) take space.

[!warning] Assuming private members are protected at run time Access control is a compile-time rule. In memory, private members are bytes like any others.

Writing an object with virtual functions to a file

Its first 8 bytes are a pointer that will be wrong the next time the program runs. Save the data members, not the raw object.

    At the start of the derived object, at offset 0 for a single base The base's members come first, so a pointer to the derived object is also a valid pointer to its base.
