Imports, Exports and the Loader

lesson 9.033 of 10 in milestone 96 min1 practice task

A program's import table lists every function it uses from DLLs; a DLL's export table lists every function it offers. Together they are a map of what a program can do and how its modules connect. This lesson reads both, explains the import address table that the loader fills in at start-up, and shows how to convert RVAs to file offsets so tables can be read from a file on disk.

Why imports matter so much

For a reverse engineer, the import table is often the most informative part of a program. A program that imports CreateFileW, ReadFile and CryptDecrypt reads and decrypts files; one importing WSAStartup and send uses the network; one importing CreateWindowExW has a window. Before reading a single instruction, the imports outline what the program does. Tools list them first for this reason:

Terminal
dumpbin /imports game.exe
dumpbin /exports plugin.dll

The import table

Data directory 1 (lesson 9.02) points at an array of import descriptors, one per DLL, ending with an all-zero entry:

Field Meaning
Name RVA of the DLL's name, such as "KERNEL32.dll"
OriginalFirstThunk RVA of the import lookup table: what to import
FirstThunk RVA of the import address table (IAT): where the addresses go

Each lookup table entry is 8 bytes. If the top bit is set, the function is imported by ordinal (a number); otherwise the entry is the RVA of a hint/name entry: a 2-byte hint followed by the function's name, "CreateFileW\0".

flowchart LR
    D["Import descriptor<br/>KERNEL32.dll"] --> ILT["Lookup table<br/>→ 'CreateFileW'<br/>→ 'ReadFile'<br/>→ 0"]
    D --> IAT["Import address table<br/>(on disk: same as lookup table)<br/>(after loading: real addresses)"]
    IAT --> K["kernel32!CreateFileW<br/>kernel32!ReadFile"]

What the loader does

When the program starts (lesson 1.06), the loader, for each import descriptor:

  1. loads the DLL (finding it by the search order, lesson 5.08) if it is not already loaded;
  2. for each function in the lookup table, finds its address in the DLL's export table;
  3. writes that address into the corresponding slot of the IAT.

The program's code never contains the address of CreateFileW itself. Every call to an imported function goes through the IAT:

Assembly
call  qword ptr [__imp_CreateFileW]     ; read the address from the IAT slot, then call it

So in disassembly, calls to imported functions are indirect calls through a fixed set of memory slots, and disassemblers label them with the function names, which makes them easy landmarks. After loading, the IAT is made read-only, so it cannot be changed by accident.

The export table

A DLL's data directory 0 points at its export directory, which holds three parallel arrays:

Array Holds
AddressOfFunctions RVAs of the exported functions, indexed by ordinal minus the base
AddressOfNames RVAs of the exported names, sorted alphabetically so they can be binary-searched
AddressOfNameOrdinals For each name, the index into the functions array

GetProcAddress(module, "scaleDamage") (lesson 4.05) binary-searches the names, takes the matching ordinal index, and returns module + AddressOfFunctions[index].

An export can also be forwarded: its "address" points at a string such as "NTDLL.RtlAllocateHeap", meaning "this function really lives in another DLL". Many kernel32.dll exports are forwarders.

RVA to file offset

All these tables use RVAs, which are offsets in memory. To read them from the file on disk, convert each RVA through the section table (lesson 9.02): find the section whose range contains the RVA, then

file offset = RVA − section.VirtualAddress + section.PointerToRawData

because a section's bytes are at VirtualAddress in memory and at PointerToRawData in the file. An RVA that falls in no section's file data (for example in zero-filled .bss space) has no file offset. The practice task writes this function; every PE tool has it at its core.

Reading your own imports at run time

A loaded module's tables are already in memory at module + RVA, with no conversion needed:

C++
#include <windows.h>
#include <iostream>
#include <string>

int main()
{
    auto* base{ reinterpret_cast<unsigned char*>(GetModuleHandleW(nullptr)) };
    const auto* nt{ reinterpret_cast<IMAGE_NT_HEADERS64*>(base + reinterpret_cast<IMAGE_DOS_HEADER*>(base)->e_lfanew) };
    const IMAGE_DATA_DIRECTORY dir{ nt->OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_IMPORT] };

    bool importsKernel32{ false };
    int dlls{ 0 };
    for (auto* d{ reinterpret_cast<IMAGE_IMPORT_DESCRIPTOR*>(base + dir.VirtualAddress) }; d->Name != 0; ++d)
    {
        ++dlls;
        std::string name{ reinterpret_cast<const char*>(base + d->Name) };
        if (_stricmp(name.c_str(), "KERNEL32.dll") == 0) importsKernel32 = true;
    }
    std::cout << "imports from several DLLs: " << (dlls >= 1 ? "yes" : "no") << ", including KERNEL32.dll: " << (importsKernel32 ? "yes" : "no") << '\n';
    return 0;
}
Output
imports from several DLLs: yes, including KERNEL32.dll: yes

Delay-load and dynamic imports

Not every DLL a program uses appears in its import table. Delay-loaded DLLs (lesson 5.08) have their own table (data directory 13), and anything loaded with LoadLibraryW and GetProcAddress at run time appears only as strings in the program, which is why reverse engineers search for DLL and function names among a program's strings (lesson 9.06) as well as reading the import table.

Common mistakes

Reading table RVAs as file offsets

Convert through the section table first, or the tables will appear to contain garbage.

Assuming every import is by name

Entries with the top bit set are imported by ordinal; there is no name to read.

Concluding a program never uses a function because it is not imported

It may be loaded at run time with GetProcAddress.
