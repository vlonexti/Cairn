Errors, GetLastError and Reading the Documentation

lesson 5.022 of 9 in milestone 56 min1 practice task

The Windows API reports failure in several ways: a BOOL that is FALSE, a null or invalid handle, an HRESULT, or a status code. The details usually come from GetLastError. This lesson shows each pattern, how to turn an error number into a readable message, how HRESULTs are built, and how to read a Microsoft documentation page so you know which pattern a function uses.

Three patterns

1. BOOL plus GetLastError. Many functions return BOOL (an int): non-zero for success, FALSE (0) for failure. On failure, the reason is a number kept per thread, fetched with GetLastError().

C++
#include <windows.h>
#include <iostream>

int main()
{
    if (!DeleteFileW(L"C:\\this\\file\\does\\not\\exist.txt"))
    {
        const DWORD error{ GetLastError() };     // read it straight away
        std::cout << "DeleteFileW failed with error " << error << '\n';
    }
    return 0;
}
Output
DeleteFileW failed with error 3

Error 3 is ERROR_PATH_NOT_FOUND. GetLastError must be called immediately: almost any later API call, including some done inside std::cout, may overwrite it.

2. Handles plus GetLastError. Creation functions return nullptr or INVALID_HANDLE_VALUE (lesson 5.01), and again GetLastError says why.

3. HRESULT. COM-based APIs (DirectX, the Windows shell, audio) return an HRESULT directly: a 32-bit code where negative means failure. Test them with the SUCCEEDED(hr) and FAILED(hr) macros, never with == 0 or != 0, since some success codes are not zero.

Turning a number into a message

FormatMessageW looks up the text Windows has for an error code, in the user's language:

C++
#include <windows.h>
#include <iostream>
#include <string>

std::wstring describeError(DWORD error)
{
    wchar_t* buffer{ nullptr };
    const DWORD length{ FormatMessageW(
        FORMAT_MESSAGE_ALLOCATE_BUFFER | FORMAT_MESSAGE_FROM_SYSTEM | FORMAT_MESSAGE_IGNORE_INSERTS,
        nullptr, error, 0, reinterpret_cast<wchar_t*>(&buffer), 0, nullptr) };
    std::wstring text{ length ? std::wstring(buffer, length) : L"unknown error" };
    LocalFree(buffer);                                    // FormatMessage allocated it
    while (!text.empty() && (text.back() == L'\n' || text.back() == L'\r')) text.pop_back();
    return text;
}

int main()
{
    HANDLE file{ CreateFileW(L"no_such_save.dat", GENERIC_READ, 0, nullptr, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, nullptr) };
    if (file == INVALID_HANDLE_VALUE)
    {
        const DWORD error{ GetLastError() };
        std::wcout << L"error " << error << L": " << describeError(error) << L'\n';
    }
    else CloseHandle(file);
    return 0;
}
Output
error 2: The system cannot find the file specified.

The ones you will meet most:

Code Name Meaning
2 ERROR_FILE_NOT_FOUND No such file
3 ERROR_PATH_NOT_FOUND A folder in the path does not exist
5 ERROR_ACCESS_DENIED You do not have the rights (lesson 6.08)
6 ERROR_INVALID_HANDLE A closed or wrong handle
32 ERROR_SHARING_VIOLATION Another program has the file open without sharing
87 ERROR_INVALID_PARAMETER An argument is wrong
122 ERROR_INSUFFICIENT_BUFFER The buffer you passed is too small: call again with a bigger one
126 ERROR_MOD_NOT_FOUND LoadLibrary could not find the DLL or one it depends on

In the debugger, $err,hr in the Watch window shows the current value with its name (lesson 4.08), and Tools → Error Lookup decodes any number.

Inside an HRESULT

An HRESULT packs three fields into 32 bits:

 31  30..27   26..16          15..0
┌───┬───────┬───────────────┬────────────────┐
│ S │ flags │ facility (11) │ code (16)      │
└───┴───────┴───────────────┴────────────────┘
S = 1: failure (so failures are negative as signed ints)
  • Severity (bit 31): 1 is failure.
  • Facility: which subsystem the code comes from, such as FACILITY_WIN32 (7) or FACILITY_DXGI.
  • Code: the error number within that facility.

A Win32 error code can be wrapped as an HRESULT with HRESULT_FROM_WIN32(error): error 2 becomes 0x80070002. You will recognise that shape everywhere: 0x8007xxxx is "a Win32 error, number xxxx".

Reading a documentation page

Every function's page on Microsoft's site (search "CreateFileW function") has the same sections, and each answers a question you must ask:

Section Answers
Syntax The exact declaration, parameter types and annotations such as [in], [out], [in, optional]
Parameters What each one means, what values are allowed, and whether null is accepted
Return value What success and failure look like, and whether to call GetLastError
Remarks The important details: threading rules, ownership of buffers, what to free and with what, common traps
Requirements Which header to include, which .lib to link, which DLL implements it, and the oldest Windows version

The Return value and Remarks sections are where most bugs are prevented. For example, CreateFileW's Return value section says it returns INVALID_HANDLE_VALUE on failure; ReadFile's Remarks explain when it can succeed but read fewer bytes than asked.

Many functions also follow a two-call pattern for variable-sized results: call once with a null or small buffer to learn the size needed (often failing with ERROR_INSUFFICIENT_BUFFER), allocate, then call again.

Common mistakes

[!warning] Calling GetLastError too late Store it in a variable on the very next line after the failing call.

[!warning] Calling GetLastError after success Its value is only meaningful when the function reported failure. Some functions leave an old value there on success.

[!warning] Testing an HRESULT with if (hr) S_FALSE is 1 and means success. Use SUCCEEDED and FAILED.

    • Check errno

  2. What does 0x80070005 mean?

    • Memory address 0x80070005

    A failure HRESULT wrapping Win32 error 5, access denied Severity bit set, facility 7 (Win32), code 5.

  3. Which section of a documentation page says whether to call GetLastError?
    • Syntax
    • Return value
    • Requirements
    Show the answer

    Return value It describes what success and failure look like for that particular function.

  4. Why use FAILED(hr) instead of hr != 0?
    • Some success codes, such as S_FALSE, are not zero
    • HRESULT values are always negative
    • The comparison does not compile
    Show the answer

    Some success codes, such as S_FALSE, are not zero Only the severity bit separates success from failure.
