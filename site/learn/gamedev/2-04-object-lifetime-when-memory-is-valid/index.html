Object Lifetime: When Memory Is Valid

lesson 2.044 of 11 in milestone 27 min1 practice task

An object's lifetime runs from the end of its construction to the start of its destruction. Outside that window its memory may still be there, but using it is a bug. This lesson traces lifetimes for locals, temporaries, heap objects and members, and introduces RAII: tying every resource to an object's lifetime so it is released automatically.

Memory and objects are not the same thing

Memory is bytes at an address. An object is a value of some type that lives in those bytes for a while. The two have separate lives:

  • The memory can exist before the object is created in it (a stack frame is set up before its locals are constructed).
  • The memory can exist after the object is gone (a freed heap block is still mapped; a returned function's frame is still part of the stack).

An object's lifetime starts when its constructor finishes and ends when its destructor starts. C++ only promises anything about an object during its lifetime. Reading or writing it outside that window is undefined behaviour, even if the bytes are still there.

Watching constructors and destructors

The clearest way to see lifetimes is a type that announces itself.

C++
#include <iostream>
#include <string>

struct Noisy
{
    std::string name;
    explicit Noisy(std::string n) : name{ std::move(n) } { std::cout << "  + " << name << '\n'; }
    ~Noisy() { std::cout << "  - " << name << '\n'; }
};

Noisy g_global{ "global" };

void level()
{
    std::cout << "level starts\n";
    Noisy a{ "a" };
    {
        Noisy b{ "b" };
        std::cout << "inner block ends\n";
    }
    Noisy c{ "c" };
    std::cout << "level ends\n";
}

int main()
{
    std::cout << "main starts\n";
    level();
    Noisy* boss{ new Noisy{ "boss" } };
    delete boss;
    std::cout << "main ends\n";
    return 0;
}
Output
  + global
main starts
level starts
  + a
  + b
inner block ends
  - b
  + c
level ends
  - c
  - a
  + boss
  - boss
main ends
  - global

Read it carefully. Every rule of object lifetime is in that output:

Kind of object Lifetime starts Lifetime ends
Global Before main After main returns
Local At its declaration At the end of the enclosing block { }
Several locals in one block In declaration order In reverse order: c before a
Heap object At new At delete

The reverse order matters: c was created after a and might depend on it, so it is destroyed first.

Temporaries

A temporary is an unnamed object created in the middle of an expression, such as the result of std::string("Lv") + "1". It lives until the end of the full expression: roughly, until the next semicolon.

C++
#include <iostream>
#include <string>

std::string levelName(int n) { return "Level " + std::to_string(n); }

int main()
{
    std::cout << levelName(3) << '\n';              // fine: used within the same expression

    const char* text{ levelName(4).c_str() };       // the string dies at the semicolon...
    // ...so text now points into freed memory. Using it here would be a bug.

    const std::string& kept{ levelName(5) };         // a const reference extends the temporary's life
    std::cout << kept << '\n';
    return 0;
}
Output
Level 3
Level 5

The middle line is a classic: c_str() returns a pointer into the string's buffer, and the string is a temporary destroyed at the end of the line. The pointer survives; the characters do not. Binding the temporary to a const reference, as on the third line, keeps it alive as long as the reference, but only in that direct form.

Lifetime bugs in real code

These are the shapes lifetime bugs take. Each compiles. Each "works" sometimes.

C++
#include <string>
#include <string_view>
#include <vector>

struct Enemy { int health; };

int* dangling()
{
    int local{ 5 };
    return &local;                 // 1. address of a local that is about to die
}

std::string_view nameView()
{
    std::string name{ "Grim" };
    return name;                   // 2. a view of a string that is about to die
}

void invalidated(std::vector<Enemy>& enemies)
{
    Enemy& first{ enemies[0] };
    enemies.push_back(Enemy{ 10 }); // 3. may move every element to a new block...
    first.health = 0;              //    ...so first may refer to freed memory
}

The third one deserves attention because it involves no delete at all. When a std::vector runs out of capacity, it allocates a bigger block, moves the elements across and frees the old block. Every pointer, reference and iterator into the old block is now dangling. Lesson 3.07 shows exactly when this happens.

RAII: let lifetimes do the cleaning up

Destructors run automatically and reliably: at the end of a block, on return, and when an exception passes through. C++ uses this to manage every kind of resource, not just memory. The idea is called RAII (Resource Acquisition Is Initialisation), and it is simple:

  1. Acquire the resource in a constructor.
  2. Release it in the destructor.
  3. Hold the object by value (as a local or a member), so its lifetime is the resource's lifetime.
Resource RAII type
Heap memory std::unique_ptr, std::vector, std::string
A file std::ifstream, std::ofstream
A lock std::lock_guard, std::scoped_lock
A Windows handle A small class of your own that calls CloseHandle (chapter 5)
"Undo this change when I'm done" A small class of your own, as in the practice task
C++
#include <iostream>

class ScopedTimerName
{
public:
    explicit ScopedTimerName(const char* name) : m_name{ name } { std::cout << "begin " << m_name << '\n'; }
    ~ScopedTimerName() { std::cout << "end " << m_name << '\n'; }
private:
    const char* m_name;
};

int loadLevel(bool fail)
{
    ScopedTimerName scope{ "loadLevel" };
    if (fail) return -1;        // the destructor still runs
    return 1;
}

int main()
{
    loadLevel(true);
    loadLevel(false);
    return 0;
}
Output
begin loadLevel
end loadLevel
begin loadLevel
end loadLevel

Whichever way loadLevel leaves, "end" is printed. Code written in this style cannot forget to clean up, because there is no cleanup code to forget.

Common mistakes

[!warning] Keeping c_str(), data() or a string_view of a temporary The pointer outlives the string. Keep the std::string itself if you need the text later.

Holding a reference into a vector while adding to it

push_back, insert, resize and reserve can move every element. Store indices instead, or re-read the reference after the change.

Manual cleanup at the end of a function

An early return or an exception skips it. Put the cleanup in a destructor.

Capturing locals by reference in a lambda that outlives them

A callback stored for later that captured [&] refers to locals of a function that has long since returned.
