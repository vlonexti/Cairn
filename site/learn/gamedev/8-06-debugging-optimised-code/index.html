Debugging Optimised Code

lesson 8.066 of 8 in milestone 86 min

Some bugs only appear in Release builds, and crash dumps from players are always from optimised code. Debugging it is harder (variables vanish, lines run out of order, functions disappear into their callers) but entirely possible. This lesson gives a practical toolkit: make Release builds debuggable, read values from registers and the disassembly, switch optimisation off selectively, and use logging where stepping fails.

What goes wrong in the debugger

Lesson 4.10 explained what the optimiser does; here is what that looks like when you debug:

Symptom Cause
"Variable is optimised away and not available" It lives only in a register, which has since been reused, or it was removed
The yellow arrow jumps backwards and forwards Instructions from different lines were interleaved
A breakpoint in a function never hits The function was inlined into its callers
A function is missing from the call stack Inlined, or left by a tail call (lesson 7.11)
Locals show wrong values The debugger reads a stack slot the optimised code no longer uses

None of this means the debugger is broken. It means the source is only an approximation of what runs, and you sometimes have to look at what really runs.

Make Release builds debuggable

These settings cost nothing at run time and should be on for every Release build:

Setting Effect
C/C++ → General → Debug Information Format: /Zi Writes a full PDB for Release
Linker → Debugging → Generate Debug Info: /DEBUG Links the PDB
C/C++ → Command Line: /Zo (default in recent versions) Records which register each variable is in at each point, so more locals are visible
Linker → Optimization → /OPT:REF, /OPT:ICF (keep them) Unaffected; note that ICF can merge identical functions, so a call stack may show a different name with the same body

Reading values the debugger cannot show

When a variable is "optimised away", the value usually still exists somewhere:

  1. Open the Disassembly window (Ctrl+Alt+D) at the current instruction.
  2. Find the instruction that last loaded or computed the value. mov ebx, dword ptr [rcx+0Ch] tells you ebx holds the member at offset 12 of whatever rcx pointed to.
  3. Read the register in the Registers window, or in Watch as @ebx.
  4. For objects, cast a register in Watch: (Player*)@rdi.

Function arguments are in rcx, rdx, r8, r9 only at the very start of a function (lesson 7.06); optimised code moves them into non-volatile registers or overwrites them soon after. Set the breakpoint on the function's first instruction (right-click → Go To Disassembly, F9 on the first line) to catch them in place.

Turn optimisation off where you are looking

When you need to step through one area of a Release build comfortably:

C++
#pragma optimize("", off)
void Inventory::recalculate()
{
    // compiled without optimisation in an otherwise optimised build
}
#pragma optimize("", on)

Or disable it for a whole .cpp file: right-click the file → Properties → C/C++ → Optimization: Disabled (/Od). Remember to remove these: they are debugging aids, not fixes. If the bug disappears when optimisation is turned off in one place, that is itself a strong clue: undefined behaviour (uninitialised values, overruns, data races, lesson 4.10) in or near that code.

Logging and asserts in Release

Stepping is often impractical in timing-sensitive or rare bugs. Use the tools from lesson 8.03, kept enabled in a test configuration:

  • a ring-buffer log dumped on crash;
  • asserts enabled in an "optimised with checks" configuration;
  • tracepoints (lesson 4.09), which work in optimised code at instruction level.

Bugs that only appear in Release

A checklist, roughly in order of how often each is the cause:

  1. Uninitialised variables: Debug's 0xCC fill was consistent; Release's garbage is not. Turn on warning level 4 (C4700, C4701).
  2. Out-of-bounds access: Debug's padding and guard bytes absorbed it. Run AddressSanitizer (lesson 2.10).
  3. Data races: Release keeps values in registers and reorders memory accesses (lesson 6.06).
  4. Code inside assert that no longer runs.
  5. Timing: Release runs faster, changing the order of events between threads or frames.
  6. Signed overflow or other undefined behaviour the optimiser exploited.
  7. A compiler bug: possible, but almost always the last explanation, after everything above.

Common mistakes

Giving up when a variable is optimised away

Look at the disassembly: the value is usually in a register.

Fixing a Release-only bug by turning optimisation off

That hides it. Find the undefined behaviour.

Trusting the source view's line in optimised code

Check the Disassembly window to see which instruction actually faulted.
