Writing Assembly Functions with MASM

lesson 7.1010 of 11 in milestone 75 min

Microsoft's assembler, MASM (ml64.exe), ships with Visual Studio. This lesson writes a few functions in assembly, adds them to a C++ project, and calls them from C++, following the calling convention by hand. Writing even a little assembly makes reading it much easier, and shows exactly what the compiler does for you.

When to write assembly

Almost never in game code. Compilers produce excellent code, and intrinsics (lesson 7.09) cover most hand-tuned SIMD. Hand-written assembly survives in a few places: the start-up code of operating systems and runtimes, a handful of instructions compilers cannot express, and teaching. 64-bit MSVC does not even support inline __asm blocks; assembly goes in separate .asm files.

We write it here to learn: every rule in this chapter must be followed by hand, and the assembler will not save you.

Setting up a project

  1. In your course solution, right-click the project → Build Dependencies → Build Customizations → tick masm.
  2. Add a new file named maths.asm (choose a C++ file and rename it). In its properties, Item Type should now be Microsoft Macro Assembler.
  3. Build: ml64.exe assembles maths.asm into maths.obj, and the linker joins it with your C++ objects like any other (lesson 4.02).

A first function

Assembly
; maths.asm: int addThree(int a, int b, int c)
.code

addThree PROC
    lea   eax, [rcx+rdx]      ; a + b        (a in ecx, b in edx)
    add   eax, r8d            ; + c          (c in r8d)
    ret                       ; result in eax
addThree ENDP

END
C++
// main.cpp
#include <iostream>

extern "C" int addThree(int a, int b, int c);   // declared in C++, defined in assembly

int main()
{
    std::cout << addThree(1, 2, 39) << '\n';
}

extern "C" matters: the assembly defines the plain name addThree, and without extern "C" the C++ side would look for the mangled ?addThree@@YAHHHH@Z and fail with LNK2019 (lesson 4.02).

A loop and a non-volatile register

Assembly
; long long sumArray(const int* values, long long count)
.code

sumArray PROC
    push  rbx                 ; we use rbx below, and it is non-volatile: save it
    xor   eax, eax            ; total = 0 (64-bit: writing eax clears the top of rax)
    xor   ebx, ebx            ; i = 0
    test  rdx, rdx
    jle   done                ; count <= 0: nothing to add
next:
    movsxd r9, dword ptr [rcx+rbx*4]   ; values[i], sign-extended to 64 bits
    add   rax, r9
    inc   rbx
    cmp   rbx, rdx
    jl    next
done:
    pop   rbx                 ; restore it before returning
    ret
sumArray ENDP

END

Nothing here needed rbx: r10 (volatile) would have done without the push and pop. Using it shows the rule: touch a non-volatile register, and you must save and restore it.

Calling C++ from assembly

Calling out is where the convention bites. Before a call, rsp must be 16-byte aligned and 32 bytes of shadow space reserved:

Assembly
; void logTwice(int value)   calls the C++ function  extern "C" void logValue(int)
EXTERN logValue:PROC

.code
logTwice PROC
    push  rbx                 ; entry: rsp was 8 off a multiple of 16; after this push it is aligned
    sub   rsp, 32             ; shadow space for the calls: still aligned (8 + 8 + 32 = 48 bytes in all)
    mov   ebx, ecx            ; keep value in a non-volatile register across the calls
    call  logValue            ; ecx still holds value
    mov   ecx, ebx            ; ecx is volatile: logValue may have changed it
    call  logValue
    add   rsp, 32
    pop   rbx
    ret
logTwice ENDP
END

The arithmetic: on entry rsp is a multiple of 16 minus 8 (the return address). push rbx subtracts 8 (now a multiple of 16), sub rsp, 32 keeps it a multiple of 16, and leaves the 32 bytes of shadow space the callee may use. Getting this wrong works most of the time and then crashes inside some library function that uses aligned SSE stores: one of the hardest bugs to trace back.

Unwind information

Functions that change rsp or save registers should, strictly, also describe their prologue to Windows with MASM's .PUSHREG, .ALLOCSTACK and .ENDPROLOG directives (using PROC FRAME), so exceptions and the debugger can walk the stack through them. For learning exercises that never throw, it can be left out; production assembly must include it.

Common mistakes

[!warning] Forgetting extern "C" The linker cannot match the assembly's plain name with a mangled C++ declaration.

Misaligned stack at a call

Count every push and sub rsp from entry: at the call, rsp must be a multiple of 16, with 32 bytes of shadow space reserved.

Keeping values in volatile registers across a call

rcx, rdx, r8 to r11 and rax may all change. Keep anything you need afterwards in a non-volatile register or on the stack.
