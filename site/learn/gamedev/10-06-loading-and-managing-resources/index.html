Loading and Managing Resources

lesson 10.066 of 9 in milestone 105 min1 practice task

Textures, sounds, models, levels and fonts are resources: large, loaded from disk, shared between many users, and expensive to load twice. A resource manager loads each one once, hands out handles to it, counts who is still using it, unloads it when nobody is, and ideally loads in the background. This lesson designs one, and covers asset pipelines and hot reloading.

What a resource manager does

Without one, every part of the game that needs goblin.png loads it itself: the same texture ends up in memory five times, loaded five times, and nobody knows when it is safe to free. A resource manager fixes that:

Job How
Load each resource once Keep a table from name (or a hash of the name, lesson 3.08) to the loaded resource
Share it Hand out handles (or reference-counted pointers) instead of copies
Know when it is unused Count references; or unload a whole level's resources together
Keep the game responsive Load in the background, show a placeholder until ready

Handles, not raw pointers

As with entities (lesson 3.10), handing out raw pointers to resources is fragile: if the resource is unloaded or reloaded, the pointer dangles. Engines hand out handles (an index and generation), and the renderer looks the resource up each time it uses it. That also makes hot reloading possible: replace the texture behind the handle, and everything using it shows the new one next frame.

Reference counting

The simplest lifetime rule: each resource counts how many users hold it. acquire increments the count (loading the resource the first time); release decrements it, and at zero the resource can be unloaded. std::shared_ptr does exactly this automatically, which makes it a reasonable first design:

C++
#include <iostream>
#include <map>
#include <memory>
#include <string>

struct Texture { std::string name; int width{ 0 }, height{ 0 }; };

class TextureCache
{
public:
    std::shared_ptr<Texture> get(const std::string& name)
    {
        if (auto existing{ m_loaded[name].lock() }) return existing;    // still alive: share it
        auto fresh{ std::make_shared<Texture>(Texture{ name, 64, 64 }) }; // "load" it
        ++m_loads;
        m_loaded[name] = fresh;                                         // remember it without owning it
        return fresh;
    }
    int loads() const { return m_loads; }
private:
    std::map<std::string, std::weak_ptr<Texture>> m_loaded;
    int m_loads{ 0 };
};

int main()
{
    TextureCache cache;
    auto a{ cache.get("goblin.png") };
    auto b{ cache.get("goblin.png") };             // the same texture, not loaded again
    std::cout << "shared: " << (a == b) << ", loads: " << cache.loads() << '\n';
    a.reset(); b.reset();                          // nobody uses it now: it is freed
    auto c{ cache.get("goblin.png") };             // so it is loaded again
    std::cout << "loads after release: " << cache.loads() << '\n';
    return 0;
}
Output
shared: 1, loads: 1
loads after release: 2

The cache holds weak_ptrs, which observe without keeping the resource alive. In practice, unloading the moment the count reaches zero causes churn (a texture unloaded and reloaded as an enemy dies and another spawns), so engines often keep unused resources for a while, or unload per level. The practice task builds an explicit reference-counted cache.

Loading without freezing

Loading a large file on the main thread stalls the game for its duration. Better:

  1. The main thread requests the resource and immediately gets a handle whose state is "loading".
  2. A worker thread (lesson 6.05) reads the file and decodes it.
  3. GPU resources must be created through the graphics API, often on the main or render thread, so the worker passes the decoded data back through a queue (lesson 6.06's job queue).
  4. Until the resource is ready, the game uses a placeholder (a grey texture, a silent sound), or the level waits behind a loading screen.

Asset pipelines

Source assets (.psd, .blend, .wav) are rarely what the game loads. An asset pipeline converts them at build time into formats that load fast: textures compressed into GPU formats with mipmaps, models flattened into vertex buffers, many small files packed into one archive with a table of contents. The game then reads exactly what it needs with almost no processing, and a level loads in a few large reads instead of thousands of small ones.

Hot reloading

During development, reloading a resource the moment its file changes (watching the folder with ReadDirectoryChangesW, then replacing the data behind the handle) lets artists and designers see changes without restarting the game. It is one of the biggest productivity features an engine can have, and handles make it straightforward.

Common mistakes

Loading the same file in several places

Go through the manager, so it is loaded once and shared.

Keeping raw pointers to resources

They dangle on unload or reload. Use handles or reference-counted pointers.

Loading synchronously in the middle of gameplay

The game freezes for the load. Preload, or load in the background with a placeholder.
