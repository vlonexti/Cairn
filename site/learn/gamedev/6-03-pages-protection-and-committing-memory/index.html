Pages, Protection and Committing Memory

lesson 6.033 of 9 in milestone 66 min1 practice task

Under the heap sits VirtualAlloc, which manages memory directly in pages. A region of the address space can be free, reserved (set aside, but with no memory behind it) or committed (backed by memory), and every committed page has a protection: readable, writable, executable, or none. This lesson uses these tools directly, and shows how games use them for huge growable arrays, guard pages and catching bugs.

Three states for every page

State Means Costs
Free Not in use; any access faults Nothing
Reserved Set aside: no other allocation will use these addresses. Still no memory behind it; any access faults Almost nothing (some bookkeeping)
Committed Backed by memory (RAM or page file). Can be accessed according to its protection Counts against the system's commit limit; RAM used once touched

VirtualAlloc moves pages between these states. Reserving is done in units of the allocation granularity, 64 KB; committing and protection work per 4 KB page.

C++
#include <windows.h>
#include <iostream>

int main()
{
    // Reserve 1 GB of address space: no memory is used yet.
    const SIZE_T reserveSize{ 1ull << 30 };
    char* base{ static_cast<char*>(VirtualAlloc(nullptr, reserveSize, MEM_RESERVE, PAGE_NOACCESS)) };
    if (!base) { std::cout << "reserve failed\n"; return 1; }

    // Commit just the first two pages, readable and writable.
    VirtualAlloc(base, 2 * 4096, MEM_COMMIT, PAGE_READWRITE);
    base[0] = 42;                         // fine: committed
    base[8191] = 7;                       // fine: last byte of the second page
    std::cout << "first byte " << static_cast<int>(base[0]) << ", committed memory starts zeroed: " << static_cast<int>(base[100]) << '\n';
    // base[8192] = 1;                    // would be an access violation: reserved, not committed

    VirtualFree(base, 0, MEM_RELEASE);    // give back the whole reservation
    return 0;
}
Output
first byte 42, committed memory starts zeroed: 0

Reserving a gigabyte took no memory at all, only addresses, which a 64-bit process has plenty of. Committed pages always start filled with zeros: Windows never hands one process another process's old data.

Protection

Every committed page carries a protection, enforced by the processor on each access:

Constant Read Write Execute Typical use
PAGE_NOACCESS Guard regions, reserved space
PAGE_READONLY ✓ Constants (.rdata)
PAGE_READWRITE ✓ ✓ Heap, stack, globals (.data)
PAGE_EXECUTE_READ ✓ ✓ Code (.text)
PAGE_EXECUTE_READWRITE ✓ ✓ ✓ Rarely legitimate: avoid

Combined with the section table of lesson 2.03, this is why writing to a string literal or to your own code crashes: those pages are mapped read-only.

VirtualProtect changes a page's protection. One legitimate use in games: make a big table read-only after loading it, so any accidental write anywhere in the program crashes immediately at the culprit, instead of silently corrupting the data.

C++
VirtualProtect(itemTable, tableBytes, PAGE_READONLY, &oldProtection);
Why writable and executable are kept apart

A page that is both writable and executable lets any bug that writes memory also plant code to run. Windows' Data Execution Prevention (DEP) makes data pages non-executable, and modern compilers, the loader and security features all assume code pages are not writable. Programs that generate code at run time (JIT compilers, emulators) write into a read-write page, then switch it to execute-read before running it, never holding both at once.

Guard pages and catching overruns

A page marked PAGE_NOACCESS placed right after a buffer turns an overrun into an immediate crash at the exact instruction, much like AddressSanitizer's red zones (lesson 2.10) but enforced by the hardware for free. Debugging tools use this idea: Windows' page heap (enabled per program with the gflags tool) places every heap allocation at the end of its own page, followed by an inaccessible page, so a write one byte past the end faults instantly.

Thread stacks use the related PAGE_GUARD flag: the page just below the stack's committed part is a guard page, and touching it commits more stack. That is how a thread's stack grows up to its reserved size, and why a stack overflow is detected: the guard page is finally hit with nothing reserved below it.

Reserve big, commit as you go

Reserving and committing separately gives a pattern games use for large, growable data: reserve the maximum size up front (say 4 GB of addresses for an asset buffer), then commit pages only as the buffer actually fills. Unlike std::vector (lesson 3.07):

  • the data never moves, so pointers into it stay valid forever;
  • growing never copies anything;
  • unused space costs no memory.

Some engines build their entity arrays and frame allocators this way.

Common mistakes

Using memory that is only reserved

Reserved pages fault on any access. Commit them first.

Freeing with the wrong size

VirtualFree(base, 0, MEM_RELEASE) releases an entire reservation; the size must be 0 and the address must be exactly what VirtualAlloc returned.

[!warning] PAGE_EXECUTE_READWRITE "to be safe" It is the opposite of safe. Use the narrowest protection that works.

[!warning] Using VirtualAlloc for small objects Each allocation is at least one 4 KB page and 64 KB of address space. Use the heap for small objects.
