Building a Virtual Machine Lab

lesson 15.088 of 8 in milestone 156 min

Kernel experiments belong in a virtual machine: a whole Windows installation running as a program on your PC, which can crash, be debugged from outside, and be restored to a clean state in seconds. This lesson sets up the lab used by chapter 16: a Windows VM with snapshots, test signing enabled inside it, kernel debugging from the host with WinDbg over the network, and the habits that keep your real machine safe.

Why a VM

Without a VM With a VM
A driver bug crashes your PC and loses your work It crashes the VM; your PC carries on
A kernel debugger needs a second physical computer The host debugs the guest
A broken system takes hours to repair Restore a snapshot in seconds
Test-signing mode weakens your everyday system Only the lab VM is in test mode

Every kernel lesson from here on assumes this lab. Never load a driver you are developing on your everyday machine.

Choosing a hypervisor

Hypervisor Notes
Hyper-V Built into Windows 10/11 Pro, Enterprise and Education (enable "Hyper-V" in Windows Features). Good kernel debugging support
VMware Workstation Pro Free for personal use; mature, good snapshots
VirtualBox Free and open source

Any works. Give the VM 2 or more processors, 4 GB or more of RAM, and 64 GB of disk. Install Windows 10 or 11 from Microsoft's official ISO; an unactivated installation is fine for a lab.

Setting up the guest

Inside the VM, from an administrator command prompt:

Terminal
:: 1. Allow test-signed drivers (lesson 16.09). Only in the lab VM.
bcdedit /set testsigning on

:: 2. Turn on kernel debugging over the network to the host.
::    Replace the IP with the host's address on the VM network; the command prints a key for the host.
kdnet.exe 192.168.50.1 50000

:: 3. Write a kernel memory dump on bug checks.
::    (Or System Properties > Advanced > Startup and Recovery.)

kdnet.exe comes with the Windows Driver Kit's debugging tools (lesson 16.01); copy it and VerifiedNICList.xml from the host's C:\Program Files (x86)\Windows Kits\10\Debuggers\x64\ into the VM. Restart the VM; the desktop shows "Test Mode" in a corner, which is how you know it worked.

Also:

  • Turn Secure Boot off in the VM's settings if test signing will not enable (Secure Boot prevents changing boot configuration this way).
  • Disable automatic restart on system failure so you can read stop codes.
  • Create a shared folder, or copy files over the network, to move built drivers from host to guest.

Snapshots

Take a snapshot as soon as the guest is set up and working: "clean, test mode, debugging on". Before each experiment, take another or know which to return to. When a driver leaves the VM unbootable, revert in seconds instead of repairing it. Snapshots are the most valuable feature of the lab.

Connecting the kernel debugger

On the host, start WinDbg (lesson 8.05) → Attach to kernel → Net, enter the port (50000) and the key printed by kdnet in the guest, and start the session. Restart the guest; WinDbg connects as it boots.

Now WinDbg controls the guest's whole kernel:

Command Effect
Break (Ctrl+Break) Freezes the entire VM, every processor, at once
g Lets it run again
lm Loaded kernel modules (drivers)
bp XenonEcho!DriverEntry Breakpoint in your driver, even before it loads (bu, "unresolved breakpoint", for drivers not yet loaded)
!process 0 0 Every process in the guest
!analyze -v After a bug check, analyse it live
ed nt!Kd_DEFAULT_Mask 0xF Show DbgPrint/KdPrint output from drivers in the debugger

Kernel debugging stops the entire guest operating system while you inspect it, which is exactly what is needed: nothing changes underneath you.

Habits that keep you safe

  • Build on the host; copy to the guest; load only in the guest.
  • Keep the guest off your main network shares and without your personal accounts.
  • Revert to a clean snapshot after anything unusual.
  • Keep test signing only in the lab VM, never on your main machine (lesson 16.09 explains why).

Common mistakes

Loading a development driver on your main PC

One mistake costs a blue screen and possibly your work. Always the VM.

No snapshot before an experiment

Take one; restoring takes seconds, repairing takes hours.

Enabling test signing on your everyday system

It weakens its protection against unsigned drivers. Lab VM only.
