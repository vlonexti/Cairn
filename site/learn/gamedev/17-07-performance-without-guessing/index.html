Performance Without Guessing

lesson 17.077 of 8 in milestone 175 min1 practice task

Programmers are famously bad at guessing where time goes. This lesson replaces guessing with measurement: frame budgets, profilers (Visual Studio's CPU Usage tool and sampling in general), microbenchmarks done properly, and the statistics that make timings trustworthy (medians and percentiles instead of averages). It ends with the common real causes of slow C++: cache misses, allocations, and work repeated every frame.

Budgets first

"Fast enough" needs a number. A game at 60 frames per second has 16.7 ms per frame for everything: input, simulation, rendering, audio, and the tools of chapter 12 if they are running. At 144 Hz it is 6.9 ms. A budget turns "it feels slow" into "the overlay takes 3.1 ms of our 16.7".

For tools the budget is different (a memory scan should finish in under a second, an overlay should cost under 0.5 ms a frame), but it is still a number.

Measure, then change one thing, then measure again

flowchart LR
    A["Measure<br/>(profiler or timer)"] --> B["Find the biggest cost"]
    B --> C["Change one thing"]
    C --> D["Measure again,<br/>same conditions"]
    D -->|"better and still correct"| A
    D -->|"not better"| E["Revert it"]
    E --> B

Always measure Release builds (lesson 4.10: Debug builds can be ten times slower, and differently slow), on the same machine, with the same input, several times.

Profilers

A sampling profiler interrupts the program thousands of times a second and records which function was running. Functions that appear in many samples are where the time goes. In Visual Studio: Debug → Performance Profiler → CPU Usage, run the scenario, stop, and read the Hot Path and the list of functions sorted by Total CPU (including callees) and Self CPU (excluding them).

Other useful tools:

Tool Shows
Visual Studio CPU Usage Where CPU time goes, by function and line
Visual Studio Memory Usage Allocations and their call stacks
Windows Performance Recorder and Analyzer Whole-system timelines: threads, waits, disk, GPU
PIX GPU and frame timing for Direct3D games
An in-game frame timer Per-system timings every frame, for regressions

Microbenchmarks done properly

Sometimes you want to compare two versions of one function. Timing it naively lies in several ways:

C++
#include <algorithm>
#include <chrono>
#include <iostream>
#include <numeric>
#include <vector>

volatile long long sink;        // stops the optimiser removing the work

long long sumVector(const std::vector<int>& v) { return std::accumulate(v.begin(), v.end(), 0LL); }

int main()
{
    std::vector<int> data(1'000'000);
    std::iota(data.begin(), data.end(), 0);

    std::vector<double> samples;
    for (int run{ 0 }; run < 25; ++run)
    {
        const auto start{ std::chrono::steady_clock::now() };
        sink = sumVector(data);
        const auto end{ std::chrono::steady_clock::now() };
        samples.push_back(std::chrono::duration<double, std::micro>(end - start).count());
    }
    std::sort(samples.begin(), samples.end());
    std::cout << "min " << samples.front() << " us, median " << samples[samples.size() / 2] << " us\n";
}
Output (yours will differ)
min 212.4 us, median 231.9 us

The rules it follows:

  • Repeat many times and look at the distribution; one run means nothing.
  • Use the result (here through a volatile variable) so the optimiser cannot delete the work.
  • Use steady_clock, which never jumps, not the wall clock.
  • Report the median and a high percentile (p95, p99), not just the mean: a single slow run caused by the operating system can pull the mean far away, while players feel the slow frames that the percentiles show. The practice task computes these.
  • Keep input sizes realistic: data that fits in the cache behaves completely differently from data that does not.

The usual real causes

When you do measure, the culprit in C++ is usually one of a short list:

Cause Sign Typical fix
Cache misses Time in simple loops over large data; pointer-heavy structures (lesson 2.06) Contiguous arrays, structure of arrays, smaller structs
Allocations in the frame loop operator new and malloc high in the profile Reserve once, reuse buffers, pools (lesson 3.10)
Repeated work The same computation or lookup every frame Cache the result; recompute only on change
Algorithmic cost Time grows much faster than input size A better algorithm: hashing instead of searching, sorting once
Waiting Low CPU but slow; threads blocked Profile waits (WPA); avoid blocking calls on the main thread
Debug-only overhead Fast in Release Nothing to fix; measure Release

Note what is not on the list: rewriting clear code into clever code with no measurement. That rarely helps and often hurts.

Common mistakes

Profiling Debug builds

You will optimise the wrong things.

Trusting one timing

Run many times; report the median and a percentile.

Benchmarks the optimiser deletes

If the result is unused, the compiler may remove the code and report it as free.
