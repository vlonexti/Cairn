The I/O Manager and the Driver Model

lesson 15.055 of 8 in milestone 156 min1 practice task

Every read, write and device request in Windows becomes an I/O request packet (IRP) handed to a stack of drivers by the I/O manager. This lesson explains IRPs, driver and device objects, how a request travels down a device stack and its completion travels back up, the kinds of drivers (filter, function, bus), and the frameworks (WDM and KMDF) drivers are written with.

Requests as packets

When a program calls ReadFile on a file or a device, the I/O manager in the kernel builds an IRP, a structure describing the request:

Part of an IRP Meaning
Major function What kind of request: IRP_MJ_CREATE (open), IRP_MJ_READ, IRP_MJ_WRITE, IRP_MJ_DEVICE_CONTROL (custom commands, lesson 16.05), IRP_MJ_CLOSE ...
Parameters Length, offset, the control code ... in the current stack location
Buffers Where the data is, described in one of three ways (lesson 16.07)
I/O status When finished: an NTSTATUS and how many bytes were transferred

The I/O manager then hands the IRP to the driver responsible for the target device. Drivers never call each other's functions directly; everything goes through IRPs.

Driver objects and device objects

Object One per Holds
Driver object Loaded driver The table of dispatch routines: one function per major function the driver handles
Device object Device the driver manages (a disk, a port, or a purely software device like chapter 16's) The device's state, and which driver handles it

When DriverEntry (lesson 16.02) runs, the driver fills its driver object's dispatch table: driver->MajorFunction[IRP_MJ_READ] = EchoRead;. When an IRP for one of its devices arrives, the I/O manager calls the matching routine.

Device stacks

Most hardware is handled by several drivers layered on top of each other, each adding something:

flowchart TB
    U["ReadFile on the volume"] --> F1["Upper filter driver<br/>e.g. encryption, antivirus scanning"]
    F1 --> FN["Function driver<br/>e.g. the file system (NTFS) or the device's main driver"]
    FN --> F2["Lower filter driver"]
    F2 --> B["Bus driver<br/>e.g. USB, PCI: talks to the bus the device is on"]
    B --> HW["Hardware"]
    B -.->|"completion travels back up"| F2
    F2 -.-> FN
    FN -.-> F1
    F1 -.-> U

Each driver, given an IRP, does one of three things:

  1. Complete it itself (IoCompleteRequest) with a status, if it can satisfy the request.
  2. Pass it down to the next driver in the stack (IoCallDriver), possibly after changing it, optionally asking to be told when it completes (a completion routine).
  3. Queue it (mark it pending) to finish later, for example when hardware responds.

The practice task simulates a request going down a stack until one driver completes it, and the completion coming back up through the drivers that asked to see it.

Kind of driver Role
Bus driver Discovers devices on a bus (PCI, USB) and creates their lowest device objects
Function driver The main driver for a device: knows how to operate it
Filter driver Sits above or below and adds or changes behaviour: encryption, compression, monitoring
Software-only driver No hardware; provides a service to user mode through a device object (chapter 16's driver is one)

Asynchronous by design

Device I/O takes time. Rather than making the caller's thread wait inside the driver, an IRP can be pending: the driver returns STATUS_PENDING at once, and completes the IRP later from an interrupt or a worker. User mode sees this as overlapped (asynchronous) I/O, or simply as ReadFile returning when the I/O manager finally completes the request. This design is why Windows I/O can keep thousands of requests in flight.

WDM and KMDF

Framework Notes
WDM (Windows Driver Model) The original model: drivers handle IRPs directly, including all the plug-and-play and power management requests. Powerful and error-prone
KMDF (Kernel-Mode Driver Framework) A library over WDM that handles the standard plug-and-play, power and queueing logic, and gives drivers objects with reference counting and cleanup. Microsoft's recommended choice for new drivers
UMDF Drivers for some device classes that run in user mode, so a bug crashes only a host process, not the machine. Preferred whenever the device type allows it

Chapter 16 starts with a minimal WDM-style driver to see the raw mechanism, and the same ideas carry over to KMDF.

Common mistakes

Completing an IRP and then touching it

After IoCompleteRequest, the IRP belongs to the I/O manager and may already be freed.

Both completing and passing down the same IRP

Each IRP must be completed exactly once, by one driver.

Writing a kernel driver when a user-mode one would do

UMDF, or an ordinary service, keeps bugs out of the kernel.
