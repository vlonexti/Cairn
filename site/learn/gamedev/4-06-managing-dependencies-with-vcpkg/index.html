Managing Dependencies with vcpkg

lesson 4.066 of 10 in milestone 45 min

Real projects use other people's libraries: a window and input library, an image loader, a user interface toolkit. vcpkg is Microsoft's package manager for C and C++: you list the libraries a project needs in a vcpkg.json file, and it downloads, builds and links them with settings that match your project. This lesson sets it up for the course's later chapters.

The problem vcpkg solves

Using a third-party C++ library by hand means: find its source, build it with the right compiler, platform, runtime library and configuration (lesson 4.04's matching rules), copy its headers somewhere, add include and library paths to your project, and repeat for every library it depends on, and again for every machine that builds your project.

vcpkg automates all of that. It knows how to build thousands of libraries, builds each one to match your project's triplet (for example x64-windows: 64-bit, DLL runtime), and plugs the results into MSBuild so your project finds headers and libraries automatically.

Getting vcpkg

Visual Studio 2022 includes a copy of vcpkg, available in the Developer PowerShell as vcpkg. To check:

Terminal
vcpkg --version

If the command is not found, install the vcpkg package manager component from the Visual Studio Installer (Individual components tab), or clone it yourself:

Terminal
git clone https://github.com/microsoft/vcpkg C:\dev\vcpkg
C:\dev\vcpkg\bootstrap-vcpkg.bat
C:\dev\vcpkg\vcpkg integrate install

integrate install connects vcpkg to every MSBuild project for your user account.

Manifest mode: dependencies in a file

The modern way to use vcpkg is manifest mode: a vcpkg.json file next to your solution lists what the project needs, so anyone who builds it gets the same libraries.

Terminal
cd course
vcpkg new --application
vcpkg add port fmt
vcpkg add port sdl2

That creates and fills vcpkg.json:

JSON
{
  "dependencies": [
    "fmt",
    "sdl2"
  ]
}

Then, in each project that should use vcpkg: Properties → vcpkg → Use Vcpkg Manifest: Yes. The next build reads the manifest, builds the listed libraries (the first time takes a while; later builds reuse the results) and adds their include folders, libraries and DLLs to the project. DLLs are copied next to your .exe automatically.

C++
#include <fmt/core.h>

int main()
{
    fmt::print("{} has {} health\n", "Rook", 87);
    return 0;
}

No include paths, no library paths, no copying: the manifest is the only thing you wrote.

Triplets: matching the build

A triplet names the platform and the linkage vcpkg should build for.

Triplet Platform Libraries built as C runtime
x64-windows 64-bit DLLs DLL (/MD)
x64-windows-static 64-bit Static .lib Static (/MT)
x64-windows-static-md 64-bit Static .lib DLL (/MD)

vcpkg picks x64-windows for an x64 project by default and builds Debug and Release versions of every library, linking the right one for each configuration. If your projects use /MT (as the course's static builds might), set Properties → vcpkg → Use Static Libraries: Yes so the libraries match.

Pinning versions

By default, vcpkg uses whichever versions its own copy currently has. For a project you want to build the same way next year, add a baseline, which pins every library to the versions vcpkg had at a particular commit:

Terminal
vcpkg x-update-baseline --add-initial-baseline

The manifest gains a "builtin-baseline" line. Commit vcpkg.json to version control; do not commit the vcpkg_installed folder it creates, which is build output.

Common mistakes

Mixing manifest mode and manually copied libraries

Two copies of a library's headers on the include path, from different versions, cause confusing errors. Let vcpkg own each library.

A triplet that does not match the runtime library

A static-runtime project with DLL-runtime libraries gives LNK2038. Match them with the vcpkg project settings.

[!warning] Committing vcpkg_installed It is large and machine-specific build output. Add it to .gitignore.
