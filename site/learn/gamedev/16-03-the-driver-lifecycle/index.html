The Driver Lifecycle

lesson 16.033 of 10 in milestone 165 min1 practice task

A driver sets things up in DriverEntry (devices, links, memory, timers) and must tear every one of them down in its unload routine, in reverse order, leaving nothing behind. If set-up fails halfway, it must undo exactly the steps that succeeded. This lesson builds that discipline: the load and unload sequence, the service registry key, cleanup on partial failure, and why anything left behind after unload crashes the machine.

Load to unload

sequenceDiagram
    participant U as sc / Service Control Manager
    participant IO as I/O manager
    participant D as XenonEcho.sys
    U->>IO: start service (registry key says: kernel driver, this file)
    IO->>IO: map the .sys, check its signature, resolve imports
    IO->>D: DriverEntry(driver, registryPath)
    D->>D: create device, link, allocate state, start timers ...
    D-->>IO: STATUS_SUCCESS
    Note over D: the driver serves requests (lessons 16.05 to 16.07)
    U->>IO: stop service
    IO->>D: DriverUnload(driver)
    D->>D: stop timers, delete link, delete device, free memory (reverse order)
    IO->>IO: unmap the .sys

The service's registry key (HKLM\SYSTEM\CurrentControlSet\Services\XenonEcho) records the type (kernel driver), the file, and the start type: on demand (sc start), at boot, or at system start. The lab always uses on-demand, so a broken driver never loads automatically.

The unload rule

After DriverUnload returns, the driver's code and global data are unmapped. Anything that still refers to them becomes a pointer into nothing:

Left behind What happens later
A timer or DPC still queued It fires and jumps into unmapped code: bug check 0xCE (DRIVER_UNLOADED_WITHOUT_CANCELLING_PENDING_OPERATIONS)
A device object Requests can still be routed to a driver that is gone
A symbolic link Programs can open a name pointing at a deleted device
Pool memory Leaked until reboot (lesson 15.04); Driver Verifier reports it
A registered callback The kernel calls it later: bug check
An IRP still pending Completing it later touches freed state

So unload undoes everything, in reverse order of creation, waiting where necessary (for example, KeCancelTimer and flushing queued DPCs with KeFlushQueuedDpcs) until nothing can call into the driver any more. It is lesson 2.04's RAII and destructor-order rule, enforced by the hardware.

Partial failure in DriverEntry

DriverEntry does several steps that can each fail. If step 3 fails, steps 1 and 2 must be undone before returning the failure, because the unload routine will not be called. The clear way to write it is to record what succeeded and undo it in reverse:

C++
extern "C" NTSTATUS DriverEntry(PDRIVER_OBJECT driver, PUNICODE_STRING)
{
    NTSTATUS status{ STATUS_SUCCESS };
    PDEVICE_OBJECT device{ nullptr };
    bool linkCreated{ false };

    do
    {
        status = IoCreateDevice(driver, sizeof(EchoState), &kDeviceName, FILE_DEVICE_UNKNOWN,
                                FILE_DEVICE_SECURE_OPEN, FALSE, &device);
        if (!NT_SUCCESS(status)) break;

        status = IoCreateSymbolicLink(&kLinkName, &kDeviceName);
        if (!NT_SUCCESS(status)) break;
        linkCreated = true;

        // ... more steps, each followed by a check and a "created" flag ...
    } while (false);

    if (!NT_SUCCESS(status))                 // undo, in reverse, only what succeeded
    {
        if (linkCreated) IoDeleteSymbolicLink(&kLinkName);
        if (device) IoDeleteDevice(device);
        return status;
    }

    driver->DriverUnload = EchoUnload;
    return STATUS_SUCCESS;
}

The practice task simulates this: given which steps succeed, produce the cleanup calls in the right order.

Reference counting and in-flight work

Unload can arrive while requests are still being processed on other processors. The I/O manager will not unload a driver while it still has device objects with open handles (the device's reference count, lesson 15.03), so a program holding the device open keeps the driver loaded, and sc stop fails until it closes. Work the driver started itself (timers, work items, threads) is the driver's responsibility to stop and wait for in unload.

Common mistakes

Unload that forgets one thing

Every resource created in DriverEntry needs a matching release in unload. Write them as pairs.

Cleanup in the wrong order

Reverse order of creation: links before devices, timers stopped before freeing what they use.

Partial failure that leaks

Undo exactly the steps that succeeded before returning a failure from DriverEntry.
