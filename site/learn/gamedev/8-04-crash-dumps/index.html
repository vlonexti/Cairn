Crash Dumps

lesson 8.044 of 8 in milestone 86 min1 practice task

When a game crashes on a player's machine, you cannot attach a debugger. A crash dump captures the crashed process's state (threads, stacks, registers, some or all memory) into a file you can open later in Visual Studio or WinDbg as if you had been there. This lesson explains exception codes, writing a minidump from your own crash handler, collecting dumps with Windows Error Reporting, and opening them.

What happens when a program crashes

A "crash" on Windows is an unhandled exception: the processor or the program raised an exception (an access violation, a divide by zero, a C++ throw nobody caught), and nothing handled it. Windows then calls the process's unhandled exception filter, which by default hands the crash to Windows Error Reporting and ends the process.

Each exception has a code. The ones you will see most:

Code Name Usual cause
0xC0000005 Access violation Null or dangling pointer, out-of-bounds access, writing to read-only memory
0xC00000FD Stack overflow Runaway recursion, huge locals (lesson 1.05)
0xC0000094 Integer divide by zero x / 0 or x % 0 with integers
0xC000001D Illegal instruction Jumping into data, or an instruction the CPU does not support
0xC0000409 Stack buffer overrun / fail fast A /GS cookie check failed (lesson 7.05), or abort()-style fast fail
0x80000003 Breakpoint An int 3 / __debugbreak() with no debugger attached
0xE06D7363 C++ exception A throw that was never caught (the hex spells "msc" in ASCII)

For an access violation, the exception record also says whether it was a read, write or execute, and the address: the clues from lessons 3.02 and 6.02.

Minidumps

A minidump (.dmp) is a snapshot of a process: the list of modules with their versions and signatures, every thread's registers and stack, the exception record, and optionally some or all of the heap. Opened with the matching PDBs (lesson 8.02), it shows the call stack and variables at the moment of the crash.

Dump type Contains Size
Small (MiniDumpNormal) Modules, threads, stacks, exception Tens to hundreds of KB
With data segments and indirectly referenced memory Also globals and memory pointed to from the stacks A few MB
Full memory (MiniDumpWithFullMemory) Everything in the address space As big as the process's memory

Small dumps are usually enough for a call stack and the locals on the stack. Full dumps let you inspect any object, at a cost.

Writing one yourself

A game installs its own filter at start-up, so it can write a dump (and its recent log lines, lesson 8.03) before exiting:

C++
#include <windows.h>
#include <dbghelp.h>
#pragma comment(lib, "dbghelp.lib")

static LONG WINAPI writeCrashDump(EXCEPTION_POINTERS* info)
{
    HANDLE file{ CreateFileW(L"crash.dmp", GENERIC_WRITE, 0, nullptr, CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, nullptr) };
    if (file != INVALID_HANDLE_VALUE)
    {
        MINIDUMP_EXCEPTION_INFORMATION exception{};
        exception.ThreadId = GetCurrentThreadId();
        exception.ExceptionPointers = info;
        exception.ClientPointers = FALSE;
        MiniDumpWriteDump(GetCurrentProcess(), GetCurrentProcessId(), file,
                          static_cast<MINIDUMP_TYPE>(MiniDumpWithDataSegs | MiniDumpWithIndirectlyReferencedMemory),
                          &exception, nullptr, nullptr);
        CloseHandle(file);
    }
    return EXCEPTION_EXECUTE_HANDLER;      // let the process end
}

int wmain()
{
    SetUnhandledExceptionFilter(&writeCrashDump);
    // ... the game ...
}

Notes from experience:

  • Write dumps to a folder the user can write (lesson 5.04), with a time stamp in the name.
  • The crashed process may be badly damaged (a corrupt heap, an exhausted stack). The most robust crash reporters do as little as possible in the crashed process and let a separate small watchdog process write the dump, using MiniDumpWriteDump on the crashed process from outside.
  • Some failures (0xC0000409 fast fail, stack overflow on a thread with no stack left) bypass or break the filter; the system's own reporting is the fallback.

Letting Windows collect dumps

Windows Error Reporting can save a dump for every crash of a given program, with no code at all, using a registry key (for developers' and testers' machines):

Output
HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\game.exe
    DumpFolder  (REG_EXPAND_SZ)  %LOCALAPPDATA%\CrashDumps
    DumpType    (REG_DWORD)      1 = mini, 2 = full
    DumpCount   (REG_DWORD)      10

You can also write a dump of any running process from Task Manager → Details → right-click → Create dump file, which is handy for a game that is hung rather than crashed.

Opening a dump

In Visual Studio, File → Open → File and choose the .dmp. The summary page shows the exception code, the faulting module and the module list; press Debug with Native Only. With matching symbols (and the source, if you have it), you land on the crashing line with the Call Stack, Locals and Threads windows working, though you cannot step: the process is a snapshot, not running.

WinDbg (next lesson) opens the same files and has !analyze -v, which reads the exception, finds the faulting frame and summarises the likely cause.

Common mistakes

Dumps without matching PDBs

A dump is only as useful as the symbols you can load for it. Archive the PDBs of every build you give to anyone.

Doing heavy work inside the crash handler

Allocating, loading DLLs or taking locks in a crashed process can hang. Keep the handler minimal.

Only collecting full dumps

They can be gigabytes. Small dumps with a little extra memory are usually enough and far easier to collect from players.
