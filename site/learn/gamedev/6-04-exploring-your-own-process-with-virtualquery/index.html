Exploring Your Own Process with VirtualQuery

lesson 6.044 of 9 in milestone 65 min1 practice task

VirtualQuery answers "what is at this address?": the region's start and size, its state, protection and type. Walking it across the whole address space produces a map of your process: the modules, heaps, stacks and reserved areas. This lesson builds that map, the same view tools like VMMap show, and uses it to identify what any pointer points at.

Asking about an address

C++
MEMORY_BASIC_INFORMATION info{};
VirtualQuery(someAddress, &info, sizeof(info));

VirtualQuery fills a MEMORY_BASIC_INFORMATION describing the region containing the address: a run of consecutive pages that all share the same state, protection and type.

Field Meaning
BaseAddress Start of the region containing the address
RegionSize Size of the region, in bytes
AllocationBase Start of the original VirtualAlloc (or mapping) the region belongs to
State MEM_FREE, MEM_RESERVE or MEM_COMMIT (lesson 6.03)
Protect Current protection, such as PAGE_READWRITE
Type MEM_IMAGE (an exe or DLL), MEM_MAPPED (a file mapping) or MEM_PRIVATE (heap, stack, VirtualAlloc)

What is this pointer?

The Type and AllocationBase fields identify where any pointer leads. For an image, AllocationBase is the module's HMODULE, so GetModuleFileNameW gives its name:

C++
#include <windows.h>
#include <iostream>
#include <memory>
#include <string>

const char* kind(const void* p)
{
    MEMORY_BASIC_INFORMATION info{};
    if (!VirtualQuery(p, &info, sizeof(info)) || info.State != MEM_COMMIT) return "not committed memory";
    if (info.Type == MEM_IMAGE)
        return (info.Protect & (PAGE_EXECUTE | PAGE_EXECUTE_READ | PAGE_EXECUTE_READWRITE)) ? "code in a module" : "data in a module";
    if (info.Type == MEM_MAPPED) return "a mapped file";
    return "private memory (heap, stack or VirtualAlloc)";
}

int g_global{ 1 };

int main()
{
    int local{ 2 };
    auto heap{ std::make_unique<int>(3) };
    std::cout << "main:       " << kind(reinterpret_cast<const void*>(&main)) << '\n';
    std::cout << "g_global:   " << kind(&g_global) << '\n';
    std::cout << "a literal:  " << kind("text") << '\n';
    std::cout << "local:      " << kind(&local) << '\n';
    std::cout << "heap:       " << kind(heap.get()) << '\n';
    std::cout << "nullptr+16: " << kind(reinterpret_cast<const void*>(16)) << '\n';
    return 0;
}
Output
main:       code in a module
g_global:   data in a module
a literal:  data in a module
local:      private memory (heap, stack or VirtualAlloc)
heap:       private memory (heap, stack or VirtualAlloc)
nullptr+16: not committed memory

A crash reporter or a debugging tool does exactly this to say "the bad pointer pointed into freed space" or "the crash was in plugin.dll's code".

Walking the whole address space

Regions are consecutive, so you can walk them all: start at address 0, query, then jump to BaseAddress + RegionSize, until VirtualQuery fails at the end of user space.

C++
#include <windows.h>
#include <iostream>

int main()
{
    SIZE_T committed{ 0 }, reserved{ 0 };
    int regions{ 0 }, imageRegions{ 0 };
    MEMORY_BASIC_INFORMATION info{};
    for (const char* at{ nullptr }; VirtualQuery(at, &info, sizeof(info)) == sizeof(info); at = static_cast<const char*>(info.BaseAddress) + info.RegionSize)
    {
        ++regions;
        if (info.State == MEM_COMMIT) committed += info.RegionSize;
        if (info.State == MEM_RESERVE) reserved += info.RegionSize;
        if (info.State == MEM_COMMIT && info.Type == MEM_IMAGE) ++imageRegions;
    }
    std::cout << regions << " regions, " << imageRegions << " committed image regions\n";
    std::cout << committed / 1024 << " KB committed, " << reserved / (1024 * 1024) << " MB reserved\n";
    return 0;
}
Output (yours will differ)
212 regions, 63 committed image regions
6044 KB committed, 2056 MB reserved

Even a tiny program has a couple of hundred regions: every DLL contributes several (one per section with a different protection: code, read-only data, writable data), plus heaps, the stack and its guard page, and areas Windows reserves for itself. The reserved total is large because of reservations such as the stack's 1 MB and heap segments, which cost no memory.

Microsoft's VMMap (part of the free Sysinternals tools) shows this map for any process with a friendly interface, and Visual Studio's diagnostic tools can too. Writing the walk yourself is the best way to understand what they show.

Common mistakes

Not advancing past free regions

Free regions are regions too. Always step by BaseAddress + RegionSize, whatever the state.

[!warning] Treating Protect as meaningful for free or reserved regions It only describes committed pages; for reserved regions, AllocationProtect holds the protection the reservation was made with.

[!warning] Reading memory just because VirtualQuery said it was committed Another thread can free it a moment later. Tools that read arbitrary memory must be prepared for the read to fail (chapter 12).
