A Tour of the Rendering Pipeline

lesson 10.044 of 9 in milestone 106 min1 practice task

Rendering turns the game's state into pixels, mostly on the GPU. This lesson follows a frame from the CPU's side (what to draw, culling, sorting, draw calls) through the GPU's pipeline (vertex shaders, rasterisation, pixel shaders, depth testing) to the screen, with the coordinate transforms in between. It is a map for the graphics work in chapter 11 and beyond.

The CPU and the GPU

The GPU is a separate processor with thousands of simple cores, built to run the same small program on huge numbers of vertices and pixels in parallel. The CPU does not draw pixels; it prepares work for the GPU and submits it through a graphics API: Direct3D 11/12 on Windows, Vulkan, OpenGL, or Metal on Apple systems. Libraries like SDL and raylib (chapter 11) sit on top of these.

The CPU's part

Each frame the renderer:

  1. Collects what might be visible: sprites, models, particles, interface.
  2. Culls: skips everything outside the camera's view (a rectangle in 2D, a pyramid-shaped frustum in 3D). Cheap bounding-box tests remove most objects before any GPU work. The practice task does this for 2D.
  3. Sorts: transparent objects back to front (so blending is correct); opaque objects by material or texture, to minimise state changes.
  4. Submits draw calls: each tells the GPU "draw these triangles with this shader, these textures and these settings".

Draw calls have a CPU cost of their own. Drawing ten thousand sprites as ten thousand separate calls is slow; batching them (many sprites sharing a texture atlas in one call) or instancing (one model drawn many times in one call) is how games draw large scenes.

Coordinates and transforms

Positions pass through several coordinate systems on the way to the screen:

Space Meaning
Model (local) space Relative to the object itself: a character model's feet at (0, 0, 0)
World space Where it is in the level (the scene graph of lesson 3.09 combines these)
View (camera) space Relative to the camera
Clip space / NDC After projection: what lies inside the view becomes the range −1 to 1
Screen space Pixels on the render target

Each step is a matrix multiplication, combined into one matrix per object and applied to every vertex by the vertex shader. In 2D the idea is the same with simpler maths: subtract the camera's position, multiply by the zoom, and add half the screen size to put the camera's centre in the middle.

The GPU's part

  • Vertex shader: a small program run once per vertex, transforming its position into clip space and passing along data such as texture coordinates and colours.
  • Rasterisation: fixed hardware works out which pixels each triangle covers and interpolates the vertex data across them.
  • Pixel (fragment) shader: run once per covered pixel, computing its colour: sampling textures, applying lighting.
  • Output merging: the depth test discards pixels behind something already drawn (using the depth buffer); blending combines transparent pixels with what is behind them.

Shaders are written in their own languages (HLSL for Direct3D, GLSL for OpenGL and Vulkan) and compiled for the GPU.

Buffers and presenting

The GPU draws into a back buffer while the monitor shows the front buffer; at the end of the frame they are swapped (present), the same idea as lesson 5.06's double buffering. With vsync, the swap waits for the monitor's refresh (lesson 10.02).

Where the time goes

Bottleneck Symptom Typical fix
CPU: too many draw calls GPU often idle; CPU busy in the renderer Batching, instancing, fewer state changes
GPU: too many pixels (fill rate) Slower at higher resolutions; heavy effects Cheaper pixel shaders, lower resolution effects, less overdraw
GPU: too many vertices Slower with detailed models regardless of resolution Level of detail (simpler models far away)
Transfers Stalls when uploading textures mid-game Upload during loading, or asynchronously

GPU profilers (PIX for Direct3D, RenderDoc for most APIs, vendor tools) show where a frame's GPU time goes, like lesson 8.08's CPU profiling.

Common mistakes

One draw call per sprite

Batch sprites that share a texture, or use an atlas.

Reading back from the GPU every frame

The CPU waits for the GPU to finish. Avoid it, or read results a frame or two later.

Drawing everything without culling

Off-screen objects still cost CPU and GPU time.
