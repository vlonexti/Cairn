What the Operating System Does for a Program

lesson 1.066 of 8 in milestone 18 min1 practice task

Between your program and the hardware sits the operating system. It loads the program into memory, gives it a private address space, shares the CPU between hundreds of programs, and is the only way to reach files, the screen or the network. Each of these ideas gets its own chapter later; this lesson is the map.

The program is not alone

On the tiny computer from lesson 1.01, one program owned the whole machine. A Windows PC runs hundreds of programs at once: the game, the browser, the music player, dozens of background services. None of them can be allowed to overwrite another's memory or hog the processor forever.

The operating system (OS) is the program that makes sharing possible. Its core, the kernel, runs with full control of the hardware. Everything else, including your game, runs with restricted rights and has to ask the kernel for anything that touches the outside world.

Chapter 15 looks inside the kernel. For now, five jobs matter.

1. Loading the program

An .exe on disk is a file in the PE format (Portable Executable). When you start it, the Windows loader:

  1. Creates a new process: the container for one running copy of a program.
  2. Maps the .exe file's code and data into the process's memory.
  3. Loads every DLL the program needs (such as kernel32.dll and the C++ runtime), and fills in the addresses of the functions the program calls in them.
  4. Creates the first thread and starts it at the program's entry point, which eventually calls your main.

Chapter 9 takes the PE format apart byte by byte. Chapter 4 builds DLLs of your own.

2. Giving each process its own memory

Every process gets its own virtual address space. The addresses your program prints are not positions in the RAM chips. They are positions in a private, pretend memory that the OS and the processor translate to real memory behind the scenes.

Two programs can both use the address 0x7FF61000, and they reach different physical memory. That is how Windows keeps programs from reading or wrecking each other: there is simply no address in one process that leads to another process's memory. Memory is handed out in pages, which are 4,096 bytes (0x1000) each on x64. Chapter 6 explains the translation and how to explore your own address space.

3. Sharing the processor

A CPU has a handful of cores, and there are thousands of threads that want to run. The OS scheduler gives each thread a short turn, a time slice of a few milliseconds, then saves its registers and lets another thread run. It switches so often that everything appears to run at once.

This is why your game's frame time is never perfectly steady, and why one program stuck in an endless loop does not freeze the whole PC. Chapter 6 covers threads and scheduling.

4. Being the only door to the hardware

User-mode programs cannot touch the disk, the graphics card or the network directly. They call system calls, functions that switch the CPU into kernel mode, do the work with full rights and switch back. On Windows you almost never make system calls yourself. You call documented functions in DLLs, the Windows API, and those make the system calls for you.

C++
#include <windows.h>
#include <iostream>

int main()
{
    SYSTEM_INFO info{};
    GetSystemInfo(&info);       // asks Windows about the machine and the address space

    std::cout << "Page size:              " << info.dwPageSize << " bytes\n";
    std::cout << "Allocation granularity: " << info.dwAllocationGranularity << " bytes\n";
    std::cout << "Lowest usable address:  " << info.lpMinimumApplicationAddress << '\n';
    return 0;
}
Output
Page size:              4096 bytes
Allocation granularity: 65536 bytes
Lowest usable address:  0000000000010000

GetSystemInfo is part of the Windows API, declared in <windows.h> and implemented in kernel32.dll. Chapter 5 is all about this API: how to read its documentation, handle its errors and use its strange string types.

Even std::cout ends in a system call. The C++ library collects your text, then calls WriteFile in kernel32.dll, which asks the kernel to put the bytes on the console.

5. Keeping track of who owns what

When your program opens a file, the kernel creates an object to represent the open file and hands your process a handle: a small number that means "that file I opened". Threads, processes, events and windows are all handled the same way. The kernel checks every handle against the process's rights, and closes everything a process left open when it exits.

C++
#include <windows.h>
#include <iostream>

int main()
{
    std::cout << "This process has id " << GetCurrentProcessId() << '\n';
    std::cout << "Its main thread has id " << GetCurrentThreadId() << '\n';
    return 0;
}
Output (yours will differ)
This process has id 18324
Its main thread has id 20916

Run it twice and the numbers change: every run is a new process with a new id. Open Task Manager → Details while a program is running and you can find it by this id.

Much of what the OS does is say no: no, you cannot read that process; no, you cannot load that driver. These rules are what keep a PC stable and keep one bad program from compromising the others. The course works with them, using documented interfaces on programs you write yourself.

Common mistakes

Thinking a pointer value is a place in RAM

It is a virtual address, meaningful only inside its own process. The same number in another process leads somewhere else, or nowhere.

Assuming your thread runs without interruption

The scheduler can pause it between any two instructions. Code that shares data between threads has to be written for that, as chapter 6 shows.

Forgetting that handles must be closed

Windows closes them when the process exits, but a long-running game that opens files or threads in a loop and never closes them will run out.

    The container for one running copy of a program: its address space, its threads and its handles The .exe is the file on disk. Starting it creates a process. Starting it twice creates two processes.

    • 1,024 bytes
    • 4,096 bytes (0x1000)

    Show the answer

    4,096 bytes (0x1000) 65,536 is the allocation granularity, which chapter 6 explains. A page is 4 KB.
