Shipping and Maintaining What You Build

lesson 17.088 of 8 in milestone 176 min1 practice task

A program is not finished when it works on your machine. This lesson covers what it takes to put a tool or game in other people's hands and keep it working: reproducible Release builds, versioning with semantic versions, crash reports with symbols kept for every release, installers and updates, documentation, licences, and the habits of maintenance (changelogs, issue tracking, and deciding what not to build).

A reproducible Release build

Anyone on the team, or a build server, should produce the same release from the same commit:

  • The build is one command or one button: Build → Batch Build or msbuild Delve.sln /p:Configuration=Release /p:Platform=x64.
  • Dependencies are pinned: the SDL2 version from lesson 11.01 is checked in or fetched at a fixed version (vcpkg with a manifest and baseline does this).
  • Release settings are deliberate: optimisation on, warnings as errors, /guard:cf and other mitigations on (lesson 17.04), and /Zi with PDBs even for Release.
  • A continuous integration service (GitHub Actions, Azure Pipelines) builds and runs the tests (17.01) on every push, so a broken build is noticed in minutes.

Semantic versions

A semantic version MAJOR.MINOR.PATCH tells users what an update means:

Part Increase when Example
MAJOR You make a change that breaks compatibility: an old save format no longer loads, a plugin API function changes 1.4.2 → 2.0.0
MINOR You add features compatibly 1.4.2 → 1.5.0
PATCH You fix bugs compatibly 1.4.2 → 1.4.3

Pre-releases add a suffix (2.0.0-beta.1) and sort before the final version. Versioning interfaces between components (lesson 12.06's telemetry protocol, lesson 13.07's plugin API) follows the same rule, which is why those had version fields. The practice task compares and bumps versions.

Put the version in the executable's version resource (Add → Resource → Version) so it shows in the file's properties, in the crash report, and in the title or about screen.

Crash reports and symbols

Users will hit crashes you never saw. Lesson 8.04's minidumps are how you find out:

  1. The program installs an unhandled-exception filter that writes a minidump with MiniDumpWriteDump and offers to send it.
  2. For every release, you keep the exact PDBs produced by that build, in a symbol store (symstore add) or a folder named by version.
  3. When a dump arrives, WinDbg or Visual Studio loads it with the matching symbols and shows the call stack and variables at the crash.

Without the matching PDB, a dump is a list of addresses. Losing a release's symbols means losing the ability to debug its crashes.

Installers and updates

Option Suits
A zip file with a portable folder Small tools; nothing to install or uninstall
An MSIX package or an MSI (WiX) Applications that need Start menu entries, file associations, clean uninstall
A store or launcher (Steam, itch.io, Microsoft Store) Games: it handles distribution, updates and signing
Your own updater Only when nothing else fits; it must verify signatures (17.06)

Whatever the method: code-sign the files, install per-user without administrator rights when possible (lesson 6.08), and keep settings and saves in the user's folders (%APPDATA%, Saved Games), not next to the program.

Documentation

Three documents cover most needs:

  • A README: what it is, how to install it, how to use the common features, system requirements.
  • A changelog: each version, with what was added, changed, fixed and removed, in plain language.
  • For anything with an interface others build on (a plugin API, a protocol, a driver's IOCTLs), a reference: every function or message, its parameters, errors and version.

Licences

Every dependency's licence must allow your use: SDL2 uses the zlib licence (very permissive), Dear ImGui is MIT, some libraries are GPL (which places conditions on your own code if you distribute it). List them in a third-party notices file. Choose a licence for your own code too, if you publish it; without one, others have no right to use it.

Maintenance

After release, most of the work is maintenance:

  • Track bugs and requests in an issue tracker, each with steps to reproduce, version and logs.
  • Fix with a regression test first (17.01), then the fix.
  • Release patches from a known commit, tagged with the version (git tag v1.4.3).
  • Say no to features that do not fit. Each one is code to maintain forever, a lesson that applies with special force to low-level tools, where every new feature is also new attack surface (17.05).

Common mistakes

Not keeping Release PDBs

Crash reports become useless.

Breaking compatibility in a minor version

Users and plugin authors trusted the version number.

Saving data next to the executable

Program Files is not writable by normal users, and updates may replace the folder.
