Fuzzing

lesson 17.033 of 8 in milestone 175 min1 practice task

Fuzzing feeds a program huge numbers of automatically generated, mostly broken inputs and watches for crashes, hangs and sanitizer reports. Coverage-guided fuzzers such as libFuzzer learn which inputs reach new code and mutate those further, finding bugs no human would think to test. This lesson writes fuzz targets for Delve's parsers, runs them with MSVC's fuzzer support and AddressSanitizer, and minimises the crashing inputs.

The idea

Tests check the cases you thought of. Bugs live in the cases you did not: a level file with a 2-billion-character line, a save whose length field says 0xFFFFFFFF, a message cut off mid-header. A fuzzer generates such inputs automatically, millions per hour:

flowchart LR
    C["Corpus<br/>example inputs"] --> M["Mutate<br/>flip bits, insert, delete,<br/>splice, repeat"]
    M --> T["Run the fuzz target<br/>with ASan and UBSan"]
    T -->|"crash or sanitizer report"| R["Save the input as a reproducer"]
    T -->|"reached new code (coverage)"| C
    T -->|"nothing new"| M

Coverage guidance is what makes modern fuzzers effective: the compiler instruments the program to record which code each input reaches, and inputs that reach something new are kept and mutated further. The fuzzer gradually learns the format's structure (the magic number, the version field, valid section headers) without being told.

Writing a fuzz target

A fuzz target is one function that takes a block of bytes and passes them to the code under test:

C++
// fuzz_level.cpp: fuzz Delve's level parser (lesson 11.02's practice task)
#include <cstddef>
#include <cstdint>
#include <string>
#include "level.h"

extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size)
{
    const std::string text(reinterpret_cast<const char*>(data), size);
    const auto level{ parseLevel(text) };            // must never crash, hang or trip a sanitizer
    if (level)
    {
        // Check invariants the parser promises: the result is self-consistent.
        if (level->tiles.size() != static_cast<size_t>(level->width * level->height)) __debugbreak();
    }
    return 0;
}

Good fuzz targets:

  • target one parser or decoder of untrusted data: level files, saves (lessons 10.07, 11.06), INI settings (10.08), telemetry snapshots (12.04), IOCTL request structures (16.05), PE headers (9.02);
  • are deterministic and fast (thousands of runs per second);
  • check invariants as well as crashes: a successful parse should produce a consistent result;
  • do not touch the file system, network or global state.

Running it with MSVC

Visual Studio 2022 supports libFuzzer directly:

  1. A new console project fuzz_level containing the target and the parser's source.
  2. C/C++ → Command Line: /fsanitize=fuzzer /fsanitize=address (ASan makes memory bugs crash immediately instead of silently).
  3. A corpus folder with a few valid level files as starting points.
  4. Run: fuzz_level.exe corpus -max_total_time=600

The fuzzer prints progress (cov: grows as it discovers code). On a crash it stops, prints the sanitizer report, and writes the input to a file such as crash-3f2a.... Running fuzz_level.exe crash-3f2a... reproduces it under the debugger.

Minimising

Fuzzer-found inputs are often large and noisy. Minimisation shrinks one to the smallest input that still fails, which usually makes the bug obvious. libFuzzer does it with -minimize_crash=1; the underlying idea is simple enough to write yourself, and the practice task does: repeatedly try removing parts of the input, keeping any removal after which it still fails.

Fuzzing a driver's interface

Lesson 16.10's test plan included fuzzing the driver from user mode: a program in the lab VM that opens the device and sends random control codes, lengths and buffer contents in a loop, with Driver Verifier on. Any bug check is a finding; the last request is logged before sending, so it can be reproduced. That is exactly how many real driver vulnerabilities are found, which is why driver authors should do it first.

Common mistakes

Fuzzing without sanitizers

Most memory bugs do not crash on their own. Combine fuzzing with ASan.

Slow targets

A target doing file I/O or logging runs a hundred times slower and finds far less.

Fixing the crash but not adding the input to the tests

Every fuzzer finding becomes a regression test (lesson 17.01).
