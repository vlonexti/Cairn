Reconstructing Structs from Compiled Code

lesson 9.099 of 10 in milestone 95 min

Types disappear in compilation, but every struct leaves a trail of offsets and sizes in the code that uses it. This lesson is a step-by-step method for rebuilding a struct definition from those accesses, combining static evidence (offsets, sizes, instructions used) with dynamic evidence (values seen in the debugger), and recording the result as a type the disassembler can apply everywhere.

The evidence an access gives

Each instruction that touches a struct member tells you three things (lesson 7.08):

Evidence Example Tells you
Offset [rcx+14h] A member starts at 0x14
Size dword ptr, byte ptr, qword ptr It is 4, 1 or 8 bytes
Instruction movss vs mov; movsx vs movzx; jl vs jb afterwards float or integer; signed or unsigned
Use Passed to printf with %s; followed as a pointer; compared with 0 and branched A string pointer or buffer; a pointer; a flag or count

A method

  1. Pick one struct pointer and find every function that receives it (from xrefs and from the calls in its creator).
  2. Collect accesses: every [reg+offset] with that pointer, noting offset, size and instruction. The disassembler's structure editor helps: Ghidra's Auto Create Structure on a parameter does a first pass.
  3. Lay them out by offset (this is lesson 7.08's practice task). Gaps are either padding (lesson 2.05) or members this code never touches.
  4. Type the members using instructions and uses: movss means float; a value compared with jl/jg is signed; an 8-byte member that is dereferenced is a pointer, and what it points to is another struct to rebuild.
  5. Name them from strings and context: a member printed with "HP: %d" is health.
  6. Check alignment: a 4-byte member at an offset that is not a multiple of 4 suggests the struct is packed, or you mis-read an access.
  7. Confirm dynamically: break where the struct is used and look at it in the debugger's memory view (lesson 2.11); the values should make sense with your types (floats look like floats, pointers like pointers, counts are small).
  8. Apply the type to the parameter and globals, and iterate: the decompiler output improves, revealing more.

A worked example

A function in a stripped target contains:

Assembly
movss   xmm0, dword ptr [rcx+8]        ; float at 8
addss   xmm0, dword ptr [rcx+10h]      ; float at 0x10
movss   dword ptr [rcx+8], xmm0
mov     eax, dword ptr [rcx+18h]       ; 4-byte integer at 0x18
test    eax, eax
jle     dead                            ; signed compare with 0: health-like
movzx   edx, byte ptr [rcx+1Ch]        ; 1-byte unsigned at 0x1C, then tested: a bool
test    dl, dl
...
mov     rax, qword ptr [rcx+20h]       ; 8 bytes at 0x20, then used as an address: a pointer
mov     rcx, qword ptr [rax]           ; reading through it: its first member

Elsewhere, a constructor stores a vtable address at [rcx], and a function prints [rcx+0Ch] as a float alongside [rcx+8] with "pos %.1f,%.1f".

Reconstruction:

C++
struct Entity              // reconstructed
{
    void* vftable;         // 0x00  written by the constructor (lesson 9.06)
    float x;               // 0x08  printed with "pos %.1f,%.1f"
    float y;               // 0x0C
    float vx;              // 0x10  added to x each update: a velocity
    float vy;              // 0x14  (by symmetry with x/vx; confirm in the debugger)
    int health;            // 0x18  signed, compared with 0
    bool alive;            // 0x1C
    // 0x1D..0x1F          padding before the pointer
    Entity* target;        // 0x20  dereferenced, and its first member looks like a vtable
};                         // size 0x28 if nothing follows (check the allocation size in the creator)

The size can usually be confirmed where objects are created: operator new(0x28) or a HeapAlloc with that size right before the constructor call.

Recording it

In Ghidra, create the structure in the Data Type Manager, fill in the members, and Retype the parameter (Ctrl+L) in every function that receives it. Keep a notes file alongside: which evidence supports each member, and which are guesses. When new evidence contradicts a guess, you will know which to revisit.

Common mistakes

Assuming you have seen every member

Code you have not looked at may use offsets you have not seen. Mark uncertain regions as unknown rather than as padding.

Ignoring the creator

The allocation size and the constructor's initial values are some of the best evidence for a struct's size and members.

Over-trusting names

A member you called "health" is a hypothesis until behaviour confirms it.
