Entities, Components and Systems

lesson 10.033 of 9 in milestone 106 min

How should a game represent its thousands of objects? Deep inheritance trees (Monster : Character : Entity) become rigid and slow. Many engines use entity-component-system (ECS) design instead: an entity is just an id, components are plain data attached to it, and systems are loops over every entity with a given set of components. This lesson explains why, and builds a small ECS on the sparse set structure.

The trouble with deep hierarchies

The object-oriented first attempt at a game world looks like this:

flowchart TB
    E["Entity"] --> C["Character"]
    E --> P["Prop"]
    C --> PL["Player"]
    C --> M["Monster"]
    M --> F["FlyingMonster"]
    P --> B["Barrel"]

Then the designers ask for a barrel that can fly, a monster that can be picked up like a prop, and a player who can turn into a barrel. Each request fits awkwardly into the tree, and features drift up into the base class until Entity has a hundred members, most unused by most objects. Performance suffers too: each object is a separate heap allocation with a vptr, updating them means a virtual call each, and their data is scattered (lessons 3.02, 3.05).

Composition: entities, components, systems

ECS splits things differently:

Part Is Example
Entity An id. Nothing else. Entity{ 42 }
Component A small, plain struct of data, attached to an entity Position{ x, y }, Velocity{ vx, vy }, Health{ hp }, Sprite{ textureId }
System A function that loops over every entity having certain components Movement: every entity with Position and Velocity

A flying barrel is just an entity with Position, Velocity, Sprite and Breakable. A monster you can pick up has Carryable added. No class hierarchy has to change: behaviour comes from which components an entity has, and which systems act on them.

C++
void movementSystem(World& world, float dt)
{
    for (Entity e : world.with<Position, Velocity>())
    {
        Position& p{ world.get<Position>(e) };
        const Velocity& v{ world.get<Velocity>(e) };
        p.x += v.vx * dt;
        p.y += v.vy * dt;
    }
}

Why it is fast

Each component type is stored in its own dense array: all Positions side by side, all Velocitys side by side. A system walks those arrays in order, which is exactly what caches and vectorisation want (lessons 2.07, 7.09): no pointer chasing, no virtual calls, every byte loaded is used. This layout is called data-oriented design, and it is the main reason large engines adopted ECS.

The sparse set

How do you store components so that you can (a) loop over all of them densely, (b) find an entity's component instantly, and (c) add and remove them cheaply? The usual answer is a sparse set per component type:

Output
sparse: indexed by entity id → position in the dense arrays (or "none")
        [0]: none   [1]: 0   [2]: none   [3]: 2   [4]: 1

dense:  entity ids in order       [1]  [4]  [3]
        components, same order    {P1} {P4} {P3}
Operation How Cost
Does entity e have it? sparse[e] != none Constant
Get e's component components[sparse[e]] Constant
Add to e Append to the dense arrays; sparse[e] = new index Constant (amortised)
Remove from e Swap-and-pop (lesson 3.07): move the last element into e's slot, fix the moved entity's sparse entry Constant
Loop over all Walk the dense arrays Fast, contiguous

It combines lesson 3.07's swap-and-pop with lesson 3.10's stable ids. The practice task builds one.

Systems that need several components

world.with<Position, Velocity>() must find entities that have both. With sparse sets, loop over the smaller of the two sets and check the other with a constant-time lookup. Larger engines group entities by their exact set of components into archetypes, each stored as its own table, so every system's loop is a straight walk with no checks; that is how Unity's DOTS and the flecs library work. EnTT, a popular open-source C++ ECS, is built on sparse sets.

When not to use ECS

ECS shines with many similar objects and simple, repeated behaviour. For a game with a few dozen unique objects, or for one-off logic (a boss's scripted sequence, the user interface), plain classes are simpler and fine. Many shipped games mix both: an ECS for the crowd, ordinary objects for the rest.

Common mistakes

Putting logic in components

Components are data. Behaviour lives in systems.

Keeping pointers to components

Removing another entity's component can move this one (swap-and-pop). Store the entity id and look the component up.

Adding or removing components while a system loops over them

The arrays change under the loop. Queue structural changes and apply them after the system finishes.
