Game State and Save Files

lesson 10.077 of 9 in milestone 106 min1 practice task

Saving a game means deciding what state matters, writing it in a format that will still load after the game is updated, and never leaving a corrupted file behind. This lesson covers what to save and what to rebuild, binary and text formats, versioning and migrating old saves, checksums that detect damage, and writing files safely.

What to save

A running game holds far more state than needs saving. Divide it:

Save Rebuild on load Do not save
The player's position, stats, inventory, quest flags Anything derived: collision grids, pathfinding data, cached totals Pointers and handles (lesson 6.09): they mean nothing next time
What has changed in the world: opened chests, killed bosses Static level content: it comes from the level file Rendering state, GPU resources
Settings the player chose Temporary effects that do not matter

A useful principle: save the minimum from which everything else can be rebuilt. Small saves are fast to write, and less saved state means fewer ways for a save to be inconsistent.

References between saved objects (a quest that refers to an NPC) are saved as ids, and resolved back to objects after loading, never as pointers.

Binary or text

Binary Text (JSON, INI, your own)
Size and speed Small and fast Larger and slower to parse
Readable by people No Yes: easy to inspect and debug
Robust to change Needs explicit versioning Easier to add fields (unknown keys can be ignored)
Editable by players Hard Easy, which may or may not be wanted

Many games use text during development and binary when shipping, or text for settings and binary for saves. Whichever you choose, write fields individually in a defined byte order (lesson 2.06), never by dumping structs from memory: padding, pointers and compiler differences would all leak into the file.

A header with a version

Every save file should start with a small fixed header:

C++
// Written field by field, little-endian, 16 bytes:
//   magic     4 bytes   'S','A','V','E'      what kind of file this is
//   version   4 bytes   format version        how to read the rest
//   length    4 bytes   bytes after the header
//   checksum  4 bytes   CRC-32 of those bytes
  • The magic number rejects files that are not saves at all.
  • The version lets the game read old formats after updates.
  • The checksum detects corruption: truncated writes, disk errors, a file damaged in transfer.

Versioning and migration

Games change after release, and players expect their saves to keep working. The usual approach: each format version gets a loader, and old versions are migrated step by step to the current one:

flowchart LR
    V1["version 1 file"] -->|"migrate 1→2:<br/>add 'gold', default 0"| V2["version 2 data"]
    V2 -->|"migrate 2→3:<br/>split 'name' into first/last"| V3["version 3 data<br/>(current)"]

Each migration is small and tested once, and a save from any old version passes through all of them. Never reuse a version number for a different layout, and keep test saves from every released version so you can check old saves still load.

Checksums

A checksum is a number computed from all the bytes, stored alongside them. On loading, recompute it; if it differs, the data is damaged. CRC-32 is the standard choice: it catches accidental corruption (bit flips, truncation, garbage) with very high probability, and it is cheap. The practice task implements it.

A CRC detects accidents, not deliberate tampering: anyone who edits a save can recompute it. Preventing cheating in a single-player game is rarely worth it; in multiplayer, anything that matters must live on the server, not in a file on the player's machine.

Writing safely

Lesson 5.04's technique applies fully: write the whole save to a temporary file, flush it, then atomically replace the old save. Keeping the previous save as a backup (slot1.sav.bak) as well means even a save that was written correctly but contains a game bug can be recovered.

Common mistakes

[!warning] Dumping structs to disk with fwrite(&state, sizeof state, ...) Padding, pointers and layout differences make the file fragile and unportable. Write fields one by one.

No version number

The first update that changes the format breaks every existing save.

Overwriting the save in place

A crash mid-write destroys it. Write a temporary file and replace.

Trusting the file

A save may be damaged or edited. Check the magic, the version, the checksum and every length before using the data.
