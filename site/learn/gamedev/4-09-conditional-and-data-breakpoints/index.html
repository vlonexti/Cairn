Conditional and Data Breakpoints

lesson 4.099 of 10 in milestone 47 min1 practice task

A plain breakpoint stops every time. In a game loop that runs 60 times a second, that is useless. Conditions, hit counts and filters make a breakpoint stop only when it matters; tracepoints log without stopping; and data breakpoints stop on the exact instruction that changes a piece of memory, which is the fastest way to find who corrupted a value.

Making breakpoints selective

Right-click a breakpoint's red dot → Conditions (or hover and press the gear icon) to add any of these:

Setting Stops when Example
Conditional expression, Is true The expression is true enemy.health < 0
Conditional expression, When changed The expression's value differs from last time player.state
Hit count It has been reached a given number of times = 500, >= 100, is a multiple of 60
Filter On a particular thread or process ThreadId = 12345

Conditions are evaluated by the debugger each time the line is reached, which makes the program slower while the breakpoint is set; that is usually fine.

A typical use: an enemy occasionally gets negative health and you do not know which one or when. Put a breakpoint on the line that subtracts damage, with the condition health - amount < 0 && id == 17. The game runs normally until exactly that moment.

Tracepoints: printing without stopping

Tick Actions in the same settings panel and the breakpoint becomes a tracepoint: instead of (or as well as) stopping, it writes a message to the Output window. Put expressions in braces:

Output
frame {frameCount}: {name} takes {amount} damage, health now {health}

Leave Continue code execution ticked and the program does not pause at all. It is std::cout debugging without editing, rebuilding or remembering to remove the lines afterwards. Special keywords like $FUNCTION, $CALLER and $TID add context.

Data breakpoints: who changed this?

Lesson 2.09's hardest bug was "something overwrote this value, and I don't know what". A data breakpoint stops the program on the instruction that writes to a given address, whoever does it, wherever the code is.

  1. Run to a point where the variable exists, for example a breakpoint just after hero is constructed.
  2. In Locals or Watch, right-click the variable → Break When Value Changes. Or Debug → New Breakpoint → Data Breakpoint, and enter an address expression such as &hero.gold and a size of 4 bytes.
  3. Continue (F5).

When any instruction changes those bytes, the debugger stops just after it, showing the line and the Call Stack. If the culprit is an overrun from the neighbouring name array (lesson 2.09), the stack points straight at the copy loop.

How it works, and its limits

Data breakpoints use the processor's debug registers. x64 CPUs have four of them, DR0 to DR3, each holding an address to watch for writes (or reads). The CPU itself checks every memory access against them, so the program runs at full speed. The hardware imposes limits:

Limit Why
At most 4 data breakpoints at a time 4 debug registers
Each watches 1, 2, 4 or 8 bytes The hardware's sizes
The address must be aligned to that size Hardware requirement
An address, not a variable A local's address is only valid while its frame exists; the breakpoint stays on the address after the frame is gone

That last row matters. Set a data breakpoint on a local, return from the function, and the breakpoint now watches whatever reuses that stack memory. Visual Studio removes data breakpoints when the process ends, but not when a frame ends; delete them yourself when they are no longer meaningful.

A worked hunt

The Debug heap reported "HEAP CORRUPTION DETECTED after normal block #312". Steps:

  1. Turn on _CrtSetDbgFlag leak checking and rerun to confirm block 312 is the same each run (allocation numbers are stable if the program does the same things).
  2. Call _CrtSetBreakAlloc(312) at the start of main: the debugger stops when block 312 is allocated, and the Call Stack shows what it is.
  3. Note its address and size. Set a data breakpoint on the 8 bytes just after its end, where the guard bytes are.
  4. Continue. The program stops on the instruction that writes past the end.

That is the whole bug, found in four steps without reading a single line of unrelated code.

Common mistakes

Slow conditions on very hot lines

A condition evaluated millions of times per second makes the game crawl. Put the breakpoint on a less frequent line, or add a cheap check in code temporarily.

Data breakpoints left on reused memory

After the variable's lifetime ends, the address belongs to something else. Delete the breakpoint.

Watching more than 8 bytes

Hardware only watches up to 8 bytes per breakpoint. For a larger region, watch the specific field that goes wrong, or the guard bytes at its edge.
