System Calls: Crossing the Boundary

lesson 15.022 of 8 in milestone 155 min1 practice task

Every time a program opens a file, allocates memory or waits on an event, it crosses from user mode into the kernel and back. This lesson follows one call, CreateFileW, through kernelbase.dll and ntdll.dll to the syscall instruction and into the kernel's system service dispatcher, and explains the rule that makes the boundary safe: the kernel never trusts anything that comes from user mode.

Following CreateFileW down

flowchart TB
    G["game.exe<br/>CreateFileW(L'save.dat', ...)"] --> KB["kernelbase.dll!CreateFileW<br/>converts parameters, builds an object path"]
    KB --> ND["ntdll.dll!NtCreateFile<br/>a tiny stub: system call number in eax, then syscall"]
    ND -->|"syscall: switch to ring 0"| SD["Kernel: system service dispatcher<br/>looks up the call number in a table"]
    SD --> NT["ntoskrnl!NtCreateFile<br/>validates and captures the parameters"]
    NT --> IO["I/O manager → file system driver → storage drivers (lesson 15.05)"]
    IO -->|"result in a status code"| NT
    NT -->|"sysret: back to ring 3"| ND
    ND --> KB
    KB -->|"handle, or INVALID_HANDLE_VALUE with GetLastError"| G
  • The documented Windows API (lesson 5.x) lives in kernel32.dll and kernelbase.dll. It translates friendly parameters into the kernel's.
  • The native API is in ntdll.dll: functions named Nt... (and Zw...). Each is a few instructions: put the system call number in eax, and execute syscall.
  • The syscall instruction switches the processor to ring 0 and jumps to the kernel's single entry point, which uses the number to find the right kernel function in its system service table.
  • The kernel's function does the work and returns an NTSTATUS code; sysret returns to user mode; kernelbase converts the status into a Win32 error for GetLastError (lesson 5.02).

You can see a stub in the debugger: in any program, open the Disassembly window at ntdll!NtCreateFile (lesson 4.08):

Assembly
ntdll!NtCreateFile:
    mov   r10, rcx              ; the syscall instruction overwrites rcx, so the first argument moves to r10
    mov   eax, 55h              ; the system call number (it differs between Windows versions)
    test  byte ptr [7FFE0308h], 1
    jne   use_int2e             ; an alternative path on some systems
    syscall                     ; into the kernel
    ret

The numbers change between Windows builds, which is one reason programs use the documented API rather than calling syscall themselves.

NTSTATUS

Kernel functions return NTSTATUS values, 32-bit codes like HRESULTs (lesson 5.02): negative for errors. Common ones: STATUS_SUCCESS (0), STATUS_ACCESS_DENIED (0xC0000022), STATUS_OBJECT_NAME_NOT_FOUND (0xC0000034), STATUS_INVALID_PARAMETER (0xC000000D). Lesson 8.04's exception codes are NTSTATUS values too: 0xC0000005 is STATUS_ACCESS_VIOLATION. Chapter 16's drivers return these from every function.

The kernel never trusts user mode

A system call hands the kernel values from user mode: numbers, and pointers into user memory. Any of them may be wrong by accident or by malice: a pointer into kernel space, a length that overflows, a buffer another thread changes while the kernel reads it. The kernel defends itself with three rules, and every driver that accepts requests from user mode must follow them too (lesson 16.07):

  1. Probe: check that a user pointer and length describe memory entirely within the user part of the address space (ProbeForRead, ProbeForWrite), so a caller cannot trick the kernel into reading or writing kernel memory on its behalf. Watch for overflow: address + length must not wrap around.
  2. Capture: copy the user's data into kernel memory once, and then use only the copy. Otherwise another user thread can change the data between the kernel checking it and using it: a time-of-check to time-of-use (TOCTOU) bug.
  3. Guard the access: user memory can be freed or protected at any moment by another thread, so kernel code touches it only inside a structured exception handler (__try/__except) that turns a fault into an error status instead of a bug check.

The practice task implements the probing arithmetic.

Previous mode

The kernel records whether a call came from user mode or from kernel code (the previous mode). Calls from kernel mode (drivers calling ZwCreateFile) skip some checks because kernel callers are trusted. This is why drivers must be careful never to pass user-supplied pointers on to kernel functions as if they were their own: the checks that protected the kernel would be skipped.

Common mistakes

[!warning] Calling Nt functions or syscall directly in applications Undocumented, changing between versions, and unnecessary. Use the Windows API.

Checking a user buffer, then reading it again later

Capture it once into kernel memory; the user can change it between the two reads.

Forgetting overflow in range checks

address + length can wrap past the end of the address space and appear valid.
