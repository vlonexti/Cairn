Static Storage and the Layout of a Program in Memory

lesson 2.033 of 11 in milestone 27 min1 practice task

Besides the stack and the heap, a running program has memory that exists for its whole life: its code, its constants and its global and static variables. These come straight from the .exe file, in named sections. Knowing the layout tells you at a glance what kind of thing an address points to.

Three kinds of storage

Every object in a C++ program has a storage duration: how long its memory exists.

Storage duration Examples Lives Memory comes from
Automatic Locals, function arguments Until the block or function ends The stack
Dynamic Anything from new, containers' contents Until freed The heap
Static Globals, static variables, string literals The whole run of the program The program's own image

The last row is this lesson's subject. Static storage is not allocated while the program runs at all. It is laid out by the compiler and linker, written into the .exe file, and mapped into memory by the loader before main starts.

Sections of an executable

The linker groups everything with static storage into sections, each with its own purpose and its own memory protection.

Section Holds Protection when loaded
.text The machine code of every function Read and execute
.rdata Read-only data: string literals, const globals, tables the compiler generates Read only
.data Global and static variables that start with a value Read and write
.bss part of .data Globals that start at zero. They take no room in the file, only in memory Read and write
.pdata, .reloc, .idata ... Bookkeeping for exceptions, relocation and imports Read only

The protections are enforced by the processor, page by page. Writing to .rdata or .text crashes the program with an access violation. Chapter 6 explains page protection, and chapter 9 reads these sections straight out of an .exe.

C++
#include <iostream>

int g_highScore{ 1200 };          // .data: starts with a value, can change
int g_frameCount;                 // zero-initialised: takes no space in the .exe file
const int g_maxLives{ 3 };        // .rdata (or folded straight into the code)
const char* g_title{ "Dungeon" }; // the pointer is in .data; the characters are in .rdata

int nextId()
{
    static int counter{ 0 };      // static local: lives in .data, initialised once
    return ++counter;
}

int main()
{
    std::cout << nextId() << ' ' << nextId() << ' ' << nextId() << '\n';
    std::cout << g_highScore << ' ' << g_frameCount << ' ' << g_maxLives << ' ' << g_title << '\n';
    return 0;
}
Output
1 2 3
1200 0 3 Dungeon

The static local counter behaves like a global with a private name. It is initialised once, the first time nextId runs, and keeps its value between calls because it is not in any stack frame.

The whole picture

Put the three kinds of storage together and you have the outline of a process's memory. On 64-bit Windows the exact addresses are randomised (lesson 6.09), but the families are recognisable:

You can see the families by printing one address of each kind:

C++
#include <iostream>
#include <memory>

int g_global{ 7 };

void someFunction() {}

int main()
{
    int local{ 1 };
    auto onHeap{ std::make_unique<int>(2) };
    static int staticLocal{ 3 };

    std::cout << "code     " << reinterpret_cast<void*>(&someFunction) << '\n';
    std::cout << "literal  " << static_cast<const void*>("hello") << '\n';
    std::cout << "global   " << &g_global << '\n';
    std::cout << "static   " << &staticLocal << '\n';
    std::cout << "heap     " << onHeap.get() << '\n';
    std::cout << "stack    " << &local << '\n';
    return 0;
}
Output (yours will differ)
code     00007FF7A3E413B6
literal  00007FF7A3E5AC28
global   00007FF7A3E61000
static   00007FF7A3E61004
heap     0000020E6C8F5E30
stack    000000E4F1CFF6A4

Look at the first four. They share most of their digits (00007FF7A3E...), because code, literals and globals are all parts of the same image, loaded as one block. Within it, code comes first, then read-only data, then writable data. The heap and the stack are somewhere else entirely, and each looks different. With a little practice you can tell what a pointer points at from its value alone: a very useful skill in the Memory window.

Initialisation order, and why globals are risky

Globals with simple constant initial values are written straight into the .data section by the linker, so they are ready before any code runs. Globals that need code to initialise them (a std::string, a std::vector, anything with a constructor) run that code before main, in an order that is only defined within one .cpp file. Across files, the order is unspecified. A global in a.cpp that uses a global from b.cpp during its own initialisation may see it not yet constructed. This is called the static initialisation order fiasco.

The usual fix is the pattern nextId used: a function holding a static local. The local is initialised the first time the function is called, whatever order things happen in, and C++ guarantees this is safe even with threads.

C++
#include <string>

const std::string& defaultPlayerName()
{
    static const std::string name{ "Adventurer" };   // built on first use, then kept
    return name;
}

More generally, mutable globals make code hard to follow and hard to test, because any function might change them. Use them sparingly. Constants are fine.

Common mistakes

Writing through a pointer to a string literal

char* s = (char*)"hello"; s[0] = 'J'; crashes: the characters are in read-only .rdata. Copy the text into a std::string or a char array first.

Returning a pointer to a static buffer

A function that fills a static char buffer[64] and returns it hands every caller the same buffer, so the second call overwrites what the first caller still holds. It is also unsafe with threads.

Assuming globals in different files are initialised in a particular order

They are not. Use a function with a static local for anything that other globals depend on.

Knowledge check

quizIn Xenon your best score is kept.
  1. Which section holds the characters of the string literal "Game Over"?
    • .text
    • .rdata
    • .data
    Show the answer

    .rdata Literals are read-only data. Writing to them is an access violation.

  2. A static int counter{ 0 }; inside a function. How many times is counter initialised?
    • Once, the first time the function runs
    • Every time the function is called
    • Never: statics are always zero
    Show the answer

    Once, the first time the function runs A static local lives in static storage for the whole program and is initialised the first time control reaches its declaration.

  3. Two addresses are 00007FF6C1A21000 and 00007FF6C1A3B0E0. What is the most likely relationship?
    • They are both inside the same loaded image, such as the program's own code and data
    • One is on the stack and one is on the heap
    • They belong to two different processes
    Show the answer

    They are both inside the same loaded image, such as the program's own code and data They share their high digits and differ only in the low ones: about 100 KB apart, typical of sections within one module.

  4. Why does a zero-initialised global array of a million ints not make the .exe four megabytes bigger?
    • The compiler compresses it
    • Zero-initialised data takes no space in the file: the loader just provides zeroed memory for it
    • Globals are always allocated on the heap
    Show the answer

    Zero-initialised data takes no space in the file: the loader just provides zeroed memory for it The file only records how much zeroed memory is needed, not the zeros themselves.
