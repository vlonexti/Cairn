The Game Loop

lesson 10.011 of 9 in milestone 105 min

Every real-time game is built around one loop that runs as long as the game does: read input, update the world, render a frame, repeat, dozens of times a second. This lesson builds that loop step by step, explains what belongs in each phase, and shows how an engine is organised around it.

The heart of every game

A word processor waits for the user to do something. A game does not wait: monsters move, timers tick and the screen redraws whether or not the player touches anything. So at the centre of every game engine is a loop:

flowchart LR
    I["Process input<br/>keys, mouse, pad, network"] --> U["Update<br/>move, collide, think, animate"]
    U --> R["Render<br/>draw the current state"]
    R --> I

Each trip round the loop produces one frame. At 60 frames per second the whole loop has 16.7 ms (lesson 8.08).

C++
#include <chrono>
#include <iostream>

struct World { float x{ 0 }; float speed{ 2.0f }; int frames{ 0 }; bool running{ true }; };

void processInput(World&) { /* read keys; set flags such as world.running = false on Escape */ }

void update(World& w, float dt)
{
    w.x += w.speed * dt;               // move 2 units per second, however long the frame was
    ++w.frames;
    if (w.x >= 1.0f) w.running = false;
}

void render(const World& w) { std::cout << "frame " << w.frames << ": x = " << w.x << '\n'; }

int main()
{
    World world;
    const float dt{ 0.1f };            // pretend each frame takes 0.1 s, so the output is the same every run
    while (world.running)
    {
        processInput(world);
        update(world, dt);
        render(world);
    }
    return 0;
}
Output
frame 1: x = 0.2
frame 2: x = 0.4
frame 3: x = 0.6
frame 4: x = 0.8
frame 5: x = 1

A real game measures dt with a clock (lesson 5.07) instead of pretending; the next lesson covers how to use it well.

What goes in each phase

Phase Does Must not
Input Drain the window messages (lesson 5.05's PeekMessage loop), read devices, turn them into actions (lesson 10.05) Change the world directly
Update Advance the simulation by dt: movement, physics, AI, timers, animation, game rules, spawning and removing entities Draw anything, or wait for anything
Render Draw the world as it is now: sprites, models, effects, interface Change the world

Keeping these separate is what lets engines run update at a fixed rate while rendering as fast as possible (lesson 10.02), run rendering on another thread, record and replay input, or run a server with no rendering at all.

The engine around the loop

An engine is mostly the systems that the loop calls each frame:

flowchart TB
    L["Game loop"] --> IN["Input system"]
    L --> SIM["Simulation<br/>entities and components (10.03)"]
    SIM --> PH["Physics and collision"]
    SIM --> AI["AI and scripts (10.08)"]
    SIM --> AN["Animation"]
    L --> AU["Audio"]
    L --> RE["Renderer (10.04)"]
    RES["Resource manager (10.06)"] --> RE
    RES --> AU
    RES --> SIM

A small game calls these in a fixed order on one thread. A large engine spreads their work across worker threads with a job system (lesson 6.05) while keeping the same overall order, because order matters: physics must run after movement is decided and before rendering, or the frame shows stale positions.

Starting and stopping

Around the loop sit initialisation (create the window, load the first level, start subsystems in dependency order) and shutdown (stop them in the reverse order, as RAII does for objects, lesson 2.04). Many engine bugs are ordering bugs here: audio shut down before the entities that still play sounds, a resource released before the renderer stops using it.

Common mistakes

Updating in the render phase

Rendering must only read the state, or the result depends on how often frames are drawn.

Waiting inside the loop

Blocking on a file, the network or a lock stalls every frame. Move slow work to other threads (lesson 6.05) and check its result each frame.

Moving by a fixed amount per frame

x += 2 moves twice as fast at 120 fps as at 60. Multiply by dt.
