A Minimal Debugger of Your Own

lesson 12.033 of 7 in milestone 125 min1 practice task

Visual Studio, WinDbg and x64dbg are all built on the same Windows debugging API. This lesson uses it directly to write a tiny debugger: it launches a program of yours as its debuggee, receives debug events (process and thread creation, DLL loads, exceptions, debug output, exit), reports them, and continues. It demystifies every debugger you have used, and is the core of crash-catching tools.

How debugging works on Windows

A debugger is an ordinary program that has a special relationship with its debuggee: Windows suspends the debuggee whenever something interesting happens and sends the debugger a debug event describing it. The debuggee stays frozen until the debugger says to continue.

sequenceDiagram
    participant D as Debugger
    participant W as Windows
    participant P as Debuggee
    D->>W: CreateProcessW(..., DEBUG_ONLY_THIS_PROCESS)
    W->>P: start, suspended at each event
    loop until the debuggee exits
        P-->>W: something happens (DLL load, exception, ...)
        W-->>D: WaitForDebugEvent returns the event
        D->>D: inspect: registers, memory, call stack
        D->>W: ContinueDebugEvent(handled or not)
        W->>P: carry on
    end

Every debugger you have used is this loop with a large interface around it.

The debug event loop

C++
#include <windows.h>
#include <cstdio>
#include <string>

int wmain(int argc, wchar_t** argv)
{
    if (argc < 2) { std::wprintf(L"usage: tinydbg program.exe\n"); return 1; }
    std::wstring command{ L"\"" + std::wstring(argv[1]) + L"\"" };
    STARTUPINFOW si{ sizeof(si) };
    PROCESS_INFORMATION pi{};
    if (!CreateProcessW(nullptr, command.data(), nullptr, nullptr, FALSE, DEBUG_ONLY_THIS_PROCESS, nullptr, nullptr, &si, &pi))
    {
        std::wprintf(L"could not start it: %lu\n", GetLastError());
        return 1;
    }

    bool running{ true };
    while (running)
    {
        DEBUG_EVENT ev{};
        if (!WaitForDebugEvent(&ev, INFINITE)) break;
        DWORD status{ DBG_CONTINUE };
        switch (ev.dwDebugEventCode)
        {
        case CREATE_PROCESS_DEBUG_EVENT:
            std::wprintf(L"process started, image at %p\n", ev.u.CreateProcessInfo.lpBaseOfImage);
            CloseHandle(ev.u.CreateProcessInfo.hFile);          // the event hands us a file handle: close it
            break;
        case LOAD_DLL_DEBUG_EVENT:
            std::wprintf(L"DLL loaded at %p\n", ev.u.LoadDll.lpBaseOfDll);
            CloseHandle(ev.u.LoadDll.hFile);
            break;
        case OUTPUT_DEBUG_STRING_EVENT:
            std::wprintf(L"debuggee says something (OutputDebugString)\n");
            break;
        case EXCEPTION_DEBUG_EVENT:
        {
            const EXCEPTION_RECORD& er{ ev.u.Exception.ExceptionRecord };
            const bool firstChance{ ev.u.Exception.dwFirstChance != 0 };
            std::wprintf(L"exception 0x%08lX at %p (%s chance)\n", er.ExceptionCode, er.ExceptionAddress, firstChance ? L"first" : L"second");
            if (er.ExceptionCode == EXCEPTION_BREAKPOINT) status = DBG_CONTINUE;           // the initial breakpoint, or ours
            else status = DBG_EXCEPTION_NOT_HANDLED;                                       // let the program's own handlers see it
            break;
        }
        case EXIT_PROCESS_DEBUG_EVENT:
            std::wprintf(L"process exited with code %lu\n", ev.u.ExitProcess.dwExitCode);
            running = false;
            break;
        }
        ContinueDebugEvent(ev.dwProcessId, ev.dwThreadId, status);
    }
    CloseHandle(pi.hThread);
    CloseHandle(pi.hProcess);
    return 0;
}

Run it on any small program of your own (tinydbg.exe delve.exe) and you will see the process start, every DLL load in order (ntdll, kernel32, KernelBase, the C++ runtime, SDL...), an initial breakpoint exception (0x80000003, lesson 8.04) that Windows raises in every debugged process just before its own code runs, and finally the exit.

First and second chance

When the debuggee raises an exception, the debugger gets it twice if needed:

  1. First chance: before the program's own exception handlers run. A debugger normally continues with DBG_EXCEPTION_NOT_HANDLED, letting the program handle it (a C++ throw that is caught arrives here and is harmless).
  2. Second chance: only if nothing in the program handled it. The program is about to crash. This is the moment to write a crash dump (lesson 8.04) with the process frozen exactly at the fault, which is how out-of-process crash reporters work: they are tiny debuggers.

Breakpoints, by hand

A software breakpoint (lesson 4.07) is now easy to understand in code:

  1. Read and remember the byte at the address (ReadProcessMemory).
  2. Write 0xCC there (WriteProcessMemory, then FlushInstructionCache).
  3. When the EXCEPTION_BREAKPOINT arrives with that address, the instruction pointer has moved one byte past the CC. Restore the original byte, move rip back by one with GetThreadContext/SetThreadContext, and continue (setting the trap flag to single-step once, so the breakpoint can be re-armed after the instruction runs).

Reading registers is GetThreadContext on the thread from the event (with CONTEXT_FULL), and the call stack is StackWalk64 from the DbgHelp library with symbols loaded (lesson 8.02). Everything Visual Studio's debugger shows is built from these calls.

Rights and limits

A debugger needs full access to its debuggee. Launching the debuggee yourself grants that. Attaching to a running process (DebugActiveProcess) requires the same rights as Visual Studio's Attach (lesson 4.07): your own processes at your integrity level; protected processes refuse (lesson 6.08). Only one debugger can be attached to a process at a time.

Common mistakes

Forgetting to close the file handles in events

CREATE_PROCESS_DEBUG_EVENT and LOAD_DLL_DEBUG_EVENT hand you file handles; not closing them leaks one per DLL.

Continuing every exception as handled

DBG_CONTINUE on a real exception re-executes the faulting instruction forever. Pass the program's own exceptions on with DBG_EXCEPTION_NOT_HANDLED.

Exiting the debugger while the debuggee runs

By default the debuggee is killed with it. Call DebugActiveProcessStop (or DebugSetProcessKillOnExit(FALSE)) to detach first.
