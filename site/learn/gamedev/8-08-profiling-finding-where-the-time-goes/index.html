Profiling: Finding Where the Time Goes

lesson 8.088 of 8 in milestone 86 min1 practice task

When a game is slow, the cause is almost never where you would guess. A profiler measures where the time actually goes. This lesson covers the two kinds of profiler (sampling and instrumenting), Visual Studio's CPU Usage tool, frame-based instrumentation with scoped timers, and how to read the results to find the few places worth optimising.

Measure, don't guess

Programmers are famously bad at predicting which code is slow. A function that looks expensive runs once per level; an innocent-looking std::string built every frame runs a million times. So the rule is: measure first, in a Release build (lesson 4.10), on realistic content, and optimise only what the measurement points at. Typically a small fraction of the code accounts for most of the time; finding that fraction is the whole job.

Two kinds of profiler

Sampling profiler Instrumenting profiler
How Interrupts the program thousands of times a second and records the call stack each time Code you add (or the compiler adds) records the start and end time of each marked section
Shows Statistically, which functions are on the stack most often Exact times for each marked section, frame by frame
Overhead Low; no code changes Small per marker; you choose what to mark
Good for "Where does the time go overall?" "Why was this frame slow?", spikes, timelines across threads
Examples Visual Studio CPU Usage, Windows Performance Analyzer, Superluminal, VTune Tracy, Optick, PIX markers, your own scoped timers

Games use both: sampling to find hot spots, instrumentation to understand frame-to-frame behaviour.

Visual Studio's CPU Usage tool

  1. Switch to Release (with /Zi and /DEBUG for symbols, lesson 8.06).
  2. Debug → Performance Profiler (Alt+F2), tick CPU Usage, press Start.
  3. Play the slow part of the game, then stop.

The report lists functions by:

  • Self CPU: time spent in the function's own code;
  • Total CPU: time in the function and everything it calls.

Start from the hot path (the report highlights it): the chain of calls with the highest total time from main down. A function with high total but low self time is not itself slow; something it calls is. A function with high self time is where the actual work happens. Instrumenting frames yourself

A scoped timer measures the time from its construction to its destruction (RAII again, lesson 2.04):

C++
#include <chrono>
#include <cstdio>

class ScopedTimer
{
public:
    explicit ScopedTimer(const char* name) : m_name{ name }, m_start{ std::chrono::steady_clock::now() } {}
    ~ScopedTimer()
    {
        const auto us{ std::chrono::duration_cast<std::chrono::microseconds>(std::chrono::steady_clock::now() - m_start).count() };
        std::printf("%-12s %6lld us\n", m_name, static_cast<long long>(us));
    }
private:
    const char* m_name;
    std::chrono::steady_clock::time_point m_start;
};

void updateFrame()
{
    ScopedTimer frame{ "frame" };
    { ScopedTimer t{ "physics" };   /* ... */ }
    { ScopedTimer t{ "ai" };        /* ... */ }
    { ScopedTimer t{ "render" };    /* ... */ }
}

Printing every frame is too noisy and too slow; real systems record the samples into a buffer and either show a live overlay (average and worst over the last second) or send them to a viewer such as Tracy, which draws a timeline of every frame across all threads. The practice task builds the aggregation step: totals, counts and worst cases per name.

Reading frame times

A game at 60 frames per second has 16.7 ms per frame for everything. A useful habit is to think in milliseconds per frame rather than frames per second, because milliseconds add up: physics 3 ms + AI 2 ms + rendering 9 ms = 14 ms, room to spare. Frames per second do not add.

Look at the worst frames as well as the average. A game that averages 8 ms but has a 40 ms frame every few seconds stutters, and players notice stutter more than a lower steady frame rate. Spikes usually come from occasional work: an allocation-heavy event, loading, garbage collection in a script language, a file write on the main thread.

What usually turns out to be slow

Common culprit Usual fix
Allocations every frame (strings, vectors, new) Reuse, reserve, pools, arenas (lessons 2.02, 3.10)
Pointer chasing over scattered objects Contiguous arrays, data-oriented layouts (lessons 2.07, 3.02)
Searching linearly in large containers every frame Hash maps, spatial grids (lesson 3.08)
Work done every frame that could be done once Cache the result, recompute only on change
Waiting: locks, file I/O, synchronous GPU reads on the main thread Move it to another thread or make it asynchronous

Common mistakes

Profiling a Debug build

Debug distorts everything: some functions are ten times slower, others hardly change. Profile Release.

Optimising what you guess is slow

Measure first; you will usually be surprised.

Reading total time as self time

A function at the top of the call tree always has a large total. Look for where the self time is.

Only watching the average frame time

Spikes cause stutter. Track the worst frames too.
