Trees and Graphs

lesson 3.099 of 10 in milestone 37 min

When data has branches rather than a single line, pointers or indices join it into trees and graphs. Games are full of them: the scene graph of objects attached to other objects, the binary search tree inside std::map, the graph of rooms in a dungeon, and the grid a monster searches to find the player. This lesson covers the shapes, the two ways to walk them, and a shortest-path search.

Trees

A tree is a set of nodes where each node has one parent (except the single root) and any number of children. There are no loops.

The most visible tree in a game is the scene graph: a sword is attached to a hand, the hand to an arm, the arm to a knight, the knight to a horse. Move the horse and everything attached moves with it.

flowchart TB
    W["World"] --> H["Horse"]
    W --> T["Tree"]
    H --> K["Knight"]
    K --> A["Arm"]
    A --> S["Sword"]
    K --> HE["Helmet"]
C++
#include <iostream>
#include <memory>
#include <string>
#include <vector>

struct SceneNode
{
    std::string name;
    float x{ 0 };                                     // position relative to the parent
    std::vector<std::unique_ptr<SceneNode>> children;

    SceneNode* add(std::string childName, float childX)
    {
        children.push_back(std::make_unique<SceneNode>(SceneNode{ std::move(childName), childX, {} }));
        return children.back().get();
    }
};

// Depth-first: handle a node, then each child's whole subtree in turn.
void printWorld(const SceneNode& node, float parentX, int depth)
{
    const float worldX{ parentX + node.x };
    std::cout << std::string(depth * 2, ' ') << node.name << " at " << worldX << '\n';
    for (const auto& child : node.children) printWorld(*child, worldX, depth + 1);
}

int main()
{
    SceneNode world{ "world", 0, {} };
    SceneNode* horse{ world.add("horse", 10) };
    SceneNode* knight{ horse->add("knight", 0.5f) };
    knight->add("sword", 0.75f);
    world.add("tree", 3);
    printWorld(world, 0, 0);
    return 0;
}
Output
world at 0
  horse at 10
    knight at 10.5
      sword at 11.25
  tree at 3

Each node owns its children through std::unique_ptr, so destroying a node destroys its whole subtree. Each position is relative to the parent, and the walk adds them up on the way down: that is how attaching works.

Binary search trees

A binary search tree gives each node at most two children with a rule: everything in the left subtree is smaller than the node, everything in the right is larger. Finding a key means comparing at each node and going left or right, so a balanced tree of a million entries needs about 20 comparisons.

std::map and std::set are balanced binary search trees (red-black trees in the common implementations). That is why they keep keys in order and why lookups cost "about log n" comparisons, not constant time like a hash table (lesson 3.08).

Graphs

A graph drops the tree's rules: any node can connect to any other, and connections can form loops. The nodes are often called vertices and the connections edges.

Game graph Vertices Edges
Dungeon layout Rooms Doors
Navigation mesh Walkable regions Shared borders
Tile map Walkable tiles Steps to neighbouring tiles
Dialogue Lines of dialogue Player choices
Quest dependencies Quests "Must finish first"

Graphs are usually stored as an adjacency list: for each vertex, a list of the vertices it connects to. A tile map is a graph that needs no stored edges at all, because a tile's neighbours can be calculated from its position.

Two ways to walk

Every tree and graph algorithm builds on one of two orders of visiting:

Depth-first search (DFS) Breadth-first search (BFS)
Order Go as deep as possible down one branch, then back up Visit everything 1 step away, then everything 2 steps away, ...
Natural tool A stack (or recursion) A queue
Good for Visiting everything, scene graphs, flood fills Shortest paths where every step costs the same

On a graph with loops, both must remember which vertices they have already visited, or they go round forever. The flood fill in lesson 2.01 was a depth-first search on a tile map.

Shortest path on a grid with BFS

To find how many steps a monster needs to reach the player, run a breadth-first search from the monster. Because BFS visits tiles in order of distance, the first time it reaches a tile, it has found the shortest way there.

C++
#include <iostream>
#include <queue>
#include <string>
#include <vector>

// Steps from (sx, sy) to (tx, ty) moving up, down, left or right through '.' tiles; -1 if unreachable.
int shortestSteps(const std::vector<std::string>& map, int sx, int sy, int tx, int ty)
{
    const int h{ static_cast<int>(map.size()) }, w{ static_cast<int>(map[0].size()) };
    std::vector<int> dist(static_cast<std::size_t>(w * h), -1);       // -1 means not reached yet
    std::queue<std::pair<int, int>> frontier;
    dist[static_cast<std::size_t>(sy * w + sx)] = 0;
    frontier.push({ sx, sy });
    const int dx[]{ 1, -1, 0, 0 }, dy[]{ 0, 0, 1, -1 };
    while (!frontier.empty())
    {
        const auto [x, y] = frontier.front();
        frontier.pop();
        if (x == tx && y == ty) return dist[static_cast<std::size_t>(y * w + x)];
        for (int d{ 0 }; d < 4; ++d)
        {
            const int nx{ x + dx[d] }, ny{ y + dy[d] };
            if (nx < 0 || ny < 0 || nx >= w || ny >= h || map[ny][nx] == '#') continue;
            int& seen{ dist[static_cast<std::size_t>(ny * w + nx)] };
            if (seen != -1) continue;
            seen = dist[static_cast<std::size_t>(y * w + x)] + 1;
            frontier.push({ nx, ny });
        }
    }
    return -1;
}

int main()
{
    const std::vector<std::string> map{
        "#########",
        "#M..#...#",
        "#.#.#.#.#",
        "#.#...#P#",
        "#########",
    };
    std::cout << shortestSteps(map, 1, 1, 7, 3) << '\n';
    return 0;
}
Output
12

The queue is the whole trick: tiles are taken out in the order they were discovered, so all tiles at distance 3 come out before any at distance 4. Storing which tile each one was reached from (a "came from" array) lets you walk back from the target to recover the actual path. When steps have different costs (mud is slower than road), BFS becomes Dijkstra's algorithm, and with a distance estimate to guide it, A*, which most game pathfinding uses. Chapter 11's monsters use this.

Common mistakes

Forgetting the visited set on a graph

A search on a graph with loops never ends. Mark vertices when you first discover them.

Recursion on deep trees

A very deep or degenerate tree (one long chain) can overflow the stack, as in lesson 2.01. Use an explicit stack for data that might be deep.

Marking visited when popping instead of when pushing

In BFS, mark a tile when you add it to the queue. Otherwise the same tile can be queued many times.

    Every node except the root has exactly one parent, and there are no loops A binary tree has at most two children; a tree in general may have any number.

  2. Why does breadth-first search find the shortest path when every step costs the same?
    • It visits places in order of their distance from the start, so the first time it reaches the target is by a shortest route
    • It tries every possible path and keeps the shortest
    • It always moves towards the target
    Show the answer

    It visits places in order of their distance from the start, so the first time it reaches the target is by a shortest route The queue ensures all places at distance n are handled before any at distance n + 1.

  3. What data structure drives a breadth-first search?
    • A stack
    • A queue
    • A hash table

    A queue First in, first out: places are explored in the order they were discovered.

  4. What kind of structure is std::map built on?
    • A hash table
