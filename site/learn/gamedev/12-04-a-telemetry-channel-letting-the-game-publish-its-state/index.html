A Telemetry Channel: Letting the Game Publish Its State

lesson 12.044 of 7 in milestone 125 min1 practice task

Delve will publish its live state (frame time, floor, the player's health and position, monster count) in shared memory for tools to read. The hard part is consistency: the game writes while the tool reads, so the tool must never see half an update. This lesson designs the shared block with a header and version, and protects it with a sequence lock, a lock-free scheme where the writer never waits.

What the game publishes

C++
// telemetry.h: shared by Delve and its tools. Plain data, fixed sizes, no pointers.
#pragma once
#include <atomic>
#include <cstdint>

struct TelemetryV1
{
    std::uint32_t magic;          // 'DLVT'
    std::uint32_t version;        // 1
    std::uint32_t size;           // sizeof(TelemetryV1): lets old tools read newer games (lesson 12.06)
    std::atomic<std::uint32_t> sequence;   // the sequence lock, below

    std::uint64_t frame;
    float frameMs;
    std::int32_t floor;
    std::int32_t playerX, playerY;
    std::int32_t playerHp, playerMaxHp;
    std::int32_t monstersAlive;
    std::uint32_t turn;
};

Every field is a fixed-size number at a fixed offset (lesson 2.05), the same in both programs because both include the same header. The header fields (magic, version, size) let a tool check, before trusting anything, that it is looking at the right kind of block and knows how to read it (lesson 10.07's save header, applied to memory).

The consistency problem

The game updates all these fields once per frame. A tool reading them at the same moment might copy playerX from the new frame and playerY from the old one, a position the player was never at. With a dozen fields, torn reads happen often enough to matter (lesson 6.06's data races, between processes).

A mutex shared between processes would work (a named mutex), but then the game could be made to wait by a slow or stuck tool, which is unacceptable: a tool must never be able to make the game stutter.

The sequence lock

A sequence lock (seqlock) lets one writer update freely while readers detect and retry torn reads:

Writer (the game, once per frame):

  1. Increment sequence (it becomes odd: "update in progress").
  2. Write all the fields.
  3. Increment sequence again (it becomes even: "consistent").

Reader (the tool):

  1. Read sequence. If it is odd, the writer is mid-update: try again shortly.
  2. Copy all the fields into a local struct.
  3. Read sequence again. If it changed, the writer updated during the copy: discard and retry. If it is the same (and even), the copy is consistent.
C++
// Game side, each frame:
t->sequence.fetch_add(1, std::memory_order_acq_rel);      // odd: writing
t->frame = frame; t->frameMs = ms; t->playerX = x; /* ... */
t->sequence.fetch_add(1, std::memory_order_release);      // even: done

// Tool side:
bool readSnapshot(const TelemetryV1* t, TelemetryV1& out)
{
    for (int attempt{ 0 }; attempt < 100; ++attempt)
    {
        const std::uint32_t before{ t->sequence.load(std::memory_order_acquire) };
        if (before & 1) continue;                            // being written: try again
        copyFields(out, *t);                                 // plain copy of the data fields
        std::atomic_thread_fence(std::memory_order_acquire);
        if (t->sequence.load(std::memory_order_relaxed) == before) return true;   // nothing changed meanwhile
    }
    return false;                                            // the game is writing constantly: report "busy"
}

The writer never waits for anyone: tools can be slow, stuck or crashed and the game does not notice. Readers occasionally retry, which costs nothing noticeable because the write takes well under a microsecond. Seqlocks are used in operating system kernels for exactly this pattern: frequently updated data with one writer and readers that can retry.

The memory-order arguments make sure the processor and compiler do not reorder the field writes across the sequence updates (lesson 6.06's atomics); the practice task models the protocol's logic.

Creating the channel in Delve

At start-up, Delve creates the mapping Local\Delve.Telemetry.<process id> (including the id lets several copies of the game run side by side), fills in magic, version and size, and publishes each frame. If creating it fails, the game simply runs without telemetry: tools are optional, the game is not. In shipping builds the channel can be left on (it is harmless) or compiled out like the console (lesson 11.07).

Common mistakes

Locking between the game and a tool

A stuck tool must never be able to stall the game. The writer must not wait.

Trusting the block without checking its header

Check the magic, version and size before reading fields.

Forgetting that a reader can loop forever

Bound the retries and report "busy" instead of hanging the tool.
