Sanitizers and Static Analysis

lesson 17.022 of 8 in milestone 175 min1 practice task

Tools find bugs that tests and reviews miss. Sanitizers add checks while the program runs (AddressSanitizer for memory, UndefinedBehaviorSanitizer for undefined behaviour); static analysis examines the code without running it (compiler warnings, MSVC's /analyze, clang-tidy, annotations). This lesson sets up each for a Visual Studio project and shows the classes of bug each one catches.

Two kinds of tool

Sanitizers (dynamic) Static analysis
How Instrument the program; check while it runs Analyse the source without running it
Finds Bugs on the paths actually executed Possible bugs on any path, including rare ones
False alarms Almost none: it saw the bug happen Some: it may flag code that cannot actually go wrong
Cost A slower test build Longer build time

They complement each other, and both complement tests.

Sanitizers

Sanitizer Catches On Windows
AddressSanitizer (ASan) Overruns, use-after-free, double free (lesson 2.10) MSVC /fsanitize=address; clang-cl too
UndefinedBehaviorSanitizer (UBSan) Signed overflow, invalid shifts, misaligned pointers, out-of-range enum values, null dereferences clang-cl (-fsanitize=undefined)
ThreadSanitizer (TSan) Data races (lesson 6.06) Not on Windows; run tests on Linux builds with clang or gcc if your code is portable
MemorySanitizer Reads of uninitialised memory Linux only

A practical setup: an ASan configuration in Visual Studio for the test suite and play sessions (lesson 2.10), and, if the code builds with clang, a clang-cl configuration with ASan and UBSan together. Visual Studio installs clang-cl with the "C++ Clang tools for Windows" component.

UBSan catches problems ASan cannot, such as int overflow (lesson 1.02), which can silently break checks like if (a + b < a) because the optimiser assumes signed overflow never happens.

Compiler warnings

The cheapest static analysis is already in your compiler:

  • Warning level 4 (/W4) and warnings as errors (/WX): lesson 4.03's table of valuable warnings.
  • /permissive- for standard conformance (Visual Studio's default for new projects).
  • Selected extra warnings with /w14xxx (enable warning xxxx at level 1), for example /w14062 (an enumerator not handled in a switch) and /w14265 (a class with virtual functions but no virtual destructor).

MSVC Code Analysis

Analyze → Run Code Analysis (or /analyze on every build) runs a deeper analysis: null dereferences on some paths, buffer overruns it can prove, uninitialised memory, resource leaks, misuse of Windows APIs, and the C++ Core Guidelines checks (/analyze with the Core Check rule sets). It understands SAL annotations (source annotation language) that describe what functions expect:

C++
// "dest points to destSize bytes the function writes; src is a zero-terminated string it reads."
size_t copyName(_Out_writes_z_(destSize) char* dest, size_t destSize, _In_z_ const char* src);

With the annotation, the analyzer checks every caller passes a buffer at least destSize long, and checks the function itself never writes past it. The Windows headers are fully annotated, which is how /analyze catches misuse of Windows API calls. Driver projects use the same annotations for IRQL rules (lesson 16.01).

clang-tidy

clang-tidy (included with Visual Studio's clang tools; enable it in Properties → Code Analysis → Clang-Tidy) checks style and bug patterns with hundreds of configurable checks: bugprone-* (suspicious patterns such as sizeof mistakes, swapped arguments), performance-* (unnecessary copies), modernize-* (C++ idioms), cppcoreguidelines-*. A .clang-tidy file in the solution folder chooses the checks for everyone.

Making it routine

Tools only help when they run all the time:

  1. Warnings at level 4, as errors, from day one.
  2. Code Analysis on every build in at least one configuration.
  3. The test suite run under ASan regularly, and in continuous integration (lesson 17.08).
  4. New warnings are fixed, not suppressed; when a suppression is genuinely right, it is narrow (one line, #pragma warning(suppress: ...)) with a comment saying why.

The practice task writes the overflow-checked arithmetic that UBSan and the analyzers push you towards.

Common mistakes

Turning tools on late in a project

Hundreds of warnings at once get suppressed wholesale. Start clean and keep it clean.

Blanket suppressions

#pragma warning(disable: ...) for a whole file hides future bugs too.

Assuming a clean run means no bugs

Sanitizers only see the paths that ran; analysers cannot see everything. Use all of them, plus tests.
