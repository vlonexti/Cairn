Health, Items and Inventory

lesson 11.055 of 8 in milestone 115 min1 practice task

Combat and loot turn Delve into a game. This lesson adds health and attack components, a damage formula with a little randomness, death and drops, item definitions loaded from data, pickups, and an inventory where identical items stack. Every number lives in a data file, so balancing never needs a rebuild.

Components for combat

Following lesson 10.03, combat is a few components and one system:

C++
struct Health   { int current; int maximum; };
struct Attack   { int power; int accuracy; };      // accuracy: chance to hit, in percent
struct Defence  { int armour; };
struct Drops    { std::string itemId; int chance; };  // percent

The player and every monster have Health, Attack and Defence; values come from monsters.ini (lesson 10.08), so a troll is just a different set of numbers.

The damage formula

When an attacker hits a defender:

  1. Roll to hit: a random number from 1 to 100; it hits if the roll is at most the attacker's accuracy.
  2. Damage: power − armour / 2, plus a small random spread (−1 to +1), but at least 1 so every hit matters.
  3. Subtract from the defender's health; at 0 or below, the defender dies.
C++
int rollDamage(const Attack& a, const Defence& d, Random& rng)
{
    if (rng.range(1, 100) > a.accuracy) return 0;             // a miss
    const int base{ a.power - d.armour / 2 };
    return std::max(1, base + rng.range(-1, 1));
}

Two habits make combat code easy to balance and test:

  • One random number generator object, passed in, never rand() scattered around. Seed it from the time in normal play and from a fixed number for tests and replays (lesson 10.02's determinism).
  • Log every combat event to the message log (lesson 8.03's ring buffer, shown on screen): "The goblin hits you for 3. (HP 17/20)". Players need the feedback, and you need it to see whether the numbers feel right.

Death and drops

When a monster dies, the combat system removes its entity (lesson 3.10's handles mean nothing else is left pointing at it) and, according to its Drops component, may place an item on its tile. The player dying ends the run with a "you died" screen showing the last few log lines, so the player knows why.

Items from data

INI
; items.ini
[potion]
name = Healing potion
heal = 10
stack = 5

[dagger]
name = Rusty dagger
power = 2
stack = 1

[gold]
name = Gold coins
stack = 999

An item definition (the data) is shared; an item in the world or inventory is just a definition id and a count. That keeps inventories small and makes "how many potions do I have?" a lookup.

The inventory

The inventory is a fixed number of slots (say 10). Each slot holds an item id and a count, up to that item's stack limit. Picking up items:

  1. First top up existing slots of the same item, up to the stack limit.
  2. Then put the rest into empty slots.
  3. Whatever does not fit stays on the floor.
Output
picking up 7 potions (stack 5) with slots:  [potion 4] [dagger 1] [empty] [empty]
→ [potion 5] [dagger 1] [potion 5] [potion 1]      nothing left over

Using an item removes one from its slot, and an empty slot becomes free. The practice task implements adding and removing with exactly these rules, which is the part most likely to hide off-by-one bugs.

Common mistakes

Damage that can be zero or negative

High armour should reduce damage, not heal the target. Clamp to at least 1 on a hit.

[!warning] Calling rand() everywhere Use one seeded generator object so tests and replays are repeatable.

Copying item definitions into every slot

Store an id and a count; look the definition up when needed.
