Testing and Hardening a Tool

lesson 12.077 of 7 in milestone 125 min1 practice task

A tool that crashes, hangs or shows wrong numbers is worse than none: people stop trusting it. This lesson hardens the chapter's tools: treating everything read from another process as untrusted input, validating snapshots, timeouts and reconnection, running with least privilege, and testing the logic separately from the platform code, including deliberately feeding it garbage.

Everything from outside is untrusted

The telemetry block, pipe messages and memory read from another process all come from a different program, which may be an older or newer version, half-initialised, crashed in the middle of writing, or simply buggy. Treat it exactly like a file from the internet:

Check Why
Header: magic, version, size (lesson 12.06) Is this even the right kind of data?
Sizes and counts against limits A count of 2 billion monsters means corruption, not a busy floor
Ranges Health between 0 and its maximum; positions inside the map; frame time positive and below, say, 10 seconds
Consistency Frame number never goes backwards (except after a restart, which the process id change reveals)
Strings Fixed-size character arrays must contain a terminator within their size (lesson 2.08)

A value that fails a check is shown as invalid, not used to index arrays or size allocations. The practice task writes a validator returning a list of problems.

Never hang

Every wait in a tool needs a limit:

  • Sequence-lock reads retry a bounded number of times (lesson 12.04).
  • Pipe reads use overlapped I/O or a timeout, so a game that stops responding does not freeze the tool.
  • Opening the game's mapping happens on a timer, not in a tight loop.

If the game is frozen, the tool should say so (lesson 12.05's "stale" state) and stay responsive.

Least privilege

The chapter's tools need very little:

  • Read-only views of the shared memory (FILE_MAP_READ).
  • PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE on the game's process, to watch whether it runs.
  • No administrator rights, ever: if a tool seems to need elevation, something in its design is wrong (lesson 6.08).

Asking for little keeps the tool working for ordinary users and limits the harm any bug in it can do.

Testing the logic

Every practice task in this course has followed one structure: the logic (formatting, validation, version checks, statistics, protocols) is plain C++ with no Windows calls, tested in isolation; a thin platform layer does the Windows calls. That pays off most in tools:

flowchart LR
    P["Platform layer<br/>OpenFileMapping, ReadProcessMemory,<br/>console output"] --> L["Logic<br/>validate, decode, compute,<br/>format: pure functions"]
    T["Unit tests<br/>(chapter 17)"] --> L
  • Unit tests feed the logic known inputs, including recorded real snapshots, and check the outputs.
  • Garbage tests feed it random bytes, truncated blocks, wrong versions, extreme values. The tool must report problems, never crash. Chapter 17 automates this as fuzzing.
  • End-to-end tests run the real game with a scripted input and check the tool shows what was expected.

Failure modes to rehearse

Before calling a tool done, try each of these on purpose:

  1. Start the tool with no game running.
  2. Start the game, then the tool; close the game; start it again.
  3. Pause the game in the debugger while the tool watches.
  4. Run two copies of the game.
  5. Run an older and a newer build of the game against the same tool.
  6. Corrupt the shared block from a test program (write random bytes into it).

A tool that handles all six calmly can be trusted.

Common mistakes

Using an untrusted count to size an allocation

A corrupt count of billions turns into a crash or an out-of-memory. Validate against a sensible limit first.

Waiting without a timeout

A frozen game must not freeze its tools.

Testing only the happy path

Rehearse the failure modes; they are what users will hit.
