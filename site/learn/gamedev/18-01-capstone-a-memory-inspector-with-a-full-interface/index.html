Capstone: A Memory Inspector with a Full Interface

lesson 18.011 of 4 in milestone 187 min1 practice task

The first capstone joins chapters 6, 12 and 14 into one polished tool: a read-only memory inspector for programs you built yourself, with a Dear ImGui interface showing the region map, a hex view with typed overlays, snapshots with change highlighting, and the telemetry channel from chapter 12. This lesson gives the specification, an architecture, the milestones in order, the acceptance tests and stretch goals.

What you are building

Xenon Inspector is a desktop tool for looking inside your own running programs while you develop them: Delve, the practice targets of lesson 9.10, and anything else you compile. It answers questions like "what does this struct look like in memory right now?", "which bytes changed when I picked up that item?" and "how is this program's address space laid out?".

The ground rules from chapter 12 are part of the specification, not an afterthought:

Scope
  • The inspector only opens processes whose executable lies under a folder you configure as your build output (for example D:\dev\bin), or processes it starts itself from there. It refuses anything else, with a message explaining why.
  • It is read-only: it never writes to the target's memory.
  • It uses documented APIs only (OpenProcess with PROCESS_QUERY_INFORMATION | PROCESS_VM_READ, VirtualQueryEx, ReadProcessMemory, the Tool Help snapshot functions) and needs no administrator rights.

Architecture

flowchart TB
    UI["ImGui panels<br/>(picker, regions, hex, overlay, snapshots, telemetry)"] --> M["Inspector model<br/>selected process, ranges, snapshots"]
    M --> P["Process access layer<br/>scope check, OpenProcess, VirtualQueryEx,<br/>ReadProcessMemory, module list"]
    M --> T["Struct definition parser"]
    M --> D["Snapshot diff"]
    M --> C["Telemetry reader (chapter 12)"]
    P --> W[("Windows APIs")]

Keep the layers separate, as lesson 17.01 recommends: the struct parser and the snapshot diff are pure functions with unit tests; the process access layer is the only code that calls Windows; the panels only draw the model and send it commands. Then most of the program can be tested without a target running.

Milestones

Build it in order; each milestone is usable on its own.

  1. Skeleton: the ImGui window from lesson 14.02 with an empty dock space, a settings file and the build-folder setting.
  2. Process access: list processes, apply the scope check (resolve the executable path with QueryFullProcessImageNameW, then check it is under the build folder after normalising both), open with the minimum rights. Unit-test the path check with lesson 17.04's lessons about .. and case.
  3. Region map: the VirtualQueryEx walk from lesson 6.04 on the target, shown in a sortable table with module names.
  4. Hex view: read on demand only the visible rows, handle unreadable pages (ReadProcessMemory fails or reads partially: show ??), and refresh at the configured rate.
  5. Snapshots and diff: copy a range, compare later, list changed ranges, highlight them in the hex view.
  6. Typed overlay: parse definitions such as struct Player { i32 health; f32 x; f32 y; u8 flags; } with natural alignment (lesson 2.05) and show the values.
  7. Telemetry: connect to the target's telemetry channel if it exists, and show its version check from lesson 12.06.
  8. Hardening: lesson 12.07's checklist: the target exiting at any moment, huge regions, invalid addresses typed by the user, and a fuzz test of the struct parser (17.03).

Acceptance tests

The inspector is done when:

  • it refuses a process outside the build folder, including one reached by a path with .., a different case, or a short 8.3 name;
  • it shows Delve's region map and its main module's base matches the one Delve prints (lesson 6.09);
  • the overlay of Delve's Player struct shows the health dropping when a monster hits;
  • a snapshot diff around the inventory shows exactly the bytes that change when an item is picked up;
  • closing Delve while the inspector is reading it gives a clear message, not a crash;
  • the unit tests pass under AddressSanitizer;
  • it never opens a handle with write or operation rights (verify with Process Explorer's handle view).

Stretch goals

  • Read the target's PDB with the DIA SDK or dbghelp to show real type names and fields instead of hand-written definitions.
  • A "watch list" of addresses with a plot of each value over time (lesson 14.04).
  • Export a snapshot and its overlay as a report for a bug ticket.

Common mistakes

Reading huge ranges every frame

Read only what is visible, and only at the refresh rate.

Mixing Windows calls into the UI code

It makes the inspector untestable and the UI slow when a read blocks.

Loosening the scope check "just for testing"

The rule is the feature. Keep test targets in the build folder.
