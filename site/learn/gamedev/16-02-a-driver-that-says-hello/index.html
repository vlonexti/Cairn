A Driver That Says Hello

lesson 16.022 of 10 in milestone 165 min1 practice task

The smallest useful driver has two functions: DriverEntry, called when it loads, and an unload routine, called when it is removed. This lesson writes them, prints to the kernel debugger, loads the driver in the lab VM as a service, watches its messages in WinDbg, and unloads it, the complete cycle every later lesson builds on.

The code

C++
// driver.cpp
#include <ntddk.h>

extern "C" DRIVER_INITIALIZE DriverEntry;     // declarations with the WDK's annotation types
DRIVER_UNLOAD EchoUnload;

void EchoUnload(PDRIVER_OBJECT driver)
{
    UNREFERENCED_PARAMETER(driver);
    KdPrint(("XenonEcho: unloading\n"));
}

extern "C" NTSTATUS DriverEntry(PDRIVER_OBJECT driver, PUNICODE_STRING registryPath)
{
    UNREFERENCED_PARAMETER(registryPath);
    driver->DriverUnload = EchoUnload;        // without this, the driver can never be unloaded
    KdPrint(("XenonEcho: hello from the kernel, IRQL %u\n", KeGetCurrentIrql()));
    return STATUS_SUCCESS;
}

Line by line:

  • DriverEntry is the driver's main. The I/O manager calls it once, at PASSIVE_LEVEL (lesson 15.06), with the driver object (lesson 15.05) and the path of the driver's registry key. It must be extern "C" so its name is not mangled (lesson 4.02).
  • It returns an NTSTATUS (lesson 15.02). Returning a failure code makes the I/O manager unload the driver at once, without calling its unload routine, so a failing DriverEntry must clean up anything it already did (lesson 16.03).
  • DriverUnload must be set for the driver to be stoppable. It undoes everything DriverEntry set up.
  • KdPrint sends text to an attached kernel debugger. It compiles to nothing in Release builds. (DbgPrintEx is the always-present version with component ids and levels.)
  • UNREFERENCED_PARAMETER silences warning C4100 for unused parameters, which matters because warnings are errors.

Loading it in the VM

Copy XenonEcho.sys (and its test certificate, lesson 16.09) to the lab VM, for example to C:\Drivers\. A software-only driver like this one can be loaded as a kernel service with the built-in sc tool, from an administrator prompt in the VM:

Terminal
sc create XenonEcho type= kernel binPath= C:\Drivers\XenonEcho.sys
sc start XenonEcho
sc stop XenonEcho
sc delete XenonEcho

(The space after each = is required by sc.) sc create writes the service's registry key under HKLM\SYSTEM\CurrentControlSet\Services\XenonEcho; sc start asks the kernel to load the driver and call DriverEntry; sc stop calls the unload routine and unloads it.

Hardware drivers are installed differently, through an INF file that plug and play uses to match them with devices; software drivers like this one do not need one.

Seeing the output

With WinDbg connected to the VM's kernel (lesson 15.08), enable debug output once per session and start the driver:

Output
kd> ed nt!Kd_DEFAULT_Mask 0xF
kd> g
Output
XenonEcho: hello from the kernel, IRQL 0
XenonEcho: unloading

Without a debugger attached, Sysinternals DebugView run as administrator in the VM (with "Capture Kernel" enabled) shows the same messages.

To stop in your code, set a breakpoint before starting the driver:

Output
kd> bu XenonEcho!DriverEntry
kd> g

bu sets an unresolved breakpoint that is placed when the module loads. When sc start runs, the whole VM freezes at DriverEntry, and you can step through it with p and inspect driver with dt nt!_DRIVER_OBJECT poi(driver) (lesson 8.05).

When it goes wrong

  • sc start fails with error 577 (ERROR_INVALID_IMAGE_HASH): the driver is not signed in a way the VM accepts. Check test signing is on and the driver is test-signed (lesson 16.09).
  • Error 2: the path in binPath is wrong.
  • A bug check: the VM stops, WinDbg breaks in with the bug check, and !analyze -v names your driver (lesson 15.07). Revert to your snapshot if the VM cannot boot.

Common mistakes

[!warning] Forgetting to set DriverUnload The driver can then never be stopped without a reboot.

[!warning] Missing extern "C" on DriverEntry The linker cannot find the entry point.

Loading on the host

Only in the lab VM.
