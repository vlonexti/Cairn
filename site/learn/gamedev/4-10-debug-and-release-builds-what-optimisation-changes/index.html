Debug and Release Builds: What Optimisation Changes

lesson 4.1010 of 10 in milestone 47 min

A Release build runs the same source code many times faster, because the optimiser rewrites it: it keeps values in registers, inlines functions, removes work whose result is unused, and assumes your code has no undefined behaviour. This lesson shows each transformation, explains why some bugs only appear in Release, and sets up a build that is both optimised and debuggable.

The same code, two programs

Compile this function in each configuration:

C++
int sumTo(int n)
{
    int total{ 0 };
    for (int i{ 1 }; i <= n; ++i)
        total += i;
    return total;
}

Debug (/Od, no optimisation) does exactly what the source says, keeping every variable in memory so the debugger can show it:

Assembly
sumTo PROC
    mov  DWORD PTR [rsp+8], ecx        ; store n to its stack slot
    sub  rsp, 24
    mov  DWORD PTR total$[rsp], 0
    mov  DWORD PTR i$[rsp], 1
    jmp  SHORT $check
$next:
    mov  eax, DWORD PTR i$[rsp]
    inc  eax
    mov  DWORD PTR i$[rsp], eax
$check:
    mov  eax, DWORD PTR n$[rsp]
    cmp  DWORD PTR i$[rsp], eax
    jg   SHORT $done
    mov  eax, DWORD PTR i$[rsp]
    mov  ecx, DWORD PTR total$[rsp]
    add  ecx, eax
    mov  DWORD PTR total$[rsp], ecx
    jmp  SHORT $next
$done:
    mov  eax, DWORD PTR total$[rsp]
    add  rsp, 24
    ret  0
sumTo ENDP

Release (/O2) keeps everything in registers, and may restructure the loop, unroll it, or even recognise the pattern and compute the answer with arithmetic. Every loop iteration in the Debug version reads and writes memory several times; the Release version barely touches memory at all. For code like this, Release is commonly 5 to 50 times faster.

What the optimiser does

Transformation What it means What you see in the debugger
Register allocation Variables live in registers instead of on the stack "Variable is optimised away and not available"
Inlining A small function's body is pasted into its caller; there is no call The function never appears in the Call Stack; breakpoints in it may not hit
Constant folding Expressions with known values are computed at compile time int x = 60 * 60; becomes 3600; no multiplication in the code
Dead code elimination Work whose result is never used is removed Breakpoints on those lines have nowhere to go
Loop transformations Unrolling, moving invariant work out of loops, vectorising with SIMD instructions Stepping jumps around unpredictably
Reordering Instructions are moved to keep the processor busy The yellow arrow seems to go backwards

None of this changes what a correct program does. The C++ standard lets the compiler make any change whose effect on the program's visible behaviour cannot be detected, the as-if rule.

Why some bugs only appear in Release

The as-if rule only applies to programs without undefined behaviour. The optimiser is allowed to assume there is none, and it uses that assumption aggressively:

  • Uninitialised variables hold 0xCC filler in Debug, which is at least consistent. In Release they hold whatever was in that register or stack slot, which changes with unrelated code.
  • Signed overflow: the compiler may assume i + 1 > i is always true for an int, and remove a check that relied on wrap-around.
  • Out-of-bounds reads: in Debug, the read gets the neighbouring variable; in Release, the neighbour may be in a register and the read gets something else.
  • Timing and threads: a variable shared between threads without synchronisation may be kept in a register in Release, so one thread never sees the other's change (chapter 6).

And Debug builds hide bugs with their extra help: 0xCC fill, guard bytes, iterator checks and assert all vanish in Release, because NDEBUG is defined there.

So when something "only breaks in Release", the answer is almost never "the optimiser has a bug". It is almost always undefined behaviour in your code that Debug happened to tolerate. AddressSanitizer (lesson 2.10) and warnings at level 4 find most of these.

Debugging an optimised build

You can debug Release builds, and you sometimes must, because the bug only happens there. Make it easier:

  1. Generate debug information in Release: C/C++ → General → Debug Information Format: Program Database (/Zi) and Linker → Debugging → Generate Debug Info: Yes. This costs nothing at run time; the .pdb is a separate file.
  2. Keep optimisation on, but optionally add /Zo (enhanced optimised debugging, on by default in recent versions), which records where variables live in registers so more of them can be shown.
  3. To debug one function without optimisation inside an optimised build, wrap it:
C++
#pragma optimize("", off)
void suspiciousFunction()
{
    // compiled without optimisation, so every variable is visible
}
#pragma optimize("", on)

Many studios use a third configuration for day-to-day work: optimised enough to run at a playable speed, with full debug information and asserts still enabled. In Visual Studio you can create it by copying Release in Configuration Manager and removing NDEBUG from its preprocessor definitions.

The settings that differ

Setting Debug Release
Optimisation /Od (off) /O2 (speed)
Runtime library /MDd (debug runtime) /MD
_DEBUG / NDEBUG _DEBUG defined NDEBUG defined: assert does nothing
Basic runtime checks /RTC1: stack frame checks, uninitialised use Off
Iterator debugging On (_ITERATOR_DEBUG_LEVEL=2) Off
Whole-program optimisation Off /GL and /LTCG: the linker can inline across files
Incremental linking On (fast rebuilds) Off

Common mistakes

Measuring performance in Debug

Debug can be ten times slower, unevenly. Always measure speed in Release (chapter 17).

[!warning] Putting real work inside assert assert(loadLevel(name)); loads the level in Debug and does nothing at all in Release. Do the work first, then assert on the result.

Blaming the optimiser

Look for undefined behaviour first: uninitialised values, overruns, signed overflow, data races.
