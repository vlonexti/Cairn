Virtual Address Spaces

lesson 6.022 of 9 in milestone 67 min1 practice task

Every address a program uses is virtual: the processor translates it, page by page, into a physical location in RAM using page tables the operating system maintains for each process. This lesson explains the translation, the size and shape of a 64-bit address space, why some addresses are impossible, and what happens when a page is not in RAM at all.

Every address is translated

Lesson 1.06 said each process has a private address space. Here is how that works. Every time the CPU reads or writes memory, the address goes through the memory management unit (MMU), part of the processor, which translates it from a virtual address to a physical address: a real location in the RAM chips.

flowchart LR
    C["CPU wants<br/>virtual 0x00007FF6A1234567"] --> M["MMU<br/>looks up the page tables<br/>of the current process"]
    M --> R["Physical 0x00000002_4C8F1567<br/>in RAM"]

Translation happens in units of pages, 4,096 bytes (0x1000) each. An address splits into two parts:

virtual address 0x00007FF6A1234567
                └────────┬───────┘└┬┘
                 page number        offset within the page: 0x567
                 0x7FF6A1234

The page number is looked up and replaced with a physical frame number; the offset stays the same. So within a page, bytes keep their order, but two neighbouring virtual pages can be anywhere in physical memory, in any order.

Because each process has its own page tables, the same virtual page number leads to different frames in different processes. When the scheduler switches to another process, it switches the CPU to that process's tables (by loading the register CR3), and the whole address space changes in one step.

Four levels of tables

A 64-bit address space is enormous. A single flat table with one entry per page would be gigabytes per process. So the tables are a tree with four levels, and only the parts that are actually used exist. On x64, the 48 significant bits of an address split like this:

 47     39 38     30 29     21 20     12 11          0
┌─────────┬─────────┬─────────┬─────────┬────────────┐
│ level 4 │ level 3 │ level 2 │ level 1 │  offset    │
│ 9 bits  │ 9 bits  │ 9 bits  │ 9 bits  │  12 bits   │
└─────────┴─────────┴─────────┴─────────┴────────────┘

Each 9-bit index picks one of 512 entries in a table; each entry points to the next level's table; the last level gives the physical frame. The practice task splits addresses this way.

Walking four tables for every memory access would be slow, so the CPU caches recent translations in the TLB (translation lookaside buffer). Nearly all accesses hit the TLB and cost nothing extra. Code that jumps randomly across a very large amount of memory misses it, which is another reason (besides the cache, lesson 2.07) to keep data compact.

The shape of a 64-bit address space

x64 processors use 48 bits of address today, not 64. The top 16 bits must all copy bit 47, which splits the space into two halves with a huge gap between them:

Range Size Used by
0x00000000'00000000 to 0x00007FFF'FFFFFFFF 128 TB User mode: your process
(the gap) Not valid: using an address here is an immediate fault
0xFFFF8000'00000000 to 0xFFFFFFFF'FFFFFFFF 128 TB Kernel mode: shared by all processes, inaccessible from user mode

Addresses in the valid ranges are called canonical. That is why every user-mode pointer you print starts with 0000, and why the top two bytes in the Memory window are always 00 00 (lesson 2.11). A pointer like 0x12345678'9ABCDEF0 is not just invalid, it is impossible, and is a sure sign of corrupted data.

Within the user half, Windows places the program's modules near the top (0x00007FF...), and stacks and heaps lower down, at addresses randomised each run (lesson 6.09). The first 64 KB (0x0 to 0xFFFF) are never mapped, so that a null pointer plus a small offset always faults.

Pages that are not in RAM

A page table entry can also say "not present". Touching such a page raises a page fault, an exception the kernel handles:

Why it was not present What the kernel does
The page was never committed (lesson 6.03), or is in the gap The access is invalid: the program gets an access violation
It was committed but never touched yet Finds a free frame, fills it with zeros, maps it, and resumes the program: a demand-zero fault
It was moved out to the page file on disk to free RAM Reads it back, maps it, resumes: a hard fault, which takes milliseconds
It is part of a file mapping (the .exe's code, a DLL) Reads it from the file, maps it, resumes

The program never notices the middle three, except as a pause. This is how a 100 GB address space can exist on a PC with 16 GB of RAM, and why a game that uses more memory than the machine has starts to stutter: its pages are going to and from disk. Task Manager's Commit size and Working set columns show how much memory a process has committed and how much is currently in RAM.

Common mistakes

Thinking a pointer value is a RAM location

It is virtual. The physical location may change and is never visible to user-mode code.

Ignoring a non-canonical pointer in a crash

A pointer with random high bits is corrupted data: look for whatever overwrote it, not for the code that used it.

Assuming memory use is the same as RAM use

Committed memory may be in the page file; RAM in use is the working set.
