Secure Coding: Buffers, Integers and Trust

lesson 17.044 of 8 in milestone 175 min1 practice task

Security bugs are ordinary bugs in code that handles input an attacker can control. This lesson collects the course's lessons into secure coding practice for C++: trust boundaries, the classic bug classes (buffer overruns, integer errors, use after free, path traversal, format strings, time-of-check to time-of-use), and the habits and safe building blocks that prevent them.

Trust boundaries

A trust boundary is any place where data crosses from something you do not control into something you do. Everything this course built has them:

Boundary Untrusted side
Files loaded by the game Level files, saves, settings, mods (lessons 10.07, 13.02)
Network messages Other players, servers, anything on the internet
Plugins and scripts Mod authors' code and data (lesson 13.07)
Shared memory and pipes The other process (lesson 12.07)
Command-line arguments and environment Whoever started the program
A driver's IOCTLs Any user who can open the device (lesson 16.07)

The rule is the same at every one: validate at the boundary, before the data is used for anything (sizes, indices, paths, allocations, decisions). Inside, code can rely on data being valid because it was checked once, at the edge.

The classic bug classes

Bug How it happens Prevention
Buffer overrun Copying or indexing past a buffer's end with a length from input (lessons 2.08, 2.09) std::string, std::vector, std::span; check lengths against the destination; .at() in debug paths
Integer overflow and truncation count * size wraps; a 64-bit length truncated to 32 bits; signed/unsigned mix-ups (lessons 1.02, 17.02) Checked arithmetic; consistent unsigned sizes; compiler warnings C4244, C4267, C4018
Use after free / dangling Keeping pointers to objects that can disappear (lessons 2.04, 3.10) Ownership through smart pointers; ids and handles instead of raw pointers
Uninitialised memory Reading or sending memory never written, leaking its old contents (lesson 16.07) Always initialise; zero output structures
Path traversal A file name like ..\..\Windows\system.ini from input reaches files outside the intended folder (lesson 13.02) Reject .., absolute paths and drive letters; resolve and check the result stays under the base; the practice task
Format string printf(userText) interprets % sequences in input Always printf("%s", text); prefer std::format with a constant format
Time of check to time of use Data checked, then read again after it may have changed (lessons 15.02, 12.04) Copy once, then check and use the copy
Injection Building commands, SQL or scripts by concatenating input Pass input as data (arguments, parameters), never as code

Nearly every security advisory for C and C++ software falls in this table.

Safe building blocks

Modern C++ removes whole classes of these bugs if you let it:

  • std::span<T> carries a pointer and a length together, so functions can never lose track of a buffer's size (lesson 2.07).
  • std::string_view for read-only text, with the lifetime caveat of lesson 2.04.
  • Containers instead of raw arrays and new[].
  • std::optional and status returns instead of sentinel values that can be mistaken for data.
  • std::format instead of printf-family formatting.
  • RAII for every resource, so error paths cannot leak (lesson 2.04).

Defence in depth

No single measure is perfect, so layers are combined:

  1. Correct code: validation at boundaries, safe building blocks.
  2. Tools: warnings, analysis, sanitizers, fuzzing (lessons 17.02, 17.03).
  3. Platform mitigations left on: ASLR (lesson 6.09), DEP and non-executable data (6.03), stack cookies (7.05), control-flow guard. They turn many exploitable bugs into crashes.
  4. Least privilege: programs and tools that run with only the rights they need (lesson 6.08) limit what any remaining bug can do.

Common mistakes

Validating deep inside the code instead of at the boundary

Some path will skip the check. Validate where the data enters.

Trusting your own file formats

Users and attackers can edit any file on their machine.

Turning mitigations off for convenience

They cost almost nothing and defeat whole classes of attack.
