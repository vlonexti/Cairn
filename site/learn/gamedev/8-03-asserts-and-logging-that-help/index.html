Asserts and Logging That Help

lesson 8.033 of 8 in milestone 86 min1 practice task

The best bugs to fix are the ones the program reports itself, at the moment things go wrong. Asserts check assumptions and stop immediately when one is false; logs record what happened so you can reconstruct it later. This lesson shows how to write both well: static_assert and assert, a better assert macro, log levels, and a ring buffer that keeps the last moments before a crash.

Asserts: check your assumptions

Every piece of code assumes things: this index is in range, this pointer is not null, this list is sorted. An assert turns an assumption into a check that stops the program, in a debugger-friendly way, the moment it is violated:

C++
#include <cassert>

int& Grid::at(int x, int y)
{
    assert(x >= 0 && x < width && "x out of range");
    assert(y >= 0 && y < height && "y out of range");
    return cells[static_cast<std::size_t>(y * width + x)];
}

When an assert fails in a Debug build, the program stops with the condition, file and line; under the debugger it breaks right there, with the call stack showing who passed the bad coordinates. The string after && is a trick: a string literal is always true, so it does not change the condition, but it appears in the failure message.

Two properties to remember:

  • assert does nothing in Release builds (NDEBUG is defined, lesson 4.10). Never put work that must happen inside it.
  • Asserts are for programming errors ("this can never happen if the code is right"), not for things that can legitimately happen at run time, such as a missing file or bad player input. Those need real error handling.

static_assert: checks at compile time

Some assumptions can be checked by the compiler, costing nothing at run time:

C++
#include <cstdint>

struct SaveHeader { char magic[4]; std::uint32_t version; std::uint32_t length; };

static_assert(sizeof(SaveHeader) == 12, "SaveHeader must match the file format");
static_assert(sizeof(void*) == 8, "This code assumes a 64-bit build");
static_assert(alignof(SaveHeader) == 4);

int main() { return 0; }

If someone adds a member to SaveHeader, the build fails with that message instead of saves silently breaking. Use static_assert for layouts, sizes, and template requirements.

A better assert

The standard assert is minimal. Most engines write their own, adding a formatted message, a log line, a break into the debugger, and the option to keep checks on in some release builds:

C++
#include <cstdio>
#include <cstdlib>
#include <intrin.h>

#ifndef GAME_ASSERTS
#  ifdef NDEBUG
#    define GAME_ASSERTS 0
#  else
#    define GAME_ASSERTS 1
#  endif
#endif

#if GAME_ASSERTS
#  define GAME_ASSERT(condition, message)                                                            \
     do {                                                                                            \
         if (!(condition)) {                                                                         \
             std::fprintf(stderr, "Assertion failed: %s\n  %s\n  at %s:%d\n", #condition, message,   \
                          __FILE__, __LINE__);                                                       \
             std::fflush(stderr);                                                                    \
             __debugbreak();     /* stops here under a debugger; crashes cleanly without one */       \
             std::abort();                                                                           \
         }                                                                                           \
     } while (false)
#else
#  define GAME_ASSERT(condition, message) do { (void)sizeof(condition); } while (false)
#endif
  • #condition turns the condition's source text into a string for the message.
  • __debugbreak() is the int 3 instruction from lesson 4.07: under a debugger it stops exactly at the failing line.
  • do { ... } while (false) makes the macro behave like one statement, so it is safe after an if without braces.
  • The disabled version uses sizeof(condition) so the condition is still compiled (and type-checked) but never evaluated.

Logging

Logs record what the program did, so you can understand a bug after the fact, on a player's machine, or in a situation you cannot reproduce. Useful logs have:

Property Why
Levels: trace, debug, info, warning, error So you can turn detail up or down without changing code
A time stamp and frame number So you can line events up
A category: "audio", "net", "save" So you can filter
Facts, not feelings "loaded level 3 (forest) in 412 ms, 1,204 entities", not "level loaded!!"
Cheap when disabled Messages below the current level should cost almost nothing

What to log: start-up and configuration, level loads and saves, network connections, every error and warning with the values involved, and occasional performance summaries. What not to log: anything every frame at normal levels (the file becomes useless), passwords, tokens or personal data.

The last moments before a crash

Writing every debug message to a file is too slow, but the most useful messages are the ones just before a crash. A ring buffer solves this: keep the last N messages in memory, overwriting the oldest, and dump them in the crash handler (next lesson). The practice task builds one.

Common mistakes

Side effects inside asserts

assert(file.open(path)) opens the file only in Debug. Do the work, then assert on its result.

Asserting on things that can really happen

A missing file, bad input or a lost connection must be handled in Release too.

Logging every frame

Nobody can read it, and it slows the game. Log events and summaries.

Logging secrets or personal data

Logs get attached to bug reports and shared. Keep them clean.
