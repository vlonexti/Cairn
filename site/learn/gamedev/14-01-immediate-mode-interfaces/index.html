Immediate-Mode Interfaces

lesson 14.011 of 6 in milestone 145 min1 practice task

Most application toolkits are retained mode: you create widget objects once and keep them in sync with your data. Immediate mode turns that around: every frame, code describes the whole interface with function calls, and each call both draws its widget and reports what the user did. This lesson explains the model, why it suits tools and games so well, and how it works underneath, with ids, hot and active widgets.

Two ways to build an interface

Retained mode (Windows controls, Qt, web pages): you create a button object, give it a callback, and it lives until you destroy it. When your data changes, you must update every widget that shows it; when a widget changes, a callback updates your data. Keeping the two in sync is a large part of interface code.

Immediate mode (Dear ImGui, Nuklear, many in-house game tools): there are no widget objects in your code. Every frame you call functions that describe the interface as it should look now, reading directly from your data:

C++
// Every frame:
ImGui::Begin("Player");
ImGui::Text("Health: %d / %d", player.hp, player.maxHp);   // always shows the current value
ImGui::SliderInt("Speed", &player.speed, 1, 10);            // writes straight into your variable
if (ImGui::Button("Heal")) player.hp = player.maxHp;        // true on the frame it was clicked
ImGui::End();

There is nothing to keep in sync: the interface is a function of your data, recomputed each frame, like rendering the game itself (lesson 10.01).

Retained Immediate
Widget objects in your code Yes, created and destroyed No
Keeping data and interface in sync Your job Automatic: redrawn from data each frame
Showing or hiding parts Create, destroy, show, hide An if around the calls
Lists of changing length Add and remove widgets A for loop
Cost Only changes are redrawn The whole interface is re-described every frame (cheap for tools)
Best for Polished applications, accessibility, text-heavy forms Tools, debug interfaces, editors inside games

How a button knows it was clicked

If no button object exists between frames, how does Button("Heal") know the mouse went down on it last frame and up on it now? The library keeps a little state itself, keyed by an id for each widget, computed from its label (and the window and any pushed ids):

  • The hot widget is the one the mouse is over this frame.
  • The active widget is the one the mouse button went down on, and it stays active until the button is released.
  • A button reports a click when the mouse is released over it while it is active: press on it, release on it.
stateDiagram-v2
    [*] --> Idle
    Idle --> Hot: mouse over it
    Hot --> Idle: mouse leaves
    Hot --> Active: mouse pressed while hot
    Active --> Clicked: released while still over it
    Active --> Idle: released elsewhere (no click)
    Clicked --> Hot

So the only state that survives between frames is "which id is active" (plus a few things like scroll positions and window placement), not a tree of objects. The practice task implements exactly this logic.

Ids and why labels must be unique

Because ids come from labels, two buttons both labelled "Delete" in one window would share an id and behave as one. ImGui's answers:

  • "Delete##3": text after ## is part of the id but not shown;
  • ImGui::PushID(i) / PopID() around each item in a loop, so every row's widgets get distinct ids.

Forgetting this is the most common immediate-mode bug: clicking one row's button activates another.

Why tools and games use it

Game engines are already redrawing everything every frame, already have the data in memory, and need interfaces that change constantly with the game (debug views, editors, profilers). Immediate mode fits that loop exactly, and a tool window is a few dozen lines, so engineers actually write them. That is why Dear ImGui is in so many engines and tools, and why the next lessons use it for the chapter 12 tools.

Common mistakes

Duplicate labels in one window

Widgets share an id and behave strangely. Use ##suffix or PushID.

Keeping your own copies of values just for the interface

The point is to read and write your real data directly.

Doing expensive work while describing the interface

The description runs every frame; cache anything slow.
