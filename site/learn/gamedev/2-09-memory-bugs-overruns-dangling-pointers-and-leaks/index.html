Memory Bugs: Overruns, Dangling Pointers and Leaks

lesson 2.099 of 11 in milestone 28 min1 practice task

Memory bugs are the hardest bugs in C++ because the symptom often appears far from the cause, or only sometimes. This lesson names the main kinds (buffer overruns, use after free, double free, uninitialised reads and leaks), shows what each one looks like when it strikes, and gives the habits that prevent them.

Why these bugs are different

Most bugs are wrong logic: the code does what it says, and what it says is wrong. Memory bugs are worse. The code breaks one of the language's rules, the behaviour becomes undefined, and anything can happen:

  • it works perfectly, every time you test it;
  • it works in Debug and crashes in Release;
  • it crashes, but somewhere else entirely, minutes later;
  • it quietly changes a different variable, and the game misbehaves in a way that seems impossible.

That last one is the nastiest. A write past the end of one array changes whatever happens to sit next to it in memory, which might be a player's health, a pointer, or the allocator's own bookkeeping. You will see these effects in this course's tools, so it is worth knowing their shapes.

1. Buffer overrun

Writing (or reading) past the end of an array or buffer.

C++
struct Player
{
    char name[8];
    int gold;
};

void rename(Player& p, const char* newName)
{
    int i{ 0 };
    while (newName[i] != '\0') { p.name[i] = newName[i]; ++i; }  // no limit!
    p.name[i] = '\0';
}
// rename(p, "Maximilian") writes 11 bytes into an 8-byte array.
// The extra bytes land in gold, which suddenly holds 28,257 if it was 0: the bytes 61 6E 00 are "an" and its terminator.

The program does not crash. The player's gold changes to a nonsense number, and nobody looking at the gold code will ever find out why. Off-by-one loops (<= instead of <) are the most common cause; unchecked copies like this one are the most dangerous, because the length comes from outside.

Prevention: use containers that know their size (std::string, std::vector, std::array, std::span), use .at() or Debug iterator checks while developing, and never copy data whose length you have not checked against the destination.

2. Use after free

Using memory through a pointer after it has been freed.

C++
Enemy* target{ findNearestEnemy() };
removeDeadEnemies();          // deletes target's Enemy, among others
target->health -= 10;         // writes into freed memory

If the freed block has been handed out again, the write corrupts whatever now lives there. If not, it may seem to work. In a Debug build the freed block is filled with DD, so reading it gives obviously wrong values like -572662307 (0xDDDDDDDD).

Prevention: be clear about who owns each object. Use std::unique_ptr for ownership; refer to objects that can disappear by id or handle and look them up each time, instead of keeping raw pointers to them. Lesson 3.10 builds exactly such a system for game entities.

3. Dangling pointers and references

The general form of use after free: a pointer or reference that outlives what it refers to. Lesson 2.04 showed the common shapes: a pointer to a local that has returned, a view of a temporary string, a reference into a vector that has since grown.

Prevention: return values, not pointers to locals; do not store views or pointers into containers that might change; prefer indices into a vector over pointers to its elements.

4. Double free

Freeing the same block twice.

C++
Texture* t{ new Texture{} };
cache.add(t);        // the cache will delete it when cleared...
delete t;            // ...and so does this code

The allocator's bookkeeping is corrupted. The Debug runtime usually stops the program on the second delete; a Release build may crash much later, inside an unrelated allocation.

Prevention: one owner per object. Smart pointers make ownership visible in the type: a std::unique_ptr cannot be copied, so two owners cannot both think they should free it.

5. Uninitialised reads

Reading a variable before giving it a value.

C++
int damage;                         // no initialiser
if (critical) damage = 50;
health -= damage;                   // garbage when critical is false

In Debug, the garbage is 0xCCCCCCCC (-858993460), which at least looks wrong. In Release it is whatever was on the stack, which is often a plausible-looking number, so the bug hides.

Prevention: always initialise, with braces: int damage{ 0 };. Turn on warning level 4: MSVC warns about many uninitialised uses (C4700, C4701).

6. Leaks

Memory that is allocated and never freed. Leaks do not corrupt anything; they just make the process grow until it runs out of memory or slows the machine down.

C++
void spawnWave()
{
    for (int i{ 0 }; i < 20; ++i)
    {
        Monster* m{ new Monster{} };
        if (!placeOnMap(m)) continue;     // leaked: nobody will ever delete m
        world.add(m);
    }
}

Prevention: never write new without immediately handing the result to an owner (std::make_unique, a container). Then early returns, continues and exceptions cannot leak. The Debug runtime can list leaks when the program exits: call _CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF) at the start of main, and Visual Studio's Output window shows every block still allocated at the end, with its size and contents.

A summary table

Bug Typical symptom Debug-build clue
Buffer overrun Neighbouring data changes; heap corruption message on delete FD guard bytes changed
Use after free Strange values, or corruption elsewhere Values like 0xDDDDDDDD
Double free Crash in delete or a later allocation Debug assertion in the heap
Uninitialised read Random behaviour, different in Release Values like 0xCCCCCCCC or 0xCDCDCDCD
Leak Memory use grows over time Leak report at exit

Debugging a memory bug

When something changes that should not:

  1. Make it repeatable. Find inputs that trigger it every time.
  2. Find what changed. Use a data breakpoint (lesson 4.09) on the variable that goes wrong: the debugger stops on the exact instruction that writes it, and the Call Stack shows who did it.
  3. Run a sanitizer. AddressSanitizer, in the next lesson, catches overruns and use after free at the moment they happen, with the line numbers of the allocation, the free and the bad access.

Common mistakes

"It works on my machine"

Undefined behaviour may happen to work in one build and not another. Code that only works by luck is not working.

Fixing the symptom

Adding a check where the corrupted value is used hides the problem. Find the write that caused it.

[!warning] Raw new in game code Every raw new is a potential leak, double free or dangling pointer. Prefer containers and smart pointers.
