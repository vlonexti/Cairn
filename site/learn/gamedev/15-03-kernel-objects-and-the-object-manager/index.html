Kernel Objects and the Object Manager

lesson 15.033 of 8 in milestone 155 min1 practice task

Lesson 5.01 showed handles from the user's side. Inside the kernel, the object manager creates every kernel object (files, processes, threads, events, devices, registry keys), gives each a header with its type, reference counts and security, keeps a namespace of named objects, and maintains each process's handle table. This lesson looks at all of that, and at the object names drivers use.

Every object has a header

Each kernel object is a block of kernel memory: an object header managed by the object manager, followed by the object's own body (an event's signalled state, a file's position):

In the header Meaning
Type Which kind of object: Process, Thread, File, Event, Device, Key, Section ... Each type has its own procedures (open, close, delete) and its own access rights
Handle count How many handles, in all processes, refer to it
Pointer (reference) count How many references in total, including the kernel's own pointers
Security descriptor Who may do what (lesson 6.08)
Name For named objects, its place in the namespace

An object is deleted only when both counts reach zero. Kernel code that keeps a pointer to an object takes a reference (ObReferenceObject) and later releases it (ObDereferenceObject), the kernel's equivalent of lesson 10.06's reference counting. Forgetting to release keeps the object alive until reboot; releasing twice frees it while still in use, usually ending in a bug check.

Handles, from the inside

A handle (lesson 5.01) is an index into the process's handle table, maintained by the object manager. Each entry holds a pointer to the object and the access mask granted when it was opened. When a user calls, say, SetEvent(h), the kernel:

  1. looks up h in the calling process's table (ObReferenceObjectByHandle);
  2. checks the object's type is right (an Event), and the granted access includes what the operation needs;
  3. takes a reference while it works, and drops it afterwards.

The access check against the security descriptor happened only once, when the handle was created (lesson 6.08).

The object namespace

Named objects live in a tree, like a file system for the kernel:

\
├── Device\
│   ├── HarddiskVolume3          the C: volume
│   ├── Null
│   └── XenonEcho                a device created by chapter 16's driver
├── Driver\                      loaded drivers
├── GLOBAL??\                    "DOS device" names: symbolic links
│   ├── C:  → \Device\HarddiskVolume3
│   └── XenonEcho → \Device\XenonEcho
├── BaseNamedObjects\            named events, mutexes, sections from user mode
│   └── (Local\ and Global\ names, lesson 12.01)
└── Sessions\ ...                per-session namespaces

Symbolic links connect friendly names to devices. The user-mode path C:\save.dat becomes \??\C:\save.dat in the kernel; \?? looks in the caller's own and then the global DOS device directory, where C: is a symbolic link to \Device\HarddiskVolume3; the object manager follows it, and the rest of the path (\save.dat) is handed to the file system driver on that device. The practice task resolves paths through links like this, including stopping a link that points back at itself.

Chapter 16's driver creates a device object (\Device\XenonEcho) and a symbolic link to it (\??\XenonEcho), so a user program can open it with CreateFileW(L"\\\\.\\XenonEcho", ...): the \\.\ prefix is user mode's way of saying \??\.

Seeing it

Sysinternals WinObj shows the whole namespace: devices, drivers, symbolic links and named objects. Sysinternals Handle and Process Explorer's lower pane list every handle a process holds, with types and names, which is how you find which program has a file locked (lesson 5.04's sharing violations).

Common mistakes

Holding an object pointer without a reference

The object can be deleted underneath you. Reference it for as long as you keep the pointer.

Unbalanced reference counts

A missing dereference leaks the object until reboot; an extra one frees it while still in use.

Confusing user-mode and kernel-mode names

\\.\Name from user mode corresponds to \??\Name (a link) in the kernel, which points at \Device\Name.

  3. What does \??\C: refer to?
