What Happens When a Program Runs

lesson 1.011 of 8 in milestone 115 min2 practice tasks

A computer does one small thing at a time. It fetches an instruction from memory, works out what it means, and does it. Everything a game does, from drawing a frame to saving your progress, is billions of those small steps.

Why this course starts here

This course is about what is really going on inside a running game: where its numbers live, how the processor works through its code, what the operating system does around it, and how tools such as debuggers look inside.

All of that rests on one picture of how a computer runs a program. If that picture is clear, later topics such as pointers, assembly language and debugging become ordinary consequences of it. If it is fuzzy, they stay mysterious however many times they are explained.

So this lesson builds the picture, and it lets you operate a small computer yourself.

A program on your disk is only a file. It does nothing until the operating system copies it into memory and tells the CPU where its first instruction is. From then on the CPU and memory do all the work, and storage is only touched when the program reads or writes a file.

That is why this course spends so much time on memory. While a game is running, everything it knows is in memory: the player's health, the position of every monster, the level layout, and the game's own instructions.

A program is a list of numbers

Memory is a long row of numbered boxes, and each box holds a number. Nothing else. There are no words in there, no pictures and no C++.

A program is stored in those boxes as numbers too. The people who design a CPU decide which number means which action. On the tiny machine you are about to use, the code works like this:

Number Written as What the CPU does
1nn LOAD nn Copy the number in cell nn into register A
2nn ADD nn Add the number in cell nn to register A
3nn SUB nn Subtract the number in cell nn from register A
4nn STORE nn Copy register A into cell nn
5nn JUMP nn Carry on from cell nn instead of the next cell
6nn JUMPZ nn If register A is zero, carry on from cell nn
0 HALT Stop

So the number 110 means "load cell 10", and 412 means "store into cell 12". The words LOAD and STORE are only there for people. The CPU sees 110 and 412.

The same number can be an instruction or a value

Memory does not label its boxes. 110 is "load cell 10" when the CPU fetches it as an instruction, and it is just the quantity one hundred and ten when a program adds it to something. What a number means depends entirely on how it is used. This idea comes back throughout the course.

A register is a storage slot inside the CPU itself. It is much faster to reach than memory, and there are very few of them. This machine has one for doing sums, called A.

The cycle: fetch, decode, execute

The CPU repeats three steps for as long as the power is on.

  1. Fetch. A register called the program counter holds the number of the cell where the next instruction is. The CPU copies that cell's contents into its instruction register, then adds one to the program counter so it points at the following cell.
  2. Decode. The CPU works out what the number in the instruction register means.
  3. Execute. It does it: copies a number, adds, or changes the program counter.

Then it goes back to step 1. That loop is the whole of how a computer runs a program.

Things to notice:

  • The program counter always names the cell that will be fetched next. It is the CPU's bookmark.
  • Nothing happened to memory until the STORE. Loading and adding only changed register A.
  • When the machine halted, the answer was sitting in cell 12. A program's results are simply whatever it left in memory.

Now type different numbers into cells 10 and 11. The machine goes back to the start each time you change one. Then press Run. The program is the same four instructions; only the data changed. That separation between the instructions and the data they work on is what makes a program reusable.

This machine is invented, but the idea is exact

The processor in your computer has sixteen general registers instead of one, hundreds of instructions instead of seven, and its instructions are different lengths. Chapter 7 covers the real thing. The cycle of fetch, decode and execute is the same.

Loops and decisions are jumps

Left alone, the program counter just counts upward, so the CPU runs instructions in the order they sit in memory. JUMP and JUMPZ are the two instructions that put a different number in the program counter. That is all a loop or an if is at this level.

The instructions in cells 1 to 4 run once for every count. Cell 1 is the question "has it reached zero yet?" and cell 4 is "go round again".

Change the counter in cell 10 to 5 and run it again. It takes more instructions to finish, because the loop goes round more times, although the program itself did not get any longer.

When you write a while loop or an if statement in C++, the compiler turns it into exactly this: a test that sets up a condition, and a jump that depends on it.

From C++ to those numbers

You do not write programs as numbers. You write something like this, and a compiler translates it into the CPU's instructions.

C++
#include <iostream>

int main()
{
    int first{ 7 };
    int second{ 5 };
    int answer{ first + second };
    std::cout << answer << '\n';
    return 0;
}
Output
12

For the line int answer{ first + second }; a compiler for a real x64 processor produces instructions along these lines:

Assembly
mov  eax, dword ptr [first]     ; LOAD   copy first into a register
add  eax, dword ptr [second]    ; ADD    add second to it
mov  dword ptr [answer], eax    ; STORE  copy the register into answer

It is the same three steps you watched in the first demonstration. The names first, second and answer are for you and the compiler. In the finished program they are gone, replaced by the numbers of the memory cells where those values live. Lesson 1.03 is about those cell numbers, which are called addresses.

How fast this happens

One core of a modern processor gets through billions of these steps every second. A game that draws 60 frames a second has about 16.7 milliseconds for each frame, and in that time one core can carry out tens of millions of instructions.

That is why a game can move hundreds of objects, check their collisions, play sound and draw the screen, all between one frame and the next. Each of those jobs is still nothing more than loading numbers, doing arithmetic on them, storing them and jumping.

Where the operating system comes in

Three things happen when you start a program on Windows.

  1. Windows finds the program file on disk and reads it.
  2. It sets aside memory for the program and copies the program's instructions and starting data into it. A program that has been loaded and is running is called a process.
  3. It sets the program counter to the program's first instruction and lets the CPU go.

Windows also keeps many processes going at once by letting each use the CPU for a short slice of time, then switching to another. It keeps each process's memory separate from every other's. Chapter 6 covers processes and their memory in detail.

Why this matters for games

Take the picture you now have and look at a game with it.

  • Game state is numbers in memory. Health, gold, position, the current level: each is a number in some memory cell.
  • The game is a loop. Read the input, update the numbers, draw the picture, go round again. It is the countdown program with a much bigger body.
  • A debugger stops the cycle. Because the CPU does one instruction at a time, a tool can pause it between two instructions and show you every register and every memory cell. That is what Visual Studio's debugger does, and you will use it constantly in this course.

Common misunderstandings

"The computer understands C++"

It does not. The CPU only carries out its own numbered instructions. C++ exists for people, and a compiler has to translate it before anything can run.

"Instructions and data are kept in different kinds of memory"

They sit in the same memory, as the same kind of numbers. Modern operating systems do mark regions as "may be run" or "may only be read", which is a safety measure you will meet later, but the bytes themselves are no different.

"Variables keep their names inside the machine"

Names disappear when the program is compiled. Only cell numbers remain. This is why a debugger needs a separate file of symbols to show you names again.

"A computer does many things at the same moment"

One core does one instruction at a time. It appears to do many things because it is fast and because the operating system switches between programs many times a second. A processor with several cores really does run several instruction streams at once, one per core.
