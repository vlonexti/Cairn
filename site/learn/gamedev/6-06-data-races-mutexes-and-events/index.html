Data Races, Mutexes and Events

lesson 6.066 of 9 in milestone 66 min1 practice task

When two threads use the same memory and at least one writes, without coordination, the result is a data race: undefined behaviour that shows up as lost updates, torn values and bugs that vanish under the debugger. This lesson shows a race, then the tools that prevent them: mutexes, atomics, condition variables and Windows events, and the classic trap of deadlock.

A race you can see

C++
#include <iostream>
#include <thread>

int main()
{
    int score{ 0 };
    auto addPoints = [&score] { for (int i{ 0 }; i < 1'000'000; ++i) ++score; };
    std::thread a{ addPoints };
    std::thread b{ addPoints };
    a.join();
    b.join();
    std::cout << score << '\n';     // should be 2,000,000
    return 0;
}
Output (yours will differ)
1318772

Each run prints a different number, almost never 2,000,000. ++score looks like one step but is three: read score into a register, add one, write it back. If both threads read 41, both write 42, and one point is lost:

sequenceDiagram
    participant A as Thread A
    participant M as score (memory)
    participant B as Thread B
    A->>M: read 41
    B->>M: read 41
    A->>A: 41 + 1
    B->>B: 41 + 1
    A->>M: write 42
    B->>M: write 42 (A's point is lost)

The C++ rules go further than "points get lost": any unsynchronised access by two threads where one writes is undefined behaviour, so the optimiser may also keep score in a register for the whole loop. The symptoms are not limited to wrong totals.

Atomics: indivisible operations

For a single counter or flag, std::atomic makes each operation indivisible. The processor provides special instructions (lock xadd, lock cmpxchg) that do read-modify-write as one step:

C++
#include <atomic>
#include <iostream>
#include <thread>

int main()
{
    std::atomic<int> score{ 0 };
    auto addPoints = [&score] { for (int i{ 0 }; i < 1'000'000; ++i) ++score; };
    std::thread a{ addPoints };
    std::thread b{ addPoints };
    a.join();
    b.join();
    std::cout << score << '\n';
    return 0;
}
Output
2000000

Atomics are right for counters, flags ("stop now") and simple statistics. They do not help when several values must change together, such as moving an item from one list to another.

Mutexes: one thread at a time

A mutex (mutual exclusion) guards a section of code: a thread that calls lock on a mutex another thread holds waits until it is released. Always lock with an RAII guard (lesson 2.04), so the mutex is released on every path:

C++
#include <iostream>
#include <mutex>
#include <string>
#include <thread>
#include <vector>

class EventLog
{
public:
    void add(std::string line)
    {
        std::lock_guard lock{ m_mutex };          // locked here...
        m_lines.push_back(std::move(line));
    }                                             // ...released here
    std::size_t size()
    {
        std::lock_guard lock{ m_mutex };
        return m_lines.size();
    }
private:
    std::mutex m_mutex;
    std::vector<std::string> m_lines;
};

int main()
{
    EventLog log;
    std::vector<std::thread> threads;
    for (int t{ 0 }; t < 4; ++t)
        threads.emplace_back([&log, t] { for (int i{ 0 }; i < 1000; ++i) log.add("thread " + std::to_string(t)); });
    for (auto& th : threads) th.join();
    std::cout << log.size() << " lines\n";
    return 0;
}
Output
4000 lines

Without the mutex, two push_backs at once can both decide to grow the vector, and the program corrupts its heap. The rule: every access to shared mutable data, reads included, happens while holding the same mutex. Keep the locked section short: do slow work (formatting, file writes) outside it.

Waiting for something to happen

Threads often need to wait until another thread has done something: a job is available, loading has finished. Spinning in a loop checking a flag wastes a whole core. Proper waiting puts the thread to sleep until it is woken:

Tool Use
std::condition_variable Wait until a condition on data guarded by a mutex becomes true (a queue is not empty)
std::latch, std::barrier (C++20) Wait until N threads have reached a point
std::future / std::promise Wait for one result from another thread
Windows event (CreateEventW) A kernel object that is signalled or not; threads wait on it with WaitForSingleObject; works across processes too

A Windows event is like a flag that threads can sleep on. A manual-reset event stays signalled until reset (good for "loading finished": everyone may proceed); an auto-reset event wakes one waiter and resets itself (good for "one job available").

C++
HANDLE loaded{ CreateEventW(nullptr, TRUE, FALSE, nullptr) };   // manual-reset, starts unsignalled
// loader thread, when done:   SetEvent(loaded);
// main thread:                WaitForSingleObject(loaded, INFINITE);   // sleeps until then

The practice task builds the most common combination: a thread-safe queue that consumers can wait on.

Deadlock

Two threads, two mutexes. Thread 1 locks A then waits for B. Thread 2 locks B then waits for A. Both wait forever: a deadlock. The game freezes with 0% CPU.

Prevent it by:

  • always taking locks in the same order everywhere in the program;
  • locking several mutexes at once with std::scoped_lock lock{ a, b };, which avoids deadlock internally;
  • never calling unknown code (callbacks, virtual functions) while holding a lock.

When a game freezes, Break All in the debugger and look at each thread's call stack in the Threads window: two threads each waiting in a lock function, each holding what the other wants, is the signature of a deadlock (chapter 8).

Common mistakes

Reading shared data without the lock "because it's only a read"

A read concurrent with a write is still a data race.

[!warning] Using volatile for thread communication In C++, volatile does not make anything atomic or ordered. Use std::atomic.

Holding a lock while doing slow work

Every other thread that needs it waits. Copy what you need, unlock, then work.

Waiting with a busy loop

Use a condition variable, an event, or a future, so the waiting thread sleeps.

Knowledge check

quizIn Xenon your best score is kept.
  1. Why can two threads doing ++score lose updates?
    • ++score is a read, an add and a write; both threads can read the same old value
    • Integers cannot be shared between threads
    • The scheduler skips some increments
    Show the answer

    ++score is a read, an add and a write; both threads can read the same old value Without synchronisation, the steps of the two threads interleave.

  2. When is std::atomic enough on its own?
    • For a single value updated by indivisible operations, such as a counter or a flag
    • Whenever several values must change together
    • Never; a mutex is always needed
    Show the answer

    For a single value updated by indivisible operations, such as a counter or a flag Changes involving several values need a mutex around all of them.

  3. Thread 1 holds mutex A and waits for B; thread 2 holds B and waits for A. What is this?
    • A deadlock
    • A data race
    • A context switch
    Show the answer

    A deadlock Taking locks in a consistent order, or with std::scoped_lock, prevents it.

  4. What is the difference between a manual-reset and an auto-reset event?
    • A manual-reset event stays signalled until reset, releasing every waiter; an auto-reset event releases one waiter and resets itself
    • Manual-reset events are faster
    • Auto-reset events work only within one process
    Show the answer

    A manual-reset event stays signalled until reset, releasing every waiter; an auto-reset event releases one waiter and resets itself Choose by whether one or all waiting threads should proceed.
