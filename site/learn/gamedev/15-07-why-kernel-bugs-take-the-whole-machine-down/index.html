Why Kernel Bugs Take the Whole Machine Down

lesson 15.077 of 8 in milestone 156 min1 practice task

When kernel-mode code fails, Windows stops the machine with a bug check (the blue screen) rather than risk corrupting data. This lesson explains why, what the stop code and parameters mean, the most common driver bug checks, how kernel crash dumps are collected and read with !analyze, and how Driver Verifier turns rare driver bugs into immediate, diagnosable ones.

Why stop everything?

In user mode, an access violation ends one process; Windows still has an intact kernel to clean up after it (lesson 1.06). In kernel mode there is no such referee. If a driver writes through a bad pointer, the damage could be anywhere in the shared kernel address space (lesson 15.01): the file system's caches, another driver's data, the memory manager's tables. Continuing might write corrupted data to disk. So when the kernel detects a condition it cannot safely recover from, it calls KeBugCheckEx, which:

  1. stops all processors,
  2. writes a crash dump to the page file (copied to C:\Windows\MEMORY.DMP or C:\Windows\Minidump\ on the next boot),
  3. shows the stop screen with a stop code, and restarts.

Stopping is the safe choice. A blue screen loses unsaved work; silent corruption could lose everything.

Reading a stop code

A bug check has a code and four parameters whose meaning depends on the code. The ones caused most often by drivers:

Code Name Usual meaning
0x0A IRQL_NOT_LESS_OR_EQUAL Paged or invalid memory touched at DISPATCH_LEVEL or above (lesson 15.06)
0xD1 DRIVER_IRQL_NOT_LESS_OR_EQUAL The same, in a driver; parameter 4 is the faulting address in the driver
0x50 PAGE_FAULT_IN_NONPAGED_AREA Referenced invalid memory: a bad or freed pointer
0x3B SYSTEM_SERVICE_EXCEPTION An exception during a system call, often in a driver handling a user request
0x7E SYSTEM_THREAD_EXCEPTION_NOT_HANDLED An exception in a system thread that nothing handled
0xC4 DRIVER_VERIFIER_DETECTED_VIOLATION Driver Verifier caught a rule violation (below)
0x19 BAD_POOL_HEADER Pool corruption: an overrun into the next allocation
0xC2 BAD_POOL_CALLER Bad pool request: double free, wrong IRQL for the pool type
0xCE DRIVER_UNLOADED_WITHOUT_CANCELLING_PENDING_OPERATIONS A driver unloaded while timers, DPCs or IRPs still referred to its code
0xEF CRITICAL_PROCESS_DIED A process Windows cannot run without ended

Microsoft's Bug Check Code Reference documents every code and its parameters. The practice task decodes the common ones.

Reading a kernel dump

Open MEMORY.DMP or a minidump in WinDbg (lesson 8.05), fix the symbols (.symfix, .reload) and run:

Output
!analyze -v

It reports the bug check and its parameters, the faulting module (very often the culprit driver's name, such as XenonEcho.sys), the call stack at the crash, and the source line if the driver's PDB is available. lm lists loaded drivers; !irql shows the IRQL at the time of the crash; !pool and !poolused investigate pool problems (lesson 15.04).

Kernel dumps are configured in System Properties → Advanced → Startup and Recovery: a small memory dump is enough for most driver bugs; a kernel memory dump contains all kernel memory for harder ones.

Driver Verifier

Many driver bugs only crash in rare situations: when memory happens to be paged out, when an allocation fails, when two processors race. Driver Verifier (verifier.exe, built into Windows) makes them happen every time, by adding checks to chosen drivers:

Option Catches
Special pool Overruns and use-after-free in pool memory, at the faulting instruction (like page heap, lesson 6.03)
Force IRQL checking Paged memory touched at DISPATCH_LEVEL even when it is currently in RAM (by paging it out)
Pool tracking Leaks: unfreed pool when the driver unloads
I/O verification IRPs completed twice, completed with bad status, leaked
Deadlock detection Lock order violations
Low resources simulation Code that does not handle allocation failure
DDI compliance checking Calls made against the documented rules

Turn it on for your own driver, in the virtual machine (lesson 15.08), from an administrator prompt (verifier /standard /driver XenonEcho.sys, then reboot), and leave it on throughout development. A bug Verifier catches gives bug check 0xC4 with parameters describing exactly which rule was broken, instead of a mysterious crash weeks later. Microsoft requires drivers to pass Verifier testing before signing them for release.

Common mistakes

Ignoring the faulting module

!analyze names it; that is where to look first.

Developing a driver without Driver Verifier

Its checks find in minutes what otherwise takes months of rare crashes.

Testing kernel code on your everyday PC

A bug check there costs your work and possibly your data. Use a VM with snapshots.
