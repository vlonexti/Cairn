Windows and the Message Loop

lesson 5.055 of 9 in milestone 56 min

A Windows program with a window does not ask "has a key been pressed?". Windows tells it, by putting messages in a queue that the program reads in a message loop and hands to a window procedure. This lesson explains window classes, messages, the loop, and the variant games use so they can keep rendering when no messages arrive.

Event-driven programs

A console program runs top to bottom and asks for input when it wants it. A windowed program is the other way round: it sits waiting, and the operating system sends it events: a key was pressed, the mouse moved, the window was resized, the window needs repainting, the user clicked Close.

Windows delivers these as messages. Each message is a small structure:

C++
struct MSG
{
    HWND   hwnd;      // which window it is for
    UINT   message;   // what happened: WM_KEYDOWN, WM_MOUSEMOVE, WM_PAINT, ...
    WPARAM wParam;    // extra information, meaning depends on the message
    LPARAM lParam;    // more extra information
    DWORD  time;
    POINT  pt;
};

Every thread that creates a window gets a message queue. Windows appends messages to it; the program takes them out one at a time.

Window classes and the window procedure

Before creating a window you register a window class: a template naming, among other things, the window procedure, the function Windows calls for every message to windows of that class. It is a callback (lesson 3.04): you give Windows a function pointer, and Windows calls it.

C++
LRESULT CALLBACK WindowProc(HWND hwnd, UINT message, WPARAM wParam, LPARAM lParam)
{
    switch (message)
    {
    case WM_KEYDOWN:
        if (wParam == VK_ESCAPE) DestroyWindow(hwnd);   // Esc closes the window
        return 0;
    case WM_DESTROY:
        PostQuitMessage(0);                             // ask the message loop to end
        return 0;
    }
    return DefWindowProcW(hwnd, message, wParam, lParam);   // default handling for everything else
}

The switch handles the messages the program cares about. Everything else must go to DefWindowProcW, which implements the standard behaviour: moving the window when its title bar is dragged, resizing, the system menu, closing on Alt+F4. A window procedure that returns 0 for everything produces a window that cannot be moved or closed.

The message loop

C++
MSG msg{};
while (GetMessageW(&msg, nullptr, 0, 0) > 0)
{
    TranslateMessage(&msg);     // turns key presses into WM_CHAR messages for typed text
    DispatchMessageW(&msg);     // calls the window procedure of msg.hwnd
}
  • GetMessageW takes the next message from the queue, waiting if it is empty. It returns 0 when it finds WM_QUIT, which PostQuitMessage puts in the queue, and -1 on error.
  • DispatchMessageW looks up the window's class and calls its window procedure.

That is the whole skeleton of every classic Windows program: register a class, create a window, loop until WM_QUIT. The next lesson writes a complete one.

Some messages skip the queue entirely: Windows calls the window procedure directly for them (they are "sent" rather than "posted"), for example WM_CREATE during CreateWindowExW and WM_SIZE during resizing. So a window procedure can be called from inside other API calls, not only from DispatchMessageW.

Messages you will handle most

Message Sent when Useful data
WM_CREATE The window is being created
WM_DESTROY The window is being destroyed Post WM_QUIT here
WM_CLOSE The user asked to close (X button, Alt+F4) Ask "save first?" here, or call DestroyWindow
WM_PAINT Part of the window needs redrawing Use BeginPaint / EndPaint
WM_SIZE The client area changed size New width and height in lParam
WM_KEYDOWN, WM_KEYUP A key went down or up Virtual-key code in wParam (lesson 5.07)
WM_CHAR Text was typed (after TranslateMessage) The UTF-16 character in wParam
WM_MOUSEMOVE, WM_LBUTTONDOWN, ... Mouse movement and buttons Coordinates in lParam (lesson 5.07)
WM_TIMER A timer set with SetTimer fired Timer id in wParam
WM_ACTIVATE The window gained or lost focus Pause the game when it loses focus

The game loop variant

GetMessageW waits when there are no messages. A game cannot wait: it must update and draw 60 or more times a second whether or not the player touches anything. Games use PeekMessageW, which returns immediately, and run a frame whenever the queue is empty:

C++
bool running{ true };
while (running)
{
    MSG msg{};
    while (PeekMessageW(&msg, nullptr, 0, 0, PM_REMOVE))   // handle everything waiting...
    {
        if (msg.message == WM_QUIT) running = false;
        TranslateMessage(&msg);
        DispatchMessageW(&msg);
    }
    if (!running) break;

    updateGame();      // ...then run one frame
    renderGame();
}

Draining all waiting messages each frame, not just one, keeps input responsive and the window behaving normally. Chapter 10 builds the full game loop with proper timing around this.

Common mistakes

[!warning] Not calling DefWindowProcW for unhandled messages The window cannot be moved, resized or closed normally.

[!warning] Forgetting PostQuitMessage in WM_DESTROY The window disappears but the message loop keeps waiting, and the process keeps running invisibly. Check Task Manager.

Long work inside the window procedure

While it runs, no other messages are handled, and after a few seconds Windows marks the window "Not Responding". Do slow work elsewhere, or in steps.

[!warning] Using GetMessageW in a game The game only updates when a message arrives, such as when the mouse moves. Use PeekMessageW.
