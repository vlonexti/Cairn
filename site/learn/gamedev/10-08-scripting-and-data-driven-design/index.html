Scripting and Data-Driven Design

lesson 10.088 of 9 in milestone 105 min1 practice task

Engines get faster to work with when behaviour and content move out of C++ and into data: monster stats in a file, levels from an editor, dialogue in a table, and, for logic, scripts in an embedded language such as Lua. Designers can then change the game without recompiling it. This lesson covers data files, a small configuration parser, embedding a scripting language, and the trade-offs.

Hard-coded versus data-driven

C++
// Hard-coded: changing a goblin needs a programmer and a rebuild.
Monster makeGoblin() { return Monster{ "Goblin", 30, 4, 1.2f }; }
INI
; monsters.ini: a designer edits this, the game reloads it
[goblin]
health = 30
damage = 4
speed = 1.2

[troll]
health = 120
damage = 15
speed = 0.6

When monster stats, weapon tables, level layouts, loot tables and dialogue live in data files:

  • Designers iterate without programmers: change a number, reload (lesson 10.06's hot reloading), play.
  • Modders can change the game too (chapter 13).
  • The code gets smaller and more general: one Monster loader instead of a function per monster.

Formats

Format Good for
INI / key-value Settings, simple tables. Trivial to parse (the practice task)
JSON Nested data: items with lists of effects. Many C++ libraries (nlohmann/json, simdjson, RapidJSON)
CSV / spreadsheets Large tables edited by designers in a spreadsheet: balance numbers, localisation
Custom binary Shipping builds, produced by the asset pipeline from the formats above (lesson 10.06)

Whatever the format, validate on load: a misspelt key or a negative health should produce a clear message naming the file and line, not a crash three levels later.

Scripting languages

Data files describe what; some things need logic: a boss's attack pattern, a quest's conditions, a cutscene's sequence. Writing all of that in C++ means a rebuild for every tweak. Many engines embed a scripting language:

Language Notes
Lua Tiny, fast, easy to embed in C++; used in a great many games
Python Common in tools and editors, heavier to embed in a shipping game
C# Unity's language; managed runtime
GDScript Godot's own
Visual scripting Node graphs for non-programmers (Unreal's Blueprints)
Your own small command language Enough for debug consoles and simple sequences (lesson 3.04's command table)

Embedding Lua looks like this: the C++ side registers functions scripts may call, then runs script files:

C++
#include <lua.hpp>

static int luaSpawn(lua_State* L)                 // callable from Lua as spawn("goblin", x, y)
{
    const char* kind{ luaL_checkstring(L, 1) };
    const double x{ luaL_checknumber(L, 2) };
    const double y{ luaL_checknumber(L, 3) };
    world.spawn(kind, static_cast<float>(x), static_cast<float>(y));
    return 0;                                     // no return values
}

int main()
{
    lua_State* L{ luaL_newstate() };
    luaL_openlibs(L);
    lua_register(L, "spawn", &luaSpawn);
    if (luaL_dofile(L, "scripts/wave1.lua") != LUA_OK)
        std::fprintf(stderr, "script error: %s\n", lua_tostring(L, -1));
    lua_close(L);
}
Lua
-- scripts/wave1.lua
for i = 1, 5 do
  spawn("goblin", 100 + i * 32, 200)
end
spawn("troll", 300, 240)

The script can only do what the registered functions allow, which keeps it safe and the engine in charge.

Trade-offs

Benefit Cost
Fast iteration, no recompiling Scripts run slower than C++; keep heavy loops in C++
Designers and modders can work independently Two languages to debug; errors appear at run time instead of compile time
Behaviour can change after shipping (patches as data) The boundary between C++ and script needs careful design

The rule most engines follow: systems in C++, content and one-off logic in data and scripts.

Common mistakes

No validation of data files

Report problems with the file name, line and key at load time.

Moving hot loops into scripts

Scripts are for decisions, not for processing ten thousand particles per frame.

Exposing everything to scripts

Register a deliberate, small set of functions; scripts and mods should not reach arbitrary engine internals.
