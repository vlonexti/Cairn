Virtual Functions and Vtables in Memory

lesson 3.055 of 10 in milestone 37 min1 practice task

A virtual call picks the function to run from the object's real type, at run time. Compilers do it with a vtable: a table of function pointers, one per class, and a hidden vptr in every object pointing at its class's table. This lesson shows the layout, walks through a virtual call step by step, and explains what it costs.

The problem virtual functions solve

C++
#include <iostream>
#include <memory>
#include <vector>

struct Entity
{
    virtual ~Entity() = default;
    virtual void update() { std::cout << "entity idles\n"; }
    virtual int damage() const { return 0; }
};

struct Goblin : Entity
{
    void update() override { std::cout << "goblin sneaks\n"; }
    int damage() const override { return 4; }
};

struct Dragon : Entity
{
    void update() override { std::cout << "dragon breathes fire\n"; }
    int damage() const override { return 40; }
};

int main()
{
    std::vector<std::unique_ptr<Entity>> world;
    world.push_back(std::make_unique<Goblin>());
    world.push_back(std::make_unique<Dragon>());
    world.push_back(std::make_unique<Entity>());

    int total{ 0 };
    for (const auto& e : world)
    {
        e->update();               // which update? decided by the object, at run time
        total += e->damage();
    }
    std::cout << "total damage " << total << '\n';
    return 0;
}
Output
goblin sneaks
dragon breathes fire
entity idles
total damage 44

The loop only knows it has an Entity*. The compiler cannot know, when it compiles e->update(), which function to call: that depends on the object at run time. So it cannot emit call Goblin::update. It needs a way to look the function up.

One table per class, one pointer per object

For every class with virtual functions, the compiler builds a vtable: an array of function pointers, one slot per virtual function, stored in the read-only .rdata section. Every object of that class gets a hidden first member, the vptr, holding the address of its class's vtable. The constructor sets it.

Every Goblin shares the one Goblin vtable. Slots are in the order the virtual functions were first declared in the base class, so update is in the same slot in every class's table. That is the key: the caller knows the slot number at compile time, even though it does not know the class.

A virtual call, step by step

e->update() compiles to roughly this (MSVC x64, with e in rcx):

Assembly
mov  rax, QWORD PTR [rcx]        ; 1. read the vptr from offset 0 of the object
call QWORD PTR [rax+8]           ; 2. read slot 1 of the vtable, and call that address
  1. Load the vptr from the object.
  2. Load the function pointer from the vtable at slot × 8. Here slot 1, offset 8, because slot 0 holds the destructor.
  3. Call it, with the object's address still in rcx as this.

Two memory reads and an indirect call. That is all "dynamic dispatch" is.

Seeing the vptr

The vptr is ordinary memory. Implementation details like this should never be relied on in real code, but looking at them once makes the idea concrete:

C++
#include <cstdint>
#include <cstring>
#include <iostream>

struct Entity { virtual ~Entity() = default; virtual int damage() const { return 0; } };
struct Goblin : Entity { int damage() const override { return 4; } };
struct Dragon : Entity { int damage() const override { return 40; } };

std::uintptr_t vptrOf(const void* object)
{
    std::uintptr_t vptr{};
    std::memcpy(&vptr, object, sizeof vptr);    // the first 8 bytes of the object
    return vptr;
}

int main()
{
    Goblin a, b;
    Dragon c;
    std::cout << "two goblins share a vtable: " << (vptrOf(&a) == vptrOf(&b)) << '\n';
    std::cout << "a dragon has a different one: " << (vptrOf(&a) != vptrOf(&c)) << '\n';
    std::cout << "sizeof(Goblin) = " << sizeof(Goblin) << '\n';
    return 0;
}
Output
two goblins share a vtable: 1
a dragon has a different one: 1
sizeof(Goblin) = 8

Goblin has no data members, yet it is 8 bytes: just the vptr. In the Visual Studio debugger, expanding an object shows the vptr as __vfptr, and expanding that lists the vtable's entries with their function names.

This is also why the first 8 bytes of many objects in a memory view look like an address inside the program's image: they are vptrs into .rdata. Chapter 9 uses vtables to discover the classes in a compiled program, because each vtable is a list of a class's virtual functions.

Construction and destruction

The vptr changes while an object is being built. During the Entity part of constructing a Goblin, the vptr points at Entity's vtable; only when the Goblin constructor body runs does it point at Goblin's. So a virtual call inside a constructor or destructor calls the version for the class currently being built, not the most derived one. This surprises people once, and then they remember it.

It is also why a base class used through pointers needs a virtual destructor. delete e on an Entity* calls the destructor through the vtable; without virtual, only ~Entity runs and the Dragon part is never destroyed.

The cost

Cost Size
Memory 8 bytes per object for the vptr, one small table per class
Each call Two dependent loads and an indirect call
Optimisation The compiler usually cannot inline a virtual call

For a few hundred calls per frame, none of this matters. For millions (every particle, every tile), it can. Engines often avoid virtual calls in the hottest loops by keeping objects of one type together in arrays and processing each array with ordinary calls. Chapter 10's entity-component designs are partly a response to this.

Common mistakes

Forgetting the virtual destructor

Deleting a derived object through a base pointer without one is undefined behaviour and usually leaks the derived part.

Calling virtual functions from constructors

They do not dispatch to the derived class yet. Move such work to a separate init step if needed.

Misspelling an override

Without override, a typo in the name or a missing const silently creates a new function instead of overriding. Always write override.

Copying objects with vptrs as raw bytes

Saving them to a file or memcpy-ing into unrelated memory copies an address that means nothing elsewhere.
