Capstone: A Moddable Game with a Plugin System

lesson 18.022 of 4 in milestone 187 min1 practice task

The second capstone turns Delve into a game built to be modded, joining chapters 10, 11 and 13 with the security of chapter 17. Mods add data (levels, items, monsters), scripts and optional native plugins through a versioned API; a mod manager resolves load order and dependencies; the game survives broken mods. This lesson gives the specification, the mod format, the plugin API shape, milestones, acceptance tests and stretch goals.

What you are building

Delve: Open Depths is Delve with a mod system that strangers could use safely:

  • Data mods add or override levels, items, monsters and text, with no code at all (lesson 13.02).
  • Script mods add behaviour through the small scripting layer from lesson 10.08.
  • Native plugins are DLLs using a versioned C interface (lessons 13.03, 13.04), disabled by default and enabled per mod with a clear warning.
  • A mod manager screen lists installed mods, shows conflicts and missing dependencies, and lets the player enable, disable and reorder them.
  • The game never crashes because of a mod: bad data is rejected with a message, and a plugin that fails is disabled for the next start.

The mod format

Each mod is a folder under Mods\ with a manifest:

INI
; Mods\lantern\mod.ini
[mod]
id = lantern
name = The Lantern
version = 1.2.0
api = 1
requires = core-items >= 1.0.0
after = brighter-torches
[content]
items = data/items.ini
levels = data/levels
plugin = lantern.dll          ; optional, native code
Field Rules
id Lower-case letters, digits and -; unique
version A semantic version (lesson 17.08)
api The plugin and script API version it was built for; the game refuses mods for a newer major version
requires Other mod ids, with optional minimum versions; a missing one disables this mod with a message
after Soft ordering: load after these if present, without requiring them
content paths Relative to the mod folder, passed through safeJoin (lesson 17.04)

Load order

Mods that override the same item need a deterministic order. Build a graph where an edge a → b means "a loads before b" (from requires and after), then a topological sort, with alphabetical order breaking ties so the result never depends on folder listing order. A cycle is reported to the player, naming the mods in it, and those mods are disabled. The practice task implements this.

The plugin API

The native API follows lesson 13.07: a C interface with a version, a table of functions the game provides, and a table the plugin fills in.

C++
// delve_api.h, shipped to plugin authors
#define DELVE_API_VERSION 1

struct DelveHost                  // functions the game gives the plugin
{
    uint32_t size;                // sizeof(DelveHost), so fields can be added later
    void (*log)(const char* text);
    int  (*registerItem)(const char* id, const char* name, int value);
    int  (*onEvent)(const char* event, void (*handler)(const char* payload));
};

struct DelvePlugin                // functions the plugin gives the game
{
    uint32_t size;
    const char* id;
    void (*shutdown)();
};

// The one export every plugin provides:
extern "C" __declspec(dllexport) int DelvePluginInit(uint32_t apiVersion, const DelveHost* host, DelvePlugin* out);

Rules for the host side:

  • Check the apiVersion and each table's size before using it.
  • Load plugins only from their own mod folder, by full path, with LoadLibraryExW and LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32 (lesson 13.04).
  • Never let a C++ exception or a structured exception cross the boundary: wrap every call into a plugin, and on failure disable the plugin and record it in Mods\disabled.ini.
  • Plugins run with the game's rights: the warning to the player says so plainly (lesson 17.06).

Milestones

  1. Manifests: find and parse every mod.ini, validate fields, report problems in a log and on screen.
  2. Load order: dependency checks, the topological sort, cycle reports.
  3. Data mods: item and level overrides applied in load order; later mods win; the debug menu (lesson 13.06) shows which mod defined each item.
  4. Mod manager screen: enable, disable, reorder (which edits after hints in a user file, never the mod's own manifest), and show errors.
  5. Scripts: event hooks (onPickup, onLevelStart) calling the script layer, with a time limit per call.
  6. Native plugins: the API above, with the version and size checks and crash containment.
  7. A sample mod pack: three small mods (a new item set, a new level, and a plugin that adds an achievement log) that exercise every feature, shipped with a short modding guide.
  8. Hardening: fuzz the manifest and item parsers (lesson 17.03), and work through the threat model from lesson 17.05 for the mod folder.

Acceptance tests

  • With the sample pack installed in any folder order, the load order is the same every time.
  • A mod requiring a missing mod is disabled with a message naming the missing id.
  • Two mods that require each other are both disabled with a message naming the cycle.
  • A manifest with a content path of ..\..\saves is refused.
  • A plugin built for API version 2 is refused by a version 1 game with a clear message.
  • A plugin that throws during DelvePluginInit is disabled, and the game starts normally the next time.
  • Removing every mod gives exactly the original game.

Stretch goals

  • Hot reload of data mods while the game runs.
  • A mod.ini linter as a separate command-line tool for mod authors.
  • Packaging mods as a single zip file with a hash in the manifest, verified on load.

Common mistakes

Load order that depends on the file system

Folder listing order differs between machines. Sort explicitly.

Passing C++ types across the plugin boundary

std::string and exceptions differ between compiler versions. Keep the API in C.

Letting one bad mod stop the game

Report, disable, continue.
