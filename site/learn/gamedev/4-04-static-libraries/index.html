Static Libraries

lesson 4.044 of 10 in milestone 46 min

A static library (.lib) is a bundle of object files. Linking it into a program copies in the parts the program uses, so the result is one self-contained .exe. This lesson builds the course's engine library, shows how the linker pulls code out of it, and covers the settings that must match between a library and the program that uses it.

A bundle of object files

When a project's Configuration Type is Static library (.lib), its build stops after compiling: instead of linking the object files into an executable, the librarian (lib.exe) packs them into one .lib file with an index of the symbols each defines.

flowchart LR
    A["math.cpp"] --> AO["math.obj"]
    B["tilemap.cpp"] --> BO["tilemap.obj"]
    C["random.cpp"] --> CO["random.obj"]
    AO --> L["lib.exe"]
    BO --> L
    CO --> L
    L --> LIB["engine.lib<br/>(index + 3 object files)"]

When a program links against engine.lib, the linker looks up each unresolved symbol in the index and copies in only the object files that define what is needed. If the game never calls anything in random.obj, none of it ends up in the .exe.

Building the engine library

In the course solution from lesson 4.01, engine is already a static library project. Give it some real code:

C++
// engine/vec2.h
#pragma once

struct Vec2
{
    float x{ 0 };
    float y{ 0 };
};

Vec2 operator+(Vec2 a, Vec2 b);
Vec2 operator*(Vec2 v, float s);
float length(Vec2 v);
C++
// engine/vec2.cpp
#include "vec2.h"
#include <cmath>

Vec2 operator+(Vec2 a, Vec2 b) { return { a.x + b.x, a.y + b.y }; }
Vec2 operator*(Vec2 v, float s) { return { v.x * s, v.y * s }; }
float length(Vec2 v) { return std::sqrt(v.x * v.x + v.y * v.y); }
C++
// game/main.cpp
#include <iostream>
#include "vec2.h"

int main()
{
    Vec2 position{ 1, 2 };
    Vec2 velocity{ 3, 4 };
    position = position + velocity * 0.5f;
    std::cout << position.x << ", " << position.y << "  speed " << length(velocity) << '\n';
    return 0;
}

With the project reference and include directory from lesson 4.01 in place, building the solution builds engine.lib first, then compiles main.cpp and links it with engine.lib. The output prints 2.5, 4 speed 5.

Without a project reference (for example, a library someone else built), you tell the linker yourself:

  • Linker → General → Additional Library Directories: the folder containing the .lib;
  • Linker → Input → Additional Dependencies: the file name, engine.lib;
  • or, in code, #pragma comment(lib, "engine.lib").

Settings that must match

Object files compiled with different settings may not work together, and the linker catches some (not all) of these mismatches:

Setting Must match because Mismatch error
Platform (x64 / x86) 64-bit and 32-bit code cannot be mixed LNK1112: module machine type conflicts
Runtime library (/MD, /MDd, /MT, /MTd) Each object file asks for a particular C runtime; they must agree LNK2038: mismatch detected for 'RuntimeLibrary'
Debug / Release (_ITERATOR_DEBUG_LEVEL) Standard containers have different layouts in Debug and Release LNK2038: mismatch detected for '_ITERATOR_DEBUG_LEVEL'
C++ standard, struct packing, other defines that change layout A class laid out differently in two files is a silent ODR violation Usually none: just strange crashes

The LNK2038 checks exist because these mismatches used to cause baffling crashes: a std::vector passed from a Release library to Debug code has a different layout on each side. So build every library in the same configuration as the program. A project reference does this automatically; a pre-built library usually ships in both Debug and Release forms for this reason.

The runtime library choice deserves a note. /MD links the C and C++ runtime as DLLs (the user needs the Visual C++ Redistributable installed); /MT copies the runtime into your executable. Either is fine for this course; just be consistent across every project in the solution.

Static libraries versus DLLs

Static library DLL (next lesson)
When code is joined At link time, copied into the .exe At run time, loaded from a separate file
Files to ship Just the .exe The .exe and every .dll
Updating the library Rebuild and relink the program Replace the .dll
Loading code chosen at run time (plugins) Not possible Possible
Sharing between programs Each program has its own copy One file can be shared

The course uses a static library for the engine, which the game always needs, and a DLL for plugins, which the game chooses to load.

Common mistakes

Linking a Debug library into a Release program

LNK2038 warns you. Use project references, or link the matching build of the library.

Expecting a static library to work without its headers

The .lib holds code; your program still needs the declarations from its headers to call it.

Global objects in a static library that nothing references

The linker only pulls in object files that define something needed. A self-registering global in an otherwise unreferenced .obj is silently left out.
