Cross-References: Finding Where Data Is Used

lesson 9.088 of 10 in milestone 95 min1 practice task

A cross-reference (xref) records that one place in a program refers to another: a call to a function, a read of a global, a use of a string. Following xrefs, backwards to "who uses this?" and forwards to "what does this use?", is how you navigate an unknown program. This lesson covers the kinds of xref, how disassemblers find them, and how to decode a call instruction's target yourself.

What a cross-reference is

When an instruction mentions an address (calls it, jumps to it, reads or writes it, or takes it with lea), the disassembler records a reference from that instruction to that address. Seen from the target, those are its xrefs: every place that refers to it.

Kind Example Meaning
Call call 140001070 Code that calls this function
Jump jmp 140001200 / jne ... Code that branches here
Read mov eax, [140005010] Code that reads this data
Write mov [140005010], eax Code that writes this data
Offset (address taken) lea rcx, [140004120] Code that takes this address: passing a string, a callback, a table
Data an 8-byte pointer in a vtable or table Data that points here

In Ghidra, the XREF[n]: annotation at each label lists them, and References → Show References to (Ctrl+Shift+F) opens the full list.

Navigating with xrefs

Most reverse engineering is moving along xrefs from something you understand to something you do not:

flowchart LR
    S["String<br/>'Failed to open save file %s'"] -->|"xref: lea rcx"| F["FUN_140003A10<br/>now: loadSave"]
    F -->|"xref to loadSave: call"| M["FUN_140001B00<br/>calls loadSave on the menu's 'Continue'"]
    F -->|"calls"| C["CreateFileW, ReadFile<br/>(imports)"]
    F -->|"writes"| G["DAT_140009040<br/>now: g_currentSave"]

Typical starting points:

  • Strings (lesson 9.06): follow the string's xref to the code that prints or uses it.
  • Imports: xrefs to CreateFileW list every place the program opens files.
  • A global you found in the debugger (lesson 9.07): its read and write xrefs list every function that uses it.
  • A vtable: its xrefs are constructors and destructors (lesson 9.06).

How call targets are found

Disassemblers find most code xrefs by decoding instructions. The most common, the near call, is easy to decode by hand: the byte E8 followed by a 4-byte signed displacement relative to the address of the next instruction:

address 140001000:  E8 6B 00 00 00      call 140001070
                    └┘ └──────────┘
                    op   rel32 = 0x0000006B

target = address of next instruction + rel32
       = (140001000 + 5) + 0x6B = 140001070

The displacement is relative (lesson 6.09's RIP-relative idea), so the same bytes work wherever the module is loaded. Negative displacements call backwards. Scanning code for E8 bytes and computing targets finds call xrefs, with one caveat: E8 can also appear inside other instructions' operands, so real disassemblers decode instruction by instruction rather than scanning blindly. The practice task does the simple scan on a buffer known to contain only calls and padding.

RIP-relative data references (mov eax, [rip+disp32], lea rcx, [rip+disp32]) work the same way: target = next instruction's address + displacement.

Xrefs the analysis misses

Some references are invisible to static analysis:

  • Addresses computed at run time (base + index * 8 into a table it did not decode).
  • Functions found with GetProcAddress from a string.
  • Pointers stored in data structures built at run time.

Dynamic analysis fills these gaps: a breakpoint or hardware watchpoint shows the real reference, and you add it manually (Ghidra lets you add references by hand).

Common mistakes

Forgetting reads versus writes

"Who writes this global?" usually narrows things far more than "who uses it?". Filter xrefs by kind.

Computing a relative target from the instruction's own address

Relative displacements count from the address of the next instruction.

Trusting a lack of xrefs

No xrefs found does not mean unused: the reference may be computed at run time.

Knowledge check

quizIn Xenon your best score is kept.
  1. A call at 0x140002000 is encoded E8 F0 FF FF FF. Where does it call?
    • 0x140001FF5
    • 0x140002005
    • 0x1400020F0
    Show the answer

    0x140001FF5 rel32 = 0xFFFFFFF0 = -16; next instruction at 0x140002005; 0x140002005 - 16 = 0x140001FF5.

  2. What do the xrefs to a vtable usually point to?
    • The constructors and destructors that store it into objects
    • Every virtual call
    • The class's data members
    Show the answer

    The constructors and destructors that store it into objects Virtual calls read the vptr from the object, not the vtable's address directly.

  3. How can you find every place a program opens a file?
    • List the cross-references to the imported CreateFileW
    • Search for .txt in the strings
    • Read the entry point
    Show the answer

    List the cross-references to the imported CreateFileW Every call to an import goes through its IAT slot, and each is an xref.
