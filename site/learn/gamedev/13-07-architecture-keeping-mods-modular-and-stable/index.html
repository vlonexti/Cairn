Architecture: Keeping Mods Modular and Stable

lesson 13.077 of 8 in milestone 135 min1 practice task

A game with mods is a platform other people build on. This lesson covers the architecture that keeps it stable: isolating failures so one broken mod cannot take the game down, budgets for mod work, keeping saves safe, versioning everything mods touch, diagnosing problems from players' reports, and the honest limits of isolating native code.

Failures must stay local

With twenty mods installed, something will go wrong eventually. The architecture decides whether that means "mod X stopped working, the game told you why" or "the game crashes on start-up and nobody knows why".

Kind of mod How to contain a failure
Data Validate on load; report the mod, file, line and key; skip the bad entry (lessons 10.08, 13.02)
Scripts Catch script errors at each call into the script; report the mod and line; disable that mod's scripts for the session
Plugins Catch C++ exceptions at the boundary; validate tables (lesson 13.03); count failures and disable a plugin that keeps failing

The practice task builds the plugin guard: every call into a plugin goes through it, exceptions are caught and recorded against the plugin, and after a few failures the plugin is switched off for the rest of the session with a message to the player.

The limits of isolating native code

A plugin DLL runs inside the game's process with the same memory and rights (lesson 13.04). Catching exceptions handles the polite failures. An impolite one (a plugin writing through a dangling pointer, corrupting the heap) cannot be contained in-process: it can corrupt anything, and the crash may appear somewhere else entirely (lesson 2.09). The honest options:

  • Accept it and diagnose well: crash dumps (lesson 8.04) that record which plugins were loaded and which module the crash was in, so players and authors can find the culprit.
  • Offer safer layers: data and scripts (sandboxed, with only the functions the game exposes) cover most mods; native plugins are for the few that need them.
  • Out-of-process plugins: run plugins in a separate process talking through pipes or shared memory (chapter 12's channels). A crash there kills only the helper process. It costs speed and complexity, so it is used where stability matters most, such as editors and browsers.

Budgets

A mod that spends 20 ms per frame turns a smooth game into a slideshow, and players blame the game. Measure each plugin's and script's time per frame with lesson 13.05's scoped timers, show it in the debug menu and a mod list, and warn when one exceeds its budget. Scripting languages can also limit instruction counts per call, stopping infinite loops.

Saves and mods

Lesson 11.06's save format records the enabled mods and their versions. On loading:

  • Missing mod: warn, and either refuse or load with its content removed (items from a missing mod become "unknown item" placeholders rather than crashing the loader).
  • Different version: warn; the mod may provide a migration (lesson 10.07) for its own saved data.
  • Mods store their own data in namespaced sections (mod.lantern-light.fuel) so they cannot collide with each other or with the game.

Diagnosing players' problems

Most mod problems arrive as "the game crashes, I have 40 mods". Make diagnosis possible:

  1. The log (lesson 8.03) starts with the game version and the full, ordered mod list with versions.
  2. Every warning and error names the mod responsible.
  3. Crash dumps include the module list; the crash report says which module the crash happened in (lesson 8.02).
  4. A safe mode start option disables all mods, so players can confirm whether mods are involved, and a "disable half" option lets them bisect (lesson 8.01) to the culprit.

Common mistakes

One bad mod stops the game from starting

Validate, report and skip; never let a single mod's failure become the game's failure.

Claiming plugins are "sandboxed"

Native code in your process is not. Be honest with players and offer safer layers.

Logs that do not say which mod

Every message about a problem should name its source.
