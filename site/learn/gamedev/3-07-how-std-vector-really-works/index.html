How std::vector Really Works

lesson 3.077 of 10 in milestone 37 min

std::vector is three pointers and a heap block. Its size is how many elements are in use, its capacity how many fit before it must grow. When it grows, it allocates a bigger block, moves everything across and frees the old one, which is why pointers into a vector can suddenly dangle. Knowing this lets you use the most important container in C++ efficiently.

Three pointers

A std::vector<T> object is 24 bytes in a Release build, three pointers:

std::vector<int> (Release x64)          heap block
┌───────────────┐                       ┌────┬────┬────┬────┬────┬────┐
│ first ────────┼──────────────────────▶│ 10 │ 20 │ 30 │ 40 │ ?? │ ?? │
│ last  ────────┼───────┐               └────┴────┴────┴────┴────┴────┘
│ end   ────────┼───┐   │                                   ▲         ▲
└───────────────┘   │   └───────────────────────────────────┘         │
                    └─────────────────────────────────────────────────┘

    size()     = last − first = 4      (last points just past the 40)
    capacity() = end − first  = 6      (end points just past the block)
  • first points at element 0 (data() returns it),
  • last points just past the last element in use,
  • end points just past the end of the block.

size() and capacity() are subtractions. The elements in use are exactly an array, which is why everything from lesson 2.07 applies: indexing is one calculation, and looping walks memory in order.

Growing

When push_back finds size() == capacity(), there is no room. The vector then:

  1. allocates a new, bigger block;
  2. moves (or copies) every element into it;
  3. destroys the old elements and frees the old block;
  4. adds the new element.

That is expensive, so the new block is not just one bigger. Microsoft's implementation grows by half again each time (a factor of 1.5); others use 2. Because the growth is a fixed factor, the total work averages out to a constant amount per push_back, but individual pushes are occasionally very slow.

C++
#include <iostream>
#include <vector>

int main()
{
    std::vector<int> v;
    std::size_t lastCapacity{ v.capacity() };
    std::cout << "capacity " << lastCapacity;
    for (int i{ 0 }; i < 100; ++i)
    {
        v.push_back(i);
        if (v.capacity() != lastCapacity)
        {
            lastCapacity = v.capacity();
            std::cout << ' ' << lastCapacity;
        }
    }
    std::cout << '\n';
    return 0;
}
Output
capacity 0 1 2 3 4 6 9 13 19 28 42 63 94 141

Thirteen reallocations to reach 100 elements, each copying everything so far. If you know roughly how many elements are coming, say so up front:

C++
std::vector<Bullet> bullets;
bullets.reserve(512);     // one allocation; no regrowth until 512

reserve changes capacity, not size: the vector is still empty, but the room is there. resize(n) changes size, creating or destroying elements.

Growth invalidates pointers

Step 3 above frees the old block. Every pointer, reference and iterator to an element pointed into that block, and now dangles:

C++
#include <iostream>
#include <vector>

int main()
{
    std::vector<int> v{ 1, 2, 3 };
    int* first{ &v[0] };
    v.push_back(4);             // capacity was 3: reallocates
    std::cout << *first << '\n';  // reads freed memory
    return 0;
}

The rules, briefly:

Operation What it invalidates
push_back, emplace_back, insert Everything, if it reallocates; otherwise elements at or after the insertion point
reserve (to a bigger capacity) Everything
erase Elements at or after the erased position
pop_back Only the removed element
Reading, writing existing elements Nothing

The robust habit in game code is to refer to vector elements by index, not by pointer. An index stays meaningful when the block moves. Lesson 3.10 builds on this.

Inserting and erasing in the middle

The elements are contiguous, so inserting or erasing anywhere except the end has to shift every later element by one place. Erasing the first of a million elements moves 999,999 of them.

When order does not matter, which in games it often does not, use swap and pop: move the last element into the hole and shrink by one.

C++
#include <iostream>
#include <vector>

void removeAtUnordered(std::vector<int>& v, std::size_t i)
{
    v[i] = std::move(v.back());   // the last element fills the hole
    v.pop_back();                 // and the end shrinks by one
}

int main()
{
    std::vector<int> enemies{ 10, 20, 30, 40, 50 };
    removeAtUnordered(enemies, 1);
    for (int e : enemies) std::cout << e << ' ';
    std::cout << '\n';
    return 0;
}
Output
10 50 30 40

Constant time, however big the vector. And to remove every element that matches a condition, std::erase_if(v, predicate) (C++20) does it in one pass, moving each kept element at most once.

emplace_back versus push_back

push_back(obj) copies or moves an existing object into the vector. emplace_back(args...) constructs the element directly in the vector's memory from constructor arguments, skipping the temporary. For simple types the difference is nothing; for objects that are expensive to move, emplace_back can save work.

A vector of objects or of pointers?

std::vector<Enemy> std::vector<std::unique_ptr<Enemy>>
Enemies stored side by side: fast to loop over Pointers side by side; enemies scattered on the heap
Growing moves the enemies themselves Growing moves only the pointers; the enemies stay put
Pointers to enemies dangle after growth Pointers to enemies stay valid
All elements must be the same type Can hold derived classes (polymorphism)

Games favour the left column for anything numerous and processed every frame, and use indices to refer to elements.

Common mistakes

[!warning] Keeping &v[i] or an iterator across a push_back Store the index instead, or re-take the pointer after the change.

Erasing inside a range-based for loop

The loop's hidden iterators are invalidated. Use std::erase_if, or an index loop that does not advance when it erases.

[!warning] Calling reserve inside a loop v.reserve(v.size() + 1) before each push defeats the growth factor and reallocates every time. Reserve once, before the loop.

[!warning] Confusing reserve with resize After reserve(10), v[0] is still out of range: the size is 0.

  1. A vector has size 6 and capacity 6. What happens on push_back?
    • A bigger block is allocated, the 6 elements are moved into it, the old block is freed, and the new element is added

    • The program throws an exception
    Show the answer

    A bigger block is allocated, the 6 elements are moved into it, the old block is freed, and the new element is added A heap block cannot grow in place, so the vector moves to a new, larger one.

  2. Why does a vector grow by a factor (such as 1.5×) instead of by one element at a time?
    • To waste less memory
    • So that the total cost of many push_backs averages out to a constant per element
    • Because the heap only allocates in powers of two
    Show the answer

    So that the total cost of many push_backs averages out to a constant per element Growing by one would copy everything on every push: the cost would grow with the square of the size.

  3. What does v.reserve(100) do to an empty vector's size?
    • Nothing: the size stays 0, only the capacity changes
    • Sets it to 100
    • Sets it to 100 default-constructed elements
    Show the answer

    Nothing: the size stays 0, only the capacity changes reserve makes room; resize changes the number of elements.

  4. What is the cost of swap-and-pop removal?
    • Constant, whatever the size of the vector
    • Proportional to the number of elements after the removed one
    • Proportional to the size of the vector
    Show the answer

    Constant, whatever the size of the vector One move and one pop_back. The order of the elements changes, which is the price.
