The Memory Manager

lesson 15.044 of 8 in milestone 156 min1 practice task

The kernel's memory manager provides every process's virtual address space (chapter 6) and also manages kernel memory. This lesson covers the kernel side: paged and non-paged pool, why the difference matters so much in drivers, pool tags for tracking allocations, memory descriptor lists (MDLs) for describing buffers, and how the memory manager handles page faults.

Paged and non-paged pool

Kernel code allocates memory from pools, the kernel's heaps, shared by all drivers:

Pool Can be paged out to disk? Usable at
Paged pool Yes Only when page faults are allowed: IRQL below DISPATCH_LEVEL (lesson 15.06)
Non-paged pool No: always in RAM Any IRQL, including interrupt handlers

Why both? Non-paged memory is precious: it permanently consumes RAM. But some kernel code runs at times when a page fault cannot be handled (while holding a spin lock, in an interrupt or DPC, lesson 15.06), and touching paged memory then, if it has been paged out, crashes the machine with IRQL_NOT_LESS_OR_EQUAL or PAGE_FAULT_IN_NONPAGED_AREA. So drivers put in non-paged pool exactly the data that code at high IRQL touches, and everything else in paged pool.

The same rule applies to code: a driver function that may run at DISPATCH_LEVEL must be in non-paged memory. Drivers mark functions that only run at PASSIVE_LEVEL as pageable with #pragma alloc_text(PAGE, ...) and assert their IRQL with the PAGED_CODE() macro.

Allocating with tags

C++
// A 4-character tag identifies who allocated it: here 'Echo', written backwards in memory as a little-endian integer.
constexpr ULONG kTag{ 'ohcE' };

auto* buffer{ static_cast<char*>(ExAllocatePool2(POOL_FLAG_NON_PAGED, size, kTag)) };
if (!buffer) return STATUS_INSUFFICIENT_RESOURCES;       // allocation can fail: always check
// ... use it ...
ExFreePoolWithTag(buffer, kTag);
  • ExAllocatePool2 (Windows 10 2004 and later) zero-initialises memory, unlike its predecessor ExAllocatePoolWithTag, which avoided a whole class of information-leak bugs.
  • Every allocation carries a pool tag, a four-character code chosen by the driver. Tools such as !poolused in WinDbg and Sysinternals PoolMon show how much memory each tag holds, which is how kernel memory leaks are found: a tag whose usage keeps growing points at the guilty driver. The practice task builds this kind of tracking.
  • Leaked pool memory is never reclaimed until reboot, because there is no process to clean up after (lesson 15.01).

Memory descriptor lists

When a driver needs to work with a buffer that belongs to a user process, for example to read data directly into it, it cannot simply keep the user's virtual address: that address is only valid in that process, and the pages could be paged out or freed. An MDL (memory descriptor list) describes the buffer by its physical pages:

  1. Build an MDL for the user range (IoAllocateMdl).
  2. Lock the pages in RAM (MmProbeAndLockPages, inside __try, with the probing rules of lesson 15.02).
  3. Map them into kernel space if needed (MmGetSystemAddressForMdlSafe), giving an address valid in any process context and at raised IRQL.
  4. Unlock and free when done.

Chapter 16's "direct I/O" (lesson 16.07) has the I/O manager do these steps for the driver.

Page faults, from the kernel's side

When a thread touches a page that is not present (lesson 6.02), the processor raises a page fault and the memory manager runs:

  • Is the address valid for this process (committed or a mapping)? If not: an access violation exception in user mode, a bug check in kernel mode if nothing handles it.
  • If valid: find a free physical page, fill it (zeros, or read from the page file or a mapped file, which means waiting for disk I/O), update the page table, and resume the thread.

Waiting for disk is why a page fault can only be handled at low IRQL: at DISPATCH_LEVEL and above, the thread cannot wait.

Common mistakes

Paged memory touched at DISPATCH_LEVEL or higher

Works until the page happens to be paged out, then crashes the machine. Use non-paged pool for anything touched at raised IRQL.

Not checking pool allocations

Pool allocation can fail; return STATUS_INSUFFICIENT_RESOURCES.

Keeping a user virtual address in a driver

It is meaningless in another process context. Use an MDL or copy the data.
