Debugging Threads

lesson 8.077 of 8 in milestone 85 min1 practice task

Multithreaded bugs are timing-dependent, so they hide when you look for them. This lesson covers the tools that make them visible: naming threads, the Threads and Parallel Stacks windows, freezing threads to force an ordering, diagnosing deadlocks from call stacks, and finding races with careful logging and data breakpoints.

Name your threads

The first step costs one line per thread. Give each thread a name, and every tool shows it instead of a bare id:

C++
#include <windows.h>
#include <thread>

void startAudioThread()
{
    std::jthread audio{ [] {
        SetThreadDescription(GetCurrentThread(), L"Audio mixer");
        // ...
    } };
}

SetThreadDescription (Windows 10 1607 and later; lesson 5.08 showed how to call it safely on older systems) names the thread for Visual Studio, WinDbg, crash dumps and profilers.

The Threads window

Debug → Windows → Threads lists every thread when the program is paused: its id, name, location (the function it is in) and priority. Double-click a thread to switch to it: the Call Stack, Locals and editor then show that thread's view. A yellow arrow marks the current thread.

Right-click → Freeze suspends a thread so it will not run when you continue; Thaw releases it. Freezing is a powerful way to force an interleaving: freeze the main thread at a chosen line, let a worker run past a critical point, then thaw the main thread. A race that appears once in a thousand runs can be reproduced every time this way.

Parallel Stacks

Debug → Windows → Parallel Stacks draws every thread's call stack at once, merging the frames they share into a graph. With twenty worker threads, you see at a glance that eighteen are idle in the job queue's wait, one is in physics, and one is stuck somewhere unexpected.

Diagnosing a deadlock

The game freezes and the CPU usage is near zero: the signature of a deadlock (lesson 6.06), as opposed to an infinite loop, which shows 100% of a core.

  1. Break All (Ctrl+Alt+Break).
  2. Open Parallel Stacks or go through the threads in the Threads window. Look for threads waiting inside lock functions: std::mutex::lock, EnterCriticalSection, WaitForSingleObject, RtlpWaitOnCriticalSection.
  3. For each, find which lock it waits for (the argument to the lock call, visible in its frame) and which locks it holds (locks taken in earlier frames of its own stack).
  4. Draw the arrows: "thread A holds lock 1 and waits for lock 2; thread B holds lock 2 and waits for lock 1". A cycle is a deadlock.

In WinDbg, !locks lists Windows critical sections that are held, with the owning thread, and ~*k prints every thread's stack, which does steps 2 and 3 quickly. The practice task automates step 4: finding a cycle in "who waits for whom".

Finding races

Data races are harder: there is no hang and no crash at the moment of the race, only a wrong value later. Approaches, cheapest first:

  • Think about ownership. For each piece of shared data, which threads touch it and which lock protects it? Data touched by two threads with no lock in common is the suspect.
  • Data breakpoints (lesson 4.09) on the corrupted value: the debugger stops on whichever thread writes it, and the Threads window shows what the others were doing.
  • Logging with thread ids and sequence numbers, written to a lock-free per-thread ring buffer (formatting and locks inside logging change the timing enough to hide the bug).
  • Stress: run the suspected code in a tight loop with many threads to make the race frequent.
  • Tools: Clang's ThreadSanitizer (on Linux builds, or Clang on Windows with limits) detects races automatically; on MSVC, the Concurrency Visualizer extension shows which threads ran when.

Common mistakes

Stepping a single thread and expecting others to wait

When you step, all threads run (unless frozen). Breakpoints in shared code can hit on any thread.

Adding a log line and the bug disappears

Logging changes timing. That does not mean the bug is fixed; it confirms it is timing-dependent.

Fixing a deadlock by adding a timeout

The cycle is still there. Fix the lock order.
