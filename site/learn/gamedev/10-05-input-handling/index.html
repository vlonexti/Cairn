Input Handling

lesson 10.055 of 9 in milestone 105 min1 practice task

Raw input (keys, mouse buttons, gamepad sticks) is not what game code should depend on. Engines turn it into actions ("jump", "move left"), track for each one whether it was pressed, held or released this frame, and let players rebind the keys. This lesson builds that layer, and covers gamepads, dead zones and input buffering.

From devices to actions

Game code should never ask "is the space bar down?". It should ask "does the player want to jump?". The difference matters as soon as you support rebinding, a gamepad, or a second keyboard layout:

flowchart LR
    K["Keyboard<br/>Space, W, A, D"] --> B["Bindings<br/>Space → Jump<br/>W → MoveUp<br/>Pad A → Jump"]
    P["Gamepad<br/>A button, left stick"] --> B
    M["Mouse"] --> B
    B --> S["Action state this frame<br/>Jump: pressed<br/>MoveUp: held"]
    S --> G["Game code<br/>if (input.pressed(Action::Jump))"]

Pressed, held and released

Lesson 5.07 showed two ways to read keys: messages, and the current state. For game controls the cleanest model is: once per frame, take a snapshot of every action's state (down or up), and keep the previous frame's snapshot. Then for each action:

Query Previous Now Use for
held (any) down Continuous actions: walking, aiming, charging
pressed up down One-shot actions: jump, fire one shot, open a menu
released down up Releasing a charged attack, ending a drag

Because the snapshot is taken once at the start of the frame (lesson 10.01's input phase), every system in that frame sees the same answer. Checking the live key state in the middle of an update lets two systems disagree about whether a key was pressed.

There is one trap: a tap shorter than a frame can be missed by pure polling, because the key is already up again when the snapshot is taken. Recording "went down at least once this frame" from the key-down messages, as well as the current state, fixes it.

Bindings and rebinding

A binding maps a physical input to an action. Keep them in data, not code:

C++
enum class Action { MoveLeft, MoveRight, Jump, Attack, Count };

struct Binding { int key; Action action; };

std::vector<Binding> bindings{
    { 'A', Action::MoveLeft }, { VK_LEFT, Action::MoveLeft },
    { 'D', Action::MoveRight }, { VK_RIGHT, Action::MoveRight },
    { VK_SPACE, Action::Jump }, { 'J', Action::Attack },
};

Several keys may map to one action (an action is down if any of its keys is down). Rebinding is then just editing the table and saving it with the settings (lesson 10.07). Use virtual-key codes or, for layout-independent positions such as WASD, scan codes (lesson 5.07).

Gamepads and dead zones

On Windows, Xbox-compatible controllers are read with XInput (XInputGetState) or the newer GameInput API; libraries like SDL (chapter 11) cover many controllers. Analogue sticks report numbers (for XInput, −32768 to 32767 per axis), and a stick at rest never reads exactly zero: it drifts by a few percent. A dead zone ignores small values:

C++
float applyDeadZone(float value, float deadZone)    // value from -1 to 1
{
    const float magnitude{ std::abs(value) };
    if (magnitude < deadZone) return 0.0f;
    // Rescale so movement starts smoothly from 0 just outside the dead zone.
    return std::copysign((magnitude - deadZone) / (1.0f - deadZone), value);
}

For a 2D stick, apply the dead zone to the length of the (x, y) vector, not each axis separately, or diagonal movement feels wrong.

Input buffering

Players press buttons slightly early. If the jump button was pressed three frames before the character landed, a strict game ignores it and the player feels the game "ate" their input. Buffering remembers recent presses for a short window (often 100 to 150 ms) and acts on them as soon as the action becomes possible. Its cousin, coyote time, still allows a jump for a few frames after walking off a ledge. Small touches like these are a large part of why some games "feel" responsive.

Common mistakes

Hard-coding keys in game logic

Map keys to actions in one place, so rebinding and gamepads work everywhere.

Reading live key state during the update

Snapshot once per frame so every system agrees.

No dead zone on analogue sticks

Characters drift on their own. Apply a dead zone to the stick vector.

Acting on input while the window is unfocused

GetAsyncKeyState sees keys typed in other programs. Ignore input when the game is not in front.
