Thinking Like a Debugger

lesson 8.011 of 8 in milestone 86 min1 practice task

Debugging is a method, not a talent. This lesson sets out the method experienced engineers use: make the bug happen reliably, form a hypothesis, test it with the smallest possible experiment, and narrow the search by halving it. It covers minimal reproductions, bisecting code and history, and the habits that make the tools in the rest of this chapter effective.

The loop

Every effective debugging session runs the same loop:

flowchart LR
    R["Reproduce<br/>make it happen on demand"] --> O["Observe<br/>what exactly happens?"]
    O --> H["Hypothesise<br/>one specific cause"]
    H --> T["Test<br/>an experiment that could prove it wrong"]
    T -->|"wrong"| O
    T -->|"confirmed"| F["Fix, then check the<br/>original reproduction"]

The common failure is skipping steps: changing code at random ("maybe it's this"), or fixing the first suspicious thing without confirming it caused the symptom. A fix you cannot explain is a guess, and guesses usually move a bug rather than remove it.

Step 1: reproduce

A bug you can trigger on demand is half solved. A bug that happens "sometimes" is the hardest kind, so the first job is to make it reliable:

  • Write down the exact steps, inputs, save file, settings and build.
  • Remove randomness: fix the random seed, fix the time step, record the input.
  • For "sometimes" bugs, run it in a loop (a script that starts the game a hundred times) and look for what the failing runs have in common.
  • Check the obvious variables: Debug or Release? Your machine or another? Fresh install or old settings?

Step 2: observe precisely

"It crashes" is not an observation. "It crashes with an access violation reading 0x10, in Inventory::weight, called from Hud::draw, only after picking up an item while the inventory screen is open" is. The debugger's job (chapter 4) is to turn vague symptoms into precise ones: the exact instruction, the exact values, the exact call stack.

Read error messages and crash details completely, as lesson 4.03 said for compiler errors. The address, the exception code (lesson 8.04) and the module are each clues.

Step 3: one hypothesis at a time

A good hypothesis is specific and testable: "the item pointer is stale because the inventory vector grew" can be tested with a data breakpoint or a log line. "Something's wrong with memory" cannot.

Test it with the cheapest experiment that could prove it wrong: a conditional breakpoint, a log line, an assert, changing one input. If the experiment shows the hypothesis is wrong, that is progress too: one possibility is gone.

Narrowing the search: halve it

When you do not know where a bug is, do not read code hoping to spot it. Bisect: split the search space in half, find out which half contains the bug, repeat. Each step halves the remaining space, so even a huge search is short: about 10 steps for a thousand possibilities, 20 for a million.

What to bisect How
History: which change introduced the bug? git bisect: mark a known good and a known bad commit; Git checks out the midpoint, you test and answer "good" or "bad", repeat
Input: which part of a level or save file triggers it? Delete half the content; does the bug remain?
Code path: where does a value go wrong? Check the value at the midpoint of the computation with a breakpoint or log
Time: when does state become corrupt? Log or assert the invariant every frame; find the first frame it fails

The practice task implements the search at the heart of this.

Minimal reproductions

Once a bug is reliable, shrink it: remove everything that is not needed for it to happen. A 30-line program that shows the bug is far easier to reason about than a whole game, and very often the act of shrinking it reveals the cause. It is also what you need to report a bug in someone else's library or compiler.

Habits that pay off

  • Check your assumptions out loud. Explaining the code line by line to someone else, or to a rubber duck, forces you to notice the step you were skipping.
  • Change one thing at a time, and keep notes of what you tried.
  • Suspect your newest code first, and your oldest assumptions second.
  • When the impossible happens, an assumption is wrong. "This pointer can't be null here" is a hypothesis to test, not a fact.
  • After fixing, write a test that would have caught it (chapter 17), so it stays fixed.

Common mistakes

Changing several things at once

If the bug disappears, you do not know which change fixed it, or whether one of them just hid it.

Debugging a different build than the one that fails

If it only fails in Release, debug the Release build (lesson 8.06).

Stopping at the first suspicious code

Confirm it causes the symptom: does the bug go away when it is fixed, and come back when it is restored?
