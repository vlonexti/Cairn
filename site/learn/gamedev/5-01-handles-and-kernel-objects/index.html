Handles and Kernel Objects

lesson 5.011 of 9 in milestone 56 min1 practice task

Files, threads, processes, events and many other resources are kernel objects: they live inside the Windows kernel, and your program refers to them only through handles. This lesson explains what a handle is, the rules for getting and closing one, the two different "invalid" values, and how to wrap handles in an RAII class so they can never leak.

Objects you cannot touch

When a program opens a file, Windows creates a file object inside the kernel: a structure recording which file, the current position, the access rights granted, and more. That structure lives in kernel memory, which user-mode code cannot read (lesson 1.06). So instead of a pointer, the program gets a handle, a small number that identifies the object within this process.

Every process has its own handle table. A handle value means nothing outside its process, just like a virtual address. When you pass the handle back to Windows, for example to ReadFile, the kernel looks it up in your table, checks the rights recorded there, and acts on the object.

Many kinds of object work this way:

Object Created by Used for
File CreateFileW Reading and writing files, pipes, devices
Thread CreateThread Running code in parallel (chapter 6)
Process CreateProcessW, OpenProcess Starting programs, waiting for them (chapter 6)
Event, mutex, semaphore CreateEventW, CreateMutexW, ... Synchronising threads (chapter 6)
File mapping CreateFileMappingW Shared memory between processes (chapter 12)

Windows also has window handles (HWND), GDI handles (HBRUSH, HDC) and module handles (HMODULE). They look similar but are managed by different parts of Windows and closed with different functions. This lesson is about kernel object handles, closed with CloseHandle.

Getting and closing a handle

C++
#include <windows.h>
#include <iostream>

int main()
{
    HANDLE ready{ CreateEventW(nullptr, TRUE, FALSE, nullptr) };   // a manual-reset event, not yet signalled
    if (ready == nullptr)
    {
        std::cout << "CreateEventW failed: " << GetLastError() << '\n';
        return 1;
    }

    SetEvent(ready);                                      // signal it
    const DWORD result{ WaitForSingleObject(ready, 0) };  // is it signalled? (don't wait)
    std::cout << (result == WAIT_OBJECT_0 ? "the event is signalled" : "not signalled") << '\n';

    CloseHandle(ready);                                   // give the handle back
    return 0;
}
Output
the event is signalled

The rules:

  1. Every handle you open, you must close, exactly once, with the matching function. Kernel objects are reference-counted: the object is destroyed when its last handle is closed.
  2. After closing, the value is meaningless. Windows reuses handle values, so a stale handle can end up referring to a different object, just like a dangling pointer (lesson 2.09).
  3. When the process ends, Windows closes everything it left open. That is a safety net, not a plan: a game that leaks a handle per frame runs out within hours.

Task Manager can show leaks: on the Details tab, right-click the column headers → Select columns → Handles. A number that keeps growing while the game runs is a handle leak.

Two kinds of "invalid"

A historical wart: failing functions do not all return the same value.

Function Returns on failure
CreateFileW INVALID_HANDLE_VALUE (which is -1)
CreateEventW, CreateThread, OpenProcess, most others nullptr (0)

The documentation for each function says which. Checking for the wrong one is a classic bug: if (h == nullptr) after CreateFileW never catches a failure.

An RAII wrapper

Lesson 2.04's RAII idea is a perfect fit. A small class owns the handle and closes it in its destructor:

C++
#include <windows.h>
#include <iostream>
#include <utility>

class UniqueHandle
{
public:
    UniqueHandle() = default;
    explicit UniqueHandle(HANDLE h) : m_handle{ h } {}
    ~UniqueHandle() { reset(); }

    UniqueHandle(const UniqueHandle&) = delete;               // one owner only
    UniqueHandle& operator=(const UniqueHandle&) = delete;
    UniqueHandle(UniqueHandle&& other) noexcept : m_handle{ std::exchange(other.m_handle, nullptr) } {}
    UniqueHandle& operator=(UniqueHandle&& other) noexcept
    {
        if (this != &other) { reset(); m_handle = std::exchange(other.m_handle, nullptr); }
        return *this;
    }

    HANDLE get() const { return m_handle; }
    explicit operator bool() const { return m_handle != nullptr && m_handle != INVALID_HANDLE_VALUE; }
    void reset()
    {
        if (*this) CloseHandle(m_handle);
        m_handle = nullptr;
    }

private:
    HANDLE m_handle{ nullptr };
};

int main()
{
    UniqueHandle event{ CreateEventW(nullptr, TRUE, TRUE, nullptr) };
    if (!event) return 1;
    std::cout << (WaitForSingleObject(event.get(), 0) == WAIT_OBJECT_0) << '\n';
    return 0;
}   // closed here, on every path out of main
Output
1

Treating both nullptr and INVALID_HANDLE_VALUE as "no handle" makes the class safe whichever function produced the value. The Windows Implementation Libraries (WIL, available through vcpkg as wil) provide polished versions of this for every handle type: wil::unique_handle, wil::unique_hfile, wil::unique_event.

Common mistakes

[!warning] Checking CreateFileW's result against nullptr It returns INVALID_HANDLE_VALUE on failure. Read each function's documentation.

Closing a handle twice

The second CloseHandle may close an unrelated object that reused the value. Under a debugger, Windows raises an "invalid handle" exception for it.

[!warning] Closing a window, module or GDI handle with CloseHandle They have their own functions: DestroyWindow, FreeLibrary, DeleteObject, ReleaseDC.

Copying a raw handle into two owners

Only one should close it. If two parts of the program genuinely need their own handle, use DuplicateHandle.
