Designing a Plugin Interface

lesson 13.033 of 8 in milestone 135 min1 practice task

A plugin is native code built separately from the game, possibly with a different compiler version, that the game loads at run time. The interface between them must therefore be a stable C interface: plain types, function pointers, explicit versions and sizes. This lesson designs Delve's plugin API in both directions (the host API the game offers plugins, and the plugin API plugins offer the game) using lessons 4.05, 3.04 and 12.06.

Two directions

flowchart LR
    G["Delve (host)"] -->|"HostApi: functions plugins may call<br/>log, spawn, give item, subscribe to events"| P["plugin.dll"]
    P -->|"PluginApi: functions the game calls<br/>init, update, shutdown"| G
  • The host API is what the game lets plugins do. It defines the plugin's powers, so it is designed carefully and kept small.
  • The plugin API is what every plugin must provide, so the game can initialise it, call it each frame, and shut it down.

Rule 1: a C interface, not C++ classes

The game and a plugin may be built with different compilers, settings or standard library versions. Lesson 4.05 explained why std::string, std::vector and C++ classes with virtual functions must not cross that boundary. The interface uses only:

  • integers, floats, and fixed-size plain structs;
  • const char* strings in UTF-8, valid only for the duration of the call (copy them if you need them later);
  • function pointers;
  • opaque handles (typedef struct DelveEntity* DelveEntityHandle;, or plain integer ids, lesson 3.10).

Rule 2: tables of function pointers, with a version and a size

Both directions are structs of function pointers, the hand-made vtables of lesson 3.05's practice task, each starting with lesson 12.06's version and size:

C++
// delve_plugin.h: the only header plugins include. C-compatible.
#pragma once
#include <stdint.h>

#define DELVE_API_VERSION_MAJOR 1
#define DELVE_API_VERSION_MINOR 0

typedef struct DelveHostApi
{
    uint32_t size;                 // sizeof(DelveHostApi) as the game was built: fields past it do not exist
    uint16_t versionMajor, versionMinor;

    void (*log)(const char* message);
    int  (*spawnMonster)(const char* kind, int x, int y);               // returns an entity id, or -1
    int  (*giveItem)(const char* itemId, int count);                    // returns how many did not fit
    int  (*playerHealth)(void);
    void (*subscribe)(const char* eventName, void (*handler)(const char* eventName, int64_t value, void* user), void* user);
    // version 1.1 and later add fields here, at the end only
} DelveHostApi;

typedef struct DelvePluginApi
{
    uint32_t size;
    uint16_t versionMajor, versionMinor;
    const char* name;

    int  (*init)(const DelveHostApi* host);      // return 0 for success
    void (*update)(double dt);                   // may be null if the plugin needs no per-frame work
    void (*shutdown)(void);
} DelvePluginApi;

// The one function every plugin DLL exports:
//   extern "C" __declspec(dllexport) int delvePluginEntry(DelvePluginApi* out);
// The game passes a zeroed struct whose size it sets; the plugin fills it in.

Why this shape:

  • One exported function (delvePluginEntry) instead of many keeps GetProcAddress lookups to one and the export table simple (lesson 4.05).
  • Function pointers in a struct let the game add functions later (at the end, lesson 12.06) without breaking old plugins.
  • size and the version let each side check what the other supports: a plugin built for API 1.0 runs on a 1.3 game; a plugin needing 1.3 refuses politely on a 1.0 game.
  • void* user in callbacks lets a plugin get back its own state when the game calls it, since C function pointers carry no data (lesson 3.04).

Rule 3: ownership is explicit

Every pointer crossing the boundary has a documented owner and lifetime:

  • Strings passed into a plugin call are valid only during the call.
  • The host API table stays valid until shutdown returns.
  • Memory a plugin allocates, the plugin frees; memory the game allocates, the game frees (lesson 4.05: different heaps).

Write these rules in comments in the header: it is the plugin authors' only documentation.

Rule 4: the host API decides what plugins can do

Every function in DelveHostApi is a capability given to code you did not write. Expose gameplay-level operations (spawn, give, read health, subscribe to events), validated like console commands (lesson 11.07), not raw pointers into the game's internals. A plugin that can only call spawnMonster("goblin", x, y) cannot corrupt the entity storage; one handed a pointer to it can. Native code can still do anything in principle (it runs in your process), but a good API means well-behaved plugins never need to.

Common mistakes

C++ types in the interface

std::string, std::vector, exceptions and classes do not cross a DLL boundary safely. Use C types.

No version or size

The first change to the API breaks every existing plugin silently.

Exposing internal pointers

Give plugins operations, not access to your data structures.

Throwing exceptions across the boundary

C++ exceptions must not escape a plugin into the game (or the reverse). Catch them at the boundary and return error codes.
