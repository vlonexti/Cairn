Polish and Packaging

lesson 11.088 of 8 in milestone 115 min

The difference between a working prototype and a game people enjoy is polish: feedback for every action, a little motion, sound, and no rough edges. The difference between a game on your machine and one on a friend's is packaging: a Release build with everything it needs, version information, and a test on a clean system. This lesson finishes Delve.

Feedback for every action

Players should never wonder whether something happened. Each action gets a visible, and ideally audible, response:

Event Feedback
Hitting a monster A brief flash on the monster, a number floating up, a short sound
Being hit A red flash at the screen's edges, a small screen shake
Missing "miss" floating up, a different sound
Picking up an item The item slides to the inventory bar; the slot pulses
Low health The health bar pulses; a heartbeat sound
Bumping a wall A tiny nudge of the player sprite towards the wall and back

All of these are presentation only: they live in the renderer and never change game state (lesson 10.01), so they cannot introduce gameplay bugs.

Screen shake, for example, is a random offset added to the camera that decays over a fraction of a second:

C++
// Called when the player is hit: strength in pixels.
void addShake(float strength) { m_shake = std::min(m_shake + strength, 12.0f); }

// Each frame, in the renderer:
const float ox{ m_shake * rng.unit() * 2 - m_shake };
const float oy{ m_shake * rng.unit() * 2 - m_shake };
drawWorld(cameraX + ox, cameraY + oy);
m_shake = std::max(0.0f, m_shake - 40.0f * frameTime);   // fades in about a quarter of a second

Use a separate random generator for presentation, so effects do not consume numbers from the gameplay generator and change the game's outcomes (lesson 11.05).

Sound

SDL_mixer (vcpkg add port sdl2-mixer) plays sound effects and music in a few lines. Keep sounds short and quiet by default, give every sound a slight random pitch or choose between two or three variants so repetition does not grate, and give players volume settings for effects and music separately.

Settings and accessibility

A settings screen (saved like lesson 10.07's files, in AppData) should cover at least: key bindings (lesson 10.05), volume, window or full screen, screen shake on/off, and text size. Turning off screen shake and flashes matters to players sensitive to motion, and costs one boolean.

The Release build

Lesson 4.10's checklist, applied:

  1. Build Release x64 with /Zi and linker /DEBUG, and archive the PDB with the version number (lesson 8.02): crash dumps from players are useless without it.
  2. Define DELVE_SHIPPING to remove debug commands (lesson 11.07).
  3. Install the crash handler that writes a minidump and the recent log (lesson 8.04).
  4. Add version information: a VERSIONINFO resource (Add → Resource → Version) with the product name and version, shown in the file's Properties dialog and recorded in crash dumps.
  5. Turn on all the security options that are on by default (ASLR, DEP, /GS, control-flow guard) and leave them on.

Packaging

A Delve release is a folder:

Output
Delve-1.0.0\
    Delve.exe
    SDL2.dll              from vcpkg_installed\x64-windows\bin
    SDL2_mixer.dll
    data\
        levels\*.txt
        items.ini  monsters.ini
        sounds\*.wav
    README.txt            how to play, controls, where saves are kept
    LICENSES.txt          SDL's licence (zlib) and any others you used

Zip it, or build an installer (Inno Setup and WiX are free; MSIX for the Microsoft Store). Two details people forget:

  • Third-party licences. SDL's zlib licence is permissive, but you must keep its notice; check every library you ship.
  • The Visual C++ runtime. If you build with /MD (the default), players need the Visual C++ Redistributable. Either ship its installer, or build with /MT so the runtime is inside your exe (lesson 4.04).

Test on a clean machine

The game works on your PC because everything it needs is already installed there. Test the zip on a clean Windows installation, ideally a virtual machine (lesson 15.08 sets one up) restored to a fresh snapshot each time: missing DLLs, a missing runtime, paths that assume your folders, and writing next to the exe (lesson 5.04) all show up immediately.

Common mistakes

Not keeping the PDB of the build you released

Every crash report from that version becomes unreadable.

Testing only on the development machine

Use a clean virtual machine.

Polish that changes the game

Effects belong in the renderer, with their own random numbers.
