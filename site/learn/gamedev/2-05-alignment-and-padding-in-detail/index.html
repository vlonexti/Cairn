Alignment and Padding in Detail

lesson 2.055 of 11 in milestone 27 min1 practice task

Every type has an alignment: the addresses it may start at must be a multiple of it. To keep each member of a struct aligned, the compiler inserts unused padding bytes. This lesson gives the exact rules, shows how to predict a struct's size and members' offsets, and how to arrange members so less memory is wasted.

Why alignment exists

Memory is a row of bytes, but the processor does not read it one byte at a time. It fetches aligned chunks: 8, 16 or 64 bytes at once. A 4-byte int that starts at an address divisible by 4 always falls inside one chunk. One that starts at address 6 might straddle two chunks and need two fetches, and some instructions refuse misaligned data altogether.

So compilers follow a simple rule: a value of a type with alignment N is placed at an address that is a multiple of N. On x64 Windows, a basic type's alignment is the same as its size:

Type Size Alignment
char, bool, std::uint8_t 1 1
short, std::int16_t 2 2
int, float, std::int32_t 4 4
long long, double, any pointer 8 8

alignof(T) gives a type's alignment, just as sizeof(T) gives its size.

The three rules for a struct

The compiler lays out a struct's members in the order they are declared and follows three rules:

  1. Each member starts at the next offset that is a multiple of its own alignment. Any skipped bytes are padding.
  2. The struct's own alignment is the largest alignment of any member.
  3. The struct's size is rounded up to a multiple of its alignment, adding tail padding if needed. This keeps every element of an array of the struct aligned.

Work through one by hand:

C++
struct Pickup
{
    char kind;      // offset 0, size 1
                    // padding: offsets 1..3, so the int can start at a multiple of 4
    int amount;     // offset 4, size 4
    bool active;    // offset 8, size 1
                    // padding: offsets 9..15
    double expires; // offset 16, size 8
};                  // largest alignment is 8; 24 is already a multiple of 8, so sizeof is 24

Reordering to save space

The fix is to declare members from the largest alignment to the smallest. Then each member already lands on a suitable offset and padding only appears at the very end, if at all.

C++
#include <cstddef>
#include <iostream>

struct PickupWasteful
{
    char kind;
    int amount;
    bool active;
    double expires;
};

struct PickupTidy
{
    double expires;   // 0
    int amount;       // 8
    char kind;        // 12
    bool active;      // 13, then 2 bytes of tail padding
};

int main()
{
    std::cout << "wasteful: " << sizeof(PickupWasteful) << " bytes\n";
    std::cout << "tidy:     " << sizeof(PickupTidy) << " bytes\n";
    std::cout << "offsets:  expires " << offsetof(PickupTidy, expires)
              << ", amount " << offsetof(PickupTidy, amount)
              << ", kind " << offsetof(PickupTidy, kind)
              << ", active " << offsetof(PickupTidy, active) << '\n';
    return 0;
}
Output
wasteful: 24 bytes
tidy:     16 bytes
offsets:  expires 0, amount 8, kind 12, active 13

A third smaller for the same information. For one object it does not matter. For a game holding 100,000 pickups, particles or tiles, it is the difference between 2.4 MB and 1.6 MB, and fewer bytes means fewer trips to memory when the game loops over them every frame.

[!tip] offsetof and the Watch window offsetof(Type, member) from <cstddef> gives a member's offset in bytes. In Visual Studio you can also type &obj.member and &obj into the Watch window and subtract.

Controlling alignment

Sometimes you need a different layout on purpose.

More alignment with alignas. Data used with wide maths instructions often has to start on a 16-byte boundary, and data shared between threads is sometimes aligned to 64 bytes so two threads never write the same cache line.

C++
#include <iostream>

struct alignas(16) Vec4
{
    float x, y, z, w;
};

struct alignas(64) PerThreadCounter
{
    long long value;
};

int main()
{
    std::cout << alignof(Vec4) << ' ' << sizeof(Vec4) << '\n';
    std::cout << alignof(PerThreadCounter) << ' ' << sizeof(PerThreadCounter) << '\n';
    return 0;
}
Output
16 16
64 64

Less alignment with #pragma pack. File formats and network packets have exact byte layouts with no padding. #pragma pack(push, 1) tells the compiler to place members one after another with no gaps.

C++
#include <cstdint>
#include <iostream>

#pragma pack(push, 1)
struct SaveHeader
{
    char magic[4];          // "SAVE"
    std::uint16_t version;
    std::uint32_t length;
};
#pragma pack(pop)

int main()
{
    std::cout << sizeof(SaveHeader) << '\n';   // 4 + 2 + 4, no padding
    return 0;
}
Output
10

Use packing only for data that has to match an outside format byte for byte. Accessing misaligned members is slower, and taking a pointer to one is dangerous because code using that pointer assumes it is aligned. Chapter 9 uses packed structs to read the headers of .exe files.

Padding is not zero

Padding bytes are not set to anything in particular. In a Debug build a local struct's padding shows CC; elsewhere it holds leftovers. Two consequences:

  • Comparing structs with memcmp can say two equal structs differ, because their padding differs. Compare member by member, or define operator==.
  • Writing a struct to a file or the network as raw bytes writes the padding too, which may leak leftover memory contents and wastes space. Write members individually, or use a packed struct you fully initialise.

Common mistakes

[!warning] Adding up member sizes to get sizeof The struct also contains padding. Use sizeof, or work through the three rules.

Packing everything to save memory

Reordering members usually saves the same space without misaligned access. Keep #pragma pack for outside formats.

[!warning] Forgetting #pragma pack(pop) Without it, every struct after it in the file, including ones in headers included later, is packed too.
