Linked Lists from Scratch

lesson 3.066 of 10 in milestone 36 min1 practice task

A linked list stores each element in its own node, and each node points to the next. Inserting and removing anywhere is cheap, but finding anything means following pointers one at a time. Building one by hand is the best practice there is for pointers, and it explains why games use them rarely and carefully.

Nodes and links

An array keeps its elements side by side. A linked list scatters them: each element sits in a separately allocated node, together with a pointer to the next node. The list itself only remembers the first node, the head.

C++
struct Node
{
    int value;
    Node* next;       // nullptr in the last node
};
flowchart LR
    H["head"] --> A["value 7<br/>next"]
    A --> B["value 3<br/>next"]
    B --> C["value 9<br/>next = nullptr"]

Walking the list means following next until it is null:

C++
#include <iostream>

struct Node
{
    int value;
    Node* next;
};

int main()
{
    Node c{ 9, nullptr };
    Node b{ 3, &c };
    Node a{ 7, &b };
    Node* head{ &a };

    for (Node* n{ head }; n != nullptr; n = n->next)
        std::cout << n->value << ' ';
    std::cout << '\n';
    return 0;
}
Output
7 3 9

Inserting

Adding at the front takes a constant amount of work, however long the list is: make a node, point it at the old head, make it the new head.

C++
void pushFront(Node*& head, int value)
{
    head = new Node{ value, head };
}

Inserting after a node you already have is just as cheap: two pointer writes, no elements moved. Compare an array, where inserting at the front means shifting every element along by one.

Removing, and the pointer-to-pointer trick

Removing a node means making whatever pointed at it point at its successor instead. The first node is pointed at by head; every other node is pointed at by the previous node's next. Treating those two cases separately is clumsy:

C++
// Clumsy: a special case for the head.
void removeFirstClumsy(Node*& head, int value)
{
    if (head && head->value == value) { Node* dead{ head }; head = head->next; delete dead; return; }
    for (Node* n{ head }; n && n->next; n = n->next)
        if (n->next->value == value) { Node* dead{ n->next }; n->next = dead->next; delete dead; return; }
}

The neat way is to walk with a pointer to the link itself, a Node** (lesson 3.01). It starts at &head and moves to &node->next. Whichever link it holds, removing the node it points at is the same one line:

C++
void removeFirst(Node*& head, int value)
{
    for (Node** link{ &head }; *link != nullptr; link = &(*link)->next)
    {
        if ((*link)->value == value)
        {
            Node* dead{ *link };
            *link = dead->next;      // whoever pointed at dead now skips it
            delete dead;
            return;
        }
    }
}
flowchart LR
    H["head"] --> A["7"]
    A -->|"link points at this next"| B["3 (dead)"]
    B --> C["9"]
    A -.->|"*link = dead->next"| C

This is one of the few places where ** makes code shorter and clearer, and it is a classic interview question. The practice task asks you to write it.

The cost: walking is slow

Operation Array / std::vector Linked list
Get element number i One calculation Follow i pointers
Insert or remove at the front Move every element Two pointer writes
Insert or remove in the middle, given its position Move the elements after it Two pointer writes
Loop over everything Walks memory in order Jumps around the heap: one cache miss per node, likely
Extra memory None One pointer (8 bytes) per element, plus allocator overhead

That last-but-one row usually decides it. Looping over a std::vector<int> of a million elements reads contiguous memory the processor can stream in. Looping over a list of a million nodes follows a million dependent pointers into scattered heap blocks (lesson 3.02's pointer chasing). In practice the vector is often ten times faster or more, even for workloads with many inserts, because shifting contiguous memory is so cheap.

So the standard advice is: default to std::vector. Use a list only when you have measured a reason.

Where lists do appear in games

  • Intrusive lists: the next pointer lives inside an object that already exists for another reason, such as all the enemies in one grid cell of a spatial partition. No extra allocations, and an object can unlink itself in constant time.
  • Free lists in pools (lesson 3.10): unused slots point to the next unused slot, so allocating is "take the head".
  • Engines' own systems, such as lists of timers or render commands, often allocated from an arena so the nodes are close together anyway.

The standard library has std::list (doubly linked) and std::forward_list (singly linked) if you need one.

Common mistakes

Using a node after deleting it

In n = n->next after delete n, the read is from freed memory. Save next first.

Losing the rest of the list

Overwriting head before saving the old head leaks every node. Draw the arrows before writing the code.

Forgetting to free the nodes

A list built with new needs a loop that deletes every node, or nodes owned by std::unique_ptr.

  2. In removeFirst, why does link have type Node**?

    It points at the link (either head or some node's next) that may need to change Changing a pointer requires its address. *link = dead->next updates whichever pointer pointed at the dead node.

  3. Why is a std::vector usually faster to loop over than a linked list with the same elements?

    • Linked lists must be sorted

    Its elements are contiguous, so the processor reads them in order from cache; list nodes are scattered and each step depends on the last Contiguous memory is streamed efficiently; pointer chasing waits on memory at every step.
