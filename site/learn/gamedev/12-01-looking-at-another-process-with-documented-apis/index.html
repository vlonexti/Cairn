Looking at Another Process with Documented APIs

lesson 12.011 of 7 in milestone 126 min

Development tools often need to see inside a running game from a separate program: a stats panel, a level editor that previews live, a profiler. Each process has its own private memory (lesson 6.02), so tools need a deliberate channel. This lesson surveys the documented ways (the game publishing data through shared memory, pipes or sockets; the debugging API for a process you start; dumps) and builds a shared-memory channel, the method the rest of this chapter uses.

The problem

The game and the tool are separate processes. A pointer in one means nothing in the other, and Windows' access checks (lesson 6.08) decide who may look at whom. So how does a tool show the game's frame time, the player's health or the number of live monsters?

There are several documented ways, and they differ in who cooperates:

Method The game cooperates? Good for
Shared memory (file mapping) Yes: the game writes a block of data that the tool maps too Fast, continuous data: stats, graphs, live values
Named pipes or sockets Yes: they exchange messages Commands and events: "spawn a troll", "level loaded"
Log files and ETW events Yes Records over time, profiling (lesson 8.08)
The debugging API on a process the tool starts No code in the game, but the tool must be its debugger Debuggers and crash catchers (lesson 12.03)
Crash dumps No Inspecting state after the fact (lesson 8.04)

The first rows are how professional engines connect their editors and tools: the game publishes what tools may see, through an interface designed for it. That is reliable (no guessing at memory layouts), fast, survives game updates when versioned properly (lesson 12.06), and needs no special rights. This chapter builds that kind of tooling for Delve, plus a small debugger for a program the tool launches itself.

Ground rules

The tools here inspect programs you build yourself, or programs started by your own tool. Reading or changing the memory of other people's software, particularly online games and anything protected by anti-cheat, is outside this course (lesson 9.01's ground rules): it harms other players, breaks the terms you agreed to, and is often illegal.

Shared memory with a file mapping

Windows can map the same block of physical memory into two processes' address spaces. Each sees it at its own virtual address, but writes by one are visible to the other. The block is a file mapping object, created by name:

C++
#include <windows.h>
#include <iostream>

struct Telemetry               // the agreed layout: plain data only, no pointers (lesson 6.09)
{
    unsigned version;
    unsigned frame;
    float frameMs;
    int playerHp;
};

int main()
{
    // The game creates a named, page-file-backed mapping big enough for the struct...
    HANDLE game{ CreateFileMappingW(INVALID_HANDLE_VALUE, nullptr, PAGE_READWRITE, 0, sizeof(Telemetry), L"Local\\XenonDemoTelemetry") };
    auto* written{ static_cast<Telemetry*>(MapViewOfFile(game, FILE_MAP_WRITE, 0, 0, sizeof(Telemetry))) };

    // ...and a tool opens the same name. (Here in one process, to keep the example runnable.)
    HANDLE tool{ OpenFileMappingW(FILE_MAP_READ, FALSE, L"Local\\XenonDemoTelemetry") };
    const auto* read{ static_cast<const Telemetry*>(MapViewOfFile(tool, FILE_MAP_READ, 0, 0, sizeof(Telemetry))) };

    *written = Telemetry{ 1, 1234, 16.4f, 17 };
    std::cout << "two different addresses: " << (static_cast<const void*>(written) != static_cast<const void*>(read)) << '\n';
    std::cout << "the tool sees frame " << read->frame << ", hp " << read->playerHp << '\n';

    UnmapViewOfFile(read); CloseHandle(tool);
    UnmapViewOfFile(written); CloseHandle(game);
    return 0;
}
Output
two different addresses: 1
the tool sees frame 1234, hp 17

Two different virtual addresses, one block of physical memory. Points to note:

  • INVALID_HANDLE_VALUE as the file means "backed by the page file": pure shared memory, no file on disk.
  • The name Local\... is visible to processes in the same login session. Choose names unique to your game.
  • The tool opens the mapping read-only (FILE_MAP_READ): least privilege (lesson 6.08). A stats panel has no business writing into the game.
  • The layout contains only plain values, never pointers: an address in the game is meaningless in the tool.
  • Reading while the game writes can produce a torn snapshot (half old, half new). Lesson 12.04 fixes this with a sequence counter.

Pipes for commands

Shared memory is ideal for "the current state". For messages ("load level 3", "screenshot taken") a named pipe (CreateNamedPipeW in the game, CreateFileW on \\.\pipe\name in the tool) carries a stream of bytes both ways, like a local network connection. Many engines run a small command server this way so editors can control the game; it is the debug console of lesson 11.07, reachable from outside.

Common mistakes

[!warning] Putting pointers or std::string in shared memory Their contents are addresses in one process. Use fixed-size plain data.

Opening the mapping writable in the tool

Read-only is all a viewer needs, and protects the game from tool bugs.

Treating the shared block as always consistent

Without a protocol (lesson 12.04), the tool may read a half-updated state.
