Dynamic Analysis with a Debugger

lesson 9.077 of 10 in milestone 96 min

Static analysis shows every path a program could take; dynamic analysis shows what it actually does, with real values. This lesson uses a debugger on a program without its source (x64dbg as well as the debuggers you know): breaking on API calls, watching arguments and return values, following indirect calls, and tracing the path through code to confirm what static analysis suggested.

Why run it

Some questions are slow to answer from the listing alone:

  • Which of five possible callbacks does this indirect call rax actually reach?
  • What does this decryption routine produce?
  • Which branch is taken with real input?
  • What values does this function receive?

A debugger answers them in seconds. The usual rhythm is: form a hypothesis in the disassembler, confirm it in the debugger, write the conclusion back as a name or comment in the disassembler.

x64dbg

x64dbg is a free, open-source debugger designed for working without source. Its main window shows the disassembly, registers, the stack and a memory dump all at once, much like the Visual Studio windows of lesson 4.08 side by side. Download it from its official site, and use x64dbg.exe (not x32dbg) for 64-bit programs. Visual Studio and WinDbg can do everything below too; x64dbg is simply convenient when there is no source or PDB.

As always in this chapter, practise on the targets from lesson 9.10 or other programs you have the right to analyse.

Breaking on API calls

Imports are the landmarks (lesson 9.03). Breaking on them shows you exactly when the program does something significant, and with what:

Want to know Break on
Which files it opens CreateFileW
What it writes WriteFile
Which DLLs it loads at run time LoadLibraryW, LoadLibraryExW, GetProcAddress
Which registry keys it reads RegOpenKeyExW, RegQueryValueExW
When it allocates large blocks VirtualAlloc

In x64dbg type bp CreateFileW in the command bar; in WinDbg bp kernelbase!CreateFileW. When it stops, the arguments are in rcx, rdx, r8, r9 (lesson 7.06): for CreateFileW, rcx points at the file name, so follow it in the dump as a UTF-16 string. Then run to return (Ctrl+F9 in x64dbg) to see the result in rax, and step out to land in the code that called it: that is the program's own function that opens the file, now found.

Following indirect calls

Virtual calls, callbacks and function tables (lessons 3.04, 3.05) appear as call rax or call qword ptr [rax+18h], which static analysis cannot always resolve. Put a breakpoint on the indirect call, run, and step into it: you are now in the actual target, and can name it in your static notes ("slot 3 of this vtable is Goblin::update").

Tracing a path

When you need to know which way a series of branches went for a given input:

  • Step over the region (F8), watching the jumps: x64dbg shows whether each conditional jump will be taken before you step it.
  • Use conditional breakpoints and logging breakpoints (lesson 4.09) to record values each time a location is hit without stopping.
  • Use trace features (x64dbg's "Trace over" with a condition, or WinDbg's wt) to record every instruction executed until a condition holds, then inspect the record.

Watching memory change

Data breakpoints (hardware breakpoints, lesson 4.09) work the same without source: right-click an address in the dump → Breakpoint → Hardware, on write. Run, and the debugger stops on whatever instruction changes it, telling you which function owns that data. Combined with lesson 9.08's cross-references, this is how unknown data is tied to the code that uses it.

Patching for experiments

Debuggers can change instructions in memory. During analysis this is useful for experiments: force a branch the other way to see what the alternative path does, or skip a call. Changes are made only to the running copy in memory, are gone on restart, and are for understanding your practice targets. (Changing software to bypass licence checks or protections is outside this course's ground rules, lesson 9.01.)

Common mistakes

Breaking on a high-traffic function without a condition

CreateFileW or VirtualAlloc may be called thousands of times at start-up. Add a condition or enable the breakpoint only when you reach the interesting part.

Reading arguments after the function has started

The argument registers are reliable only at the function's first instruction.

Forgetting that the program may behave differently under a debugger

Timing changes, and some programs check for debuggers. If behaviour differs, note it as a finding.
