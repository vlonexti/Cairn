Address Space Layout Randomisation and Base Addresses

lesson 6.099 of 9 in milestone 66 min1 practice task

Run a program twice and its code, heap and stack land at different addresses. That is ASLR, a security feature. This lesson explains why it exists, how a module that can load anywhere still works (relocations and RIP-relative code), how to turn any address into a stable module + offset (RVA) form, and why raw pointers must never be saved in files.

Different every time

C++
#include <windows.h>
#include <iostream>

int g_global{ 0 };

int main()
{
    int local{ 0 };
    std::cout << "exe loaded at   " << static_cast<void*>(GetModuleHandleW(nullptr)) << '\n';
    std::cout << "a global at     " << &g_global << '\n';
    std::cout << "a local at      " << &local << '\n';
    std::cout << "kernel32 at     " << static_cast<void*>(GetModuleHandleW(L"kernel32.dll")) << '\n';
    return 0;
}
Output (yours will differ)
exe loaded at   00007FF7C3E20000
a global at     00007FF7C3E3A030
a local at      0000009B4C2FF8D4
kernel32 at     00007FFE4C0A0000

Run it again and the first three lines change. (System DLLs like kernel32.dll are randomised once per boot, so they stay the same until you restart.) But look at the first two: the global is always the same distance after the exe's start, here 0x1A030, whatever the start is.

Why randomise

Many attacks on programs depend on knowing where something is in memory: a function to jump to, a structure to overwrite. Address space layout randomisation (ASLR) makes those addresses different on every run and every machine, so an attacker who finds a memory bug still does not know where to aim. It is on by default for everything built with modern Visual Studio (the linker option /DYNAMICBASE, plus /HIGHENTROPYVA for 64-bit programs to use the full range).

How code works at any address

If a module can be loaded anywhere, how does its code find its own globals and functions?

  • RIP-relative addressing. Most x64 instructions that touch globals or call functions use an offset from the current instruction (rip): "the global 0x1A030 bytes ahead of this instruction". Since the code and the data move together, the offset is always right. This is why x64 code mostly needs no fixing up.
  • Relocations. A few values in a module are absolute addresses, such as a table of pointers, or a vtable pointing at functions. The linker records each of them in the module's relocation table (.reloc section). When the loader puts the module somewhere other than its preferred image base, it adds the difference to every one of those values.

The preferred image base for 64-bit executables built by Visual Studio is 0x140000000, and for DLLs 0x180000000. With ASLR, the loader nearly always picks a different address, so these numbers appear only in the file, in tools such as dumpbin /headers, and in disassemblers that show the program as if it were loaded at its preferred base.

RVAs: addresses that do not move

Because everything inside a module keeps its distance from the module's start, the stable way to name a location in a module is its offset from the start: its relative virtual address (RVA).

RVA = address − module base address
address = module base address + RVA

Executable files use RVAs everywhere: the entry point, the start of each section, every import and export is an RVA (chapter 9). Debugging and crash tools use them too: "crashed at game.exe+0x35F10" means the same instruction on every machine, and it can be found in the build's .pdb or in a disassembler by adding it to the image base the tool displays.

Output
crash at              0x00007FF7C3E55F10
game.exe loaded at    0x00007FF7C3E20000
RVA                              0x35F10
in a disassembler showing image base 0x140000000:  0x140035F10

The practice task builds this conversion against a list of modules, as a crash reporter or a debugger does.

Never save raw pointers

ASLR is the clearest reason never to write pointers into save files, network messages or caches. The next run of the game has a different layout, so a saved address means nothing. Save ids, indices or handles (lesson 3.10), and rebuild pointers after loading. The same goes for a "pointer" written down from a debugger session: it is valid only for that one run.

Common mistakes

Hard-coding addresses

Any absolute address learned in one run is wrong in the next. Store module-relative offsets, or better, look things up by name or id.

Turning off ASLR "to make debugging easier"

It weakens every user's security. Learn to read RVAs instead; the debugger and symbols do the arithmetic for you.

Confusing an RVA with a file offset

An RVA is an offset in memory once loaded. Sections can sit at different offsets in the file on disk (chapter 9 shows how to convert).
