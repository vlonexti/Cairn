A First Look at WinDbg

lesson 8.055 of 8 in milestone 86 min

WinDbg is Microsoft's command-line-driven debugger. It does everything Visual Studio's debugger does and much more, opens any crash dump, and is the only debugger for the Windows kernel (chapter 16). This lesson installs it and teaches the two dozen commands that cover nearly all everyday work, mapped to the Visual Studio windows you already know.

Why another debugger

Visual Studio's debugger is the most comfortable way to debug your own code. WinDbg is worth knowing because:

  • it opens crash dumps from anywhere, quickly, with !analyze summarising them;
  • it can debug programs and machines where Visual Studio is not installed;
  • it has powerful commands for heaps, handles, locks and Windows internals;
  • it is the kernel debugger: chapters 15 and 16 depend on it.

Install WinDbg from the Microsoft Store (search "WinDbg"; older guides call the new version "WinDbg Preview"). It has a modern window with source, locals and call stack panes, but its heart is the command window.

Getting started

  • File → Launch executable to start a program under the debugger, Attach to process for a running one, or Open dump file for a .dmp.
  • First, set up symbols (lesson 8.02):
Output
.symfix C:\Symbols          ; use Microsoft's symbol server, caching in C:\Symbols
.sympath+ C:\code\game\x64\Debug   ; add your own PDB folder
.reload                     ; load symbols with the new path

Commands that start with . are debugger meta-commands; those starting with ! are extensions, larger commands supplied by DLLs loaded into the debugger.

Analysing a crash dump

Open a dump from lesson 8.04 and run:

Output
!analyze -v

It reads the exception record, finds the faulting thread and frame, applies heuristics, and prints a summary:

Output
EXCEPTION_CODE: (NTSTATUS) 0xc0000005 - The instruction at 0x7ff6a1235f10 referenced memory at 0x10.
                                        The memory could not be read.
FAULTING_SOURCE_LINE:  C:\code\game\inventory.cpp
FAULTING_SOURCE_LINE_NUMBER:  42
STACK_TEXT:
game!Inventory::totalWeight+0x20
game!Hud::drawWeight+0x45
game!Hud::draw+0x9a
...

Then dig in with k, .frame, dv and dt as in a live session. .ecxr switches the debugger's context to the moment of the exception (the registers when it happened), which matters for dumps where the current context is the crash handler.

Useful extensions

Command Shows
!heap -s Summary of the process heaps
!handle Open handles and their types (spotting handle leaks, lesson 5.01)
!locks Critical sections that are held, and by which thread (deadlocks, lesson 8.07)
!peb The process environment block: command line, environment, loaded modules
!address addr What kind of memory an address is in (lesson 6.04's VirtualQuery, done for you)

Common mistakes

Forgetting symbols

Without .symfix and your PDB path, everything is addresses. Fix symbols before anything else.

[!warning] Reading a dump's stack without .ecxr You may be looking at the crash handler's stack instead of the crash.

[!warning] Typing g by habit in a dump A dump is not running: it cannot continue. Use the inspection commands.
