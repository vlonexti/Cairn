Your First Debugging Session: Watching Memory Change

lesson 1.088 of 8 in milestone 19 min1 practice task

A debugger pauses a running program so you can look inside it. This lesson walks through a first session in Visual Studio: setting a breakpoint, stepping one line at a time, reading variables in the Locals and Watch windows, and opening the Memory window to watch the bytes of a variable change.

Why use a debugger

Printing values with std::cout works, but it shows you only what you thought to print, and only after the program has moved on. A debugger stops the program while it is running and lets you look at everything: every variable, every byte of memory, every register, and the chain of calls that led here.

It is also the tool that ties together everything in this chapter. You will see the stack from lesson 1.05, the bytes from lesson 1.02 and the addresses from lesson 1.03, in a real program, live.

The program to debug

Create a console project (lesson 1.07) and replace the code with this:

C++
#include <iostream>

struct Player
{
    int health;
    int gold;
    float speed;
};

int addGold(Player& player, int amount)
{
    player.gold += amount;
    return player.gold;
}

int main()
{
    Player hero{ 100, 0, 1.5f };
    int total{ 0 };

    for (int round{ 1 }; round <= 3; ++round)
    {
        total = addGold(hero, round * 10);
        hero.health -= 15;
    }

    std::cout << "health " << hero.health << ", gold " << total << '\n';
    return 0;
}
Output
health 55, gold 60

Make sure the configuration box says Debug and the platform x64.

Step 1: a breakpoint

Click in the grey margin to the left of the line Player hero{ 100, 0, 1.5f };. A red dot appears: a breakpoint. It tells the debugger "pause just before this line runs".

Press F5 (Start Debugging). The program starts, reaches the breakpoint and stops. A yellow arrow in the margin marks the line that will run next. It has not run yet.

Step 2: the Locals window

At the bottom of the screen, find the Locals window (if it is not there: Debug → Windows → Locals). It lists every local variable of the current function.

Right now hero and total have not been initialised, so they hold whatever was in that stack memory. In a Debug build that is the 0xCC filler from the last lesson: total probably shows -858993460.

Key Command What it does
F10 Step Over Run the current line, including any function it calls, and stop at the next line
F11 Step Into If the line calls a function, go into it and stop at its first line
Shift+F11 Step Out Run until the current function returns, then stop in the caller
F5 Continue Run until the next breakpoint, or the end

Press F10 once. hero now shows {health=100 gold=0 speed=1.50000000}. Values that just changed are shown in red. Expand hero with the little triangle to see each member.

Step 3: stepping into a function

Press F10 until the yellow arrow reaches total = addGold(hero, round * 10);, then press F11 to step into addGold.

Look at two windows now:

  • Locals shows player and amount, the locals of addGold. The locals of main are gone from view because this is a different frame.
  • Call Stack (Debug → Windows → Call Stack) lists the frames on the stack, newest at the top: addGold, then main, then the runtime code that called main. This is the stack from lesson 1.05, for real. Double-click the main line and the Locals window switches to main's variables, then double-click addGold to go back.

Press Shift+F11 to step out. You are back in main, and total holds the returned value.

Step 4: the Watch window

The Watch window shows any expression you type, kept up to date as you step. Open Debug → Windows → Watch → Watch 1 and add these lines:

Output
hero.gold
&hero
&hero.gold
sizeof(Player)
hero.health * 2

&hero shows the address of hero on the stack, and &hero.gold shows an address 4 higher, because gold comes straight after the 4-byte health. sizeof(Player) is 12: three 4-byte members.

Step 5: the Memory window

Now the most important window for this course. Open Debug → Windows → Memory → Memory 1. In its Address box, type &hero and press Enter.

You see raw bytes, in hexadecimal, sixteen per row by default. The first twelve are hero:

Output
0x000000A1B2CFF7A8  46 00 00 00  1e 00 00 00  00 00 c0 3f  cc cc cc cc
                    \_ health _/ \_ gold  _/ \_ speed _/

(The address and the values will depend on where you paused.)

Read them with lesson 1.02's rules:

  • 46 00 00 00 is little-endian for 0x00000046, which is 70.
  • 1e 00 00 00 is 0x1E, which is 30. This is the second time round the loop: 10 + 20 gold so far, and 100 − 15 − 15 health.
  • 00 00 c0 3f is the float 1.5. Floating-point numbers have their own bit layout, which chapter 2 explains.
  • cc cc cc cc after it is Debug-build filler: memory nobody has written.

Now press F10 to step through the loop. Each time a value changes, its bytes turn red in the Memory window. Watch gold go up by 10, 20, 30 and health go down by 15, byte by byte.

Changing values while paused

Double-click a value in the Locals or Watch window to type a new one, or type over the hex digits in the Memory window. The program carries on with the changed value. Try setting hero.health to 1000 and pressing F5 to see the final line change.

What you just did

In one session you used the four ideas this chapter introduced:

Idea Where you saw it
Programs run one instruction at a time (1.01) Stepping line by line, with the yellow arrow showing what runs next
Values are bytes, often written in hex (1.02) The Memory window, little-endian ints
Variables live at addresses (1.03) &hero and &hero.gold in the Watch window
Calls make stack frames (1.05) The Call Stack window, and Locals switching between frames

Chapter 4 returns to the debugger for conditional breakpoints, data breakpoints (stop when a particular address changes) and the Registers and Disassembly windows.

Common mistakes

Debugging a Release build

Variables appear as "optimised away" and the yellow arrow jumps around. Switch to Debug for this kind of session.

Thinking the highlighted line has already run

The yellow arrow marks the next line. Values change after you step over it.

Reading a multi-byte value front to back

14 00 00 00 is 20, not a huge number. Little-endian puts the lowest byte first.

Pressing F5 instead of F10

F5 runs on to the next breakpoint, or to the end. If the program finishes in a flash, you probably meant to step.

Knowledge check

quizIn Xenon your best score is kept.
  1. The yellow arrow is on the line total = addGold(hero, 10);. Which key runs that line and stops on the next line of main?
    • F10 (Step Over)
    • F11 (Step Into)
    • Shift+F11 (Step Out)
    Show the answer

    F10 (Step Over) Step Over runs the whole line, including the call, and stops at the next line of the same function.

  2. While paused inside addGold, what does the Call Stack window show at the top?
    • addGold, with main below it
    • main, with addGold below it
    • Only addGold
    Show the answer

    addGold, with main below it The newest frame is listed first. main is waiting underneath for addGold to return.

  3. The Memory window shows 1e 00 00 00 where an int lives. What is its value?
    • 30,000,000
    • 30
    • 1,966,080
    Show the answer

    30 Little-endian: the lowest byte comes first, so the value is 0x0000001E, which is 30.

  4. Why is &hero.gold exactly 4 more than &hero?
    • Addresses always go up in fours
    • gold is stored straight after health, which takes 4 bytes
    • The debugger adds 4 to every member's address
    Show the answer

    gold is stored straight after health, which takes 4 bytes A struct's members are laid out in order. Chapter 2 shows when the compiler adds gaps between them.
