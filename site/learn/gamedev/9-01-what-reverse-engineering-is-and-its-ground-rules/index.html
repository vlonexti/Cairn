What Reverse Engineering Is, and Its Ground Rules

lesson 9.011 of 10 in milestone 96 min

Reverse engineering means working out how a program works from the program itself, without its source. It is how security researchers find vulnerabilities, how malware is analysed, how old software is kept running and how file formats are documented for interoperability. This lesson sets out what it involves, the tools, and the legal and ethical ground rules this course follows.

Running the pipeline backwards

Lesson 1.04's pipeline turned source into machine code. Reverse engineering goes the other way, recovering understanding, never the original source, from the compiled program:

The earlier chapters were the preparation: the PE format of chapter 6's modules, the assembly of chapter 7, the debuggers of chapters 4 and 8, and the layouts of chapters 2 and 3.

Who does it, and why

Field What they reverse engineer
Security research Software, to find and responsibly report vulnerabilities before attackers do
Malware analysis Malicious programs, to understand them, detect them and remove them
Interoperability File formats and protocols, so that other programs can read and write them (many open-source tools exist because of this)
Preservation and compatibility Old software and games whose source is lost, to keep them running on new systems
Debugging and support Third-party libraries and drivers without source, when they misbehave inside your program
Learning How compilers, operating systems and well-written programs work

Static and dynamic analysis

  • Static analysis examines the program without running it: reading the file's headers and the disassembly, following cross-references (lessons 9.02 to 9.06, 9.08). Tools: Ghidra, IDA, Binary Ninja, dumpbin.
  • Dynamic analysis runs it and watches: breakpoints, memory, calls into the operating system (lesson 9.07). Tools: x64dbg, WinDbg, Visual Studio, Process Monitor.

Each answers what the other cannot. Static analysis sees every path, including ones that rarely run; dynamic analysis sees real values and resolves indirect calls. Real work alternates between them.

The ground rules for this course

Reverse engineering is a legitimate, widely practised skill. Like any capability, how it is used matters, and the law varies by country. The rules this course follows:

  1. Practise on programs you have the right to analyse: programs you compiled yourself (lesson 9.10 builds a series of practice targets), open-source programs (where you can check your conclusions against the source), and challenges published specifically as practice ("crackmes" and capture-the-flag tasks).
  2. Read the licence. Many licences restrict reverse engineering. Some laws allow limited reverse engineering for specific purposes such as interoperability (for example, Article 6 of the EU Software Directive) or good-faith security research, with conditions. When it matters, ask someone qualified rather than assuming.
  3. Do not use it to cheat other people. Altering online games to gain an advantage over other players, or bypassing anti-cheat systems, harms those players, breaks the terms you agreed to and can break the law. This course does not teach that, and it does not teach defeating copy protection or licence checks.
  4. Report vulnerabilities responsibly. If you find a security flaw, tell the vendor privately, through their security contact or bug bounty programme, and give them time to fix it before discussing it publicly.
  5. Handle malware with care. Real malicious samples belong in an isolated virtual machine with no access to your files or network, which lesson 15.08 sets up. The practice targets in this course are harmless programs you build yourself.

What you can expect to recover

Survives compilation Lost
The machine code and its control flow Comments, formatting, local variable names
String literals and constants Most type information (structs become offsets, lesson 7.08)
Imported and exported function names Templates and inline functions as separate entities
Class names (through RTTI, lesson 9.06), if not disabled Macros, constexpr values folded into code
Everything, if a PDB is available The original structure of the source files

Recovering a program's logic is slow, careful work, done function by function. Recovering its exact source is impossible. Good reverse engineers are patient, take notes, and name things as they understand them.

Common mistakes

Starting with a large, unfamiliar program

Practise on small programs you wrote, where you can check every conclusion against the source.

Trusting the decompiler blindly

Decompiler output is a guess at C code. Check important conclusions against the assembly.

Assuming that being able to do it means being allowed to

Check the licence and the law, and stay within the ground rules.
