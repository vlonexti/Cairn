Catching Memory Bugs with AddressSanitizer

lesson 2.1010 of 11 in milestone 27 min

AddressSanitizer (ASan) is a compiler feature that adds a check to every memory access. It stops the program at the exact moment of a buffer overrun or use after free, and prints where the memory was allocated, where it was freed and where it was misused. Visual Studio supports it with one switch. This lesson shows how it works and how to read its reports.

The idea

The previous lesson's bugs are hard because nothing happens at the moment of the mistake. A Debug build's patterns help after the fact; AddressSanitizer catches the mistake as it happens.

When you compile with ASan, the compiler adds a small check before every load and store. The check asks: "is the address about to be touched part of a live object?" If not, the program stops immediately with a report.

To answer that question quickly, ASan keeps shadow memory: for every 8 bytes of the program's memory, one byte of shadow says how many of those 8 are valid to use. Around every heap block, stack array and global it places red zones, bytes marked as forbidden. Freed heap blocks are marked forbidden too, and held back for a while before being reused, so a late use of one is still caught.

heap block of 10 bytes, as ASan sees it
 ┌────────┬──────────┬──┬──────────────────┐
 │ red    │ 10 bytes │  │ red zone         │
 │ zone   │ usable   │6 │ (forbidden)      │
 └────────┴──────────┴──┴──────────────────┘
                       ▲
          bytes 10..15: forbidden, though in the same 8-byte group

The checks make a program about twice as slow and use more memory. That is fine for testing, and ASan builds are not meant for shipping.

Turning it on in Visual Studio

  1. Install the C++ AddressSanitizer component (lesson 1.07 ticked it).
  2. Project Properties → C/C++ → General → Enable Address Sanitizer: Yes (/fsanitize=address).
  3. In the same properties, under C/C++ → General, set Debug Information Format to Program Database (/Zi) if it is not already, and turn Edit and Continue off; ASan is not compatible with it.
  4. Build and run under the debugger (F5).

When ASan finds an error, the debugger stops on the bad line and the Output window shows the report.

Reading a report: heap buffer overflow

C++
#include <iostream>

int main()
{
    int* scores{ new int[4]{ 10, 20, 30, 40 } };
    int total{ 0 };
    for (int i{ 0 }; i <= 4; ++i)        // <= is one too many
        total += scores[i];
    std::cout << total << '\n';
    delete[] scores;
    return 0;
}

Without ASan this usually prints a wrong total and carries on. With ASan it stops on the fifth read:

Output
==14260==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x11b5c0420040
READ of size 4 at 0x11b5c0420040 thread T0
    #0 0x7ff6d4e81103 in main C:\code\scores\main.cpp:8
    #1 0x7ff6d4e8b4e8 in invoke_main exe_common.inl:78
    ...

0x11b5c0420040 is located 0 bytes to the right of 16-byte region [0x11b5c0420030,0x11b5c0420040)
allocated by thread T0 here:
    #0 0x7ffe4c0d8d5b in operator new[] ...
    #1 0x7ff6d4e81069 in main C:\code\scores\main.cpp:5

Read it from the top:

Line What it tells you
heap-buffer-overflow The kind of bug: past the end of a heap block
READ of size 4 An int was read (a write would say WRITE)
#0 ... main.cpp:8 The exact line that did it: total += scores[i];
0 bytes to the right of 16-byte region It touched the byte just after a 16-byte block, which is 4 ints
allocated by ... main.cpp:5 Where that block came from: the new int[4]

That is the whole investigation done for you: what went wrong, where, and with which block.

Reading a report: use after free

C++
#include <iostream>
#include <vector>

int main()
{
    std::vector<int> health{ 100, 80 };
    int& first{ health[0] };
    health.push_back(60);       // reallocates: first now refers to freed memory
    first -= 10;
    std::cout << health[0] << '\n';
    return 0;
}

ASan reports heap-use-after-free, with three stacks: where the bad access happened (first -= 10), where the memory was freed (inside push_back, called from your line), and where it was originally allocated (the vector's constructor). That third-party "freed inside push_back" line is exactly the clue that points at iterator and reference invalidation from lesson 2.04.

What ASan catches, and what it does not

Catches Does not catch
Heap buffer overflow and underflow Reading uninitialised memory
Stack buffer overflow Leaks, on Windows (use the CRT leak report)
Global buffer overflow Overruns that stay inside the same object, such as from one struct member into the next
Use after free Logic errors
Use after return or scope (with extra options) Data races between threads
Double free, mismatched new[]/delete

The "same object" row deserves attention: the Player::name overrun in lesson 2.09 writes into gold, which is part of the same struct. Both are inside one live object, so ASan sees nothing wrong. Prevention there is still std::string and bounds checks.

Using it well

  • Run your tests and a play session under ASan regularly, not only when something breaks. Bugs that have not caused a crash yet are the cheapest to fix.
  • Fix the first report first. One overrun can cause later, confusing reports.
  • Keep a separate configuration. In Configuration Manager, copy Debug to a new configuration called ASan with the option on, so normal debugging stays fast.
  • Third-party code may need to be rebuilt with ASan, or its errors may show up inside your program's reports.

Common mistakes

Shipping an ASan build

It is slower and depends on the ASan runtime DLL. ASan is for testing only.

Mixing ASan and Edit and Continue

Visual Studio refuses to build with both. Switch Edit and Continue off for the ASan configuration.

Assuming no report means no memory bugs

ASan only checks code paths that actually ran, and it misses overruns within one object. It finds a lot; it does not prove correctness.

  1. When does AddressSanitizer report a buffer overrun?
    • At the moment the bad read or write happens
    • When the program exits
    • When the corrupted value is next used
    Show the answer

    At the moment the bad read or write happens Every access is checked as it happens, which is what makes ASan so much more useful than finding the damage later.

  2. A report says "0 bytes to the right of 16-byte region". What happened?
    • The code touched the first byte after the end of a 16-byte block
    • The code read a 16-byte value
    • 16 bytes leaked
    Show the answer

    The code touched the first byte after the end of a 16-byte block "To the right" means past the end; "0 bytes" means immediately after it.

  3. Which of these does ASan not catch?
    • Use after free
    • Heap buffer overflow
    • An overrun from one struct member into the next member of the same struct
    Show the answer

    An overrun from one struct member into the next member of the same struct Both members belong to one live object, so the access is to valid memory as far as ASan can tell.

  4. What is shadow memory?
    • A copy of the program kept for debugging
    • Extra memory where ASan records which bytes of the program's memory are valid to use
    • Memory used by the GPU
    Show the answer

    Extra memory where ASan records which bytes of the program's memory are valid to use One shadow byte describes eight bytes of real memory.
