Dynamic Libraries: Building and Loading Your Own DLL

lesson 4.055 of 10 in milestone 47 min

A DLL is a library that stays a separate file and is joined to a program when it runs. This lesson builds a DLL, exports functions from it, uses it in the two ways Windows offers (load-time linking through an import library, and run-time loading with LoadLibrary and GetProcAddress), and covers the rules about DllMain, memory and C++ types across the boundary.

What a DLL is

A dynamic-link library is built much like an .exe: compiled and linked into a PE file (chapter 9) with code, data and imports. The difference is that it has no main; instead it exports functions and variables for programs to use. kernel32.dll, user32.dll and the C++ runtime are all DLLs, and every Windows program uses dozens of them.

The Windows loader maps a DLL into the process's address space and fills in the addresses of its exports wherever the program needs them. One DLL file on disk can be loaded into many processes at once.

Building one

Add a project to the course solution: Dynamic-Link Library (DLL), named plugin. Replace its code with:

C++
// plugin/plugin.h: shared with the programs that use the DLL
#pragma once

#ifdef PLUGIN_EXPORTS
#define PLUGIN_API extern "C" __declspec(dllexport)
#else
#define PLUGIN_API extern "C" __declspec(dllimport)
#endif

PLUGIN_API int pluginVersion();
PLUGIN_API int scaleDamage(int damage, int level);
C++
// plugin/plugin.cpp
#include "plugin.h"

int pluginVersion() { return 3; }

int scaleDamage(int damage, int level)
{
    return damage + damage * level / 10;
}

In the plugin project's properties, add PLUGIN_EXPORTS to C/C++ → Preprocessor → Preprocessor Definitions (the DLL template usually adds a similar name already). The same header then means "export" inside the DLL and "import" everywhere else.

  • __declspec(dllexport) puts the function in the DLL's export table.
  • extern "C" gives it a plain, unmangled name (lesson 4.02), so it can be found as scaleDamage rather than ?scaleDamage@@YAHHH@Z.

Building produces two files: plugin.dll, the code, and plugin.lib, a small import library that only says "these symbols live in plugin.dll".

Terminal
dumpbin /exports plugin.dll
Output
    ordinal hint RVA      name
          1    0 00011023 pluginVersion
          2    1 00011028 scaleDamage

Using it, way 1: load-time linking

Add a project reference from game to plugin (or link plugin.lib), include plugin.h, and call the functions normally:

C++
#include <iostream>
#include "plugin.h"

int main()
{
    std::cout << "plugin version " << pluginVersion() << '\n';
    std::cout << "level 5 damage: " << scaleDamage(40, 5) << '\n';
    return 0;
}

The linker uses the import library to record, in game.exe's import table, that it needs scaleDamage from plugin.dll. When the game starts, the loader finds plugin.dll (in the .exe's folder first, then the system folders and PATH), maps it, and fills in the addresses. If the DLL is missing, the game does not start at all: Windows shows "The code execution cannot proceed because plugin.dll was not found."

Using it, way 2: run-time loading

The program can instead load the DLL itself, when and if it chooses, and look functions up by name. No import library and no reference are needed, which is exactly what a plugin system wants: the game does not know at build time which plugins exist.

C++
#include <windows.h>
#include <iostream>

using ScaleDamageFn = int (*)(int, int);

int main()
{
    HMODULE module{ LoadLibraryW(L"plugin.dll") };
    if (!module)
    {
        std::cout << "no plugin found, error " << GetLastError() << '\n';
        return 1;
    }

    auto scale{ reinterpret_cast<ScaleDamageFn>(GetProcAddress(module, "scaleDamage")) };
    if (scale)
        std::cout << "level 5 damage: " << scale(40, 5) << '\n';

    FreeLibrary(module);
    return 0;
}
  • LoadLibraryW maps the DLL and returns an HMODULE, which is the address the DLL was loaded at.
  • GetProcAddress looks a name up in its export table and returns the function's address, or null.
  • The result is cast to the right function pointer type (lesson 3.04). The cast is a promise you make: if the signature is wrong, the call corrupts the stack or registers.
  • FreeLibrary unloads it. Any pointer into the DLL is invalid after that.

DllMain: keep it tiny

A DLL may define DllMain, which Windows calls when the DLL is loaded into a process, unloaded, and when threads start and stop:

C++
#include <windows.h>

BOOL APIENTRY DllMain(HMODULE module, DWORD reason, LPVOID)
{
    if (reason == DLL_PROCESS_ATTACH) DisableThreadLibraryCalls(module);
    return TRUE;
}

DllMain runs while Windows holds the loader lock, a lock that serialises all DLL loading in the process. Doing almost anything interesting there (loading another DLL, waiting for a thread, calling into COM, even some C++ static initialisation that does those things) can deadlock the process. The rule: in DllMain, do nothing that could wait or load. Put real initialisation in an exported init function that the program calls after loading.

Rules for the boundary

A DLL and the program that loads it are built separately, possibly by different compilers or settings. So the interface between them should be simple:

  • Plain C types across the boundary: integers, floats, pointers to plain structs, function pointers. Passing std::string or std::vector across works only if both sides were built with the same compiler version and settings, and is a common source of crashes.
  • Free memory on the side that allocated it. If the DLL allocates with its own runtime, it should provide a function to free it too. Mixing heaps between modules is a classic crash.
  • Version your interface. An exported pluginVersion (like the one above) lets the program refuse a plugin built for an incompatible interface.

Common mistakes

[!warning] The DLL is not next to the .exe Set every project's output directory to the same folder (lesson 4.01), or the loader cannot find it.

[!warning] Forgetting extern "C" GetProcAddress(module, "scaleDamage") returns null because the exported name is mangled.

[!warning] Calling functions after FreeLibrary The code is gone from memory; the call jumps into nothing and crashes.

[!warning] Real work inside DllMain Deadlocks under the loader lock are hard to diagnose. Export an init function instead.
