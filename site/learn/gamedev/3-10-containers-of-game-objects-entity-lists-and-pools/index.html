Containers of Game Objects: Entity Lists and Pools

lesson 3.1010 of 10 in milestone 36 min1 practice task

A game creates and destroys objects constantly: bullets, particles, enemies, pickups. This lesson puts the chapter together into the structures engines use for them: dense arrays with swap-and-pop, object pools with free lists, and generational handles that let code refer to an object safely even after it has been destroyed and its slot reused.

What games need

A shooter might fire 50 bullets a second, each living for a second or two. A particle effect might spawn thousands of sparks. The container holding them must:

  1. Loop fast, every frame, over everything alive.
  2. Add and remove cheaply, many times per frame.
  3. Let other code refer to an object (the missile's target, the player's selected unit) without that reference turning into a dangling pointer when the object dies.

No single standard container does all three. These are the patterns engines combine.

Pattern 1: a dense vector with swap-and-pop

Keep live objects side by side in a std::vector, and remove with swap-and-pop (lesson 3.07):

C++
#include <iostream>
#include <vector>

struct Bullet { float x; float speed; float life; };

void update(std::vector<Bullet>& bullets, float dt)
{
    for (std::size_t i{ 0 }; i < bullets.size(); )
    {
        Bullet& b{ bullets[i] };
        b.x += b.speed * dt;
        b.life -= dt;
        if (b.life <= 0)
        {
            bullets[i] = bullets.back();    // swap-and-pop: the last bullet takes this slot
            bullets.pop_back();             // don't advance i: the moved bullet needs updating too
        }
        else ++i;
    }
}

int main()
{
    std::vector<Bullet> bullets{ { 0, 10, 0.05f }, { 0, 20, 1 }, { 0, 30, 0.05f }, { 0, 40, 1 } };
    update(bullets, 0.1f);
    for (const Bullet& b : bullets) std::cout << b.speed << ' ';
    std::cout << '\n';
    return 0;
}
Output
40 20

Fast to loop over, cheap to remove from. But it fails requirement 3: an object's position in the vector changes whenever another object is removed, so neither a pointer nor an index to it stays valid.

Pattern 2: a pool with a free list

A pool allocates a fixed array of slots once and never moves them. Each slot is either in use or free. The free slots form a linked list threaded through the slots themselves (an intrusive list, lesson 3.06), so finding a free slot is "take the head of the free list" and freeing one is "push it back on".

Output
slots:   [0: bullet] [1: free → 3] [2: bullet] [3: free → 4] [4: free → end]
freeHead = 1

No heap allocations after start-up, objects never move, so a slot index stays valid while its object lives. Looping over the live objects means skipping free slots, which is slower than a dense vector when the pool is mostly empty.

The remaining problem: stale references

Suppose a missile stores "my target is slot 7". The target dies and slot 7 is freed. A moment later a new enemy is spawned into slot 7. The missile now chases the wrong enemy, and nothing tells it so. Index 7 is a dangling reference, just as a pointer would have been.

Pattern 3: generational handles

The fix is to give every slot a generation counter, incremented each time the slot is freed. A handle to an object is the pair (slot index, generation at the time). To use a handle, check that the slot's current generation still matches:

flowchart LR
    H1["missile's handle<br/>slot 7, gen 3"] --> S7["slot 7<br/>gen 3: goblin"]
    S7 -->|"goblin dies: gen becomes 4"| S7b["slot 7<br/>gen 4: free"]
    S7b -->|"bat spawned into slot 7"| S7c["slot 7<br/>gen 4: bat"]
    H1 -.->|"lookup: 3 ≠ 4, so the goblin is gone"| X["nullptr"]

The missile's handle says generation 3, the slot now says 4, so the lookup returns null: "your target no longer exists". The new bat in slot 7 gets handles with generation 4, which work normally.

C++
struct Handle
{
    std::uint32_t index;
    std::uint32_t generation;
};

Eight bytes, trivially copyable, safe to store anywhere, safe to save to a file, and impossible to dangle. This is the approach used by most modern engines for entities, resources and anything else whose lifetime other systems cannot predict. The practice task is to build one.

Choosing

Need Use
Many short-lived objects nobody else refers to (particles, bullets) Dense std::vector with swap-and-pop
Objects referred to from elsewhere (enemies, units, items in the world) A pool with generational handles
Both fast loops and stable handles A pool for identity plus a dense array of the data, with an index map between them (a "slot map" or "sparse set": the same idea, one step further)
Few objects, created rarely Whatever is simplest: std::vector<std::unique_ptr<T>> is fine

Chapter 10 uses these in its entity-component system.

Common mistakes

Advancing the index after swap-and-pop

The element moved into slot i has not been processed yet. Only advance when nothing was removed.

Storing raw pointers to pooled objects for later

They stay valid in memory, but may point at a different object after reuse. Store handles.

Letting the generation counter wrap round quickly

With a 32-bit counter it would take billions of reuses of one slot, which is fine. An 8-bit counter wraps after 256 and can, rarely, let a stale handle match again.

Knowledge check

quizIn Xenon your best score is kept.
  1. Why does a dense vector with swap-and-pop not give objects stable references?
    • Removing one object moves another into its slot, so positions change
    • Vectors cannot be indexed
    • Swap-and-pop allocates memory
    Show the answer

    Removing one object moves another into its slot, so positions change The last element is moved to fill the gap, so its index changes.

  2. What does a pool's free list link together?
    • The unused slots, through a "next free" index stored in each free slot
    • The live objects, in creation order
    • Every slot, used or not
    Show the answer

    The unused slots, through a "next free" index stored in each free slot Allocating takes the head of the free list; freeing pushes the slot back on.

  3. A handle says (slot 12, generation 5). The pool's slot 12 has generation 6. What does a lookup return?
    • The object in slot 12
    • Nothing: the object the handle referred to has been destroyed
    • The object, after updating the handle
    Show the answer

    Nothing: the object the handle referred to has been destroyed A different generation means the slot has been freed since the handle was made.
