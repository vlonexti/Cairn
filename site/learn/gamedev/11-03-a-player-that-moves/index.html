A Player That Moves

lesson 11.033 of 8 in milestone 115 min1 practice task

Delve is turn-based on a grid: each key press moves the player one tile, and the world (monsters, doors) responds. This lesson connects lesson 10.05's input actions to movement, handles walls, doors and stairs, adds key repeat for held keys, and makes moves look smooth by sliding between tiles in the renderer only.

Turns on a grid

Many roguelike games, Delve included, are turn-based: nothing in the world happens until the player acts, then every monster takes its turn. The game loop still runs at 60 frames per second (input, animation and drawing need it), but the game rules advance one turn per player action.

Actions and moves

Using lesson 10.05's input map, the movement actions become a direction:

C++
struct Dir { int dx; int dy; };

std::optional<Dir> movementFrom(const InputMap& in)
{
    if (in.pressed(Action::Up))    return Dir{ 0, -1 };
    if (in.pressed(Action::Down))  return Dir{ 0, 1 };
    if (in.pressed(Action::Left))  return Dir{ -1, 0 };
    if (in.pressed(Action::Right)) return Dir{ 1, 0 };
    return std::nullopt;
}

Bindings put both the arrow keys and WASD on these actions, and a gamepad's d-pad later just adds more bindings.

Moving into a tile

What happens depends on what is in the target tile. Keeping the decision in one function makes the rules easy to read and test:

Target Result Takes a turn?
Floor Move there Yes
Stairs Move there; the level is complete (lesson 11.06) Yes
Closed door The door opens and becomes floor; the player stays Yes
Wall, or outside the map Nothing: a bump No
A monster Attack it instead of moving (lesson 11.05) Yes

A bump not costing a turn matters for feel: walking into a wall by mistake should not let monsters catch up. The practice task implements this table as tryMove.

Holding a key

Pressing an arrow for every step is tiring in long corridors. Holding the key should repeat the move, after a short delay, at a steady rate:

C++
// A held movement key repeats: the first move on press, then after 0.25 s, then every 0.08 s.
if (auto dir{ movementFrom(input) }) { tryMove(*dir); m_repeatTimer = 0.25; m_heldDir = *dir; }
else if (heldDirection(input) == m_heldDir)
{
    m_repeatTimer -= dt;
    if (m_repeatTimer <= 0) { tryMove(m_heldDir); m_repeatTimer += 0.08; }
}

The update runs at a fixed step, so the repeat rate is the same on every machine (lesson 10.02).

Smooth movement, without changing the rules

The player's logical position is a whole tile: the rules (collision, monster AI, saving) only ever see whole tiles. To avoid the character teleporting a tile at a time on screen, the renderer draws it sliding from the previous tile to the current one over a short time:

C++
// In the player's state:  int x, y;  int fromX, fromY;  float slide;   (slide goes 0 → 1 after each move)
const float t{ std::min(player.slide, 1.0f) };
const float drawX{ (player.fromX + (player.x - player.fromX) * t) * kTile };
const float drawY{ (player.fromY + (player.y - player.fromY) * t) * kTile };

This is lesson 10.02's interpolation applied to a turn-based game: the simulation is exact and simple, and only the picture is smooth. The camera follows the drawn position, not the logical one, so it glides too.

Common mistakes

Letting a bump cost a turn

Players feel cheated when walking into a wall lets monsters move. Only real actions take turns.

Mixing drawn and logical positions

Collision and AI must use the whole-tile position; only rendering uses the sliding one.

[!warning] Moving on held without a repeat timer The player rushes across the map at 60 tiles per second.
