Loading Libraries at Run Time

lesson 5.088 of 9 in milestone 56 min

Lesson 4.05 loaded a DLL of your own. This lesson looks at the loader's side: the search order Windows uses to find a DLL, why that order is a security risk and how to restrict it, finding modules that are already loaded, getting a module's file path, using functions that only exist on newer versions of Windows, and delay loading.

Where Windows looks for a DLL

When a program calls LoadLibraryW(L"plugin.dll") with a bare file name, or when its import table lists plugin.dll, the loader searches a sequence of places. For a normal desktop application the standard search order, simplified, is:

  1. DLLs already loaded in the process with that name, and a list of known DLLs (core system DLLs that always come from the system folder).
  2. The folder the application's .exe is in.
  3. The system folder, C:\Windows\System32.
  4. The Windows folder.
  5. The current working directory.
  6. Each folder on the PATH environment variable.

The first match wins. This is why putting your DLLs next to your .exe (lesson 4.01's shared output folder) works.

The risk: loading the wrong DLL

A search order is also an attack surface. If an attacker can put a file with the right name in a folder that is searched before the real one, your program loads their code with your program's rights. This is called DLL search-order hijacking (or "DLL planting"), and it has affected many real applications. The current directory (step 5) and PATH (step 6) are the classic weak points: a double-clicked document can make its own folder the current directory.

Defend your programs:

Defence How
Remove the current directory and other unsafe locations from the search for the whole process Call SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_DEFAULT_DIRS) at the very start of main
Search only the system folder for system DLLs LoadLibraryExW(L"bcrypt.dll", nullptr, LOAD_LIBRARY_SEARCH_SYSTEM32)
Load your own DLLs by full path Build the path from the .exe's folder (below) and pass it to LoadLibraryExW
Do not load DLLs from folders ordinary users can write to Especially for anything that runs with administrator rights

This matters for the plugin system in chapter 13: a game that loads every .dll in a mods folder is, by design, running code from that folder, so the folder's location and permissions are part of the design.

Finding the program's own folder

C++
#include <windows.h>
#include <iostream>
#include <string>

std::wstring exeFolder()
{
    std::wstring path(MAX_PATH, L'\0');
    for (;;)
    {
        const DWORD length{ GetModuleFileNameW(nullptr, path.data(), static_cast<DWORD>(path.size())) };
        if (length == 0) return {};
        if (length < path.size()) { path.resize(length); break; }
        path.resize(path.size() * 2);                    // truncated: try a bigger buffer
    }
    return path.substr(0, path.find_last_of(L"\\/"));
}

int main()
{
    const std::wstring folder{ exeFolder() };
    std::cout << "found the program's folder: " << (folder.empty() ? "no" : "yes") << '\n';
    return 0;
}
Output
found the program's folder: yes

GetModuleFileNameW(nullptr, ...) gives the path of the .exe; passing a DLL's HMODULE instead gives that DLL's path. It does not report how much space it needed; it truncates silently and returns the buffer size, hence the loop.

Modules that are already loaded

GetModuleHandleW(L"kernel32.dll") returns the HMODULE of a DLL that is already loaded, without loading it or changing its reference count. GetModuleHandleW(nullptr) returns the .exe's own module, the same value as wWinMain's HINSTANCE. An HMODULE is simply the address where the module's image starts in memory, which is why chapter 9 can read a loaded module's headers directly from it.

C++
#include <windows.h>
#include <iostream>

int main()
{
    HMODULE kernel{ GetModuleHandleW(L"kernel32.dll") };
    HMODULE self{ GetModuleHandleW(nullptr) };
    std::cout << "kernel32 is loaded: " << (kernel != nullptr) << '\n';
    std::cout << "the exe's first two bytes: " << static_cast<const char*>(static_cast<const void*>(self))[0]
              << static_cast<const char*>(static_cast<const void*>(self))[1] << '\n';
    return 0;
}
Output
kernel32 is loaded: 1
the exe's first two bytes: MZ

Every executable and DLL starts with the letters MZ, the signature of its header. Chapter 9 starts there.

Using newer functions when they exist

A game may want a function that only exists on newer versions of Windows, while still running on older ones. Linking to it normally would stop the game starting at all on an older system (the loader fails on the missing import). Look it up at run time instead:

C++
using SetThreadDescriptionFn = HRESULT (WINAPI*)(HANDLE, PCWSTR);

void nameThisThread(const wchar_t* name)
{
    auto fn{ reinterpret_cast<SetThreadDescriptionFn>(
        GetProcAddress(GetModuleHandleW(L"kernel32.dll"), "SetThreadDescription")) };
    if (fn) fn(GetCurrentThread(), name);   // shown in the debugger's Threads window (chapter 8)
}

Delay loading

Delay loading is a linker feature that gives you run-time loading with normal-looking calls. Add a DLL to Linker → Input → Delay Loaded Dlls and link its import library as usual. The linker replaces each import with a small stub; the first call to any function in that DLL loads it then. If the DLL never gets used (an optional feature the player never turns on), it is never loaded, and the program still starts when it is missing.

Common mistakes

Loading DLLs by bare name from a program with high privileges

Use full paths and SetDefaultDllDirectories. Search-order hijacking is a real attack.

[!warning] Calling FreeLibrary on a handle from GetModuleHandleW GetModuleHandleW does not increase the reference count, so freeing it can unload a DLL that something else still uses.

[!warning] Assuming GetModuleFileNameW fits in MAX_PATH Long paths are possible. Check the returned length and grow the buffer.
