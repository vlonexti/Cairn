Test Signing

lesson 16.099 of 10 in milestone 166 min

64-bit Windows loads only kernel drivers with a trusted digital signature: driver signature enforcement. During development, drivers are signed with a test certificate and loaded on machines in test mode, which is why the lab VM has it on. This lesson explains how signing works, sets up test signing, explains how real drivers are signed for release, and why test mode belongs only in a lab.

Why Windows requires signatures

A kernel driver can do anything (lesson 15.01). If any program could load any driver, malware would simply load its own and take full control of the machine. So 64-bit Windows enforces driver signature enforcement (DSE): a driver is loaded only if it carries a valid signature chaining to a certificate Windows trusts for kernel code, and for current Windows releases that means a signature from Microsoft itself, obtained through Microsoft's signing service after the driver's author has been verified.

A signature does two things: it proves who published the driver (accountability), and that the file has not been changed since it was signed (integrity). Microsoft can also revoke signatures and block known-vulnerable drivers (lesson 16.07), and features such as Hypervisor-protected Code Integrity (memory integrity) enforce these rules even against kernel-level tampering.

How a signature works, briefly

  1. A hash of the driver file is computed.
  2. The hash is signed with the publisher's private key; the signature and the publisher's certificate are embedded in the file (or in a catalog .cat file for installed driver packages).
  3. When loading, Windows recomputes the hash, checks the signature with the certificate's public key, and checks the certificate chains to a root it trusts for kernel drivers, and that it has not been revoked.

Change one byte of a signed driver and the hash no longer matches: it will not load.

Test signing for development

Getting every development build signed by Microsoft would be impossible, so Windows has a test mode for development machines:

  • On the test machine (the lab VM): bcdedit /set testsigning on, then restart (lesson 15.08). The desktop shows "Test Mode".
  • The driver is signed with a test certificate that the developer creates. Visual Studio's driver projects do this automatically: with Driver Signing → Sign Mode: Test Sign, the build creates a test certificate (XenonEcho.cer) and signs XenonEcho.sys with it.
  • In test mode, Windows accepts drivers signed with test certificates, provided the certificate is trusted on that machine. For drivers loaded as services with sc, test mode with a test-signed driver is usually enough; installing the test certificate into the VM's Trusted Root and Trusted Publishers stores (with certmgr or the Certificates console) covers the remaining cases.

You can check a signature with signtool verify /v /kp XenonEcho.sys (kernel-mode policy), or in the file's Properties → Digital Signatures tab.

Why test mode stays in the lab

Test mode weakens a fundamental protection: it lets the machine load drivers signed by anyone who can make a test certificate, which is anyone at all. That is fine in a disposable VM that holds nothing of value, and unacceptable on a computer you use for anything else. Never turn on test signing (or disable signature enforcement in any other way) on your everyday machine, and be suspicious of any software that asks you to.

Signing for release

Drivers distributed to other people go through Microsoft's Partner Center (Hardware Dev Center):

Step Purpose
An extended validation (EV) code-signing certificate for the company Proves the publisher's identity to Microsoft
Attestation signing (for testing and limited release), or full Windows Hardware Compatibility Program certification with the HLK test suite Microsoft checks and tests the driver
Microsoft signs the driver Windows then trusts it on every machine

That process is deliberate: it is why Windows users can trust that a driver came from an accountable publisher, and it is far outside an individual learner's needs. For this course, test signing in the lab VM is all you need.

Common mistakes

Disabling signature checks on your main PC "to make it work"

Use the lab VM. Test mode on an everyday machine weakens its security for everything.

[!warning] Changing the .sys after signing Any change breaks the signature. Sign as the last build step (Visual Studio does).

Assuming a signed driver is safe

A signature proves who published it and that it is unchanged, not that it has no bugs; vulnerable signed drivers exist, which is why Windows blocks known ones.
