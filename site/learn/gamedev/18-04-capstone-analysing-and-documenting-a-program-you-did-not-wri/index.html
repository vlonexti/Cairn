Capstone: Analysing and Documenting a Program You Did Not Write

lesson 18.044 of 4 in milestone 187 min1 practice task

The last capstone applies chapter 9's reverse engineering, chapter 8's debugging and chapter 7's assembly to a program whose source you have not read, and turns the findings into a clear technical report. Targets are chosen so the analysis is legal and checkable: open-source programs you build yourself with the source set aside, practice programs published for analysis, and programs a classmate writes for you. The lesson covers choosing a target, the method, the report's structure and how to check your conclusions against the truth.

Choosing a target

The analysis must be legal and checkable. Good targets:

Target Why it works
An open-source program you compile yourself, in Release, then analyse without reading the source; the source is the answer key afterwards Legal under its licence; you can check every conclusion
A practice program written for analysis (often called a "crackme" or reversing challenge) from a site whose rules allow it Made for this; usually comes with write-ups to compare
A program a classmate or friend writes for you with a short brief ("a small file format and a checksum"), who keeps the source until you finish Realistic and fun; both of you learn
One of your own old programs whose source you no longer remember Surprisingly instructive

Not suitable: commercial software or games whose licence forbids reverse engineering, anything protected by anti-tamper (lesson 17.06), online games, and anything you would analyse to get around a protection or a payment. Lesson 9.01's ground rules apply unchanged.

A good size is 50 to 500 KB of code: large enough to need a method, small enough to finish. A command-line tool with a file format (a compressor, an image converter, a small game with save files) is ideal.

The method

flowchart TB
    A["1. Triage<br/>PE headers, imports, strings, sections"] --> B["2. Run it<br/>observe files, output, behaviour"]
    B --> C["3. Find the interesting code<br/>cross-references from strings and imports"]
    C --> D["4. Understand it<br/>functions, loops, structs, in the disassembler"]
    D --> E["5. Confirm dynamically<br/>breakpoints, watch memory, change inputs"]
    E -->|"new question"| C
    E --> F["6. Document<br/>names, structures, diagrams, the report"]
  1. Triage (lessons 9.02, 9.03): architecture, sections, imports (file, network, crypto, UI?), exported functions, strings. Write down hypotheses: "it reads .cfg files", "it uses zlib".
  2. Run it in a VM or sandbox folder and watch with Process Monitor: files it opens, registry keys, what it prints.
  3. Find the interesting code (lesson 9.08): from a string such as "invalid header" or an import such as CreateFileW, follow cross-references back to the functions that use them.
  4. Understand it (lessons 9.04 to 9.06, 9.09, chapter 7): rename functions and variables in the disassembler as you go, reconstruct structs from field offsets, recognise loops, switches, vtables and library code.
  5. Confirm dynamically (lesson 9.07): break on the function, check arguments and results match your reading, change an input byte and predict what happens.
  6. Document: names, structures and the report below.

Keep a lab notebook: every address, hypothesis, test and result, dated. It is what turns hours of clicking into a report.

The report

Section Contents
Summary What the program does, in one paragraph, for someone who will not read further
Target and method Exact file, version, hash, how it was obtained and why analysing it is permitted; tools used
Architecture Main modules or components and how they interact, with a diagram
Function map A table of the important functions: address, your name, purpose, confidence
Data structures Reconstructed structs with offsets, sizes and field meanings
File format or protocol A byte-level description, if the program has one, with an example decoded by hand
Findings Anything notable: bugs, unsafe patterns (lesson 17.04), surprising design choices
Verification How each major conclusion was confirmed, and what is still uncertain
Comparison (open-source targets) What you got right, wrong and missed, once you read the source

The confidence column matters: "high (confirmed in the debugger)", "medium (consistent with the code)", "low (a guess from the name of a string)". Honest uncertainty is what makes a report trustworthy.

Acceptance criteria

  • The target is one of the permitted kinds, recorded with its hash and licence.
  • The function map covers the program's main path from main (or WinMain) to its output, with at least 15 functions named.
  • At least two structures are reconstructed with every field's offset.
  • If the program has a file format, a small program of yours reads or writes it correctly (proof of understanding).
  • Every high-confidence claim has a recorded dynamic confirmation.
  • For an open-source target, the comparison section is honest about errors.

Stretch goals

  • Write a script for your disassembler (Ghidra's Python or Java API) that applies your function names and struct definitions automatically, and include it.
  • Analyse two builds of the same program (Debug and Release, or two versions) and document what changed.
  • Turn the report into a short talk for classmates.

Common mistakes

Reading everything in order

Start from strings, imports and behaviour, and work towards the interesting code.

Not writing things down

Without a notebook, you will analyse the same function twice.

Stating guesses as facts

Give every conclusion a confidence and the evidence for it.
