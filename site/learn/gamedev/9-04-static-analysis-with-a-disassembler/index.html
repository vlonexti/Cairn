Static Analysis with a Disassembler

lesson 9.044 of 10 in milestone 96 min

A disassembler turns a program's machine code back into assembly and organises it into functions, cross-references and control-flow graphs; a decompiler goes one step further, to C-like pseudocode. This lesson sets up Ghidra, the free, open-source reverse engineering suite, and walks through analysing a small program you built yourself: finding main, reading the listing and the decompiler side by side, and annotating as you learn.

The tools

Ghidra needs a Java runtime (JDK 17 or later). Download it from its official GitHub releases page, unzip it, and start ghidraRun.bat.

A target to analyse

Build this in Visual Studio in Release, x64, and keep the source closed while you analyse it. (You will check your conclusions at the end.)

C++
#include <cstdio>
#include <cstring>

struct Hero { char name[16]; int level; int xp; };

int xpForLevel(int level) { return level * level * 100; }

void gainXp(Hero& hero, int amount)
{
    hero.xp += amount;
    while (hero.xp >= xpForLevel(hero.level + 1))
    {
        ++hero.level;
        std::printf("%s reached level %d!\n", hero.name, hero.level);
    }
}

int main()
{
    Hero hero{};
    std::strcpy(hero.name, "Rook");
    hero.level = 1;
    for (int quest{ 0 }; quest < 5; ++quest) gainXp(hero, 250);
    std::printf("Final: level %d, %d xp\n", hero.level, hero.xp);
    return 0;
}

To make it a fair exercise, do not give Ghidra the PDB at first: move x64\Release\*.pdb somewhere else.

Importing and analysing

  1. File → New Project, non-shared, in a folder of your choice.
  2. File → Import File, pick the .exe. Ghidra recognises it as "Portable Executable (PE)", x86:LE:64. Accept.
  3. Double-click it to open the CodeBrowser, and say Yes to analyse it with the default analysers.

Ghidra now disassembles everything reachable from the entry point and exports, finds functions, follows cross-references, identifies standard library code it recognises (function signatures for the C runtime), and builds a decompilation for each function.

Finding main

The entry point is the C runtime's start-up code, not main. Two quick ways to find main:

  • In Defined Strings, find "Final: level %d, %d xp\n", double-click it, and look at its cross-reference (the XREF annotation): the function that uses it is main. Strings are the fastest way into unfamiliar code (lesson 9.08).
  • Or follow the entry point's code until a call with three arguments set up from argc, argv, envp-like values just before the program exits: that is the start-up code calling main.

Reading the decompiler with the listing

Ghidra's decompiler for gainXp might show something like:

C
void FUN_140001070(longlong param_1, int param_2)
{
  int iVar1;

  *(int *)(param_1 + 0x14) = *(int *)(param_1 + 0x14) + param_2;
  while (iVar1 = *(int *)(param_1 + 0x10),
         (iVar1 + 1) * (iVar1 + 1) * 100 <= *(int *)(param_1 + 0x14)) {
    *(int *)(param_1 + 0x10) = iVar1 + 1;
    printf("%s reached level %d!\n", param_1, iVar1 + 1);
  }
  return;
}

Everything from earlier chapters is visible: param_1 is a pointer (it is used with offsets); offset 0x10 and 0x14 are 4-byte members (lesson 7.08); xpForLevel has been inlined (lesson 7.11), so its formula appears directly; and the printf format string tells us param_1 points at a name and offset 0x10 is a level.

Now annotate, which is most of the work:

  • Rename the function (L key): gainXp.
  • Rename the parameters: hero, amount.
  • Create a structure (Data Type Manager → New → Structure) Hero with a char[16] name, an int level at 0x10 and an int xp at 0x14, and retype param_1 as Hero * (Ctrl+L). The decompiler now prints hero->level and hero->xp.
  • Add comments (; key) for anything you work out.

Annotations propagate: every other function that uses a Hero * now reads better too. That snowball effect is why careful naming early pays off.

Checking your work

Open the source and compare. Then give Ghidra the PDB (File → Load PDB File) and look at the same function: names, types and line numbers appear, and you can see exactly what the PDB contributes (lesson 8.02) and what you had to reconstruct.

Common mistakes

Believing every detail of the decompiler output

It is reconstructed C, sometimes with wrong types or awkward casts. For anything important, check the listing.

Reading top to bottom from the entry point

Start from something meaningful: a string, an import, an exported function.

Not saving your annotations

Ghidra saves them in the project; save often, and keep the project with your notes.
