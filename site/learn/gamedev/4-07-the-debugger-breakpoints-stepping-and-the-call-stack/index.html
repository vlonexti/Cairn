The Debugger: Breakpoints, Stepping and the Call Stack

lesson 4.077 of 10 in milestone 48 min

Lesson 1.08 was a first session. This lesson covers the debugger as a daily tool: every way of controlling execution (run to cursor, step into a specific call, set the next statement), moving around the Call Stack, breaking when an exception is thrown, Just My Code, and attaching to a program that is already running.

How a debugger stops a program

It helps to know what a breakpoint is. When you set one on a line, the debugger finds the first machine instruction for that line and overwrites its first byte with 0xCC, the int 3 instruction. When the CPU reaches it, the processor raises a breakpoint exception; Windows sees that a debugger is attached to the process and hands it the event. The debugger then puts the original byte back, shows you the line, and waits.

Stepping works similarly: the debugger sets temporary breakpoints, or turns on the processor's trap flag, which raises an exception after every single instruction. Chapter 12 uses these same Windows debugging events to build a tiny debugger of your own.

Controlling execution

Command Key What it does
Start Debugging / Continue F5 Run until a breakpoint, an exception, or the end
Step Over F10 Run the current line, including calls, stop at the next line
Step Into F11 Go into the function the line calls
Step Out Shift+F11 Run until the current function returns
Run To Cursor Ctrl+F10 Run until the line the cursor is on, as if it had a one-time breakpoint
Run to Click The green arrow that appears when hovering at the left of a line Same, with the mouse
Step Into Specific Right-click → Step Into Specific Choose which call to step into when a line makes several, such as update(getPlayer(), clamp(x))
Set Next Statement Ctrl+Shift+F10, or drag the yellow arrow Make a different line run next, skipping or repeating code
Break All Ctrl+Alt+Break Pause the program wherever it is, for example when it seems stuck
Stop Debugging Shift+F5 End the program
Restart Ctrl+Shift+F5 End and start again

Set Next Statement is powerful and dangerous: it changes where the CPU goes next without running the code in between. It is excellent for re-running a function after changing a variable, and can crash the program if you skip something important such as a constructor. Use it within one function.

Break All is the answer to "my game froze": pause, open the Call Stack, and see what every thread is doing (chapter 8 covers threads).

The Call Stack window, as a tool

Debug → Windows → Call Stack (Ctrl+Alt+C) lists the frames from the current function down to the start of the thread (lesson 1.05). Using it well:

  • Double-click a frame to make it current: the editor shows that function's line, and Locals and Watch show that frame's variables. This is how you find out why a function was called with a bad argument: go up one frame and look at the caller's variables.
  • Right-click → Show External Code reveals frames from the standard library and Windows, hidden by default.
  • Right-click → Show Parameter Values / Parameter Types puts the arguments on each line.
  • Run To Cursor in an earlier frame (select it, then Ctrl+F10 on a line) runs until control comes back up to that point.

Just My Code

By default, Visual Studio's Just My Code setting hides and skips code that is not yours: the standard library, Windows, third-party libraries without debug information. Step Into then does not wander into std::vector's internals. When you need to see inside them (for example, to watch a std::vector reallocate), turn it off in Tools → Options → Debugging → General → Enable Just My Code.

Breaking on exceptions

By default, the debugger stops only on exceptions nobody catches. That is often too late: by then the stack has unwound past the code that threw. Open Debug → Windows → Exception Settings (Ctrl+Alt+E) and tick the categories you want to stop on when thrown:

  • C++ Exceptions: stop at any throw, even if it will be caught. Good for "something throws and gets swallowed somewhere".
  • Win32 Exceptions → Access violation (0xC0000005): usually already on. Stops at the exact instruction that read or wrote bad memory, with the full stack intact.

When the debugger stops on an access violation, the message says "reading location 0x..." or "writing location 0x...". As lesson 3.02 explained, a small address there means a null pointer plus an offset.

Attaching to a running program

You do not have to start a program from Visual Studio to debug it. Debug → Attach to Process (Ctrl+Alt+P) lists running processes; pick yours and press Attach. Breakpoints, Break All and the windows all work, provided the debugger can find the program's .pdb symbols (lesson 8.02).

This is how you debug a game that only misbehaves after an hour of play, a program started by another program, or a tool you want to inspect without restarting it. You can attach only to your own processes unless Visual Studio runs as administrator, and Windows refuses debugging of protected system processes entirely.

Debug → Detach All lets the program carry on without the debugger.

Common mistakes

A breakpoint that never hits

A hollow red circle means the debugger could not place it: the code is not loaded yet, the build is out of date, or the line has no code (in Release, the compiler may have removed or merged it). Rebuild in Debug.

Set Next Statement across function boundaries

Moving the yellow arrow into a different function leaves the stack in a state the code does not expect. Stay within one function.

Stopping too late on exceptions

Turn on "break when thrown" for C++ exceptions to see where an exception starts, not just where it ends.
