Unit Tests for Low-Level Code

lesson 17.011 of 8 in milestone 175 min1 practice task

Every practice task in this course has been checked by unit tests. This lesson turns that around: writing tests for your own low-level code with a framework such as Catch2 or GoogleTest, structuring code so it can be tested (pure logic, injected clocks, random numbers and platform calls), and deciding what is worth testing in games, tools and drivers.

What a unit test is

A unit test calls one piece of code with chosen inputs and checks its outputs, automatically, in milliseconds. A suite of them runs on every build:

C++
#include <catch2/catch_test_macros.hpp>
#include "inventory.h"

TEST_CASE("potions stack up to their limit")
{
    Inventory inv{ 4, { { "potion", 5 } } };
    REQUIRE(inv.add("potion", 7) == 0);
    CHECK(inv.slot(0) == std::pair<std::string, int>{ "potion", 5 });
    CHECK(inv.slot(1) == std::pair<std::string, int>{ "potion", 2 });
}

The course's practice harness works the same way (TEST, CHECK, CHECK_EQ). Real projects use a framework:

Framework Notes
Catch2 Header-friendly, readable, TEST_CASE and sections; vcpkg port catch2
GoogleTest Widely used, fixtures and mocking (GoogleMock); vcpkg port gtest; Visual Studio's Test Explorer runs it
Microsoft Native Unit Test Framework Built into Visual Studio's C++ test project template
doctest Very fast to compile, Catch2-like

Put tests in a separate project (lesson 4.01's tests), linked against the engine library, and run it after every build, locally and in continuous integration (lesson 17.08).

Designing code to be testable

Code is easy to test when its logic does not reach directly for things the test cannot control:

Hard to test Make it testable by
Calls QueryPerformanceCounter or std::chrono directly Passing a clock (an interface or function) in; tests use a fake clock they advance by hand
Calls rand() Passing a seeded random generator in
Opens files, windows, devices Separating the platform layer from pure logic (lesson 12.07): parse text, not files
Uses global state Passing state in, or resetting it per test
Big functions doing everything Small functions with inputs and outputs

This is why the practice tasks always asked for a function taking data and returning data: parseLevel(text) rather than loadLevel(path), tryMove(map, ...) rather than code buried in the game loop. The practice task for this lesson injects a clock into a cooldown timer.

What to test

Test Example
Normal cases A potion heals 10
Edges Health exactly 0; an inventory exactly full; the first and last tile of a map
Invalid input A ragged level file, a negative count, an unknown command
Regression tests For every bug fixed, a test that would have caught it (lesson 8.01)
Round trips Save then load gives the same state (lesson 11.06)
Properties For any random input, sorting gives an ordered result of the same length

Not everything needs a unit test: rendering and "does it feel right" are checked by people, and drivers' kernel code is tested in the VM (lesson 16.10). But every piece of pure logic, the majority of most programs, can and should be.

Testing low-level code specifically

  • Bit and byte code (lessons 1.02, 2.06, 9.02): test against known byte sequences, written out in the test, including the edges (0, maximum values, negative numbers).
  • Parsers of untrusted data (save files, network messages, PE headers): test valid, truncated, oversized and nonsense inputs; then fuzz them (lesson 17.03).
  • Concurrency (lesson 6.06): tests that run many threads are useful but cannot prove absence of races; combine with careful design and tools.
  • Memory: run the test suite under AddressSanitizer (lesson 2.10) in a separate configuration, so tests also catch overruns and use-after-free.

Common mistakes

Tests that depend on time or randomness

They pass and fail at random. Inject the clock and the generator.

Testing only the happy path

Bugs live at edges and in invalid input.

Tests that are slow or need setup

Unit tests should run in seconds with no outside dependencies, or nobody runs them.
