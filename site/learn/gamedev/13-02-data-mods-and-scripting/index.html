Data Mods and Scripting

lesson 13.022 of 8 in milestone 135 min1 practice task

The simplest and safest mods change data. This lesson gives Delve a layered file system that looks for each file in the enabled mods (last first) before the base game, then improves on whole-file replacement by merging data entries so several mods can change different things in the same file. It ends by opening the game's scripting to mods, with limits.

A layered file system

The game never opens data\monsters.ini directly. It asks the virtual file system for monsters.ini, which searches the layers from the top:

Output
layer 3:  mods\easy-mode\data\         (last in the load order: searched first)
layer 2:  mods\tougher-trolls\data\
layer 1:  data\                        (the base game: searched last)
C++
class VirtualFileSystem
{
public:
    void addLayer(std::filesystem::path root) { m_layers.push_back(std::move(root)); }   // base first, mods after

    // The path of the file that wins, or nothing if no layer has it.
    std::optional<std::filesystem::path> find(const std::string& relative) const
    {
        for (auto it{ m_layers.rbegin() }; it != m_layers.rend(); ++it)                  // top layer first
            if (auto candidate{ *it / relative }; std::filesystem::exists(candidate)) return candidate;
        return std::nullopt;
    }

    // Every layer's version, base first: for merging.
    std::vector<std::filesystem::path> findAll(const std::string& relative) const;
private:
    std::vector<std::filesystem::path> m_layers;
};

Every asset the game loads, textures, sounds, levels, goes through find. Replacing a texture is then just putting a file with the same name in a mod folder. This is the same idea games use for their own patches: a patch is a layer above the original data.

Validate paths. A mod asks for files by relative name; reject names containing .. or absolute paths, so a mod cannot reach files outside its own and the game's folders (lesson 17.04).

Merging instead of replacing

Whole-file replacement makes mods fight: two mods both shipping monsters.ini means only the last one's file is used. Merging works entry by entry:

  1. Load the base game's monsters.ini into a map of section.key → value (lesson 10.08's INI parser).
  2. For each enabled mod in load order, load its monsters.ini (if any) and overwrite only the keys it contains.
  3. The result is the base game plus every mod's changes, with later mods winning only where they touch the same key.
Output
base:            troll.health = 120    goblin.damage = 4
tougher-trolls:  troll.health = 200
easy-mode:                             goblin.damage = 2
merged:          troll.health = 200    goblin.damage = 2       both mods apply

The practice task implements the merge and reports which keys were changed by more than one mod, the true conflicts a mod manager should show.

Mod scripts

If the game embeds a scripting language (lesson 10.08), mods can add behaviour too: each mod's scripts\ folder is run at start-up, and scripts register for events the game publishes ("monster died", "level loaded"; lesson 13.05 builds the event system):

Lua
-- mods/lantern-light/scripts/main.lua
on("level_loaded", function(floor)
  if floor >= 3 then
    message("It is getting dark. Your lantern flickers.")
  end
end)

The game decides exactly which functions scripts may call (on, message, spawn...), and each mod's scripts should run in their own environment so they cannot overwrite another mod's functions. A script error is caught, reported with the mod's name, and the mod is disabled for the session, without taking the game down (lesson 13.07).

Common mistakes

Opening files directly in game code

Go through the virtual file system so mods (and patches) can override them.

[!warning] Accepting .. in paths from mods A mod could then read or overwrite files anywhere. Reject them.

Whole-file replacement for shared data

Merge entries so independent mods can coexist.
