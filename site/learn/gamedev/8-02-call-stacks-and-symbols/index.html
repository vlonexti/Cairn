Call Stacks and Symbols

lesson 8.022 of 8 in milestone 87 min1 practice task

A call stack turns a crash address into a story: which function, called from where, with what. Making that work needs symbols: the .pdb files that map machine code back to names and source lines. This lesson covers what is in a PDB, how debuggers find the right one, Microsoft's symbol server for Windows' own DLLs, how stacks are walked without frame pointers, and how to capture a stack trace from inside your own program.

What symbols are

The compiler and linker throw names away: in the .exe, a function is just bytes at an RVA. The program database (.pdb) file written alongside it keeps everything a debugger needs to get the names back:

In the PDB Lets the debugger
Function names and their RVA ranges Name the function containing any address
Line number tables Map each instruction to a source file and line
Types and struct layouts Show player.health instead of raw bytes
Local variables and where they live Fill the Locals window
Frame data Help walk the stack

A PDB matches exactly one build. The exe records a unique signature (a GUID and an age) and the PDB's file name in its debug directory; the debugger only loads a PDB whose signature matches. Rebuild even without changing anything, and the old PDB no longer fits. That is why you keep the PDB of every build you ship: without it, a crash report from that build can only show raw addresses.

How the debugger finds symbols

For each loaded module, the debugger searches, in order:

  1. The path recorded in the exe (where the PDB was written at build time).
  2. The folder the module was loaded from.
  3. The symbol path: folders and symbol servers you configure (Tools → Options → Debugging → Symbols).

Visual Studio's Modules window shows, for every DLL and exe, whether symbols loaded and from where. "Cannot find or open the PDB file" there explains a call stack full of game.exe!00007ff6a1235f10() instead of names.

The Microsoft symbol server

Windows' own DLLs have public symbols too: Microsoft publishes them on a symbol server, a web service that hands out the PDB matching each DLL's signature. Turn it on in Visual Studio (tick Microsoft Symbol Servers) or set the environment variable used by WinDbg and other tools:

Output
_NT_SYMBOL_PATH=srv*C:\Symbols*https://msdl.microsoft.com/download/symbols

srv* means "use a symbol server", C:\Symbols is a local cache, and the URL is Microsoft's server. With it, call stacks through Windows code show names like ntdll.dll!RtlUserThreadStart and kernel32.dll!BaseThreadInitThunk instead of raw addresses, which is often exactly where the interesting part of a crash is. Studios run their own symbol servers for their builds, so any crash from any shipped version can be symbolised.

Walking the stack without frame pointers

Lesson 7.05 said x64 Windows code usually does not keep a frame pointer in rbp. So how does a debugger find each caller? Every function's prologue is described in unwind information in the exe's .pdata and .xdata sections: "this function pushed rbx and rdi, then subtracted 40 from rsp". Given the current rip and rsp, the debugger finds the function containing rip, applies its unwind description in reverse to recover the caller's rsp and the return address, and repeats. Windows uses the same data to unwind the stack when an exception is thrown.

This is also why corrupt stacks look so strange: if the return address on the stack has been overwritten (lesson 7.05), the unwinder follows garbage, and the call stack ends abruptly or shows nonsense.

Capturing a stack in your own program

A crash reporter or an assert (next lesson) wants the call stack as text. C++23's std::stacktrace does it portably:

C++
#include <iostream>
#include <stacktrace>

void deepInside()
{
    const auto trace{ std::stacktrace::current() };
    std::cout << "captured " << (trace.size() >= 2 ? "a stack with several frames" : "almost nothing") << '\n';
    // std::cout << trace;   // prints each frame: function, file and line, when symbols are available
}

void middle() { deepInside(); }

int main()
{
    middle();
    return 0;
}
Output
captured a stack with several frames

Printing the whole trace (the commented line) gives function names and source lines when the PDB is next to the exe. On Windows the lower-level tools are CaptureStackBackTrace (just the return addresses) and the DbgHelp library (SymFromAddr, SymGetLineFromAddr64) to turn them into names. Without symbols, store the addresses as module + RVA (lesson 6.09) and symbolise them later on a machine that has the PDB.

Reading a call stack

Output
game.exe!Inventory::totalWeight() Line 42
game.exe!Hud::drawWeight(const Player & player) Line 118
game.exe!Hud::draw(const World & world) Line 87
game.exe!Game::render() Line 210
game.exe!wWinMain(...) Line 35
kernel32.dll!BaseThreadInitThunk()
ntdll.dll!RtlUserThreadStart()

Read from the top: the crash is in totalWeight at line 42; it was called by drawWeight, which was called by draw, and so on down to the thread's start in Windows. Double-click any frame to see its variables (lesson 4.07). The bug is often not in the top frame, but in a caller that passed it something bad.

Common mistakes

Not keeping the PDBs of shipped builds

A crash report from players is then just numbers. Archive every released build's PDB, or run a symbol server.

A PDB from a different build

It will not load, even if the code looks the same. Rebuild and keep exe and PDB together.

Shipping PDBs to players

Private PDBs contain your full source structure. Ship none, or stripped public ones (/PDBSTRIPPED), and keep the full ones yourself.
