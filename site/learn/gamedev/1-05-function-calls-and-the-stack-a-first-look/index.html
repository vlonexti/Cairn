Function Calls and the Stack: A First Look

lesson 1.055 of 8 in milestone 18 min1 practice task

When a function is called, the CPU has to remember where to come back to, and the function needs somewhere to keep its local variables. Both go on the stack, a region of memory that grows by one frame per call and shrinks again when the call returns.

Two questions every call has to answer

The tiny computer in lesson 1.01 had a JUMP instruction: carry on from a different cell. A function call needs more than that. When main calls heal, the CPU jumps into heal. When heal finishes, the CPU has to jump back, to the exact instruction after the call in main.

So a call raises two questions:

  1. Where do I return to? heal can be called from fifty different places. Each call must return to its own caller.
  2. Where do my local variables live? heal may call itself, or be running in several threads at once. Each run needs its own copy of its locals.

One idea answers both: a stack.

A stack of frames

A stack is a pile where you only ever add to the top or take from the top, like a pile of plates. The program reserves a region of memory for it when it starts, about one megabyte by default on Windows.

Each time a function is called, a block of that region is set aside for the call. The block is called a stack frame, and it holds:

  • the return address: where in the caller to carry on afterwards,
  • the function's local variables,
  • some of its arguments, and some bookkeeping.

When the function returns, its frame is released, and the caller's frame is on top again.

Things to notice:

  • The newest frame always sits at the lowest address. On x64 Windows, as on most systems, the stack grows downwards in memory.
  • The stack pointer register, rsp, always holds the address of the top of the stack. Making a frame is just subtracting from rsp; releasing it is adding back. That is why calls are fast.
  • total exists only while heal is running. Once heal returns, the memory it used is free to be reused by the next call.

Seeing the stack grow from C++

You can watch the addresses yourself by printing the address of a local variable at different depths of recursion.

C++
#include <iostream>

void dive(int depth)
{
    int marker{ depth };                     // one local per call
    std::cout << "depth " << depth << ": marker is at " << &marker << '\n';
    if (depth < 3)
        dive(depth + 1);
}

int main()
{
    dive(1);
    return 0;
}
Output (yours will differ)
depth 1: marker is at 000000E1A3AFF6B4
depth 2: marker is at 000000E1A3AFF654
depth 3: marker is at 000000E1A3AFF5F4

Your addresses will differ, and they change between runs. What stays the same is the pattern: each deeper call's marker is at a lower address, here 0x60 (96) bytes lower each time. That gap is the size of one dive frame. Each call really does have its own marker, in its own place.

Return values and the stack pointer

How does clamp hand back 100? Small return values do not go through the stack at all. On x64 Windows they are left in the register rax, and the caller reads them from there straight after the call. The first four arguments travel in registers too (rcx, rdx, r8, r9), which is why addBonus in the last lesson found score in rcx. The exact rules are the calling convention, which chapter 7 covers in detail.

The two instructions that make calls work are:

Instruction What it does
call heal Pushes the address of the next instruction onto the stack (rsp goes down by 8), then jumps to heal
ret Pops that address off the stack (rsp goes up by 8) and jumps to it

That is the whole trick. call leaves a note of where to come back to, and ret reads it.

When it goes wrong

The stack is a fixed size. A recursive function that never stops calling itself keeps adding frames until the region is full. The next frame lands outside it, and Windows stops the program with a stack overflow (exception code 0xC00000FD).

C++
// Do not run this one: it never stops.
int forever(int n)
{
    return forever(n + 1) + 1;
}

Large local arrays use stack space too. int grid[1000000]; inside a function asks for 4 MB of stack and will overflow on its own. Big data belongs on the heap, which chapter 2 covers.

The other classic stack bug is returning the address of a local:

C++
int* makeScore()
{
    int score{ 500 };
    return &score;        // score's frame is released as the function returns
}

The caller gets an address inside a frame that no longer exists. The next call reuses that memory, and the "score" changes underneath you. The compiler warns about this (warning C4172). It is one form of dangling pointer, a bug chapter 2 looks at closely.

Common mistakes

Thinking locals keep their values between calls

Each call gets a fresh frame. A local starts uninitialised (or with its initialiser) every time. Use a static local or a member variable for something that must survive.

Expecting the stack to grow upwards

Newer frames are at lower addresses on x64. If you see addresses getting smaller as you go deeper, that is correct.

Huge arrays as local variables

The default stack is about 1 MB. Use std::vector or another heap allocation for anything large.

Returning a pointer or reference to a local

The frame is gone once the function returns. Return the value itself instead.

quizIn Xenon your best score is kept.
  1. What two things does every function call need the stack for?
    • Storing the program's code and its global variables
    • Remembering where to return to, and holding the call's local variables
    • Holding the heap and the list of open files
    Show the answer

    Remembering where to return to, and holding the call's local variables The return address lets the CPU come back to the right place in the caller; the frame gives each call its own locals.

  2. On x64 Windows, a function calls itself three levels deep. Where is the deepest call's frame?
    • At the highest address, above the others
    • At the lowest address, below the others
    • In the same place as the first frame, which it overwrites
    Show the answer

    At the lowest address, below the others The stack grows downwards: each new frame is placed below the previous one.

  3. What does the ret instruction do?
    • Pops the return address off the stack and jumps to it
    • Pushes the return value onto the stack
    • Ends the program
    Show the answer

    Pops the return address off the stack and jumps to it call pushed the return address; ret takes it back off and carries on from there.

  4. Why does int grid[1000000]; inside a function usually crash?
    • int arrays cannot be that long
    • It needs about 4 MB of stack, more than the 1 MB the stack has by default
    • The compiler rejects it
    Show the answer

    It needs about 4 MB of stack, more than the 1 MB the stack has by default Locals live in the frame. A frame bigger than the whole stack overflows it immediately.
