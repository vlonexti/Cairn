Following Pointers Through Objects

lesson 3.022 of 10 in milestone 35 min1 practice task

Real programs are webs of objects joined by pointers: a world holds a player, a player holds an inventory, an inventory holds items. Getting from one object to another means following a chain of pointers, each step a read of an address and an offset. This lesson shows what that looks like in memory, how to follow it safely, and what it costs.

A small web of objects

C++
#include <iostream>
#include <string>
#include <vector>

struct Item
{
    std::string name;
    float weight;
};

struct Inventory
{
    std::vector<Item*> slots;     // pointers to items stored elsewhere
    float maxWeight{ 30.0f };
};

struct Player
{
    int health{ 100 };
    Inventory* inventory{ nullptr };
};

struct World
{
    Player* player{ nullptr };
};

int main()
{
    Item sword{ "sword", 6.5f };
    Item rope{ "rope", 2.0f };
    Inventory bag{ { &sword, &rope } };
    Player hero{ 100, &bag };
    World world{ &hero };

    // world -> player -> inventory -> slots[0] -> name
    std::cout << world.player->inventory->slots[0]->name << '\n';
    return 0;
}
Output
sword

That one line follows four arrows. Each -> means "read the pointer stored here, go to that address, then move to a member at a fixed offset". In memory it looks like this:

flowchart LR
    W["World<br/>+0 player"] -->|"read +0"| P["Player<br/>+0 health<br/>+8 inventory"]
    P -->|"read +8"| I["Inventory<br/>+0 slots (vector)<br/>+24 maxWeight"]
    I -->|"read slots data, index 0"| S["Item sword<br/>+0 name<br/>+32 weight"]

(The offsets here are those of a Release build, where std::vector is 24 bytes and std::string 32.)

What the CPU actually does

Following one link is two simple steps: load 8 bytes from (object address + member offset), and use the result as the next address. Written as the arithmetic a debugger or a memory tool would do:

Output
player    = read8(address of world + 0)
inventory = read8(player + 8)
slotArray = read8(inventory + 0)          the vector's data pointer
item      = read8(slotArray + 0 * 8)
name      = item + 0

This is exactly what the debugger's Watch window does when you expand world.player->inventory, and it is the skill chapter 9 uses to rebuild an unknown program's data structures: find an object, see that offset 8 holds a pointer, follow it, and work out what kind of object is there.

Every arrow can be null

Each link in the chain can be missing: the player might not have an inventory yet, a slot might be empty. Following a null pointer is undefined behaviour, and on Windows it crashes with an access violation reading location 0x0000000000000008 or similar. The small number in that message is a clue: it is the offset of the member being read from a null object.

So code that walks a chain checks each step, or guarantees in its design that the link cannot be null:

C++
float carriedWeight(const World& world)
{
    if (!world.player || !world.player->inventory) return 0.0f;
    float total{ 0.0f };
    for (const Item* item : world.player->inventory->slots)
        if (item) total += item->weight;
    return total;
}

Two habits help:

  • Prefer references or values where a link is always present. If every player always has an inventory, make it a member Inventory inventory; rather than a pointer. Then there is nothing to check and one fewer arrow to follow.
  • Use a pointer when the link is genuinely optional, and check it. std::optional and nullptr checks say so in the code.

The cost of chasing pointers

Each arrow is a memory read whose address depends on the previous read. The processor cannot start fetching the item until it knows the item's address, which it only learns after fetching the inventory, and so on. If the objects are scattered around the heap, each step is likely to miss the cache and wait for main memory. This chain of dependent loads is called pointer chasing, and it is one of the main reasons data-heavy code is slow.

Game engines therefore prefer:

  • objects stored by value inside the objects that own them, so they sit in the same cache lines;
  • arrays of objects rather than arrays of pointers to objects, so a loop walks memory in order (lesson 2.07);
  • indices or handles into such arrays instead of raw pointers (lesson 3.10).

std::vector<Item*> above is the slow shape; std::vector<Item> is the fast one, when the items do not need to be shared.

Common mistakes

Long unchecked chains

a->b->c->d->value crashes if any link is null, and the crash message only tells you the final offset. Check optional links, or restructure so they are not optional.

Storing pointers to elements of a vector

The vector may move its elements (lesson 2.04). Store indices instead.

Assuming the debugger's offsets match your release build

Debug builds of standard containers are bigger. Offsets you work out in one configuration can differ in the other.

Knowledge check

quizIn Xenon your best score is kept.
  1. A crash says "access violation reading location 0x0000000000000010". What is the most likely cause?
    • Code read a member at offset 16 of an object through a null pointer
    • The program ran out of memory
    • A function returned 16
    Show the answer

    Code read a member at offset 16 of an object through a null pointer Null plus a member offset gives a tiny address like 0x10. Look for an unchecked pointer whose member at offset 16 was being read.

  2. Why is following a long chain of pointers through scattered heap objects slow?
    • Pointers are slower to read than integers
    • Each read needs the previous one's result as its address, and each may miss the cache
    • The compiler cannot optimise ->
    Show the answer

    Each read needs the previous one's result as its address, and each may miss the cache Dependent loads cannot overlap, so every cache miss along the chain is paid in full.

  3. When should a member be a pointer rather than a value?
    • When the link is genuinely optional or the object is shared or owned elsewhere
    • Always, because pointers are smaller
    • Never
    Show the answer

    When the link is genuinely optional or the object is shared or owned elsewhere If an object always has exactly one of something, a value member is simpler, safer and faster.
