Reading the Memory Window in Visual Studio

lesson 2.1111 of 11 in milestone 29 min1 practice task

The Memory window shows raw bytes, and this chapter has given you everything you need to read them. This lesson puts it together: setting the window's display, recognising pointers, Debug patterns, text and floating-point numbers at a glance, and decoding a whole object by hand.

Setting the window up

Open it while paused: Debug → Windows → Memory → Memory 1 (Visual Studio has four, so you can keep several places open). The useful controls:

Control What it does
Address box Type any expression that gives an address: &hero, ptr, names.data(), 0x00000052A3CFF7A8, rsp. Press Enter.
Reevaluate automatically (the circular arrows) Keeps following the expression as you step: useful for a pointer that changes.
Columns How many units per row. Set it to 16 bytes, or to 8 when looking at pointers.
Right-click → 1-, 2-, 4- or 8-byte integer Groups bytes into numbers, already put back into the right order for little-endian.
Right-click → 32-bit or 64-bit floating point Shows each group as a float or double.
Right-click → Signed / Unsigned / Hexadecimal display How the numbers are written.
Right-click → ANSI / Unicode text (the column on the right) Shows the bytes as one-byte or UTF-16 characters.

You can also drag a variable from the code editor or Locals window into the Memory window to jump to its address.

Recognising what you are looking at

With practice you can tell what a group of bytes is from its shape alone. Here is the catalogue for a 64-bit Windows program:

You see (bytes, as shown) It is probably
xx xx xx xx f6 7f 00 00 A pointer into the program's own image (code or globals): high bytes 00 00 7f f6 or nearby
xx xx xx xx fe 7f 00 00 A pointer into a system DLL
xx xx xx xx 0X 0X 00 00 with small X A heap pointer: two high bytes zero, then smallish
xx xx xx xx xx 00 00 00, 8-byte aligned, near rsp A stack address
cc cc cc cc Uninitialised stack memory (Debug)
cd cd cd cd Allocated, never written heap memory (Debug)
dd dd dd dd Freed heap memory (Debug)
fd fd fd fd Heap guard bytes (Debug)
00 00 80 3f The float 1.0
00 00 00 00 00 00 f0 3f The double 1.0
xx 00 xx 00 xx 00, letters in the right-hand column with dots between UTF-16 text
Small numbers followed by 00 00 00 Small ints: counts, ids, health

Pointers stand out most: eight bytes ending in 00 00, with the high bytes repeating the same few values. Since x64 programs only use the lower 47 bits of an address, the top two bytes of a user-mode pointer are always zero.

Reading floating-point numbers

float and double are not stored like integers. A 32-bit float has three parts:

 bit 31   30 ......... 23   22 ...................... 0
┌──────┬─────────────────┬──────────────────────────────┐
│ sign │ exponent (8)    │ fraction (23)                │
└──────┴─────────────────┴──────────────────────────────┘
value = (-1)^sign × 1.fraction × 2^(exponent − 127)

You will rarely decode one by hand, because the Memory window can do it for you. But a few values are worth recognising, because they appear constantly in game data such as positions, speeds and scales:

Value float bits Bytes in memory
0.0 0x00000000 00 00 00 00
0.5 0x3F000000 00 00 00 3f
1.0 0x3F800000 00 00 80 3f
2.0 0x40000000 00 00 00 40
10.0 0x41200000 00 00 20 41
100.0 0x42C80000 00 00 c8 42
−1.0 0xBF800000 00 00 80 bf

A rule of thumb: a 4-byte group whose last byte is 3f, 40, 41, 42, bf, c0, c1 or c2 and whose first bytes are often 00 is very likely a float of modest size.

You can see a value's bits from C++ by copying its bytes into an integer. std::bit_cast (C++20) does it in one step:

C++
#include <bit>
#include <cstdint>
#include <format>
#include <iostream>

int main()
{
    for (float f : { 1.0f, -1.0f, 0.5f, 100.0f, 0.1f })
        std::cout << std::format("{:>6} -> 0x{:08X}\n", f, std::bit_cast<std::uint32_t>(f));
    return 0;
}
Output
     1 -> 0x3F800000
    -1 -> 0xBF800000
   0.5 -> 0x3F000000
   100 -> 0x42C80000
   0.1 -> 0x3DCCCCCD

0.1 has no exact binary form, which is why its bits look busy. It is also why comparing floats with == after arithmetic often fails.

Decoding a whole object

Here is the routine for any object, using everything from this chapter.

  1. Find its type's layout. Work through the members and the alignment rules (lesson 2.05), or let the Watch window tell you with &obj.member.
  2. Point the window at the object. Type &obj in the Address box. Set 8 or 16 columns.
  3. Split the bytes by offset. Mark where each member starts.
  4. Read each member with the right rule: little-endian integers, float bits, a pointer (follow it by typing it into a second Memory window), padding to skip.
  5. Check against the Locals window. Once your reading matches, you understand the layout.

Try it on this object:

C++
struct Item
{
    const char* name;     // 0
    float weight;         // 8
    std::int32_t count;   // 12
    bool stackable;       // 16, then 7 bytes of tail padding
};
Output
0x0000004F8C8FF8A0  e8 4c 2b a1 f6 7f 00 00  00 00 00 3f 0c 00 00 00
0x0000004F8C8FF8B0  01 cc cc cc cc cc cc cc
  • Bytes 0 to 7: e8 4c 2b a1 f6 7f 00 00 is the pointer 0x00007FF6A12B4CE8: in the program's image, so name points at a string literal in .rdata.
  • Bytes 8 to 11: 00 00 00 3f is the float 0.5.
  • Bytes 12 to 15: 0c 00 00 00 is 12.
  • Byte 16: 01 is true.
  • Bytes 17 to 23: cc, tail padding in a Debug build.

Common mistakes

Reading pointers byte by byte

Switch the window to 8-byte integers in hexadecimal and the pointers read naturally, already reversed into the right order.

Forgetting the window keeps the old address

When you step into a different function, the window still shows the same address, which may now belong to a different frame. Use Reevaluate automatically, or type the expression again.

Treating every 4-byte group as an int

Positions and speeds are usually floats. If an "int" is a huge number like 1,065,353,216, try reading it as a float: that one is 1.0.

  4. Why do user-mode pointers on x64 Windows always end in 00 00 in memory?

    Only the lower 47 bits of an address are used, so the top two bytes are zero, and little-endian puts them last The highest bytes of the value come last in memory, and for user-mode addresses they are zero.
