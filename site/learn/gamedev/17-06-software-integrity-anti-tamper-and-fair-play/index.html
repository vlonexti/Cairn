Software Integrity, Anti-Tamper and Fair Play

lesson 17.066 of 8 in milestone 177 min1 practice task

This course taught how programs look from the inside, which is also how cheats and tampering work. This lesson takes the defender's side: why a game can never fully trust the client, why server authority is the foundation of fair online play, how to verify the integrity of your own files and updates with hashes and code signing, what client-side anti-tamper can and cannot do, and the legal, ethical and privacy limits that apply to both sides.

The client is in the player's hands

Every technique in chapters 5 to 16 works on a program running on your own machine: reading its memory, changing its code, injecting a DLL, inspecting its traffic. A player can do all of that to a game on their machine. That leads to the most important rule of game security:

Never trust the client

Anything that runs on the player's computer can be read and changed by the player. Decisions that affect other players must be made, or at least checked, somewhere the player does not control.

Client-side protection can make tampering slower and more obvious; it cannot make it impossible. Fair play in online games rests on design first and detection second.

Server authority

In an authoritative server design, clients send inputs ("move forward", "fire at this direction") and the server runs the simulation and decides the results. A modified client can still send inputs, but it cannot directly set its health, teleport, or award itself a score.

sequenceDiagram
    participant C as Client
    participant S as Server (authoritative)
    C->>S: input: move right, tick 1042
    S->>S: validate: speed, collisions, cooldowns
    S->>S: simulate the tick
    S-->>C: state: position, health, events
    Note over C: the client predicts locally for smoothness,<br/>then corrects to the server's state

What the server validates:

Check Example
Physics limits A move longer than maximum speed times elapsed time is clamped or rejected (the practice task)
Rates and cooldowns No more shots than the weapon's fire rate allows
Visibility The server sends a player only what that player could legitimately see, so there is nothing hidden in memory to reveal
Game rules Items can only be used if owned; doors only opened if unlocked
Plausibility over time Statistics that are consistently beyond human limits are flagged for review, never banned automatically

For single-score games like Delve's leaderboard, the equivalent is submitting a replay (the seed and the inputs) instead of a score; the server re-simulates it deterministically and computes the score itself (the leaderboard threat in lesson 17.05).

Integrity of your own files

Separately from cheating, you need to know the code and data you ship are the code and data that run, and that updates come from you:

  • Hash manifests: a list of every shipped file with its SHA-256 hash. The launcher or updater checks files against it, which catches corruption and incomplete updates (lesson 3.08's checksums, made cryptographic).
  • Code signing: an Authenticode signature on your executables and DLLs (and the manifest) proves who published them and that they were not changed. Windows shows the publisher and SmartScreen builds reputation from it; drivers must be signed to load at all (lesson 16.01).
  • Signed updates: an updater verifies the signature of a downloaded update before installing it, so a compromised download server cannot push malicious code.
  • Safe loading: load DLLs only from your own folder with full paths (lesson 13.04), so a planted DLL is not picked up instead.

What client-side anti-tamper does

Commercial games add protection on the client. Understanding its purpose, at a high level, helps you design around it and judge its trade-offs:

Measure Purpose Limit
Integrity checks of the game's own code and data Detect modified files or patched code Runs on the same machine it is protecting
Obfuscation Make analysis (chapter 9) slower Slows, never prevents
Detecting debuggers and injected modules Notice the tools of chapters 8 and 13 False positives on legitimate software
Kernel-mode components Observe from a more privileged level Very high trust demanded from players; a driver bug crashes their machine (chapter 16)

The cost side matters: kernel-level anti-cheat asks players to trust your code with full control of their computer, and some players reasonably refuse. Collect only what is needed, document what is collected, and remove the component when the game is uninstalled.

The rules for both sides

  • Terms of service and the law apply. Modifying or analysing a game you do not own can break its licence, and creating or selling cheats for online games has led to lawsuits. Cheating in online games harms other players, and this course does not teach it.
  • Fair-play enforcement must be fair: decisions reviewed by humans, an appeal process, and evidence kept (the repudiation row in 17.05).
  • Privacy: anti-cheat that scans the player's machine is handling personal data and falls under laws such as the GDPR.
  • Single-player modding is a different matter: it harms no one, and many developers support it with official tools (chapter 13).

Common mistakes

Trusting client-reported results

"The client says it hit for 9999 damage" must never be believed.

Sending hidden information to clients

If the client receives every enemy position, a modified client can show them. Send only what can be seen.

Relying on obfuscation instead of design

Obfuscation buys time. Server authority removes whole classes of cheats.
