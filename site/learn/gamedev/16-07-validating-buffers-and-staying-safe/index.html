Validating Buffers and Staying Safe

lesson 16.077 of 10 in milestone 166 min1 practice task

A driver that accepts requests from user mode is a doorway into the kernel, and many serious Windows vulnerabilities have been driver bugs in exactly this code. This lesson covers the three ways buffers reach a driver (buffered, direct and neither I/O), and the rules that keep a driver safe: check every length, never return more than was written, never leak kernel memory, and handle every failure.

Why this matters

Lesson 15.02 explained that the kernel never trusts user mode. A driver's dispatch routines are kernel code run with user-supplied inputs: lengths, control codes and buffer contents chosen by whoever opened the device. A bug that lets a caller read or write memory it should not becomes a way to take over the machine. Vulnerable drivers are a well-known attack route, which is why Windows maintains a blocklist of known-vulnerable signed drivers and why Microsoft's signing process includes testing (lesson 16.09). Writing this code carefully is not optional.

Three ways to pass buffers

The method in the control code (lesson 16.05) decides how the I/O manager presents the caller's buffers:

Method What the driver gets Safety
METHOD_BUFFERED One system buffer in non-paged pool, max(input, output) bytes. The I/O manager copies the input in before the call and copies Information bytes out after Safest: the driver never touches user memory. Best for small requests
METHOD_IN_DIRECT / METHOD_OUT_DIRECT Input in a system buffer; the output (or second) buffer described by an MDL whose pages the I/O manager has probed and locked (lesson 15.04) Safe, avoids copying large data
METHOD_NEITHER The raw user pointers The driver must probe, capture and guard every access itself (lesson 15.02's three rules). Avoid unless there is a strong reason

The echo driver uses METHOD_BUFFERED throughout, and so should yours unless measurements show copying is too slow.

The rules for every request

  1. Check every length before touching any buffer. Input at least as large as the structure you will read; output at least as large as what you will write. Return STATUS_BUFFER_TOO_SMALL (or STATUS_INVALID_PARAMETER) otherwise.
  2. Treat every field read from the input as hostile. Counts, sizes, offsets and indices inside the request get the same checks as the lengths, including overflow in arithmetic (count * sizeof(T) can wrap, lesson 15.02).
  3. Set Information to exactly the number of bytes written, never more than the output length. With buffered I/O, the I/O manager copies Information bytes from the system buffer back to the caller; a larger number copies out whatever else is in that pool memory: an information leak.
  4. Never leak kernel memory. Zero output structures before filling them (padding bytes too, lesson 2.05). ExAllocatePool2 zero-initialises, which is one reason it replaced the older function (lesson 15.04).
  5. Handle every failure. Allocations can fail; return STATUS_INSUFFICIENT_RESOURCES. Never assume.
  6. Keep the state consistent across processors. Requests can arrive on several processors at once (lesson 15.06): protect shared state.

The echo handler, carefully

C++
NTSTATUS EchoEcho(EchoState* state, PIRP irp, const auto& p, ULONG_PTR& information)
{
    const ULONG in{ p.InputBufferLength };
    const ULONG out{ p.OutputBufferLength };
    if (in == 0) return STATUS_INVALID_PARAMETER;
    if (in > kMaxEchoBytes) return STATUS_INVALID_PARAMETER;      // a limit protects the pool
    if (out < in) return STATUS_BUFFER_TOO_SMALL;                  // we will write exactly `in` bytes

    // Buffered I/O: input and output share the system buffer, and the input is already there.
    // Echoing means leaving it in place and reporting that many bytes as output.
    information = in;                                              // never more than out

    InterlockedIncrement64(&state->stats.requests);
    InterlockedAdd64(&state->stats.bytesEchoed, in);
    return STATUS_SUCCESS;
}

Every number that comes from the caller (in, out) is checked before it is used; the output count is exactly what is valid; the shared statistics use interlocked operations. The practice task writes the general validator that checks a request against these rules.

Tools that help

  • Driver Verifier (lesson 15.07) with I/O verification catches IRPs completed wrongly and leaks.
  • Code Analysis for drivers (lesson 16.01) and its annotations (_In_reads_bytes_, _IRQL_requires_max_) find length and IRQL mistakes at build time.
  • Fuzzing the IOCTL interface from user mode with random codes, lengths and contents (lesson 17.03) finds what review misses. Run it in the lab VM, with Verifier on.

Common mistakes

Reading the input before checking its length

Even one field read from a too-short buffer reads past it.

[!warning] Information larger than what was written Leaks pool contents to user mode.

[!warning] METHOD_NEITHER without probing, capturing and guarding A classic source of exploitable driver bugs. Prefer buffered I/O.

Trusting sizes inside the request

A count field in the request is as untrusted as the buffer length.
