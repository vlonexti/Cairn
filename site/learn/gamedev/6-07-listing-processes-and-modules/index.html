Listing Processes and Modules

lesson 6.077 of 9 in milestone 65 min

Task Manager, Process Explorer and every debugger start by asking Windows "what is running?". This lesson uses the Tool Help API to list running processes and the modules loaded in your own process, the building block of crash reporters, launchers that check whether the game is already open, and the tools in chapter 12.

Snapshots

The Tool Help API works in two steps: take a snapshot of some part of the system, then walk through it. A snapshot is a copy taken at one moment, so it does not change while you read it (processes that start or end afterwards are not reflected).

Snapshot flag Lists
TH32CS_SNAPPROCESS Every running process
TH32CS_SNAPTHREAD Every thread in the system
TH32CS_SNAPMODULE The modules (exe and DLLs) of one process

Listing processes

C++
#include <windows.h>
#include <tlhelp32.h>
#include <iostream>
#include <string>

int main()
{
    HANDLE snapshot{ CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0) };
    if (snapshot == INVALID_HANDLE_VALUE) return 1;

    PROCESSENTRY32W entry{};
    entry.dwSize = sizeof(entry);                  // must be set before the first call
    int count{ 0 };
    bool sawMyself{ false };
    for (BOOL more{ Process32FirstW(snapshot, &entry) }; more; more = Process32NextW(snapshot, &entry))
    {
        ++count;
        if (entry.th32ProcessID == GetCurrentProcessId()) sawMyself = true;
        // entry.szExeFile is the file name, entry.th32ParentProcessID the parent, entry.cntThreads the thread count
    }
    CloseHandle(snapshot);
    std::cout << "found " << (count > 1 ? "several" : "too few") << " processes, including this one: " << (sawMyself ? "yes" : "no") << '\n';
    return 0;
}
Output
found several processes, including this one: yes

Each PROCESSENTRY32W gives the process id, its parent's id, its thread count and its executable's file name (not the full path). To learn more (the full path, memory use, start time) you open the process by id with OpenProcess asking for PROCESS_QUERY_LIMITED_INFORMATION, which Windows grants for almost every process, and call functions such as QueryFullProcessImageNameW (lesson 6.01) or GetProcessTimes.

A common real use: a game launcher or the game itself checking whether another copy is already running before starting a second one. (The more robust way to enforce "one copy only" is a named mutex: CreateMutexW(nullptr, FALSE, L"MyGame.SingleInstance"), then check whether GetLastError() returned ERROR_ALREADY_EXISTS.)

Listing your own modules

C++
#include <windows.h>
#include <tlhelp32.h>
#include <iostream>
#include <string>

int main()
{
    HANDLE snapshot{ CreateToolhelp32Snapshot(TH32CS_SNAPMODULE, GetCurrentProcessId()) };
    if (snapshot == INVALID_HANDLE_VALUE) return 1;

    MODULEENTRY32W module{};
    module.dwSize = sizeof(module);
    bool kernel32{ false };
    int count{ 0 };
    for (BOOL more{ Module32FirstW(snapshot, &module) }; more; more = Module32NextW(snapshot, &module))
    {
        ++count;
        if (_wcsicmp(module.szModule, L"kernel32.dll") == 0) kernel32 = true;
        // module.modBaseAddr is where it is loaded, module.modBaseSize its size, module.szExePath its full path
    }
    CloseHandle(snapshot);
    std::cout << "modules loaded: " << (count > 3 ? "many" : "few") << ", kernel32.dll among them: " << (kernel32 ? "yes" : "no") << '\n';
    return 0;
}
Output
modules loaded: many, kernel32.dll among them: yes

Each MODULEENTRY32W gives a module's base address and size, exactly the ranges lesson 6.04's VirtualQuery walk found as MEM_IMAGE regions. Combining them turns any code address into "module + offset", the form crash reports use (lesson 6.09).

A crash report's module list

When a game crashes, a useful report says not just "crashed at 0x00007FF6A1235F10" but "crashed in game.exe at offset 0x35F10", together with the list of loaded modules and their versions. With that, a developer can open the matching build's .pdb and find the exact source line, even though addresses differ on the player's machine. Chapter 8 builds this with crash dumps; the module list above is half of it.

Rights and limits

Listing names and ids of all processes needs no special rights. Opening other processes for more than limited information, or listing their modules, requires access rights that Windows grants only for processes running as the same user and at the same or lower integrity level, and never for protected processes (next lesson). Tools in this course look at processes you start yourself.

Common mistakes

[!warning] Forgetting to set dwSize Process32FirstW fails if the structure's size field is not set first.

Treating a process name as unique

Many processes can have the same file name. Use the process id, and check the full path if it matters.

Holding on to a PID for a long time

When a process ends, its id can be reused by a new, unrelated process. Hold a process handle instead if you need to keep referring to it.
