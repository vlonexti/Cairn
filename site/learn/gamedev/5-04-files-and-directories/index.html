Files and Directories

lesson 5.044 of 9 in milestone 56 min1 practice task

Games read assets and configuration and write save files and logs. This lesson uses the Windows file API directly (CreateFileW, ReadFile, WriteFile), shows where a game should keep its files, how to list a directory, how to save without ever leaving a half-written file, and when the portable std::filesystem and std::fstream are the better choice.

Opening a file

Every file operation starts with CreateFileW, which both creates new files and opens existing ones despite its name:

C++
HANDLE file{ CreateFileW(
    L"settings.ini",            // path
    GENERIC_READ,               // what you want to do: GENERIC_READ, GENERIC_WRITE or both
    FILE_SHARE_READ,            // what others may do while you have it open
    nullptr,                    // security attributes: default
    OPEN_EXISTING,              // what to do if it exists or not (see below)
    FILE_ATTRIBUTE_NORMAL,      // flags
    nullptr) };                 // template file: unused

The creation disposition decides what happens depending on whether the file exists:

Value If it exists If it does not
OPEN_EXISTING Open it Fail (error 2)
CREATE_NEW Fail (error 80) Create it
CREATE_ALWAYS Truncate it to empty Create it
OPEN_ALWAYS Open it Create it
TRUNCATE_EXISTING Truncate it Fail

The share mode is often overlooked. It says what other handles may do to the file while yours is open. With 0, no one else can even read it, and they get ERROR_SHARING_VIOLATION (32). That is why a game that holds its log file open with share mode 0 stops you viewing the log while it runs.

Reading and writing

C++
#include <windows.h>
#include <iostream>
#include <string>
#include <vector>

int main()
{
    wchar_t tempDir[MAX_PATH]{};
    GetTempPathW(MAX_PATH, tempDir);
    const std::wstring path{ std::wstring{ tempDir } + L"xenon_demo_save.txt" };

    // Write
    HANDLE out{ CreateFileW(path.c_str(), GENERIC_WRITE, 0, nullptr, CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, nullptr) };
    if (out == INVALID_HANDLE_VALUE) { std::cout << "create failed " << GetLastError() << '\n'; return 1; }
    const std::string text{ "level=4\ngold=1250\n" };
    DWORD written{ 0 };
    WriteFile(out, text.data(), static_cast<DWORD>(text.size()), &written, nullptr);
    CloseHandle(out);

    // Read it back
    HANDLE in{ CreateFileW(path.c_str(), GENERIC_READ, FILE_SHARE_READ, nullptr, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, nullptr) };
    if (in == INVALID_HANDLE_VALUE) { std::cout << "open failed " << GetLastError() << '\n'; return 1; }
    LARGE_INTEGER size{};
    GetFileSizeEx(in, &size);
    std::vector<char> buffer(static_cast<std::size_t>(size.QuadPart));
    DWORD read{ 0 };
    ReadFile(in, buffer.data(), static_cast<DWORD>(buffer.size()), &read, nullptr);
    CloseHandle(in);
    DeleteFileW(path.c_str());

    std::cout << "wrote " << written << " bytes, read " << read << ":\n" << std::string(buffer.data(), read);
    return 0;
}
Output
wrote 18 bytes, read 18:
level=4
gold=1250

Note the DWORD out parameters: WriteFile and ReadFile report how many bytes they actually moved. A ReadFile that returns success with read == 0 means end of file. A read can also return fewer bytes than asked (for pipes and network files especially), so code that needs an exact amount loops until it has it.

Where a game should put its files

The folder the .exe is in (C:\Program Files\...) is read-only for normal users. Writing saves there fails with ERROR_ACCESS_DENIED, or worse, gets silently redirected by compatibility shims. Windows provides per-user folders, found with SHGetKnownFolderPath:

Folder Known folder id Typical path For
Saved Games FOLDERID_SavedGames C:\Users\name\Saved Games Save files
Local AppData FOLDERID_LocalAppData C:\Users\name\AppData\Local Settings, caches, logs
Roaming AppData FOLDERID_RoamingAppData ...\AppData\Roaming Settings that follow the user between PCs on a domain
Documents FOLDERID_Documents C:\Users\name\Documents Things the user made and wants to find, such as screenshots
C++
#include <shlobj.h>
#pragma comment(lib, "shell32.lib")

std::wstring savedGamesFolder()
{
    PWSTR path{ nullptr };
    std::wstring result;
    if (SUCCEEDED(SHGetKnownFolderPath(FOLDERID_SavedGames, 0, nullptr, &path))) result = path;
    CoTaskMemFree(path);                 // the documentation says to free it this way
    return result + L"\\MyGame";
}

Saving safely

If the game crashes, or the power goes, halfway through writing a save file, the player loses their save. The standard technique: write to a temporary file, then replace the real one in a single step.

  1. Write the whole save to slot1.sav.tmp.
  2. Call FlushFileBuffers and close it, so the data is on disk.
  3. MoveFileExW(L"slot1.sav.tmp", L"slot1.sav", MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH), or ReplaceFileW.

At every moment, either the old complete save or the new complete save is on disk, never a broken mixture.

Listing a directory

C++
#include <windows.h>
#include <iostream>

int main()
{
    WIN32_FIND_DATAW entry{};
    HANDLE find{ FindFirstFileW(L"C:\\Windows\\*.exe", &entry) };
    if (find == INVALID_HANDLE_VALUE) return 1;
    int count{ 0 };
    do
    {
        if (!(entry.dwFileAttributes & FILE_ATTRIBUTE_DIRECTORY)) ++count;
    } while (FindNextFileW(find, &entry));
    FindClose(find);                     // not CloseHandle: find handles have their own close function
    std::cout << "found " << (count > 0 ? "some" : "no") << " programs\n";
    return 0;
}
Output
found some programs

The portable alternative

For ordinary game files, the C++ standard library is simpler and works on every platform:

C++
#include <filesystem>
#include <fstream>
namespace fs = std::filesystem;

for (const auto& entry : fs::directory_iterator{ "levels" })
    if (entry.path().extension() == ".lvl") loadLevel(entry.path());

std::ofstream log{ fs::path{ "logs" } / "game.log", std::ios::app };

On Windows, std::filesystem::path stores UTF-16 internally and calls the W functions, so it handles any characters correctly. Use the Windows API directly when you need what the standard library does not expose: share modes, overlapped (asynchronous) I/O, memory-mapped files (chapter 12), file change notifications, or exact error codes.

Common mistakes

[!warning] Writing next to the .exe It works on your machine because you are an administrator or the game is in your own folder. On players' machines it fails. Use Saved Games or AppData.

Overwriting a save in place

A crash mid-write destroys it. Write a temporary file and replace atomically.

Share mode 0 on files others need to read

Logs and config files should usually allow FILE_SHARE_READ.

[!warning] Assuming one ReadFile reads everything Check the bytes-read count, and loop when you need an exact amount.

    • OPEN_ALWAYS
    • OPEN_EXISTING

  2. Another program cannot open your game's log while the game runs, getting error 32. Why?
    • The game opened the file with a share mode that does not allow reading
    • The log file is too large
    • Windows locks all files a game opens
    Show the answer

    The game opened the file with a share mode that does not allow reading Error 32 is a sharing violation: the existing handle's share mode forbids it.

  3. Why should save files not be written to the game's installation folder?
    • Under Program Files it is read-only for normal users
    • Windows deletes files there on restart
    • It is slower
    Show the answer

    Under Program Files it is read-only for normal users Use the per-user Saved Games or AppData folders.

  4. How do you update a save file so a crash can never leave it half-written?
    • Write a temporary file completely, then replace the real file with it in one step
    • Write the new save in small pieces
    • Delete the old file first, then write the new one
    Show the answer

    Write a temporary file completely, then replace the real file with it in one step The move or replace is atomic: the file is always either the old version or the new one.
