Reading the Source of an Open-Source Game

lesson 10.099 of 9 in milestone 105 min

One of the best ways to learn engine architecture is to read a real one. Many shipped games and engines have released their source. This lesson is a method for approaching a large, unfamiliar codebase: building it, finding the main loop, tracing one feature end to end, and recognising the patterns from this chapter in someone else's code.

Why read real code

Everything in this chapter (the loop, time steps, entities, rendering, input, resources, saves, scripting) exists in every shipped game, solved under real constraints. Reading how experienced teams did it shows trade-offs no tutorial covers: what they simplified, what they optimised, which corners they cut to ship.

Where to find source

Project Notes
id Software's games (Doom, Quake, Quake III Arena) Released under the GPL; small, clear C codebases, widely studied
OpenTTD, Wesnoth, SuperTuxKart, Cataclysm: DDA Large open-source games in C++, actively developed
Godot A complete open-source engine in C++
raylib A small, very readable C library for games (used in the planned raylib course)
Dear ImGui The interface library of chapter 14, a famously readable single codebase

Respect each project's licence: reading and learning is always fine; reusing code in your own project means following the licence's terms.

A method

1. Build and run it

Clone the repository, follow its build instructions, and get it running under your debugger. A codebase you can run and step through is ten times easier to understand than one you can only read. Note what you had to install: the dependencies are a first map of the architecture.

2. Map the top level

Look at the folder structure and the largest directories. Typical names: engine, game, render/gfx, audio/snd, net, ui, script, tools, platform/sys. Write a one-line guess for each and correct it later.

3. Find the main loop

Search for the entry point (main, WinMain, wWinMain, or the platform layer's equivalent), then step into it with the debugger until you reach the loop that runs every frame. Note what it calls each frame and in which order: that is lesson 10.01's diagram for this engine. Quake III, for example, has Com_Frame doing exactly input, events, server frame, client frame and rendering.

4. Trace one feature end to end

Pick something small and visible: what happens when the player presses fire, picks up an item or opens a door. Follow it from input to effect:

flowchart LR
    I["Key press"] --> B["Binding / command"]
    B --> G["Game logic<br/>(weapon fires)"]
    G --> E["Entity created<br/>(projectile)"]
    E --> R["Rendered and<br/>heard (sound)"]

Use the tools you have: search for the string on screen or in the console, set breakpoints, use the IDE's "find all references" (Shift+F12 in Visual Studio) and "go to definition" (F12), and the call stack at each breakpoint.

6. Write it down

Keep notes as you go: a diagram of the main systems, the frame's order of calls, the path of your traced feature. Explaining the architecture in a page of your own words is the test of whether you understood it.

Common mistakes

Reading files top to bottom

Large codebases are read by following execution, not alphabetically.

Trying to understand everything

Pick one feature and follow it; the rest will become familiar along the way.

Not running it

Reading without a debugger leaves you guessing which code actually runs.
