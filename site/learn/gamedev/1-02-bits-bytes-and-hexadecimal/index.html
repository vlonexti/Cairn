Bits, Bytes and Hexadecimal

lesson 1.022 of 8 in milestone 115 min3 practice tasks

Memory holds only bits, switches that are on or off. Eight bits make a byte, and hexadecimal is a shorthand that writes a byte as two digits. Once you can read hexadecimal, a screen full of memory stops looking like noise.

Only two symbols

The last lesson said that every memory cell holds a number. Electrically, a computer stores numbers using parts that have two steady states: charged or not, on or off. One such switch is a bit, and it can hold a 0 or a 1.

One bit is not much use. A row of them is, in the same way that a single decimal digit only counts to 9 but a row of digits can write any number.

Counting with place values

In the decimal number 345, each position is worth ten times the one to its right: 3 hundreds, 4 tens, 5 ones. Binary works the same way, except each position is worth two times the one to its right.

Position 7 6 5 4 3 2 1 0
Worth 128 64 32 16 8 4 2 1

To read a binary number, add up the worth of every position that holds a 1. So 0100 1101 is 64 + 8 + 4 + 1, which is 77.

Things to try:

  • Switch every bit off, then make 200. Start from the left: is 128 needed? Then 64? Keep going.
  • Switch every bit on. That is 255, the largest value eight bits can hold.
  • Press << 1 a few times with only the rightmost bit on. Each shift left doubles the value, just as adding a zero to the end of a decimal number multiplies it by ten.
  • With 255 showing, press + 1. There is no ninth bit to carry into, so the value wraps round to 0.

Bytes, and how many values fit

Eight bits make a byte. The byte is the unit that memory is measured and numbered in: when the last lesson talked about memory cells, each cell of a real computer is one byte.

Every extra bit doubles the number of different values a group of bits can hold.

Bits Bytes Different values Largest unsigned value
8 1 256 255
16 2 65,536 65,535
32 4 4,294,967,296 about 4.29 billion
64 8 about 18.4 quintillion about 1.8 × 10¹⁹

A value that needs more than one byte simply uses several bytes next to each other. This is where C++ types come from: a type says how many bytes a value takes and how to interpret them.

C++
#include <iostream>

int main()
{
    std::cout << "char:      " << sizeof(char) << '\n';
    std::cout << "short:     " << sizeof(short) << '\n';
    std::cout << "int:       " << sizeof(int) << '\n';
    std::cout << "long long: " << sizeof(long long) << '\n';
    std::cout << "float:     " << sizeof(float) << '\n';
    std::cout << "double:    " << sizeof(double) << '\n';
    std::cout << "int*:      " << sizeof(int*) << '\n';
    return 0;
}
Output
char:      1
short:     2
int:       4
long long: 8
float:     4
double:    8
int*:      8

sizeof gives the size of a type in bytes. These are the sizes on 64-bit Windows, which is what this course targets.

When the exact size matters, say so

C++ only promises minimum sizes for int and its relatives. The header <cstdint> provides types with the size in the name: std::uint8_t is exactly one unsigned byte, std::int32_t exactly four signed bytes, std::uint64_t exactly eight unsigned bytes. Low-level code uses these whenever it is describing memory precisely.

Hexadecimal: four bits per digit

Binary is what the machine uses, but it is hard on the eyes. 1011 1110 1110 1111 is sixteen digits for one small number. Decimal is shorter, but there is no tidy relationship between decimal digits and bits.

Hexadecimal (base 16, "hex" for short) fixes both problems. It has sixteen digits: 0 to 9, then A to F for the values ten to fifteen.

Hex Binary Decimal Hex Binary Decimal
0 0000 0 8 1000 8
1 0001 1 9 1001 9
2 0010 2 A 1010 10
3 0011 3 B 1011 11
4 0100 4 C 1100 12
5 0101 5 D 1101 13
6 0110 6 E 1110 14
7 0111 7 F 1111 15

Sixteen is 2 × 2 × 2 × 2, so one hex digit is exactly four bits. That is the whole reason hexadecimal is used. A byte is always two hex digits, a 32-bit value is always eight, and you can convert between hex and binary one digit at a time without doing any arithmetic.

Hexadecimal numbers are written with 0x in front so they cannot be mistaken for decimal. 0x10 is sixteen, not ten. C++ accepts the same notation, and 0b for binary:

C++
#include <iostream>

int main()
{
    int a{ 0xFF };          // hexadecimal: 255
    int b{ 0b1111'1111 };   // binary: 255. The ' is only there to make it readable
    int c{ 255 };           // decimal
    std::cout << a << ' ' << b << ' ' << c << '\n';
    return 0;
}
Output
255 255 255

All three lines store exactly the same bits. Hexadecimal, binary and decimal are three ways of writing a number. The number in memory is the same whichever one you use.

Reading hex without a calculator

You will read a great deal of hexadecimal in this course, in debuggers, memory views and assembly listings. A few landmarks make it quick.

Hex Decimal Worth remembering because
0x0A 10 A is ten
0x10 16 One "sixteen"
0x20 32 The space character
0x41 65 The letter A
0x7F 127 Largest positive value of a signed byte
0xFF 255 A byte with every bit on
0x100 256 One more than a byte can hold
0x1000 4,096 The size of a page of memory, as chapter 6 explains

Adding in hex works like decimal, carrying at sixteen instead of ten. 0x1000 + 0x24 is 0x1024. 0x0F + 0x01 is 0x10. You will do sums like these whenever you work out where something sits in memory.

Negative numbers: two's complement

Bits have no minus sign, so negative numbers need a convention. Every modern computer uses two's complement. In a signed type, the leftmost bit is worth minus its usual amount. In a signed byte, the bits are worth:

Position 7 6 5 4 3 2 1 0
Worth −128 64 32 16 8 4 2 1

So 1111 1111 is −128 + 127, which is −1, and a signed byte runs from −128 to 127.

The explorer shows both readings of the same bits. Look at the Unsigned and Signed lines.

  • With all bits on, the unsigned reading is 255 and the signed reading is −1. The bits did not change. The interpretation did.
  • To negate a number in two's complement: flip every bit, then add one. Set the value to 5, press Invert, then + 1, and the signed reading is −5.
  • Press − 1 from 0. The unsigned reading jumps to 255 and the signed reading says −1. Both are correct descriptions of the same bits.

This is why a type has to say whether it is signed. signed char and unsigned char hold identical bits and disagree about what half of them mean.

Overflow

A type has a fixed number of bits, so there is a largest value it can hold. Going past it does not produce an error. With unsigned types the value wraps round, exactly as you saw when 255 + 1 became 0.

C++
#include <cstdint>
#include <iostream>

int main()
{
    std::uint8_t health{ 250 };
    health = static_cast<std::uint8_t>(health + 10);   // 260 does not fit in 8 bits
    std::cout << static_cast<int>(health) << '\n';

    std::uint8_t lives{ 0 };
    lives = static_cast<std::uint8_t>(lives - 1);      // below zero wraps to the top
    std::cout << static_cast<int>(lives) << '\n';
    return 0;
}
Output
4
255

Healing a character from 250 health left it with 4. Taking a life from a player with none gave them 255. Both are real categories of game bug, and both come from forgetting that a type has edges.

Signed overflow is worse than wrapping

For unsigned types, C++ guarantees the wrap-around. For signed types such as int, going past the largest value is undefined behaviour: the language makes no promise about what happens, and compilers are allowed to assume it never does. Do not rely on signed numbers wrapping.

Byte order: which end comes first

A 32-bit value takes four bytes, and those four bytes sit in four neighbouring memory cells. There are two sensible orders to store them in, and processors do not all agree.

Interactive demo. This part of the lesson is a working model you can step through in Xenon. Try it in Xenon

The processors in PCs are little-endian: the lowest-value byte goes at the lowest address. So the number you would write as 0x12345678 sits in memory as the bytes 78 56 34 12.

This matters every time you look at raw memory. If a memory view shows E8 03 00 00 and you know an int lives there, you read the bytes back to front to get 0x000003E8, which is 1000. It looks backwards at first and becomes automatic with practice.

Switch the demonstration to Big-endian to see the other order. Network protocols and some file formats use it, so code that reads them has to swap the bytes.

Printing numbers in other bases from C++

C++
#include <bitset>
#include <format>
#include <iostream>

int main()
{
    int value{ 200 };
    std::cout << std::format("decimal {}  hex 0x{:02X}  binary {:#010b}\n", value, value, value);
    std::cout << "bitset:   " << std::bitset<8>(value) << '\n';
    std::cout << "literals: " << 0xC8 << ' ' << 0b1100'1000 << '\n';
    return 0;
}
Output
decimal 200  hex 0xC8  binary 0b11001000
bitset:   11001000
literals: 200 200

In std::format, {:02X} means hexadecimal in capitals, at least two digits, padded with zeros. {:#010b} means binary with the 0b prefix, ten characters wide in all. std::bitset<8> prints exactly eight bits.

Common mistakes

Reading a hex number as decimal

0x10 is sixteen. 0x64 is one hundred. If a number in a debugger looks odd, check which base the window is showing. Visual Studio can switch between them with a right-click.

Forgetting byte order when reading memory

In a memory view, multi-byte values appear lowest byte first. 01 00 00 00 is the int 1, not sixteen million.

Assuming a type's size

int is 4 bytes on the systems this course uses, but the language only promises "at least 2". Use sizeof to check, and the <cstdint> types when the size is part of what you mean.

Mixing signed and unsigned

Comparing a signed value with an unsigned one converts the signed value first, so −1 becomes a very large number. The compiler warns about this. Take the warning seriously.

Mixing up 1000 and 1024

A kilobyte in memory sizes is usually 1,024 bytes (0x400), because memory is counted in powers of two. Disk makers use 1,000. When exactness matters, write the number of bytes.

    • 65
    • 129
    Show the answer

    65 The bits that are on are worth 64 and 1. In hexadecimal the same byte is 0x41, which is where the wrong answer 41 comes from.

  2. Why is hexadecimal used instead of decimal when looking at memory?
    • It can store larger numbers
    • Computers calculate in hexadecimal internally
    • Each hex digit stands for exactly four bits, so a byte is always two digits
    Show the answer

    Each hex digit stands for exactly four bits, so a byte is always two digits Hexadecimal is only a way of writing numbers. Its advantage is the exact fit: four bits per digit, two digits per byte.

  3. A signed byte holds the bits 1111 1111. What value is that?
    • 255
    • -1
    • -127
    Show the answer

    -1 In two's complement the top bit is worth -128, and the other seven add up to 127. Read as unsigned, the same bits are 255.

  4. An int on a PC holds the value 0x0A0B0C0D. In what order do its bytes sit in memory, from the lowest address up?
    • 0A 0B 0C 0D
    • 0D 0C 0B 0A
    • D0 C0 B0 A0
    Show the answer

    0D 0C 0B 0A PCs are little-endian: the lowest byte is stored first. The digits inside each byte are not reversed, only the order of the bytes.

  5. A std::uint8_t holds 200 and the program adds 100 to it. What does it hold now?
    • 300
    • 255
    • 44
    Show the answer

    44 300 does not fit in eight bits, so it wraps: 300 - 256 = 44. Unsigned arithmetic always wraps round like this.
