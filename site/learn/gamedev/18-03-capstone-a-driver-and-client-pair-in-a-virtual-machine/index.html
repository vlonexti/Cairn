Capstone: A Driver and Client Pair in a Virtual Machine

lesson 18.033 of 4 in milestone 187 min1 practice task

The third capstone grows chapter 16's echo driver into XenonLog, a small, well-engineered driver and client pair that runs only in your lab virtual machine. The driver keeps a bounded in-kernel message log that clients append to and read back through versioned IOCTLs; the client is an ImGui tool with live statistics. The emphasis is engineering quality: validation, locking at the right IRQL, Driver Verifier, a fuzzing client, kernel debugging and a written design.

What you are building

XenonLog is a teaching driver: it does nothing a user-mode program could not, which is exactly why it is a good capstone. All the difficulty is in doing it correctly in kernel mode.

  • The driver (XenonLog.sys) creates \Device\XenonLog, keeps a ring buffer of up to 256 messages of up to 200 bytes each, and supports four control codes: append a message, read messages from a sequence number, get statistics, and clear.
  • The client (XenonLogUI.exe) is an ImGui window that sends messages, shows the log live, plots messages per second, and displays the driver's statistics and version.
  • The fuzzer (XenonLogFuzz.exe) sends random and malformed requests for hours with Driver Verifier enabled.
Lab rules (from chapters 15 and 16)
  • Everything runs in the lab VM from lesson 15.08, with a snapshot taken before every test, test signing on in the VM only, and kernel debugging over the network from the host.
  • The driver touches only its own buffers. It never reads or writes another process's memory, never registers callbacks on other processes or threads, and never hides anything. Those are out of scope for this course.
  • It never ships outside the VM and is never installed on your everyday machine.

The interface

C++
// xenonlog_ioctl.h, shared by the driver and its clients
#define XENONLOG_VERSION        1
#define XENONLOG_MAX_TEXT     200
#define XENONLOG_DEVICE_TYPE  0x8001

#define IOCTL_XENONLOG_APPEND  CTL_CODE(XENONLOG_DEVICE_TYPE, 0x801, METHOD_BUFFERED, FILE_WRITE_DATA)
#define IOCTL_XENONLOG_READ    CTL_CODE(XENONLOG_DEVICE_TYPE, 0x802, METHOD_BUFFERED, FILE_READ_DATA)
#define IOCTL_XENONLOG_STATS   CTL_CODE(XENONLOG_DEVICE_TYPE, 0x803, METHOD_BUFFERED, FILE_READ_DATA)
#define IOCTL_XENONLOG_CLEAR   CTL_CODE(XENONLOG_DEVICE_TYPE, 0x804, METHOD_BUFFERED, FILE_WRITE_DATA)

#pragma pack(push, 8)
struct XenonLogHeader      { UINT32 version; UINT32 size; };                 // every request starts with this
struct XenonLogAppend      { XenonLogHeader h; UINT32 length; CHAR text[XENONLOG_MAX_TEXT]; };
struct XenonLogReadRequest { XenonLogHeader h; UINT64 fromSequence; UINT32 maxMessages; };
struct XenonLogMessage     { UINT64 sequence; LARGE_INTEGER time; UINT32 processId; UINT32 length; CHAR text[XENONLOG_MAX_TEXT]; };
struct XenonLogStats       { XenonLogHeader h; UINT64 appended; UINT64 dropped; UINT64 rejected; UINT32 stored; };
#pragma pack(pop)

Every request carries a header with the interface version and the structure's size, as lesson 12.06 taught for user-mode protocols. The driver rejects a request whose header does not match before reading anything else. The practice task writes that validation as plain C++ that can be unit-tested outside the kernel.

Engineering requirements

Area Requirement From
Validation Check input and output lengths for every code; validate the header; check length <= XENONLOG_MAX_TEXT and that length bytes fit in the input; count rejected requests 16.07, 17.04
Output Zero output buffers before filling; set Information to exactly the bytes written 16.07
Locking Protect the ring buffer with a spin lock or a fast mutex, choosing by the IRQL the code runs at; hold it only while copying 15.06
Memory Allocate the ring buffer once in DriverEntry from non-paged pool with a pool tag; free it in unload 15.04
Access The device's security descriptor allows administrators and the client group only; FILE_READ_DATA and FILE_WRITE_DATA in the control codes 16.04, 6.08
Cleanup Unload deletes the symbolic link and device and frees everything; no leaks reported by Driver Verifier's pool tracking 16.03
Analysis Builds with /W4 /WX and passes Code Analysis with the driver rule set 17.02

Milestones

  1. Design document: a page describing the interface, the ring buffer's behaviour when full (oldest messages dropped and counted), locking, and the threat model from lesson 17.05 for the device interface.
  2. User-mode core: the ring buffer and request validation as plain C++ with unit tests on the host (the practice task covers validation).
  3. Driver skeleton: lesson 16.10's echo driver renamed, with the new device name and the four control codes returning STATUS_NOT_IMPLEMENTED.
  4. Append and read: the ring buffer in the driver, with locking and validation; a command-line client to test.
  5. Statistics and clear.
  6. ImGui client: live log, sending, statistics, a plot, and a clear message when the driver is not loaded.
  7. Verification: Driver Verifier with standard settings plus pool tracking; a kernel debugging session stepping through an append; the fuzzer running for an hour without a bug check.
  8. Write-up: the design document updated with what changed, test results, and one bug you found and how.

Acceptance tests

  • Two clients appending at the same time never corrupt a message (check sequence numbers are unique and continuous).
  • Appending 1000 messages leaves the 256 newest, with dropped equal to 744.
  • A request with the wrong version, a wrong size, length of 201, or a too-small output buffer is rejected with STATUS_INVALID_PARAMETER or STATUS_BUFFER_TOO_SMALL, and rejected increases.
  • The fuzzer runs for an hour with Driver Verifier on and no bug check.
  • Load, use, unload and reload ten times without a leak or bug check.
  • A standard user who is not in the client group cannot open the device.

Stretch goals

  • Rewrite the driver with KMDF and compare the amount of code (lesson 16.10's note).
  • Add an event that the driver signals when new messages arrive, so the client waits instead of polling.
  • Write the ring buffer once and compile the same source into the unit tests and the driver.

Common mistakes

Testing outside the VM

One mistake costs a blue screen on the machine you work on. Use the lab.

Holding a spin lock while calling anything that can wait

At raised IRQL that is an immediate bug check. Copy under the lock, do everything else outside it.

Validating the length field but not that the bytes are there

length must fit inside the input buffer the I/O manager actually passed.
