Kernel Debugging with WinDbg

lesson 16.088 of 10 in milestone 165 min

With WinDbg attached to the lab VM (lesson 15.08), you can break into your driver's code, step through it, and inspect every kernel structure involved in a request. This lesson is a working session: breakpoints on driver load and on dispatch routines, debug output with levels, examining driver and device objects and IRPs with !drvobj, !devobj and !irp, and analysing a bug check your driver caused.

Before you start

  • WinDbg on the host is connected to the VM's kernel (lesson 15.08) and the VM is running.
  • Symbols: .symfix for Microsoft's, plus your build folder for the driver's PDB: .sympath+ C:\code\XenonEcho\x64\Debug, then .reload.
  • Debug output enabled: ed nt!Kd_DEFAULT_Mask 0xF (or for DbgPrintEx with your own component and level, ed nt!Kd_IHVDRIVER_Mask 0xF).

Breaking into your driver

Goal Command
Stop at DriverEntry before the driver is loaded bu XenonEcho!DriverEntry (an unresolved breakpoint, placed when the module loads)
Stop in a dispatch routine bp XenonEcho!EchoDeviceControl
Stop only for one control code Set the breakpoint on a line inside that case (F9 in the source window), rather than on the function
Step over / into / out p / t / gu
Show locals and parameters dv /t
Show the call stack k (kP with parameters)
Continue g
Break in at any time Ctrl+Break

Start the driver in the VM (sc start XenonEcho); WinDbg stops at DriverEntry, and the entire VM freezes while you step through it. Then run the client (lesson 16.06) and stop in EchoDeviceControl for each request.

With the PDB loaded, WinDbg's source window follows along; the Locals and Call Stack panes behave like Visual Studio's (lesson 4.07).

Looking at kernel structures

The ! extensions understand the I/O manager's objects (lesson 15.05):

Output
kd> !drvobj XenonEcho 7
Driver object (ffffa50c1a2b3e30) is for:  \Driver\XenonEcho
Device Object list:  ffffa50c19f0c8a0
...
Dispatch routines:
[00] IRP_MJ_CREATE              fffff8063f5e1010  XenonEcho!EchoCreateClose
[02] IRP_MJ_CLOSE               fffff8063f5e1010  XenonEcho!EchoCreateClose
[0e] IRP_MJ_DEVICE_CONTROL      fffff8063f5e1080  XenonEcho!EchoDeviceControl
...
kd> !devobj ffffa50c19f0c8a0
Device object (ffffa50c19f0c8a0) is for:  XenonEcho \Driver\XenonEcho DriverObject ffffa50c1a2b3e30
Current Irp 00000000 RefCount 1 Type 00008001 Flags 00000040
DevExt ffffa50c19f0c9f0 ...
  • !drvobj shows the driver's devices and, with flag 7, its dispatch table: a quick check that DriverEntry filled it in correctly.
  • !devobj shows a device's reference count (open handles, lesson 16.03), type (your 0x8001) and extension.
  • Inside a dispatch routine, !irp @rdx (the IRP is the second argument, so it is in rdx at the routine's first instruction, lesson 7.06) shows the request: major function, control code, buffer lengths, and the system buffer's address, which db can then dump.
  • dt XenonEcho!EchoState <address> shows your device extension with field names, from the PDB.

A bug check, end to end

Introduce a bug on purpose in the lab driver, for example reading the input header before checking its length in a copy of lesson 16.07's handler, and send it a 1-byte request. With Driver Verifier's special pool on (lesson 15.07), the read past the system buffer faults at once. WinDbg breaks in with the bug check; then:

Fix the check, rebuild, revert the VM to the snapshot if needed, and test again.

Common mistakes

Breakpoints that never hit

Check symbols with lm v m XenonEcho and that the loaded driver is the build whose PDB you gave WinDbg.

Forgetting the debug output mask

KdPrint output is filtered until the mask is set.

Leaving the VM frozen

While stopped in the debugger the whole guest is frozen: continue with g when done.
