What Optimised Code Looks Like

lesson 7.1111 of 11 in milestone 76 min

Release builds rarely look like their source. Functions disappear into their callers, loops are unrolled and vectorised, variables never touch memory, and branches become arithmetic. This lesson is a field guide to the transformations you will meet in optimised disassembly, so that you can map it back to the C++ (or, when reverse engineering, to something like it).

The same function, three ways

C++
int countAlive(const int* health, int n)
{
    int alive{ 0 };
    for (int i{ 0 }; i < n; ++i)
        if (health[i] > 0) ++alive;
    return alive;
}

Debug (/Od): every variable in memory, every line separate, one element per iteration, a real branch for the if. Easy to follow, slow.

Optimised (/O2), roughly:

Assembly
    xor    eax, eax                ; alive = 0
    test   edx, edx
    jle    done
    ; ... (a vectorised loop handles 8 elements at a time here, see below)
scalar:
    cmp    dword ptr [rcx], 0
    setg   r8b                     ; r8b = health[i] > 0 ? 1 : 0   (no branch)
    add    eax, r8d                ; alive += that
    add    rcx, 4                  ; walk a pointer instead of indexing
    dec    edx
    jnz    scalar
done:
    ret

Notice what changed:

  • alive and i live only in registers.
  • The if became setg plus add: branchless code, because whether a monster is alive is unpredictable and a mispredicted branch is costly (lesson 7.04).
  • health[i] became a pointer that moves along (add rcx, 4), and the loop counts down to zero, so dec sets ZF for the jump without a cmp.

The vectorised part, for large n, compares 4 or 8 values at once with pcmpgtd (packed compare greater-than), uses the all-ones result lanes as -1, and subtracts them from a counter vector: eight comparisons and additions per instruction pair, then adds the lanes together at the end.

Field guide

You see It was probably
A call is missing; the callee's body appears inline Inlining: small functions are copied into their callers
A loop body repeated 4 or 8 times per jump Unrolling: fewer jumps, more work per iteration
xmm/ymm packed instructions in integer or float loops Vectorisation (lesson 7.09)
setcc, cmov, sbb, and with -1 masks instead of jumps Branch removal
A constant where you expected arithmetic Constant folding
A multiply by a large odd constant then a shift Division by a constant (lesson 7.03)
lea doing sums and small multiplies Strength reduction (lesson 7.02)
A loop that counts down, or a pointer that advances Induction variable rewriting
jmp to another function at the end instead of call + ret Tail call: the callee returns straight to our caller
Code you wrote is gone entirely Dead code elimination: its result was never used
A function's code shared by several functions with identical bodies Identical COMDAT folding (/OPT:ICF)

Inlining and the missing functions

Inlining matters most for reading. A small getter like int health() const { return m_health; } usually vanishes: the caller simply reads [rcx+0Ch]. Calls to it no longer exist in the program, so a breakpoint in it may never hit, and a reverse engineer sees one large function where the source had ten small ones. With link-time code generation (/GL + /LTCG), functions from different .cpp files can be inlined into each other too.

Tail calls

C++
int damageFor(const Weapon& w, int level) { return scaleDamage(w.baseDamage, level); }
Assembly
damageFor PROC
    mov   ecx, dword ptr [rcx+8]
    jmp   scaleDamage            ; not call: scaleDamage's ret returns to our caller
damageFor ENDP

damageFor has nothing to do after the call, so it jumps instead of calling, and damageFor never appears in the call stack while scaleDamage runs. Debugger call stacks in optimised code can skip frames for this reason.

Reading optimised code well

  1. Find the structure first: loops (backward jumps), calls, returns. Ignore the clever arithmetic until you know what the function's shape is.
  2. Track values, not variables: one C++ variable may live in different registers at different points, and one register may hold different variables.
  3. Expect the vectorised and scalar versions of a loop side by side: a SIMD loop for most of the elements and a plain "remainder" loop for the last few.
  4. Use the symbols: with a .pdb, the Disassembly window interleaves source lines; even when they are out of order, they tell you which C++ each instruction came from.

Common mistakes

Concluding a function is never called

It may be called everywhere, inlined into each caller.

Reading a vectorised loop instruction by instruction

First find the scalar remainder loop, which does the same thing one element at a time and is much easier to read.

Assuming the source order of operations

The optimiser reorders anything whose order does not change the result.

  1. A small getter function has no call to it anywhere in an optimised build. Why?
    • It was inlined: its body was copied into each caller
    • It is never used
    • Getters cannot be called in Release
    Show the answer

    It was inlined: its body was copied into each caller Inlining removes the call entirely.

  2. Why might an if inside a loop compile to setg and add instead of a jump?
    • To avoid mispredicted branches when the condition is unpredictable
    • Because jumps are not allowed in loops
    • Because if is not supported in Release
    Show the answer

    To avoid mispredicted branches when the condition is unpredictable Branchless code costs the same every iteration.

  3. A function ends with jmp otherFunction instead of call and ret. What is this?
    • A tail call: otherFunction returns directly to our caller
    • An infinite loop
    • A crash
    Show the answer

    A tail call: otherFunction returns directly to our caller The current function has no more work after the call, so it jumps instead.

  4. What usually accompanies a vectorised loop?
    • A scalar loop handling the leftover elements
    • A second vectorised loop doing the same work again
    • A call to a library function
    Show the answer

    A scalar loop handling the leftover elements The number of elements is rarely a multiple of the vector width.
