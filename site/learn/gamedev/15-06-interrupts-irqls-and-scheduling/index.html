Interrupts, IRQLs and Scheduling

lesson 15.066 of 8 in milestone 155 min1 practice task

Hardware demands attention at any moment through interrupts, and the kernel must decide what can interrupt what. Windows does this with interrupt request levels (IRQLs). The IRQL a piece of code runs at decides what it may do: whether it can wait, touch paged memory, or be preempted. This lesson explains the levels, DPCs, spin locks, and the rules that cause the most famous blue screen of all.

Interrupts

When a device needs the processor (a network packet arrived, a disk read finished, a key was pressed) it raises an interrupt. The processor stops what it is doing, saves enough state to resume, and runs the driver's interrupt service routine (ISR). A clock also interrupts regularly, which is how the scheduler gets control to switch threads (lesson 6.05).

But an interrupt can arrive while the kernel is in the middle of something delicate, even while handling another interrupt. Windows needs rules for what may interrupt what.

IRQLs

Each processor has a current IRQL (interrupt request level). Code at a given IRQL can only be interrupted by something at a higher level. The levels that matter for drivers:

IRQL Runs May wait? May touch paged memory? Scheduler can switch thread?
PASSIVE_LEVEL (0) Normal threads: all user code, most driver code, DriverEntry, most dispatch routines Yes Yes Yes
APC_LEVEL (1) Asynchronous procedure calls, some file system code Limited Yes Yes
DISPATCH_LEVEL (2) The scheduler itself, DPCs, code holding a spin lock No No No: the thread keeps the processor
DIRQL (3 and up) Device interrupt service routines No No No

The two crucial rules for DISPATCH_LEVEL and above:

  1. No waiting. The scheduler runs at DISPATCH_LEVEL, so code at that level or above cannot be switched out. Waiting on an event or a mutex there would wait forever, so it is forbidden.
  2. No paged memory. A page fault may need to wait for the disk (lesson 15.04), which is impossible at DISPATCH_LEVEL. Touching paged memory there crashes the machine with bug check IRQL_NOT_LESS_OR_EQUAL (0xA) or DRIVER_IRQL_NOT_LESS_OR_EQUAL (0xD1), the most famous blue screens, usually caused by a driver.

The practice task encodes these rules as a checker.

DPCs: doing the work later

An ISR runs at a high IRQL, blocking everything below, so it must be very short: acknowledge the device and note what happened. The rest of the work goes into a deferred procedure call (DPC), queued by the ISR and run soon after at DISPATCH_LEVEL, where other device interrupts can still get through. Work that needs to wait or touch paged memory goes one step further down, into a work item that runs in a system thread at PASSIVE_LEVEL.

flowchart LR
    I["Interrupt<br/>ISR at DIRQL:<br/>acknowledge, queue DPC"] --> D["DPC at DISPATCH_LEVEL:<br/>process the data,<br/>complete IRPs"]
    D --> W["Work item at PASSIVE_LEVEL:<br/>anything that waits or<br/>uses paged memory"]

Spin locks

Lesson 6.06's mutexes make a waiting thread sleep, which is impossible at DISPATCH_LEVEL. For data shared with DPCs or ISRs, drivers use spin locks:

  • Acquiring a spin lock raises the IRQL to DISPATCH_LEVEL (so the holder cannot be preempted on its processor), then spins (busy-waits) until the lock is free, in case another processor holds it.
  • Code holding a spin lock therefore follows every DISPATCH_LEVEL rule: no waiting, no paged memory, and should hold it for only a few microseconds, because other processors may be spinning.
C++
KIRQL old;
KeAcquireSpinLock(&m_lock, &old);         // IRQL is now DISPATCH_LEVEL
m_queue.push(item);                       // short, non-paged work only
KeReleaseSpinLock(&m_lock, old);          // back to the previous IRQL

For data used only at PASSIVE_LEVEL, drivers use waiting locks such as fast mutexes or executive resources instead.

Finding out the current IRQL

KeGetCurrentIrql() returns it. Well-written drivers assert their assumptions: PAGED_CODE() at the top of pageable functions checks the IRQL is below DISPATCH_LEVEL, and Driver Verifier (lesson 15.07) adds checks that catch IRQL mistakes immediately rather than in rare situations.

Common mistakes

Waiting at DISPATCH_LEVEL

Including while holding a spin lock. It hangs or bug-checks the machine.

Touching paged memory or calling pageable code at DISPATCH_LEVEL

Works until the page is paged out; then IRQL_NOT_LESS_OR_EQUAL.

Long work in an ISR or under a spin lock

Everything else on that processor, and processors spinning for the lock, waits. Defer to a DPC or a work item.
