Threat Modelling

lesson 17.055 of 8 in milestone 176 min1 practice task

A threat model is a structured answer to "what could go wrong, and what are we doing about it?" written before the code, not after the breach. This lesson walks through the four questions of threat modelling, draws a data-flow diagram with trust boundaries, applies STRIDE to find threats systematically, and ranks them so effort goes where it matters. The worked example is Delve with mods, saves and an online leaderboard.

The four questions

Threat modelling sounds formal, but it comes down to four questions:

  1. What are we building? A diagram of the parts and the data flowing between them.
  2. What can go wrong? Threats, found systematically rather than by guessing.
  3. What are we going to do about it? A mitigation, an acceptance, or a design change for each one.
  4. Did we do a good job? Review it as the design changes, and check mitigations were really built.

It takes an hour for a small project and saves weeks of fixes later, because design changes are cheap before the code exists.

Step 1: a data-flow diagram

Draw the processes, data stores, external parties and flows, and mark where trust changes:

    P(["Player"]) -->|"keyboard and mouse"| G["Delve game process"]
    M[("Mod folder<br/>untrusted files")] -->|"load"| G
    S[("Save files")] <-->|"read and write"| G
    G -->|"score submission over HTTPS"| L["Leaderboard server"]
    L <--> D[("Score database")]
    O(["Other players"]) -->|"view scores"| L
    classDef boundary stroke-dasharray: 5 5

Trust boundaries in this diagram: between the mod folder and the game (anyone can write files there), between the player's machine and the server (the server cannot trust anything the client sends), and between the server and other players viewing scores (their browsers will render whatever names are stored).

Step 2: STRIDE

STRIDE is a checklist of six threat types. Walk every element and flow in the diagram and ask each question:

Letter Threat Question Property it violates
S Spoofing Can someone pretend to be another user or component? Authentication
T Tampering Can someone change data or code they should not? Integrity
R Repudiation Can someone deny doing something, with no way to prove otherwise? Accountability
I Information disclosure Can someone read what they should not? Confidentiality
D Denial of service Can someone stop it working for others? Availability
E Elevation of privilege Can someone gain rights they should not have? Authorisation

Step 3: threats and responses for Delve

Element STRIDE Threat Response
Mod folder → game T, E A malicious mod's data overflows a parser and runs code Validate at the boundary (17.04), fuzz the parsers (17.03), data-only mods by default, native plugins opt-in with a warning (13.07)
Mod folder → game I A mod path like ..\..\ reads files outside its folder safeJoin (17.04's practice)
Save files T A player edits their save Accept for single player: it is their game
Game → leaderboard T, S A client submits an impossible score, or one in someone else's name Server-side validation and replay checks (17.06), accounts with tokens
Leaderboard D One client floods submissions Rate limiting per account and address
Leaderboard → other players T, E A player name containing a script runs in viewers' browsers Escape output; limit name characters
Score database I Leaked email addresses Store only what is needed; access control on the database
Game → leaderboard R A player disputes a ban Keep submitted replays and the server's decision log

Note the save-file row: accepting a threat is a legitimate answer, when the impact falls only on the person causing it.

Step 4: ranking

Not every threat deserves the same effort. A simple ranking multiplies likelihood (1 to 5) by impact (1 to 5) and handles the highest scores first, with ties broken by whichever is cheapest to fix. Many teams use richer schemes, but any explicit ranking beats fixing whatever someone noticed last. The practice task implements one.

Keeping it alive

A threat model is a document in the repository next to the design notes. Update it when a feature adds a new data flow or trust boundary (an online feature, a plugin API, a new file format), and check the "response" column against the code during reviews.

Common mistakes

Starting from attacks you have heard of

STRIDE over a diagram finds the threats specific to your design, not just famous ones.

Treating every threat as "must fix"

Some are accepted, some are cheap to fix, some need a design change. Rank and decide.

Writing it once

A threat model of last year's design protects last year's design.
