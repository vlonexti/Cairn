The Stack: Frames, Locals and Return Addresses

lesson 2.011 of 11 in milestone 29 min1 practice task

Lesson 1.05 introduced the stack. This lesson looks at a real x64 Windows frame: the return address, the 32-byte shadow space, saved registers, locals and the 16-byte alignment rule. It also covers how big the stack is, how recursion uses it, and how to replace deep recursion with a loop.

What is really in a frame

The demonstration in lesson 1.05 showed a frame as a return address plus some variables. A real frame on 64-bit Windows has a few more parts, always in the same order. Here is the frame of a function update that was called by tick, drawn with higher addresses at the top:

higher addresses
  ┌───────────────────────────────┐
  │ ... tick's own locals ...     │  tick's frame
  ├───────────────────────────────┤
  │ shadow space for update       │  32 bytes that tick reserved for update's
  │ (4 slots × 8 bytes)           │  first four register arguments
  ├───────────────────────────────┤
  │ return address into tick      │  pushed by the call instruction
  ├───────────────────────────────┤ ◀ update starts here
  │ saved registers               │  registers update must give back unchanged
  │ update's local variables      │
  │ space for update's own calls  │  shadow space for the functions it calls
  └───────────────────────────────┘ ◀ rsp while update runs
lower addresses

The parts, from the top:

Part Who makes it Why it is there
Shadow space (home space) The caller The first four arguments arrive in registers rcx, rdx, r8, r9. The caller always leaves 32 bytes where the called function may store them, for example so a debugger can show them.
Return address The call instruction Where to continue in the caller. 8 bytes.
Saved registers The called function Some registers (rbx, rbp, rdi, rsi, r12 to r15) must have the same value after a call as before. A function that wants to use them saves the old values first and restores them before returning.
Locals The called function Its local variables, and temporaries the compiler needs.
Outgoing area The called function Room for the shadow space, and any arguments beyond the fourth, for the functions it calls.

The rules come from the Microsoft x64 calling convention, which chapter 7 reads at the instruction level.

The alignment rule

At the moment of every call, rsp must be a multiple of 16. The call pushes an 8-byte return address, so inside the function rsp is 8 off, and the function's first job is to subtract enough to make it a multiple of 16 again. That is why frames are always sized in odd-looking amounts such as 40 or 56 bytes: shadow space and locals, plus 8 to fix the alignment.

The rule exists because some instructions that work on 16-byte blocks of data, used heavily for floating point and in game maths, require 16-byte-aligned addresses.

Locals live at fixed offsets

The compiler decides where each local lives inside the frame when it compiles the function. At run time there is no searching: a local is always "rsp plus 40" or similar. That is why reading a local costs the same as reading any other memory.

You can see the offsets by printing addresses.

C++
#include <cstdint>
#include <iostream>

void frameTour()
{
    int a{ 1 };
    double b{ 2.0 };
    char name[12]{ "frame" };
    const auto base{ reinterpret_cast<std::uintptr_t>(&a) };
    std::cout << "a     at offset 0\n";
    std::cout << "b     at offset " << static_cast<std::intptr_t>(reinterpret_cast<std::uintptr_t>(&b) - base) << '\n';
    std::cout << "name  at offset " << static_cast<std::intptr_t>(reinterpret_cast<std::uintptr_t>(&name) - base) << '\n';
}

int main()
{
    frameTour();
    return 0;
}
Output (yours will differ)
a     at offset 0
b     at offset 36
name  at offset 68

The exact offsets depend on the compiler, its version and the build settings. In a Debug build the compiler leaves gaps between locals on purpose and fills them with 0xCC, so that writing past the end of one local is more likely to be caught. In a Release build, locals are packed tightly, and some never reach memory at all because they live entirely in registers.

How big is the stack?

Each thread gets its own stack. On Windows the main thread's stack is 1 MB by default. That is plenty for normal code: a typical frame is tens or hundreds of bytes, so even a chain of a thousand calls uses only a fraction of it.

Two things eat stack quickly:

  • Big locals. A local int grid[512][512] is a full megabyte.
  • Deep recursion. A recursive function that goes 100,000 calls deep, at 100 bytes a frame, needs 10 MB.

The size is a linker setting (Linker → System → Stack Reserve Size, or /STACK), and threads created with CreateThread or std::thread can be given their own size. Raising it hides the problem rather than fixing it, though. The usual fix is to move big data to the heap (next lesson) and turn deep recursion into a loop.

Recursion versus an explicit stack

Recursion is natural for anything shaped like a tree or a flood: exploring a maze, filling a region of a tile map, walking a scene graph. Here is a flood fill written recursively, the way it is often first written:

C++
#include <iostream>
#include <string>
#include <vector>

void fill(std::vector<std::string>& map, int x, int y)
{
    if (y < 0 || y >= static_cast<int>(map.size())) return;
    if (x < 0 || x >= static_cast<int>(map[y].size())) return;
    if (map[y][x] != '.') return;
    map[y][x] = '~';                  // flooded
    fill(map, x + 1, y);
    fill(map, x - 1, y);
    fill(map, x, y + 1);
    fill(map, x, y - 1);
}

int main()
{
    std::vector<std::string> map{
        "#######",
        "#..#..#",
        "#..#..#",
        "####..#",
        "#######",
    };
    fill(map, 1, 1);
    for (const std::string& row : map) std::cout << row << '\n';
    return 0;
}
Output
#######
#~~#..#
#~~#..#
####..#
#######

It works, and for this map it is fine. But every cell flooded is one more frame, and on a 1000 × 1000 open map the chain of calls can be hundreds of thousands deep. The program dies with a stack overflow.

The fix is to keep the "cells still to visit" in a container you manage yourself, on the heap, and loop until it is empty. The program's call stack then stays one frame deep, however big the map. This is the practice task for this lesson.

Seeing frames in the debugger

In Visual Studio, pause anywhere and open Debug → Windows → Call Stack. Each line is a frame. Right-click and turn on Show Parameter Values to see the arguments of every call. Open Debug → Windows → Registers to see rsp, then type rsp into the Memory window's address box to look at the raw frame. The return address appears as an 8-byte value that looks like 00007FF6xxxxxxxx: an address inside your program's code.

Common mistakes

Assuming locals are in declaration order

The compiler is free to place them in any order, and to keep some only in registers. Never compute the address of one local from another.

Raising the stack size to fix a recursion crash

It moves the limit; it does not remove it. A bigger level will crash again. Use an explicit stack or queue for anything whose depth depends on input data.

Forgetting that every thread has its own stack

A local in one thread's function is invisible to other threads. Sharing data between threads goes through the heap or globals, with proper synchronisation (chapter 6).

Knowledge check

quizIn Xenon your best score is kept.
  1. What is the 32-byte shadow space for?
    • It is room the caller leaves where the called function may store its four register arguments
    • It holds the return address and saved registers
    • It is padding that is never used
    Show the answer

    It is room the caller leaves where the called function may store its four register arguments The first four arguments travel in rcx, rdx, r8 and r9. The caller always reserves 32 bytes so the called function has a place to spill them.

  2. At the moment of a call instruction, rsp must be a multiple of what?
    • 8
    • 16
    • 32
    Show the answer

    16 The x64 Windows convention requires 16-byte alignment at every call. The pushed return address then leaves rsp 8 off inside the function, and the function fixes that when it sets up its frame.

  3. A flood fill on a huge open map crashes with a stack overflow. What is the best fix?
    • Increase the stack size in the linker settings
    • Keep the cells still to visit in a container on the heap and loop until it is empty
    • Make the function inline
    Show the answer

    Keep the cells still to visit in a container on the heap and loop until it is empty Any depth that depends on input data can outgrow any fixed stack. An explicit container grows on the heap instead.

  4. Which of these does the called function have to restore before it returns?
    • rax
    • rbx
    • rcx
    Show the answer

    rbx rbx, rbp, rdi, rsi and r12 to r15 are non-volatile: callers rely on them being unchanged. rax carries the return value and rcx the first argument; both may be overwritten.
