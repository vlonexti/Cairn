The PE File Format

lesson 9.022 of 10 in milestone 96 min1 practice task

Every .exe and .dll on Windows is a Portable Executable (PE) file: a set of headers describing the program, followed by its sections of code and data. This lesson walks through the headers in order (the DOS header and MZ, the PE signature, the file header, the optional header and its data directories, and the section table) and reads them from C++.

The overall shape

┌──────────────────────────┐  offset 0
│ DOS header ("MZ")        │  64 bytes; e_lfanew at offset 0x3C says where the PE header is
├──────────────────────────┤
│ DOS stub                 │  a tiny DOS program: "This program cannot be run in DOS mode."
├──────────────────────────┤  offset e_lfanew
│ "PE\0\0" signature       │  4 bytes
│ File header (COFF)       │  20 bytes: machine, number of sections, ...
│ Optional header          │  240 bytes for 64-bit: entry point, image base, data directories
├──────────────────────────┤
│ Section table            │  40 bytes per section: name, RVA, size, file offset, flags
├──────────────────────────┤
│ .text                    │  code
│ .rdata                   │  constants, import and export tables, RTTI
│ .data                    │  writable globals
│ .pdata                   │  unwind information (lesson 8.02)
│ .rsrc                    │  resources: icons, version information
│ .reloc                   │  relocations (lesson 6.09)
└──────────────────────────┘

The same layout appears in memory once the loader maps the file: GetModuleHandleW(nullptr) points at the MZ (lesson 5.08), and every RVA in the headers is an offset from there.

The DOS header

For backward compatibility with 1980s DOS, every PE file starts with a DOS header. Only two fields matter now:

Offset Field Value
0x00 e_magic 0x5A4D: the bytes 4D 5A, "MZ"
0x3C e_lfanew The file offset of the PE signature (often 0x80 to 0x100)

The NT headers

At e_lfanew come the NT headers: the signature, the file header and the optional header.

Field Where Meaning
Signature +0 0x00004550: the bytes 50 45 00 00, "PE\0\0"
FileHeader.Machine +4 0x8664 for x64, 0x14C for 32-bit x86, 0xAA64 for ARM64
FileHeader.NumberOfSections +6 How many entries the section table has
FileHeader.TimeDateStamp +8 When it was linked (or a hash, for reproducible builds)
FileHeader.SizeOfOptionalHeader +20 Where the section table starts, relative to the optional header
FileHeader.Characteristics +22 Flags: executable, DLL, large-address-aware ...
OptionalHeader.Magic +24 0x20B for 64-bit (PE32+), 0x10B for 32-bit
OptionalHeader.AddressOfEntryPoint +24+16 RVA where execution starts (the C runtime's start-up code, which calls main)
OptionalHeader.ImageBase +24+24 Preferred load address: 0x140000000 for exes (lesson 6.09)
OptionalHeader.SizeOfImage Size of the whole image in memory
OptionalHeader.DllCharacteristics Security flags: ASLR (dynamic base), DEP (NX compatible), CFG ...
OptionalHeader.DataDirectory[16] the last 128 bytes RVA and size of the import table, export table, resources, relocations, debug data ...

The data directories are the index of the file: each entry points (by RVA and size) at one important table. The ones you will use most:

Index Directory
0 Export table (lesson 9.03)
1 Import table (lesson 9.03)
2 Resources
3 Exception (unwind) data, .pdata
5 Base relocations
6 Debug directory: the PDB's name and signature (lesson 8.02)
12 Import address table (IAT)

The section table

After the optional header, one 40-byte entry per section:

Field Meaning
Name 8 bytes, such as .text\0\0\0
VirtualSize Size in memory
VirtualAddress RVA where the section starts in memory
SizeOfRawData Size in the file (rounded up to the file alignment, often 512)
PointerToRawData Offset where the section starts in the file
Characteristics Flags: code, initialised data, readable, writable, executable

Sections start on 4 KB page boundaries in memory, but only 512-byte boundaries in the file, so an RVA and a file offset differ: converting between them needs the section table (lesson 9.03's practice task).

Reading the headers from C++

<windows.h> defines all these structures (IMAGE_DOS_HEADER, IMAGE_NT_HEADERS64, IMAGE_SECTION_HEADER), so a loaded module's headers can be read directly:

C++
#include <windows.h>
#include <iostream>
#include <string>

int main()
{
    const auto* base{ reinterpret_cast<const unsigned char*>(GetModuleHandleW(nullptr)) };
    const auto* dos{ reinterpret_cast<const IMAGE_DOS_HEADER*>(base) };
    const auto* nt{ reinterpret_cast<const IMAGE_NT_HEADERS64*>(base + dos->e_lfanew) };

    std::cout << "MZ found:      " << (dos->e_magic == IMAGE_DOS_SIGNATURE) << '\n';
    std::cout << "PE found:      " << (nt->Signature == IMAGE_NT_SIGNATURE) << '\n';
    std::cout << "x64:           " << (nt->FileHeader.Machine == IMAGE_FILE_MACHINE_AMD64) << '\n';
    std::cout << "64-bit header: " << (nt->OptionalHeader.Magic == IMAGE_NT_OPTIONAL_HDR64_MAGIC) << '\n';
    std::cout << "ASLR enabled:  " << ((nt->OptionalHeader.DllCharacteristics & IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE) != 0) << '\n';

    const IMAGE_SECTION_HEADER* section{ IMAGE_FIRST_SECTION(nt) };
    bool hasText{ false };
    for (int i{ 0 }; i < nt->FileHeader.NumberOfSections; ++i)
        if (std::string(reinterpret_cast<const char*>(section[i].Name), 5) == ".text") hasText = true;
    std::cout << "has .text:     " << hasText << '\n';
    return 0;
}
Output
MZ found:      1
PE found:      1
x64:           1
64-bit header: 1
ASLR enabled:  1
has .text:     1

dumpbin /headers game.exe prints all of this from the file on disk, and tools like PE-bear and CFF Explorer show it graphically. For an untrusted file, never cast raw file bytes to these structures without checking every offset against the file's size first: malformed files are a classic attack on parsers. The practice task parses from a byte buffer with those checks.

Common mistakes

Mixing RVAs and file offsets

Header fields are RVAs (memory offsets). In a file on disk, convert through the section table before reading.

Assuming a fixed offset for the PE header

Always read e_lfanew.

Trusting the sizes in a file

Check every offset and count against the actual file size before using it.

    • 4D 5A ("MZ")
    • 50 45 ("PE")
    • 7F 45 ("\x7FE")
    Show the answer

    4D 5A ("MZ") "MZ" is the DOS header's signature; the PE signature comes later, at e_lfanew.

  2. What does e_lfanew hold?
    • The file offset of the PE signature and NT headers
    • The entry point
    • The number of sections
    Show the answer

    The file offset of the PE signature and NT headers It is at offset 0x3C of the DOS header.

  3. What is the value of FileHeader.Machine for a 64-bit x86 program?
    • 0x8664
    • 0x14C
    • 0x20B
    Show the answer

    0x8664 0x20B is the optional header's magic for PE32+.

  4. What are the data directories?
    • A table of RVAs and sizes pointing at the import table, export table, resources, relocations and other key structures
    • The folders the program was built in
    • The list of sections
    Show the answer

    A table of RVAs and sizes pointing at the import table, export table, resources, relocations and other key structures They are the index of the file's important tables.
