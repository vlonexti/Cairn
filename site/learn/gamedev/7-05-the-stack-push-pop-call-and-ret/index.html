The Stack, push, pop, call and ret

lesson 7.055 of 11 in milestone 75 min

Four instructions manage the stack from lesson 1.05 at the machine level. push and pop add and remove 8-byte values; call pushes a return address and jumps; ret pops it and jumps back. This lesson steps through them, shows a function's prologue and epilogue, and explains what a corrupted stack does to ret.

push and pop

The stack grows downwards, and rsp always points at the value on top (lesson 1.05).

Instruction Does Equivalent to
push rbx rsp −= 8, then store rbx at [rsp] sub rsp, 8 / mov [rsp], rbx
pop rbx load [rsp] into rbx, then rsp += 8 mov rbx, [rsp] / add rsp, 8

On x64, push and pop always move 8 bytes. Their main use in compiled code is saving and restoring the non-volatile registers (rbx, rbp, rdi, rsi, r12 to r15) that a function must give back unchanged (lesson 2.01).

call and ret

Instruction Does
call target push the address of the next instruction (the return address), then jump to target
ret pop the return address into rip: continue there
ret 0 the same (the number is how many extra bytes to pop; always 0 on x64)

Prologue and epilogue

Most compiled functions start and end with a fixed pattern that builds and dismantles their stack frame:

Assembly
update PROC
    push  rbx                 ; prologue: save non-volatile registers used below
    push  rdi
    sub   rsp, 40             ; reserve the frame: locals + 32 bytes of shadow space, aligned
    ...                       ; the body
    add   rsp, 40             ; epilogue: release the frame
    pop   rdi                 ; restore in reverse order
    pop   rbx
    ret
update ENDP

The numbers follow the alignment rule from lesson 2.01: on entry rsp is 8 off a multiple of 16 (the return address), two pushes make it 8 off again (24 bytes), and sub rsp, 40 brings the total to 64, a multiple of 16, ready for this function's own calls.

Older code, and code compiled for easier debugging, also sets up rbp as a frame pointer:

Assembly
push  rbp
mov   rbp, rsp          ; rbp marks the frame; locals are at rbp-8, rbp-16 ...
sub   rsp, 48
...
mov   rsp, rbp
pop   rbp
ret

x64 Windows code usually omits it. The debugger and Windows find frames through unwind information that the compiler stores in the .pdata and .xdata sections, describing each function's prologue so the stack can be walked without a frame pointer (lesson 8.02).

When the stack is corrupted

ret trusts whatever 8 bytes are at [rsp]. If a buffer overrun on the stack (lesson 2.09) has overwritten the return address, ret jumps to that garbage, and the crash happens at a nonsense address with a nonsense call stack. This is also the classic way attackers hijack programs, which is why compilers add defences:

  • Stack cookies (/GS, on by default): the prologue puts a secret value between the locals and the return address, and the epilogue checks it before ret. An overrun that reaches the return address changes the cookie first, and the program is stopped with a security check failure instead of jumping.
  • Control-flow guard and shadow stacks (on recent CPUs and Windows) check calls and returns against what is allowed.

When you see a crash at a strange address with a broken call stack, suspect a stack overrun and turn on AddressSanitizer (lesson 2.10).

Common mistakes

Unbalanced push and pop

Every push in a function must be matched by a pop (or an add rsp) before ret, or ret pops the wrong value.

Popping in the wrong order

Registers must be restored in the reverse order they were saved.

[!warning] Reading ret 0 as "return 0" The 0 is a byte count for the stack, not the return value. The return value is in rax.
