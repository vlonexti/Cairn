Solutions, Projects and Build Configurations

lesson 4.011 of 10 in milestone 47 min

A real game is not one .cpp file. It is a solution holding several projects, such as the game, an engine library, a tools DLL and a test runner, each built in several configurations and for one or more platforms. This lesson shows how Visual Studio organises that, where the settings live, and how to set up a multi-project solution you will reuse for the rest of the course.

Solutions and projects

Lesson 1.07 created one console project. From now on the course builds several things that belong together: a game, a library it uses, a DLL it loads, tests that check them. Visual Studio's structure for this is:

Thing File What it is
Solution .sln A list of projects, plus which of them to build in which configuration
Project .vcxproj One output (an .exe, .dll or .lib), its source files, and all its compiler and linker settings
Filters .vcxproj.filters Only the folders shown in Solution Explorer. They do not have to match folders on disk
User settings .vcxproj.user Your personal debugging settings, such as command arguments. Not shared

A .vcxproj file is XML that you can open in a text editor. Everything in the Properties dialog ends up in it, which is useful when comparing two projects' settings or reviewing a change in version control.

A solution for the course

Here is the layout the rest of the course assumes. Create it now so later lessons can add to it.

Output
course\
    course.sln
    engine\          Static library (.lib): shared code, such as maths, the tile map, memory helpers
    game\            Console app (.exe): the game itself, uses engine
    plugin\          Dynamic library (.dll): built in lesson 4.05
    tests\           Console app (.exe): unit tests for engine
  1. File → New → Project → Blank Solution, name it course.
  2. Right-click the solution → Add → New Project → Static Library, name it engine.
  3. Add a Console App named game, and another named tests.
  4. Right-click game → Add → Reference → tick engine. Do the same for tests.
  5. Right-click game → Set as Startup Project: F5 now runs the game.

The reference does two things: it makes engine build before game, and it links engine.lib into game.exe automatically. You still have to tell the compiler where engine's headers are: in game's properties, C/C++ → General → Additional Include Directories, add $(SolutionDir)engine.

Configurations and platforms

Every project is built in a configuration for a platform. Visual Studio starts you with two of each:

x64 Win32 (x86)
Debug Debug, 64-bit Debug, 32-bit
Release Release, 64-bit Release, 32-bit

Each of the four combinations has its own complete set of settings. That is powerful (Debug can have checks Release does not), and it is the cause of the most common project mistake: changing a setting in one combination and wondering why another behaves differently. When a setting should apply everywhere, select All Configurations and All Platforms at the top of the Properties dialog before changing it.

You can add your own configurations in Build → Configuration Manager. Common additions:

  • ASan: Debug plus AddressSanitizer (lesson 2.10).
  • Profile: Release with debug information and profiling hooks, for measuring (chapter 8).

Macros in settings

Paths in project settings use macros so they work on any machine. The ones you will use most:

Macro Expands to
$(SolutionDir) The folder holding the .sln, with a trailing backslash
$(ProjectDir) The folder holding the .vcxproj
$(Configuration) Debug or Release (or your own)
$(Platform) x64 or Win32
$(OutDir) Where the project's output goes
$(TargetPath) The full path of the .exe or .dll being built

A tidy convention is to send every project's output to one folder per configuration, so the game, its DLLs and its tests end up side by side: set General → Output Directory to $(SolutionDir)bin\$(Platform)\$(Configuration)\ for all projects and all configurations.

Property sheets

When five projects need the same settings (C++20, warning level 4, the same output folder), setting them five times invites mistakes. A property sheet (.props file) holds settings that several projects share. Open View → Other Windows → Property Manager, right-click a project → Add New Project Property Sheet, set things there, then add the same sheet to the other projects. Change it once and every project follows.

Building from the command line

Everything Visual Studio does can be done from the Developer PowerShell, which is how build servers do it:

Terminal
msbuild course.sln /p:Configuration=Release /p:Platform=x64 /m

/m builds projects in parallel. Being able to build without the IDE is useful for scripts, and for checking that a build does not secretly depend on something only your IDE session had set up.

Common mistakes

Settings changed in one configuration only

If Debug works and Release does not, compare the two configurations' settings. Use All Configurations for project-wide options.

Including another project's headers by relative path

#include "../engine/tilemap.h" breaks when files move. Add the folder to Additional Include Directories and write #include "tilemap.h".

[!warning] Committing .vs, bin, obj and x64 folders They are build output and caches. A .gitignore for Visual Studio projects excludes them.
