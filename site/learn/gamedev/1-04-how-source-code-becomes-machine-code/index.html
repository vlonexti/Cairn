How Source Code Becomes Machine Code

lesson 1.044 of 8 in milestone 19 min1 practice task

The CPU only understands numbers, so C++ has to be translated before it can run. Four tools do it in turn: the preprocessor, the compiler, the assembler and the linker. Knowing what each one does explains most build errors and almost everything you will see in a debugger.

From text to numbers

In lesson 1.01 the tiny computer ran a program that was nothing but numbers in memory. A real CPU is the same. It has never heard of C++. A .cpp file is text for people, and something has to turn it into the numbers the processor executes.

That job is split into stages. Each stage takes one kind of file and produces another.

flowchart LR
    SRC["main.cpp<br/>your source"] --> PRE["Preprocessor<br/>pastes in headers,<br/>expands macros"]
    PRE --> COMP["Compiler<br/>C++ to<br/>assembly"]
    COMP --> ASM["Assembler<br/>assembly to<br/>machine code"]
    ASM --> OBJ["main.obj<br/>object file"]
    OBJ --> LINK["Linker<br/>joins object files<br/>and libraries"]
    LIB["Libraries<br/>(.lib)"] --> LINK
    LINK --> EXE["game.exe"]

When you press Build in Visual Studio, all of these run one after another, so it feels like one step. It is worth knowing the stages apart, because each has its own kind of error.

Stage 1: the preprocessor

Every line that starts with # is an instruction to the preprocessor, which works on plain text before any C++ is understood.

Directive What the preprocessor does
#include <iostream> Pastes the whole of that file in place of the line
#define MAX_PLAYERS 4 From here on, replaces the word MAX_PLAYERS with 4
#ifdef _DEBUG ... #endif Keeps or drops the lines in between, depending on whether _DEBUG is defined

The result is one long file called a translation unit. Including <iostream> alone adds tens of thousands of lines. You never see this file, but the compiler does.

C++
#include <iostream>

#define GREETING "Hello from the preprocessor"
#define SQUARE(x) ((x) * (x))

int main()
{
    std::cout << GREETING << '\n';
    std::cout << SQUARE(7) << '\n';
#ifdef _DEBUG
    std::cout << "This is a debug build\n";
#endif
    return 0;
}
Output
Hello from the preprocessor
49
This is a debug build

The examples on this site are built as Debug builds, where _DEBUG is defined, so the last line appears. In a Release build the preprocessor removes that line before the compiler ever sees it.

By the time the compiler sees main, the second line reads std::cout << ((7) * (7)) << '\n';. The word SQUARE is gone. Macros are text substitution and nothing more, which is why modern C++ prefers constexpr variables and ordinary functions: those obey the language's rules for types and scope.

See the preprocessed file yourself

In Visual Studio, open the project's properties, go to C/C++ → Preprocessor and set Preprocess to a File to Yes. Building then writes main.i, the text the compiler actually reads. Turn the option off again afterwards, because it stops the build from producing an executable.

Stage 2: the compiler

The compiler reads the translation unit, checks that it is valid C++, and translates every function into assembly language: a text form of machine instructions, one per line. This is the stage that reports most of the errors you meet, such as a missing semicolon, a type that does not match, or a name that does not exist.

Here is a small function and what Microsoft's compiler turns it into, with optimisation switched on:

C++
int addBonus(int score)
{
    return score + 50;
}
Assembly
addBonus PROC
    lea  eax, DWORD PTR [rcx+50]
    ret  0
addBonus ENDP

Two instructions. The argument score arrived in a register called rcx, the result is left in a register called eax, and ret returns to whoever called the function. You do not need to read assembly yet: chapter 7 teaches it properly. For now, notice that each line is one small action, just like the tiny computer's instructions.

Stage 3: the assembler

The assembler turns each assembly line into its numeric encoding. ret becomes the single byte C3. The lea line becomes three bytes, 8D 41 32, and the 32 at the end is 50 in hexadecimal: the bonus itself, stored inside the instruction.

Output
addBonus:
  8D 41 32      lea eax, [rcx+32h]
  C3            ret

This is exactly what lesson 1.01 described: a program is numbers in memory. These four bytes are the function addBonus. When the game runs, they sit somewhere in memory, and calling addBonus means telling the CPU to fetch its next instruction from there.

The assembler's output is an object file (.obj on Windows). It holds the machine code for one .cpp file, plus a list of names it defines and names it uses but does not define.

Stage 4: the linker

A real program is many .cpp files, and each one is compiled on its own. If main.cpp calls addBonus but addBonus lives in score.cpp, then main.obj contains a call to a function whose address it does not know. It leaves a note: "fill in the address of addBonus here".

The linker reads every object file and every library, matches each "I need" note with the "I define" entry that answers it, fills in the real addresses, and writes the final .exe.

flowchart LR
    M["main.obj<br/>defines: main<br/>needs: addBonus, printf"] --> L["Linker"]
    S["score.obj<br/>defines: addBonus"] --> L
    C["C runtime library<br/>defines: printf, ..."] --> L
    L --> E["game.exe<br/>every call has a real address"]

That explains the two classic linker errors:

Error Meaning
LNK2019: unresolved external symbol addBonus Something needs addBonus, and no object file or library defines it. Often a .cpp file is missing from the project, or a library was not added.
LNK2005: addBonus already defined in main.obj Two object files both define it. Often a function body was written in a header that two .cpp files include.

Neither is a mistake in the C++ syntax, which is why they only appear after compiling has succeeded.

Why the stages matter later

Everything in the rest of this course rests on this pipeline.

  • Debugging. The debugger shows you the running machine code and maps it back to your source lines using a separate file of debug symbols (.pdb) that the compiler and linker write alongside the program.
  • Assembly. Chapter 7 reads the compiler's output, the stage 2 text you saw above.
  • Libraries and DLLs. Chapter 4 shows how the linker can leave some addresses to be filled in when the program starts, which is how DLLs work.
  • Reverse engineering. Chapter 9 runs the pipeline backwards: from the numbers in an .exe back to something a person can understand.

Common mistakes

[!warning] Thinking #include is like import in other languages It is a literal copy and paste of text. Including the same header twice pastes it twice, which is why headers start with #pragma once.

[!warning] Putting function bodies in headers without inline Each .cpp that includes the header gets its own copy of the function, and the linker reports already defined. Put the body in a .cpp file, or mark it inline.

Reading a linker error as a syntax error

If the message starts with LNK, your code compiled. Look for a missing file, a missing library, or a declaration that does not match its definition exactly.

Macros with missing brackets

#define SQUARE(x) x * x turns SQUARE(2 + 3) into 2 + 3 * 2 + 3, which is 11. This is one reason to prefer constexpr functions.
