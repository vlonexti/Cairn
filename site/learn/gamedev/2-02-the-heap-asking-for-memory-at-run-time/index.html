The Heap: Asking for Memory at Run Time

lesson 2.022 of 11 in milestone 29 min1 practice task

The stack is fast but small, and everything on it disappears when its function returns. For data whose size or lifetime is only known at run time (a level loaded from disk, a list of bullets), programs ask the heap for memory. This lesson shows how new, delete, smart pointers and containers use it, what it costs, and what a Debug build does to help you catch heap mistakes.

Why a second kind of memory

Stack memory has two limits:

  1. Its lifetime is tied to a function call. A local disappears when its function returns. A level loaded inside loadLevel must outlive loadLevel.
  2. Its size is fixed when the program is compiled. The compiler must know how big a frame is. A level whose size is read from a file cannot be a local array.

The heap answers both. It is a large area of the process's memory managed by an allocator: you ask for a number of bytes at run time, it finds a free block and gives you its address, and the block stays yours until you give it back.

Stack Heap
Size decided At compile time At run time
Lifetime Until the function returns Until you free it
Speed of getting memory One subtraction from rsp A search through the allocator's free blocks
Typical capacity 1 MB per thread Gigabytes, limited by the system
Freed by Returning delete, a smart pointer, or a container

new and delete

new asks the heap for room for an object, constructs it there and returns a pointer. delete destroys the object and gives the memory back.

C++
#include <iostream>

struct Monster
{
    int health;
    int damage;
};

int main()
{
    Monster* boss{ new Monster{ 500, 40 } };     // lives on the heap
    std::cout << "boss has " << boss->health << " health\n";
    boss->health -= 120;
    std::cout << "boss has " << boss->health << " health\n";
    delete boss;                                  // gives the memory back
    boss = nullptr;                               // the old address is no longer valid

    int count{ 5 };
    int* scores{ new int[count]{ 10, 20, 30, 40, 50 } };   // an array sized at run time
    std::cout << "third score " << scores[2] << '\n';
    delete[] scores;                              // arrays need delete[]
    return 0;
}
Output
boss has 500 health
boss has 380 health
third score 30

The pointer boss itself is a local on the stack. The Monster it points at is on the heap. When main returns, the pointer disappears, but the Monster would not: if nobody calls delete, its memory stays reserved until the process exits. That is a memory leak.

Don't use raw new and delete in modern code

Every new needs exactly one matching delete, on every path through the program, including early returns and exceptions. That is hard to get right by hand, so modern C++ gives the job to objects that free memory in their destructors.

C++
#include <iostream>
#include <memory>
#include <vector>

struct Monster
{
    int health;
    int damage;
};

int main()
{
    // One object, one owner: freed automatically when boss goes out of scope.
    std::unique_ptr<Monster> boss{ std::make_unique<Monster>(Monster{ 500, 40 }) };
    std::cout << "boss: " << boss->health << '\n';

    // Many objects: the vector owns a heap block and grows it as needed.
    std::vector<Monster> wave;
    for (int i{ 0 }; i < 4; ++i)
        wave.push_back(Monster{ 50 + i * 10, 5 });
    std::cout << "wave of " << wave.size() << ", last has " << wave.back().health << '\n';
    return 0;
}   // wave and boss free their heap memory here
Output
boss: 500
wave of 4, last has 80

std::vector, std::string, std::unique_ptr and std::shared_ptr all use the heap underneath. Lesson 2.04 explains the rule that makes this safe (RAII), and lesson 3.07 opens up std::vector to show exactly how it manages its block.

What an allocation costs

Asking the heap for memory is not free. The allocator has to find a suitable free block, split it, record that it is in use, and later merge it back when it is freed. Each allocation also carries hidden bookkeeping bytes beside it.

Games care about this because they run the same code sixty or more times a second. Allocating a few objects at start-up costs nothing noticeable. Allocating thousands of small objects every frame (every bullet, every particle, every temporary string) adds up to real time and scatters data across memory, which is slow to read. Common answers, which later lessons build:

  • Reserve up front. vector.reserve(1000) gets one block big enough for the whole wave.
  • Reuse. Keep dead objects in a pool and recycle them instead of freeing (lesson 3.10).
  • Arenas. Grab one large block per frame or per level and hand out pieces of it by moving a pointer along, then release the whole block at once. This is the practice task for this lesson.

Where heap memory comes from

On Windows, new calls the C runtime's malloc, which uses a heap managed by Windows itself (the functions HeapAlloc and HeapFree in kernel32.dll). The heap in turn gets large regions of memory from the operating system a page at a time with VirtualAlloc, which chapter 6 covers.

flowchart LR
    A["new Monster"] --> B["operator new / malloc<br/>(C runtime)"]
    B --> C["HeapAlloc<br/>(Windows heap)"]
    C --> D["VirtualAlloc<br/>(pages from the OS)"]

Most of the time only the top of that chain matters. The bottom of it matters when you look at memory in a debugger, because it explains why heap addresses look different from stack addresses.

What a Debug build does to the heap

In a Debug build, Microsoft's C runtime wraps every allocation with extra checks and fills memory with recognisable patterns. Learn them: you will see them constantly in the Memory window.

Byte pattern Meaning
CD CD CD CD Heap memory that was allocated but not yet written ("clean")
DD DD DD DD Heap memory that has been freed ("dead"). Reading it means you used a pointer after delete.
FD FD FD FD Guard bytes ("no man's land") placed just before and after each block. If they change, something wrote past the end.
CC CC CC CC Uninitialised stack memory (lesson 1.07)

When you delete a block, the Debug runtime checks its guard bytes. If you wrote one element past the end of a new int[5], it notices and stops the program with a "HEAP CORRUPTION DETECTED" message naming the block. Release builds do none of this, which is why heap bugs often "only happen in Release": they were there all along, just not caught.

Common mistakes

new[] with delete, or new with delete[]

Arrays made with new[] must be freed with delete[]. Mixing them is undefined behaviour. The simplest fix is to use std::vector instead.

Using a pointer after delete

The memory may be handed out again for something else. Set raw pointers to nullptr after deleting, or better, use std::unique_ptr.

Allocating in the hot loop

Building a temporary std::string or std::vector inside per-frame code allocates every frame. Hoist it out of the loop and reuse it, or reserve once.

Thinking a leak is harmless because the program ends

Games run for hours. A few bytes leaked per frame is megabytes per hour, and leaks inside long-running servers or tools eventually exhaust memory.

Knowledge check

quizIn Xenon your best score is kept.
  1. A level's size is read from a file when the game starts. Where should its tile data go?
    • In a local array inside loadLevel
    • On the heap, for example in a std::vector
    • In the shadow space
    Show the answer

    On the heap, for example in a std::vector Its size is only known at run time and it must outlive the function that loads it. Both point to the heap.

  2. In a Debug build, you look at a pointer's target and see DD DD DD DD. What has happened?
    • The memory was freed, and the program is still using a pointer to it
    • The memory was allocated but never written
    • Something wrote past the end of the block
    Show the answer

    The memory was freed, and the program is still using a pointer to it DD is the Debug heap's "dead memory" fill, written when a block is freed.

  3. Why do games avoid allocating many small objects every frame?
    • The heap only allows a fixed number of allocations
    • Each allocation takes time and scatters data, and doing it thousands of times per frame adds up
    • Small objects must go on the stack
    Show the answer

    Each allocation takes time and scatters data, and doing it thousands of times per frame adds up Allocation is a search plus bookkeeping. Reserving, pooling and arenas avoid repeating it every frame.

  4. What frees the memory owned by a std::vector local?
    • You must call delete on it
    • The operating system, when the program exits
    • The vector's destructor, when the vector goes out of scope
    Show the answer

    The vector's destructor, when the vector goes out of scope Containers and smart pointers free their heap memory in their destructors. That is the RAII idea in lesson 2.04.
