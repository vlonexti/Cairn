A Method for Unknown Programs

lesson 6.011 of 5 in milestone 65 min1 practice task

How to approach a program you know nothing about without getting lost - start from a question, triage, find landmarks, form a hypothesis, test it dynamically, write it down, and know when to stop reading and switch technique.

The trap

The beginner's approach to an unknown binary is to open it at the entry point and read. After two hours you have understood the C runtime's start-up code in detail and know nothing about the program. Real programs are millions of instructions; nobody reads them all. Experienced reverse engineers read a tiny fraction, chosen carefully.

Start from a question

Every session needs a concrete goal, written down before you start:

  • "Where does it store its settings, and in what format?"
  • "Why does it crash when the file name contains a space?"
  • "How does the save file encode the player's inventory?"
  • "What does this DLL's exported Init function expect as its arguments?"

A question tells you what you can ignore, which is almost everything.

The loop

  1. Triage (lesson 1.05): what is it, how was it built, what does it import, which strings does it contain? Ten minutes.
  2. Find landmarks related to the question: strings ("Save failed"), imports (CreateFileW, RegSetValueExW), exports, RTTI class names, behaviour seen in Process Monitor. Each landmark leads to code through cross-references.
  3. Form a hypothesis: "this function parses the save file; its first argument is the file contents; [rcx+8] is the item count".
  4. Test it dynamically: put a breakpoint there, trigger the behaviour, check the registers and memory against your guess. Change an input (a different save) and predict the change.
  5. Record what you learned: rename the function, define the struct, add a comment, note the evidence.
  6. Repeat, each answer raising the next, smaller question.

Static reading suggests; dynamic testing confirms. A claim that has not been checked in a debugger, or against a second sample, is still a guess. Mark it as one.

Top down and bottom up

  • Top down: start from a high-level landmark (the save command in the menu) and descend into the functions it calls until you reach the detail you need.
  • Bottom up: start from a low-level landmark (the call to WriteFile) and climb the call stack to find who decided what to write.

Bottom up is usually faster for questions about data; top down for questions about behaviour. Switch whenever you stall.

Recognise library code

A large part of any program is library code: the C runtime, the C++ standard library, compression, image loading, JSON parsing. Do not reverse it. Recognise it and name it:

  • Ghidra's Function ID and IDA's FLIRT signatures name known library functions automatically.
  • Strings give libraries away: inflate 1.2.13 Copyright, stb_image, error messages of well-known libraries.
  • Constants give algorithms away: 0x67452301 starts MD5 and SHA-1, 0xEDB88320 is CRC-32's polynomial, 0x9E3779B9 appears in TEA and in hash functions.

Once you know a function is memcpy or zlib's inflate, you know its arguments and can step over it.

Keep notes

Write as you go, in the disassembler's database and in a plain notes file:

  • the question, and what you have concluded so far;
  • each finding with its evidence: address (as module+offset), what you saw, how you confirmed it;
  • open questions and things you assumed.

Notes make the work resumable tomorrow, shareable with someone else, and checkable when a new build arrives.

Know when to switch

If you have read the same function for an hour, stop and change technique: run it with different inputs and watch, diff two runs (lesson 3.05), look for a library signature, or find a different landmark. Reverse engineering is mostly choosing the right next small question.
