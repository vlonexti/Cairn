Inside a PE File

lesson 1.033 of 5 in milestone 16 min1 practice task

Every .exe and .dll on Windows is a Portable Executable - a DOS header pointing at the PE headers, a file header, an optional header with the entry point, image base and data directories, and a table of sections. RVAs versus file offsets, and how to convert between them.

One format for every program

Windows programs and libraries, .exe, .dll, .sys, all use the Portable Executable (PE) format. It tells the Windows loader how to map the file into memory, where execution starts, which DLLs and functions it needs, and where everything is. Reading it is the first thing every reverse engineering tool does.

Text
file offset 0     +---------------------------+
                  | DOS header ("MZ")         |  e_lfanew at 0x3C -> PE headers
                  | DOS stub                  |  "This program cannot be run in DOS mode."
e_lfanew          +---------------------------+
                  | "PE\0\0" signature        |
                  | File header (20 bytes)    |  machine, number of sections
                  | Optional header (240)     |  entry point, image base, data directories
                  | Section table             |  40 bytes per section
                  +---------------------------+
                  | .text   (code)            |
                  | .rdata  (constants, imports)
                  | .data   (globals)         |
                  | .pdata, .rsrc, .reloc ... |
                  +---------------------------+

All numbers are little-endian. Every structure here is in winnt.h under names like IMAGE_DOS_HEADER and IMAGE_NT_HEADERS64.

The DOS header

The file starts with the two bytes 4D 5A, "MZ", a leftover from MS-DOS that every PE still carries. Of the DOS header's fields only one still matters: the 4-byte e_lfanew at offset 0x3C, the file offset of the real PE headers.

The NT headers

At e_lfanew are the bytes 50 45 00 00, "PE" and two zeros. Then:

The file header (IMAGE_FILE_HEADER, 20 bytes):

Offset Size Field
+0 2 Machine: 0x8664 for x64, 0x14C for 32-bit x86, 0xAA64 for ARM64
+2 2 NumberOfSections
+4 4 TimeDateStamp: when it was linked (or a hash, in reproducible builds)
+16 2 SizeOfOptionalHeader: 0xF0 for 64-bit images
+18 2 Characteristics: flags such as "is a DLL" (0x2000)

The optional header (IMAGE_OPTIONAL_HEADER64, despite the name always present) starts right after it. The fields you will use most:

Offset Size Field
+0 2 Magic: 0x20B means 64-bit (PE32+), 0x10B 32-bit
+16 4 AddressOfEntryPoint: where execution starts, as an RVA
+24 8 ImageBase: the preferred load address, typically 0x140000000 for an .exe
+32 4 SectionAlignment: sections start on multiples of this in memory (0x1000)
+36 4 FileAlignment: and on multiples of this in the file (0x200)
+56 4 SizeOfImage: total size once loaded
+70 2 DllCharacteristics: flags such as ASLR-compatible (0x40)
+112 16 × 8 the data directories

Each data directory is an RVA and a size pointing at a table the loader needs. The important ones by index: 0 exports, 1 imports, 2 resources, 3 exceptions (.pdata), 5 base relocations, 6 debug information, 12 the import address table.

Sections

The section table follows the optional header: NumberOfSections entries of 40 bytes (IMAGE_SECTION_HEADER):

Offset Size Field
+0 8 Name, padded with zeros: .text, .rdata, .data...
+8 4 VirtualSize: size in memory
+12 4 VirtualAddress: where it starts in memory, as an RVA
+16 4 SizeOfRawData: size in the file
+20 4 PointerToRawData: where it starts in the file
+36 4 Characteristics: code (0x20), read (0x40000000), write (0x80000000), execute (0x20000000)

The usual sections: .text for code (read + execute), .rdata for constants, strings and import tables (read only), .data for globals (read + write), .pdata for exception unwinding information, .rsrc for resources such as icons, .reloc for relocations.

A section can be bigger in memory than in the file: .data holds zero-initialised globals that take no space on disk, so its VirtualSize exceeds its SizeOfRawData and the loader fills the rest with zeros.

RVAs and file offsets

Almost every address inside a PE is a relative virtual address (RVA): an offset from wherever the image is loaded in memory. Loaded at ImageBase, the real address is ImageBase + RVA; with ASLR, the actual base differs each run, but RVAs stay the same.

Reading the file instead of memory, you need to turn an RVA into a file offset. Find the section that contains it, then:

file offset = RVA − section.VirtualAddress + section.PointerToRawData

Text
.rdata: VirtualAddress 0x3000, PointerToRawData 0x1E00
RVA 0x3450  ->  0x3450 - 0x3000 + 0x1E00 = 0x2250 in the file

If the RVA falls in the part of a section beyond SizeOfRawData (the zero-filled tail), it has no bytes in the file at all. RVAs below the first section point into the headers, which are mapped at the same offsets in the file.
