Code Caves

lesson 4.033 of 5 in milestone 45 min1 practice task

When a patch needs more room than the instructions it replaces - finding unused space in a binary, jumping out to it with a detour, running the overwritten instructions there, and jumping back - plus adding a section or allocating memory instead.

When a patch does not fit

Turning a je into a jmp fits in the same two bytes. Adding behaviour does not: logging a value, adding a check, calling a function. You need somewhere to put new code. A code cave is unused space in the program where new code can live, reached by a jump from the original code.

Where caves are

  • Padding between functions: MSVC aligns functions to 16 bytes and fills the gaps with CC (lesson 2.02). Each gap is small (up to 15 bytes) but there are many.
  • The end of a section: sections are padded in the file to a multiple of FileAlignment (0x200) with zeros, and in memory to SectionAlignment (0x1000). The space between a section's VirtualSize and its padded size is mapped with the section's permissions, so in .text it is executable. In the file, it is the bytes between VirtualSize and SizeOfRawData.
  • A new section: a PE editor (CFF Explorer, or a few lines of code) can add a section with read+execute permissions and as much room as you like, updating NumberOfSections and SizeOfImage.
  • At run time: VirtualAlloc a page of executable memory, preferably within 2 GB of the module so 5-byte jumps reach it (lesson 4.02).

To find caves in a section, look for runs of 00 or CC at least as long as the code you need, preferably not directly after real code (a run of zeros can be a legitimate array of zeros that something reads).

The detour

Say you want to log every value passed to a function in your own program, at an instruction in the middle of it:

Assembly
140001A30:  8B 47 1C         mov eax, dword ptr [rdi+1Ch]
140001A33:  2B C3            sub eax, ebx
140001A35:  89 47 1C         mov dword ptr [rdi+1Ch], eax
140001A38:  ...

A 5-byte jmp to the cave must overwrite whole instructions, so it takes the first two (3 + 2 = 5 bytes, exactly; with other lengths, the leftover bytes become nops). Those overwritten instructions are called the stolen bytes, and the cave must run them, or the program loses them:

Assembly
; at 140001A30, the patch:
E9 xx xx xx xx               jmp cave

; in the cave:
cave:
    ; ... your new code: save registers, call a logger, restore registers ...
    8B 47 1C                 mov eax, dword ptr [rdi+1Ch]    ; the stolen instructions,
    2B C3                    sub eax, ebx                    ; exactly as they were
    E9 xx xx xx xx           jmp 140001A35                   ; back to the next original instruction

Rules that keep a detour correct:

  1. Steal whole instructions: at least 5 bytes' worth, rounded up to the next instruction boundary.
  2. Do not steal a jump target: if any other code jumps into the middle of the stolen range, that jump now lands inside your jmp. Check the cross-references for each stolen address.
  3. Relocate relative instructions: a stolen call, jmp or jcc, or any instruction with a RIP-relative operand (mov eax, [rip+...]), means something else once it runs at the cave's address. Its displacement must be recalculated for the new location, or the instruction replaced.
  4. Preserve state: your new code must save and restore every register and the flags it changes (pushfq/popfq), and keep the stack 16-byte aligned before any call.

Planning the stolen bytes

Given the lengths of the instructions at the patch point, the number of bytes to steal is the smallest sum of whole instructions that reaches 5:

Text
lengths 3, 2, 3, ...  -> steal 5 (two instructions)
lengths 2, 2, 4, ...  -> steal 8 (three instructions; 3 nops after the jmp)
lengths 7, ...        -> steal 7 (one instruction; 2 nops)

Your disassembler (or the one you build in milestone 5) gives the lengths.
