Reversing a Network Protocol

lesson 6.033 of 5 in milestone 65 min1 practice task

Working out a custom protocol between a client and a server you run yourself - capturing the traffic, finding how messages are framed in a TCP stream, identifying message types, sequence numbers and fields, handling partial messages, and writing a dissector to decode captures automatically.

The setting

A protocol is a file format that arrives in pieces over time. The techniques of lesson 6.02 apply, plus the problem of splitting a stream into messages. Typical legitimate cases: the protocol of an old multiplayer game whose servers are gone, so a community server can be written; a device on your desk with its own control protocol; a debugging tool's link to your own game, which you wrote years ago and documented poorly.

Work with a client and server you run yourself: capture traffic between them on your own machine or network. Other people's services, accounts and traffic are not yours to analyse.

Capturing

Wireshark captures the traffic (lesson 3.04). For a TCP connection, Follow > TCP Stream shows each direction's bytes in order; save each direction as raw bytes for analysis. Do several captures with controlled actions, as with files: connect and disconnect; connect, send one chat message, disconnect; move one step left; move one step right.

If the traffic is encrypted (TLS), the capture shows nothing useful. With your own client you can log the plaintext before encryption, or find the send function in the client and put a logging breakpoint there.

Framing

TCP delivers a stream of bytes, not messages: one send of 20 bytes may arrive as 20 bytes, or as 7 then 13, or glued to the next message. So every protocol over TCP has a framing rule that says where each message ends. The common ones:

Framing Looks like
length prefix every message starts with its length (often 2 or 4 bytes, often big-endian)
delimiter messages end with \n or \r\n (text protocols: HTTP headers, SMTP, IRC)
fixed size every message is N bytes
type then known size a type byte, and each type has a fixed length

To find a length prefix, look at the first bytes of each message and compare with the message's length: 00 0B followed by 11 bytes, 00 05 followed by 5. Watch whether the length counts itself or not.

Inside a message

Once messages are separated:

  • Type: an early byte with few distinct values, which correlates with actions (always 02 when you move, 03 when you chat).
  • Sequence numbers: a field that increases by one with every message in a direction. Gaps tell you about lost or filtered messages; the server's acknowledgements often echo them.
  • Fields: decoded as in a file format. Movement messages hold small signed numbers (FF FF is −1 in 16 bits); chat messages hold a length and text.
  • Variable-length integers (varints): bytes with the top bit meaning "more follows", common in modern formats such as Protocol Buffers.

Replaying a captured message, or sending a hand-made one from a small script, to your server and watching its reaction confirms what a field means.

Partial messages

A decoder must not assume messages arrive whole. It keeps a buffer, appends whatever arrives, and repeatedly takes a complete message from the front while enough bytes are present, leaving any partial tail for next time:

C++
buffer.insert(buffer.end(), received.begin(), received.end());
while (buffer.size() >= 2)
{
    const std::size_t length{ static_cast<std::size_t>((buffer[0] << 8) | buffer[1]) };
    if (buffer.size() < 2 + length) break;          // wait for the rest
    handle(std::span(buffer).subspan(2, length));
    buffer.erase(buffer.begin(), buffer.begin() + 2 + static_cast<std::ptrdiff_t>(length));
}

This same loop appears in every network program, and it is half of the Networking course's work too.

Dissectors

When you understand the protocol, teach Wireshark: a dissector written in Lua (a few dozen lines) decodes your protocol's messages in every capture, showing types, sequence numbers and fields by name. It turns future debugging of the protocol from hex reading into reading.
