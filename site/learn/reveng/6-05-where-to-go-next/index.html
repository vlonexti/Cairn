Keep practising on targets made for it

Reverse engineering is learned by doing, and there is plenty to do legally:

  • Your own programs. Build open-source programs (or your own projects) in Release without the PDB, reverse a function, then compare with the source. It is the best feedback loop there is: you can always check your answer.
  • Crackmes. Small programs written to be reversed, with a password or key to find, sorted by difficulty: crackmes.one has thousands. This milestone's capstone is one.
  • CTF challenges. Capture the Flag competitions have "reversing" and "pwn" categories; past challenges with write-ups are archived (CTFtime lists events). picoCTF is aimed at beginners.
  • FLARE-On. An annual reversing challenge from Google's Mandiant FLARE team, with a dozen or so levels of increasing difficulty and published solutions.
  • Old games and software with official modding or source releases. Many classic games had their source released; comparing their binaries with the source is excellent practice.

Malware analysis, safely

Analysing malware is one of the main professional uses of these skills, and it must be done in an isolated lab: a virtual machine with no shared folders, a snapshot to restore, and no network (or a simulated one such as INetSim). Training material comes with prepared samples. Do not go looking for live malware to practise on, and never run a sample outside the lab.

Books and courses

  • Practical Malware Analysis (Sikorski and Honig): the classic on static and dynamic analysis of Windows programs.
  • Practical Reverse Engineering (Dang, Gazet, Bachaalany): x86, x64, ARM and the Windows kernel.
  • The Ghidra Book (Eagle and Nance): using Ghidra in depth.
  • Windows Internals (Yosifovich and others): what the operating system does underneath everything in milestones 3 and 5.
  • OpenSecurityTraining2's free courses on x86-64 architecture, assembly and debuggers.

The work itself

Reverse engineering skills are used in several kinds of job:

  • Malware analysis and threat intelligence: understanding what malicious software does, to detect and remove it.
  • Vulnerability research: finding security bugs in software, for vendors, security firms or bug bounties.
  • Compatibility and interoperability: emulators, file converters, drivers for hardware with poor documentation.
  • Game development and modding: engine programmers reading compiler output, tools programmers working with old assets, modding communities working with official tools.
  • Software maintenance: every company has a program whose source was lost.

All of them value the same things: careful method, notes with evidence, and judgement about what is appropriate to examine.

What this course gave you

You can read a PE file, find your way through x64 code compiled from C and C++, drive a debugger and know what it is doing underneath, find where data lives and what changes it, patch and hook your own programs, and you have written your own versions of a PE inspector, a control flow graph, a value scanner, a patch engine and a disassembler. The capstone puts it all to work on a program you have never seen.
