Byte Patterns That Survive Rebuilds

lesson 4.055 of 5 in milestone 45 min1 practice task

Every new build moves code around, so fixed addresses break. Byte patterns with wildcards find the same code in any build - which bytes to keep and which to wildcard, keeping a pattern unique, scanning efficiently, and resolving the RIP-relative address inside a match.

Addresses do not survive a rebuild

A patch or a pointer path recorded as game.exe+0x2A1F is correct for exactly one build. Change one line of source, rebuild, and functions shift by a few bytes; everything after them moves. Debug tooling for your own game, patch scripts for an old build, and analysis notes all need a way to find "the same code" in a different build.

The instructions themselves change much less than their addresses. A byte pattern (also called a signature, or an AOB, "array of bytes") describes the code by its bytes, with wildcards for the bytes that vary between builds.

Which bytes vary

Take the instruction that subtracts damage from health:

Assembly
2B C3                   sub eax, ebx
89 47 1C                mov dword ptr [rdi+1Ch], eax
48 8B 0D 6A 2F 01 00    mov rcx, qword ptr [rip+12F6Ah]    ; a global
E8 F5 03 00 00          call UpdateHud
  • Opcodes and registers (2B C3, 89 47, 48 8B 0D, E8): change only if the compiler chooses differently, which is rare for unchanged source.
  • Struct offsets (1C): change only if the struct changes.
  • RIP-relative displacements (6A 2F 01 00) and call/jump displacements (F5 03 00 00): change with almost every build, because they are distances to other code and data that moved.
  • Absolute addresses in data: change with every build and every relocation.

So the pattern is:

Text
2B C3 89 47 1C 48 8B 0D ?? ?? ?? ?? E8 ?? ?? ?? ??

Making it unique

A pattern is only useful if it matches exactly once in the module. Short patterns of common instruction sequences match hundreds of places. Tools that generate signatures (plugins for x64dbg, IDA and Ghidra) start at the instruction you want and keep adding the following instructions, wildcarding the displacements, until the pattern is unique. Good habits:

  • Prefer patterns built from distinctive instructions: uncommon struct offsets, unusual immediates.
  • Keep them short enough to survive small code changes nearby; 15 to 30 bytes is typical.
  • Record the offset of the instruction you care about within the pattern ("the patch goes 2 bytes into the match").
  • Check uniqueness again after every rebuild; the build that breaks a pattern is the one that tells you to make a better one.

Scanning

The simplest scanner compares the pattern at every position, skipping wildcard positions:

C++
for (std::size_t i{ 0 }; i + pattern.size() <= bytes.size(); ++i)
{
    bool match{ true };
    for (std::size_t k{ 0 }; k < pattern.size() && match; ++k)
        match = !pattern[k].has_value() || bytes[i + k] == *pattern[k];
    if (match) hits.push_back(i);
}

That is fast enough for one module of a few megabytes. Scan only executable sections (.text) for code patterns; it is quicker and avoids accidental matches in data. Faster scanners first look for the pattern's rarest fixed byte with memchr, or use SIMD to compare 16 or 32 bytes at once.

Resolving what a match points at

Often the pattern finds an instruction that refers to what you want: a global variable, a function. The wildcards hide the displacement, but once you have a match you can read it and compute the target, exactly as the processor does:

Text
match at  game.exe+0x2A1F:  48 8B 0D 6A 2F 01 00   mov rcx, [rip+0x12F6A]
instruction starts at match + 5, is 7 bytes long, displacement at its byte 3
target = (address of the instruction + 7) + 0x12F6A

The same for a call (E8, 5 bytes, displacement at byte 1). This is how a pattern finds a global or function in every build: the pattern survives, and the displacement inside it tells you where the thing is this time.
