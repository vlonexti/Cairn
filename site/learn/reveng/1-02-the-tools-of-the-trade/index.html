The Tools of the Trade

lesson 1.022 of 5 in milestone 15 min1 practice task

Disassemblers and decompilers for static analysis, debuggers for dynamic analysis, hex editors, PE viewers and system monitors - what each kind of tool does, the free ones worth installing, and a first look at your own program in each.

Two ways of looking

Reverse engineering has two halves that you switch between all the time:

  • Static analysis: reading the program without running it. Its file, its machine code, its strings and data.
  • Dynamic analysis: running it and watching. Stepping through code, inspecting memory, recording what it touches.

Static analysis sees everything but has to guess what values things have. Dynamic analysis sees real values but only the paths the program actually takes. Each answers the other's questions.

Disassemblers and decompilers

A disassembler turns machine code back into assembly text. A decompiler goes a step further and produces C-like pseudocode. Both build a database of the program: functions, cross-references, names and comments that you add as you understand things.

Tool Notes
Ghidra free and open source (from the NSA), disassembler and decompiler, scripting in Java and Python
IDA Free the long-time industry standard; the free version decompiles x64 using a cloud service
Binary Ninja modern, scriptable; a free cloud version
Compiler Explorer (godbolt.org) not for binaries, but the best way to learn what source compiles into

Decompiler output is a guess. It is usually close, sometimes wrong, and never has your original names. Treat it as a map, and check important details in the disassembly.

Debuggers

A debugger runs a program under control: breakpoints, single-stepping, viewing and changing registers and memory.

Tool Notes
Visual Studio debugger best with source and symbols; shows disassembly too (Debug > Windows > Disassembly)
x64dbg free, open source, made for working without source; the usual choice for reversing on Windows
WinDbg Microsoft's debugger; powerful command language, crash dumps, kernel debugging

Looking at files and bytes

  • A hex editor (HxD, or ImHex, which also understands file structures) shows a file's raw bytes.
  • A PE viewer (PE-bear, CFF Explorer, or dumpbin /headers /imports from Visual Studio's Developer Command Prompt) shows the structure of .exe and .dll files: headers, sections, imports.
  • Strings tools (Sysinternals strings, or the strings window in Ghidra and x64dbg) list readable text in a file. Error messages and file names in a program tell you a lot before you read a single instruction.

Watching behaviour

The Sysinternals tools from Microsoft are essential:

  • Process Monitor records every file, registry and network operation a process makes.
  • Process Explorer shows each process's DLLs, handles, threads and memory.
  • API Monitor (third party) logs calls to Windows API functions with their arguments.

A first look at your own program

Build a small program in Visual Studio in Release configuration, so the optimiser has done its work:

C++
#include <cstdio>

int score(int hits, int misses)
{
    return hits * 10 - misses * 3;
}

int main(int argc, char**)
{
    std::printf("score: %d\n", score(argc * 4, argc));
}

Then:

  1. Open the .exe in a PE viewer and find its sections and its imports. You will see printf is not imported directly; the C runtime DLL (ucrtbase.dll or vcruntime140.dll plus api-ms-win-crt-*) is.
  2. Run strings on it: score: %d is there, among many strings from the runtime.
  3. Open it in Ghidra or x64dbg and find main. You may find score has disappeared entirely: the optimiser inlined it and folded the arithmetic. That is the first lesson of reverse engineering: the binary is what the compiler made, not what you wrote.

Keep the PDB (the symbol file Visual Studio writes beside the .exe) out of the way when you practise. With it, every tool shows your function names; without it, you see what a reverse engineer normally sees.
