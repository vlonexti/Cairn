Imports, Exports and Relocations

lesson 1.044 of 5 in milestone 15 min1 practice task

How a PE says which DLL functions it needs - import descriptors, the import name table and the import address table the loader fills in - how a DLL publishes its own functions in the export directory, and the base relocations that let an image load at any address.

Imports tell a story

A program reaches Windows and other libraries through imported functions. The import table lists every DLL and every function the program asked the linker for. Before reading any code, the imports alone tell you a great deal:

  • CreateFileW, ReadFile, WriteFile: it works with files.
  • RegOpenKeyExW, RegSetValueExW: it reads or writes the registry.
  • WSAStartup, connect, send, recv (from ws2_32.dll): it talks over the network.
  • CreateProcessW, OpenProcess, ReadProcessMemory: it starts or inspects other processes.
  • Very few imports, just LoadLibraryA and GetProcAddress: it looks up what it needs at run time, which hides its intentions from this kind of reading.

The import directory

Data directory 1 points at an array of import descriptors (IMAGE_IMPORT_DESCRIPTOR, 20 bytes each), one per DLL, ending with one that is all zeros:

Offset Field
+0 OriginalFirstThunk: RVA of the import name table (INT)
+12 Name: RVA of the DLL's name, a zero-terminated string such as KERNEL32.dll
+16 FirstThunk: RVA of the import address table (IAT)

The INT is an array of 8-byte entries (in 64-bit images), ending with a zero entry. Each entry says which function is wanted:

  • If the top bit is set (0x8000000000000000), the low 16 bits are an ordinal: the function's number in the DLL's export table.
  • Otherwise it is the RVA of an IMAGE_IMPORT_BY_NAME: a 2-byte hint (a guess at the function's position in the DLL's name list) followed by the function's name as a zero-terminated string.

In the file, the IAT holds the same entries as the INT. When the program loads, the loader looks up each function in its DLL and overwrites each IAT entry with the function's real address. Calls to imported functions in the code are indirect calls through the IAT:

Assembly
call qword ptr [rip+0x1A2B]   ; the IAT slot for CreateFileW

That is why a disassembler can label such calls by name: it knows which IAT slot holds which import.

Exports

A DLL publishes its own functions in the export directory (data directory 0, IMAGE_EXPORT_DIRECTORY):

Offset Field
+12 Name: RVA of the DLL's own name
+16 Base: the ordinal of the first function, usually 1
+20 NumberOfFunctions
+24 NumberOfNames
+28 AddressOfFunctions: RVA of an array of function RVAs
+32 AddressOfNames: RVA of an array of name RVAs, sorted alphabetically
+36 AddressOfNameOrdinals: RVA of an array of 2-byte indexes into the functions array

Finding a function by name, as GetProcAddress does: search the sorted names; at the same position in the name-ordinals array is an index; at that index in the functions array is the function's RVA. A function can also be exported by ordinal only, with no name.

If a function's RVA points inside the export directory itself, it is a forwarder: the "address" is really a string such as NTDLL.RtlAllocateHeap, telling the loader to look in another DLL. Many kernel32.dll exports are forwarded this way.

Base relocations

Code contains some absolute addresses, for example a pointer to a global stored in a table. They are computed assuming the image loads at ImageBase. With ASLR it usually loads elsewhere, so each such address must be adjusted by the difference.

The base relocation table (data directory 5, usually the .reloc section) lists every place that needs it, grouped by 4 KB page: a block header with the page's RVA and the block size, then 2-byte entries whose top 4 bits are a type (10, IMAGE_REL_BASED_DIR64, for a 64-bit address) and low 12 bits an offset within the page. The loader adds actualBase - ImageBase to the 8 bytes at each location.

x64 code itself mostly uses RIP-relative addressing ([rip+0x1234]), which needs no relocation at all; relocations are mostly for pointers stored in data. That is one reason x64 programs relocate cheaply.

For a reverse engineer this matters when comparing a running program with its file: bytes at relocated locations differ between the two by exactly the load difference, and tools (and the byte patterns of milestone 4) must allow for it.
