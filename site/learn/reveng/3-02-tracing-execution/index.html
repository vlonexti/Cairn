Tracing Execution

lesson 3.022 of 5 in milestone 35 min1 practice task

Following what a program actually does - stepping into, over and out, rebuilding the call stack from return addresses, naming addresses as module plus symbol plus offset, conditional and logging breakpoints, and recording traces.

Getting to the interesting code

Static analysis gives you a map; dynamic analysis tells you which roads are travelled. The usual way in is a breakpoint on something you can name:

  • an imported function the behaviour must use: CreateFileW for "it opens a file", send for "it sends a message";
  • the code that references a string you found in triage;
  • an exported function of a DLL.

When it stops, the call stack tells you how the program got there, and the caller is usually the code you want.

Step into, over and out

Command Usual key Does
Step into F7 (x64dbg), F11 (VS) run one instruction; follow calls into the function
Step over F8 (x64dbg), F10 (VS) run one instruction; run a whole call as one step
Run to return Ctrl+F9 (x64dbg), Shift+F11 (VS) run until the current function returns
Run to cursor F4 run until a chosen instruction

Stepping over a call to a library function you do not care about, and out of functions you have seen enough of, keeps you in the code that matters.

The call stack

Every call pushes a return address, so at any moment the stack holds a chain of addresses back through every active function. Turning that into a list of frames is unwinding:

  • With frame pointers: some code keeps rbp pointing at the saved rbp of the caller, with the return address just above it. Then the stack is a linked list: [rbp] is the caller's rbp, [rbp+8] the return address. Follow it until rbp is 0.
  • Without frame pointers, which is the usual case for optimised x64 Windows code, the debugger uses the unwind information in .pdata (lesson 2.02): for each function it knows how far rsp moved and where registers were saved, so it can compute the caller's rsp and find the return address. This is why x64 call stacks on Windows are reliable even in Release builds.

Naming addresses

Raw addresses change every run (ASLR), so debuggers show them as module!symbol+offset: the module the address is in, the nearest symbol at or below it, and the distance. Without symbols, module+offset: game.exe+0x1074, which is the same every run, because it is an RVA (lesson 1.03). Always record addresses this way in your notes; an absolute address from yesterday's session means nothing today.

Conditional and logging breakpoints

A breakpoint on CreateFileW in a program that opens hundreds of files is useless unless it stops only on the one you care about. Debuggers let you attach a condition:

  • x64dbg: streq(utf16(rcx), "C:\\Saves\\slot1.dat"), or a simpler test on a register such as rdx == 0xC0000000.
  • Visual Studio: a condition in C++ syntax on variables when you have symbols.
  • WinDbg: bp kernel32!CreateFileW ".if (...) {} .else {gc}".

A logging breakpoint (a tracepoint in Visual Studio) prints a message and continues without stopping: "CreateFileW {utf16@rcx}" logs every file the program opens with its name, which is often all you need.

Traces

A trace records every instruction executed (or every call, or every block) between two points. x64dbg's trace recording and WinDbg's Time Travel Debugging go further: TTD records a whole run so you can step backwards through it, put a data breakpoint on a value and run backwards to see who last wrote it. For a hard question ("where did this wrong value come from?"), a recorded trace turns hours of re-running into minutes.

Traces are large: millions of instructions per second of execution. Trace small windows, between two breakpoints around the behaviour you care about.
