Reading a Process's Memory Map

lesson 5.033 of 5 in milestone 55 min1 practice task

Seeing a running process the way debuggers do, with documented Windows APIs - opening a process with the right access rights, walking its address space with VirtualQueryEx, understanding states, protections and types, listing its modules, and reading memory safely.

The documented way in

Debuggers, profilers, Process Explorer and memory scanners all look at other processes through a handful of documented Windows functions. Using them on your own programs is how you build inspection tools for them, such as an external stats viewer for a game you are developing (the Game Development course builds one).

First, open the process with only the access you need:

C++
HANDLE process{ OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_READ, FALSE, pid) };
if (!process) { /* GetLastError(): 5 = access denied */ }

Windows checks the request against the target's security. You can open processes running as your own user; processes of other users, services and protected processes (antivirus, DRM, system processes) refuse. That is the security boundary working as intended.

Walking the address space

VirtualQueryEx describes the region of pages containing an address. Starting at 0 and jumping from region to region walks the whole address space:

C++
MEMORY_BASIC_INFORMATION info{};
for (std::uintptr_t at{ 0 }; VirtualQueryEx(process, reinterpret_cast<void*>(at), &info, sizeof(info)) == sizeof(info);
     at = reinterpret_cast<std::uintptr_t>(info.BaseAddress) + info.RegionSize)
{
    // info.BaseAddress, info.RegionSize, info.State, info.Protect, info.Type, info.AllocationBase
}

Each region is a run of pages with identical attributes:

Field Values
State MEM_FREE (0x10000), MEM_RESERVE (0x2000), MEM_COMMIT (0x1000)
Protect PAGE_NOACCESS 0x01, PAGE_READONLY 0x02, PAGE_READWRITE 0x04, PAGE_WRITECOPY 0x08, PAGE_EXECUTE 0x10, PAGE_EXECUTE_READ 0x20, PAGE_EXECUTE_READWRITE 0x40, PAGE_EXECUTE_WRITECOPY 0x80, plus the modifier PAGE_GUARD 0x100
Type MEM_IMAGE (a mapped .exe or .dll), MEM_MAPPED (a mapped file or shared memory), MEM_PRIVATE (heap, stacks, VirtualAlloc)
AllocationBase the start of the VirtualAlloc (or mapping) this region belongs to

One allocation often shows up as several regions: an image is one allocation with a region per section (.text as PAGE_EXECUTE_READ, .data as PAGE_READWRITE...), and a thread stack is one reservation with a committed part, a guard page and a reserved remainder. Grouping regions by AllocationBase reassembles them.

PAGE_WRITECOPY is how image pages that are writable start out: shared between processes until one writes, then copied for that process alone.

Modules

To list loaded modules with their names and base addresses:

C++
HANDLE snap{ CreateToolhelp32Snapshot(TH32CS_SNAPMODULE | TH32CS_SNAPMODULE32, pid) };
MODULEENTRY32W entry{ sizeof(entry) };
for (BOOL ok{ Module32FirstW(snap, &entry) }; ok; ok = Module32NextW(snap, &entry))
{
    // entry.szModule, entry.modBaseAddr, entry.modBaseSize, entry.szExePath
}
CloseHandle(snap);

(EnumProcessModulesEx with GetModuleBaseNameW is the other route.) With the module list you can turn any address into module+offset (lesson 3.02), and the module's base plus an RVA into a real address.

Reading memory

C++
std::uint32_t health{};
SIZE_T got{};
if (ReadProcessMemory(process, reinterpret_cast<void*>(address), &health, sizeof(health), &got) && got == sizeof(health))
{
    // use health
}

Rules that keep a reader robust:

  • Check every read. Memory can be freed between your query and your read; ReadProcessMemory then fails (error 299, partial copy).
  • Only read committed, readable regions. Skip PAGE_NOACCESS and PAGE_GUARD regions; touching a guard page would change the target's behaviour.
  • Read in large chunks when scanning (a whole region at a time), not one value per call: each call is a trip into the kernel.
  • The target keeps running. Values can change between reads; a consistent snapshot needs the target paused (DebugActiveProcess, or suspending its threads).

Writing (WriteProcessMemory, needing PROCESS_VM_WRITE | PROCESS_VM_OPERATION) and creating threads in another process are what debuggers do to your own programs; outside your own software, they are exactly what security software watches for.
