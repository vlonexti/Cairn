Recognising Functions

lesson 2.022 of 5 in milestone 25 min1 practice task

Where functions start and end in a binary without symbols - prologues that save registers and reserve stack, epilogues, leaf functions, int3 padding, the .pdata table that lists every function, thunks and tail calls, and following the C runtime's start-up code to main.

No labels in machine code

A .exe does not record where one function ends and the next begins. The bytes run on; only the call instructions and a few tables tell you where functions are. Disassemblers find functions with a mix of the evidence below, and when they get it wrong (and they sometimes do) you need to recognise the signs yourself.

Prologues

A function that calls others or uses non-volatile registers starts by setting itself up:

Assembly
mov  qword ptr [rsp+8], rbx     ; save rbx in the shadow space the caller reserved
push rdi                        ; save rdi
sub  rsp, 30h                   ; reserve stack: 0x20 shadow space for calls it makes, plus locals

The common forms in MSVC output:

Bytes Instruction
48 89 5C 24 08 mov [rsp+8], rbx (save to shadow space)
40 53 push rbx with a do-nothing REX prefix, used so the instruction is 2 bytes for hot-patching
55, 56, 57 push rbp, push rsi, push rdi
41 54 ... 41 57 push r12 ... push r15
48 83 EC 28 sub rsp, 28h (small frame)
48 81 EC 50 01 00 00 sub rsp, 150h (large frame)

The stack must be 16-byte aligned at every call. On entry the return address has just been pushed, so rsp is 8 more than a multiple of 16; that is why frames are odd multiples of 8 when nothing else is pushed: sub rsp, 28h, 38h, 48h.

Functions with large local arrays first call __chkstk (it touches each new page of stack in order, for the guard page of the Pointers and Memory course). Functions with buffers start with the /GS cookie: mov rax, [__security_cookie]; xor rax, rsp; mov [rsp+...], rax, and end with the matching check.

Epilogues

The end undoes the start, in reverse:

Assembly
mov  rbx, qword ptr [rsp+40h]   ; restore rbx (8 + 30h + 8 further up now)
add  rsp, 30h
pop  rdi
ret

There can be several epilogues in one function, one per return, or one shared epilogue that every path jumps to.

Leaf functions

A function that calls nothing and needs no non-volatile registers needs no frame at all:

Assembly
lea  eax, [rcx+rdx*2]           ; return a + b * 2
ret

Small leaf functions are common, and they often have no recognisable prologue. In Release builds many of them disappear entirely, inlined into their callers.

int3 padding

MSVC starts functions on 16-byte boundaries and fills the gaps between them with CC bytes, the int3 breakpoint instruction. A run of CCs after a ret or a jmp is a reliable sign that a new function follows. (CC can also appear inside an instruction, as part of an immediate or displacement, so it is evidence, not proof.)

.pdata: the list of functions

On x64 Windows there is a better source. The exception directory (data directory 3, the .pdata section) holds a RUNTIME_FUNCTION entry for every function that has a frame: three RVAs, the function's start, its end, and its unwind information. Windows needs these to unwind the stack for exceptions and to walk call stacks in a debugger, so they are always present and always right. Disassemblers use them first; leaf functions without frames are the only ones missing.

The unwind information also records exactly what the prologue does (which registers were pushed, how big the frame is), which is how a debugger rebuilds a call stack without frame pointers.

Thunks and tail calls

  • A thunk is a tiny function that only jumps somewhere else: jmp qword ptr [__imp_CreateFileW] for an import, or a stub that adjusts this and jumps to the real member function.
  • A tail call is a function ending with jmp OtherFunction instead of call and ret: the optimiser reuses the frame. Do not mistake that jmp for a jump inside the same function.

Finding main

The entry point in the PE header is not your main. In an MSVC program it is mainCRTStartup, which sets up the C runtime, runs global constructors and then calls main. A reliable route: from the entry point, follow the jump to __scrt_common_main_seh; near its end it calls _get_initial_narrow_environment, __p___argv and __p___argc and then a function with those results in r8, rdx and ecx: that call is main(argc, argv, envp). For a GUI program it is WinMain, called with the instance handle in rcx. With practice, finding main takes a minute.
