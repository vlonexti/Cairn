C++ in Machine Code

lesson 2.055 of 5 in milestone 25 min1 practice task

How C++ features look once compiled by MSVC - this in rcx, constructors that install the vtable pointer, virtual calls through vtable slots, RTTI and the type names it leaves in the binary, name mangling, and the layouts of std::string and std::vector.

Methods are functions with this

A member function is an ordinary function with a hidden first argument, this, so in MSVC x64 it arrives in rcx. Code that reads [rcx+...] at the top of a function and never sets rcx first is usually a method reading its own members:

Assembly
Player::takeDamage:
    sub  dword ptr [rcx+0Ch], edx       ; this->health -= amount
    ret

Ordinary arguments shift up one place: the first visible argument is in rdx, the second in r8.

Constructors install the vtable

A class with virtual functions has a hidden pointer at offset 0 to its class's vtable (lesson 3.05 of the Pointers and Memory course). The constructor writes it before anything else:

Assembly
Archer::Archer:
    lea  rax, [Archer::`vftable']       ; the address of Archer's table in .rdata
    mov  qword ptr [rcx], rax           ; this->vptr = &table
    mov  dword ptr [rcx+8], 64h         ; this->health = 100
    mov  rax, rcx                       ; constructors return this
    ret

A derived class's constructor calls the base constructor first (which writes the base vtable) and then overwrites offset 0 with its own. Finding every place that stores a particular vtable address finds every constructor of that class.

The vtable itself, in .rdata, is an array of function addresses: listing it gives you every virtual function of the class, in declaration order.

Virtual calls

A call through a vtable is unmistakable:

Assembly
    mov  rax, qword ptr [rcx]           ; the object's vtable pointer
    call qword ptr [rax+18h]            ; slot 3 (0x18 / 8) of the table

The displacement divided by 8 is the slot number. To find which function runs, find the object's actual class (its constructor, or the vtable pointer seen in memory in a debugger) and read that slot of its table. The same call can reach different functions for different objects; that is the point of virtual functions, and it is why static analysis alone sometimes cannot say where a call goes.

RTTI

If run-time type information is on (the default in MSVC; /GR), every polymorphic class leaves its name in the binary. Just before each vtable (at vftable - 8) is a pointer to a Complete Object Locator, which leads to a type descriptor containing the mangled class name:

Text
.?AVArcher@@        class Archer
.?AVUnit@Game@@     class Game::Unit
.?AUVec3@@          struct Vec3

These strings survive even in Release builds with no PDB, so searching a binary for .?AV lists its polymorphic classes, and the locator next to each vtable tells you which class the table belongs to. Ghidra and IDA read RTTI automatically and name vtables and classes for you.

Name mangling

C++ allows overloading, so the linker needs a unique name for each function. MSVC encodes the scope, name and signature into a decorated name:

Decorated Means
?update@Player@@QEAAXM@Z public: void Player::update(float)
?attack@Enemy@Game@@QEAAHH@Z public: int Game::Enemy::attack(int)
??0Player@@QEAA@XZ Player::Player(void): the constructor
??1Player@@UEAA@XZ virtual Player::~Player(void): the destructor

The pieces after ? up to @@ are the name and then its enclosing scopes, innermost first. ??0 and ??1 mark constructors and destructors. The undname tool from Visual Studio decodes any of them fully. You meet decorated names in exports, in imports from C++ DLLs, and in RTTI.

Standard library layouts

Recognising standard containers in memory saves a lot of time. In MSVC's Release builds:

std::string is 32 bytes:

Offset Holds
0x00 either the text itself (up to 15 characters, the small string buffer) or a pointer to it on the heap
0x10 the size
0x18 the capacity: 15 while the text is inline

So code that does cmp qword ptr [rcx+18h], 0Fh and then picks between rcx and [rcx] is reading a std::string's text: "if the capacity is above 15, follow the pointer".

std::vector<T> is three pointers, 24 bytes: first element, one past the last element, end of the allocated capacity. Its size is (end - begin) / sizeof(T), which compiles to a subtraction and a shift or division: sub rax, rcx; sar rax, 3 is the size of a vector of 8-byte elements.

std::unique_ptr<T> is just the pointer; std::shared_ptr<T> is two pointers, object then control block.

Debug builds add checking members and change these layouts; always reverse the build configuration that you actually have.
