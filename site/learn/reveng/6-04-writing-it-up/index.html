Writing It Up

lesson 6.044 of 5 in milestone 65 min

Turning an analysis into something others can use - the structure of a good report, evidence and reproducibility, annotated databases and headers, clean-room reimplementation, and handling security findings responsibly through coordinated disclosure.

Analysis nobody can use is wasted

The output of reverse engineering is understanding, and understanding that lives only in your head disappears. Whether it is for a teammate, your future self, or the maintainers of software you found a bug in, the work ends with writing it up.

The shape of a report

A useful report answers, in this order:

  1. Summary: the question and the answer, in a few sentences. Many readers stop here.
  2. Scope: exactly what was analysed: file name, version, hash (SHA-256), date, and which parts.
  3. Findings: one section each, with the claim, the evidence (addresses as module+offset, disassembly excerpts, captured bytes, screenshots) and how confident you are.
  4. How to reproduce: the steps someone else follows to see the same thing.
  5. Open questions: what you did not resolve, and what you assumed.

Evidence and reproduction are what separate a finding from an opinion. "The save file has a CRC-32 at offset 0x7C" is a claim; "changing any byte changes offset 0x7C–0x7F; the value matches crc32(bytes[0..0x7C)) in all 23 samples; the loader at game.exe+0x4A1B0 compares it and shows Corrupt save on mismatch" is a finding.

Artefacts

Alongside the report, keep what lets someone continue the work:

  • The disassembler database with your names, types and comments.
  • Headers for recovered structures, exported from the database or written by hand.
  • Parsers and scripts that encode the knowledge in executable form: a format parser is its own specification, and its tests are your evidence.
  • Signatures (lesson 4.05) for the important functions, so the work transfers to the next version.

Reimplementation

A common end goal is a new program that does what the old one did: a file converter, a replacement server, a source port of an old game. When rights matter, teams use a clean-room process: one person reverse engineers and writes a specification describing behaviour and formats; another, who never sees the original code, implements from the specification. That keeps the new code from being a copy of the old. Whether that is needed depends on the situation and the law; when it matters, take advice before starting.

Security findings

If your analysis turns up a vulnerability, in your own program or in software you were authorised to examine, the responsible path is coordinated disclosure:

  1. Report it privately to the maintainers (a security contact, SECURITY.md, a bug bounty programme), with enough detail to reproduce and fix it.
  2. Give them reasonable time to release a fix; 90 days is a common default.
  3. Publish details only after a fix is available, or by agreement.

Never test a vulnerability against systems you do not own or have explicit permission to test. Bug bounty programmes publish their rules precisely so that research within them is welcome.
