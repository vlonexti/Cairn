Comparing Runs

lesson 3.055 of 5 in milestone 35 min1 practice task

Differential analysis - snapshot memory before and after an action and diff it, compare which code ran with and without a feature (code coverage diffing), compare files a program wrote, and use time travel debugging to answer questions backwards.

Change one thing, compare the rest

Many reverse engineering questions have the form "what part of the program handles X?". The most efficient way to answer them is not to read more code, but to run the program twice, once doing X and once not, and compare. Whatever differs is about X. This is differential analysis, and it works on memory, on code coverage and on files.

Memory snapshots

Take a snapshot of a region of memory (an object, a heap, a whole module's data section), do one thing in the program, and take another. The diff shows exactly which bytes the action changed:

Text
before jump:   ...  00 00 C8 42  00 00 00 00  01 00 00 00 ...
after jump:    ...  00 00 F0 42  00 00 A0 41  00 00 00 00 ...
                    ^ y position  ^ vertical    ^ on ground:
                      100.0 ->      speed         1 -> 0
                      120.0         0 -> 20.0

Read changed 4-byte groups both as integers and as floats: 00 00 C8 42 is the float 100.0, which is far more meaningful than the integer 1 120 403 456. Changes by small, sensible amounts are interesting; values that change on every snapshot whatever you do (timers, frame counters, random state) are noise that you learn to filter out by taking a third snapshot without doing anything.

Code coverage diffing

The same idea applies to code. Record which basic blocks execute (a coverage tool, a trace, or the Lighthouse plugin for Ghidra and IDA with coverage files from DynamoRIO's drcov) during two runs:

  1. Run A: start the program, open the menu, close it.
  2. Run B: start the program, open the menu, press the button you are curious about, close it.

Blocks executed in B but not in A are the code for that button. A function with a thousand blocks often has only a dozen in the difference, and that is where to start reading.

File diffing

When a program writes files, compare them across small changes. Save a game, move one step, save again, and diff the two save files (lesson 1.02's practice): the bytes that changed hold the position. Change the player's name and save again: the bytes that changed are the name, and the bytes before them are often its length. Lesson 6.02 builds a whole file format this way.

Time travel debugging

WinDbg's Time Travel Debugging (TTD) records an entire run of a program into a trace file. Afterwards you can replay it in the debugger and move both forwards and backwards:

  • g- runs backwards to the previous breakpoint.
  • A data breakpoint plus g- finds the last write to a value before the current moment: "who set this to the wrong value?" is answered in one command.
  • Queries such as dx @$cursession.TTD.Calls("kernel32!CreateFileW") list every call to a function anywhere in the recording, with arguments.

Recording slows the program down a great deal and produces large files, so record the shortest run that shows the behaviour. For your own programs' hardest bugs, TTD is often the fastest tool there is.
