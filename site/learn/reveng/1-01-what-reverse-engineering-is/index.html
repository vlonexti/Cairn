What Reverse Engineering Is

lesson 1.011 of 5 in milestone 15 min

Reverse engineering is working out how a program works from the program itself, without its source. Why people do it - debugging, security, compatibility, preservation, learning - the ground rules about what you may examine, and how this course keeps every target your own.

Working backwards

A compiler turns source code into machine code and throws most of the meaning away: names of local variables, comments, the structure of classes, often whole functions that it inlined. Reverse engineering is working backwards from what is left, the machine code, the data, the program's behaviour, to an understanding of how it works.

You already do a little of it every time you debug a Release build and the debugger shows assembly instead of your source, or when you read a crash dump. This course turns that into a skill.

Why people do it

  • Debugging without source. A crash inside a library you only have as a DLL, a driver, or an old build of your own program whose source has changed since.
  • Security. Finding vulnerabilities so they can be fixed; analysing malware to understand what it does and how to detect and remove it; checking that a program does what its makers say.
  • Compatibility and interoperability. Reading a file format or protocol so your program can open the files or talk to the device. Wine, LibreOffice's support for old document formats and many game mods began this way.
  • Preservation. Keeping old software running after its company is gone: emulators, source ports of classic games, recovered file formats.
  • Learning. Seeing what the compiler really made of your code is the best way to understand optimisation, calling conventions and C++ objects.

The ground rules

Reverse engineering is a tool, and like any tool the question is what you point it at. Before you examine any program, ask:

  1. Is it mine? Programs you wrote and compiled are always fine to take apart. Most of this course works on exactly those.
  2. Do I have permission? Practice targets made to be reversed (crackmes, CTF challenges, this course's targets), bug bounty programs with published rules, and work your employer or client authorised in writing.
  3. What does the licence say, and the law where I live? Many end-user licences forbid reverse engineering. Some countries give limited rights to do it anyway for interoperability or security research; the details differ by country and change over time. When it matters, the answer comes from a lawyer, not a forum post.
  4. Does it affect other people? Anything that touches an online service, another player, or another person's computer or data is off limits without explicit permission, whatever the technique.

This course never goes near defeating copy protection, cheating in online games, bypassing anti-cheat or anti-debugging systems, or getting into systems you do not own. Those are not only against the rules of the services involved; they hurt the people on the other side.

Note

Every target in this course is either a program you build yourself in Visual Studio or a practice target the course provides: byte arrays, simulated memory, file formats and a tiny virtual machine designed to be taken apart.

What you need to know already

You should be comfortable with C++ and have seen some x64 assembly: registers, mov, add, cmp, jumps, call and ret. The Assembly course or milestone 7 of the Game Development course covers that. Milestone 2 here starts with a refresher aimed at reading rather than writing.

The Pointers and Memory course is useful background too: reverse engineering is mostly memory, offsets and pointers.

How the course works

Each lesson describes how the work is done with real tools on real programs, and the practice turns the core of each technique into code you write and test: parsing a PE file, finding functions, rebuilding a call stack, scanning memory, encoding jumps, disassembling instructions. By the end you will have written small versions of most of the tools you use.
