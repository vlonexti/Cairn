Finding Where Data Lives

lesson 3.033 of 5 in milestone 35 min1 practice task

Locating a value in a running program you built - value scanning by narrowing a set of candidate addresses, the types and alignments to search for, then a data breakpoint to find the code that writes it, and working back from that code to the structure and the pointer path that reach it.

The problem

You can see a number on the screen of your own game: the player has 87 health. Where in memory is it, and which code changes it? You have no symbols, or the value is deep inside objects created at run time. Three steps answer it: scan for the value, watch the address to find the code, then walk back from the code to the structures around it.

Value scanning

A value scanner (the tool you build in this milestone's project) reads all of the process's readable, writable memory and keeps a list of candidate addresses:

  1. First scan: every address where the 4 bytes equal 87. In a real program that is thousands of hits.
  2. Change the value in the program (take some damage: 87 becomes 72).
  3. Next scan: of the previous candidates, keep only those that now hold 72.
  4. Repeat until one or a few addresses remain.

When you do not know the exact value (a health bar with no number), scan for unknown first (every address is a candidate), then narrow with changed, unchanged, increased and decreased scans: lose health, scan "decreased"; do nothing, scan "unchanged"; heal, scan "increased".

To scan efficiently you have to guess the type and alignment right:

Value Likely stored as Alignment
health, ammo, score int32_t (sometimes int16_t or a float) 4
position, speed, a fraction float (or double) 4 (8)
money in a big game int64_t or double 8
a flag bool or a byte 1

Compilers align members (Pointers and Memory course, lesson 3.01), so scanning only at multiples of the size is both faster and avoids false hits from overlapping bytes. Floats are compared with a tolerance, because the shown value is rounded: 87 on screen may be 86.99997 in memory.

Note

Do this on your own programs: the debug build of a game you are writing, or the sample programs of the Game Development course. Online games, and games that forbid it, are off limits.

Data breakpoints: who writes this?

Once you have the address, set a hardware write breakpoint on it (lesson 3.01): in x64dbg, right-click the address in the dump, Breakpoint > Hardware, Write, Dword; in Visual Studio, Debug > New Breakpoint > Data Breakpoint. Then take damage again. The debugger stops on the instruction just after the write:

Assembly
game.exe+0x2A1F:  sub dword ptr [rbx+1Ch], eax     ; the write
game.exe+0x2A22:  mov ecx, dword ptr [rbx+1Ch]     ; <- execution stops here

Now you know the code (game.exe+0x2A1F), and the operand tells you more: rbx points at the object that contains the health, and health is at offset 0x1C in it. So:

object address = health address − 0x1C

That one fact turns a lone address into a structure. Other accesses through rbx in the same function are other members of the same object, and reverse engineering the struct begins (lesson 2.04).

Walking back to a stable path

The health address changes every time you start the game, because the player object is created on the heap. To find it again next time you need a pointer path from something stable (Pointers and Memory course, lesson 3.03):

  1. You know the object's address (health − 0x1C). Scan memory for pointers with that value: 8-byte values equal to the object address. Those are the places that point at the player.
  2. For each one, find what contains it: perhaps a World object's player array at offset 0x28.
  3. Repeat from that object until you reach a static address inside the module's image: game.exe+0x51A8.

The result is a path such as game.exe+0x51A8 → 0x28 → 0x1C that finds the health in every run. Tools automate this as a pointer scan: from the target, search backwards for chains of pointers within some offset limit (the Pointers and Memory course's milestone 3 project built exactly that engine). With your own program you can also just read the source, but doing it by hand once makes it clear what every debugger and memory tool is doing.
