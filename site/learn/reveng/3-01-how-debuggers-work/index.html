How Debuggers Work

lesson 3.011 of 5 in milestone 35 min1 practice task

A debugger is an ordinary program using the Windows debugging API - debug events, software breakpoints made from a single int3 byte, single-stepping with the trap flag, the four hardware breakpoint registers, and first- and second-chance exceptions.

A program that controls another

A debugger is not magic built into Windows; it is a program that uses a documented API. It either starts the target with CreateProcessW(..., DEBUG_ONLY_THIS_PROCESS, ...) or attaches to a running one with DebugActiveProcess(pid). From then on, whenever something interesting happens in the target, Windows freezes every thread of the target and reports a debug event to the debugger:

C++
DEBUG_EVENT event{};
while (WaitForDebugEvent(&event, INFINITE))
{
    switch (event.dwDebugEventCode)
    {
    case CREATE_PROCESS_DEBUG_EVENT: /* the process started: its image base, entry point */ break;
    case LOAD_DLL_DEBUG_EVENT:       /* a DLL loaded: its base address */ break;
    case EXCEPTION_DEBUG_EVENT:      /* a breakpoint, a single step, or a real crash */ break;
    case EXIT_PROCESS_DEBUG_EVENT:   return;
    }
    ContinueDebugEvent(event.dwProcessId, event.dwThreadId, DBG_CONTINUE);   // let it run again
}

While the target is frozen, the debugger reads and writes its memory (ReadProcessMemory, WriteProcessMemory) and its registers (GetThreadContext, SetThreadContext). Everything a debugger shows you comes from those four calls.

Software breakpoints: one byte

To stop at an address, the debugger overwrites the first byte of the instruction there with 0xCC, the one-byte int3 instruction, after saving the original byte.

Text
before:  48 89 5C 24 08     mov [rsp+8], rbx
armed:   CC 89 5C 24 08     int3 (and garbage after it)

When the target executes int3, the processor raises a breakpoint exception, Windows freezes the process, and the debugger gets an EXCEPTION_DEBUG_EVENT with code EXCEPTION_BREAKPOINT (0x80000003). Then it must clean up carefully:

  1. int3 has already executed, so rip points one byte past the breakpoint. Set rip back by one.
  2. Write the original byte back, so the real instruction can run.
  3. To keep the breakpoint for next time, it cannot simply write CC back now: the instruction has not run yet. So it sets the trap flag and continues; after exactly one instruction the processor stops again with a single-step exception; the debugger re-writes CC and continues normally.

When the debugger shows you memory, it shows the saved original bytes, not the CCs, so you never see them. But the program can: code that reads its own bytes (a checksum of its code, for example) sees a CC where a breakpoint is set. That is one reason the next kind exists.

Single-stepping

Bit 8 of the EFLAGS register is the trap flag (TF). When it is set, the processor raises a single-step exception (EXCEPTION_SINGLE_STEP, 0x80000004) after executing one instruction. "Step into" is: set TF, continue, wait for the event. "Step over" a call is: put a temporary breakpoint on the instruction after the call and run.

Hardware breakpoints

The processor has four debug registers, DR0 to DR3, each holding an address, and a control register DR7 that says for each one:

  • whether it is enabled;
  • what triggers it: execute, write, or read or write;
  • how many bytes it covers: 1, 2, 4 or 8.

When the condition is met, the processor raises a single-step exception and DR6 says which one fired. Because nothing in memory changes, hardware breakpoints are invisible to code that checksums itself, and they can do something software breakpoints cannot: stop when data is written or read. A data breakpoint ("break when this address is written") is the tool of lesson 3.03.

There are only four, and they are per thread: the debugger sets them in every thread's context.

Exceptions: first and second chance

Breakpoints are exceptions, but so are real errors. When any exception happens in a debugged process, the debugger hears about it first (a first-chance exception) and can choose:

  • DBG_CONTINUE: "I handled it" (used for its own breakpoints);
  • DBG_EXCEPTION_NOT_HANDLED: "pass it to the program's own handlers".

If the program's own handlers (C++ catch, __try/__except) do not handle it either, the debugger is told a second time, second chance, just before the process would die. Many programs throw and catch exceptions in normal operation, which is why debuggers let you choose which first-chance exceptions stop and which only get logged.
