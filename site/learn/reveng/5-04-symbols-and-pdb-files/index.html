Symbols and PDB Files

lesson 5.044 of 5 in milestone 55 min1 practice task

What a PDB holds, how a binary names its exact PDB through a GUID and age, symbol servers and the path layout they use, public versus private symbols, and turning addresses into names with DbgHelp - including Microsoft's symbols for Windows itself.

Names live in a separate file

When MSVC links a program it writes the machine code into the .exe and the names into a separate PDB (program database) file: function names and addresses, global variables, types and struct layouts, local variables, source file and line information. The .exe itself contains almost none of it, which is why stripped binaries are hard to read.

With the matching PDB, every tool in this course shows names: call stacks, disassembly, crash dumps. Always check whether one is available before working without it.

Which PDB matches?

A PDB is only useful for the exact build it came from. The .exe records which one it needs in a CodeView record in its debug directory (lesson 1.05):

Offset Size Field
0 4 signature RSDS
4 16 GUID: a unique id generated at link time
20 4 age: incremented by incremental relinks
24 ... PDB file name or path, zero-terminated (UTF-8)

The PDB contains the same GUID and age. Tools refuse a PDB whose GUID or age differs, even if the file name matches: a PDB from yesterday's build of the same project describes different addresses.

Symbol servers

A symbol server is a store of PDBs indexed by that GUID and age, so a debugger can fetch exactly the right one. The path inside the store is:

Text
<pdb name>/<GUID><age>/<pdb name>

Inventory.pdb/3F2504E04F8911D39A0C0305E82C33011/Inventory.pdb

The GUID is written as 32 uppercase hex digits in a specific order: its first field as a 32-bit number, the next two as 16-bit numbers, then its last 8 bytes in order; the age follows in hex with no leading zeros.

Microsoft publishes PDBs for Windows' own DLLs on its public server. Point your tools at it with the _NT_SYMBOL_PATH environment variable:

Text
srv*C:\Symbols*https://msdl.microsoft.com/download/symbols

(C:\Symbols is a local cache.) Then call stacks through ntdll.dll, kernel32.dll and user32.dll show real function names. For your own builds, keep every released build's PDBs in a store of your own (the symstore tool from the Windows SDK adds them), and every crash report from a user can be read with names, even months later.

Public and private symbols

  • Private symbols, the full PDB your build creates, include types, local variables and line numbers.
  • Public symbols contain only the names and addresses of functions and globals. Microsoft's server mostly has these. They are created with the linker's /PDBSTRIPPED option, which is what you would ship if you publish symbols for your own product without giving away its structure.

DbgHelp

Windows' DbgHelp library (dbghelp.dll) loads symbols and answers questions about them; it is what WinDbg and many crash reporters use:

C++
SymSetOptions(SYMOPT_UNDNAME | SYMOPT_DEFERRED_LOADS);
SymInitialize(process, nullptr /* use _NT_SYMBOL_PATH */, TRUE /* load every module */);

char buffer[sizeof(SYMBOL_INFO) + MAX_SYM_NAME]{};
auto* symbol{ reinterpret_cast<SYMBOL_INFO*>(buffer) };
symbol->SizeOfStruct = sizeof(SYMBOL_INFO);
symbol->MaxNameLen = MAX_SYM_NAME;
DWORD64 displacement{};
if (SymFromAddr(process, address, &displacement, symbol))
    std::printf("%s+0x%llx\n", symbol->Name, displacement);    // Player::update+0x1a

Other useful calls: SymFromName (name to address), SymGetLineFromAddr64 (address to source line), StackWalk64 (unwinding), and MiniDumpWriteDump for writing crash dumps that you later open with these same symbols.

Without any PDB, you still have the export names, RTTI class names (lesson 2.05), and whatever names you recover and add in your disassembler's database, which is effectively a PDB you write by hand.
