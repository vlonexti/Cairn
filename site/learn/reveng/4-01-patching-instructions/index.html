Patching Instructions

lesson 4.011 of 5 in milestone 45 min1 practice task

Changing a compiled program's behaviour by changing its bytes - turning a conditional jump into an unconditional one, inverting a condition, filling instructions with nops - in the file or in memory, on programs you built yourself, and what breaks when you do.

Why patch your own programs

Patching means changing a program's machine code directly instead of recompiling it. On your own software it has real uses:

  • Testing a hypothesis while reversing: "if I skip this check, does the crash go away?" answers a question in seconds.
  • Working around a bug in a build you cannot rebuild right now: an old release, a build machine that no longer exists, a tool whose source was lost.
  • Learning: seeing exactly which bytes encode which instructions makes disassembly far less mysterious.

The practice targets here are programs you compile yourself. Build a small test program with a check you can find, for example:

C++
#include <cstdio>
#include <cstring>

bool debugMenuAllowed(const char* build)
{
    return std::strcmp(build, "internal") == 0;
}

int main()
{
    if (debugMenuAllowed("release")) std::puts("debug menu on");
    else std::puts("debug menu off");
}

Compile it in Release, find the comparison in x64dbg (search for the string "debug menu off" and follow the cross-reference), and change the outcome without touching the source.

The simplest patches

The decision is almost always a conditional jump right after a test or cmp:

Assembly
call   debugMenuAllowed
test   al, al
je     short off_branch          ; 74 0C
lea    rcx, [aDebugMenuOn]

Three standard edits:

Goal Change Bytes
always take the jump je becomes jmp 74 0C becomes EB 0C
never take the jump replace it with nops 74 0C becomes 90 90
take it in the opposite case je becomes jne 74 0C becomes 75 0C

The short conditional jumps are 70 to 7F, and each condition and its opposite differ only in the lowest bit: 74 je / 75 jne, 7C jl / 7D jge, 72 jb / 73 jae. So flipping bit 0 inverts any of them. The 6-byte near forms are 0F 80 to 0F 8F, with the same rule on the second byte.

90 is nop, the one-byte "do nothing". Longer nops exist (66 90, 0F 1F 00, up to 15 bytes), and compilers use them to pad loops, but a run of 90s works fine for patching.

Patch whole instructions

A patch must leave the processor reading valid instructions. Replacing a 2-byte jump with a 5-byte one overwrites the next 3 bytes, which belong to another instruction, and the processor will then decode garbage. Rules:

  • Keep the patch the same length as what it replaces, padding with nops.
  • If you need more room, use a code cave (lesson 4.03).
  • Always check the original bytes before patching: if they are not what you expect, you are looking at a different build, and patching blindly will break it.

In the file or in memory

In memory (in the debugger, or with WriteProcessMemory): instant, undone when the program restarts. Code pages are read+execute, so a program patching memory needs VirtualProtect to make the page writable first, and FlushInstructionCache afterwards. Debuggers do this for you.

In the file: permanent. Convert the instruction's address to a file offset (the RVA conversion of lesson 1.03: address − image base − section RVA + section file offset), and change the bytes there. x64dbg can write all your memory patches back to a copy of the file (File > Patch file).

What breaks

  • Code signing: a signed .exe or .dll no longer matches its signature after any change. Windows and antivirus software treat it as unsigned. Drivers simply refuse to load.
  • Integrity checks inside the program (checksums of its own code) will notice.
  • Updates replace the file and your patch is gone; and the next build of a program has different addresses, which is what lesson 4.05 is about.

Keep the original file, record every patch (address, original bytes, new bytes, why), and patch copies.
