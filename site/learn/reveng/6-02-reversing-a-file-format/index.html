Reversing a File Format

lesson 6.022 of 5 in milestone 65 min1 practice task

Working out an undocumented binary file format from samples - collecting files from controlled changes, magic numbers and versions, lengths and counts, offsets, byte order, strings, checksums and compression - and proving your understanding by writing a parser that reads every sample and a writer the program accepts.

Why formats

Formats are where reverse engineering pays off most often in practice: opening old save files, converting a tool's project files, reading a device's logs, importing a game's levels into an editor you are writing. And a format can often be worked out from files alone, with the code only consulted to settle doubts.

Collect samples with controlled changes

The single most useful technique is to make the program write files that differ in one known way:

  • Save twice with nothing changed: the bytes that differ are timestamps, random ids or counters.
  • Change the player's name from "Ada" to "Adam": the name's bytes appear, and something nearby probably grows by one (a length).
  • Add one item to the inventory: a count goes up by one, and a block of bytes is inserted.
  • Change one number you can see (gold 100 to 101): find 64 becoming 65, and you know the field's position, size and byte order.

Diff each pair (lesson 1.02's tool) and write down every observation. Twenty careful samples beat a thousand random ones.

What to look for

Magic numbers. Most formats start with a fixed signature: PK (zip), \x89PNG, RIFF, MZ. A custom format often starts with a readable tag like SAVE or GMDT.

Versions. A small number near the start that never changes between your samples, but differs in files from an older version of the program.

Lengths and counts. A number just before a variable-length thing: a byte or two before a string that equals its length, a count before a list. Changing the thing changes the number.

Offsets. A number that equals the position of something else in the file: a table of contents. Check whether values in the header match positions where blocks start.

Byte order. 64 00 00 00 is little-endian 100; 00 00 00 64 big-endian. A value you control, such as gold, settles it.

Floats. Positions and fractions are often floats: four bytes that read as nonsense integers but sensible floats (00 00 C8 42 is 100.0).

Strings. Length-prefixed, zero-terminated, fixed-size padded with zeros, ASCII or UTF-16.

Checksums. If every change, however small, also changes a few bytes at the end (or the start), that is probably a checksum, and the program rejects files whose checksum does not match. Try the usual suspects over the rest of the file: a plain byte sum, CRC-32, Adler-32. A search for the CRC-32 constant 0xEDB88320 in the code confirms it.

Compression and encryption. A block with entropy near 8 (lesson 1.05) is compressed or encrypted. Try decompressing with zlib (zlib streams usually start 78 9C or 78 DA); otherwise find the code that reads the block.

Writing it down

Describe the format as a table of fields, then turn it into a parser:

Offset Size Field Evidence
0 4 magic SAVE same in all samples
4 2 version, little-endian 2 in all current samples, 1 in an old one
6 1 name length 3 for "Ada", 4 for "Adam"
...

Tools help: ImHex has a pattern language that overlays your field definitions on the bytes as you write them, highlighting fields so mistakes are obvious; Kaitai Struct describes formats in YAML and generates parsers in many languages.

Proving it

Your understanding is complete when:

  1. Your parser reads every sample without leftovers or errors, and the values make sense.
  2. Your writer produces a file from scratch that the program accepts and loads correctly.
  3. Changing a field with your writer changes the right thing in the program.

The practice is exactly this, for a small save file format.
