Keeping State Across a Reload

lesson 5.044 of 5 in milestone 55 min1 practice task

Hot reload is only useful if the game keeps its state - the player's position, the enemies, the score - while the code changes. This lesson shows the two strategies, host-owned memory and save and restore, and how to handle the hard case: a reload that changes the layout of the state itself.

Strategy 1: the host owns the memory

The simplest and fastest approach, popularised by Casey Muratori's Handmade Hero: the host allocates one big block of memory at start-up and hands it to the DLL every frame. The DLL keeps all of its state in that block, and none in its own globals:

C++
struct game_memory
{
    uint64_t size;
    void*    storage;       // allocated by the host once, never freed until exit
    bool     initialised;   // false the first time
};

extern "C" __declspec(dllexport) void game_update(game_memory* memory, const game_input* input, float dt)
{
    auto* state{ static_cast<GameState*>(memory->storage) };
    if (!memory->initialised) { new (state) GameState{}; memory->initialised = true; }
    state->player.x += input->moveX * dt;
}

When the DLL is swapped, the block is untouched, so the new code finds the state exactly as the old code left it.

The rules that make it work:

  • GameState is plain data: no virtual functions (their vptrs would point into the old DLL), no std::string or std::vector whose memory came from the old DLL's heap if it used its own CRT. Arrays with fixed sizes, plain structs, indices instead of pointers into code.
  • Memory that the game needs to grow comes from a simple arena inside the block, not from new.
  • No pointers to functions or string literals of the DLL are stored in the state.

Strategy 2: save and restore

If the state has to contain richer C++ objects, the DLL can instead write its state to bytes just before it is unloaded and read it back after the new one is loaded:

C++
// in the DLL's table
uint64_t (*save_state)(void* buffer, uint64_t capacity);   // returns bytes needed
int32_t  (*load_state)(const void* buffer, uint64_t size);

The host calls save_state on the old DLL, unloads it, loads the new one and calls load_state. Slower, but it handles any state, and the same code doubles as your save-game system.

When the layout changes

Both strategies face the same hard case: you add a member to GameState, or change a type. The new code then reads the old bytes with the new layout, which is lesson 3.03's versioned-struct problem in another form. The same solution works:

  • Put a version number (and size) at the start of the saved state or the memory block.
  • When the new code sees an older version, it migrates: reads the old layout, fills new fields with defaults, writes the new layout.
  • When it sees a version it cannot read, it starts fresh rather than reading garbage, and logs why.
C++
struct StateHeader { uint32_t version; uint32_t size; };

// version 1: { int32_t x, y; }    version 2: { int32_t x, y; int32_t health; }
if (header.version == 1) { /* copy x, y; health = 100; */ }
else if (header.version == 2) { /* read as is */ }
else { /* unknown: start a new game */ }

Many developers simply restart when the state layout changes, and reload freely for everything else. A version number makes that decision automatic instead of a crash.

What hot reload is good for, and what not

Excellent for: tuning movement and feel, fixing gameplay bugs while reproducing them, iterating on enemy behaviour, UI layout. Poor for: changes to data the host owns, changes to the host itself, and big structural changes, which still need a restart.

Common mistakes

A static variable inside the gameplay DLL

It resets on every reload. Move it into the state.

Reading old state with a new layout

Values land in the wrong fields. Version the state and migrate or start fresh.
