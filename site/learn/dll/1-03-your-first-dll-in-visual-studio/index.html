Your First DLL in Visual Studio

lesson 1.033 of 6 in milestone 15 min2 practice tasks

Build a DLL and a program that uses it, in one Visual Studio solution. You meet the export macro pattern that lets one header serve both the library and the programs using it, and see where the .dll and its import .lib end up.

The plan

You will make one solution with two projects:

Stones.sln
├── StoneMath/          a DLL project
│   ├── stone_math.h    the public header: what users of the DLL see
│   └── stone_math.cpp  the implementation
└── StoneDemo/          a console program that calls the DLL
    └── main.cpp

1. The DLL project

In Visual Studio: File, New, Project, choose Dynamic-Link Library (DLL) for C++, name it StoneMath. The template adds pch.h, framework.h and a dllmain.cpp. You can leave dllmain.cpp as it is for now (lesson 2.04 explains it), or turn off precompiled headers in Properties, C/C++, Precompiled Headers to keep things small.

Note one setting the template made for you, in Properties, C/C++, Preprocessor, Preprocessor Definitions: STONEMATH_EXPORTS. Only the DLL project defines it. That is what the header uses to tell "building the library" from "using the library".

2. The export macro

A function must be marked to appear in the DLL's export table. When building the DLL, the marker is __declspec(dllexport). When a program uses the DLL, the same declaration should say __declspec(dllimport), which lets the compiler call it through the import table directly. One header serves both by switching on STONEMATH_EXPORTS:

C++
// stone_math.h
#pragma once

#ifdef STONEMATH_EXPORTS
#define STONEMATH_API __declspec(dllexport)
#else
#define STONEMATH_API __declspec(dllimport)
#endif

STONEMATH_API int stackHeight(int stones, int stonesPerLayer);
STONEMATH_API double stackWeight(int stones, double kilosEach);
C++
// stone_math.cpp
#include "stone_math.h"

int stackHeight(int stones, int stonesPerLayer)
{
    if (stonesPerLayer <= 0) return 0;
    return (stones + stonesPerLayer - 1) / stonesPerLayer;   // round up: a part layer is still a layer
}

double stackWeight(int stones, double kilosEach)
{
    return stones * kilosEach;
}

Build the project. In the output folder (x64\Debug under the solution) you find:

File What it is
StoneMath.dll The library itself, needed at run time
StoneMath.lib The import library: small, says "these names live in StoneMath.dll". Needed at link time
StoneMath.pdb Debug symbols
StoneMath.exp Export file the linker made along the way; you can ignore it
Only marked functions are exported

A function without STONEMATH_API is still in the DLL's code, but no other module can find it. That is how a DLL keeps helpers private.

3. The program that uses it

Add a project to the same solution: Console App, named StoneDemo.

C++
// main.cpp
#include <iostream>
#include "stone_math.h"

int main()
{
    std::cout << "Layers: " << stackHeight(10, 4) << '\n';     // 3
    std::cout << "Weight: " << stackWeight(10, 2.5) << " kg\n"; // 25
}

Three settings connect them:

  1. Find the header. StoneDemo, Properties, C/C++, General, Additional Include Directories: $(SolutionDir)StoneMath.
  2. Link the import library. Right-click StoneDemo, Add, Reference, tick StoneMath. Visual Studio then links StoneMath.lib and builds StoneMath first.
  3. Run from the right place. Both projects already write to $(SolutionDir)x64\Debug, so StoneMath.dll sits next to StoneDemo.exe, which is the first place Windows looks.

Set StoneDemo as the startup project and run it.

4. Break it on purpose

  • Delete StoneMath.dll from the output folder and run StoneDemo.exe from Explorer: the loader says it cannot find the DLL. The program never reaches main.
  • Remove STONEMATH_API from stackWeight, rebuild both: now the linker fails with LNK2019: unresolved external symbol, because the import library no longer lists it.

Exporting a class

You can put the macro on a class to export all its members:

C++
class STONEMATH_API Xenon
{
public:
    explicit Xenon(int stones);
    int height() const;
private:
    int m_stones;
};

It works, but it ties every program to the exact compiler, settings and class layout the DLL was built with. Milestone 3 shows why most long-lived DLLs export plain C functions instead.

Common mistakes

Defining STONEMATH_EXPORTS in the program too

Then the program's copy of the header says dllexport, and you get confusing link errors. Only the DLL project defines it.

Copying the DLL by hand into the wrong folder

Debug and Release, and x64 and x86, each have their own output folder. Keep both projects writing to the same one.
