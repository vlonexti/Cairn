Import Libraries and Load-Time Linking

lesson 1.055 of 6 in milestone 15 min2 practice tasks

When a program links against a DLL's import library, the linker writes an import table into the program and calls go through the import address table, which the loader fills in. This lesson follows one call from your source code to the DLL.

What an import library contains

StoneMath.lib from lesson 1.03 is small. It contains no machine code for stackHeight. It contains, for each export:

  • the symbol the linker is looking for (__imp_stackHeight, and a stub called stackHeight), and
  • a record saying "this comes from StoneMath.dll, under the name stackHeight".

When StoneDemo's linker sees a call to stackHeight, it finds the symbol in the import library and records the dependency. The result in StoneDemo.exe is an import table:

Output
StoneDemo.exe imports
  StoneMath.dll
      stackHeight
      stackWeight
  KERNEL32.dll
      WriteFile
      GetStdHandle
      ...

The import address table

Alongside the names, the program has an import address table (IAT): one pointer-sized slot for every imported function. In the file the slots hold placeholders. At load time, the loader looks up each name in the DLL's export table and writes the real address into the slot (lesson 1.02, step 5).

Your call compiles into an indirect call through that slot:

Assembly
; with __declspec(dllimport) on the declaration
call qword ptr [__imp_stackHeight]     ; jump to whatever address the loader wrote into the slot

Without dllimport, the compiler does not know the function is in a DLL. It emits a normal call stackHeight, and the linker makes stackHeight a tiny stub that jumps through the slot. It works, just with one extra jump. That is why the header from lesson 1.03 says dllimport for users.

Following one call

sequenceDiagram
  participant M as main() in StoneDemo.exe
  participant IAT as IAT slot for stackHeight
  participant D as stackHeight in StoneMath.dll
  Note over IAT: filled in by the loader before main
  M->>IAT: call [slot]
  IAT->>D: address of StoneMath.dll + RVA
  D-->>M: returns 3

The cost is one memory read to fetch the address. The benefit is that the program does not need to know where StoneMath.dll will be loaded.

When a name cannot be resolved

At load time, every import must be found. If StoneDemo.exe was built against a StoneMath.dll that exported stackHeight and stackWeight, but the DLL on disk is an older one with only stackHeight, the loader stops with:

Output (yours will differ)
The procedure entry point stackWeight could not be located in the dynamic link library StoneMath.dll.

The program does not start. This is the strongest argument for never removing an export from a published DLL (milestone 3).

Linking against a DLL without a project reference

The project reference from lesson 1.03 is the easiest way in one solution. For a DLL from somewhere else you set two linker properties yourself:

  • Linker, General, Additional Library Directories: the folder with StoneMath.lib.
  • Linker, Input, Additional Dependencies: add StoneMath.lib.

Or, in code, a comment that tells the linker:

C++
#pragma comment(lib, "StoneMath.lib")

You still need the DLL next to the program when it runs.

Making an import library from a DLL

Sometimes you have only a DLL (and its documentation). You can rebuild an import library from a .def file listing its exports:

Output
lib /def:StoneMath.def /out:StoneMath.lib /machine:x64

Common mistakes

Shipping only the .lib

The import library is for building. Users of your program need the .dll.

Using an import library from a different version of the DLL

The program then imports names the DLL on disk may not have. Keep the .lib and .dll from the same build together.
