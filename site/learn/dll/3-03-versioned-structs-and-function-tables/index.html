Versioned Structs and Function Tables

lesson 3.033 of 6 in milestone 35 min2 practice tasks

Sometimes callers need to see a struct, such as an options block. Windows' trick is to start every such struct with its own size, so the library can tell which version the caller was built with. The same idea, applied to a struct full of function pointers, gives a function table that can grow across versions.

The problem with visible structs

A creation function with many options is clumsy with a long parameter list. A struct is nicer:

C++
typedef struct xenon_world_options
{
    int32_t width;
    int32_t height;
    int32_t gravity;
} xenon_world_options;

XENON_API int32_t xenon_world_create_ex(const xenon_world_options* options, xenon_world** out);

Then version 2 needs a seed. Add it to the struct, and a program compiled against version 1 passes a 12-byte struct where version 2 reads 16. The seed comes from whatever memory follows: garbage.

Size first

The Win32 API's answer, used by hundreds of its structs (cbSize in WNDCLASSEXW, dwSize in many others): the first member is the size of the struct, filled in by the caller.

C++
typedef struct xenon_world_options
{
    uint32_t size;      // the caller sets this to sizeof(xenon_world_options)
    int32_t  width;     // version 1
    int32_t  height;    // version 1
    int32_t  gravity;   // version 1
    uint32_t seed;      // version 2: added at the END
} xenon_world_options;

The caller always writes:

C++
xenon_world_options options{};
options.size = sizeof(options);
options.width = 64;

A program compiled against version 1 sets size to 16; one compiled against version 2 sets 20. The library reads only the fields that fit:

C++
int32_t xenon_world_create_ex(const xenon_world_options* options, xenon_world** out)
{
    if (!options || options->size < offsetof(xenon_world_options, seed)) return fail(XENON_INVALID_ARGUMENT, "options too small");
    WorldSettings s;
    s.width   = options->width;
    s.height  = options->height;
    s.gravity = options->gravity;
    // a field is present if the struct reaches past its end
    s.seed = options->size >= offsetof(xenon_world_options, seed) + sizeof(options->seed) ? options->seed : 12345u;
    ...
}

offsetof(T, member) is the byte position of a member, from <stddef.h>. A member is present when size >= offsetof(T, member) + sizeof(member).

The rules that make this work:

  • New members only ever go at the end.
  • Never remove, reorder or resize a member.
  • Every new member has a sensible default for callers who did not send it.
  • A size bigger than the library knows (a newer program with an older DLL) is fine: read what you know, ignore the rest. Or reject it if you cannot honour fields you do not understand; decide and document.

Function tables

The same trick works for a whole interface. Instead of exporting thirty functions, export one that returns a table of function pointers:

C++
typedef struct xenon_api
{
    uint32_t size;                                              // of this table
    uint32_t version;                                           // e.g. 2
    int32_t (*world_create)(xenon_world** out);
    void    (*world_destroy)(xenon_world* world);
    int32_t (*world_add_stone)(xenon_world*, int32_t, int32_t, int32_t);
    // version 2:
    int32_t (*world_save)(const xenon_world*, const char* path);
} xenon_api;

XENON_API const xenon_api* xenon_get_api(uint32_t wantedVersion);

A program asks for the version it was built for. The library returns its table if it is at least that new, or NULL if it is too old. The program checks size before touching later members. This is how Vulkan, OpenXR and many game engines expose their APIs, and it suits plugins (milestone 5): one GetProcAddress gets everything.

Common mistakes

Forgetting to set size

A zero size makes the library reject or misread the struct. Many APIs return an error for that; yours should too.

Inserting a new member in the middle

Every member after it moves, so old programs' values land in the wrong fields. Always append.
