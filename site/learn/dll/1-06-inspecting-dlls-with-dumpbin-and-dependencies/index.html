Inspecting DLLs with dumpbin and Dependencies

lesson 1.066 of 6 in milestone 15 min2 practice tasks

When a program will not start or calls the wrong thing, you need to see what a module exports, what it imports, and where each DLL really came from. This lesson covers dumpbin, the Dependencies tool, the debugger's Modules window and Process Monitor.

dumpbin

dumpbin comes with Visual Studio. Run it from a Developer Command Prompt (Start menu: "Developer Command Prompt for VS").

Command Shows
dumpbin /exports X.dll The export table: ordinal, hint, RVA, name
dumpbin /imports X.exe Every DLL the module imports from, and every function
dumpbin /dependents X.exe Just the list of DLLs it needs directly
dumpbin /headers X.dll Machine type (x64 or x86), preferred base, subsystem, characteristics

A typical check when a program refuses to start: dumpbin /dependents on the .exe, then make sure every listed DLL exists, then dumpbin /exports on the suspicious one and compare against dumpbin /imports.

Output (yours will differ)
Dump of file StoneDemo.exe

  Image has the following dependencies:

    StoneMath.dll
    MSVCP140D.dll
    VCRUNTIME140D.dll
    VCRUNTIME140_1D.dll
    ucrtbased.dll
    KERNEL32.dll

The D at the end of the runtime names means debug runtime. Those DLLs exist only on machines with Visual Studio installed, which is why a Debug build will not run on a friend's computer (lesson 4.04).

dumpbin /headers answers "is this 32-bit or 64-bit?": look for machine (x64) or machine (x86).

Dependencies

Dependencies is a free, open-source tool that shows the whole dependency tree of a module, recursively, and marks in red anything it cannot find. It understands Windows' API sets (names like api-ms-win-core-file-l1-1-0.dll, which are redirected to real system DLLs), which confuses older tools.

Open StoneDemo.exe in it, expand StoneMath.dll, and you see what StoneMath itself needs.

The debugger's Modules window

While debugging, Debug, Windows, Modules lists every module actually loaded, with:

  • Path: exactly which file was loaded. This answers "which copy of the DLL did it pick?"
  • Address: where it was mapped (lesson 1.02).
  • Symbol Status: whether its .pdb was found, so you can step into it.
  • Version: from its version resource (lesson 4.04).

A DLL loaded with LoadLibraryW appears in the list the moment the call returns.

Process Monitor

When Windows looks for a DLL, it tries a sequence of folders (lesson 4.01). Process Monitor from Sysinternals records every file access. Filter on your process name and on paths ending in .dll, start the program, and you see each place the loader tried, with NAME NOT FOUND until it finds the file. That tells you exactly why the wrong copy was loaded, or why none was.

Reading a loader failure, step by step

  1. Note the exact message (lesson 1.02's table).
  2. dumpbin /dependents the .exe: which DLLs does it need?
  3. For each one, is it next to the program, or in a folder Windows searches?
  4. Is it the right architecture? (dumpbin /headers)
  5. If the message names a missing entry point, dumpbin /exports the DLL that was loaded (find its path in Process Monitor or the Modules window) and compare with what the program imports.

Common mistakes

Inspecting the wrong copy

There are often several copies of a DLL on a machine. Check the path Windows actually loaded, not the one you expected.

Running dumpbin from an ordinary prompt

It is only on the PATH in a Developer Command Prompt.
