Name Mangling and extern "C"

lesson 2.011 of 6 in milestone 25 min2 practice tasks

C++ lets two functions share a name if their parameters differ, so the compiler gives every function a decorated name that encodes its parameter types. Those names are what a DLL exports by default. extern "C" turns decoration off, giving the plain names that GetProcAddress, .def files and other languages need.

Why names are decorated

In C++ these are three different functions:

C++
int    area(int side);
int    area(int width, int height);
double area(double radius);

The linker, though, only knows symbol names: strings. To keep the three apart, the compiler gives each a decorated name (also called a mangled name) that includes the parameter types, the return type, the namespace and class, and more. With MSVC:

Declaration Decorated name
int area(int) ?area@@YAHH@Z
int area(int, int) ?area@@YAHHH@Z
double area(double) ?area@@YANN@Z
int stackHeight(int, int) ?stackHeight@@YAHHH@Z
void reset() ?reset@@YAXXZ

GCC and Clang use a completely different scheme (_Z4areai). That alone is a good reason not to export C++ names from a DLL meant for anyone else.

Reading an MSVC name

For a plain function outside any class or namespace, the pattern is:

Output
?  name  @@  YA  <return type>  <parameter types>  @Z
                                 (no parameters:   XZ)
  • ? marks a decorated C++ name.
  • @@ ends the name and its (empty) scope.
  • Y means "a function outside a class", A means the default calling convention (__cdecl).
  • The type codes:
Type Code Type Code
void X int H
char D unsigned int I
bool _N long long _J
float M double N
  • After the parameters comes @Z. A function with no parameters has X (void) as its parameter list and ends XZ with no @.

So ?add@@YAHHH@Z is "a free function add, returning int (H), taking int, int (HH)". You will build exactly this decorator in the practice.

To decode a name you do not recognise, Visual Studio ships undname:

Output
undname ?stackHeight@@YAHHH@Z
Output (yours will differ)
Undecoration of :- "?stackHeight@@YAHHH@Z"
is :- "int __cdecl stackHeight(int,int)"

extern "C"

Wrapping a declaration in extern "C" tells the compiler to use C linkage: no overloading, no decoration, the plain name.

C++
// stone_math.h
#ifdef __cplusplus
extern "C" {
#endif

STONEMATH_API int    stackHeight(int stones, int stonesPerLayer);
STONEMATH_API double stackWeight(int stones, double kilosEach);

#ifdef __cplusplus
}
#endif

Now dumpbin /exports lists stackHeight and stackWeight. The #ifdef __cplusplus lets the same header be used from C, which does not know the words extern "C".

What you give up:

  • No overloading. Two extern "C" functions cannot share a name. Use distinct names: area_square, area_rect.
  • No C++ types in the signature that C cannot express, if you want other languages to call it. The compiler allows std::string in an extern "C" function, but no other language can construct one (lesson 2.06).

The body of an extern "C" function is still C++. You can use classes, templates and the standard library inside it; only the name and signature are C.

Which names to export

A good rule for any DLL that outlives one build of one program:

Export extern "C" functions with plain C types in their signatures. Keep C++ on the inside.

Milestone 3 builds whole interfaces this way, including ones that give users objects and methods.

Common mistakes

[!warning] GetProcAddress(dll, "stackHeight") returns NULL The function was exported with its decorated name. Add extern "C", or ask for the decorated name (fragile).

[!warning] extern "C" in the .cpp file but not the header Callers then look for the decorated name and the linker cannot find it. Put extern "C" on the declaration everyone sees.
