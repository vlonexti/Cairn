Versioning and Compatibility

lesson 3.055 of 6 in milestone 35 min2 practice tasks

A version number is a promise about compatibility. Semantic versioning turns that promise into rules: major for breaking changes, minor for additions, patch for fixes. This lesson applies it to DLLs, shows how a program checks the version it got at run time, and covers side-by-side installs for breaking changes.

Semantic versioning

A version is three numbers, MAJOR.MINOR.PATCH, such as 2.4.1:

Part Increase it when Example
MAJOR You break compatibility: remove or change a function, change a visible struct 2.4.1 to 3.0.0
MINOR You add something without breaking anything: new functions, new codes, new struct fields at the end 2.4.1 to 2.5.0
PATCH You fix bugs without changing the interface 2.4.1 to 2.4.2

Increasing one part resets the parts after it to 0. A version can carry a pre-release label after a hyphen, 3.0.0-beta.2, which sorts before 3.0.0.

For a DLL, this tells users exactly what is safe:

A program built against version X.Y.Z works with any DLL version X.y.z where y.z ≥ Y.Z: the same major version, and at least as new.

A newer minor version only adds things the old program does not use. An older minor version might lack a function the program needs. A different major version may have changed anything.

Comparing versions

Versions compare part by part, as numbers, not as text. As strings, "2.10.0" < "2.9.0" because '1' < '9'; as versions, 2.10.0 is newer. The practice has you write this comparison properly.

Checking at run time

Load-time linking catches a missing function (the program will not start), but not a function whose behaviour changed in a breaking way. So well-behaved libraries let callers check:

C++
#define XENON_VERSION_MAJOR 2
#define XENON_VERSION_MINOR 4
#define XENON_VERSION_PATCH 1

// The version of the DLL actually loaded, packed as major << 22 | minor << 12 | patch
XENON_API uint32_t xenon_version(void);

The header's macros say which version the program was compiled against; the function says which DLL it is running with:

C++
const uint32_t running{ xenon_version() };
const uint32_t major{ running >> 22 }, minor{ (running >> 12) & 0x3FF };
if (major != XENON_VERSION_MAJOR || minor < XENON_VERSION_MINOR)
{
    std::cerr << "This program needs xenon " << XENON_VERSION_MAJOR << '.' << XENON_VERSION_MINOR << " or newer\n";
    return 1;
}

Packing the three parts into one integer, as Vulkan does, makes the version easy to pass around and compare: with 10 bits for minor and 12 for patch, a larger packed number is always a newer version.

When you must break things

Sometimes a major version is unavoidable. Then change the DLL's file name along with it: xenon2.dll. Programs built for version 1 keep loading xenon.dll; programs built for version 2 load xenon2.dll; both can be installed together. That is how the Visual C++ runtime does it (msvcp140.dll versus the older msvcp120.dll) and how Windows' own system DLLs stay compatible for decades.

The alternative, replacing xenon.dll with an incompatible one, is what was once called DLL Hell: installing one program broke another that used the same file name with different expectations.

The file version resource

Windows also stores a version number inside the DLL file as a resource, shown in Explorer's Properties, Details tab. Lesson 4.04 adds one to your build. It is for people and installers; your code should check versions through its own function as above.

Common mistakes

Comparing version strings as text

"2.10" sorts before "2.9". Split them and compare numbers.

Shipping a breaking change as a minor version

Every program built for the previous minor version may now fail. If you broke something, it is a major version.
