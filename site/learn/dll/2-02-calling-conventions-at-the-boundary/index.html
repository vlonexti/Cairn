Calling Conventions at the Boundary

lesson 2.022 of 6 in milestone 25 min1 practice task

A calling convention is the agreement about where a function's arguments go and who cleans up afterwards. On 64-bit Windows there is essentially one; on 32-bit Windows there are several, and they change the exported name. Getting the convention wrong across a DLL boundary corrupts the stack.

The agreement every call relies on

When main calls stackHeight(10, 4), both sides must agree on:

  • where the arguments go: registers or the stack, and in which order;
  • where the return value comes back;
  • which registers the called function may change;
  • who removes the arguments from the stack afterwards.

That agreement is the calling convention. Inside one program the compiler uses the same one everywhere, so you never think about it. Across a DLL boundary, the caller and the DLL were compiled separately, possibly by different compilers or languages, so the convention is part of the interface.

64-bit Windows: one convention

On x64 Windows every function uses the Microsoft x64 calling convention:

  • the first four integer or pointer arguments go in RCX, RDX, R8, R9; the first four floating-point ones in XMM0 to XMM3;
  • further arguments go on the stack;
  • the caller reserves 32 bytes of "shadow space" on the stack and cleans up;
  • the return value comes back in RAX (or XMM0).

Keywords like __stdcall and __cdecl are accepted on x64 but ignored. Names are not decorated for them either: an extern "C" function is exported exactly as stackHeight.

32-bit Windows: several conventions

32-bit code is still around (older plugins, some game engines), and there the keyword matters:

Convention Arguments Who cleans the stack extern "C" name
__cdecl (default for C/C++) stack, right to left the caller _name
__stdcall (the Win32 API, WINAPI) stack, right to left the callee _name@N, N = bytes of arguments
__fastcall first two in ECX, EDX, rest on stack the callee @name@N

N is the total size of the arguments, each rounded up to 4 bytes: int stackHeight(int, int) as __stdcall is exported as _stackHeight@8. That decoration is why so many old DLLs use a .def file: to export the plain name stackHeight from a __stdcall function.

When the two sides disagree

Suppose a DLL defines __stdcall but the program declares the function __cdecl and calls it through a function pointer (lesson 2.03). On 32-bit Windows:

  1. The program pushes 8 bytes of arguments.
  2. The DLL's function returns and, being __stdcall, removes 8 bytes.
  3. The program, believing it is __cdecl, removes 8 more.

The stack pointer is now 8 bytes wrong. Local variables and return addresses are read from the wrong places, and the program crashes somewhere unrelated, often much later. In a Debug build MSVC catches it with:

Output (yours will differ)
Run-Time Check Failure #0 - The value of ESP was not properly saved across a function call.

A portable habit

Pick a convention for your public API and spell it out with a macro, so the header says it once:

C++
#ifdef _WIN32
#define STONEMATH_CALL __cdecl
#else
#define STONEMATH_CALL
#endif

STONEMATH_API int STONEMATH_CALL stackHeight(int stones, int stonesPerLayer);
typedef int (STONEMATH_CALL *StackHeightFn)(int, int);   // for GetProcAddress users

On x64 the macro does nothing. On x86 it makes both sides agree, including people writing their own declarations from your documentation.

Common mistakes

Declaring a function pointer without the convention

A GetProcAddress result cast to the wrong function pointer type is the most common way to get a convention mismatch. Put the convention in the typedef.

Assuming 32-bit rules on x64

On x64 _name@8 decoration never happens. If you see it, you are looking at a 32-bit DLL.
