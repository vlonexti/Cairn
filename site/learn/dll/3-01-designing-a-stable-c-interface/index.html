Designing a Stable C Interface

lesson 3.011 of 6 in milestone 35 min2 practice tasks

A library that other programs depend on for years needs an interface that can grow without breaking them. The standard shape is a set of extern "C" functions around opaque handles, with a consistent naming scheme and clear ownership. This lesson designs one from scratch and lists the rules that keep it stable.

What "stable" means

A DLL interface has two kinds of compatibility:

  • Source compatibility: code written against version 1's header still compiles with version 2's.
  • Binary compatibility (the ABI): a program already built against version 1 still works when you replace the DLL with version 2, without recompiling.

Binary compatibility is the one DLLs are about, and it is much stricter. Changing a function's parameter from int to long long is fine for source code (it still compiles) and fatal for binaries (the old program passes 4 bytes; the new DLL reads 8).

The opaque handle

The core idea: the library's types are never visible to callers. They get a pointer to a type they cannot see inside.

C++
// xenon.h, the public header
#pragma once
#include <stdint.h>

#ifdef __cplusplus
extern "C" {
#endif

typedef struct xenon_world xenon_world;        // opaque: declared, never defined here

XENON_API int  xenon_world_create(xenon_world** out);
XENON_API void xenon_world_destroy(xenon_world* world);

XENON_API int  xenon_world_add_stone(xenon_world* world, int32_t x, int32_t y, int32_t weight);
XENON_API int  xenon_world_stone_count(const xenon_world* world, int32_t* out);
XENON_API int  xenon_world_tallest(const xenon_world* world, int32_t* x, int32_t* y, int32_t* height);

#ifdef __cplusplus
}
#endif

Inside the DLL:

C++
// xenon.cpp
struct xenon_world               // the real definition, only here
{
    std::unordered_map<Point, std::vector<int>, PointHash> stacks;
    int stoneCount{ 0 };
};

Because callers never see the definition, you can change it in every version: add members, reorder them, swap the unordered_map for a grid. Their compiled code only stores a pointer.

Naming

Exported names share one flat namespace in the process. Prefix everything with the library's name, and name functions <library>_<type>_<verb>:

  • xenon_world_create, xenon_world_destroy
  • xenon_world_add_stone, xenon_world_stone_count

Callers can guess names, and nothing collides with another library's create.

Fixed-size types

int is 32 bits on Windows today, but long is 32 bits on Windows and 64 bits on Linux. For anything that crosses the boundary, use the <stdint.h> types whose size is part of their name: int32_t, uint64_t, uint8_t. Use size_t only when you mean "a size in this process". Avoid bool in C interfaces (its size has varied between compilers); use int32_t with 0 and 1.

Results and outputs

Every function that can fail returns a result code, and returns values through out-parameters. That keeps one shape everywhere:

C++
int32_t count{ 0 };
if (xenon_world_stone_count(world, &count) != XENON_OK) { /* handle it */ }

The stability rules

Once version 1 is published:

You may You may not
Add new functions Remove or rename a function
Add new result codes (callers must treat unknown codes as failure) Change a function's parameters or return type
Change anything behind an opaque handle Change the layout of a struct callers can see (lesson 3.03 shows the safe way to grow one)
Add a new enum value at the end Change the meaning or number of an existing enum value
Fix bugs Change documented behaviour callers rely on

If you truly must break one of these, it is a new major version (lesson 3.05), often with a new DLL name (xenon2.dll) so both can be installed side by side.

Common mistakes

Putting a struct definition in the public header "just for convenience"

Callers' code now knows its size and layout, so it can never change. Keep it opaque, or version it (lesson 3.03).

[!warning] Using long or bool in the interface Their sizes are not the same everywhere. Use int32_t, int64_t, and int32_t for true/false.
