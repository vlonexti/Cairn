A Plugin System

lesson 5.011 of 5 in milestone 55 min1 practice task

A plugin system lets your program load DLLs it was never built with - written later, by you or by players making mods. This lesson designs one for a game - a plugin folder, one required export, an API version check, an interface the host gives to the plugin, and clean loading and unloading - using everything from milestones 2 to 4.

The contract

A plugin system is a contract between the host (your game) and plugins (DLLs in a folder). Write it down as a header both sides compile against, xenon_plugin.h. It contains:

  1. A version number for the contract itself.
  2. What the host offers plugins: a table of functions they may call (lesson 3.03).
  3. What a plugin offers the host: a table of callbacks the host calls.
  4. The one exported function every plugin must have, with a fixed name.
C++
// xenon_plugin.h: shared by the game and every plugin
#pragma once
#include <stdint.h>

#define XENON_PLUGIN_API_VERSION 1

// What the game offers a plugin.
typedef struct xenon_host_api
{
    uint32_t size;
    void    (*log)(const char* message);
    int32_t (*spawn_stone)(int32_t x, int32_t y, int32_t weight);
    double  (*time_seconds)(void);
} xenon_host_api;

// What a plugin offers the game.
typedef struct xenon_plugin
{
    uint32_t    size;
    uint32_t    api_version;                 // the XENON_PLUGIN_API_VERSION it was built with
    const char* name;                        // string literal, lives as long as the DLL
    int32_t (*start)(const xenon_host_api* host);   // after loading
    void    (*update)(double dt);                   // every frame
    void    (*stop)(void);                          // before unloading
} xenon_plugin;

// Every plugin exports this, with exactly this name (extern "C").
typedef const xenon_plugin* (*xenon_get_plugin_fn)(void);
#define XENON_GET_PLUGIN_NAME "xenon_get_plugin"

Everything crosses as plain C: no std::string, no exceptions, no shared heap (milestone 2). Each side only calls through tables, so neither needs an import library for the other.

A plugin

C++
// fog.cpp, built as fog.dll
#include "xenon_plugin.h"

static const xenon_host_api* g_host{ nullptr };

static int32_t start(const xenon_host_api* host)
{
    g_host = host;
    g_host->log("fog: hello");
    return 0;
}
static void update(double) {}
static void stop() { g_host->log("fog: goodbye"); g_host = nullptr; }

static const xenon_plugin g_plugin{ sizeof(xenon_plugin), XENON_PLUGIN_API_VERSION, "Fog", start, update, stop };

extern "C" __declspec(dllexport) const xenon_plugin* xenon_get_plugin(void) { return &g_plugin; }

Note what it does not do: nothing in DllMain or global constructors (lesson 2.04). Real work starts in start, called by the host after LoadLibrary returns.

The host's loader

C++
struct LoadedPlugin { HMODULE module; const xenon_plugin* plugin; };

std::vector<LoadedPlugin> loadPlugins(const std::filesystem::path& folder, const xenon_host_api& host)
{
    std::vector<LoadedPlugin> loaded;
    for (const auto& entry : std::filesystem::directory_iterator(folder))
    {
        const auto& path{ entry.path() };
        if (!entry.is_regular_file() || path.extension() != L".dll") continue;

        HMODULE module{ LoadLibraryExW(path.c_str(), nullptr, LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS) };
        if (!module) { logf("skipped %ls: could not load (error %lu)", path.c_str(), GetLastError()); continue; }

        auto get{ reinterpret_cast<xenon_get_plugin_fn>(GetProcAddress(module, XENON_GET_PLUGIN_NAME)) };
        const xenon_plugin* plugin{ get ? get() : nullptr };
        if (!plugin || plugin->size < sizeof(xenon_plugin) || plugin->api_version != XENON_PLUGIN_API_VERSION)
        {
            logf("skipped %ls: not a plugin for this version", path.c_str());
            FreeLibrary(module);
            continue;
        }
        if (plugin->start(&host) != 0) { logf("skipped %s: start failed", plugin->name); FreeLibrary(module); continue; }
        loaded.push_back({ module, plugin });
    }
    return loaded;
}

Every check matters:

  • Only .dll files, by full path, with the safe search flags (lesson 4.02). Plugins with their own dependencies keep them in their own folder.
  • The export must exist. A random DLL in the folder is skipped, not crashed on.
  • Size and version. A plugin built for another version of the contract is refused politely (lesson 3.05).
  • start can fail, and then the plugin is unloaded again.
  • A failing plugin never stops the others from loading.

Unloading

At shutdown, or when the player disables a plugin, the order is: call stop, forget every pointer the plugin gave you (its name, its tables, any objects), then FreeLibrary. Unload in the reverse order of loading, so a plugin that relied on another's services stops before them.

Mods and trust

A plugin runs inside your process with all of its permissions. For plugins you write yourself, that is fine. For mods made by players, treat the plugin folder as "code the player chose to run", like any program they download, and say so in your game's documentation. Many games that want untrusted mods use a scripting language with limited access (Lua, a WebAssembly runtime) instead of DLLs.

Common mistakes

Keeping a plugin's name string after unloading it

It points into the DLL's read-only data. Copy it into a std::string if you need it later.

Letting one bad plugin crash the whole load

Check every step and skip what does not fit.
