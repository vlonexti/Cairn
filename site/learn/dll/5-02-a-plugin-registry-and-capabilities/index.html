A Plugin Registry and Capabilities

lesson 5.022 of 5 in milestone 55 min2 practice tasks

Once several plugins are loaded, the host needs to know what each one provides - new stone types, weather effects, console commands - and route requests to the right one. This lesson builds a registry that plugins register into during start, handles name clashes and dependencies between plugins, and cleans up everything a plugin registered when it unloads.

Registering instead of exporting

In lesson 5.01 a plugin offered fixed callbacks: start, update, stop. Real plugins add things to the game: three new stone types, a weather effect, two console commands. Rather than one export per thing, the host offers registration functions in its table, and the plugin calls them from start:

C++
typedef struct xenon_stone_type
{
    uint32_t    size;
    const char* id;                  // "fog.ghost_stone"
    int32_t     weight;
    int32_t   (*on_place)(int32_t x, int32_t y);
} xenon_stone_type;

typedef struct xenon_host_api
{
    uint32_t size;
    void    (*log)(const char* message);
    int32_t (*register_stone_type)(const void* owner, const xenon_stone_type* type);
    int32_t (*register_command)(const void* owner, const char* name, void (*run)(const char* args));
} xenon_host_api;

In the plugin:

C++
static const xenon_stone_type g_ghost{ sizeof(xenon_stone_type), "fog.ghost_stone", 2, onPlaceGhost };

static int32_t start(const xenon_host_api* host)
{
    if (host->register_stone_type(&g_plugin, &g_ghost) != 0) return 1;
    host->register_command(&g_plugin, "fog.thickness", setThickness);
    return 0;
}

The owner argument (the plugin's own table, a unique address) lets the host remember who registered each thing.

The host's registry

C++
class Registry
{
public:
    int32_t addStoneType(const void* owner, const xenon_stone_type& type);
    const xenon_stone_type* stoneType(std::string_view id) const;
    void removeEverythingFrom(const void* owner);       // when a plugin unloads
private:
    struct Entry { const void* owner; xenon_stone_type type; std::string id; };
    std::map<std::string, Entry, std::less<>> m_stones;
};

Design decisions:

  • Copy what you keep. The registry stores its own copy of the struct and of the id text. Pointers into the plugin (on_place) are still pointers into its code, which is why...
  • Remove everything on unload. Before FreeLibrary, the host calls removeEverythingFrom(plugin). Otherwise the registry holds function pointers into unmapped memory (lesson 2.03).
  • Names are namespaced by convention: pluginname.thing. Two plugins can both have a "ghost_stone" without clashing.
  • A clash is refused, not overwritten. If fog.ghost_stone is already registered by someone else, the second registration fails and the plugin can decide what to do. Silently replacing a registration makes bugs that depend on load order.

Plugins that depend on plugins

A "seasons" plugin might need the "weather" plugin's commands. Give each plugin a list of the plugins it requires, by name, and load them in dependency order: the same depth-first, dependencies-first walk as the loader itself (lesson 1.02). A plugin whose requirement is missing, or that is part of a cycle, is not started, and the host says why.

Capabilities and versions per feature

Instead of one version for the whole contract, a host can offer capabilities: named features with their own version, such as "stone_types": 2, "commands": 1. A plugin lists what it needs; the host starts it only if every need is met with at least that version. This lets the contract grow one feature at a time without every plugin being rebuilt.

Common mistakes

Storing the plugin's pointers in the registry without an owner

You then cannot find and remove them on unload, and the game crashes the first time it calls one.

Last registration wins

The result depends on which DLL the directory listing returned first. Refuse duplicates and report them.
