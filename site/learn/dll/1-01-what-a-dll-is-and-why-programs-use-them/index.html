What a DLL Is and Why Programs Use Them

lesson 1.011 of 6 in milestone 17 min2 practice tasks

A dynamic-link library is compiled code that is not part of your .exe but is joined to it when the program starts or while it runs. This lesson explains what a DLL contains, how it differs from a static library, and the real reasons programs are split into them, along with the costs.

Code that lives in another file

Every Windows program you have built so far ends up as one .exe. The compiler turns each .cpp file into an object file, and the linker copies the code from every object file, and from every static library you use, into that one executable.

A DLL (dynamic-link library) is the other choice. It is a file with the same format as an .exe (both are PE files, "Portable Executable") that holds compiled functions and data but has no main. It cannot run by itself. Instead, a running program asks Windows to map the DLL into its memory, and from then on it can call the DLL's functions as if they were its own.

Look at almost any program on your computer and you find DLLs next to it, and many more in C:\Windows\System32: kernel32.dll, user32.dll, d3d11.dll. Your own Hello, world already uses several. std::cout ends up calling WriteFile in kernel32.dll, and unless you link the C runtime statically, the C and C++ runtime themselves live in DLLs (vcruntime140.dll, msvcp140.dll, ucrtbase.dll).

Static library or DLL

Static library (.lib) DLL (.dll plus its import .lib)
When the code joins your program At link time, copied into the .exe At load time or run time, mapped from the DLL file
Files you ship Just the .exe The .exe and every DLL it needs
Update a bug fix in the library Rebuild and reship every program that uses it Replace the DLL; programs pick it up next time they start
Two programs using it Each has its own copy on disk and in memory One copy on disk; Windows can share its code pages between processes
Calling a function A direct call Usually an indirect call through a table (lesson 1.05)
Can go missing No Yes: "The code execution cannot proceed because X.dll was not found"

Neither is "better". Lesson 4.05 comes back to choosing between them once you know all the costs.

Why programs use DLLs

1. Sharing one copy. user32.dll is used by nearly every program. Windows loads its code once and maps the same physical memory pages into every process that uses it. Only pages a process writes to get private copies. With hundreds of processes, that saves a great deal of memory.

2. Updating parts separately. A graphics driver, a font engine or a game's audio library can be replaced without rebuilding the programs that use it, as long as the replacement keeps the same interface (milestone 3 is about keeping that promise).

3. Loading code you did not have at build time. A program can look in a folder, find DLLs it has never seen, load them and call into them. That is how plugin systems, mods and many editors work (lesson 5.01).

4. Reloading code while running. Game developers put gameplay code in a DLL, change it, rebuild it and swap it into the running game without restarting (lesson 5.03).

5. Language boundaries. A DLL with a plain C interface can be called from C#, Python, Rust or a scripting language. The C ABI is the common language they all speak.

The costs

  • Distribution. Every DLL is a file that can be missing, the wrong version, or the wrong architecture (a 32-bit DLL cannot load into a 64-bit process).
  • A boundary. Memory, exceptions and C++ library types do not cross safely between modules built with different settings (lesson 2.05 and 2.06).
  • Start-up time. Each DLL must be found, mapped and connected when the program starts.
  • Security. If Windows looks for a DLL in the wrong place, it can load the wrong file. Lesson 4.02 shows how to load only the files you meant.

What is inside a DLL

Because it is a PE file, a DLL has the same parts as an .exe:

my_library.dll
├── headers           which machine (x64), where each section goes, the entry point
├── .text             machine code of the functions
├── .rdata            read-only data, plus the EXPORT table: the names and addresses it offers
├── .data             global variables
├── import table      the DLLs and functions it needs in turn
└── .reloc            how to fix addresses if it is loaded somewhere unexpected (lesson 1.02)

The export table is what makes a DLL a library: a list of names (and numbers, called ordinals) with the address of each function inside the file. A program that wants AddNumbers from my_library.dll looks that name up in the export table.

Common mistakes

Thinking a DLL makes code faster

Calls into a DLL go through an extra jump. Sharing memory helps the whole system, not one program's speed.

Shipping a program without its DLLs

Run your program on a clean machine, or a fresh virtual machine, before you share it. Missing runtime DLLs are the most common cause of "it works on my machine".
