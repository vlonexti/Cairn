Hot Reloading Code

lesson 5.033 of 5 in milestone 55 min1 practice task

Hot reloading means changing game code, rebuilding, and having the running game pick up the new code within a second, without restarting or losing your place. The trick is to put gameplay code in a DLL and swap it. This lesson covers the loop - watch, copy, unload, load - and the problems each step solves.

The idea

Split the game into two parts:

  • The host (game.exe): window, main loop, memory, input, loading assets. It rarely changes and keeps running.
  • The game code (gameplay.dll): the rules, movement, enemy behaviour. You change it all day.

The host calls into the DLL through a small table, exactly like a plugin:

C++
typedef struct game_api
{
    uint32_t size;
    void (*update)(game_state* state, const game_input* input, float dt);
    void (*render)(const game_state* state, render_list* out);
} game_api;

extern "C" __declspec(dllexport) const game_api* get_game_api(void);

All game state lives in memory the host owns and passes in (lesson 5.04 explains why). The DLL is just functions.

The reload loop

Every frame, before calling update, the host checks whether the DLL file has changed:

C++
FILETIME lastWrite(const wchar_t* path);

void Host::reloadIfChanged()
{
    const FILETIME now{ lastWrite(L"gameplay.dll") };
    if (CompareFileTime(&now, &m_loadedWriteTime) == 0) return;   // unchanged

    // 1. Copy the new DLL to a fresh name and load the copy.
    const std::wstring copy{ L"gameplay_" + std::to_wstring(++m_generation) + L".dll" };
    if (!CopyFileW(L"gameplay.dll", copy.c_str(), FALSE)) return;  // the compiler may still be writing it: try next frame
    HMODULE fresh{ LoadLibraryW(copy.c_str()) };
    auto get{ fresh ? reinterpret_cast<const game_api* (*)()>(GetProcAddress(fresh, "get_game_api")) : nullptr };
    if (!get) { if (fresh) FreeLibrary(fresh); return; }               // keep running the old code

    // 2. Swap: drop every pointer into the old DLL, then unload it.
    m_api = get();
    if (m_module) FreeLibrary(m_module);
    m_module = fresh;
    m_loadedWriteTime = now;
}

Why copy before loading?

A loaded DLL's file is locked: Windows maps it into memory and will not let anyone overwrite it. If the game loaded gameplay.dll itself, the next build would fail with "cannot open file for writing". Loading a copy leaves the original free for the compiler. Each reload uses a new name (gameplay_7.dll) because the previous copy may still be loaded at the moment you copy.

Why only after the build has finished?

The linker writes the DLL over several hundred milliseconds. If the host notices the new time stamp half-way through, it may copy a half-written file. Two common fixes:

  • Wait until the time stamp has been stable for a few checks (say 200 ms) before reloading.
  • Have the build write a small "lock" file first and delete it when done; reload only when the lock file is gone.

The practice builds the "stable for several polls" watcher.

The PDB problem

The debugger also locks the DLL's PDB (debug symbols) while the DLL is loaded, so the next link fails to write gameplay.pdb. Give each build's PDB a unique name in Linker, Debugging, Generate Program Database File, for example $(OutDir)gameplay_$([System.DateTime]::Now.Ticks).pdb. Old PDB files pile up; delete them on start-up.

What must not survive a reload

After FreeLibrary on the old DLL, everything that pointed into it is invalid:

  • function pointers (the old game_api table, callbacks stored anywhere);
  • string literals from the old DLL;
  • vtables: any C++ object created by the old DLL's code has a vptr into the old DLL;
  • static and global variables inside the DLL, which are reset to their initial values in the new one.

That is why state lives in host memory, and why the state is plain data without virtual functions. Lesson 5.04 handles state whose layout changes between builds.

Common mistakes

Loading the DLL itself instead of a copy

The next build cannot overwrite the locked file.

Keeping the old table after unloading

Read the new table before freeing the old module, and never keep pointers to the old one.
