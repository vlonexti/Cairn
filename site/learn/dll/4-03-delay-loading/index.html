Delay Loading

lesson 4.033 of 5 in milestone 45 min1 practice task

Delay loading gives you the convenience of linking against an import library with the timing of run-time loading. The DLL is loaded the first time one of its functions is called, not when the program starts. This lesson shows how to turn it on, what happens on the first call, and how to handle a DLL that turns out to be missing.

Between the two

Load time Delay load Run time
Write code with Normal calls Normal calls LoadLibraryW and GetProcAddress
DLL loaded Before main On the first call into it When you ask
Missing DLL Program does not start An exception on the first call NULL, you decide

Delay loading is ideal for a DLL that only some users need: an exporter for one file format, a voice-chat library, a crash reporter. The program starts faster and works without it, and your code still calls its functions normally.

Turning it on

Two linker settings on the program (nothing changes in the DLL):

  • Linker, Input, Delay Loaded Dlls: StoneMath.dll (this adds /DELAYLOAD:StoneMath.dll).
  • Linker, Input, Additional Dependencies: add delayimp.lib, the helper library that does the loading.

Keep linking StoneMath.lib as before. Your code does not change at all.

What happens on the first call

The linker writes each delay-loaded import with a placeholder that points at a small thunk instead of the real function. On the first call:

  1. The thunk calls the delay-load helper, __delayLoadHelper2.
  2. The helper loads the DLL with LoadLibrary (if this is the first function from it) and finds the function with GetProcAddress.
  3. It writes the real address into the delay-load import table, so the next call goes straight to the function.
  4. It jumps to the function.

So the first call is slower, every later call is as fast as a normal import. The practice simulates exactly this: a slot that resolves itself once.

When the DLL is missing

With load-time linking, a missing DLL stops the program before main. With delay loading, the problem appears on the first call, as a structured exception (not a C++ exception) with the code VcppException(ERROR_SEVERITY_ERROR, ERROR_MOD_NOT_FOUND), or ERROR_PROC_NOT_FOUND for a missing function.

Two ways to handle it:

Check first. Before calling into the DLL, try to load it yourself:

C++
bool stoneMathAvailable()
{
    // Loads the delay-loaded DLL now, or returns a failure instead of an exception.
    return SUCCEEDED(__HrLoadAllImportsForDll("StoneMath.dll"));
}

A failure hook. The helper calls a function you provide when loading fails, which can return a fallback:

C++
#include <delayimp.h>

FARPROC WINAPI onDelayLoadFailure(unsigned notification, PDelayLoadInfo info)
{
    if (notification == dliFailGetProc && std::strcmp(info->dlp.szProcName, "stackWeight") == 0)
        return reinterpret_cast<FARPROC>(&fallbackStackWeight);   // used instead of the missing function
    return nullptr;                                               // nullptr: raise the exception as usual
}

ExternC const PfnDliHook __pfnDliFailureHook2 = onDelayLoadFailure;

Unloading

A delay-loaded DLL can also be unloaded with __FUnloadDelayLoadedDLL2("StoneMath.dll") if you link with /DELAY:UNLOAD. The thunks are reset so the next call loads it again. It is rarely needed; plugin systems and hot reload use LoadLibraryW directly instead.

Limits

  • You cannot delay-load a DLL whose data (exported variables) you use directly; only function calls go through thunks.
  • kernel32.dll cannot be delay-loaded (the helper itself needs it).
  • Do not delay-load DLLs called from DllMain or global constructors (lesson 2.04): the first call would load a DLL under the loader lock.

Common mistakes

Forgetting delayimp.lib

The linker reports __delayLoadHelper2 as an unresolved external symbol.

Catching the failure with try/catch

It is a structured exception, not a C++ exception. Check availability first, or use the failure hook.
