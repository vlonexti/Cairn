DllMain and the Loader Lock

lesson 2.044 of 6 in milestone 26 min2 practice tasks

A DLL can have an entry point, DllMain, that Windows calls when the DLL is loaded and unloaded and when threads start and end. It runs while the loader holds a lock, which makes most interesting work inside it dangerous. This lesson shows what DllMain is for, what it must never do, and what to do instead.

The entry point

C++
#include <windows.h>

BOOL APIENTRY DllMain(HMODULE module, DWORD reason, LPVOID reserved)
{
    switch (reason)
    {
    case DLL_PROCESS_ATTACH:   // the DLL was just mapped into a process
        DisableThreadLibraryCalls(module);   // we do not need the two thread notifications
        break;
    case DLL_THREAD_ATTACH:    // a new thread started in the process
        break;
    case DLL_THREAD_DETACH:    // a thread is ending cleanly
        break;
    case DLL_PROCESS_DETACH:   // the DLL is about to be unmapped
        // reserved != nullptr: the whole process is exiting; reserved == nullptr: FreeLibrary
        break;
    }
    return TRUE;               // FALSE from PROCESS_ATTACH makes the load fail (error 1114)
}

The template in lesson 1.03 created exactly this in dllmain.cpp. You do not have to write a DllMain; if you do not, the C runtime supplies one.

What really runs at load time

Before your DllMain is called with DLL_PROCESS_ATTACH, the C runtime's own entry point (_DllMainCRTStartup) runs. It initialises the CRT for this DLL and then runs the constructors of the DLL's global C++ objects. At DLL_PROCESS_DETACH, after your DllMain returns, it runs their destructors.

So a global like

C++
std::vector<std::string> g_names{ "basalt", "granite" };
Logger g_log{ "stonemath.log" };     // opens a file in its constructor

runs its constructor under the same conditions as DllMain, with the same rules.

The loader lock

While the loader maps DLLs, runs their entry points and updates its module list, it holds a process-wide lock: the loader lock. DllMain and global constructors run while it is held. Any other thread that wants to load a DLL, unload one, or even look up certain module information, waits for the lock.

That makes these things dangerous inside DllMain (and in global constructors and destructors of a DLL):

Do not Why
Call LoadLibrary or FreeLibrary Changes the module list while it is being changed; can deadlock or load in the wrong order
Create a thread and wait for it The new thread's start needs the loader lock (it sends DLL_THREAD_ATTACH), which you hold: deadlock
Wait on any lock another thread might hold while it needs the loader lock Deadlock
Call into other DLLs that may not be initialised yet Only kernel32.dll is guaranteed ready
Use COM, sockets, the registry, or user interface functions Each may load DLLs or wait on locks internally

Microsoft's guidance is blunt: do as little as possible in DllMain. Setting variables, DisableThreadLibraryCalls, InitializeCriticalSection, TlsAlloc: fine. Anything that loads, waits or talks to other components: not fine.

Deadlocks here are intermittent

Code that waits inside DllMain often works on your machine and hangs on someone else's, depending on timing and on which DLLs happen to be loaded already.

What to do instead: explicit initialisation

Give the DLL functions for setting up and tearing down, and have the program call them at a normal time:

C++
extern "C" STONEMATH_API int  stonemath_init(const char* logPath);   // after LoadLibrary returns
extern "C" STONEMATH_API void stonemath_shutdown();                  // before FreeLibrary

Inside stonemath_init, the loader lock is not held. You can open files, start worker threads and wait for them, load other DLLs, read settings. That is the pattern every plugin system in milestone 5 uses.

Another useful pattern is lazy initialisation: set things up the first time a function needs them, guarded by std::call_once or a function-local static (which C++ makes thread-safe).

Thread notifications

DLL_THREAD_ATTACH arrives for threads started after the DLL was loaded, not for threads that already existed. DLL_THREAD_DETACH arrives when a thread ends cleanly, but not for every thread if the process is ending. Code that tries to track every thread through these notifications always has gaps; use thread-local storage (thread_local) instead, which the CRT manages for you. DisableThreadLibraryCalls turns the two notifications off, which saves work in programs with many threads.

Process exit

When the whole process exits, Windows ends every other thread first, abruptly, and then sends DLL_PROCESS_DETACH with reserved non-null. At that point other threads may have died holding locks, and memory your DLL depends on may already be gone. In that case the safest thing is to do nothing: the operating system reclaims all memory and handles anyway. Only clean up when reserved is null (an explicit FreeLibrary).

Common mistakes

Starting a worker thread in DllMain and joining it

The join waits for a thread that is waiting for the loader lock you hold. Start and stop threads from an explicit init and shutdown function.

Global objects with heavy constructors in a DLL

They run inside the loader lock too. Prefer creating them in an init function or on first use.
