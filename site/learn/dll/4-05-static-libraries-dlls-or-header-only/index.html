Static Libraries, DLLs or Header-Only

lesson 4.055 of 5 in milestone 45 min1 practice task

You now know what DLLs cost and what they give. This lesson compares the three ways to package reusable C++ code - header-only, static library, DLL - and gives a short set of questions for choosing, with examples from real projects.

The three packages

Header-only. All the code is in headers, often templates or inline functions. Every program that includes them compiles its own copy. Examples: much of the standard library, {fmt}, nlohmann/json, Dear ImGui's helpers.

Static library (.lib). Compiled once into object code; the linker copies what each program uses into its .exe. Examples: most libraries you get through a package manager by default.

DLL. Compiled once into its own file; programs load it when they start or while they run. Examples: the Windows API, graphics drivers, the C runtime, plugin systems.

Questions to choose with

Ask them in order; the first "yes" usually decides.

  1. Do other languages or other teams' programs need to call it? A DLL with a C interface.
  2. Must it be loaded, swapped or unloaded while running (plugins, mods, hot reload)? A DLL.
  3. Must it be updated without rebuilding the programs that use it (a driver, a shared component)? A DLL.
  4. Is it mostly templates, or small? Header-only.
  5. Otherwise: a static library. It is the simplest thing that works: one file to ship, no ABI to design, no search order, no loader lock.

How real game projects use them

  • Engine as DLLs, during development only. Engines such as Unreal build each module (Core, Renderer, Physics...) as a DLL in development, so editing one module relinks one small DLL instead of the whole game, and enables hot reload. Shipping builds link the same code statically into one executable for speed and simplicity. Both use the same source; a build setting switches the export macro to nothing.
  • Gameplay code as a DLL while developing, reloaded on every rebuild (lesson 5.03).
  • Mods and plugins as DLLs with a stable C or COM-style interface (lessons 5.01 and 5.02).
  • Third-party SDKs (audio middleware, platform services) usually as DLLs, because they are updated separately from your game.

One codebase, both ways

The export macro from lesson 1.03 can do double duty:

C++
#if defined(STONEMATH_STATIC)
#define STONEMATH_API                              // linked statically: no import or export
#elif defined(STONEMATH_EXPORTS)
#define STONEMATH_API __declspec(dllexport)
#else
#define STONEMATH_API __declspec(dllimport)
#endif

Define STONEMATH_STATIC in both the library and the program when you build the library as a static .lib.

Common mistakes

Making everything a DLL "for modularity"

Modularity is about interfaces, not file formats. Every DLL adds a boundary with real rules. Use one when you need what only a DLL gives.

A header-only library that is huge

Every file that includes it pays to compile it. Split heavy code into a compiled library and keep the header light.
