Exporting Functions and Data

lesson 1.044 of 6 in milestone 15 min2 practice tasks

There are two ways to say what a DLL exports, __declspec(dllexport) and a module-definition file (.def). This lesson covers both, plus ordinals, exporting variables, and what goes into the export table.

The export table, up close

Each entry in a DLL's export table has:

  • a name (optional), such as stackHeight;
  • an ordinal, a number unique within the DLL;
  • an RVA: where the function or variable starts, relative to the DLL's base.

Other modules find an export either by name or by ordinal. Names are the normal way. Ordinals are small numbers that are faster to look up and hide the name, but they are fragile: if ordinal 3 means a different function in the next version, every program built against the old one silently calls the wrong code.

Way 1: __declspec(dllexport)

You met this in lesson 1.03. The compiler writes an instruction for the linker into the object file, and the linker adds the name to the export table. It is easy and keeps the "this is public" information next to the declaration.

The catch is the name. For a C++ function the exported name is the compiler's decorated (mangled) name, which also encodes the parameter types:

Output
int stackHeight(int, int)   is exported as   ?stackHeight@@YAHHH@Z

Lesson 2.01 explains decoration and how extern "C" gives you the plain name stackHeight instead, which is what you want for anything called from another language or loaded with GetProcAddress.

Way 2: a module-definition file

A .def file lists exports by hand. Add one to the DLL project (Add, New Item, Module-Definition File); Visual Studio sets Linker, Input, Module Definition File to it.

Output
LIBRARY   StoneMath
EXPORTS
    stackHeight       @1
    stackWeight       @2
    internalCounter   @3   DATA
    debugDump         @4   NONAME
    StackHeight = stackHeight
Line Meaning
LIBRARY StoneMath The DLL's name
stackHeight @1 Export stackHeight with ordinal 1
internalCounter @3 DATA Export a variable, not a function
debugDump @4 NONAME Export by ordinal only: no name in the table
StackHeight = stackHeight Export the internal function stackHeight under a different public name

Lines starting with ; are comments. The names in a .def file must match the symbols the compiler produced, so a .def file works most comfortably with extern "C" functions.

Why use a .def file at all?

  • To give fixed ordinals that never change between versions.
  • To export a function under a different name than the one in the code.
  • To export plain names from code you cannot or do not want to change.

Exporting variables

A DLL can export a global variable:

C++
// in the DLL
STONEMATH_API int g_stonesCreated = 0;

// in the header, for users
extern STONEMATH_API int g_stonesCreated;

The program then reads and writes the DLL's variable directly. It works, but every program now depends on that variable's type and meaning. A function such as int stonesCreated() can change how it works without breaking anyone, so prefer functions. Lesson 3.01 turns that into a rule.

Seeing what you exported

Open a Developer Command Prompt and run:

Output
dumpbin /exports StoneMath.dll
Output (yours will differ)
    ordinal hint RVA      name

          1    0 00011023 stackHeight = @ILT+30(stackHeight)
          2    1 000110A5 stackWeight = @ILT+160(stackWeight)
          3    2 0001C000 internalCounter
          4      000111D6 [NONAME]

The hint is an index into the name table that lets the loader skip a search when it is right. Lesson 1.06 covers dumpbin and other tools.

Common mistakes

Reusing an ordinal for a different function

Programs that import by ordinal will call the wrong function. Once published, an ordinal belongs to its function forever.

[!warning] Putting a C++ name with no extern "C" in a .def file The linker looks for a symbol called exactly that and does not find the decorated one. Use extern "C" for exported functions listed in a .def file.
