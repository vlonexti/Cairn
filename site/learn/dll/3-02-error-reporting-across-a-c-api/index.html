Error Reporting Across a C API

lesson 3.022 of 6 in milestone 35 min1 practice task

A C interface reports failure with result codes, but a code alone rarely tells a developer what went wrong. This lesson designs a result enum that can grow, adds a thread-local last error message like GetLastError, and shows how callers should handle codes they have never seen.

Result codes

Every function returns an int32_t result. Zero means success, which makes checks cheap and readable:

C++
typedef enum xenon_result
{
    XENON_OK                 = 0,
    XENON_INVALID_ARGUMENT   = 1,
    XENON_OUT_OF_MEMORY      = 2,
    XENON_NOT_FOUND          = 3,
    XENON_IO_ERROR           = 4,
    XENON_UNSUPPORTED        = 5,
    XENON_INTERNAL_ERROR     = 99,
} xenon_result;

Rules for codes:

  • Give every value an explicit number and never change it. A program compiled against version 1 has the numbers baked in.
  • Only add at the end (or in gaps you reserved).
  • Callers must treat an unknown nonzero code as a failure. Version 3 might return XENON_RATE_LIMITED = 6, which version 1's program has never heard of. A switch over the codes needs a default: that says "failed".

The return type is int32_t, not xenon_result, because the size of a C enum is not guaranteed to be the same everywhere.

Messages: a thread-local last error

A code says what kind of failure. A message says what exactly: "file 'world.xenon' line 12: weight must be positive". Windows itself solves this with GetLastError; the same pattern works for any library:

C++
// in the DLL
namespace { thread_local std::string t_lastError; }

static int32_t fail(int32_t code, std::string message)
{
    t_lastError = std::move(message);
    return code;
}

extern "C" XENON_API int32_t xenon_world_load(xenon_world* world, const char* path)
{
    if (!world || !path) return fail(XENON_INVALID_ARGUMENT, "world and path must not be null");
    ...
}

// returns the length; copies into buffer with the usual caller-buffer contract (lesson 2.05)
extern "C" XENON_API int32_t xenon_last_error(char* buffer, int32_t capacity);

Why thread-local? Two threads can call the library at once. With one global string, thread A's message could be overwritten by thread B's before A reads it. thread_local gives each thread its own.

Should success clear the message? Windows does not (a successful call may leave the previous error), and callers should only read the message right after a failure. Either way, document it.

A message for every code

It also helps to have a fixed description for each code, which never changes and needs no buffer:

C++
extern "C" XENON_API const char* xenon_result_name(int32_t code);
// "XENON_OK", "XENON_INVALID_ARGUMENT", ... and "XENON_UNKNOWN_RESULT" for anything else

Returning a const char* to a string literal is safe across the boundary: it lives in the DLL's read-only data and is never freed. Callers must not keep it after unloading the DLL.

Checking results without drowning in ifs

In C++ callers, a small helper turns codes back into exceptions on their side of the boundary, where both sides of the throw are in the same module:

C++
inline void check(int32_t result)
{
    if (result == XENON_OK) return;
    std::string message(static_cast<std::size_t>(xenon_last_error(nullptr, 0)), '\0');
    xenon_last_error(message.data(), static_cast<int32_t>(message.size()) + 1);
    throw std::runtime_error(std::string(xenon_result_name(result)) + ": " + message);
}

check(xenon_world_load(world, "world.xenon"));

Common mistakes

A switch with no default

New versions add codes. Without a default, an unknown failure is silently treated as... whatever the code after the switch does.

A global last-error string

Threads overwrite each other's messages. Use thread_local.

Returning a pointer to a std::string's buffer

It dangles as soon as the string changes. Return string literals, or copy into a caller buffer.
