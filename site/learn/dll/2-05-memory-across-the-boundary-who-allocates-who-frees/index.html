Memory Across the Boundary: Who Allocates, Who Frees

lesson 2.055 of 6 in milestone 25 min2 practice tasks

Memory allocated in one module and freed in another can crash, because each module may have its own copy of the C runtime and its own heap. The fix is a simple rule: whoever allocates, frees. This lesson shows why it breaks and the standard patterns that keep it safe.

The crash

A DLL function returns a string the caller should free:

C++
// in StoneMath.dll
extern "C" STONEMATH_API char* describeStack(int stones)
{
    char* text{ new char[64] };
    snprintf(text, 64, "%d stones", stones);
    return text;
}

// in the program
char* s{ describeStack(12) };
std::cout << s << '\n';
delete[] s;           // may crash, may corrupt memory, may seem fine

Whether it works depends on how both modules were built.

Why: one CRT per module, sometimes

new, delete, malloc and free belong to the C runtime library (CRT). Each module chooses how it gets its CRT:

Setting What the module gets
/MD (Multi-threaded DLL, the default) The shared runtime DLLs (ucrtbase.dll, vcruntime140.dll). Modules using the same version share one heap
/MT (Multi-threaded, static) Its own private copy of the CRT linked inside, with its own heap
/MDd, /MTd The same, but debug versions, with a different heap layout again

If the DLL is built with /MT, its new takes memory from the DLL's private heap, and the program's delete gives it back to the program's heap, which has never seen that block. If the DLL is Debug and the program is Release, the heaps disagree about the block's layout. Either way the heap is corrupted, and the crash can come much later.

Even when both use /MD today, a future version of the DLL might be built with a different compiler or setting. You cannot rely on it.

The rule

Memory is freed by the module that allocated it.

Three patterns follow from it.

1. The library frees what it allocates

C++
extern "C" STONEMATH_API char* stonemath_describe(int stones);   // caller must call stonemath_free
extern "C" STONEMATH_API void  stonemath_free(char* text);       // frees with the DLL's own delete[]

2. The caller provides the buffer

The Win32 API's favourite: the caller owns the memory, the DLL only writes into it.

C++
// Returns the number of characters needed, not counting the terminating zero.
// Writes at most capacity characters including the zero.
extern "C" STONEMATH_API int stonemath_describe_into(int stones, char* buffer, int capacity);

// Asking twice: once for the size, once for the text
int needed{ stonemath_describe_into(12, nullptr, 0) };
std::string text(static_cast<std::size_t>(needed), '\0');
stonemath_describe_into(12, text.data(), needed + 1);

The practice has you write a function with exactly this contract.

3. Objects with a create/destroy pair

For anything bigger than a string, the DLL hands out an opaque handle and offers a function to release it (lesson 3.01 builds a whole API this way):

C++
extern "C" STONEMATH_API Xenon* xenon_create(int stones);
extern "C" STONEMATH_API void   xenon_destroy(Xenon* xenon);

What about std::string and std::vector?

Passing a std::string by value or reference across the boundary means one module may grow or free a buffer the other allocated. And the layout of std::string differs between Debug and Release, and has changed between compiler versions. That is lesson 2.06's topic. For now: inside a DLL, use whatever you like; at its C interface, use pointers, sizes and plain structs.

Finding leaks across a boundary

Because ownership is now explicit, you can track it. Keep a count of live objects in the DLL: increase it in every create function, decrease it in every destroy function, and report anything left over in stonemath_shutdown. The practice builds such a tracker.

Common mistakes

Freeing a DLL's memory with your own free or delete

Use the DLL's free function. Even if it works today, it will break when either side's build settings change.

Off-by-one in buffer sizes

Document whether a size includes the terminating zero, and test the boundary: a buffer exactly one character too small.

  1. A DLL built with /MT allocates with new. The program frees with delete. What is wrong?
    • The DLL has its own private heap, so the program frees memory its heap never allocated
    • Nothing; new and delete are always shared
    • delete is slower across a DLL boundary

    The DLL has its own private heap, so the program frees memory its heap never allocated Each statically linked CRT has its own heap.

  2. Which interface follows the "whoever allocates, frees" rule?
    • A create function paired with a destroy function in the same DLL
    • A function returning new char[] that the caller deletes
    • A function returning std::string by value
    Show the answer

    A create function paired with a destroy function in the same DLL The DLL's destroy function frees with the same heap that allocated.

  3. In the "caller provides the buffer" pattern, why call the function first with a null buffer?
    • To find out how large a buffer is needed
    • To initialise the DLL
    • Because the first call always fails
    Show the answer

    To find out how large a buffer is needed The caller then allocates exactly enough and calls again.
