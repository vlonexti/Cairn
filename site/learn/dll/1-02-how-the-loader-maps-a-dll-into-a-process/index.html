How the Loader Maps a DLL into a Process

lesson 1.022 of 6 in milestone 16 min2 practice tasks

Before main runs, the Windows loader finds every DLL the program needs, maps each one into memory once, loads their own dependencies, fixes up addresses and fills in the program's tables of function addresses. Knowing these steps explains most "DLL not found" and "entry point not found" errors.

The loader

When you start a program, Windows creates a process and then runs code in ntdll.dll called the loader. Its job is to turn files on disk into a ready-to-run address space. For each module (the .exe and every DLL) it:

  1. Finds the file using the DLL search order (lesson 4.01).
  2. Maps it into memory: it reserves a range of the process's address space and makes the file's sections appear there, with the right protection (code readable and executable, data readable and writable).
  3. Relocates it if it could not be placed at its preferred address.
  4. Loads its dependencies: every DLL listed in its import table, recursively.
  5. Binds its imports: looks up each imported function in the other DLL's export table and writes the real address into this module's import address table (IAT).
  6. Runs its initialisation: for a DLL, its DllMain with DLL_PROCESS_ATTACH (lesson 2.04), which also constructs its global C++ objects.

Only when all of that has worked does the program's own start-up code run, construct its globals and call main.

Each DLL is loaded once

The loader keeps a list of modules already in the process. If game.exe needs audio.dll and physics.dll, and both of those need math.dll, math.dll is still loaded only once. The second request just finds it in the list and increases its reference count.

graph TD
  game[game.exe] --> audio[audio.dll]
  game --> physics[physics.dll]
  audio --> math[math.dll]
  physics --> math
  math --> k32[kernel32.dll]
  audio --> k32

Dependencies are initialised before the modules that need them, so math.dll is ready by the time audio.dll's initialisation runs. In the graph above one valid order is kernel32.dll, math.dll, audio.dll, physics.dll, then game.exe itself. That is a depth-first, dependencies-first walk, the order you will compute in the practice.

Preferred addresses and relocation

Every module is built for a preferred base address. Code that refers to a global variable often contains that variable's absolute address, worked out as base + offset. If the module really lands at its preferred base, all those addresses are already right.

If something else already occupies that range, the loader puts the module elsewhere and has to relocate it: for every place listed in the .reloc section, it adds the difference between the actual base and the preferred base. Offsets inside a module are called RVAs (relative virtual addresses):

Output
address = base + RVA
actual address after relocation = actual base + RVA
fix-up applied to each stored address = actual base - preferred base

With ASLR (address space layout randomisation), Windows deliberately picks a random base for most modules each time, to make attacks harder, so relocation is normal rather than rare. 64-bit code also uses addresses relative to the instruction pointer for most data, which needs no fix-ups at all.

When it goes wrong

The loader's failures have recognisable messages:

Message Meaning
"The code execution cannot proceed because X.dll was not found." Step 1 failed for X.dll
"The procedure entry point Foo could not be located in the dynamic link library X.dll." Step 5: X.dll was found but does not export Foo, usually because it is a different version
"The application was unable to start correctly (0xc000007b)." Usually a 32-bit DLL in a 64-bit process, or the reverse
A DllMain returned FALSE Step 6: initialisation of that DLL failed, so loading fails

Common mistakes

Assuming dependencies are loaded in the order you list them

The loader walks the dependency graph. Never rely on one DLL's initialisation having run before another's unless one depends on the other.

Mixing 32-bit and 64-bit

A process is one or the other, and every DLL it loads must match.

    Once; the second request increases its reference count The loader keeps a list of loaded modules and reuses them.

  2. A module's preferred base is 0x180000000 but it lands at 0x7FF600000000. A stored address was 0x180001234. What is it after relocation?
    • 0x7FF600001234
    • 0x180001234
    • 0x7FF600000000
    Show the answer

    0x7FF600001234 The fix-up adds (actual base - preferred base) to every listed address, so the RVA 0x1234 is kept.

  3. Which step of loading produces "The procedure entry point could not be located"?
    • Binding imports against the other DLL's export table
    • Mapping the file
    • Running DllMain
    Show the answer

    Binding imports against the other DLL's export table The DLL was found, but it does not export that name.
