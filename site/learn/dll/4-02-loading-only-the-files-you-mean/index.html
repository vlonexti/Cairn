Loading Only the Files You Mean

lesson 4.022 of 5 in milestone 45 min2 practice tasks

Loading a DLL by bare name leaves the choice of file to the search order, which an attacker or an accident can influence. This lesson shows how to load exactly the file you intend - full paths, SetDefaultDllDirectories, AddDllDirectory and the LOAD_LIBRARY_SEARCH_* flags - and how to check a plugin folder before loading anything from it.

The risk

If a program loads renderer.dll by name and that name is not found in the application folder, Windows keeps searching, eventually in the current directory and on PATH. Anyone who can put a file called renderer.dll in one of those places gets their code run inside your program. This is called DLL planting or DLL search-order hijacking, and it has been the cause of many real security problems.

Accidents follow the same path: an old copy of a DLL in some folder on PATH gets loaded instead of yours.

The defence is the same for both: never let Windows guess.

1. Use full paths for run-time loading

Build the path from a folder you trust, normally the application's own:

C++
#include <windows.h>
#include <filesystem>

std::filesystem::path appFolder()
{
    wchar_t buffer[MAX_PATH]{};
    const DWORD length{ GetModuleFileNameW(nullptr, buffer, MAX_PATH) };   // full path of our own .exe
    return std::filesystem::path(std::wstring(buffer, length)).parent_path();
}

HMODULE renderer{ LoadLibraryW((appFolder() / L"renderer.dll").c_str()) };

GetModuleFileNameW(nullptr, ...) returns the path of the .exe. With a full path, LoadLibraryW loads exactly that file (or fails).

2. Restrict the search for everything else

Even with full paths for your own DLLs, those DLLs import others by name. Call this once, first thing in main:

C++
SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_DEFAULT_DIRS);

From then on, every name-only load in the process searches only:

  • the application folder (LOAD_LIBRARY_SEARCH_APPLICATION_DIR),
  • System32 (LOAD_LIBRARY_SEARCH_SYSTEM32),
  • folders you add yourself with AddDllDirectory (LOAD_LIBRARY_SEARCH_USER_DIRS).

The current directory and PATH are not searched any more. For a new program there is no reason not to do this.

3. LoadLibraryExW with search flags

LoadLibraryExW takes flags that control the search for one call:

C++
HMODULE m{ LoadLibraryExW(path, nullptr, LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS) };
Flag Searches
LOAD_LIBRARY_SEARCH_APPLICATION_DIR The .exe's folder
LOAD_LIBRARY_SEARCH_SYSTEM32 System32
LOAD_LIBRARY_SEARCH_USER_DIRS Folders added with AddDllDirectory
LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR The folder of the DLL being loaded (only with a full path)
LOAD_LIBRARY_SEARCH_DEFAULT_DIRS The first three together

LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR solves lesson 4.01's subfolder problem: a plugin loaded from plugins\fog\fog.dll can now find plugins\fog\noise.dll, which it depends on.

4. Check what you are about to load

A plugin folder is a place users (and installers) write files to. Before loading, check:

  • the path is absolute and really inside the folder you meant (no .. escaping out of it);
  • the file name ends in .dll;
  • for software you distribute widely, that the file is signed with your certificate (WinVerifyTrust), so a replaced file is refused.

Lesson 5.01's plugin loader does the first two; the practice for this lesson writes the path check.

Data files that look like DLLs

If you only want to read a DLL's resources (icons, strings, version info) without running any of its code, load it as data:

C++
HMODULE resources{ LoadLibraryExW(path, nullptr, LOAD_LIBRARY_AS_DATAFILE | LOAD_LIBRARY_AS_IMAGE_RESOURCE) };

No DllMain runs and nothing is executable.

Common mistakes

Calling SetDefaultDllDirectories after DLLs were already loaded by name

It only affects loads that happen after it. Call it at the very start.

Building a plugin path from user input without checking it

"..\\..\\Windows\\something.dll" escapes the plugin folder. Normalise the path and check its parent.
