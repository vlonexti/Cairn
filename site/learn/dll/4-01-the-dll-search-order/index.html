The DLL Search Order

lesson 4.011 of 5 in milestone 45 min1 practice task

When a program asks for a DLL by name rather than by full path, Windows tries a fixed list of places. Knowing that list explains why the wrong copy of a DLL sometimes loads, why "it works on my machine", and why putting your DLLs next to your .exe is the reliable choice.

A name, not a path

Most DLLs are requested by name only: the import table of your .exe says StoneMath.dll, and LoadLibraryW(L"StoneMath.dll") gives no folder either. Windows then has to decide which file that means.

Before any folder is searched

Two checks come first:

  1. Already loaded? If a module with that name is already in the process, it is reused. This is why loading StoneMath.dll from two places never gives you two copies: the second request finds the first.
  2. Known DLLs. Windows keeps a list of core system DLLs (kernel32.dll, user32.dll, ole32.dll and others, listed in the registry under KnownDLLs). For those it always uses the copy in System32, whatever folders come later. You cannot override kernel32.dll by putting a file next to your program.

(There are also API sets, the api-ms-win-... names from lesson 1.06, which are redirected to real system DLLs without any search.)

The standard search order

If neither check settles it, a desktop application searches these places in order, and loads the first file with that name it finds:

  1. The folder the application's .exe is in.
  2. The system folder, C:\Windows\System32.
  3. The 16-bit system folder, C:\Windows\System.
  4. The Windows folder, C:\Windows.
  5. The current directory (the program's working directory).
  6. Every folder on the PATH environment variable, in order.

This is the order with safe DLL search mode, which has been on by default for many years. Without it, the current directory was searched second, which is why it was moved down: an attacker who could put a file in your working directory (a downloaded folder, a network share) could get it loaded before the system's copy. Lesson 4.02 goes further.

What this means in practice

  • Put your DLLs next to your .exe. The application folder is searched first, so your copy wins, and the program works no matter what the user's PATH or working directory is.
  • Never rely on the current directory. It changes with shortcuts, command lines and file dialogs.
  • Never rely on PATH for your own DLLs. It is the last place searched and differs on every machine. Something earlier on PATH with the same name wins, which is the classic "works on my machine" story.
  • Avoid generic names. utils.dll or zlib.dll may already be loaded into the process by some other component, and Windows will happily give you that one instead (check 1 above).

Seeing the search happen

Process Monitor (lesson 1.06) shows every attempt. A program in C:\Games\Xenon asking for missing.dll produces a trail like:

Output (yours will differ)
C:\Games\Xenon\missing.dll            NAME NOT FOUND
C:\Windows\System32\missing.dll       NAME NOT FOUND
C:\Windows\System\missing.dll         NAME NOT FOUND
C:\Windows\missing.dll                NAME NOT FOUND
C:\Users\you\Desktop\missing.dll      NAME NOT FOUND      (the current directory)
C:\Program Files\Git\cmd\missing.dll  NAME NOT FOUND      (PATH...)

A dependency's dependencies

When StoneMath.dll itself imports zlib.dll, the same search runs, still based on the application's folder, not the folder StoneMath.dll came from. So if you load a DLL from a subfolder by full path, its own dependencies are not found in that subfolder unless you say so. Lesson 4.02 shows the flags that fix this, and lesson 5.01 uses them for plugins in their own folders.

Common mistakes

Testing only on the development machine

Your PATH contains Visual Studio, SDKs and tools with DLLs in them. A clean machine has none of that. Test there before shipping.

Assuming a DLL from a subfolder finds its friends in that subfolder

Its dependencies are searched for from the application's folder. Use full paths and the search flags from lesson 4.02.
