COM-Style Interfaces with vtables

lesson 3.044 of 6 in milestone 35 min1 practice task

A C interface can still give callers objects with methods, if the object's layout is just a pointer to a table of functions. On Windows, an abstract C++ class with only virtual functions has exactly that layout, which is how COM, DirectX and many plugin systems work. This lesson builds a COM-style interface with reference counting and QueryInterface.

An object is a pointer to a table

Lesson 3.03's function table is close to an object already. Put the table pointer inside the object, and pass the object to each function:

C
typedef struct IStone IStone;
typedef struct IStoneVtbl
{
    uint32_t (*AddRef)(IStone* self);
    uint32_t (*Release)(IStone* self);
    int32_t  (*Weight)(IStone* self);
} IStoneVtbl;

struct IStone { const IStoneVtbl* vtbl; };

// a C caller:
int32_t w = stone->vtbl->Weight(stone);

Now look at how MSVC lays out a C++ class that has only pure virtual functions and no data:

C++
struct IStone
{
    virtual uint32_t AddRef() = 0;
    virtual uint32_t Release() = 0;
    virtual int32_t  Weight() = 0;
};

An IStone object is one hidden pointer, the vptr, to a table of three function pointers, in the order the functions are declared. A call stone->Weight() loads the vptr, loads entry 2, and calls it with the object pointer as the hidden first argument (this). That is the same layout as the C version. On Windows this layout is fixed by the platform's ABI, which is why a C++ interface like this can safely cross a DLL boundary between different compilers, and even be called from C, C#, Rust or Python.

What keeps it safe:

  • Only pure virtual functions, no data members, no constructors, and no virtual destructor: destructors' place in the vtable differs between compilers. The object deletes itself in Release.
  • Plain C types in every method's signature.
  • Never change an interface once published. Add a new interface instead (IStone2), which is what QueryInterface is for.
  • Everything uses the __stdcall convention on 32-bit Windows (COM's STDMETHODCALLTYPE); on x64 that does nothing.

Reference counting

Who deletes an object that several parts of a program hold? The object itself, when the last holder lets go. Each holder calls AddRef when it takes a reference and Release when it is done; Release deletes the object when the count reaches zero.

C++
class Basalt final : public IStone
{
public:
    uint32_t AddRef() override { return ++m_refs; }
    uint32_t Release() override
    {
        const uint32_t left{ --m_refs };
        if (left == 0) delete this;          // deleted by the module that created it
        return left;
    }
    int32_t Weight() override { return 7; }
private:
    std::atomic<uint32_t> m_refs{ 1 };      // the creator holds the first reference
};

delete this inside the DLL means memory is freed by the module that allocated it (lesson 2.05) no matter who calls Release. The count is atomic so threads can share objects.

QueryInterface: asking for more

A later version adds a method. Changing IStone would break every compiled caller, so you define a new interface, and let callers ask an object whether it supports it:

C++
struct IStone2 : IStone
{
    virtual int32_t Hardness() = 0;     // appended after IStone's methods
};

// Every interface identifies itself with a unique id (COM uses 128-bit GUIDs):
constexpr uint32_t IID_IStone  = 0x5354'0001;
constexpr uint32_t IID_IStone2 = 0x5354'0002;

// The base interface gains one more method, first in the table in real COM:
virtual int32_t QueryInterface(uint32_t iid, void** out) = 0;

QueryInterface(IID_IStone2, &p) returns success and an AddRef-ed pointer if the object implements it, or "not supported" and nullptr if it does not. A caller built for version 2 asks for IStone2; if the DLL is older, it falls back to IStone. Old callers never ask, so nothing changes for them.

Real COM's base interface is IUnknown with exactly three methods: QueryInterface, AddRef, Release. DirectX, the Windows shell and many audio APIs are built on it. You can use the pattern without any of COM's registration machinery.

Smart pointers

Calling AddRef and Release by hand is as error-prone as new and delete. Microsoft's Microsoft::WRL::ComPtr (and winrt::com_ptr) call them automatically, like a std::shared_ptr whose count lives in the object. Lesson 3.06 writes a small one.

Common mistakes

A virtual destructor in a cross-compiler interface

Its vtable slot (or slots) are compiler-specific. Delete through Release instead.

QueryInterface that forgets to AddRef

The caller will Release what it was given, which then frees the object too early.

Changing a published interface

Add a new one. That is the whole point of QueryInterface.
