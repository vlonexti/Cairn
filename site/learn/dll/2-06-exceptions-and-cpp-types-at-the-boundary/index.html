Exceptions and C++ Types at the Boundary

lesson 2.066 of 6 in milestone 25 min1 practice task

Besides memory, two other things must not cross a stable DLL boundary - exceptions and C++ library types such as std::string. This lesson shows what goes wrong, the "exception barrier" that turns exceptions into error codes at the edge of a DLL, and the rare case where exporting C++ types is fine.

Exceptions escaping a DLL

Inside a DLL, use exceptions as you normally would. The problem is an exception that leaves an exported function:

  • A program written in C, C#, Rust or Python has no idea what a C++ exception is. Its stack is unwound by machinery it never set up, and it usually crashes.
  • Two C++ modules built with different compilers, or different exception settings (/EHsc versus /EHa), may not agree on how exceptions are represented.
  • An exception object such as std::runtime_error contains a std::string allocated by one module's CRT and destroyed by the other's (lesson 2.05).

An extern "C" function is promising C behaviour, and C has no exceptions. So the rule is:

No exception crosses a DLL's C interface. Catch everything at the edge and turn it into an error code.

The exception barrier

Every exported function gets the same wrapper. Writing it once as a helper keeps it consistent:

C++
enum StonemathResult : int
{
    STONEMATH_OK = 0,
    STONEMATH_INVALID_ARGUMENT = 1,
    STONEMATH_OUT_OF_MEMORY = 2,
    STONEMATH_FAILED = 3,
    STONEMATH_UNKNOWN_ERROR = 4,
};

template <typename Fn>
int barrier(Fn&& body) noexcept
{
    try
    {
        body();
        return STONEMATH_OK;
    }
    catch (const std::invalid_argument&) { return STONEMATH_INVALID_ARGUMENT; }
    catch (const std::bad_alloc&)        { return STONEMATH_OUT_OF_MEMORY; }
    catch (const std::exception&)        { return STONEMATH_FAILED; }
    catch (...)                          { return STONEMATH_UNKNOWN_ERROR; }
}

extern "C" STONEMATH_API int stonemath_load(const char* path, int* stonesOut)
{
    return barrier([&] {
        if (!path || !stonesOut) throw std::invalid_argument("null argument");
        *stonesOut = loadStonesFromFile(path);      // ordinary C++ inside, may throw
    });
}

The order of the catch clauses matters: the most specific types first, std::exception after them, and catch (...) last for anything else. noexcept on the barrier documents, and enforces, that nothing gets out. Lesson 3.02 adds a way to fetch the error's message as well.

C++ types in the interface

What about a DLL that exports functions like this?

C++
STONEMATH_API std::string describeStack(const std::vector<int>& weights);

It compiles, and it works as long as the DLL and every program using it are built with:

  • the same compiler and the same major version of its standard library;
  • the same configuration: std::string and std::vector have a different layout in Debug (_ITERATOR_DEBUG_LEVEL=2) than in Release;
  • the same CRT setting (/MD everywhere), so that one heap is shared.

MSVC even helps: if you link modules with different _ITERATOR_DEBUG_LEVEL values, the linker stops with error LNK2038: mismatch detected. But that only catches modules linked together, not a DLL loaded at run time.

So there are two kinds of DLL:

Internal DLL Public, stable DLL
Built Together with the program, same solution, same settings Separately, perhaps years apart, perhaps by others
Interface C++: classes, std::string, exceptions are acceptable C: plain types, handles, error codes
Example Splitting your own game into engine.dll and game.exe built together A plugin API, a library you sell, anything other languages call

Most games' internal DLLs, and the hot-reload DLL in lesson 5.03, are the first kind. Plugin interfaces are always the second.

Passing text and lists through a C interface

Instead of std::string, pass a pointer and a length (or a zero-terminated string); instead of std::vector<int>, a pointer and a count:

C++
extern "C" STONEMATH_API int stonemath_total_weight(const int* weights, int count, long long* totalOut);

Inside, wrap them in std::string_view and std::span and you are back in comfortable C++.

Common mistakes

Forgetting catch (...)

Code you call can throw types that do not derive from std::exception. Without the last clause they escape.

Mixing Debug and Release modules with C++ types in the interface

The layout of standard library types differs. Keep internal C++ interfaces to modules built together.
