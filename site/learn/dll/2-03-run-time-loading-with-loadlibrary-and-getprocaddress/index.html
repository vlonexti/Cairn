Run-Time Loading with LoadLibrary and GetProcAddress

lesson 2.033 of 6 in milestone 25 min2 practice tasks

Instead of linking against an import library, a program can load a DLL whenever it likes with LoadLibraryW, look up functions by name with GetProcAddress, call them through function pointers, and unload the DLL with FreeLibrary. This is the foundation of plugins and hot reload.

Three functions

C++
HMODULE LoadLibraryW(LPCWSTR fileName);                 // map the DLL (and its dependencies); NULL on failure
FARPROC GetProcAddress(HMODULE module, LPCSTR name);    // address of an export; NULL if not found
BOOL    FreeLibrary(HMODULE module);                     // drop one reference; unmap at zero

HMODULE is a handle to a loaded module. Its value is in fact the module's base address. Note that GetProcAddress takes an ANSI string (there is no W version), because export names are plain bytes.

A complete example

StoneMath from lesson 1.03, now with extern "C" exports (lesson 2.01). The program does not link StoneMath.lib and does not include its header:

C++
#include <windows.h>
#include <iostream>

using StackHeightFn = int (*)(int, int);           // must match the DLL's declaration exactly

int main()
{
    HMODULE dll{ LoadLibraryW(L"StoneMath.dll") };
    if (!dll)
    {
        std::cerr << "Could not load StoneMath.dll, error " << GetLastError() << '\n';
        return 1;
    }

    auto stackHeight{ reinterpret_cast<StackHeightFn>(GetProcAddress(dll, "stackHeight")) };
    if (!stackHeight)
    {
        std::cerr << "StoneMath.dll has no stackHeight\n";
        FreeLibrary(dll);
        return 1;
    }

    std::cout << stackHeight(10, 4) << '\n';     // 3
    FreeLibrary(dll);
}

The reinterpret_cast is needed because GetProcAddress returns a generic FARPROC. The compiler cannot check that the type you cast to is right: if the DLL's function takes (double, int) and you cast to int(*)(int, int), the call compiles and silently passes garbage. Keep function pointer types in a header shared with the DLL.

Why not just link?

Run-time loading lets the program start even when the DLL is missing, choose which DLL to load (say, renderer_d3d11.dll or renderer_vulkan.dll), load DLLs it has never heard of (plugins), and unload and reload a DLL (hot reload).

Errors

When LoadLibraryW returns NULL, GetLastError() says why:

Code Name Usual cause
126 ERROR_MOD_NOT_FOUND The DLL, or one of its dependencies, was not found
127 ERROR_PROC_NOT_FOUND A dependency is missing an export the DLL imports
193 ERROR_BAD_EXE_FORMAT 32-bit DLL in a 64-bit process, or not a DLL at all
1114 ERROR_DLL_INIT_FAILED The DLL's DllMain returned FALSE

Error 126 is confusing: the DLL you named may be right there, but something it needs is not. Lesson 1.06's tools find out which.

Reference counting

Each successful LoadLibraryW of the same DLL increases its reference count and returns the same HMODULE. Each FreeLibrary decreases it. The DLL is unmapped only when the count reaches zero.

C++
HMODULE a{ LoadLibraryW(L"StoneMath.dll") };   // count 1, maps the DLL
HMODULE b{ LoadLibraryW(L"StoneMath.dll") };   // count 2, a == b
FreeLibrary(a);                                // count 1, still mapped
FreeLibrary(b);                                // count 0, unmapped

After the last FreeLibrary, every function pointer you got from that DLL points at memory that no longer belongs to it. Calling one crashes. So does using any object, string or vtable the DLL created. Lesson 5.03 deals with this carefully.

A small RAII wrapper

Forgetting FreeLibrary on an error path is easy. Wrap the handle:

C++
class Library
{
public:
    explicit Library(const wchar_t* file) : m_module{ LoadLibraryW(file) } {}
    ~Library() { if (m_module) FreeLibrary(m_module); }
    Library(const Library&) = delete;
    Library& operator=(const Library&) = delete;

    explicit operator bool() const { return m_module != nullptr; }

    template <typename Fn>
    Fn get(const char* name) const { return reinterpret_cast<Fn>(GetProcAddress(m_module, name)); }

private:
    HMODULE m_module;
};

Common mistakes

Casting to the wrong function type

The compiler cannot catch it. Share the typedef with the DLL.

Calling a function after FreeLibrary

Pointers into an unloaded DLL are dangling. Drop them before you free the library.

Passing a relative name and getting the wrong file

LoadLibraryW(L"StoneMath.dll") searches several folders. Lesson 4.02 shows how to load exactly the file you mean.
