Errors and Exceptions

lesson 3.033 of 5 in milestone 35 min1 practice task

Throwing and catching errors, the built-in error types, finally for clean-up, writing your own error classes, rethrowing what you cannot handle, error causes, validating input at the edges, and returning results instead of throwing.

throw and try/catch

When code cannot do its job, it throws an error. The error travels up through the calling functions until a try/catch handles it; if none does, the program stops with the message.

JavaScript
function parseAge(text) {
  const age = Number(text);
  if (!Number.isInteger(age)) throw new TypeError(`"${text}" is not a whole number`);
  if (age < 0 || age > 150) throw new RangeError(`age ${age} is out of range`);
  return age;
}

for (const input of ["42", "abc", "-5"]) {
  try {
    console.log("age:", parseAge(input));
  } catch (err) {
    console.log(`${err.name}: ${err.message}`);
  }
}

Always throw Error objects (or subclasses), never strings: they carry a name, a message and a stack showing where they came from.

Built-in error types

Type Thrown when
TypeError A value has the wrong type: calling something that is not a function, reading a property of undefined
RangeError A number is outside the allowed range
SyntaxError Code or JSON.parse input is not valid
ReferenceError A variable does not exist

finally

A finally block runs whether or not an error happened, even after return. It is the place for clean-up:

JavaScript
function withLog(task) {
  console.log("start");
  try {
    return task();
  } finally {
    console.log("end");          // runs before the value is returned, or while the error travels on
  }
}
console.log(withLog(() => 7));
try { withLog(() => { throw new Error("boom"); }); } catch (e) { console.log("caught", e.message); }

Your own error classes

Subclass Error so callers can tell your errors apart with instanceof:

JavaScript
class ValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

function checkUser(user) {
  if (!user.email?.includes("@")) throw new ValidationError("email", "email needs an @");
  return user;
}

try {
  checkUser({ email: "nope" });
} catch (err) {
  if (err instanceof ValidationError) console.log(`bad ${err.field}: ${err.message}`);
  else throw err;                // not ours: rethrow
}

Catch only what you can handle. A catch that swallows every error also hides bugs, like a typo that throws ReferenceError. Check the type and rethrow the rest.

When wrapping a low-level error in a clearer one, keep the original as its cause:

JavaScript
function loadConfig(text) {
  try { return JSON.parse(text); }
  catch (err) { throw new Error("config file is not valid JSON", { cause: err }); }
}
try { loadConfig("{oops"); } catch (e) { console.log(e.message, "<-", e.cause.name); }

Throwing or returning

Throw for situations the caller usually cannot continue from. When failure is an ordinary outcome (a search that finds nothing, a user typing a bad value), returning null or a result object such as { ok: false, error: "..." } is often clearer than making every caller write try. Validate input once, at the edge where it enters the program, so inner functions can trust their arguments.
