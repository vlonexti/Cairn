Testing JavaScript

lesson 8.044 of 5 in milestone 85 min2 practice tasks

Automated tests for JavaScript and TypeScript - what a test runner does, node:test and node:assert, deepStrictEqual versus strictEqual, testing errors and async code, fakes and spies made from plain functions, fake timers, and the shape of tests in Vitest and Jest.

Why write tests?

Every practice task on this site is checked by tests. Writing your own gives the same safety for your projects: change code, run the tests, and know within seconds whether something broke.

A test runner does three jobs: finds the tests, runs each one even if others fail, and reports which failed and why. Node.js has one built in (node:test), and most front-end projects use Vitest or Jest, which look almost the same.

node:test and node:assert

JavaScript
// math.test.js, run with: node --test
import { test } from "node:test";
import assert from "node:assert/strict";
import { average } from "./math.js";

test("average of two numbers", () => {
  assert.equal(average([2, 4]), 3);
});

test("empty input throws", () => {
  assert.throws(() => average([]), RangeError);
});

node --test finds files named like *.test.js and runs them. The strict assert module gives:

assertion passes when
assert.equal(a, b) a === b
assert.deepEqual(a, b) the two have the same structure and values
assert.ok(x) x is truthy
assert.throws(fn, Kind) calling fn throws an error of that kind
await assert.rejects(promise, Kind) the promise rejects
assert.match(text, /re/) the text matches

Equal and deep equal

JavaScript
import("node:assert/strict").then(({ default: assert }) => {
  assert.deepEqual({ a: [1, 2] }, { a: [1, 2] });       // passes: same contents
  try {
    assert.equal({ a: 1 }, { a: 1 });                    // fails: two different objects
  } catch (e) {
    console.log(e.name);
  }
  console.log("done");
});

=== compares objects by identity, so two objects with the same contents are not equal. Use the deep version for arrays and objects.

Testing async code

A test function can be async; the runner waits for it. An assertion that fails inside it, or a rejection that is not caught, fails the test:

JavaScript
test("loads the user", async () => {
  const user = await loadUser(1, fakeApi);
  assert.equal(user.name, "Ada");
});

test("a missing user rejects", async () => {
  await assert.rejects(loadUser(99, fakeApi), /not found/);
});

Forgetting await before assert.rejects is a classic mistake: the test finishes before the check happens.

Fakes and spies

Code that talks to the network, the clock or the disk is hard to test. The cure is the same as in every language: pass those things in, and give the test a fake.

JavaScript
function makeSpy(result) {
  const spy = (...args) => {
    spy.calls.push(args);
    return typeof result === "function" ? result(...args) : result;
  };
  spy.calls = [];
  return spy;
}

async function notifyOverdue(books, today, send) {
  let sent = 0;
  for (const b of books) {
    if (b.due < today) {
      await send(b.borrower, `"${b.title}" is overdue`);
      sent++;
    }
  }
  return sent;
}

const send = makeSpy(Promise.resolve());
notifyOverdue([{ title: "Dune", borrower: "ada", due: "2026-11-01" }, { title: "Emma", borrower: "bob", due: "2026-12-01" }], "2026-11-20", send)
  .then(n => console.log(n, send.calls));

A spy records how it was called; a stub returns what the test wants. Test frameworks provide them (mock.fn() in node:test, vi.fn() in Vitest, jest.fn()), but they are only functions that remember.

Fake timers

Waiting for real timers makes tests slow. Frameworks can replace setTimeout with a fake clock that you move by hand:

JavaScript
import { test, mock } from "node:test";

test("debounce waits 300 ms", () => {
  mock.timers.enable({ apis: ["setTimeout"] });
  const calls = [];
  const save = debounce(() => calls.push("saved"), 300);
  save(); save();
  mock.timers.tick(299);
  assert.deepEqual(calls, []);
  mock.timers.tick(1);
  assert.deepEqual(calls, ["saved"]);
  mock.timers.reset();
});

Vitest has the same with vi.useFakeTimers() and vi.advanceTimersByTime(ms).

Vitest and Jest

JavaScript
import { describe, it, expect, vi } from "vitest";

describe("cart", () => {
  it("totals the lines", () => {
    expect(total([{ price: 2, qty: 3 }])).toBe(6);
  });
  it("calls the logger once", () => {
    const log = vi.fn();
    checkout([], log);
    expect(log).toHaveBeenCalledTimes(1);
  });
});

describe groups tests, it is one test, and expect(x).toBe(y), .toEqual(y) (deep), .toThrow() and .toHaveBeenCalledWith(...) are the assertions. Jest's API is the same.

What makes a good test

  • It checks one behaviour and its name says which.
  • It sets up everything it needs and does not depend on other tests.
  • It fails for one reason only, and the message shows what was expected and what came instead.
  • It runs fast, without the network or real waiting.
