Immutable Data and Functional Patterns

lesson 8.055 of 5 in milestone 85 min2 practice tasks

Code that does not change data behind your back - why shared mutable objects cause bugs, updating with spread instead of mutating, the non-mutating array methods toSorted, toReversed, toSpliced and with, deep copies with structuredClone, deep freezing, pure functions, composing functions with pipe, and currying.

The bug that shared objects cause

JavaScript
const defaults = { theme: "light", sizes: [12, 14] };
function withLargeText(settings) {
  settings.sizes.push(18);          // changes the caller's array!
  return settings;
}
const mine = withLargeText(defaults);
console.log(defaults.sizes);        // [ 12, 14, 18 ]: the defaults changed too

Objects and arrays are passed by reference, so a function that changes its argument changes it for everyone who holds it. In a small script that is manageable; in an app with state shared by many parts (lesson 6.05), it causes bugs that are hard to trace. The cure is to not change data: make a new version instead.

Updating with spread

JavaScript
const state = { user: { name: "Ada", level: 3 }, items: ["map"] };

const next = {
  ...state,
  user: { ...state.user, level: state.user.level + 1 },
  items: [...state.items, "sword"],
};

console.log(state.user.level, state.items);   // 3 [ 'map' ]  (unchanged)
console.log(next.user.level, next.items);     // 4 [ 'map', 'sword' ]
console.log(next.user === state.user);         // false: changed, so copied

Spread copies one level. Every level on the path to the change is copied; everything else is shared, which is cheap and safe as long as nobody mutates it.

Array methods that do not mutate

sort, reverse and splice change the array in place. Their newer twins return a changed copy:

JavaScript
const scores = [30, 10, 20];
console.log(scores.toSorted((a, b) => a - b));   // [ 10, 20, 30 ]
console.log(scores.toReversed());                // [ 20, 10, 30 ]
console.log(scores.toSpliced(1, 1));             // [ 30, 20 ]
console.log(scores.with(0, 99));                 // [ 99, 10, 20 ]
console.log(scores);                             // [ 30, 10, 20 ]: unchanged

map, filter, slice, concat and reduce never mutated, which is why lesson 2.02's array style already works well with immutable data.

Deep copies

structuredClone copies a value all the way down, including nested objects, arrays, Map, Set and Date:

JavaScript
const original = { when: new Date(0), tags: new Set(["a"]), deep: { list: [1, 2] } };
const copy = structuredClone(original);
copy.deep.list.push(3);
console.log(original.deep.list, copy.deep.list, copy.when instanceof Date, copy.tags.has("a"));

It cannot copy functions or class instances' methods (a class instance comes back as a plain object). JSON.parse(JSON.stringify(x)) also copies, but loses dates, undefined, Map and Set.

Freezing

Object.freeze stops changes to an object, but only one level deep. A small recursive function freezes everything:

JavaScript
function deepFreeze(value) {
  if (value && typeof value === "object" && !Object.isFrozen(value)) {
    Object.freeze(value);
    for (const key of Reflect.ownKeys(value)) deepFreeze(value[key]);
  }
  return value;
}

const config = deepFreeze({ server: { port: 8080 }, flags: ["a"] });
config.server.port = 1;        // ignored here; in strict mode it throws a TypeError
console.log(config.server.port, Object.isFrozen(config.flags));   // 8080 true

In strict mode (every module, lesson 3.05) writing to a frozen object throws; outside it, the write is silently ignored. Freezing in development builds catches accidental mutation early.

Pure functions

A pure function's result depends only on its arguments, and it changes nothing outside itself. Pure functions are easy to test (no set-up), easy to reuse, and safe to call twice.

JavaScript
// impure: reads and changes outside state
let total = 0;
function addToTotal(price) { total += price; return total; }

// pure: everything comes in, the answer goes out
const addPrice = (total, price) => total + price;
console.log([3, 4, 5].reduce(addPrice, 0));

Programs still need side effects (saving, drawing, sending). The pattern is to keep them at the edges and the logic in the middle pure, as the update function in lesson 6.05 did.

Building functions from functions

pipe runs functions one after another, each getting the result of the last:

JavaScript
const pipe = (...fns) => input => fns.reduce((value, fn) => fn(value), input);

const slug = pipe(
  s => s.trim(),
  s => s.toLowerCase(),
  s => s.replace(/[^a-z0-9]+/g, "-"),
  s => s.replace(/^-|-$/g, ""),
);
console.log(slug("  Hello, World! 2026 "));   // hello-world-2026

Currying turns a function of several arguments into functions of one, so you can fix some arguments now and give the rest later:

JavaScript
const multiply = a => b => a * b;
const double = multiply(2);
console.log([1, 2, 3].map(double));            // [ 2, 4, 6 ]
const hasTag = tag => item => item.tags.includes(tag);
console.log([{ tags: ["red"] }, { tags: ["blue"] }].filter(hasTag("red")).length);

When to mutate anyway

Immutability costs copies. Inside one function, building a local array with push is fine: nobody else can see it until you return it. Mutate freely what you just created; do not mutate what you were given.
