The Event Loop and Callbacks

lesson 4.011 of 5 in milestone 45 min1 practice task

Why JavaScript code never blocks - one thread, the call stack, the task queue and the event loop, setTimeout and what a delay of 0 means, microtasks, callback-style APIs with error-first callbacks, and why deeply nested callbacks led to promises.

One thread

JavaScript runs your code on one thread: one thing at a time, from start to finish. Yet a web page can wait for a click, a timer and a download all at once. It does this by never waiting: slow operations are handed to the environment (the browser or Node), and your code is called back when they finish.

JavaScript
console.log("1: start");
setTimeout(() => console.log("3: timer fired"), 0);
console.log("2: end of script");

Even with a delay of 0, the timer's callback runs after the current code has finished.

The event loop

flowchart LR
  A[Your code runs to the end] --> B{Microtasks waiting?}
  B -- yes --> C[Run all microtasks] --> B
  B -- no --> D{Task waiting?}
  D -- yes --> E[Run one task: a timer, an event, I/O done] --> B
  D -- no --> F[Idle: wait for the next event] --> D
  • The call stack holds the functions running now.
  • When a timer fires or a download finishes, its callback is put in the task queue.
  • The event loop takes the next task only when the stack is empty.
  • Microtasks (promise callbacks, queueMicrotask) run as soon as the current code finishes, before the next task.
JavaScript
setTimeout(() => console.log("task"), 0);
Promise.resolve().then(() => console.log("microtask"));
queueMicrotask(() => console.log("microtask 2"));
console.log("sync");

Prints sync, microtask, microtask 2, task.

Do not block the loop

While your code runs, nothing else can: no clicks, no redraws, no timers. A loop that takes 3 seconds freezes a page for 3 seconds:

JavaScript
const end = Date.now() + 3000;
while (Date.now() < end) { }     // the whole page is frozen

Long work belongs in small pieces between which the loop can breathe, or in a Web Worker.

Callbacks

Before promises, asynchronous APIs took a callback. Node's convention is error-first: the callback's first argument is an error or null:

JavaScript
function loadUser(id, callback) {
  setTimeout(() => {
    if (id <= 0) callback(new Error(`no user ${id}`));
    else callback(null, { id, name: `user${id}` });
  }, 10);
}

loadUser(1, (err, user) => {
  if (err) return console.log("failed:", err.message);
  console.log("loaded", user.name);
});
loadUser(0, (err) => console.log("failed:", err.message));

Callback hell

Doing things in sequence means nesting callbacks inside callbacks, and every level repeats the error check:

JavaScript
loadUser(1, (err, user) => {
  if (err) return done(err);
  loadOrders(user, (err, orders) => {
    if (err) return done(err);
    loadInvoice(orders[0], (err, invoice) => {
      if (err) return done(err);
      done(null, invoice);
    });
  });
});

Promises (lesson 4.02) and async/await (lesson 4.03) turn this into straight-line code. You will still meet callbacks in event handlers, setTimeout, array methods and older libraries.
