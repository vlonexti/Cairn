Modules

lesson 3.055 of 5 in milestone 35 min1 practice task

Splitting a program into files with ES modules - named and default exports, import forms, renaming and namespace imports, module scope and strict mode, live bindings, side effects, CommonJS require in older Node code, and how to organise modules.

Why modules

A module is one file with its own scope: nothing inside it is visible to other files unless it is exported, and nothing from other files is visible unless it is imported. That keeps names from clashing and makes the dependencies of each file explicit.

JavaScript
// money.js
export const CURRENCY = "EUR";

export function format(cents) {
  return `${(cents / 100).toFixed(2)} ${CURRENCY}`;
}

function round(x) { return Math.round(x); }   // not exported: private to this file
export { round as roundCents };               // export under another name
JavaScript
// main.js
import { format, CURRENCY } from "./money.js";
import { roundCents as round } from "./money.js";
import * as money from "./money.js";           // namespace: money.format, money.CURRENCY

console.log(format(1250), CURRENCY, money.format(round(99.6)));

Relative imports start with ./ or ../. In browsers and Node, the file extension is required.

Default exports

A module may have one default export, imported without braces under any name:

JavaScript
// cart.js
export default class Cart { /* ... */ }
export const MAX_ITEMS = 50;

// main.js
import Cart, { MAX_ITEMS } from "./cart.js";

Many teams prefer named exports only: names stay the same everywhere, editors can auto-import them, and renaming finds every use.

How modules behave

  • Modules always run in strict mode and top-level this is undefined.
  • Each module runs once, the first time it is imported; later imports share the same instance. A module-level let count is shared by every importer.
  • Imports are live, read-only bindings: if the exporting module changes an exported let, importers see the new value, but they cannot assign to it themselves.
  • import statements are hoisted and resolved before any code runs. To load a module only when needed, use dynamic import: const { chart } = await import("./chart.js");
  • In modules, top-level await is allowed.

Code that runs at the top level of a module (connecting, printing, changing globals) is a side effect of importing it. Keep modules mostly to declarations so that importing them is safe.

CommonJS

Older Node code uses CommonJS, which you will meet in many packages:

JavaScript
// math.cjs
function add(a, b) { return a + b; }
module.exports = { add };

// main.cjs
const { add } = require("./math.cjs");

Node treats .mjs files, and .js files in a package whose package.json says "type": "module", as ES modules; .cjs files and other .js files as CommonJS. New code should use ES modules.

Organising modules

  • One module per idea: money.js, cart.js, storage.js, not utils.js with everything.
  • Keep pure logic in modules without side effects, and wire them together in one entry file (main.js).
  • Avoid circular imports (a imports b, b imports a): move the shared part into a third module.

In this course's practice tasks, files of a project can import each other with ./name.js, just like in Node.
