Serving Many Clients

lesson 2.044 of 5 in milestone 25 min1 practice task

A pipe server that handles several clients at once - one instance per client, the accept loop with a thread per connection, keeping an instance always listening, identifying who connected, limits, and shutting the server down cleanly.

One instance per client

A named pipe instance is one connection. To serve several clients at the same time, the server creates several instances of the same name. The standard shape is an accept loop:

C++
for (;;)
{
    HANDLE instance{ CreateNamedPipeW(name, PIPE_ACCESS_DUPLEX, PIPE_TYPE_BYTE | PIPE_WAIT | PIPE_REJECT_REMOTE_CLIENTS,
                                      PIPE_UNLIMITED_INSTANCES, 65536, 65536, 0, &security) };
    if (instance == INVALID_HANDLE_VALUE) break;

    const BOOL connected{ ConnectNamedPipe(instance, nullptr) || GetLastError() == ERROR_PIPE_CONNECTED };
    if (!connected) { CloseHandle(instance); continue; }

    std::thread{ serveClient, instance }.detach();   // serveClient reads, replies, and closes the handle
}

Each loop iteration creates a fresh instance and waits on it, so as soon as one client is handed to its thread, the next client can connect. Between ConnectNamedPipe returning and the next CreateNamedPipeW, there is a moment with no free instance; a client arriving then gets ERROR_PIPE_BUSY, waits with WaitNamedPipeW (lesson 2.02) and gets in. Some servers keep two or more instances listening to make that window smaller.

Thread per client

A thread per client is the simplest correct design: each thread runs straightforward blocking code (read a request, handle it, write a reply) and closes its instance when the client disconnects (ReadFile fails with ERROR_BROKEN_PIPE). It is the right choice for tens of clients. For hundreds or thousands, the threads' stacks and scheduling cost too much, and overlapped I/O with a completion port (lesson 2.05) serves them all with a few threads.

Shared state that client threads touch (a list of connected clients, a cache) needs a mutex, like any multi-threaded code.

Limits

nMaxInstances (the fourth argument) caps how many instances may exist. With a cap of 4, a fifth client keeps getting ERROR_PIPE_BUSY until one of the four disconnects. Set a cap that matches what your server can handle, and give clients a sensible wait and retry policy.

Who connected?

A server can ask about the process at the other end:

C++
ULONG clientPid{};
GetNamedPipeClientProcessId(instance, &clientPid);       // the client's PID

and, with care, run code in the client's security context with ImpersonateNamedPipeClient (lesson 5.05). The PID is useful for logging and for watching the client process; it is not proof of who the client is, since PIDs can be reused and any program may connect. Access control on the pipe itself is the real gate.

Shutting down

The accept loop above blocks in ConnectNamedPipe, so how does it ever stop? Common answers:

  • Set a "stopping" flag, then connect to your own pipe as a client: the blocked ConnectNamedPipe returns, the loop sees the flag and exits.
  • Use overlapped ConnectNamedPipe (lesson 2.05) and wait on both the connection event and a "stop" event.
  • CancelIoEx(instance, nullptr) from another thread cancels the pending connect.

Then tell each client thread to finish: close their handles (their reads fail) or set a flag they check between messages, and wait for them to end before the program exits.
