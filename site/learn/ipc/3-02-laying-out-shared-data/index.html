Laying Out Shared Data

lesson 3.022 of 5 in milestone 35 min1 practice task

What may live in shared memory and what may not - offsets instead of pointers, fixed-size types instead of std::string and std::vector, a header with a magic number, version and size, safe initialisation when either side may start first, and lock-free atomics.

The rules

A block of shared memory is seen by several processes, at different addresses, possibly built by different versions of your program, possibly by different compilers. So everything in it must mean the same thing to all of them:

  1. No pointers. Store offsets from the start of the block instead, and turn them into pointers locally: base + offset.
  2. No types that own heap memory. A std::string or std::vector placed in shared memory holds a pointer to its own process's heap. Use fixed-size arrays (char name[64]) or offsets to data inside the block.
  3. Fixed-size types. std::uint32_t, std::int64_t, float: never long (4 bytes on Windows, 8 on Linux) or size_t (different in 32- and 64-bit processes).
  4. Explicit layout. Put members in a stable order, use static_assert on sizes and offsets, and remember padding (Pointers and Memory course, lesson 3.01).
  5. No virtual functions, which would put a vtable pointer in the block.
C++
struct TelemetryHeader
{
    std::uint32_t magic;          // 'XTEL': this really is our block
    std::uint32_t version;        // the layout version
    std::uint32_t size;           // total bytes the creator made
    std::uint32_t ready;          // 0 until the creator has finished initialising
    std::uint64_t firstSample;    // offset of the sample table
    std::uint32_t sampleCount;
    std::uint32_t reserved;
};
static_assert(sizeof(TelemetryHeader) == 32);

A header first

Begin every shared block with a header like that:

  • A magic number confirms the block is what you think: a stale mapping from an old version, or an unrelated program using the same name, is caught at once.
  • A version lets a newer reader refuse, or adapt to, an older layout.
  • A size stops a reader from trusting offsets that point past the end. Check every offset against it before use: the other process may be buggy, or hostile.

Offsets instead of pointers

A linked structure in shared memory stores offsets. A node at offset 0 is impossible (the header is there), so 0 can mean "none":

C++
struct Node { std::uint64_t next; std::int32_t value; std::uint32_t pad; };

template <typename T>
T* at(std::byte* base, std::uint64_t offset) { return offset ? reinterpret_cast<T*>(base + offset) : nullptr; }

for (Node* n{ at<Node>(base, header->first) }; n; n = at<Node>(base, n->next)) { /* ... */ }

Because offsets are relative to the block, the structure is correct in every process however its view is placed. (The same idea is how memory-mapped file formats and pointer-free serialisation libraries such as FlatBuffers work.)

Initialising safely

Both processes may start at nearly the same moment. The creator (the one that did not get ERROR_ALREADY_EXISTS) fills in the header and the data, and sets ready last. Every other process waits until ready is set before trusting anything. Because a page-file mapping starts zeroed, ready == 0 reliably means "not yet". For this to be safe, ready must be written and read as an atomic with release and acquire ordering, so the data written before it is visible once it is seen:

C++
auto* ready{ reinterpret_cast<std::atomic<std::uint32_t>*>(&header->ready) };
ready->store(1, std::memory_order_release);                 // creator, after filling everything in
while (ready->load(std::memory_order_acquire) == 0) Sleep(1); // others (with a timeout in real code)

Atomics in shared memory

std::atomic<T> works across processes only if it is lock-free: a lock-based fallback uses a lock inside each process's own runtime, which the other process cannot see. For 32- and 64-bit integers on x64 they always are; check with static_assert(std::atomic<std::uint64_t>::is_always_lock_free). Construct them in place in the block (with placement new, or by relying on the zeroed memory for types whose zero state is valid), and never put std::mutex in shared memory; use the named kernel objects of milestone 4 instead.
