A Single-Instance Application

lesson 6.011 of 5 in milestone 65 min1 practice task

Making a second launch hand its work to the copy already running - a named mutex to detect the first instance, forwarding the command line through a pipe or WM_COPYDATA, resolving relative paths with the sender's folder, bringing the window to the front, and the races when two copies start at once.

One copy, many launches

Double-click a document while your editor is open, and the user expects the document to open in the running editor, not in a second copy. The pattern is common enough to have a name: a single-instance application. It combines three pieces from this course: a named kernel object to detect the first instance, an IPC channel to hand over the command line, and window activation.

Detecting the first instance

C++
const std::wstring name{ LR"(Local\Xenon.Editor.)" + currentUserSid() };   // per user
HANDLE instance{ CreateMutexW(nullptr, FALSE, name.c_str()) };
const bool primary{ GetLastError() != ERROR_ALREADY_EXISTS };
// keep `instance` open for the whole life of the primary: its existence is the signal

The first process creates the mutex and becomes the primary; every later one sees ERROR_ALREADY_EXISTS and becomes a secondary. The mutex is never locked; only its existence matters, and because Windows closes it when the primary exits (even by crashing), a stale "running" signal cannot survive.

Choose the scope with the name: Local\ plus the user's identity gives one instance per user per session, which is usually right. A global name would make two users on one machine fight over one instance.

Forwarding the command line

The secondary must hand its arguments to the primary and exit. Either channel works:

  • WM_COPYDATA to the primary's window (lesson 4.04): simple, if the primary has a window and runs at the same integrity level.
  • A named pipe the primary listens on (milestone 2): works for background processes too, and lets the primary reply ("opened", or an error).

What to send is not just the arguments. Relative paths (notes.md, ..\docs\a.md) mean something only relative to the secondary's current folder, which the primary does not share. Send the secondary's current directory along with the arguments, and let the primary resolve paths against it (or resolve them before sending).

Bringing the window forward

Windows restricts which process may steal the foreground, so that background programs cannot pop up over what the user is doing. The secondary was just launched by the user, so it may set the foreground, and it can pass that right on:

C++
AllowSetForegroundWindow(primaryPid);    // in the secondary, before forwarding
// the primary, on receiving the request:
if (IsIconic(window)) ShowWindow(window, SW_RESTORE);
SetForegroundWindow(window);

Without that, the primary's window just flashes in the taskbar.

The races

  • Two launches at once. Both call CreateMutexW at nearly the same moment; the kernel guarantees exactly one creates it. But the secondary may try to forward before the primary has created its pipe or window. The secondary must retry for a short while (a second or two) before giving up.
  • The primary is shutting down. The secondary forwards to a primary that is about to exit, and the request is lost. Have the primary close the mutex first when shutting down, so new launches become primaries themselves, and accept that a request arriving during shutdown may need a retry.
  • The primary is hung. Forwarding with a timeout (SendMessageTimeoutW, or a pipe with a timeout) lets the secondary tell the user, or start anyway as a second instance, rather than hanging too.
