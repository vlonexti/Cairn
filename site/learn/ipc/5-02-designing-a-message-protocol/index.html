Designing a Message Protocol

lesson 5.022 of 5 in milestone 55 min1 practice task

The decisions behind a protocol two programs will speak for years - a handshake with a magic number and version, an envelope with type, id, flags and length, kinds of messages, version negotiation, error replies, and writing it all down.

A protocol is a contract

Two programs talking over a pipe or a socket depend on a set of agreements: what bytes come first, what each message means, what happens when one side is newer than the other. That contract is the protocol, and it outlives the code: once two released versions of your programs speak it, changing it means staying compatible. A little design up front saves years of trouble.

The handshake

The first exchange on a new connection should establish that both sides speak the same protocol:

Text
client -> server   HELLO   magic "XIPC", version 2.3, client name "xenon-editor"
server -> client   WELCOME version 2.1, server name "xenon-agent", capabilities
  • A magic number catches connections from something that is not your client at all (a port scanner, an old program on a reused port, a browser) before you try to parse its bytes as messages.
  • A version lets both sides agree on the dialect. A common scheme: the major version changes when old and new cannot talk at all; the minor version changes when features are added compatibly. Both sides use the same major and the lower of the two minors, and simply avoid features newer than that.
  • Capabilities (a list of feature names or flag bits) are an alternative or complement to minor versions: "I support compression and batch requests".

If the handshake fails, say why (a message with an error code, if possible) and close the connection.

The envelope

Every message after the handshake shares one outer structure, the envelope, so that any message can be framed, routed and logged without understanding its payload:

Field Size Purpose
length 4 frame length (lesson 2.03)
type 1 or 2 what kind of message
flags 1 bits such as "this is a reply", "this is an error"
id 4 matches replies to requests (lesson 5.04)
payload rest type-specific content (lesson 5.03)

Kinds of messages

Almost every protocol needs the same three kinds:

  • Requests: "do this and tell me the result". Carry an id.
  • Responses: the result of one request, carrying its id; either a success with data or an error with a code and a message.
  • Events (notifications): sent without being asked, such as "file changed" or "build finished". No reply expected.

Keep error replies structured: a numeric code that programs can act on ("not found", "bad argument", "busy", "not supported in this version") plus a human-readable message for logs.

Rules that keep a protocol healthy

  • Unknown message types: reply "not supported" (for requests) or ignore (for events). Never crash, never close the connection.
  • Unknown fields: skip them, if the encoding allows (lesson 5.03). This is what lets a newer sender add fields that an older receiver ignores.
  • Limits: maximum message size, maximum outstanding requests, maximum string lengths. Write them in the specification and enforce them.
  • Text or binary? Text (JSON) is easy to debug and to speak from any language; binary is compact and fast. JSON lines or JSON with a length header (like the Language Server Protocol) are fine for most tools; reach for binary when messages are frequent or large.
  • Write it down. A short specification (one page with the envelope, the message types and their payloads, versions and limits) is worth more than any amount of "the code is the documentation", especially when the other side is written by someone else or in another language.
