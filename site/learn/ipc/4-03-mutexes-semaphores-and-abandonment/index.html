Mutexes, Semaphores and Abandonment

lesson 4.033 of 5 in milestone 45 min1 practice task

Exclusive access across processes with a named mutex - ownership, recursion, releasing, and WAIT_ABANDONED when the owner died holding it - and semaphores for limiting how many can do something at once.

A mutex across processes

A named mutex gives exclusive access to something several processes share: a block of shared memory with a structure too large for atomics, a log file, a device.

C++
HANDLE lock{ CreateMutexW(&security, FALSE, LR"(Local\xenon-settings-lock)") };

switch (WaitForSingleObject(lock, 2000))
{
case WAIT_OBJECT_0:
    editSharedSettings();
    ReleaseMutex(lock);
    break;
case WAIT_ABANDONED:
    // We own it now, but the previous owner died while holding it: the data may be half-written.
    repairOrResetSharedSettings();
    ReleaseMutex(lock);
    break;
case WAIT_TIMEOUT:
    /* someone has held it for 2 s: report, retry later */ break;
}

A successful wait makes the calling thread the owner; only that thread may ReleaseMutex. A Win32 mutex is recursive: the owner can wait on it again without blocking, and must release it once per successful wait. Releasing a mutex you do not own fails with ERROR_NOT_OWNER.

A kernel mutex costs a system call per wait and release, far more than a std::mutex within a process. Use it for coarse operations (edit the settings block, append a record), not in a tight loop.

Abandonment

What if a process crashes while holding the mutex? A std::mutex in shared memory would stay locked for ever. A kernel mutex is better: when its owning thread ends, Windows releases it and marks it abandoned, and the next successful wait returns WAIT_ABANDONED instead of WAIT_OBJECT_0.

That return means: you now own the mutex, but whatever it protected may be inconsistent, because the dead owner may have stopped halfway through an update. Do not treat it as plain success. Validate the shared data (checksums and version numbers in the shared header pay for themselves here), repair or reinitialise it, and carry on. The abandoned state is cleared once reported, so only the first waiter gets the warning.

Semaphores

A semaphore holds a count between 0 and a maximum. A successful wait takes one from the count (blocking while it is 0); ReleaseSemaphore(handle, n, &previous) adds n.

C++
// At most 4 builds may run at once, across every process that opens this name
HANDLE slots{ CreateSemaphoreW(nullptr, 4, 4, LR"(Local\xenon-build-slots)") };

if (WaitForSingleObject(slots, INFINITE) == WAIT_OBJECT_0)
{
    runBuild();
    ReleaseSemaphore(slots, 1, nullptr);
}

Unlike a mutex, a semaphore has no owner: any thread or process may release it. That makes it suitable for producer and consumer counting (the producer releases one per item, the consumer waits once per item), and means there is no abandonment: if a process dies holding a "slot", the count is lost for good. A watchdog that tracks which processes took slots, or a design where slots are tied to process handles, guards against that.

Choosing

Need Use
exclusive access, must survive a crashed owner mutex (and handle WAIT_ABANDONED)
at most N at once semaphore
count items between a producer and a consumer semaphore
"something happened" or "a state is now true" event
fast exclusive access inside one process std::mutex
