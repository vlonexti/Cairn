Choosing an IPC Method

lesson 1.055 of 5 in milestone 15 min

A map of the ways processes communicate on Windows - pipes, shared memory, sockets, kernel objects, window messages, files, COM and RPC - compared on speed, simplicity, who can connect and what happens when one side dies, with a guide to choosing.

Many tools, different jobs

Every IPC method moves data or signals between address spaces through the kernel, but they differ a great deal in what they are good at. The rest of the course covers each in depth; this lesson is the map.

Method Moves Strengths Weaknesses
Anonymous pipe a byte stream, one way trivial for parent and child; stdio only between related processes
Named pipe a byte or message stream, two way any two processes on the machine (or network); per-client connections; access control Windows-specific API
Shared memory (file mapping) nothing: both see the same bytes fastest by far, no copying you build every structure and all synchronisation yourself
Socket (loopback TCP, AF_UNIX) a byte stream same code works across a network; every language has it some overhead; open ports need care
Events, mutexes, semaphores signals, not data waiting without spinning; combine with shared memory carry no data
Window messages (WM_COPYDATA) small messages easy between GUI programs needs windows and a message loop; blocked between privilege levels
Files anything simple, survives restarts slow; coordinating readers and writers is hard
COM, RPC method calls rich, typed interfaces heavy machinery to learn and debug

Questions that decide

Are the processes related? A parent and the child it starts can share anonymous pipes or inherited handles. Unrelated programs need a name both know: a named pipe, a named mapping, a port number.

How much data, how often? A few messages a second: any method. Megabytes per frame (a video stream, a game's state for an external tool): shared memory, with a small signal to say "new data". Copying through a pipe costs time per byte; shared memory costs nothing per byte once mapped.

Request and response, or a stream? Pipes and sockets fit conversations naturally. Shared memory suits "latest state" and ring buffers of records.

What if one side dies? Pipes and sockets tell you: the other end is closed and reads fail. Shared memory does not: a dead writer leaves the last data in place and a mutex abandoned (lesson 4.03). Anything built on shared memory needs its own liveness checks, such as watching the other process's handle.

Across machines later? If there is any chance, use sockets from the start; the protocol is then the same locally and remotely.

Who may connect? Named pipes and kernel objects carry Windows security descriptors (lesson 5.05); TCP ports on localhost are open to every local process, so the protocol must check who is talking.

Common combinations

  • Editor and language server: stdio pipes with length-framed JSON messages.
  • Game and external debug tool: shared memory holding the game's state, plus an event or a seqlock so the tool reads consistent snapshots; a named pipe for commands back to the game.
  • Single-instance app: a named mutex to detect the running copy, a named pipe or WM_COPYDATA to hand it the new command line.
  • Browser: one process per site, communicating with the main process over named pipes with a custom message system, shared memory for rendered frames.
  • Background service and its settings app: a named pipe with an access control list allowing only the user's session.

The shape of every IPC design

Whatever the method, a robust design has the same parts, which the following milestones build one by one:

  1. Discovery: how the two sides find each other (a name, an inherited handle, a port).
  2. Framing: where each message begins and ends.
  3. Format: how values are encoded so both sides agree.
  4. Flow: who speaks when; requests, responses, events.
  5. Failure: timeouts, the other side vanishing, bad input.
  6. Security: who is allowed to connect, and never trusting what arrives.
