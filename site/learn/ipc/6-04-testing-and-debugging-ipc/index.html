Testing and Debugging IPC

lesson 6.044 of 5 in milestone 65 min1 practice task

Making communicating programs testable - keeping the protocol logic separate from the transport, in-memory transports and fault injection, golden transcripts, logging both sides with ids and times, and the tools for seeing handles, pipes and traffic, including debugging two processes at once.

Separate logic from transport

IPC code is hard to test when the protocol logic is tangled with ReadFile, WriteFile and real processes. Structure it in layers, as every practice in this course has:

  • a transport that moves bytes (a pipe, a socket, shared memory);
  • framing that turns bytes into messages;
  • protocol logic that turns messages into actions and replies.

Then the framing and the logic can be unit-tested with byte vectors and no processes at all, running in milliseconds. A thin integration test checks that the real transport is wired up correctly.

Fault injection

The bugs that matter in IPC appear only under conditions that rarely happen on a developer's machine. Make them happen on purpose with a fault-injecting transport used in tests:

  • deliver messages split into small chunks, and several joined into one read (the deframer must not care);
  • delay messages, and deliver responses out of order;
  • drop the connection halfway through a message;
  • kill the peer process in the middle of an exchange;
  • send garbage: random bytes, absurd lengths, unknown types.

Deterministic patterns (split every frame into 3-byte pieces) are easier to debug than random ones; a seeded random generator gives variety while keeping failures reproducible.

Golden transcripts

Record the messages of a known-good session as text, one per line ("client to server: REQUEST id=1 method=open path=a.md"), and keep it as a golden transcript. A test replays the client side and compares the server's replies with the transcript. To keep it stable, normalise fields that legitimately change (timestamps, generated ids) before comparing. When a change alters the protocol on purpose, regenerate the golden file and review the diff; when it does so by accident, the test catches it.

Logging both sides

When something goes wrong between two processes, you need both sides' view. Log every message sent and received with:

  • a timestamp (milliseconds, from a monotonic clock),
  • the direction and the peer (client id, PID),
  • the message id and type.

With ids in both logs, lining up the two sides is mechanical: find request 41 in the client log and in the server log, and the gap between them is the time it spent in the pipe and the queue.

Tools

  • Process Explorer: the lower pane's handle view shows every pipe, event, mutex and mapping a process has open, by name. "Find Handle or DLL" finds which process holds an object.
  • Sysinternals PipeList (pipelist.exe): every named pipe on the machine with instance counts. (In PowerShell: Get-ChildItem \\.\pipe\.)
  • Process Monitor: pipe operations appear as file operations on \Device\NamedPipe\....
  • Wireshark with the Npcap loopback adapter captures localhost TCP traffic.
  • Resource Monitor, CPU tab, "Analyze Wait Chain": shows what a hung process is waiting for, including another process.

Debugging two processes

Visual Studio can debug several processes in one session: start the server under the debugger, then Debug > Attach to Process for the client (or set both as startup projects in the solution's properties). Breakpoints in both work, and the Processes window switches between them. For child processes started by your program, Microsoft's Child Process Debugging Power Tool extension attaches automatically. Remember that stopping one side at a breakpoint makes the other side's timeouts fire; raise timeouts in debug builds, or expect them.
