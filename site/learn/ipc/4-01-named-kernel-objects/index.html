Named Kernel Objects

lesson 4.011 of 5 in milestone 45 min1 practice task

Events, mutexes and semaphores that several processes can open by name - creating versus opening, ERROR_ALREADY_EXISTS, the session namespaces, signalled and non-signalled states, and why a kernel object outlives the handle that made it until the last handle closes.

Synchronisation that crosses processes

std::mutex and std::condition_variable work between threads of one process. Between processes you use kernel objects: objects that live in the Windows kernel, reached through handles, and that can be given a name so another process can open the same one.

Object Create Open Used for
event CreateEventW OpenEventW "something happened": new data, stop now
mutex CreateMutexW OpenMutexW exclusive access to a shared resource
semaphore CreateSemaphoreW OpenSemaphoreW allow up to N at once
waitable timer CreateWaitableTimerW OpenWaitableTimerW signal at a time or interval

Processes, threads, file mappings and pipes are kernel objects too, which is why the same wait functions work on all of them.

Create or open

The usual pattern is for both sides to call Create... with the same name:

C++
HANDLE ready{ CreateEventW(&security, FALSE, FALSE, LR"(Local\xenon-telemetry-ready)") };
if (!ready) /* failed: GetLastError() */;
const bool someoneElseCreatedIt{ GetLastError() == ERROR_ALREADY_EXISTS };

If the object exists, Create... opens it instead (and the creation parameters, such as the initial state, are ignored), so it does not matter which process starts first. Open... fails with ERROR_FILE_NOT_FOUND if the object does not exist, which is what you want when only one side should create it (a client must not create the server's objects).

ERROR_ALREADY_EXISTS is how a single-instance application detects a copy already running (lesson 6.01). Note that GetLastError() must be read immediately after the call, and that the call succeeds in that case.

Names and namespaces

Kernel object names follow the rules from lesson 3.01: Local\ (the default) within the session, Global\ across sessions. Names share one namespace across object types: an event and a mutex cannot both be called xenon-lock (the second create fails with ERROR_INVALID_HANDLE). Choose specific names, and prefix them with your product and purpose.

Signalled or not

Every waitable kernel object is either signalled or non-signalled, and the wait functions block until an object is signalled:

Object Signalled when
event it has been set (lesson 4.02)
mutex nobody owns it
semaphore its count is above zero
process, thread it has ended
waitable timer its time has come

Some objects change state when a wait succeeds on them (a mutex becomes owned, a semaphore's count drops, an auto-reset event resets); others stay signalled (a process stays ended).

Lifetime

A kernel object exists as long as any process holds a handle to it. When the last handle closes, the object, and its name, are gone. Practical consequences:

  • If the creator exits but another process still has the object open, the object stays and keeps its state.
  • A process that crashes has all its handles closed by Windows, so it cannot leave objects behind for ever.
  • To keep an object available between runs you need some process to hold it open, typically a long-running service.

Security

Every named object can carry a security descriptor saying who may open it and with which rights. The default allows the creating user and administrators, which is usually right for Local\ objects. Objects shared with a service or another user need an explicit descriptor (lesson 5.05). And because anyone allowed can create an object with your name first, a client should check it really talks to your server, not an impostor.
