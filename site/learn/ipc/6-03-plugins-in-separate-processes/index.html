Plugins in Separate Processes

lesson 6.033 of 5 in milestone 65 min1 practice task

Running extensions out of process, as editors and browsers do - the host and plugin protocol, manifests and API version compatibility, subscribing plugins to events, timeouts for slow plugins, disabling misbehaving ones, and what isolation does and does not protect.

In-process and out-of-process plugins

The DLLs course built plugins as DLLs loaded into the host: fast, direct function calls, but a plugin that crashes or corrupts memory takes the host down with it, and a plugin cannot be stopped without stopping the host.

Out-of-process plugins run in their own processes and talk to the host through IPC. VS Code runs every extension in a separate extension host process; browsers run extensions and every site in separate processes; audio workstations can run plugins "sandboxed". The host survives any plugin failure, can stop a plugin at any moment, and can give plugins fewer rights than itself.

The price is that every interaction is a message: calls are slower, data must be serialised, and the plugin API must be designed as a protocol (milestone 5) rather than as C++ interfaces.

The manifest

Each plugin ships a manifest the host reads before starting anything:

JSON
{
  "name": "word-count",
  "version": "1.4.0",
  "api": "2.3",
  "entry": "word-count.exe",
  "events": ["documentSaved", "selectionChanged"],
  "commands": ["wordCount.show"]
}

From it the host decides whether the plugin is compatible (API major version equal, minor version not newer than the host's: the rules of lesson 5.02), which events to send it, and which commands it provides, all without running its code. A host that starts plugins only when one of their events or commands is first needed (lazy activation) starts fast even with many plugins installed.

The conversation

A typical host and plugin protocol:

  1. The host starts the plugin process (with a pipe on its stdio, or a named pipe whose name it passes as an argument) in a job object.
  2. Handshake: versions and capabilities.
  3. The host sends events the plugin subscribed to; the plugin sends requests to the host API (read the document, show a message) and gets responses.
  4. The host sends commands the user invoked; the plugin replies.
  5. On shutdown, a "deactivate" message, a short wait, then termination.

Slow and broken plugins

Plugins will misbehave, and the host must stay responsive whatever they do:

  • Every request to a plugin has a timeout. A command that takes too long is reported to the user as failed; the host does not wait for ever.
  • Count failures per plugin. After several timeouts or crashes in a short period, disable the plugin and tell the user which one it was, so they know what to update or remove.
  • Do not let one plugin block another. Each plugin has its own connection and queue; a busy plugin delays only its own messages. (VS Code puts all extensions in one host process, which is a compromise: one heavy extension slows the others, but the editor itself stays responsive.)

What isolation protects, and what it does not

A separate process protects the host from a plugin's crashes, hangs and memory corruption. It does not stop a plugin from doing harm with the rights it has: a plugin process running as the user can read the user's files, whatever API the host offers it. Real protection from untrusted plugins needs a restricted process (a low-integrity token, an AppContainer, a job object with UI restrictions) that cannot reach files or the network directly, so everything must go through the host's API, which can check each request. Browsers do exactly that for web content.
