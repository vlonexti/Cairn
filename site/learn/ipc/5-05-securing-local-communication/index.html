Securing Local Communication

lesson 5.055 of 5 in milestone 55 min1 practice task

Local IPC is an attack surface - other users, other programs and even web pages can reach it. Access control on pipes and objects, preventing pipe squatting, checking which program you are talking to, tokens for localhost sockets, the Host header against DNS rebinding, validating every message, and the dangers of impersonation.

"Local" is not "safe"

It is tempting to assume that anything talking to your local pipe or port is your own program. It is not:

  • Other users on the same machine (a shared PC, a terminal server) can reach Global\ objects, pipes with default permissions, and every localhost port.
  • Any program the user runs, including malware with no special rights, can connect to the user's own pipes and ports.
  • Web pages in a browser can make requests to http://127.0.0.1:port and, with tricks such as DNS rebinding, read the answers.

A local IPC endpoint that performs actions (run a build, write a file, read settings) is a privilege boundary. Design it like one.

Access control on pipes and objects

Named pipes, mappings, events and mutexes accept a security descriptor that lists who may open them. Written in SDDL (Security Descriptor Definition Language):

C++
// Only the current user (the owner) and SYSTEM may connect; nothing inherited from defaults.
PSECURITY_DESCRIPTOR sd{};
ConvertStringSecurityDescriptorToSecurityDescriptorW(L"D:P(A;;GA;;;OW)(A;;GA;;;SY)", SDDL_REVISION_1, &sd, nullptr);
SECURITY_ATTRIBUTES sa{ sizeof(sa), sd, FALSE };
HANDLE pipe{ CreateNamedPipeW(name, PIPE_ACCESS_DUPLEX | FILE_FLAG_FIRST_PIPE_INSTANCE, /* ... */, &sa) };
LocalFree(sd);

D:P is a protected list of permissions; (A;;GA;;;OW) allows (A) all access (GA) to the object's owner (OW); SY is the system account. For a service that desktop programs must reach, allow the specific group or user that should connect, not "Everyone".

Pipe squatting

A malicious program can create your pipe name before your server starts, and your client then connects to the impostor and sends it whatever it sends the real server. Defences:

  • The server creates its first instance with FILE_FLAG_FIRST_PIPE_INSTANCE: if the name already exists, creation fails and the server knows something is wrong instead of silently sharing the name.
  • The client verifies the server: GetNamedPipeServerProcessId gives the server's PID; check that process's image path (and, for high-value cases, its code signature) is your server's.
  • Use names that include something an attacker cannot predict, such as a random value from a file only the user can read.

Tokens for sockets

Localhost TCP ports have no access control at all. The usual defence is a secret token: the server generates a random token at start-up (BCryptGenRandom, at least 128 bits), writes it with the port into a file in the user's profile (readable only by that user), and requires every client to send it first. Compare tokens in constant time (examine every byte, whatever the first mismatch), so the comparison's timing cannot leak how many leading bytes were right.

Browsers and DNS rebinding

If your local server speaks HTTP, any web page can try to talk to it. Browsers' same-origin rules stop a page reading responses from 127.0.0.1 directly, but DNS rebinding gets around that: an attacker's domain first resolves to their server and then to 127.0.0.1, so the browser thinks the page and your local server share an origin. Defences:

  • Check the Host header: accept only localhost:PORT or 127.0.0.1:PORT. A rebinding attack arrives with the attacker's domain in Host.
  • Check the Origin header on requests that change anything, and refuse unknown origins.
  • Require the token as well; a web page cannot read the user's token file.

Validate everything, assume nothing

Every byte from the other side is untrusted input: lengths (lesson 2.03), message types, string contents, paths. A path from a client must be checked before use (no .. escaping an allowed folder, no device names); a request to run something must never become a command line built from client text. Treat a local client with the same suspicion as a network client.

Impersonation, carefully

A pipe server can call ImpersonateNamedPipeClient to act with the client's rights, which is how a service safely opens a file on behalf of a user: Windows checks the user's permissions, not the service's. The danger runs the other way: a client that connects to a malicious server lets that server impersonate the client. Clients of pipes they do not fully trust should open them with SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION in CreateFileW's flags, which lets the server identify the client but not act as it.
