Deadlocks and Timeouts

lesson 4.055 of 5 in milestone 45 min1 practice task

How cooperating processes get stuck waiting for each other - lock-order deadlocks, request-reply deadlocks over pipes, waiting for a peer that died - and the disciplines that prevent them - a global lock order, timeouts on every wait, never holding a lock across IPC, and watchdogs.

Stuck for ever

A deadlock is a set of threads or processes each waiting for something only another of them can provide. Nothing crashes, nothing logs an error; the programs simply stop responding. Across processes they are harder to find than within one, because no single debugger sees both sides.

Lock-order deadlocks

Two processes and two named mutexes:

Text
Process A: lock "settings", then lock "cache"
Process B: lock "cache",    then lock "settings"

If A takes "settings" and B takes "cache" at the same moment, each then waits for the other's mutex, for ever. Drawn as a wait-for graph (an arrow from each waiter to the holder of what it wants), a deadlock is a cycle: A waits for B, B waits for A.

The fix is a global lock order: give every lock a rank and always take them in increasing order, in every process. Then a cycle cannot form, because every arrow points "up" the ranking. Writing the order down (in the code next to the names) is the cheapest deadlock prevention there is.

Request-reply deadlocks

Locks are not the only thing you wait for. Over pipes:

  • Both sides send a large message at the same time, before reading. Both pipes fill, both writes block, neither side ever reads (the stdio version was in lesson 1.04).
  • A server, while handling client A's request, calls into client A (a callback), while client A is blocked waiting for the reply to its request.
  • Process A sends a WM_COPYDATA to B while B is blocked in SendMessageW to A.

The disciplines that prevent these:

  • Never hold a lock while doing IPC. Copy what you need, release, then send or wait. A lock held across a pipe write turns a slow peer into a frozen one.
  • Read continuously. A side that may need to receive while it is sending must read on another thread or with overlapped I/O.
  • Avoid synchronous calls back into the caller. Make callbacks asynchronous (post a message, queue an event) or design the protocol so only one side initiates requests.

Waiting for the dead

A process that died while you wait for its reply, its event or its mutex is the most common "deadlock" of all. Kernel objects help (pipes break, mutexes are abandoned), but an event that a dead process will never set just stays unset.

  • Time out every wait. INFINITE belongs only where something else (a stop event, a process handle in the same WaitForMultipleObjects) guarantees an end. After a timeout, check whether the peer is alive (wait on its process handle with 0 timeout) before deciding to wait again or give up.
  • Include the peer's process handle in multi-object waits (lesson 4.02).
  • Use a watchdog for long-running systems: each worker updates a heartbeat (a counter in shared memory, or a periodic message); a supervisor that sees no heartbeat for a few seconds treats the worker as hung, ends it and starts another (lesson 6.02).

Finding a deadlock

When it happens anyway:

  1. Attach a debugger to each stuck process and look at every thread's call stack: you will see each waiting in WaitForSingleObject, ReadFile or SendMessage.
  2. Find out what each is waiting for: which handle, which object name. Process Explorer's handle view (and the "wait chain" view in Resource Monitor's Analyze Wait Chain) shows which objects each process has and who holds what.
  3. Draw the wait-for graph. The cycle is the bug; the fix is usually an ordering rule or a lock released before an IPC call.
