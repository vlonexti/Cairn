Events and Waiting

lesson 4.022 of 5 in milestone 45 min1 practice task

Signalling between processes with events - auto-reset versus manual-reset, SetEvent and ResetEvent, the lost-wakeup trap and how to avoid it, WaitForMultipleObjects for waiting on several things at once, and the return values every wait must check.

An event is a flag the kernel can wait on

An event is a kernel object with two states, set (signalled) and reset (non-signalled). A process waits on it with WaitForSingleObject; another process sets it with SetEvent. The waiting thread uses no CPU while it waits.

C++
// producer, after putting a message in the shared ring buffer
ring.send(message);
SetEvent(dataReady);

// consumer
for (;;)
{
    if (WaitForSingleObject(dataReady, 1000) == WAIT_TIMEOUT) { /* check the producer is alive */ continue; }
    while (auto m{ ring.receive() }) handle(*m);
}

Shared memory carries the data; the event carries the "look now". Together they give a fast channel that neither spins nor polls.

Auto-reset and manual-reset

The second argument of CreateEventW chooses the kind:

Kind When set When a wait succeeds
auto-reset (FALSE) wakes one waiting thread the event resets itself
manual-reset (TRUE) wakes all waiting threads stays set until someone calls ResetEvent
  • Use auto-reset for "there is work": each set lets one waiter through.
  • Use manual-reset for a state that everyone should see: "shutting down", "initialisation complete". Once set, every current and future wait returns at once.

Events do not count

Setting an auto-reset event that is already set does nothing: two SetEvent calls before the consumer wakes up still wake it only once. An event is a flag, not a counter. That is fine as long as the consumer, once woken, processes everything that is waiting (the while loop above), not just one item. If you need to count, use a semaphore (lesson 4.03).

The lost wakeup

The classic bug is checking for work and then waiting, with a gap between:

C++
if (ring.empty())                               // 1. consumer sees nothing
{                                               // 2. producer sends and calls SetEvent
    ResetEvent(dataReady);                      // 3. consumer clears the signal it never saw
    WaitForSingleObject(dataReady, INFINITE);   // 4. waits for ever, with a message waiting
}

The safe pattern never resets a manual event while data may be waiting, and always re-checks the data after waking: with an auto-reset event, wait first, then drain everything; with timeouts on every wait, a missed signal costs at most one timeout instead of a hang.

Waiting for several things

A consumer usually needs to wake for more than one reason: new data, or "stop", or "the producer process died". WaitForMultipleObjects waits on up to 64 handles at once:

C++
HANDLE handles[]{ stopEvent, producerProcess, dataReady };
switch (const DWORD r{ WaitForMultipleObjects(3, handles, FALSE, 5000) })
{
case WAIT_OBJECT_0 + 0: return;                         // stop requested
case WAIT_OBJECT_0 + 1: reportProducerDied(); return;   // its process handle became signalled
case WAIT_OBJECT_0 + 2: drain(); break;                 // data ready
case WAIT_TIMEOUT:      break;                          // nothing in 5 s
default:                /* WAIT_FAILED or WAIT_ABANDONED_0 + i (lesson 4.03) */ break;
}

With bWaitAll FALSE, it returns when any is signalled and tells you which (the lowest index if several are). Put the most important handle first: if stop and data arrive together, stop wins. Waiting on the other process's handle alongside your event is how a shared-memory channel learns that its peer has gone, which shared memory alone never tells you.

Check every wait

Return Meaning
WAIT_OBJECT_0 + i object i is signalled
WAIT_TIMEOUT the time ran out
WAIT_ABANDONED_0 + i object i is a mutex whose owner died (lesson 4.03)
WAIT_FAILED an error, such as an invalid handle: GetLastError()

Code that treats every non-timeout return as success sooner or later acts on an abandoned mutex or a closed handle as if all were well.
