Ring Buffers

lesson 3.033 of 5 in milestone 35 min1 practice task

A queue in shared memory without locks - a single-producer single-consumer ring buffer with a write counter and a read counter, power-of-two capacities, detecting full and empty, acquire and release ordering, and what to do when the buffer is full.

A queue made of a circle

To stream messages through shared memory (a game sending events to an external debug tool, an audio engine passing samples), you need a queue that two processes can use at once without a lock. The standard answer is a ring buffer: an array of slots used in a circle, with two counters.

Text
            tail (next to read)          head (next to write)
                  |                            |
  slots:  [ . ][ A ][ B ][ C ][ D ][ . ][ . ][ . ]
  • The producer writes a slot at head, then advances head.
  • The consumer reads the slot at tail, then advances tail.
  • Each counter is written by only one side. That is what makes it work without locks: there is never a moment where both sides write the same variable.

This is a single-producer, single-consumer (SPSC) ring. With several producers or consumers you need more machinery (compare-and-swap loops, or a lock); keep one writer and one reader per ring, and use several rings if needed.

Counters that only grow

Store head and tail as ever-increasing counters, not as slot indexes. Then:

  • the number of items is head - tail;
  • empty is head == tail;
  • full is head - tail == capacity;
  • the slot for counter n is n % capacity, or n & (capacity - 1) when the capacity is a power of two, which is why ring sizes almost always are.

With unsigned 32- or 64-bit counters, head - tail stays correct even when the counters wrap past their maximum, as long as the capacity is less than the wrap-around range.

The code

C++
struct RingHeader
{
    std::atomic<std::uint32_t> head;     // written only by the producer
    std::atomic<std::uint32_t> tail;     // written only by the consumer
    std::uint32_t capacity;              // a power of two
};

bool push(RingHeader* h, std::uint32_t* slots, std::uint32_t value)
{
    const std::uint32_t head{ h->head.load(std::memory_order_relaxed) };     // our own counter
    const std::uint32_t tail{ h->tail.load(std::memory_order_acquire) };     // the consumer's
    if (head - tail == h->capacity) return false;                            // full
    slots[head & (h->capacity - 1)] = value;                                 // write the slot first,
    h->head.store(head + 1, std::memory_order_release);                     // then publish it
    return true;
}

std::optional<std::uint32_t> pop(RingHeader* h, std::uint32_t* slots)
{
    const std::uint32_t tail{ h->tail.load(std::memory_order_relaxed) };
    const std::uint32_t head{ h->head.load(std::memory_order_acquire) };     // see the slots written before it
    if (head == tail) return std::nullopt;                                   // empty
    const std::uint32_t value{ slots[tail & (h->capacity - 1)] };
    h->tail.store(tail + 1, std::memory_order_release);                     // hand the slot back
    return value;
}

The ordering is the important part. The producer writes the slot before publishing the new head with release; the consumer reads head with acquire before reading the slot. That pair guarantees the consumer never sees an advanced head without the slot's data. The same pairing in the other direction guarantees the producer never overwrites a slot the consumer is still reading.

When the ring is full

The producer has to choose a policy:

  • Fail and let the caller decide (the code above). Good for commands, which must not be lost.
  • Drop the new item and count the loss: good for telemetry and logs, where a live process must never wait for a slow observer. Keep a "dropped" counter in the header so the consumer can report the gap.
  • Wait: spin briefly, then wait on an event the consumer signals (milestone 4). Only when the producer can afford to block.

Avoiding false sharing

head and tail sit next to each other but are written by different processes on different cores. Each write invalidates the other core's copy of the 64-byte cache line containing both, which slows everything down. Put them on separate cache lines with alignas(64) padding. The counters are tiny; the padding is cheap.
