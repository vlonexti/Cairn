Seqlocks and Snapshots

lesson 3.055 of 5 in milestone 35 min1 practice task

Publishing a state that changes constantly, such as a game's player positions for an external tool - why readers can see torn data, double buffering, and the seqlock - a sequence counter that lets readers detect a write in progress and retry without ever blocking the writer.

The problem: torn reads

A game updates a block of shared state every frame: player position, health, the current level. An external tool (an overlay, a stats panel, a test harness) reads it whenever it likes. If the tool reads while the game is halfway through writing, it can see the new x with the old y: a torn read, a state that never existed.

A lock would fix it, but a lock lets a slow reader stall the game, which is exactly what must not happen. We want: the writer never waits; readers always get a consistent snapshot, retrying if needed.

Double buffering

Keep two copies of the state and an index saying which one is current. The writer fills the other copy, then flips the index (atomically, with release ordering). Readers read the index (acquire), then copy that buffer.

It is simple, but not quite safe on its own: a reader that is slow enough could still be copying buffer A when the writer, two frames later, starts filling A again. It works when readers are known to be fast compared with the update rate; otherwise add a check, which leads to the seqlock.

The seqlock

A seqlock pairs the data with a sequence counter:

  • The writer increments the counter (it becomes odd: "writing"), writes the data, then increments it again (even: "stable").
  • A reader reads the counter; if it is odd, a write is in progress, try again. Otherwise it copies the data, then reads the counter again. If the counter changed, a write happened during the copy, so the copy may be torn: try again.
C++
// writer: never waits
seq.store(s + 1, std::memory_order_relaxed);          // odd: writing
std::atomic_thread_fence(std::memory_order_release);
copyIn(data, state);
seq.store(s + 2, std::memory_order_release);          // even: stable

// reader: retries instead of blocking anyone
for (;;)
{
    const std::uint32_t before{ seq.load(std::memory_order_acquire) };
    if (before & 1) continue;                          // writer is busy
    State copy{ copyOut(data) };
    std::atomic_thread_fence(std::memory_order_acquire);
    if (seq.load(std::memory_order_relaxed) == before) return copy;   // nothing changed meanwhile
}

The writer never blocks, readers never block the writer, and a reader only retries in the rare case that it overlapped a write. Linux uses seqlocks for the system clock for exactly these reasons.

Doing it correctly in C++

The data is read while it may be being written, which is a data race and undefined behaviour if the data is ordinary memory, however carefully the counter is checked afterwards. The clean way is to store the payload in atomic words and copy it word by word with relaxed atomic loads and stores; the fences then order those against the counter. That is what the practice does: the state is any trivially copyable struct, copied into and out of an array of std::atomic<std::uint64_t>.

Requirements and limits:

  • One writer at a time. Several writers need a lock among themselves (they can still let readers use the seqlock).
  • The state must be trivially copyable: plain numbers and arrays, no pointers into a process's heap.
  • Readers must cope with retrying; under constant updates of a huge state they could retry several times, so keep the published state small.
