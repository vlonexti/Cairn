Worker Processes

lesson 6.022 of 5 in milestone 65 min1 practice task

Doing work in separate processes on purpose - isolating crashes, using several cores, running with fewer rights - and the supervisor that starts workers, watches their heartbeats, restarts them with exponential backoff, and stops trying when they keep crashing.

Why split work into processes

Threads are cheaper, so why would a program start extra worker processes? Because a process gives things a thread cannot:

  • Crash isolation. A worker parsing an untrusted file, running a third-party plugin, or compiling user code can crash without taking the main program with it. The main program reports the failure and starts a new worker.
  • Memory isolation. A worker that leaks or fragments its heap can simply be restarted from time to time.
  • Fewer rights. A worker can run with a restricted token or inside an AppContainer, so even a compromised worker can do little. Browsers render every site in such a sandboxed process.
  • Parallelism without shared state. Workers that share nothing need no locks between them.

The cost is communication: everything a worker needs must be sent to it, and results sent back, through the channels of this course.

The supervisor

A process that starts and watches workers is a supervisor. Its jobs:

  1. Start each worker, inside a job object so they all end if the supervisor dies (lesson 1.03), with a channel to talk to it.
  2. Watch it: wait on its process handle to learn the moment it exits, and on a heartbeat (a regular "still alive" message, or a counter it increments in shared memory) to detect a worker that is alive but hung.
  3. Stop it gracefully when asked: send "stop", wait a few seconds, then TerminateProcess if needed.
  4. Restart it when it fails, according to a policy.

A restart policy

Restarting immediately and for ever is a bad policy: a worker that crashes at start-up (a missing file, a bad configuration) would restart hundreds of times a second, filling logs and burning CPU. Good supervisors use:

  • Exponential backoff: wait 1 s before the first restart, then 2 s, 4 s, 8 s... up to a maximum (say 60 s). Transient problems get quick retries; persistent ones stop hammering the system.
  • A reset after success: if the worker ran for a good while (say 5 minutes) before failing, the next restart starts again from 1 s; it was a one-off failure, not a crash loop.
  • Giving up: if it has crashed, say, 5 times within 10 minutes, stop restarting, mark the feature unavailable and tell the user (or an administrator). A human needs to look.
  • Clean exits are not failures: a worker that exits with code 0 because it finished its job is not restarted.

Windows services have this built in (the "Recovery" tab of a service's properties sets first, second and later failure actions with delays); your own supervisor implements the same idea.

Heartbeats and hangs

A hung worker is worse than a crashed one: its process handle never signals. A heartbeat closes the gap. The worker sends one every second, for example; the supervisor treats three seconds without one as a hang, terminates the worker (it is not going to stop gracefully) and handles it like a crash, with a distinct reason in the log.

The heartbeat must come from the worker's real work loop, not from a separate timer thread that keeps ticking while the work is stuck.

Logging

Every start, exit (with its exit code described as in lesson 1.03), restart delay and give-up should be logged with the worker's name and PID. Crash loops are diagnosed from these logs, often long after the fact.
