Serialising Data

lesson 5.033 of 5 in milestone 55 min1 practice task

Turning values into bytes both sides read the same way - fixed-width little-endian numbers, length-prefixed UTF-8 strings, variable-length integers and zigzag encoding, tag-length-value records that let new fields be added without breaking old readers, and when to use JSON or a library instead.

Never send a struct's memory

The tempting shortcut is send(socket, &settings, sizeof(settings)). It breaks as soon as anything differs between the two sides: padding between members, the size of long, a std::string member (a pointer into the sender's heap), a newer version with an added field. Serialise instead: write each value in a defined byte format, and read it back the same way.

Building blocks

Fixed-width integers, in a stated byte order. Little-endian is the usual choice for new protocols between PCs:

C++
void putU32(std::vector<std::uint8_t>& out, std::uint32_t v)
{
    for (int i{ 0 }; i < 4; ++i) out.push_back(static_cast<std::uint8_t>(v >> (8 * i)));
}

Strings as a length followed by the bytes, in UTF-8 (convert from Windows' UTF-16 at the edge). Never rely on a terminating zero in the data.

Booleans as one byte, 0 or 1; reject other values on reading.

Floating point as the IEEE bit pattern (std::bit_cast<std::uint32_t>(f)), which every modern machine shares.

Variable-length integers

Most numbers in messages are small (ids, counts, lengths), so spending 8 bytes on each is wasteful. A varint (LEB128) uses 7 bits per byte, with the top bit saying "more bytes follow":

Text
1     -> 01
127   -> 7F
128   -> 80 01          (low 7 bits 0000000 with "more", then 1)
300   -> AC 02          (300 = 0b10_0101100: 0101100 | more = 0xAC, then 10 = 0x02)

Small numbers take one byte, large ones up to ten. Negative numbers would always take ten bytes, so signed values are first zigzag-encoded, mapping 0, −1, 1, −2, 2, ... to 0, 1, 2, 3, 4, ...: (n << 1) ^ (n >> 63). Protocol Buffers uses exactly these two tricks.

Readers must reject varints that are too long (more than 10 bytes) or that overflow, since the bytes come from another process.

Tag, length, value

For messages that will grow over time, write each field as a tag (which field), a length (how many bytes), and the value. A reader that meets a tag it does not know skips length bytes and carries on:

Text
field 1 (name):   01 05 41 64 61 4D 73       tag 1, 5 bytes, "AdaMs"
field 2 (volume): 02 01 4B                   tag 2, 1 byte, varint 75
field 9 (new!):   09 02 xx xx                an old reader skips these 2 bytes

This is what makes schema evolution possible: a newer sender adds fields; an older receiver ignores them; a newer receiver handles their absence from an older sender with defaults. The rules: never reuse a tag number for a different meaning, never change a field's type, and treat every field as optional.

Or use JSON, or a library

  • JSON is self-describing text: easy to read in logs, available in every language, naturally tolerant of extra fields. It is slower and bigger, and numbers lose precision beyond 2^53. Excellent for tools and control messages.
  • Protocol Buffers, FlatBuffers, MessagePack and Cap'n Proto give compact binary formats, code generation from a schema, and the evolution rules above, already tested. For a large or long-lived protocol, a library beats a home-made format.

Writing the building blocks yourself once, as this lesson's practice does, is still the best way to understand what those libraries do and to debug their output in a hex dump.
