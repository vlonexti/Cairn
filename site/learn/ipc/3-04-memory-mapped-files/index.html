Memory-Mapped Files

lesson 3.044 of 5 in milestone 35 min1 practice task

Mapping a real file into memory - reading huge files as if they were arrays, views of part of a file and the 64 KB granularity rule, writing through a mapping and flushing it, growing a mapped file, sharing a mapped file between processes, and the errors that arrive as exceptions.

A file as memory

A file mapping can be backed by a real file instead of the page file. Then the file's contents appear in memory, and reading memory reads the file:

C++
HANDLE file{ CreateFileW(path, GENERIC_READ, FILE_SHARE_READ, nullptr, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, nullptr) };
LARGE_INTEGER size{};
GetFileSizeEx(file, &size);
HANDLE mapping{ CreateFileMappingW(file, nullptr, PAGE_READONLY, 0, 0, nullptr) };   // 0, 0: the file's size
const auto* data{ static_cast<const std::uint8_t*>(MapViewOfFile(mapping, FILE_MAP_READ, 0, 0, 0)) };

std::span<const std::uint8_t> bytes{ data, static_cast<std::size_t>(size.QuadPart) };
// parse `bytes` directly: no ReadFile, no buffer, no copy

Pages are read from disk only when first touched, so mapping a 2 GB file is instant, and reading only its index touches only the index's pages. Parsers for big binary formats (game assets, databases, the PE files of the Reverse Engineering course) often work this way: the file is the data structure, navigated by offsets.

Views of part of a file

A 64-bit process can map even very large files whole. When you need only a window (a 32-bit process, or a file larger than you want mapped), map a view of part of it. The view's starting offset must be a multiple of the allocation granularity (64 KB):

Text
want bytes 100 000 to 100 499
  aligned start = 100 000 rounded down to 65 536 = 65 536
  delta         = 100 000 - 65 536 = 34 464
  map from 65 536 for 34 464 + 500 bytes; the data starts `delta` bytes into the view

Writing

Open the file and mapping for writing (GENERIC_READ | GENERIC_WRITE, PAGE_READWRITE, FILE_MAP_WRITE) and writes to memory become writes to the file. The operating system writes changed pages back to disk in its own time; FlushViewOfFile(view, 0) starts it now, and FlushFileBuffers(file) waits until it is on the disk, which matters for anything that must survive a power cut.

A mapping cannot make a file bigger than the size it was created with. To append, close the views and mapping, extend the file (SetFilePointerEx and SetEndOfFile, or create the mapping with a larger size, which extends the file), and map again. Programs that grow mapped files usually extend in large steps (doubling) to avoid remapping constantly.

Sharing a mapped file

Two processes mapping the same file see each other's writes immediately, through the same pages, exactly like a page-file mapping, and the data also persists in the file afterwards. This is how some databases share their data between processes. Coordinating writers still needs the synchronisation of milestone 4.

Errors become exceptions

With ReadFile, a disk error is a return value. With a mapped file, the error happens when you touch a page, inside an ordinary memory access, so it arrives as a structured exception, EXCEPTION_IN_PAGE_ERROR: a file on a network share that disappears, a USB drive pulled out, a file truncated by another process. Code that maps files it does not fully control wraps access in __try / __except, or prefers ReadFile for such files.

Mapped files also hold the file open: it cannot be deleted while mapped, which surprises users of tools that leave mappings around.
