Message Framing

lesson 2.033 of 5 in milestone 25 min1 practice task

Turning a byte stream into messages - length prefixes and why they beat delimiters for binary data, choosing the size and byte order of the length, refusing absurd lengths, reading exactly N bytes, and recovering when the other side sends nonsense.

Streams have no boundaries

A pipe in byte mode, a TCP socket and stdio all deliver a stream: bytes in order, with no record of how they were written. If one side writes "hello" and then "world", the other may read "hellow" and "orld". A program that exchanges messages must therefore mark where each one ends. That is framing.

Three ways to frame

Method How Good for Problem
delimiter end each message with \n (or \0) text, line-based protocols the delimiter cannot appear inside a message without escaping
fixed size every message is N bytes very simple records wastes space; inflexible
length prefix each message starts with its length binary data, anything the reader must trust the length

Length prefixes are the usual choice for program-to-program protocols. A message is sent as:

Text
[ length: 4 bytes, little-endian ][ payload: `length` bytes ]
05 00 00 00 68 65 6C 6C 6F            -> "hello"

Choosing the length field

  • Size: 2 bytes allows 64 KB messages, 4 bytes up to 4 GB. 4 bytes is the common default.
  • Byte order: say which, and stick to it. Little-endian matches x86 and ARM; network protocols traditionally use big-endian. It matters only that both sides agree.
  • What it counts: the payload only, or the whole frame including the length? Document it; the bug where one side counts the header and the other does not is a classic.

Reading a frame

On a stream, a single read may return part of a header, a header and part of a payload, or several frames at once. The robust pattern keeps a buffer (lesson 6.03 of the Reverse Engineering course used it for a protocol):

  1. Append whatever arrives to the buffer.
  2. While the buffer holds at least a header: read the length; if the whole frame is there, take it out and handle it; otherwise wait for more.

When you know how much you need and are happy to block, a "read exactly N bytes" helper is simpler:

C++
bool readExactly(HANDLE pipe, void* buffer, DWORD size)
{
    auto* at{ static_cast<char*>(buffer) };
    while (size > 0)
    {
        DWORD got{};
        if (!ReadFile(pipe, at, size, &got, nullptr) || got == 0) return false;   // closed or failed
        at += got;
        size -= got;
    }
    return true;
}

std::uint32_t length{};
if (!readExactly(pipe, &length, 4) || length > MAX_MESSAGE) return false;
std::vector<char> payload(length);
if (!readExactly(pipe, payload.data(), length)) return false;

Never trust a length

The length comes from the other process, which may be buggy, old, or hostile. A length of 0xFFFFFFFF must not make you allocate 4 GB. Always:

  • enforce a maximum message size that suits your protocol (a few megabytes at most for most uses) and treat anything larger as a protocol error;
  • decide what a length of 0 means (an empty message, or an error);
  • on any framing error, close the connection. After a bad length you no longer know where the next frame starts, so there is nothing safe to continue with.

Message mode instead

Named pipes in message mode (lesson 2.02) do the framing for you: one write is one message. The reading side still has to handle messages larger than its buffer, by reading again after ERROR_MORE_DATA and joining the pieces. It also still needs a maximum size. And everything breaks the day the protocol moves to a socket, which is why many designs frame by hand even on pipes.
