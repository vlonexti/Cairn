Window Messages Between Programs

lesson 4.044 of 5 in milestone 45 min1 practice task

Programs with windows can talk through messages - finding another program's window, WM_COPYDATA for sending a block of data, registered message numbers, message-only windows, SendMessage versus PostMessage, and the privilege boundary UIPI puts in the way.

Messages are already IPC

Every window receives messages through its message loop (Win32 API course, lesson 1.03), and a program can send messages to another program's windows. For two desktop programs that both have windows, this is the simplest IPC there is: no pipes, no shared memory, and the message arrives in the receiver's normal message loop on its UI thread.

Finding the window

The sender needs the receiver's window handle (HWND):

C++
HWND target{ FindWindowW(L"XenonMainWindowClass", nullptr) };    // by window class name

Give your windows a distinctive class name so they can be found reliably; titles change with documents and languages. Background programs without a visible window create a message-only window (CreateWindowExW with parent HWND_MESSAGE): it has no screen presence, cannot be enumerated by accident, but can be found with FindWindowExW(HWND_MESSAGE, nullptr, className, nullptr) and receives messages.

WM_COPYDATA

Ordinary messages carry only two numbers (wParam and lParam), and a pointer in them would be meaningless in the other process. WM_COPYDATA is the exception: Windows copies a block of data into the receiver for the duration of the message.

C++
// sender
const std::wstring path{ LR"(C:\Projects\demo.xproj)" };
COPYDATASTRUCT cds{};
cds.dwData = 1;                                              // your own "message type"
cds.cbData = static_cast<DWORD>((path.size() + 1) * sizeof(wchar_t));
cds.lpData = const_cast<wchar_t*>(path.c_str());
DWORD_PTR result{};
SendMessageTimeoutW(target, WM_COPYDATA, reinterpret_cast<WPARAM>(myWindow), reinterpret_cast<LPARAM>(&cds),
                    SMTO_ABORTIFHUNG, 2000, &result);

// receiver, in the window procedure
case WM_COPYDATA:
{
    const auto* cds{ reinterpret_cast<const COPYDATASTRUCT*>(lParam) };
    if (cds->dwData == 1 && cds->cbData >= sizeof(wchar_t) && cds->cbData % sizeof(wchar_t) == 0)
        openProject(std::wstring(static_cast<const wchar_t*>(cds->lpData), cds->cbData / sizeof(wchar_t) - 1));
    return TRUE;
}

Rules:

  • The data is valid only while the receiver handles the message. Copy what you need before returning.
  • WM_COPYDATA must be sent, not posted, because the copy only lives during the call. Use SendMessageTimeoutW with a timeout so a hung receiver cannot hang the sender.
  • Validate everything: dwData, the size, and the content. Any program on the desktop can send you WM_COPYDATA.

Registered messages

For simple notifications without data ("reload your settings"), define your own message number. Numbers from WM_APP up are private to one program; to agree on a number between programs, register a name:

C++
const UINT reloadMessage{ RegisterWindowMessageW(L"Xenon.ReloadSettings") };   // same number in every process
PostMessageW(HWND_BROADCAST, reloadMessage, 0, 0);                              // tell every top-level window

SendMessage and PostMessage

  • PostMessageW puts the message in the receiver's queue and returns immediately. Fire and forget; works only with plain numbers.
  • SendMessageW waits until the receiver has processed the message and returns its result. If the receiver is hung, so is the sender, which is why cross-process sends should always be SendMessageTimeoutW.

UIPI: the privilege boundary

User Interface Privilege Isolation stops a process from sending most messages to a window of a process running at a higher integrity level. A normal program cannot send WM_COPYDATA to a program running as administrator: the message is silently dropped. The elevated program can allow specific messages with ChangeWindowMessageFilterEx(hwnd, WM_COPYDATA, MSGFLT_ALLOW, nullptr), after which it must treat every such message as coming from a less trusted sender.

When not to use messages

Window messages need a window and a message loop on both sides, run on the UI thread (so heavy work blocks the interface), and are limited to one desktop. For services, background workers, large data or high rates, use pipes or shared memory. For "hand a file to the running instance of my editor", they are perfect.
