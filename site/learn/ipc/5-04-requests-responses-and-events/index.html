Requests, Responses and Events

lesson 5.044 of 5 in milestone 55 min1 practice task

The flow of a conversation - request ids that match responses to requests, many requests in flight at once, timeouts and cancellation, events the server sends unasked, what ordering a stream does and does not guarantee, and safe retries.

One at a time is too slow

The simplest client sends a request and waits for the response before sending the next. That works, but a slow request (indexing a large project) blocks every quick one behind it, and every request pays the full round trip. Real protocols let several requests be in flight at once, which needs a way to tell responses apart.

Correlation ids

Each request carries an id chosen by the sender, unique among its outstanding requests (a counter is fine). The response carries the same id. The client keeps a table of pending requests:

Text
id 41  findSymbol("Player")   sent at 10.000 s
id 42  formatFile("a.cpp")    sent at 10.002 s
id 43  ping                   sent at 10.003 s

<- response id 43  "pong"            (answered first: it was quick)
<- response id 41  [3 results]
<- response id 42  error "file locked"

When a response arrives, the client looks up its id, removes the entry and delivers the result to whoever is waiting: a callback, a promise, or a coroutine. A response with an unknown id (late, after a timeout; or a bug) is logged and dropped.

JSON-RPC 2.0, used by the Language Server Protocol, is exactly this: {"jsonrpc":"2.0","id":41,"method":"findSymbol","params":{...}} and a response {"jsonrpc":"2.0","id":41,"result":...}, with notifications having no id.

Timeouts and cancellation

Every pending request needs a deadline. A periodic check (or a timer) finds requests past their deadline, removes them from the table and reports a timeout to the caller. If the server answers later, the response no longer matches anything and is dropped.

A timeout on the client does not stop the work on the server. For expensive requests, add a cancel message (cancel id 41) that the server uses to abandon the work. It may still send a response (a result or a "cancelled" error), and the client must cope with either.

Events

The server often needs to speak first: a file changed on disk, a build finished, a log line. These are events (notifications): a message type with no id and no response. Clients subscribe to the events they want, so a server does not flood clients with messages they will ignore.

Events and responses share one connection, so the client's reading loop dispatches each incoming message by kind: response (match the id) or event (call the subscriber).

Ordering

A single stream (one pipe or TCP connection) delivers messages in the order they were sent. That gives useful guarantees: two events sent in order arrive in order, and a response sent after an event arrives after it. It does not mean responses come back in the order requests were sent, if the server handles requests concurrently. Design so that clients never depend on response order, only on ids.

Across several connections there is no ordering at all.

Retries and idempotency

After a timeout or a dropped connection, the client may not know whether the server performed a request. Retrying is safe only if the request is idempotent: doing it twice has the same effect as once (setVolume(70), getStatus). For requests that are not (appendLog, createFile), either let the server recognise a repeated request by a request key chosen by the client and return the original result, or report the uncertainty to the user instead of retrying blindly.
