What a Process Is

lesson 1.011 of 5 in milestone 15 min1 practice task

A process is a running program's container - a private address space, a table of handles, a security token, one or more threads and an exit code. Process IDs and handles, why processes cannot see each other's memory, and why that isolation is the reason inter-process communication needs special tools.

A container for a running program

When you start a program, Windows creates a process: not the code itself, but everything the running code needs and owns.

Part What it is
Address space a private range of virtual addresses (Pointers and Memory course, lesson 6.04) holding the program, its DLLs, heaps and stacks
Threads the things that actually execute; a process has at least one
Handle table the kernel objects it has opened: files, pipes, events, other processes
Access token who it runs as, and what it is allowed to do
Environment and command line text handed over at start-up
Exit code a number left behind when it ends

Every process has a process ID (PID), a number unique among running processes. PIDs are reused after a process is gone, so a PID alone is not a safe long-term reference to "that process".

Isolation

Each process has its own address space. The address 0x2C409610 in one process and the same number in another refer to entirely different memory, or to nothing. A bug in one program cannot overwrite another program's variables, and a crash ends only the process that crashed.

That isolation is the whole reason this course exists. Two threads in one process share memory and can talk by just writing variables (with care). Two processes cannot: everything they exchange has to go through something the operating system provides and both can reach:

  • a pipe carrying bytes from one to the other;
  • a file mapping that the kernel maps into both address spaces;
  • a socket, even when both ends are on the same machine;
  • named kernel objects (events, mutexes, semaphores) for signalling;
  • window messages, for programs with windows;
  • plain files, and higher layers built on the above (COM, RPC).

Handles to processes

To do anything with another process, you need a handle to it, with the access you ask for:

C++
HANDLE process{ OpenProcess(SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION, FALSE, pid) };
if (process)
{
    WaitForSingleObject(process, INFINITE);       // wait until it ends
    DWORD code{};
    GetExitCodeProcess(process, &code);
    CloseHandle(process);
}

A process handle is better than a PID for keeping track of a process: while you hold the handle, the process object stays valid (even after the process ends, so you can read its exit code), and its PID cannot be reused for another process. When you start a child yourself, CreateProcessW gives you its handle directly.

Threads, processes and jobs

  • A thread runs code inside a process. Several threads share the process's memory and handles.
  • A process owns resources and isolates them from other processes.
  • A job object groups processes so they can be managed together: limits on memory or CPU, and ending them all at once (lesson 1.03).

When should work be split across processes instead of threads? When isolation is worth the cost of communication: a crash in a plugin should not take down the editor; an untrusted file parser should run with fewer rights; a long build should continue even if the window closes. Browsers run each site in its own process for exactly these reasons.

Lifetime

A process ends when its last thread ends, when it calls ExitProcess, or when another process ends it with TerminateProcess. Windows then closes every handle it had open, which matters for IPC: a pipe whose other end belonged to a process that died is closed, and a mutex it owned is released as abandoned (lesson 4.03). Good IPC code always plans for the other side disappearing without warning.
