Overlapped I/O and Completion Ports

lesson 2.055 of 5 in milestone 25 min1 practice task

Doing pipe I/O without blocking a thread per operation - FILE_FLAG_OVERLAPPED, OVERLAPPED structures and events, ERROR_IO_PENDING, GetOverlappedResult, and I/O completion ports that let a few threads serve thousands of connections as state machines.

Asking now, finding out later

Blocking I/O ties up a thread while it waits. Overlapped I/O starts an operation and returns at once; the result arrives later. To use it, open or create the handle with FILE_FLAG_OVERLAPPED (for a pipe server, PIPE_ACCESS_DUPLEX | FILE_FLAG_OVERLAPPED), and pass an OVERLAPPED structure to each call:

C++
OVERLAPPED ov{};
ov.hEvent = CreateEventW(nullptr, TRUE, FALSE, nullptr);       // signalled when the operation completes

char buffer[4096];
if (!ReadFile(pipe, buffer, sizeof(buffer), nullptr, &ov))
{
    if (GetLastError() != ERROR_IO_PENDING) /* a real failure */;
    // ... the read is in progress; do other work, or wait ...
}
DWORD got{};
if (GetOverlappedResult(pipe, &ov, &got, TRUE /* wait */)) { /* `got` bytes are in buffer */ }

Rules that bite:

  • The OVERLAPPED and the buffer must stay alive and untouched until the operation completes. Putting them on the stack of a function that returns while the read is pending is a classic memory corruption.
  • One OVERLAPPED per outstanding operation.
  • An operation may complete immediately (the call returns TRUE); handle that path too.
  • CancelIoEx(handle, &ov) cancels a pending operation; you must still wait for its completion (with ERROR_OPERATION_ABORTED) before freeing the buffer.

With an event per operation, one thread can wait for many with WaitForMultipleObjects, up to 64 handles. Beyond that, use a completion port.

I/O completion ports

An I/O completion port (IOCP) is a queue that collects the completions of many handles. Associate each handle with the port and a key of your choosing (usually a pointer to the connection's state):

C++
HANDLE port{ CreateIoCompletionPort(INVALID_HANDLE_VALUE, nullptr, 0, 0) };
CreateIoCompletionPort(pipe, port, reinterpret_cast<ULONG_PTR>(connection), 0);   // associate

Then start overlapped operations as usual (no event needed), and have a few worker threads pull completions:

C++
for (;;)
{
    DWORD bytes{};
    ULONG_PTR key{};
    OVERLAPPED* ov{};
    const BOOL ok{ GetQueuedCompletionStatus(port, &bytes, &key, &ov, INFINITE) };
    auto* connection{ reinterpret_cast<Connection*>(key) };
    if (!ok || bytes == 0 && connection->expectingData()) { connection->close(); continue; }
    connection->onCompleted(ov, bytes);            // advance its state machine, start the next operation
}

PostQueuedCompletionStatus adds your own items to the queue, which is how you wake the workers to shut down.

Connections as state machines

With completions arriving one at a time, each connection is no longer a thread running top to bottom; it is a state machine that reacts to each completion and starts the next operation:

Text
          read 4 header bytes complete
  READING_HEADER ---------------------------> READING_BODY (start a read of `length` bytes)
        ^                                        |
        |   write complete                       | body complete: handle the request
        +------------- WRITING <-----------------+ (start writing the reply)

Each state knows which operation it is waiting for and how many bytes it still needs (a read may return fewer bytes than asked; then it simply reads again for the rest). This is more code than a thread per client, but a handful of worker threads can serve thousands of connections, and the same design works for sockets: it is how high-performance Windows servers are written.

For smaller servers the Windows thread pool API (CreateThreadpoolIo) wraps completion ports for you, and C++ libraries such as Asio provide the same model portably.
