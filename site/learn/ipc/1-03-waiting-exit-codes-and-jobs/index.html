Waiting, Exit Codes and Jobs

lesson 1.033 of 5 in milestone 15 min1 practice task

Knowing how a child process ended - waiting with timeouts, exit code conventions and the NTSTATUS codes a crash leaves behind - and job objects that group processes, end them all at once and limit what they can use.

Waiting

A process handle becomes signalled when the process ends, so every wait function works on it:

C++
switch (WaitForSingleObject(process, 30'000))      // up to 30 seconds
{
case WAIT_OBJECT_0: /* it ended */ break;
case WAIT_TIMEOUT:  /* still running: decide whether to keep waiting or end it */ break;
case WAIT_FAILED:   /* bad handle: GetLastError() */ break;
}

Always choose a timeout. A child that hangs (waiting for input it will never get, stuck on a dialog box, deadlocked) would otherwise freeze the parent for ever. WaitForMultipleObjects waits for any of several processes (up to 64 handles) at once.

Exit codes

GetExitCodeProcess gives the code a process ended with. While it is still running it returns STILL_ACTIVE (259), which is one reason not to use 259 as a real exit code, and why you should check the process has really ended before trusting the value.

Conventions:

Code Usually means
0 success
1, 2, ... small numbers the program's own errors (documented by each tool: robocopy uses 0 to 7 for success!)
0xC0000005 access violation: it crashed
0xC0000409 stack buffer overrun or fail-fast: the /GS check or abort style termination
0xC00000FD stack overflow
0xC0000374 heap corruption
0xC000013A ended with Ctrl+C
0x40010004 ended by a debugger
0xE06D7363 an unhandled C++ exception (msc in its last three bytes)

Codes starting with 0xC are NTSTATUS error values: the process did not choose to exit, Windows ended it after an unhandled exception. A supervisor that restarts helpers (milestone 6) needs to tell "the job failed" (a small code) from "the program crashed" (an NTSTATUS), and log them differently.

Ending a process

TerminateProcess(process, code) ends a process immediately: no destructors, no flushing of files, no clean-up of any kind. It is a last resort. Prefer asking the process to stop through your own channel (a "quit" message on a pipe, an event it watches), waiting a few seconds, and only then terminating.

Job objects

A job object groups processes. Its most useful features:

Kill on close. End every process in the job when the last handle to the job closes, including when your process crashes:

C++
HANDLE job{ CreateJobObjectW(nullptr, nullptr) };
JOBOBJECT_EXTENDED_LIMIT_INFORMATION info{};
info.BasicLimitInformation.LimitFlags = JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE;
SetInformationJobObject(job, JobObjectExtendedLimitInformation, &info, sizeof(info));

// start each helper with CREATE_SUSPENDED, then:
AssignProcessToJobObject(job, pi.hProcess);
ResumeThread(pi.hThread);

Without this, helper processes outlive a crashed parent and pile up in Task Manager. Children that the helpers start themselves join the job automatically.

Limits. A job can cap memory per process or for the whole job, CPU time, CPU rate, and the number of active processes. A build tool can use them to stop one runaway compiler from taking the whole machine.

Accounting. QueryInformationJobObject reports the total CPU time, I/O and peak memory of everything in the job, which is a simple way to measure what a group of processes really cost.
