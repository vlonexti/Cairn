Anonymous Pipes

lesson 2.011 of 5 in milestone 25 min1 practice task

The one-way byte channel behind standard streams - creating a pipe, its buffer and what happens when it fills, end-of-file and broken pipes, peeking without blocking, and passing pipe ends to a child.

Two ends, one direction

CreatePipe makes an anonymous pipe: a buffer in the kernel with a read end and a write end, each a handle.

C++
HANDLE readEnd{}, writeEnd{};
if (!CreatePipe(&readEnd, &writeEnd, nullptr, 64 * 1024))   // ask for a 64 KB buffer
    throw std::runtime_error("CreatePipe failed");

const char message[]{ "hello" };
DWORD n{};
WriteFile(writeEnd, message, 5, &n, nullptr);               // into the pipe
char buffer[16];
ReadFile(readEnd, buffer, sizeof(buffer), &n, nullptr);     // n == 5

Bytes come out in the order they went in, with no boundaries: two writes of 5 bytes may be read as one read of 10, or as reads of 3 and 7. For two-way communication, use two pipes.

"Anonymous" means it has no name: the only way for another process to use it is to be given a handle to one end, by inheritance when it starts (lesson 1.04) or by DuplicateHandle. That makes anonymous pipes ideal between a parent and its children, and useless between unrelated programs (lesson 2.02).

When the buffer fills

The buffer size passed to CreatePipe is a suggestion (0 means a default of a few kilobytes). When it is full, WriteFile blocks until the reader takes data out. When it is empty, ReadFile blocks until data arrives. Blocking is what makes simple pipe code correct, and also what causes the deadlocks of lesson 1.04 when both sides wait on each other.

To find out without blocking whether data is waiting, use PeekNamedPipe (it works on anonymous pipes too):

C++
DWORD available{};
if (PeekNamedPipe(readEnd, nullptr, 0, nullptr, &available, nullptr) && available > 0)
    /* a ReadFile of up to `available` bytes returns at once */;

End-of-file and broken pipes

How each side learns that the other has finished:

Situation What the other side sees
every write handle is closed, buffer empty ReadFile fails with ERROR_BROKEN_PIPE (109): this is end-of-file for a pipe
the read handle is closed WriteFile fails with ERROR_NO_DATA (232) ("the pipe is being closed")

Note "every write handle": any copy of the write end left open anywhere, in the parent or inherited by another child, keeps the reader waiting. Close your copies of ends you do not use, immediately.

Treat ERROR_BROKEN_PIPE on a read as a normal, expected end of the conversation, not as an error to report.

Sizes and speed

Each ReadFile and WriteFile is a call into the kernel and a copy of the data. Many tiny writes are slow; batch output into larger writes (a few kilobytes) where you can. Anonymous pipes on Windows are actually implemented as named pipes with generated names, so everything about performance in the next lessons applies to them too.

Inside one process

Pipes also work between threads of one process, which is occasionally handy for code that already speaks in handles. But between threads, a std::queue with a mutex and condition variable is simpler and faster: pipes earn their keep crossing process boundaries.
