Sockets on One Machine

lesson 5.011 of 5 in milestone 55 min1 practice task

Using sockets for local IPC - Winsock start-up, a TCP server bound to 127.0.0.1 and never to every interface, letting the system choose a port and publishing it in a file, Unix domain sockets on Windows, and how sockets compare with named pipes.

Why sockets locally

Named pipes are Windows-specific. Sockets are everywhere: every language, every operating system, the same API whether the other end is in the next process or on another continent. Many tools use a local socket for IPC: debuggers' remote protocols, language tooling, local web dashboards, game editors talking to a running game. The Networking course covers sockets in depth; this lesson covers what is special about using them on one machine.

A loopback server

C++
WSADATA wsa{};
WSAStartup(MAKEWORD(2, 2), &wsa);                              // once per process

SOCKET listener{ socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) };
sockaddr_in addr{};
addr.sin_family = AF_INET;
addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);                 // 127.0.0.1 only
addr.sin_port = htons(0);                                      // 0: let the system pick a free port
bind(listener, reinterpret_cast<sockaddr*>(&addr), sizeof(addr));
listen(listener, SOMAXCONN);

int length{ sizeof(addr) };
getsockname(listener, reinterpret_cast<sockaddr*>(&addr), &length);
const unsigned short port{ ntohs(addr.sin_port) };             // the port it actually got

SOCKET client{ accept(listener, nullptr, nullptr) };           // wait for a connection
// recv / send on `client`, with the framing of lesson 2.03

Three choices matter for local IPC:

  1. Bind to 127.0.0.1 (loopback), never to 0.0.0.0 (all interfaces). Bound to everything, your private IPC endpoint is reachable from the network, and Windows Firewall asks the user whether to allow it. Bound to loopback, only local processes can connect and no prompt appears.
  2. Let the system choose the port (port 0). Fixed port numbers collide with other programs and with a second copy of your own.
  3. Publish the port where the client can find it: a small file in the user's profile (%LOCALAPPDATA%\Xenon\agent.port) holding the port, the server's PID, and a random token the client must present (lesson 5.05). The client reads the file, connects to 127.0.0.1:port, and proves it read the file by sending the token.

Unix domain sockets on Windows

Windows 10 (version 1803) and later support AF_UNIX stream sockets: socket endpoints that are paths in the file system instead of ports.

C++
#include <afunix.h>
SOCKET s{ socket(AF_UNIX, SOCK_STREAM, 0) };
sockaddr_un addr{};
addr.sun_family = AF_UNIX;
strcpy_s(addr.sun_path, R"(C:\Users\sam\AppData\Local\Xenon\agent.sock)");
bind(s, reinterpret_cast<sockaddr*>(&addr), sizeof(addr));

Advantages: no ports at all, and access is controlled by the file's permissions: put it in a folder only the user can read and other users cannot connect. Code written for Linux and macOS (which have had Unix sockets for decades) ports with little change. Delete the socket file before binding again (bind fails if it exists) and when shutting down.

Sockets versus named pipes

Named pipe Loopback TCP AF_UNIX
Portable Windows only everywhere Windows 10+, Linux, macOS
Who can connect controlled by a security descriptor any local process controlled by file permissions
Discovery a name you choose a port, published somewhere a path
Message mode yes no (frame yourself) no
Client identity GetNamedPipeClientProcessId, impersonation nothing built in limited
Across machines yes (SMB) yes no

For a Windows-only program that wants strong access control, named pipes remain a good choice. For anything that might be portable, or that a tool in another language must talk to, prefer sockets, and design the security in from the start.
