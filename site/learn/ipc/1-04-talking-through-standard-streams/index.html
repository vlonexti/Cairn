Talking Through Standard Streams

lesson 1.044 of 5 in milestone 15 min1 practice task

The simplest channel between a parent and a child - its standard input, output and error redirected to pipes - and the deadlocks waiting for anyone who reads them carelessly, plus line-based protocols over stdio as used by language servers and many tools.

Three streams for free

Every process has three standard handles: input, output and error. A console program reads from the first and writes to the others. When you start a program, you can connect any of them to a pipe you hold the other end of, and you have a two-way channel with no extra setup on the child's side: it just uses std::cin and std::cout.

That is why so many tools talk this way: compilers report errors on stderr, git writes results on stdout, and language servers (the processes behind code completion in editors) exchange JSON messages over stdin and stdout.

Wiring it up

C++
SECURITY_ATTRIBUTES inheritable{ sizeof(inheritable), nullptr, TRUE };
HANDLE inRead, inWrite, outRead, outWrite;
CreatePipe(&inRead, &inWrite, &inheritable, 0);       // parent writes inWrite -> child reads inRead
CreatePipe(&outRead, &outWrite, &inheritable, 0);     // child writes outWrite -> parent reads outRead
SetHandleInformation(inWrite, HANDLE_FLAG_INHERIT, 0);  // the parent's ends must NOT be inherited
SetHandleInformation(outRead, HANDLE_FLAG_INHERIT, 0);

STARTUPINFOW si{ sizeof(si) };
si.dwFlags = STARTF_USESTDHANDLES;
si.hStdInput = inRead;
si.hStdOutput = outWrite;
si.hStdError = outWrite;                               // or a third pipe, to keep errors apart
CreateProcessW(/* ... */ TRUE /* inherit */, CREATE_NO_WINDOW, /* ... */ &si, &pi);

CloseHandle(inRead);       // the child has its own copies now
CloseHandle(outWrite);     // essential: otherwise reading outRead never ends

Closing the parent's copies of the child's ends is the step people forget. A pipe reports end-of-file to the reader only when every write handle is closed; if the parent still holds outWrite, reading outRead waits for ever after the child exits.

Likewise, when the parent has nothing more to send, it closes inWrite, and the child's next read sees end-of-file. Many tools read until end of input before they start working.

The deadlock

Pipes have a fixed buffer, typically a few kilobytes. A writer whose pipe is full blocks until the reader takes something out. That creates a classic deadlock:

  1. The parent writes a large input to the child's stdin, all of it, before reading anything.
  2. The child reads a little, then writes a lot of output, filling its stdout pipe.
  3. The child blocks writing; the parent blocks writing; neither ever reads.

The same happens with stdout and stderr on two pipes: the parent reads stdout to the end while the child blocks writing to a full stderr.

The rule: read every output pipe continuously while also writing. In practice, read each output pipe on its own thread (or use overlapped I/O, lesson 2.05), collecting what arrives, and write input on another.

Lines and encodings

Output arrives in arbitrary chunks, not lines: one read can return half a line, or three and a half. To process line by line, keep a buffer per stream, append each chunk, and take out complete lines (ending in \n, with a \r before it on Windows) as they appear; whatever is left waits for the next chunk. The final partial line is complete only when the stream reaches end-of-file.

Console programs write in the console's code page or in UTF-8; when you capture them you receive raw bytes and must decode them yourself. Many tools let you choose (git -c core.quotepath=off, Python's PYTHONIOENCODING=utf-8); for your own helpers, always write UTF-8.

Protocols over stdio

Stdio becomes a real protocol once both sides agree on message boundaries. Two common choices:

  • One message per line (JSON Lines, for example): simple, as long as messages never contain a raw newline.
  • Headers then a body of known length, as the Language Server Protocol does:
Text
Content-Length: 52\r\n
\r\n
{"jsonrpc":"2.0","id":1,"method":"initialize",...}

The reader parses headers up to the blank line, then reads exactly Content-Length bytes. Milestone 2 builds framing like this properly.

Watch out

A child that writes anything else to stdout (a debug printf, a library's warning) corrupts a stdout protocol. Send logs to stderr, or to a file.
