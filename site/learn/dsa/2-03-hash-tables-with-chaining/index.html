Hash Tables with Chaining

lesson 2.033 of 5 in milestone 26 min1 practice task

The classic hash table - an array of buckets, each holding a chain of entries, insert, find and erase, the load factor and why the expected chain length stays constant, rehashing by doubling, how std::unordered_map is built and its bucket interface, reserve and max_load_factor, and the worst case.

Buckets of chains

Separate chaining is the simplest way to handle collisions: each bucket holds a small list of every entry that hashed there.

  • find(key): hash the key, go to its bucket, scan the chain for an equal key.
  • insert(key, value): find it; if it is there, update it, otherwise add an entry to the chain.
  • erase(key): find it and remove it from the chain.

Each operation costs one hash plus the length of one chain.

The load factor

The load factor is α = n / m: the number of entries divided by the number of buckets. With a good hash, entries are spread evenly, so the expected chain length is α. If the table keeps α below a constant (say 1), every operation is expected O(1), however many entries there are.

To keep α bounded, the table rehashes when it gets too full: it allocates about twice as many buckets and reinserts every entry (each entry's bucket changes, because hash % m depends on m). One rehash costs O(n), but as with a dynamic array, doubling makes it amortised O(1) per insert.

Building one

C++
#include <functional>
#include <iostream>
#include <optional>
#include <string>
#include <utility>
#include <vector>

template <class K, class V, class Hash = std::hash<K>>
class ChainedMap
{
public:
    ChainedMap() : buckets_(8) {}

    void put(const K& key, const V& value)
    {
        auto& chain = bucketFor(key);
        for (auto& [k, v] : chain)
            if (k == key) { v = value; return; }
        chain.emplace_back(key, value);
        ++size_;
        if (size_ > buckets_.size()) rehash(buckets_.size() * 2);   // keep the load factor at most 1
    }

    std::optional<V> get(const K& key) const
    {
        for (const auto& [k, v] : bucketFor(key))
            if (k == key) return v;
        return std::nullopt;
    }

    bool erase(const K& key)
    {
        auto& chain = bucketFor(key);
        for (std::size_t i = 0; i < chain.size(); ++i)
            if (chain[i].first == key)
            {
                chain[i] = std::move(chain.back());   // order inside a chain does not matter
                chain.pop_back();
                --size_;
                return true;
            }
        return false;
    }

    std::size_t size() const { return size_; }
    std::size_t bucketCount() const { return buckets_.size(); }

private:
    using Chain = std::vector<std::pair<K, V>>;

    Chain& bucketFor(const K& key) { return buckets_[Hash{}(key) % buckets_.size()]; }
    const Chain& bucketFor(const K& key) const { return buckets_[Hash{}(key) % buckets_.size()]; }

    void rehash(std::size_t count)
    {
        std::vector<Chain> old = std::move(buckets_);
        buckets_ = std::vector<Chain>(count);
        for (auto& chain : old)
            for (auto& entry : chain) bucketFor(entry.first).push_back(std::move(entry));
    }

    std::vector<Chain> buckets_;
    std::size_t size_ = 0;
};

int main()
{
    ChainedMap<std::string, int> ages;
    ages.put("Ada", 36);
    ages.put("Grace", 85);
    ages.put("Ada", 37);                  // updates
    for (int i = 0; i < 100; ++i) ages.put("user" + std::to_string(i), i);
    ages.erase("user50");

    std::cout << "Ada " << ages.get("Ada").value_or(-1) << ", user50 " << ages.get("user50").value_or(-1)
              << ", size " << ages.size() << ", buckets " << ages.bucketCount() << '\n';
}

Each chain here is a small std::vector rather than a linked list: chains are short, and scanning a few contiguous entries is faster than following pointers. Erasing swaps the entry with the last one in its chain, which is O(1) once it is found.

std::unordered_map

The standard std::unordered_map is a chained hash table. Its rules (iterators and references to elements stay valid when other elements are inserted) force it to keep each element in its own heap node, linked in chains. It exposes the bucket structure if you want to look:

C++
#include <iostream>
#include <string>
#include <unordered_map>

int main()
{
    std::unordered_map<std::string, int> m;
    std::cout << "empty: " << m.bucket_count() << " buckets\n";
    for (int i = 0; i < 1000; ++i) m["key" + std::to_string(i)] = i;
    std::cout << "1000 entries: " << m.bucket_count() << " buckets, load factor " << m.load_factor()
              << " (max " << m.max_load_factor() << ")\n";

    std::size_t longest = 0;
    for (std::size_t b = 0; b < m.bucket_count(); ++b) longest = std::max(longest, m.bucket_size(b));
    std::cout << "longest chain: " << longest << '\n';

    std::unordered_map<std::string, int> sized;
    sized.reserve(1000);                  // allocate enough buckets once: no rehashing while filling
    std::cout << "after reserve(1000): " << sized.bucket_count() << " buckets\n";
}
Member Meaning
bucket_count(), bucket(key), bucket_size(b) The structure
load_factor(), max_load_factor(f) The current α and the limit that triggers a rehash (1.0 by default)
reserve(n) Make room for n elements without rehashing
rehash(m) At least m buckets

Because of the per-element nodes, std::unordered_map is often slower than tables that store entries directly in an array (open addressing, lesson 2.04). Libraries such as Abseil's flat_hash_map and Boost's unordered_flat_map do that and are typically two to three times faster.

The worst case

Expected O(1) assumes the hash spreads the keys. If every key lands in one bucket, which happens with a terrible hash or a deliberate attack, each operation scans one chain of length n: O(n). Hash tables trade a small chance of a bad worst case for an excellent average. When you need guaranteed O(log n), use a balanced tree (std::map, lesson 4.03).

Summary

  • Chaining keeps a list of entries per bucket; each operation costs one hash plus one chain.
  • With a good hash, the expected chain length is the load factor α = n / m; keeping α bounded makes operations expected O(1).
  • Rehashing into twice as many buckets keeps insertion amortised O(1).
  • std::unordered_map is a chained table with one node per element; reserve avoids rehashing.
  • The worst case is O(n) per operation, when keys pile into one bucket.
