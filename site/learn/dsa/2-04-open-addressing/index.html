Open Addressing

lesson 2.044 of 5 in milestone 27 min1 practice task

Hash tables that keep entries directly in the array - linear probing, why erasing needs tombstones (or backward-shift deletion), primary clustering and the expected probe counts, quadratic probing and double hashing, keeping the load factor below about 0.7, Robin Hood hashing, and power-of-two tables with a mixing step.

No chains at all

Open addressing stores every entry directly in the table's array. When a key's home slot is taken, the table probes other slots in a fixed order until it finds the key or an empty slot. There are no lists and no per-entry allocations, so the whole table is one contiguous block: cache-friendly and fast.

Linear probing

The simplest probe sequence tries the next slot, then the next, wrapping around at the end:

Output
slot = hash(key) % m,  then (slot + 1) % m,  (slot + 2) % m, ...
  • find: probe from the home slot until you find the key (found) or an empty slot (not there).
  • insert: probe until you find the key (update it) or an empty slot (put it there).
C++
#include <iostream>
#include <optional>
#include <string>
#include <vector>

class ProbingMap
{
public:
    explicit ProbingMap(std::size_t capacity) : slots_(capacity) {}

    void put(int key, std::string value)
    {
        std::size_t i = home(key);
        while (slots_[i] && slots_[i]->key != key) i = (i + 1) % slots_.size();
        if (!slots_[i]) ++size_;
        slots_[i] = Entry{ key, std::move(value) };
    }

    const std::string* get(int key) const
    {
        for (std::size_t i = home(key); slots_[i]; i = (i + 1) % slots_.size())
            if (slots_[i]->key == key) return &slots_[i]->value;
        return nullptr;
    }

    void show() const
    {
        for (std::size_t i = 0; i < slots_.size(); ++i)
            std::cout << i << ": " << (slots_[i] ? std::to_string(slots_[i]->key) + " " + slots_[i]->value : "-") << '\n';
    }

private:
    struct Entry { int key; std::string value; };
    std::size_t home(int key) const { return static_cast<std::size_t>(key) % slots_.size(); }

    std::vector<std::optional<Entry>> slots_;
    std::size_t size_ = 0;
};

int main()
{
    ProbingMap m(10);                               // a real table would grow; this one stays small to show the slots
    m.put(12, "a");                                 // home 2
    m.put(22, "b");                                 // home 2: taken, goes to 3
    m.put(3, "c");                                  // home 3: taken, goes to 4
    m.put(19, "d");                                 // home 9
    m.put(29, "e");                                 // home 9: taken, wraps to 0
    m.show();
    std::cout << "get(3) = " << *m.get(3) << ", get(32) found? " << (m.get(32) != nullptr) << '\n';
}

Keys 22 and 3 never had the same home slot, yet 3 was pushed along by 22. Runs of occupied slots grow and merge: this is primary clustering, linear probing's weakness.

Deleting needs tombstones

You cannot simply empty a slot when erasing. In the table above, erasing 22 and leaving slot 3 empty would break get(3): the key 3 has home slot 3, the probe finds that slot empty and stops, and wrongly concludes 3 is absent, although it sits one slot further on, in slot 4. Erasing 12 the same way would hide 22, and through it 3 as well.

The usual fix is a tombstone: mark the slot "deleted". Searches skip over tombstones (the key could be further along); inserts may reuse them. Tombstones count towards the load when deciding to rehash, and a rehash clears them all.

Linear probing also allows backward-shift deletion: after emptying a slot, walk forward through the run and move back any entry whose home slot is at or before the hole. No tombstones are needed, at the cost of a slightly more complex erase.

How full can it get?

For linear probing with a good hash and load factor α (now at most 1, since each slot holds one entry), the expected number of probes is about:

α Successful search Unsuccessful search or insert
0.5 1.5 2.5
0.7 2.2 6.1
0.9 5.5 50.5

(The formulas are ½(1 + 1/(1−α)) and ½(1 + 1/(1−α)²), from Knuth.) Performance falls off a cliff as the table fills, so open-addressing tables rehash at a load factor around 0.5 to 0.875, depending on the design.

Other probe sequences

Scheme Probe i Notes
Linear home + i Best cache behaviour; suffers primary clustering
Quadratic home + i² (or + (i + i²)/2) Breaks up runs; with a power-of-two table and the triangular form, it visits every slot
Double hashing home + i × h₂(key) A second hash sets each key's step; the least clustering, but each probe jumps in memory

Modern high-performance tables mostly use linear probing (or probing in groups of 16 slots checked at once with SIMD instructions, as Abseil's and Boost's flat maps do), because the cache matters more than clustering.

Robin Hood hashing

Robin Hood hashing is linear probing with one rule: during insertion, if the entry being inserted is further from its home slot than the entry occupying the current slot, they swap, and the insertion continues with the evicted entry. "Take from the rich (close to home) and give to the poor (far from home)." The variance of probe lengths drops sharply, and searches can stop early once they pass entries closer to home than the key would be.

Power-of-two tables

Computing % m is a slow division. Many tables use a power-of-two size and take hash & (m - 1), which keeps only the low bits. That only works if the low bits are well mixed, so such tables first scramble the hash, for example with a multiply by a large odd constant (Fibonacci hashing) or a few xor-shift-multiply steps:

C++
#include <cstdint>
#include <iostream>

std::uint64_t mix(std::uint64_t x)              // the finaliser of SplitMix64
{
    x ^= x >> 30; x *= 0xbf58476d1ce4e5b9ULL;
    x ^= x >> 27; x *= 0x94d049bb133111ebULL;
    x ^= x >> 31;
    return x;
}

int main()
{
    const std::uint64_t mask = 16 - 1;               // 16 slots
    std::cout << "keys 0, 16, 32, 48 without mixing go to slots";
    for (std::uint64_t k : { 0, 16, 32, 48 }) std::cout << ' ' << (k & mask);
    std::cout << "\nwith mixing:";
    for (std::uint64_t k : { 0, 16, 32, 48 }) std::cout << ' ' << (mix(k) & mask);
    std::cout << '\n';
}

std::hash<int> on the major standard libraries simply returns the number itself, which is fine for std::unordered_map (prime bucket counts, or its own mixing) but would be a disaster in a power-of-two open-addressing table without a mixing step.

Summary

  • Open addressing stores entries in the array and probes for a free slot on collision.
  • Linear probing is the most cache-friendly but clusters; quadratic probing and double hashing spread entries more.
  • Erasing needs tombstones (or backward-shift deletion) so searches still work.
  • Probe counts grow like 1/(1−α)²: keep the load factor well below 1.
  • Robin Hood hashing evens out probe lengths; power-of-two tables need a mixing step.
