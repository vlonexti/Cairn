Measuring Real Performance

lesson 1.022 of 5 in milestone 16 min1 practice task

Turning theory into measurements - timing code with std::chrono, avoiding the traps of optimisation and noise, doubling experiments that reveal the growth class, how the memory hierarchy and cache lines make some O(n) loops much faster than others, and when constant factors matter.

Timing with std::chrono

Big O predicts how running time grows. Measurements check the prediction and reveal what Big O hides: constant factors and the hardware. std::chrono::steady_clock is the clock to use, because it never jumps backwards when the system time changes.

C++
#include <chrono>
#include <iostream>
#include <vector>

int main()
{
    std::vector<int> data(10'000'000, 1);

    auto start = std::chrono::steady_clock::now();
    long long total = 0;
    for (int x : data) total += x;
    auto stop = std::chrono::steady_clock::now();

    auto us = std::chrono::duration_cast<std::chrono::microseconds>(stop - start).count();
    std::cout << "sum " << total << " in " << us << " microseconds\n";
}

Always use the result (here, print total). An optimising compiler may delete a computation whose result nobody uses, and you end up timing nothing.

Making measurements trustworthy

  • Build with optimisations (Release in Visual Studio, -O2 elsewhere). Debug builds can be ten times slower, and not uniformly so.
  • Repeat and take the minimum or the median. Other programs, the processor's turbo boost and caches all add noise; the fastest of several runs is closest to the true cost.
  • Warm up. The first run pays for page faults and cold caches.
  • Make the input big enough that the run takes at least a few milliseconds; timers are not precise below that.
  • Time only what you mean to time: build the input before starting the clock.

The doubling experiment

To find the growth class of a piece of code, time it at n, 2n, 4n... and look at the ratio between consecutive times:

Ratio when n doubles Growth class
about 1 O(1) or O(log n)
about 2 O(n)
a little more than 2 O(n log n)
about 4 O(n²)
about 8 O(n³)
C++
#include <chrono>
#include <iostream>
#include <vector>

long long countPairsBelow(const std::vector<int>& a, int limit)   // O(n²)
{
    long long count = 0;
    for (std::size_t i = 0; i < a.size(); ++i)
        for (std::size_t j = i + 1; j < a.size(); ++j)
            if (a[i] + a[j] < limit) ++count;
    return count;
}

int main()
{
    double previous = 0;
    for (int n = 1000; n <= 8000; n *= 2)
    {
        std::vector<int> a(n);
        for (int i = 0; i < n; ++i) a[i] = (i * 7919) % 1000;

        double best = 1e18;
        long long result = 0;
        for (int run = 0; run < 3; ++run)
        {
            auto t0 = std::chrono::steady_clock::now();
            result = countPairsBelow(a, 1000);
            auto t1 = std::chrono::steady_clock::now();
            best = std::min(best, std::chrono::duration<double, std::milli>(t1 - t0).count());
        }
        std::cout << "n = " << n << ": " << best << " ms (" << result << " pairs)";
        if (previous > 0) std::cout << ", ratio " << best / previous;
        std::cout << '\n';
        previous = best;
    }
}

The ratios should come out near 4, confirming O(n²). Shared online compilers are noisy, so expect some wobble; on your own machine in a Release build the pattern is clearer.

The memory hierarchy

Big O counts every memory access as one step, but real memory is a hierarchy:

Level Typical size Typical latency
Registers a few hundred bytes under 1 ns
L1 cache 32-64 KB per core about 1 ns
L2 cache 0.5-2 MB per core about 4 ns
L3 cache 8-64 MB shared about 15 ns
Main memory gigabytes about 80-100 ns

Memory moves between levels in cache lines of 64 bytes. Reading one int brings its 15 neighbours along for free, and the processor prefetches the next lines when it sees you walking forward. So:

  • Walking an array in order is very fast: almost every access hits the cache.
  • Jumping around memory (following pointers in a linked list, or indexing randomly) can be 10 to 100 times slower for the same number of steps.
C++
#include <chrono>
#include <iostream>
#include <vector>

int main()
{
    const int n = 2048;
    std::vector<int> grid(n * n, 1);

    auto time = [&](bool rowsFirst) {
        auto t0 = std::chrono::steady_clock::now();
        long long sum = 0;
        for (int a = 0; a < n; ++a)
            for (int b = 0; b < n; ++b)
                sum += rowsFirst ? grid[a * n + b] : grid[b * n + a];
        auto t1 = std::chrono::steady_clock::now();
        std::cout << (rowsFirst ? "row by row:       " : "column by column: ")
                  << std::chrono::duration<double, std::milli>(t1 - t0).count() << " ms (sum " << sum << ")\n";
    };
    time(true);
    time(false);
}

Both loops are O(n²) and add up the same numbers, yet walking column by column is several times slower: each step jumps 8 KB ahead and lands on a new cache line.

When constant factors matter

Big O wins for large inputs, but for small ones the constants decide:

  • Insertion sort (O(n²)) beats merge sort (O(n log n)) below a few dozen elements, which is why real sort functions switch to it for small pieces (lesson 3.01).
  • A linear scan of a small sorted std::vector often beats a std::map lookup, because the vector is one contiguous block.
  • A std::vector usually beats a std::list even for inserting in the middle, until the list is very long, because finding the position in a list means chasing pointers (lesson 1.04).

The rule of thumb: choose the right growth class first, then measure before optimising constants.

Summary

  • Time with std::chrono::steady_clock, in an optimised build, repeated, using the result.
  • The doubling experiment reveals the growth class from the ratio of times.
  • Memory is a hierarchy; contiguous, in-order access is far faster than scattered access.
  • Big O picks the algorithm; measurement and the memory hierarchy decide between algorithms of the same class.
