Greedy Algorithms

lesson 6.011 of 5 in milestone 67 min1 practice task

Building a solution one locally best choice at a time - when greedy works and how to prove it with an exchange argument, interval scheduling by earliest finish time, counting meeting rooms with a sweep, why greedy coin change fails for some coin systems, Huffman coding with a priority queue, the fractional knapsack, and a checklist for spotting greedy problems.

Choose the best-looking option, never look back

A greedy algorithm builds a solution step by step, at each step taking the choice that looks best right now, and never reconsidering it. Dijkstra (always finish the closest vertex), Prim and Kruskal (always take the cheapest safe edge) are greedy. When greedy works, it is usually simple and fast. The hard part is knowing whether it works: for many problems the locally best choice leads to a globally bad answer.

Interval scheduling

You have one meeting room and a list of requested meetings, each with a start and end time. What is the largest number of meetings you can accept, with no two overlapping?

Several greedy rules come to mind: the shortest meeting first, the one that starts first, the one with the fewest conflicts. Only one always works: always pick the meeting that finishes first among those that do not overlap what you have already accepted.

C++
#include <algorithm>
#include <iostream>
#include <vector>

struct Meeting { int start, end; };

int maxMeetings(std::vector<Meeting> m)
{
    std::sort(m.begin(), m.end(), [](const Meeting& a, const Meeting& b) { return a.end < b.end; });
    int count = 0, freeAt = -1;                      // the room is free from this time on
    for (const auto& x : m)
        if (x.start >= freeAt)                       // fits after the last accepted meeting
        {
            ++count;
            freeAt = x.end;
        }
    return count;
}

int main()
{
    std::vector<Meeting> requests{ { 1, 4 }, { 3, 5 }, { 0, 6 }, { 5, 7 }, { 3, 9 }, { 5, 9 }, { 6, 10 }, { 8, 11 }, { 8, 12 }, { 2, 14 }, { 12, 16 } };
    std::cout << maxMeetings(requests) << " meetings\n";
}

Why it is right: the exchange argument. Take any optimal schedule. Its first meeting ends no earlier than the meeting greedy picked first (greedy chose the earliest finish of all). So you can swap the optimal schedule's first meeting for greedy's, and nothing else in it overlaps: it is still valid and just as large. Repeat for the second meeting, and so on. So greedy's schedule is as large as any optimal one.

This is the standard way to prove a greedy algorithm correct: show that any optimal solution can be transformed step by step into the greedy one without getting worse.

How many rooms?

A related question: to hold all the meetings, how many rooms are needed? It is the largest number of meetings happening at the same moment. Sweep through time: turn each meeting into a +1 event at its start and a −1 event at its end, sort the events (ends before starts at the same time, since a room freed at 5 can be used by a meeting starting at 5), and track the running total.

C++
#include <algorithm>
#include <iostream>
#include <utility>
#include <vector>

int roomsNeeded(const std::vector<std::pair<int, int>>& meetings)
{
    std::vector<std::pair<int, int>> events;                 // (time, +1 or -1); -1 sorts before +1
    for (auto [s, e] : meetings) { events.push_back({ s, +1 }); events.push_back({ e, -1 }); }
    std::sort(events.begin(), events.end());
    int now = 0, most = 0;
    for (auto [t, change] : events) most = std::max(most, now += change);
    return most;
}

int main()
{
    std::cout << roomsNeeded({ { 0, 30 }, { 5, 10 }, { 15, 20 }, { 10, 15 }, { 25, 40 } }) << " rooms\n";
}

This sweep line idea (sort events, process them in order, keep a running state) solves many geometric and scheduling problems.

When greedy fails: coin change

To pay 63 cents with US coins (25, 10, 5, 1), take the largest coin that fits, repeatedly: 25 + 25 + 10 + 1 + 1 + 1, six coins, which is optimal. That works for most real currencies, but not for every coin system. With coins 1, 3 and 4, greedy pays 6 as 4 + 1 + 1 (three coins), while 3 + 3 uses two. The greedy choice "take the biggest" closed off the better option. Lesson 6.02 solves coin change correctly for any coins with dynamic programming.

Huffman coding

Text files store each character in 8 bits. If some characters are far more common than others, giving them shorter codes saves space. Huffman coding builds the optimal prefix-free code (no code is the beginning of another, so the bit stream can be decoded unambiguously):

  1. Put every character in a min-heap, weighted by its frequency.
  2. Repeatedly remove the two lightest items and merge them into one with the combined weight.
  3. The merges form a binary tree; a character's code is its path from the root (left = 0, right = 1).

The greedy choice, merging the two rarest items, puts the rarest characters deepest. The total encoded size is the sum of all the merged weights:

C++
#include <functional>
#include <iostream>
#include <map>
#include <queue>
#include <string>
#include <vector>

int main()
{
    std::string text = "abracadabra alakazam";
    std::map<char, long long> freq;
    for (char c : text) ++freq[c];

    std::priority_queue<long long, std::vector<long long>, std::greater<long long>> heap;
    for (auto [c, f] : freq) heap.push(f);
    long long bits = 0;
    while (heap.size() > 1)
    {
        long long a = heap.top(); heap.pop();
        long long b = heap.top(); heap.pop();
        bits += a + b;                       // every character below this merge gets one more bit
        heap.push(a + b);
    }
    std::cout << text.size() << " characters: " << text.size() * 8 << " bits plain, " << bits << " bits with Huffman coding\n";
}

Huffman coding is inside ZIP, gzip, PNG and JPEG, usually after another stage that finds repeated substrings.

The fractional knapsack

A thief can carry 50 kg and may take any fraction of each item (gold dust, not gold bars). Greedy works: sort by value per kilogram and take the best until the bag is full, taking part of the last item. If items cannot be split (the 0/1 knapsack), greedy fails, and lesson 6.03 uses dynamic programming instead.

Spotting greedy problems

  • There is a natural order (by end time, by cost, by ratio) and committing to the best item in that order never hurts.
  • You can sketch an exchange argument: "if an optimal solution did not take the greedy choice, swapping it in would not make it worse".
  • Try small counterexamples first. If greedy fails on a tiny case (like coins 1, 3, 4), switch to dynamic programming.

Summary

  • A greedy algorithm commits to the locally best choice at every step.
  • Prove it with an exchange argument; disprove it with a small counterexample.
  • Interval scheduling: earliest finish first. Rooms needed: a sweep over start and end events.
  • Huffman coding and the fractional knapsack are greedy; coin change with arbitrary coins and the 0/1 knapsack are not.
