Dynamic Programming

lesson 6.022 of 5 in milestone 66 min1 practice task

Solving problems by combining answers to overlapping subproblems - why naive recursion explodes, memoisation (top-down), tabulation (bottom-up), the recipe of state, transition, base cases and order, counting paths in a grid, minimum coins for any coin system, counting the ways to make change, rebuilding the chosen solution, and saving memory by keeping only the rows you need.

The problem with plain recursion

The Fibonacci numbers are defined by F(0) = 0, F(1) = 1 and F(n) = F(n − 1) + F(n − 2). Written directly as recursion:

C++
#include <iostream>

long long calls = 0;

long long fib(int n)
{
    ++calls;
    return n < 2 ? n : fib(n - 1) + fib(n - 2);
}

int main()
{
    for (int n : { 10, 20, 30 })
    {
        calls = 0;
        long long f = fib(n);
        std::cout << "fib(" << n << ") = " << f << " took " << calls << " calls\n";
    }
}

The number of calls grows like 1.6ⁿ: fib(50) would take hours. The reason is that the same subproblems are solved again and again: fib(30) computes fib(28) twice, fib(27) three times, fib(26) five times...

Dynamic programming (DP) applies when a problem has:

  1. optimal substructure: the answer can be built from answers to smaller subproblems, and
  2. overlapping subproblems: the same subproblems come up many times.

It solves each subproblem once and stores the answer.

Memoisation: top-down

Keep the recursion, but remember every result in a table, and look it up before computing:

C++
#include <iostream>
#include <vector>

long long fib(int n, std::vector<long long>& memo)
{
    if (n < 2) return n;
    if (memo[n] != -1) return memo[n];
    return memo[n] = fib(n - 1, memo) + fib(n - 2, memo);
}

int main()
{
    std::vector<long long> memo(91, -1);
    std::cout << "fib(90) = " << fib(90, memo) << '\n';
}

Each value from 2 to 90 is computed once: O(n). Memoisation is the easiest way to turn a correct but slow recursive solution into a fast one.

Tabulation: bottom-up

Or fill the table in an order where every subproblem's inputs are already known, with plain loops:

C++
std::vector<long long> f(n + 1);
f[0] = 0; f[1] = 1;
for (int i = 2; i <= n; ++i) f[i] = f[i - 1] + f[i - 2];

Tabulation avoids recursion (no stack overflow, less overhead) and often reveals that only the last few entries are needed, so the table can shrink: Fibonacci needs only two variables.

The recipe

Every DP solution answers four questions:

  1. State: what does a table entry mean? ("ways[r][c] = the number of paths from the top-left corner to cell (r, c)")
  2. Transition: how is an entry computed from smaller ones? ("ways[r][c] = ways[r-1][c] + ways[r][c-1]")
  3. Base cases: which entries are known directly? ("ways[0][0] = 1; blocked cells have 0")
  4. Order: in what order can the table be filled so the inputs are always ready? ("row by row, left to right")

The state is the creative part. If the transition needs information the state does not hold, add it to the state.

Paths through a grid

A robot moves only right or down through a grid with blocked cells. How many different paths lead from the top-left to the bottom-right corner?

C++
#include <iostream>
#include <string>
#include <vector>

int main()
{
    std::vector<std::string> grid{
        "....",
        ".#..",
        "...#",
        "#..." };
    int rows = 4, cols = 4;
    std::vector<std::vector<long long>> ways(rows, std::vector<long long>(cols, 0));
    for (int r = 0; r < rows; ++r)
        for (int c = 0; c < cols; ++c)
        {
            if (grid[r][c] == '#') continue;                       // no paths through a blocked cell
            if (r == 0 && c == 0) { ways[r][c] = 1; continue; }
            if (r > 0) ways[r][c] += ways[r - 1][c];               // arriving from above
            if (c > 0) ways[r][c] += ways[r][c - 1];               // arriving from the left
        }
    std::cout << ways[rows - 1][cols - 1] << " paths\n";
}

The table has rows × cols entries, each computed in O(1): O(rows × cols), compared with an exponential number of paths to enumerate.

Coin change, done right

Lesson 6.01 showed greedy coin change failing for coins 1, 3, 4. DP solves it for any coins:

  • State: best[a] = the fewest coins that make amount a (or "impossible").
  • Transition: the last coin used is some c; then best[a] = 1 + min over coins c ≤ a of best[a − c].
  • Base case: best[0] = 0.
  • Order: amounts from 0 up.

Remembering which coin achieved each minimum lets you rebuild the actual coins afterwards, a technique that works for any DP: store the choice, then walk back from the final state.

C++
#include <climits>
#include <iostream>
#include <vector>

int main()
{
    std::vector<int> coins{ 1, 3, 4 };
    int amount = 10;
    std::vector<int> best(amount + 1, INT_MAX), lastCoin(amount + 1, -1);
    best[0] = 0;
    for (int a = 1; a <= amount; ++a)
        for (int c : coins)
            if (c <= a && best[a - c] != INT_MAX && best[a - c] + 1 < best[a])
            {
                best[a] = best[a - c] + 1;
                lastCoin[a] = c;
            }

    std::cout << "fewest coins for " << amount << ": " << best[amount] << " (";
    for (int a = amount; a > 0; a -= lastCoin[a]) std::cout << lastCoin[a] << (a - lastCoin[a] > 0 ? " + " : "");
    std::cout << ")\n";
}

O(amount × number of coins). Note that this is pseudo-polynomial: polynomial in the value of the amount, not in the number of digits needed to write it.

Counting, not optimising

How many different ways are there to make 10 from coins 1, 3, 4, if the order of coins does not matter (1 + 3 and 3 + 1 are the same way)? Loop over the coins on the outside: then each combination is built in one fixed order of coins and counted once.

C++
#include <iostream>
#include <vector>

int main()
{
    std::vector<int> coins{ 1, 3, 4 };
    int amount = 10;
    std::vector<long long> ways(amount + 1, 0);
    ways[0] = 1;
    for (int c : coins)
        for (int a = c; a <= amount; ++a) ways[a] += ways[a - c];
    std::cout << ways[amount] << " ways to make " << amount << '\n';
}

Swapping the two loops (amounts outside, coins inside) counts ordered sequences instead: 1 + 3 and 3 + 1 become different. A small change in loop order changes the meaning of the state.

Summary

  • DP solves overlapping subproblems once each and stores the results.
  • Memoisation adds a cache to recursion; tabulation fills a table with loops in a safe order.
  • Design with the recipe: state, transition, base cases, order.
  • Store the choice made at each state to rebuild the actual solution.
  • Coin change and grid paths show both optimising and counting DPs; loop order can change what is counted.
