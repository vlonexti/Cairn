Hash Functions

lesson 2.022 of 5 in milestone 28 min1 practice task

Turning keys into numbers - what a hash function must and should do, from keys to bucket indexes, why naive hashes cluster, polynomial string hashing, FNV-1a, std::hash and how to hash your own types, combining hashes, collisions and the birthday paradox, and hash flooding attacks.

From keys to positions

Binary search finds a key in O(log n). A hash table aims for O(1) on average, by computing where a key should be instead of searching for it. The computation is a hash function: it turns a key (a number, a string, a point) into a big number, the hash, and the table takes it modulo its number of slots, the buckets:

Output
bucket = hash(key) % bucketCount

If every key landed in its own bucket, lookup would be a single step. Different keys that land in the same bucket are a collision, and lessons 2.03 and 2.04 show the two ways to handle them.

What a hash function needs

It must be deterministic and consistent with equality: equal keys must always give equal hashes. If a == b but hash(a) != hash(b), the table looks in the wrong bucket and never finds a. (The reverse is not required: different keys may share a hash.)

It should spread keys evenly over the buckets, including keys that are similar or follow patterns, like "item1", "item2", ... or multiples of 1000.

It should be fast, since every lookup computes it.

Bad hashes and what goes wrong

Summing the characters of a string is a classic bad hash: "stop", "pots", "tops" and "spot" all collide, and every short word lands in a few hundred buckets at most, however big the table is.

C++
#include <iostream>
#include <set>
#include <string>
#include <vector>

unsigned long long sumHash(const std::string& s)
{
    unsigned long long h = 0;
    for (unsigned char c : s) h += c;
    return h;
}

unsigned long long polyHash(const std::string& s)
{
    unsigned long long h = 0;
    for (unsigned char c : s) h = h * 31 + c;        // position matters
    return h;
}

int main()
{
    std::vector<std::string> keys;
    for (int i = 0; i < 10000; ++i) keys.push_back("user" + std::to_string(i));

    for (auto [name, hash] : { std::pair{ "sum of characters", &sumHash }, std::pair{ "polynomial", &polyHash } })
    {
        std::set<unsigned long long> buckets;
        for (const auto& k : keys) buckets.insert(hash(k) % 10007);
        std::cout << name << ": 10000 keys used " << buckets.size() << " of 10007 buckets\n";
    }
}

Placing 10,000 keys in 10,007 buckets at random would use about 63% of them (some buckets get two or three keys, so others stay empty). The polynomial hash does even better on these regular keys, using about 80%. The sum uses fewer than a hundred buckets, so its chains would be over a hundred keys long.

Integer keys have their own trap: key % bucketCount is a fine hash for random integers, but if the keys are all multiples of 8 and the bucket count is 64, only 8 buckets are ever used. That is why some tables use a prime number of buckets, and others scramble the integer first.

Polynomial string hashing

The polynomial hash treats the string as the digits of a number in base B:

hash(s) = s₀·Bⁿ⁻¹ + s₁·Bⁿ⁻² + ... + sₙ₋₁

computed left to right as h = h * B + c (Horner's rule). With unsigned arithmetic the result wraps modulo 2⁶⁴, which is well defined in C++. Java's String.hashCode is exactly this with B = 31 and 32-bit wrapping.

A useful property: the hash of a sliding window can be updated in O(1) by removing the first character's contribution and adding the next one. Lesson 6.04 uses this rolling hash for string matching (the Rabin-Karp algorithm).

FNV-1a

FNV-1a is a simple, fast and well-spread hash for bytes: start from a fixed "offset basis", and for each byte, XOR it in and multiply by a fixed prime.

C++
#include <cstdint>
#include <iostream>
#include <string_view>

std::uint64_t fnv1a(std::string_view text)
{
    std::uint64_t h = 14695981039346656037ULL;      // the 64-bit offset basis
    for (unsigned char c : text)
    {
        h ^= c;
        h *= 1099511628211ULL;                       // the 64-bit FNV prime
    }
    return h;
}

int main()
{
    for (std::string_view s : { "", "a", "b", "stop", "pots" }) std::cout << '"' << s << "\" -> " << fnv1a(s) << '\n';
}

Notice how "a" and "b" give completely different hashes even though they differ by one bit. That avalanche behaviour is what makes a hash spread similar keys apart.

std::hash and your own types

std::unordered_map and std::unordered_set use std::hash<Key>, which the library provides for numbers, pointers, std::string and std::string_view. For your own types, provide a hash yourself and an operator==. The simplest way is a function object passed as a template argument:

C++
#include <cstddef>
#include <functional>
#include <iostream>
#include <unordered_set>

struct Point
{
    int x, y;
    bool operator==(const Point&) const = default;
};

std::size_t hashCombine(std::size_t seed, std::size_t value)
{
    return seed ^ (value + 0x9e3779b97f4a7c15ULL + (seed << 6) + (seed >> 2));
}

struct PointHash
{
    std::size_t operator()(const Point& p) const
    {
        return hashCombine(std::hash<int>{}(p.x), std::hash<int>{}(p.y));
    }
};

int main()
{
    std::unordered_set<Point, PointHash> visited;
    for (int i = 0; i < 5; ++i) visited.insert({ i % 3, i % 2 });
    std::cout << visited.size() << " distinct points; contains (1,1)? " << visited.count({ 1, 1 }) << '\n';
}

Combining hashes with plain XOR (hx ^ hy) is tempting but bad: (1, 2) and (2, 1) collide, and so does every point with x == y (they all hash to 0). The hashCombine formula above (from the Boost library) mixes the bits so that order matters.

Collisions are unavoidable: the birthday paradox

How many people must be in a room before two probably share a birthday? Only 23. In general, with m buckets, you expect the first collision after about √(πm/2) keys. With a million buckets, that is about 1,250 keys. Collisions are not a sign of a bad hash; they are certain, and a hash table must handle them. A good hash only keeps them evenly spread.

C++
#include <iostream>
#include <random>
#include <unordered_set>

int main()
{
    std::mt19937_64 rng(42);
    const unsigned long long buckets = 1'000'000;
    double total = 0;
    for (int trial = 0; trial < 200; ++trial)
    {
        std::unordered_set<unsigned long long> used;
        int keys = 0;
        while (used.insert(rng() % buckets).second) ++keys;
        total += keys + 1;
    }
    std::cout << "first collision after " << total / 200 << " keys on average (theory: about 1253)\n";
}

Hash flooding

If an attacker knows your hash function, they can send thousands of keys that all land in the same bucket, turning every O(1) operation into O(n) and a web server's request handling into O(n²). This hash flooding attack took down many web frameworks in 2011. Defences include seeded hash functions (SipHash, with a random key chosen at start-up), which Python, Rust and many others use by default, and tables that switch a long bucket into a balanced tree (Java's HashMap). std::hash is not seeded on the common implementations, so do not use std::unordered_map with keys chosen by untrusted users in performance-critical servers without care.

Summary

  • A hash function maps a key to a number; hash % buckets picks the bucket.
  • It must agree with equality, and should spread similar keys evenly and be fast.
  • Polynomial hashing and FNV-1a are simple, good string hashes; combine field hashes with a mixing formula, not plain XOR.
  • Collisions are certain (the birthday paradox): tables must handle them.
  • Unseeded hashes are open to flooding attacks; seeded hashes like SipHash defend against them.
