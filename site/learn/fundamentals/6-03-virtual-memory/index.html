Virtual Memory

lesson 6.033 of 6 in milestone 65 min1 practice task

Every process sees its own private, enormous row of addresses - virtual memory. The CPU translates each virtual address to a real place in RAM through page tables the kernel keeps, in pages of 4 KB. That keeps processes apart, lets programs use more memory than there is RAM, and makes a bad pointer crash only its own program.

The problem

Lesson 4.03 described memory as one long row of numbered bytes. But many processes run at once. If they all shared that one row:

  • one program could read another's passwords, or overwrite its data by accident;
  • two programs that both expect to start at address 0x400000 would collide;
  • a program could not use more memory than happened to be free in one piece.

The trick: every process gets its own addresses

With virtual memory, every process sees its own private row of addresses, starting near 0 and stretching far beyond the real RAM (on 64-bit systems, up to 128 TB or more). These are virtual addresses.

When the program reads address 0x7ffe1234, the CPU translates it to a physical address - a real place in RAM - using a table the kernel keeps for that process. The program never sees physical addresses at all.

Both processes have a "page 0" at the same virtual address, but they land in different places in RAM. Neither can even name the other's memory.

Pages

Translating each byte separately would need an impossibly large table, so memory is translated in blocks called pages, usually 4 KiB (4,096 bytes). A virtual address splits in two:

Part For a 4 KiB page Meaning
Page number everything above the lowest 12 bits which page: looked up in the page table
Offset the lowest 12 bits (2¹² = 4096) where in the page: copied as it is

Example: virtual address 0x3A7C with 4 KiB pages has page number 0x3 and offset 0xA7C. If the page table says virtual page 3 lives in physical frame 0x51, the physical address is 0x51A7C.

The CPU does the lookup in hardware on every memory access, with a small cache of recent translations (the TLB) so it costs almost nothing.

What it makes possible

Feature How
Isolation A process's page table only contains its own pages. Touching an address that is not mapped stops the program: a segmentation fault (Linux, macOS) or access violation (Windows)
Protection Each page has permissions: read, write, execute. Code pages are read-only, so a bug cannot overwrite the program's own instructions
More memory than RAM Pages not used lately can be written out to disk (swap or the page file) and the RAM reused. If the program touches that page again, the kernel brings it back. Slow, but it works
Sharing Two processes running the same program can share the same physical pages of code, read-only
Lazy loading When a program starts, its pages are only read from disk when first touched
Why a crash says "segmentation fault"

When a program follows a bad pointer - for example address 0, the null pointer - the CPU finds no mapping for that page and raises a fault. The kernel stops the program. Address 0 is deliberately left unmapped in every process so that this common bug is caught at once instead of silently corrupting memory.
