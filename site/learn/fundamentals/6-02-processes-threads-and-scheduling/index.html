Processes, Threads and Scheduling

lesson 6.022 of 6 in milestone 65 min2 practice tasks

A running program is a process - its code, its memory, and its open files. Inside it, threads are the separate lines of execution. The scheduler shares the CPU cores by giving each thread a short time slice and switching between them hundreds of times a second, which is why many programs seem to run at once even on one core.

Program vs. process

A program is a file on disk: machine code and data (3.05). A process is a program while it runs: the operating system has loaded it into memory and keeps track of it.

A process has Such as
Its own memory its code, its variables, its stack (the Assembly course explains the stack)
Its registers' values including the program counter: where it is up to
Open files and connections file handles, network sockets
An ID the PID, a number
An owner the user who started it, which decides what it may access

Run the same program twice (two browser windows from the same app, say) and you get two processes from one program. You can see the processes on your computer with Task Manager on Windows, Activity Monitor on macOS, or ps and top on Linux.

Threads

A process starts with one thread: one line of execution, with its own program counter, registers and stack, working through the code. A process can start more threads, which run at the same time and share the process's memory.

A browser, for example, may use one thread to draw the page, another to download images, another to run a page's JavaScript. On a CPU with several cores (1.05), threads really do run simultaneously, one per core.

Shared memory is tricky

Two threads changing the same variable at the same moment can lose updates, a bug called a race condition. If two threads each do count = count + 1 (read, add, write back) at the same time, both may read 5 and both write 6. Programs use locks to let only one thread at a time change shared data.

Sharing the CPU: the scheduler

A laptop has a handful of cores but hundreds of threads. How do they all run? The kernel's scheduler shares the cores out:

  1. Pick a thread that is ready to run and give it a core.
  2. Let it run for a time slice, a few milliseconds.
  3. A timer interrupt (a signal from hardware that makes the CPU jump into the kernel) ends the slice.
  4. Save that thread's registers, pick the next thread, load its registers, and let it run. This is a context switch.
sequenceDiagram
    participant CPU as One CPU core
    participant A as Thread A
    participant B as Thread B
    participant C as Thread C
    A->>CPU: runs for a time slice
    Note over CPU: timer interrupt: save A, load B
    B->>CPU: runs for a time slice
    Note over CPU: save B, load C
    C->>CPU: runs
    Note over CPU: save C, load A
    A->>CPU: carries on where it stopped

Because this happens hundreds of times a second, everything seems to run at once, even on a single core: that is multitasking. Each thread carries on exactly where it stopped, because its registers, including the program counter, were saved and restored.

Waiting threads

Most threads are not running at all, most of the time: they are waiting - for a key press, a network reply, a file read, a timer. The scheduler only gives cores to threads that are ready.

stateDiagram-v2
    [*] --> Ready
    Ready --> Running: scheduler picks it
    Running --> Ready: its time slice ends
    Running --> Waiting: asks for input, a file, the network...
    Waiting --> Ready: the data arrived
    Running --> [*]: it finishes

That is why a computer with 300 threads can sit at 2% CPU: nearly all of them are waiting.

Priorities

Schedulers do not treat every thread the same. The thread drawing your mouse pointer or playing music gets priority over a background update, so the computer feels responsive. Modern schedulers also decide which core suits a thread best; phone and laptop chips mix fast "performance" cores and low-power "efficiency" cores.
