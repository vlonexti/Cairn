The Memory Hierarchy

lesson 4.066 of 6 in milestone 45 min1 practice task

Memory that is fast is small and expensive; memory that is big is slow. So computers stack several kinds - registers, caches, RAM, SSD - and keep what is used now close to the CPU. Caches make programs that use nearby data much faster than programs that jump around.

Fast, small, expensive; slow, big, cheap

A CPU core can do an addition in well under a nanosecond (a billionth of a second). Fetching a number from RAM takes around 100 nanoseconds: hundreds of additions' worth of waiting. If the CPU went to RAM for everything, it would spend almost all its time waiting.

The answer is a hierarchy: several layers of memory, each bigger and slower than the one above.

Level Typical size Time to get data If an addition took 1 second...
Registers a few hundred bytes under 1 ns 1 second
L1 cache 32 to 64 KB per core about 1 ns a few seconds
L2 cache 256 KB to 2 MB per core about 4 ns about 15 seconds
L3 cache 8 to 64 MB, shared about 15 ns about a minute
RAM 8 to 64 GB about 100 ns about 6 minutes
SSD 256 GB to 4 TB about 50,000 ns about 2 days
Hard drive several TB about 5,000,000 ns about 6 months
The internet everything about 50,000,000 ns about 5 years

(The times are rough; what matters is the jumps of 10 to 1000 times between levels.)

Caches

A cache is a small, fast memory that keeps copies of recently used data from the slower memory below it. When the CPU wants an address:

  • if a copy is in the cache, that is a cache hit: fast;
  • if not, a cache miss: the CPU fetches it from the next level down, and keeps a copy in the cache in case it is needed again.

Caches do not fetch one byte at a time. They fetch a whole cache line, usually 64 bytes, because programs tend to use data that sits next to what they just used.

Locality: why it works

Caches work because programs usually have locality:

  • Temporal locality: data used now is likely to be used again soon (a loop counter, a running total).
  • Spatial locality: data next to what is used now is likely to be used soon (the next item of an array).

This has a real effect on how fast code runs. Adding up a big grid of numbers row by row reads memory in order, so every cache line fetched is fully used. Adding it up column by column jumps a whole row ahead each step, uses one number from each 64-byte line, and can be several times slower - same additions, same answer, different order in memory.

Data structure Memory pattern Cache behaviour
Array or list of numbers, read in order One long run Excellent
Linked list (each item points to the next, anywhere in memory) Jumps around Poor
Grid read row by row In order Excellent
Grid read column by column Jumps by a row each time Poor for big grids
Disks have caches too

The same idea repeats at every level: the operating system keeps recently used parts of files in RAM (the "disk cache"), and web browsers keep recently downloaded pictures on disk. Keep what is used now somewhere faster.
