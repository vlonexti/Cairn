Fractions and Floating Point

lesson 3.033 of 5 in milestone 35 min1 practice task

Numbers with a fractional part are stored in floating point - like scientific notation, in binary - with a fixed number of significant bits. Many simple decimals such as 0.1 have no exact binary form, so 0.1 + 0.2 is not exactly 0.3. Money is safer in whole cents.

Binary fractions

Places to the right of a binary point keep halving:

Place ½ ¼ ⅛ 1/16
Worth 0.5 0.25 0.125 0.0625

So 0.101 in binary is 0.5 + 0.125 = 0.625, and 10.11 is 2 + 0.5 + 0.25 = 2.75.

Some fractions are easy: 0.5, 0.25, 0.75. But try 0.1 (one tenth). In decimal, 1/3 goes on forever: 0.3333... In binary, 1/10 goes on forever:

Output
0.1 (decimal) = 0.000110011001100110011... (binary, repeating forever)

A computer has to stop somewhere, so it stores the nearest value it can. 0.1 inside a computer is really 0.1000000000000000055511151231257827...

Floating point: scientific notation in binary

Scientists write very large and very small numbers as a few digits and a power of 10: 6.02 × 10²³, or 1.6 × 10⁻¹⁹. Computers do the same in binary. A floating-point number has three parts:

Part Meaning 64-bit (double) 32-bit (float)
Sign positive or negative 1 bit 1 bit
Exponent the power of 2: where the point "floats" to 11 bits 8 bits
Fraction (mantissa) the significant digits 52 bits 23 bits

This is the IEEE 754 standard (1985), used by every modern computer. A 64-bit "double" keeps about 15 to 17 significant decimal digits; a 32-bit "float" about 7. Python's float is a double.

The point floats: the same 52 bits of digits can describe 0.000000001234 or 1,234,000,000,000 - big and small numbers, but always with the same number of significant digits.

The famous surprise

Python
print(0.1 + 0.2)          # 0.30000000000000004
print(0.1 + 0.2 == 0.3)   # False

Neither 0.1 nor 0.2 is stored exactly, and their tiny errors add up to a result that is not the stored value of 0.3. This is not a Python bug: C, Java, JavaScript and every language that uses the hardware's floating point give the same answer.

Lessons from it:

  • Never compare floating-point numbers with ==. Check whether they are close: abs(a - b) < 1e-9.
  • Don't use floats for money. £0.10 a hundred times should be £10.00 exactly. Store whole pennies (cents) as integers instead, or use a decimal type (Python's decimal, C#'s decimal).
  • Large integers lose precision too. A double holds every integer exactly only up to 2⁵³ (about 9 quadrillion). Above that, it starts skipping numbers.
Special values

Floating point has values that are not ordinary numbers: inf (infinity, from 1.0 / 0.0 in many languages), -inf, and nan ("not a number", from 0.0 / 0.0). nan is not even equal to itself.

Fixed point

Some programs avoid floating point entirely and use fixed point: an integer that counts in small units. Money in cents is fixed point (two decimal places). Old games and many small chips with no floating-point hardware store positions in 1/256ths of a pixel. Integers are exact, so fixed point never surprises you; it just has a fixed range and precision.
