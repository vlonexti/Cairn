Compilers, Interpreters and Virtual Machines

lesson 5.033 of 6 in milestone 55 min1 practice task

A compiler translates a whole program into machine code before it runs; an interpreter reads the program and carries it out as it goes. Many languages do both - Java and C# compile to bytecode for a virtual machine, Python compiles to bytecode for its interpreter, and JavaScript engines compile the hot parts while running.

Two ways to run a language

The CPU only runs machine code (4.05). So a program in any other language has to become machine code somehow. There are two basic strategies.

Compile first

A compiler translates the whole program into machine code ahead of time. You get an executable file that runs directly on the CPU, with no translator needed any more.

flowchart LR
    S["Source code<br/>main.c"] -->|compiler| O["Machine code<br/>(object file)"] -->|linker| E["Executable<br/>program"] -->|run| CPU

C, C++, Rust, Go, Swift and Fortran work this way. The compilation itself takes a moment, but the result runs as fast as the hardware allows. The linker joins your code with code from libraries (such as the code behind printf) into one program.

Interpret

An interpreter is a program that reads your program and carries it out, step by step, while it runs. There is no separate machine-code file: the interpreter, which is itself a compiled program, does what each line says.

flowchart LR
    S["Source code<br/>main.py"] --> I["Interpreter<br/>(a running program)"] --> R["The program's effects"]

Early BASIC was interpreted, and so are shell scripts. You can start instantly and change code without rebuilding, but every step costs extra work, so it is usually much slower.

The trade-off

Compiled Interpreted
Speed of running Fast: machine code Slower: an interpreter does the work
Start after a change Build first Immediately
Errors in the code found Many before it runs Often only when that line runs
Runs on The CPU family it was built for Anywhere the interpreter runs

The middle way: bytecode and virtual machines

Most popular languages today do a bit of both.

Bytecode is a compact, made-up instruction set for an imaginary computer - a virtual machine (VM). The language is compiled to bytecode once; then a program on the real computer runs the bytecode.

Language Compiles to Which is run by
Java (1995) Java bytecode (.class files) The Java Virtual Machine (JVM)
C# (2000) .NET intermediate language The .NET runtime
Python (1991) Python bytecode (.pyc files, done automatically) The Python interpreter's bytecode loop
WebAssembly (2017) Wasm bytecode Every web browser

The bytecode is the same on every computer, so one compiled Java program runs on Windows, macOS and Linux: "write once, run anywhere". The VM is what differs per machine.

You can see Python's bytecode yourself:

Python
import dis

def add(a, b):
    return a + b

dis.dis(add)

LOAD_FAST, BINARY_OP, RETURN_VALUE: a tiny instruction set, very like the tiny computer of 4.04, which Python's interpreter fetches, decodes and executes in a loop.

Just-in-time compilation

A JIT (just-in-time) compiler watches a program while it runs, finds the parts that run most often - the hot loops - and compiles those to real machine code on the spot. The JVM, .NET and every JavaScript engine (Chrome's V8, Firefox's SpiderMonkey) do this, which is why Java, C# and JavaScript can be nearly as fast as compiled C for long-running programs.

    JS["JavaScript source"] --> P["Parse to bytecode"] --> I["Interpret it,<br/>counting what runs often"] --> H{"Hot?"}
    H -->|yes| J["JIT: compile to<br/>machine code"] --> CPU
    H -->|no| I

How this site runs your code

Xenon uses all of these. C, C++, Rust and assembly are compiled (on Compiler Explorer, or on your computer in the desktop app) and the machine code is run. Java and C# are compiled to bytecode and run by their VMs. Python runs in its interpreter. JavaScript and TypeScript run in your browser's JIT engine.
