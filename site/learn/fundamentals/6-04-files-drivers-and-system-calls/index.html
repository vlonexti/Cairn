Files, Drivers and System Calls

lesson 6.044 of 6 in milestone 65 min1 practice task

A disk only stores numbered blocks; the file system turns them into named files in folders. Drivers let the kernel talk to each kind of device. Programs reach both through system calls - open, read, write, close - and running a program is itself a system call that loads an executable file into a new process.

Disks store blocks, not files

An SSD or hard drive only knows how to store and fetch blocks: fixed-size chunks (often 4 KiB) with numbers, 0, 1, 2, and so on. It has no idea what a file or a folder is.

The file system is the kernel's way of organising blocks into files:

It keeps track of So that
Which blocks hold each file's bytes a file can be spread over many blocks, anywhere on the disk
Each file's name, size, dates and permissions ls -l or Explorer can show them
Folders (directories), which are lists of names paths like /home/ada/notes.txt or C:\Users\Ada\notes.txt can be followed
Which blocks are free new files can be written

Common file systems: NTFS (Windows), APFS (macOS), ext4 (Linux), FAT32 and exFAT (USB sticks and memory cards, readable everywhere).

Deleting a file usually just marks its blocks as free; the bytes stay until something overwrites them, which is why deleted files can sometimes be recovered.

Drivers

Every model of disk, graphics card, Wi-Fi chip or printer is controlled differently. A driver is the piece of kernel-mode code that knows how to talk to one kind of device and presents it to the rest of the kernel in a standard way. Install a new graphics card and you install its driver; the kernel and every app then use it through the same interface as any other.

System calls: the programmer's door

Programs reach files, devices and everything else through system calls. On Linux, a few of the most used:

Number (x86-64) Name Does
0 read read bytes from an open file or device
1 write write bytes
2 open open a file by name, get back a small number: a file descriptor
3 close close it
9 mmap map memory pages into the process
57 fork make a copy of this process
59 execve replace this process's program with another
60 exit end the process

A file descriptor is just a number the kernel gives back to name an open file. Every process starts with three already open: 0 is standard input, 1 standard output, 2 standard error. That is why write(1, ...) prints (5.06): standard output is just file 1, and it might be a terminal, a file, or a pipe to another program - the program does not need to know which.

Windows has the same ideas with different names (CreateFile, ReadFile, WriteFile, handles instead of descriptors), and programs normally reach them through Windows' own libraries rather than raw system call numbers.

In Python, open, read and write are thin wrappers around these calls:

Python
with open("notes.txt", "w") as f:     # open(): a system call; the kernel gives back a descriptor
    f.write("first line\n")           # write(): copies bytes into the file system
with open("notes.txt") as f:
    print(f.read(), end="")           # read() from the file, then write() to descriptor 1

Running a program

Starting a program is a system call too. On Linux, a shell runs python3 main.py like this:

  1. fork: copy the shell's process. Now there are two.
  2. In the copy, execve("/usr/bin/python3", ...): the kernel reads the executable file (an ELF file, 3.05), sets up fresh virtual memory (6.03), maps the code and data into it, sets the program counter to the program's entry point, and lets the scheduler (6.02) run it.
  3. The original shell waits until the new process calls exit, then prints its prompt again.

Windows does the equivalent in one call (CreateProcess). Either way, the operating system turns a file of bytes into a running process.
