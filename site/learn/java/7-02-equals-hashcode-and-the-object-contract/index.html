equals, hashCode and the Object Contract

lesson 7.022 of 5 in milestone 75 min2 practice tasks

What every class inherits from Object and the rules that come with it - equals and its five properties, why hashCode must agree with equals, compareTo consistent with equals, toString, what records write for you, and the bugs that appear in HashSet and HashMap when the rules are broken.

What every object has

Every class extends Object and so has equals, hashCode, toString, getClass and a few more. The first three are meant to be overridden, but they come with a contract: rules that collections and libraries rely on. Break them and HashMap, HashSet and contains silently misbehave.

equals

== on objects compares references: are these the same object? equals should compare values: do these two objects mean the same thing? The default equals is just ==.

The contract says equals must be:

  1. reflexive: x.equals(x) is true;
  2. symmetric: x.equals(y) exactly when y.equals(x);
  3. transitive: if x.equals(y) and y.equals(z), then x.equals(z);
  4. consistent: the answer does not change unless the objects change;
  5. x.equals(null) is false.
Java
import java.util.Objects;

public class Main {
    static final class Point {
        private final int x, y;
        Point(int x, int y) { this.x = x; this.y = y; }

        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (!(o instanceof Point other)) return false;   // also false for null
            return x == other.x && y == other.y;
        }

        @Override
        public int hashCode() {
            return Objects.hash(x, y);
        }

        @Override
        public String toString() { return "(" + x + ", " + y + ")"; }
    }

    public static void main(String[] args) {
        Point a = new Point(1, 2), b = new Point(1, 2);
        System.out.println((a == b) + " " + a.equals(b));   // false true
    }
}

Make such classes final (or compare with getClass()), otherwise a subclass that adds fields cannot keep equals symmetric.

hashCode must agree

A HashMap or HashSet first uses hashCode to pick a bucket, then equals inside it. So the rule is: equal objects must have equal hash codes. (Unequal objects may share one; that only costs speed.) Override equals without hashCode and this happens:

Java
import java.util.HashSet;
import java.util.Set;

public class Main {
    static final class Tag {
        final String name;
        Tag(String name) { this.name = name; }
        @Override public boolean equals(Object o) { return o instanceof Tag t && t.name.equals(name); }
        // no hashCode: each object keeps the default, based on its identity
    }

    public static void main(String[] args) {
        Set<Tag> tags = new HashSet<>();
        tags.add(new Tag("java"));
        System.out.println(tags.contains(new Tag("java")));   // almost certainly false
    }
}

Objects.hash(field1, field2, ...) is the easy, correct way to write hashCode. Use the same fields as equals.

Do not change keys

If a field used by hashCode changes while the object is in a HashSet or is a HashMap key, the object is now in the wrong bucket and cannot be found or removed. Make key classes immutable.

compareTo consistent with equals

Comparable.compareTo (lesson 4.03) defines natural order. It should return 0 exactly when equals is true; TreeSet and TreeMap use compareTo instead of equals, so if two different objects compare as 0, a TreeSet keeps only one of them.

Java
import java.util.Comparator;
import java.util.List;
import java.util.TreeSet;

public class Main {
    record Person(String name, int age) {}

    public static void main(String[] args) {
        var byAge = new TreeSet<Person>(Comparator.comparingInt(Person::age));
        byAge.addAll(List.of(new Person("Ada", 36), new Person("Alan", 36)));
        System.out.println(byAge.size());            // 1: same age counts as "equal"

        var full = new TreeSet<Person>(Comparator.comparingInt(Person::age).thenComparing(Person::name));
        full.addAll(List.of(new Person("Ada", 36), new Person("Alan", 36)));
        System.out.println(full.size());             // 2
    }
}

Records do it for you

A record (lesson 3.05) writes equals, hashCode and toString from its components automatically and correctly. For a plain data class, a record is the simplest way to get the contract right. (Arrays inside a record are compared by reference, so prefer List components.)

toString

toString is used by string concatenation, println, debuggers and logs. Return something short that identifies the object; the default ClassName@1b6d3586 helps nobody.
