Threads and Concurrency

lesson 6.044 of 5 in milestone 65 min1 practice task

Running work at the same time - threads and Runnable, joining, race conditions and why count++ is unsafe, synchronized and locks, atomic variables and concurrent collections, ExecutorService and Future, CompletableFuture, virtual threads, deadlock, and the rule of sharing as little mutable state as possible.

Threads

The practice sandbox runs every program on a single thread, so the examples in this lesson are for reading and for running with your own JDK (java Main.java). The practice task shows how concurrent code is designed so that its logic can be tested without real threads.

A thread is an independent path of execution. A program starts with one (main); more threads let it use several processor cores, or keep working while one task waits:

Java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            for (int i = 1; i <= 3; i++) System.out.println("worker " + i);
        });
        worker.start();                    // runs at the same time as main
        System.out.println("main continues");
        worker.join();                     // wait for it to finish
        System.out.println("worker finished");
    }
}

start() begins the new thread; calling run() directly would just run the code on the current thread. The order of output from different threads is not guaranteed.

Race conditions

When threads share mutable data, their steps interleave unpredictably. count++ is really read, add one, write back; two threads can read the same old value, and one increment is lost:

Java
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    static int unsafeCount = 0;
    static int syncCount = 0;
    static final AtomicInteger atomicCount = new AtomicInteger();

    static synchronized void incrementSync() { syncCount++; }

    public static void main(String[] args) throws InterruptedException {
        Runnable work = () -> {
            for (int i = 0; i < 100_000; i++) {
                unsafeCount++;                 // a race
                incrementSync();               // one thread at a time
                atomicCount.incrementAndGet(); // an atomic hardware operation
            }
        };
        Thread a = new Thread(work), b = new Thread(work);
        a.start(); b.start();
        a.join(); b.join();
        System.out.println((unsafeCount <= 200_000) + " " + syncCount + " " + atomicCount.get());
    }
}

synchronized lets only one thread at a time run the method (or a synchronized (lock) { ... } block) for the same lock object, and makes changes visible to the next thread that takes the lock. AtomicInteger, AtomicLong and LongAdder do single-variable updates without locks.

Thread-safe collections

ArrayList and HashMap are not safe for concurrent changes. Use the java.util.concurrent collections:

Instead of Use
HashMap ConcurrentHashMap (with merge, compute for atomic updates)
ArrayList with rare writes CopyOnWriteArrayList
a queue between threads ArrayBlockingQueue, LinkedBlockingQueue

Executors

Creating threads by hand is low level. An ExecutorService keeps a pool of threads and runs tasks you submit; Callable tasks return a result through a Future:

Java
import java.util.*;
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        try (ExecutorService pool = Executors.newFixedThreadPool(4)) {
            List<Future<Long>> results = new ArrayList<>();
            for (int part = 0; part < 4; part++) {
                long from = part * 250_000L, to = from + 250_000;
                results.add(pool.submit(() -> sumOfSquares(from, to)));   // a Callable<Long>
            }
            long total = 0;
            for (Future<Long> f : results) total += f.get();               // waits for each result
            System.out.println(total == sumOfSquares(0, 1_000_000));
        }                                                                  // closing waits for the tasks and shuts the pool down
    }

    static long sumOfSquares(long from, long to) {
        long s = 0;
        for (long i = from; i < to; i++) s += i * i % 1000;
        return s;
    }
}

Splitting work so that each task computes its own result, and combining the results at the end, avoids shared mutable state entirely. That is the safest kind of concurrency.

CompletableFuture and virtual threads

CompletableFuture chains asynchronous steps:

Java
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) {
        CompletableFuture<String> user = CompletableFuture.supplyAsync(() -> slow("Ada", 100));
        CompletableFuture<Integer> score = CompletableFuture.supplyAsync(() -> slow(42, 100));
        String summary = user.thenCombine(score, (u, s) -> u + " scored " + s)
                             .exceptionally(e -> "failed: " + e.getMessage())
                             .join();
        System.out.println(summary);

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {      // Java 21: virtual threads
            for (int i = 0; i < 10_000; i++) {
                int n = i;
                executor.submit(() -> slow(n, 10));                             // ten thousand cheap threads
            }
        }
        System.out.println("10 000 waiting tasks done");
    }

    static <T> T slow(T value, long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return value;
    }
}

Virtual threads (Java 21) are very cheap threads managed by the JVM. They make it practical to give each waiting task (a web request, a database call) its own thread, written as simple blocking code.

Deadlock and other dangers

  • Deadlock: thread A holds lock 1 and waits for lock 2, while B holds lock 2 and waits for lock 1. Both wait forever. Always take locks in the same order, and hold them briefly.
  • Visibility: without synchronisation, a change made by one thread may never be seen by another. Use volatile for simple flags, or locks and atomics.
  • InterruptedException: it means someone asked the thread to stop. Do not swallow it; finish up, or restore the flag with Thread.currentThread().interrupt().

The best concurrency advice is to avoid sharing mutable state: use immutable objects (records), give each task its own data, and communicate through concurrent queues or futures.

Testable concurrent code

Code that creates its own threads is hard to test: the results depend on timing. Instead, let the caller pass in an Executor (the interface behind every thread pool). Production code passes a real pool; a test passes Runnable::run, which runs each task immediately on the calling thread, so the result is the same every time:

Java
static long sumInChunks(int[] data, int chunks, Executor executor) {
    List<CompletableFuture<Long>> parts = new ArrayList<>();
    for (int c = 0; c < chunks; c++) {
        int from = c * data.length / chunks, to = (c + 1) * data.length / chunks;
        parts.add(CompletableFuture.supplyAsync(() -> sum(data, from, to), executor));
    }
    return parts.stream().mapToLong(CompletableFuture::join).sum();
}

sumInChunks(data, 8, Executors.newFixedThreadPool(8));   // in the program
sumInChunks(data, 8, Runnable::run);                      // in a test: deterministic
