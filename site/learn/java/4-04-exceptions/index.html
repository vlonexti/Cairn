Exceptions

lesson 4.044 of 5 in milestone 45 min1 practice task

Throwing and catching exceptions, the exception hierarchy, checked versus unchecked exceptions and the throws clause, multi-catch, finally, try-with-resources, custom exception classes with causes, stack traces, and good practice for validating arguments and handling errors.

throw and catch

When a method cannot do its job it throws an exception. The exception travels up the call stack until a catch block handles it; if none does, the program stops and prints a stack trace.

Java
public class Main {
    public static void main(String[] args) {
        String[] inputs = {"42", "abc", "-5"};
        for (String input : inputs) {
            try {
                int age = parseAge(input);
                System.out.println("age " + age);
            } catch (NumberFormatException e) {
                System.out.println("'" + input + "' is not a number");
            } catch (IllegalArgumentException e) {
                System.out.println(e.getMessage());
            }
        }
    }

    static int parseAge(String text) {
        int age = Integer.parseInt(text);       // may throw NumberFormatException
        if (age < 0) throw new IllegalArgumentException("age cannot be negative: " + age);
        return age;
    }
}

Catch blocks are tried in order, so put specific types first: NumberFormatException is a subclass of IllegalArgumentException, so the other order would not compile (the second catch could never run).

The hierarchy

flowchart TD
  T[Throwable] --> E[Exception]
  T --> ER[Error: OutOfMemoryError, StackOverflowError]
  E --> RE[RuntimeException: unchecked]
  E --> CE[IOException, other checked exceptions]
  RE --> IAE[IllegalArgumentException]
  RE --> ISE[IllegalStateException]
  RE --> NPE[NullPointerException]
  RE --> IOOBE[IndexOutOfBoundsException]
  • Unchecked exceptions (RuntimeException and its subclasses) usually mean a bug or bad argument. The compiler does not force you to handle them.
  • Checked exceptions (other Exception subclasses, like IOException) are problems a correct program can still meet: a missing file, a lost connection. A method that may throw one must declare it with throws, and callers must catch it or declare it too.
  • Errors are serious problems of the JVM itself; do not catch them.
Java
import java.io.IOException;

public class Main {
    public static void main(String[] args) {
        try {
            System.out.println(loadSetting("theme"));
            System.out.println(loadSetting("missing"));
        } catch (IOException e) {
            System.out.println("could not load: " + e.getMessage());
        }
    }

    static String loadSetting(String key) throws IOException {      // callers must deal with IOException
        if (key.equals("missing")) throw new IOException("no setting " + key);
        return "dark";
    }
}

finally and try-with-resources

finally runs whether or not an exception happened, for clean-up. For anything that must be closed (files, connections), try-with-resources closes it automatically, even if an exception is thrown:

Java
public class Main {
    public static void main(String[] args) {
        try (Resource a = new Resource("first"); Resource b = new Resource("second")) {
            System.out.println("using both");
            throw new IllegalStateException("something failed");
        } catch (IllegalStateException e) {
            System.out.println("caught: " + e.getMessage());
        } finally {
            System.out.println("finally runs too");
        }
    }
}

class Resource implements AutoCloseable {
    private final String name;
    Resource(String name) { this.name = name; System.out.println("open " + name); }
    @Override public void close() { System.out.println("close " + name); }   // closed in reverse order
}

Any class implementing AutoCloseable works in a try-with-resources statement.

Your own exceptions

Create an exception class when callers need to recognise your specific problem. Pass the original exception as the cause when you wrap one:

Java
public class Main {
    public static void main(String[] args) {
        try {
            Config.port("80x");
        } catch (ConfigException e) {
            System.out.println(e.getMessage() + " <- caused by " + e.getCause().getClass().getSimpleName());
        }
    }
}

class ConfigException extends Exception {                    // checked
    ConfigException(String message, Throwable cause) { super(message, cause); }
}

class Config {
    static int port(String text) throws ConfigException {
        try {
            return Integer.parseInt(text);
        } catch (NumberFormatException e) {
            throw new ConfigException("bad port '" + text + "'", e);
        }
    }
}

Extend RuntimeException instead for exceptions that signal programming errors, so callers are not forced to catch them.

Good practice

  • Validate arguments early with clear messages: Objects.requireNonNull(name, "name"), if (qty < 1) throw new IllegalArgumentException("qty must be at least 1: " + qty).
  • Catch only what you can handle, where you can do something useful. Never swallow an exception with an empty catch; at least log it.
  • Do not use exceptions for normal control flow: check with hasNextInt(), containsKey() or Optional (lesson 6.03) when a missing value is normal.
  • Read stack traces from the top: the first line names the exception and message; the first at line in your own code is usually where to look.
