BigInteger, BigDecimal and Exact Arithmetic

lesson 8.044 of 5 in milestone 85 min2 practice tasks

When int, long and double are not enough - silent overflow and the Math.addExact family that refuses it, BigInteger for whole numbers of any size, why 0.1 + 0.2 is not 0.3 in double, BigDecimal for exact decimal money with scale and RoundingMode, comparing with compareTo, and choosing the right type.

Overflow is silent

int holds values up to 2,147,483,647. One more wraps around to the most negative number, with no error:

Java
public class Main {
    public static void main(String[] args) {
        int big = Integer.MAX_VALUE;
        System.out.println(big + 1);                 // -2147483648
        long ms = 30L * 24 * 60 * 60 * 1000;          // 30 days in milliseconds: needs long
        int wrong = 30 * 24 * 60 * 60 * 1000;         // computed in int: wrapped
        System.out.println(ms + " " + wrong);
    }
}

The L on the first number makes the whole expression long. Without it, the multiplication happens in int and wraps before being stored.

Arithmetic that refuses to overflow

Math.addExact, subtractExact, multiplyExact, incrementExact, negateExact and toIntExact throw ArithmeticException instead of wrapping:

Java
public class Main {
    public static void main(String[] args) {
        System.out.println(Math.multiplyExact(1_000_000, 1_000));
        try {
            Math.multiplyExact(1_000_000, 1_000_000);
        } catch (ArithmeticException e) {
            System.out.println("refused: " + e.getMessage());
        }
        System.out.println(Math.toIntExact(42L));
    }
}

Use them wherever an overflow would be a bug: sizes, money in cents, counters that must not wrap.

BigInteger: whole numbers of any size

Java
import java.math.BigInteger;

public class Main {
    public static void main(String[] args) {
        BigInteger f = BigInteger.ONE;
        for (int i = 2; i <= 30; i++) f = f.multiply(BigInteger.valueOf(i));
        System.out.println("30! = " + f);
        System.out.println(f.bitLength() + " bits, " + f.toString().length() + " digits");

        BigInteger a = new BigInteger("123456789012345678901234567890");
        System.out.println(a.add(BigInteger.TEN).mod(BigInteger.valueOf(97)));
        System.out.println(BigInteger.TWO.pow(100));
        System.out.println(BigInteger.valueOf(97).isProbablePrime(20));
    }
}

BigInteger objects never change: every operation returns a new one, so always use the result (f = f.multiply(...)). They are slower than long, so use them only when values can really be that large (cryptography, exact combinatorics, IDs from other systems).

The trouble with double

double stores numbers in binary, and most decimal fractions have no exact binary form, just as 1/3 has no exact decimal form:

Java
public class Main {
    public static void main(String[] args) {
        System.out.println(0.1 + 0.2);                      // 0.30000000000000004
        System.out.println(0.1 + 0.2 == 0.3);               // false
        double total = 0;
        for (int i = 0; i < 10; i++) total += 0.1;
        System.out.println(total);                          // 0.9999999999999999
        System.out.println(Math.abs(total - 1.0) < 1e-9);    // compare with a tolerance instead
    }
}

For measurements and science, double is right and the tiny errors do not matter. For money, they do: a bank cannot lose a penny in a sum.

BigDecimal: exact decimals

Java
import java.math.*;

public class Main {
    public static void main(String[] args) {
        BigDecimal a = new BigDecimal("0.1");
        BigDecimal b = new BigDecimal("0.2");
        System.out.println(a.add(b));                                   // 0.3 exactly
        System.out.println(new BigDecimal(0.1));                        // the double's real value: not what you want
        System.out.println(BigDecimal.valueOf(0.1));                    // goes through the double's text: 0.1

        BigDecimal price = new BigDecimal("19.99");
        BigDecimal qty = BigDecimal.valueOf(3);
        BigDecimal vat = new BigDecimal("0.20");
        BigDecimal net = price.multiply(qty);
        BigDecimal gross = net.add(net.multiply(vat)).setScale(2, RoundingMode.HALF_UP);
        System.out.println(net + " + VAT = " + gross);
    }
}

Always create BigDecimal from a string (or valueOf), never with new BigDecimal(double), which copies the double's binary error.

Scale and rounding

A BigDecimal is a whole number and a scale (how many digits after the point): 19.99 is 1999 with scale 2. Division can produce endless digits, so you must say how to round:

Java
import java.math.*;

public class Main {
    public static void main(String[] args) {
        BigDecimal ten = new BigDecimal("10.00");
        try {
            ten.divide(BigDecimal.valueOf(3));
        } catch (ArithmeticException e) {
            System.out.println("needs rounding: " + e.getMessage());
        }
        System.out.println(ten.divide(BigDecimal.valueOf(3), 2, RoundingMode.HALF_UP));
        System.out.println(new BigDecimal("2.5").setScale(0, RoundingMode.HALF_UP) + " " + new BigDecimal("2.5").setScale(0, RoundingMode.HALF_EVEN));
    }
}

HALF_UP is school rounding; HALF_EVEN (banker's rounding) rounds halves to the even neighbour, which avoids a bias when adding many rounded values.

Comparing BigDecimal

equals compares the scale too, so 2.0 and 2.00 are not equal. Compare values with compareTo:

Java
import java.math.BigDecimal;

public class Main {
    public static void main(String[] args) {
        BigDecimal a = new BigDecimal("2.0"), b = new BigDecimal("2.00");
        System.out.println(a.equals(b) + " " + (a.compareTo(b) == 0));
        System.out.println(a.stripTrailingZeros().equals(b.stripTrailingZeros()));
    }
}

This also means BigDecimal values make poor HashMap keys unless you normalise them first.

Choosing

need type
counts, indexes, ids int, long (with Math.*Exact where overflow is a bug)
measurements, physics, graphics double
money, prices, tax BigDecimal, or long cents
whole numbers beyond long BigInteger
