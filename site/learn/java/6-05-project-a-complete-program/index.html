Project: A Complete Program

lesson 6.055 of 5 in milestone 65 min1 practice task

How a real Java program is organised - packages and the folder layout, access across packages, Maven and Gradle with a pom.xml or build.gradle, dependencies, unit tests with JUnit 5, building a runnable JAR, and the plan for the final project, a command-driven event planner.

Packages

Real programs put classes into packages, named like reversed domain names, matching the folder structure:

Text
planner/
  pom.xml                         (or build.gradle)
  src/main/java/
    com/example/planner/
      App.java                    package com.example.planner;
      model/Event.java            package com.example.planner.model;
      model/Schedule.java
      io/CommandParser.java       package com.example.planner.io;
  src/test/java/
    com/example/planner/model/ScheduleTest.java
Java
package com.example.planner.model;          // first line of the file

import java.time.LocalDateTime;              // imports come after the package line
import java.util.List;

public record Event(String title, LocalDateTime start, int minutes) { }
  • A class in another package is used with an import (or its full name, com.example.planner.model.Event).
  • public members are visible everywhere; members without a modifier are visible only inside their own package. This lets a package hide its helper classes.
  • Each public class lives in a file with its name, in the folder of its package.

Build tools

Maven and Gradle compile the code, download libraries, run the tests and package the program. With Maven, a pom.xml describes the project:

xml
<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>planner</artifactId>
  <version>1.0.0</version>
  <properties>
    <maven.compiler.release>25</maven.compiler.release>
  </properties>
  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.11.4</version>
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>
Terminal
mvn compile          # compile src/main/java
mvn test             # run the tests in src/test/java
mvn package          # build target/planner-1.0.0.jar
java -cp target/planner-1.0.0.jar com.example.planner.App

Gradle does the same with a build.gradle (or build.gradle.kts) script: gradle build, gradle test, gradle run. IDEs import either kind of project directly.

Unit tests with JUnit

JUnit 5 is the standard Java test framework. Test classes mirror the main classes' packages:

Java
package com.example.planner.model;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class ScheduleTest {
    @Test
    void overlappingEventsAreRejected() {
        Schedule s = new Schedule();
        s.add(new Event("Lunch", at(12, 0), 60));
        assertThrows(IllegalArgumentException.class, () -> s.add(new Event("Call", at(12, 30), 15)));
    }

    @Test
    void eventsAreListedInTimeOrder() {
        Schedule s = new Schedule();
        s.add(new Event("Late", at(18, 0), 30));
        s.add(new Event("Early", at(9, 0), 30));
        assertEquals(List.of("Early", "Late"), s.titles());
    }
}

assertEquals(expected, actual), assertTrue, assertThrows and @ParameterizedTest work like the checkEq and checkThrows you have used throughout this course.

The final project

The project for this milestone is an event planner that reads commands, keeps a schedule, refuses overlapping events, and answers questions about free time. It brings the course together:

Part Uses
Event record with validation records, java.time (3.05, 6.03)
Schedule with sorted events collections, comparators, exceptions (4.02 to 4.04)
Free-slot search and the daily summary algorithms over sorted data, streams (5.02, 6.02)
Command loop with error messages parsing, exceptions, switch (1.05, 4.04)

Build it in layers, testing each before the next: the record, then the schedule's add and list, then overlaps, then free slots, then the commands. Keep the rules in Schedule and the input handling in Main, so the rules can be tested without typing commands.
