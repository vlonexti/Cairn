Packaging, Environments and Tools

lesson 8.066 of 6 in milestone 85 min2 practice tasks

Turning scripts into a project others can install - virtual environments with venv, installing packages with pip and pinning versions, the src layout and pyproject.toml, entry points for commands, formatters and linters such as Ruff, type checking in CI, and building and sharing a package.

The problem with installing everything globally

pip install requests without anything else puts the package into the one Python on your computer. Project A needs version 2 of a library and project B needs version 3: one of them breaks. The answer is a virtual environment: a private folder of packages for each project.

Virtual environments

Text
python -m venv .venv                 # create one in the project folder
.venv\Scripts\activate               # Windows
source .venv/bin/activate            # macOS and Linux
python -m pip install requests       # installs into .venv only
deactivate                           # back to the system Python

While it is active, python and pip mean the environment's copies. Do not put .venv in version control; add it to .gitignore and recreate it when needed.

Always run pip as python -m pip: it then uses the pip that belongs to the Python you mean.

Recording what you depend on

Text
python -m pip freeze > requirements.txt     # exact versions installed now
python -m pip install -r requirements.txt   # recreate them elsewhere

A requirements.txt with exact versions (requests==2.32.3) makes a program reproducible. For libraries, version ranges are better, so users can combine them with other libraries.

A project layout

Text
weather-tool/
  pyproject.toml
  README.md
  src/
    weather_tool/
      __init__.py
      cli.py
      forecast.py
  tests/
    test_forecast.py

The src folder keeps your package from being imported by accident from the current folder, so tests run against the installed code. Package names use underscores; the project name may use dashes.

pyproject.toml

One file describes the project for every tool:

TOML
[project]
name = "weather-tool"
version = "0.3.0"
description = "Forecasts in the terminal"
requires-python = ">=3.11"
dependencies = ["requests>=2.31"]

[project.scripts]
weather = "weather_tool.cli:main"

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 100

[project.scripts] creates a weather command that calls main() in weather_tool/cli.py. During development, python -m pip install -e . installs the project in "editable" mode: changes to the code take effect without reinstalling.

A main function for the command

Python
# src/weather_tool/cli.py
import argparse
import sys

def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(prog="weather")
    parser.add_argument("city")
    args = parser.parse_args(argv)
    print(f"Forecast for {args.city}: sunny")
    return 0

if __name__ == "__main__":
    sys.exit(main())

Taking argv as a parameter lets tests call main(["London"]) directly.

Tools that keep code tidy

  • A formatter rewrites code into one consistent style, so nobody argues about spaces: ruff format or black.
  • A linter finds likely bugs and bad habits: unused imports, undefined names, a mutable default argument: ruff check.
  • A type checker reads your hints (lesson 8.03): mypy or pyright.
  • Tests: python -m pytest.

Run them on every change with a CI service (GitHub Actions or similar), so mistakes are caught before they are merged:

YAML
# .github/workflows/check.yml
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.13" }
      - run: python -m pip install -e . pytest ruff mypy
      - run: ruff check .
      - run: mypy src
      - run: python -m pytest

Building and sharing

Text
python -m pip install build
python -m build              # makes dist/weather_tool-0.3.0-py3-none-any.whl and a .tar.gz

The .whl ("wheel") file can be installed with pip install anywhere. Publishing to PyPI (the public package index) uses twine upload dist/* with an account and an API token; try test.pypi.org first.

Version numbers

Most Python projects follow semantic versioning: MAJOR.MINOR.PATCH. Bug fixes raise PATCH, new features that do not break anything raise MINOR, and anything that breaks existing users raises MAJOR.

You can read the version of an installed package from code:

Python
from importlib.metadata import version, PackageNotFoundError

try:
    print(version("pip").count(".") >= 1)
except PackageNotFoundError:
    print("pip is not installed here")
