Threads and Processes

lesson 7.055 of 6 in milestone 75 min2 practice tasks

Doing several things at once - threads with threading and concurrent.futures, why the GIL means threads speed up waiting but not calculating, race conditions and locks, queues for passing work between threads, and processes for calculations that need every core.

Why run things at the same time

Most slow programs are slow for one of two reasons:

  • Waiting: for a network reply, a disk, a database. The CPU sits idle.
  • Calculating: crunching numbers. The CPU is busy.

Running work at the same time helps both, but in different ways, and in Python the difference matters because of the GIL (below).

Threads

A thread is a separate line of execution inside the same program, sharing its memory. threading.Thread runs a function in one:

Python
import threading
import time

def download(name, seconds):
    time.sleep(seconds)                  # stands in for waiting on the network
    print(f"{name} finished")

start = time.perf_counter()
threads = [threading.Thread(target=download, args=(f"file{i}", 0.2)) for i in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()                             # wait for it to finish
print(f"all done in {time.perf_counter() - start:.1f} s")   # about 0.2 s, not 1.0

Five waits of 0.2 s overlap, so the whole thing takes about 0.2 s.

The easier way: a thread pool

Starting and joining threads by hand gets tedious. concurrent.futures.ThreadPoolExecutor keeps a few threads ready and hands them work. map works like the built-in map and returns results in order:

Python
from concurrent.futures import ThreadPoolExecutor
import time

def fetch(n):
    time.sleep(0.1)
    return n * n

with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(fetch, range(8)))
print(results)

pool.submit(f, arg) returns a future: a placeholder whose .result() waits for the value (and raises the function's exception, if it raised one).

The GIL

CPython has a global interpreter lock: only one thread runs Python code at any moment. A thread that is waiting (sleeping, reading a socket or a file) releases it, so waiting overlaps beautifully. Pure-Python calculation does not: four threads adding numbers take as long as one.

Work Threads help? Use
network, files, sleeping yes threads, or asyncio (lesson 7.06)
pure Python number-crunching no processes
NumPy and other C libraries often they release the GIL inside their C code

(Python 3.13 has an experimental build without the GIL. Until it is the default, the table above holds.)

Race conditions and locks

Threads share variables, and counter += 1 is really three steps (read, add, write). Two threads can read the same old value and one increase is lost: a race condition. A Lock lets one thread at a time into the critical part:

Python
import threading

counter = 0
lock = threading.Lock()

def add_many():
    global counter
    for _ in range(100_000):
        with lock:                        # a Lock is a context manager (lesson 7.02)
            counter += 1

threads = [threading.Thread(target=add_many) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter)                            # always 400000

The safest design is to share as little as possible: give each thread its own data and combine the results at the end.

Passing work with a queue

queue.Queue is made for threads: put and get are already locked, and get waits until something arrives. A classic pattern is producers putting work in and consumers taking it out:

Python
import queue
import threading

jobs = queue.Queue()
results = []
results_lock = threading.Lock()

def worker():
    while True:
        n = jobs.get()
        if n is None:                     # a sentinel: no more work
            break
        with results_lock:
            results.append(n * 10)

workers = [threading.Thread(target=worker) for _ in range(3)]
for w in workers:
    w.start()
for n in range(6):
    jobs.put(n)
for _ in workers:
    jobs.put(None)                        # one sentinel per worker
for w in workers:
    w.join()
print(sorted(results))

Processes for calculations

A process is a separate Python interpreter with its own memory and its own GIL, so processes really calculate in parallel on several cores. ProcessPoolExecutor has the same interface as the thread pool:

Python
from concurrent.futures import ProcessPoolExecutor

def count_primes(limit):
    return sum(1 for n in range(2, limit) if all(n % d for d in range(2, int(n ** 0.5) + 1)))

if __name__ == "__main__":                 # required: each process imports this file
    with ProcessPoolExecutor() as pool:
        print(list(pool.map(count_primes, [50_000] * 4)))

The price: arguments and results are copied between processes (they must be picklable), and starting a process costs far more than starting a thread. Use processes for big chunks of calculation, not for many tiny jobs.
