Databases with sqlite3

lesson 8.055 of 6 in milestone 85 min2 practice tasks

Keeping data in a real database without installing anything - connecting with sqlite3, creating tables, inserting with parameters (never with string formatting), querying and reading rows, transactions with commit and rollback, row factories, indexes, and when a database beats JSON files.

Why a database?

A JSON file (lesson 6.02) is perfect for settings. It gets awkward when you have thousands of records, need to find a few of them quickly, or two parts of a program write at the same time. A database stores records in tables and answers questions about them in a language called SQL.

SQLite is a complete database in one file (or in memory), and Python includes it as sqlite3. There is nothing to install.

Connecting and creating a table

Python
import sqlite3

con = sqlite3.connect(":memory:")          # a file name like "shop.db" keeps the data
con.execute("""
    CREATE TABLE products (
        id    INTEGER PRIMARY KEY,
        name  TEXT NOT NULL UNIQUE,
        price REAL NOT NULL,
        stock INTEGER NOT NULL DEFAULT 0
    )
""")
print("table created")
Output
table created

Each column has a type, and rules: PRIMARY KEY gives every row a unique id (filled in for you), NOT NULL refuses missing values, UNIQUE refuses duplicates.

Inserting safely

Values go into the SQL through ? placeholders, given as a separate tuple:

Python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT UNIQUE, price REAL, stock INTEGER)")

con.execute("INSERT INTO products (name, price, stock) VALUES (?, ?, ?)", ("tea", 2.5, 40))
rows = [("coffee", 6.0, 12), ("milk", 1.2, 0)]
con.executemany("INSERT INTO products (name, price, stock) VALUES (?, ?, ?)", rows)
con.commit()

print(con.execute("SELECT COUNT(*) FROM products").fetchone()[0])
Output
3

Never build SQL with f-strings or +. A name like x'); DROP TABLE products; -- would become part of the command: this is SQL injection, one of the most common security bugs. With ?, the value is always treated as data.

Asking questions

Python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT, price REAL, stock INTEGER)")
con.executemany("INSERT INTO products (name, price, stock) VALUES (?, ?, ?)",
                [("tea", 2.5, 40), ("coffee", 6.0, 12), ("milk", 1.2, 0), ("cocoa", 3.8, 5)])

for name, price in con.execute("SELECT name, price FROM products WHERE stock > 0 ORDER BY price DESC"):
    print(name, price)

row = con.execute("SELECT name FROM products WHERE name = ?", ("milk",)).fetchone()
print(row)
print(con.execute("SELECT name FROM products WHERE name = ?", ("bread",)).fetchone())
print(con.execute("SELECT ROUND(AVG(price), 2), SUM(stock) FROM products").fetchone())
Output
coffee 6.0
cocoa 3.8
tea 2.5
('milk',)
None
(3.38, 57)

WHERE filters, ORDER BY sorts, and functions like COUNT, SUM, AVG, MIN and MAX summarise. Looping over a query gives one tuple per row; fetchone gives the next row or None, fetchall a list. Note the comma in ("milk",): parameters are always a tuple.

Rows with names

Tuples are easy to mix up. With a row factory, rows can be read by column name:

Python
import sqlite3

con = sqlite3.connect(":memory:")
con.row_factory = sqlite3.Row
con.execute("CREATE TABLE people (name TEXT, age INTEGER)")
con.execute("INSERT INTO people VALUES (?, ?)", ("Ada", 36))
row = con.execute("SELECT * FROM people").fetchone()
print(row["name"], row["age"], dict(row))
Output
Ada 36 {'name': 'Ada', 'age': 36}

Changing and deleting

Python
con.execute("UPDATE products SET stock = stock - ? WHERE name = ?", (2, "tea"))
con.execute("DELETE FROM products WHERE stock = 0")
con.commit()

cursor.rowcount after an UPDATE or DELETE says how many rows it touched.

Transactions: all or nothing

Changes are not saved until commit(). rollback() throws them away. Using the connection as a context manager does it for you: commit if the block succeeds, rollback if it raises.

Python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER CHECK (balance >= 0))")
con.executemany("INSERT INTO accounts VALUES (?, ?)", [("ada", 100), ("bob", 20)])
con.commit()

def transfer(frm, to, amount):
    with con:
        con.execute("UPDATE accounts SET balance = balance + ? WHERE name = ?", (amount, to))
        con.execute("UPDATE accounts SET balance = balance - ? WHERE name = ?", (amount, frm))

try:
    transfer("bob", "ada", 50)        # bob only has 20: the CHECK fails
except sqlite3.IntegrityError as e:
    print("refused:", e)
print(con.execute("SELECT * FROM accounts ORDER BY name").fetchall())
Output
refused: CHECK constraint failed: balance >= 0
[('ada', 100), ('bob', 20)]

Ada's balance was raised first, but the whole transfer was rolled back, so no money appeared from nowhere.

Speed: indexes

Finding rows by a column the database must scan is slow for big tables. An index makes it fast, like the index of a book:

Python
con.execute("CREATE INDEX idx_orders_customer ON orders (customer_id)")

Primary keys and UNIQUE columns get one automatically.

Closing

Call con.close() when you are done, or use contextlib.closing(sqlite3.connect(...)) in a with. (The connection's own with handles transactions, not closing.)
