Errors and Exceptions

lesson 4.055 of 5 in milestone 45 min1 practice task

Handling what goes wrong - reading tracebacks, try and except, catching specific exceptions, else and finally, raising your own errors, custom exception classes, and the difference between asking permission and asking forgiveness.

Exceptions and tracebacks

When something goes wrong, Python raises an exception. If nothing handles it, the program stops with a traceback:

Output
Traceback (most recent call last):
  File "main.py", line 3, in <module>
    print(average([]))
  File "main.py", line 2, in average
    return sum(values) / len(values)
ZeroDivisionError: division by zero

Read it from the bottom: the last line says what happened (ZeroDivisionError) and why; the lines above show the chain of calls, ending at the line that failed.

Common exceptions:

Exception Typical cause
ValueError Right type, wrong value: int("abc")
TypeError Wrong type: "a" + 1
KeyError Missing dictionary key
IndexError List index out of range
AttributeError Misspelt attribute or method, or None where an object was expected
FileNotFoundError Opening a missing file
ZeroDivisionError Division by zero

try and except

Python
text = input("A number: ")
try:
    number = int(text)
except ValueError:
    print("That was not a whole number.")
else:
    print("Twice that is", number * 2)     # runs only if there was no exception
finally:
    print("Done.")                         # always runs

Catch specific exceptions. A bare except: (or except Exception:) also hides bugs such as misspelt names, and makes problems silently disappear.

Several kinds can share a handler, and the exception object can be inspected:

Python
for raw in ["12", "x", None]:
    try:
        print(int(raw) * 2)
    except (ValueError, TypeError) as e:
        print("skipping:", e)

Raising exceptions

A function that cannot do its job should raise rather than return a strange value:

Python
def withdraw(balance, amount):
    if amount <= 0:
        raise ValueError(f"amount must be positive, got {amount}")
    if amount > balance:
        raise ValueError("insufficient funds")
    return balance - amount

The caller decides what to do: show a message, retry, or let it stop the program.

Your own exception classes

For errors specific to your program, define a class deriving from Exception, so callers can catch exactly them:

Python
class ConfigError(Exception):
    """The configuration file is invalid."""

def read_port(settings):
    if "port" not in settings:
        raise ConfigError("missing port")
    return int(settings["port"])

try:
    read_port({})
except ConfigError as e:
    print("Config problem:", e)

raise NewError(...) from e inside an except keeps the original exception attached as the cause, which makes the traceback tell the whole story.

Asking forgiveness

Python style often prefers trying and handling the failure (EAFP: easier to ask forgiveness than permission) over checking first (LBYL: look before you leap):

Python
counts = {"a": 1}
try:
    value = counts["b"]
except KeyError:
    value = 0

Checking first can be wrong anyway: a file that exists when you check can be deleted before you open it. For simple cases, dict.get and str.isdigit are clearer than either.
