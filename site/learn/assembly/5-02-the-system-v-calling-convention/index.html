The System V Calling Convention

lesson 5.022 of 5 in milestone 55 min1 practice task

Linux and macOS follow the System V AMD64 convention. Integer and pointer arguments go in rdi, rsi, rdx, rcx, r8 and r9, the rest on the stack, and the result comes back in rax. rbx, rbp, rsp and r12 to r15 must survive a call; everything else may be changed. rsp must be a multiple of 16 at every call.

Why a convention?

The hardware does not say where arguments go. If every function chose for itself, no code could call code written by someone else. A calling convention is the agreement that lets C, Rust, Go and your assembly call each other. Linux, macOS and the BSDs use the System V AMD64 convention; Windows uses its own (lesson 5.05).

Arguments and results

Registers
integer and pointer arguments, in order rdi, rsi, rdx, rcx, r8, r9
more than six pushed on the stack, the 7th at the lowest address
floating-point arguments xmm0 to xmm7
integer or pointer result rax (and rdx for a 128-bit result)
floating-point result xmm0

So the C function long clamp(long x, long low, long high) gets x in rdi, low in rsi, high in rdx, and returns in rax. Smaller types use the low part: an int argument is in edi, an int result in eax, and the upper bits are not guaranteed to be anything in particular.

Who saves what

Kind Registers Rule
callee-saved ("non-volatile") rbx, rbp, r12, r13, r14, r15 (and rsp) a function must give them back unchanged: save with push, restore with pop
caller-saved ("volatile", "scratch") rax, rcx, rdx, rsi, rdi, r8 to r11 any call may change them: if you need one after a call, keep it somewhere safe

Choose by how long a value must live:

  • Needed only until the next call? Use a scratch register: no saving needed.
  • Needed after a call? Put it in a callee-saved register (saving the caller's value first), or on the stack.

The tests on this website check this rule after every call: change rbx without restoring it and the test reports it.

Stack alignment

At the moment of a call instruction, rsp must be a multiple of 16. The call then pushes 8 bytes, so inside a function rsp is 8 more than a multiple of 16, until the function pushes or subtracts something.

Why? Instructions that move 16 bytes at a time (SSE, used by C library functions like printf and memcpy) can require 16-byte-aligned addresses, and compilers assume the rule holds. Break it and calls into C may crash on an instruction like movaps for no visible reason.

Assembly
my_function:                    ; on entry: rsp = 16n + 8 (the return address was pushed)
        push    rbx             ; rsp = 16n: aligned again
        call    other           ; fine
        pop     rbx
        ret

two_saves:
        push    rbx             ; 16n
        push    r12             ; 16n - 8: not aligned!
        sub     rsp, 8          ; 16n - 16: aligned
        call    other
        add     rsp, 8
        pop     r12
        pop     rbx
        ret

At _start the stack is aligned, which is why _start can call functions directly.

The red zone

A function that calls nothing (a leaf function) may use the 128 bytes below rsp without moving rsp at all: the convention promises nothing else will touch them. Compilers use this "red zone" for small leaf functions. (The Linux kernel cannot rely on it, and Windows has no red zone.)
