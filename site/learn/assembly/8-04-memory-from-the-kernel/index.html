Memory from the Kernel

lesson 8.044 of 5 in milestone 85 min2 practice tasks

Getting memory at run time without a C library - the mmap system call with anonymous private pages, its six arguments and the flags that matter, errors as negative return values, munmap to give memory back, page sizes and rounding, the older brk call, and a bump allocator built on one mmap.

Where does malloc get memory?

The .bss section gives a fixed amount of memory decided when the program is assembled. To get more while the program runs, a program asks the kernel. C's malloc does exactly that underneath, with the system calls this lesson uses directly.

mmap

mmap (system call 9 on Linux x86-64) maps memory into the program's address space. For plain memory, ask for anonymous (not backed by a file), private pages:

register meaning value here
rdi where (0 lets the kernel choose) 0
rsi how many bytes the size
rdx protection `PROT_READ
r10 flags `MAP_PRIVATE
r8 file descriptor -1 (no file)
r9 offset in the file 0

Note the fourth argument goes in r10, not rcx: the syscall instruction itself overwrites rcx (and r11).

Assembly
        global  _start

SYS_MMAP   equ  9
SYS_MUNMAP equ  11
PROT_RW    equ  3
MAP_PRIV_ANON equ 0x22

        section .text
_start:
        mov     eax, SYS_MMAP
        xor     edi, edi
        mov     esi, 4096 * 4           ; four pages
        mov     edx, PROT_RW
        mov     r10d, MAP_PRIV_ANON
        mov     r8, -1
        xor     r9d, r9d
        syscall
        test    rax, rax
        js      .failed                 ; a negative result is -errno
        mov     rbx, rax                ; the new memory, zero-filled

        mov     qword [rbx], 42         ; use it like any other memory
        mov     qword [rbx + 16000], 7
        mov     rdi, [rbx]
        add     rdi, [rbx + 16000]
        call    print_int               ; 49
        call    print_newline

        mov     eax, SYS_MUNMAP
        mov     rdi, rbx
        mov     esi, 4096 * 4
        syscall
        xor     edi, edi
        jmp     .exit
.failed:
        neg     rax
        mov     rdi, rax
        call    print_int               ; the error number
        call    print_newline
        mov     edi, 1
.exit:  mov     eax, 60
        syscall

New anonymous memory is always zero-filled, so you never see another program's data.

Errors are negative

Raw system calls do not use errno. They return -errno in rax on failure (lesson 7.03): -12 is ENOMEM, -22 is EINVAL. Because no valid address is that close to the top of the range, js (jump if the sign bit is set) after test rax, rax is the usual check.

Pages

The kernel works in pages of 4096 bytes. mmap rounds the size up to whole pages, so asking for 10 bytes gives you a page. Round sizes yourself so you know what you got:

Assembly
        global  _start

        section .text
round_to_page:                          ; rdi = bytes, returns them rounded up to a multiple of 4096
        lea     rax, [rdi + 4095]
        and     rax, -4096              ; clear the low 12 bits
        ret

_start:
        mov     edi, 1
        call    round_to_page
        mov     rdi, rax
        call    print_int               ; 4096
        call    print_newline
        mov     edi, 8193
        call    round_to_page
        mov     rdi, rax
        call    print_int               ; 12288
        call    print_newline
        mov     eax, 60
        xor     edi, edi
        syscall

-4096 in two's complement is all 1s except the low 12 bits, so and clears exactly those (lesson 2.03).

brk, the old way

brk (system call 12) moves the end of the program's data area. brk(0) returns the current end; brk(new_end) asks to grow it and returns the new end (or the old one if it failed). Early mallocs were built on it; modern ones use mmap for large blocks and both for small ones. mmap is simpler to use correctly, so prefer it.

A bump allocator

Allocating with one system call per object would be slow. Instead, map one large region and hand out pieces by moving a pointer, as lesson 6.02 of the pointers course and the arena idea describe:

Assembly
        global  _start

        section .bss
arena_next: resq 1
arena_end:  resq 1

        section .text
arena_init:                             ; rdi = size; returns 0 or -errno
        mov     rsi, rdi
        mov     eax, 9
        xor     edi, edi
        mov     edx, 3
        mov     r10d, 0x22
        mov     r8, -1
        xor     r9d, r9d
        push    rsi
        syscall
        pop     rsi
        test    rax, rax
        js      .done
        mov     [rel arena_next], rax
        add     rsi, rax
        mov     [rel arena_end], rsi
        xor     eax, eax
.done:  ret

arena_alloc:                            ; rdi = bytes; returns an 8-byte-aligned pointer, or 0 when full
        add     rdi, 7
        and     rdi, -8                 ; round up to a multiple of 8
        mov     rax, [rel arena_next]
        lea     rdx, [rax + rdi]
        cmp     rdx, [rel arena_end]
        ja      .full
        mov     [rel arena_next], rdx
        ret
.full:  xor     eax, eax
        ret

_start:
        mov     edi, 64
        call    arena_init
        mov     edi, 10
        call    arena_alloc
        mov     rbx, rax
        mov     edi, 20
        call    arena_alloc
        sub     rax, rbx                ; 16: 10 rounded up to 16
        mov     rdi, rax
        call    print_int
        call    print_newline
        mov     edi, 100
        call    arena_alloc             ; does not fit in 64 bytes
        mov     rdi, rax
        call    print_int               ; 0
        call    print_newline
        mov     eax, 60
        xor     edi, edi
        syscall

A bump allocator cannot free single objects; everything is released together (with munmap, or by resetting arena_next). For many programs, such as a compiler handling one file or a game handling one frame, that is exactly what is wanted, and it is far faster than a general allocator.
