Optimisation Basics

lesson 6.033 of 5 in milestone 65 min1 practice task

Speed depends less on how many instructions run than on what they wait for. Memory is far slower than registers and caches hide it only for data used together. Chains of dependent instructions cannot overlap, wrong branch guesses cost many cycles, and division is slow. Measure with rdtsc before and after every change.

What is slow

A modern x86 core can start several instructions per cycle, if they do not wait for each other. Rough costs:

Operation Cycles (about)
add, and, mov between registers under 1 (several per cycle)
imul 3
reading memory that is in the L1 cache 4 to 5
a mispredicted branch 15 to 20
div (64-bit) 20 to 40
reading memory from the L3 cache about 40
reading memory from RAM 100 to 300

The Fundamentals course explains caches: memory moves in 64-byte lines, so reading one byte brings its neighbours too. Code that walks memory in order is fast; code that jumps around a big area waits for RAM over and over.

Dependency chains

Assembly
; one running total: every add waits for the one before
.loop:  add     rax, [rdi]
        add     rdi, 8
        cmp     rdi, rdx
        jne     .loop

Each add rax, ... needs the previous rax, so the additions happen one after another, however many the processor could do at once. Splitting the work into independent chains lets them overlap:

Assembly
; four running totals, combined at the end
.loop:  add     rax, [rdi]
        add     rcx, [rdi + 8]
        add     r8,  [rdi + 16]
        add     r9,  [rdi + 24]
        add     rdi, 32
        cmp     rdi, rdx
        jne     .loop
        add     rax, rcx
        add     r8, r9
        add     rax, r8

This is loop unrolling with several accumulators: fewer loop instructions per element, and four additions in flight at once. (The count must then be a multiple of four, or the leftovers handled separately.)

Measuring: rdtsc

Guessing about speed is usually wrong; measure. rdtsc reads the processor's time-stamp counter, which counts up at a steady rate, into edx:eax:

Assembly
        global  _start
        section .bss
array:  resq    4096

        section .data
s_one:  db      "one total:   ", 0
s_four: db      "four totals: ", 0

        section .text
_start:
        lea     rdi, [rel array]        ; touch the array once first, so the timings
        mov     ecx, 4096               ; do not include the operating system
.warm:  mov     [rdi], rcx              ; handing out its memory on first use
        add     rdi, 8
        dec     ecx
        jnz     .warm

        lea     rdi, [rel s_one]
        call    print_str
        rdtsc
        shl     rdx, 32
        or      rax, rdx
        mov     rbx, rax                ; the start time
        mov     r12d, 1000              ; repeat to get a measurable time
.rep1:  lea     rdi, [rel array]
        lea     rdx, [rdi + 4096*8]
        xor     eax, eax
.one:   add     rax, [rdi]
        add     rdi, 8
        cmp     rdi, rdx
        jne     .one
        dec     r12d
        jnz     .rep1
        rdtsc
        shl     rdx, 32
        or      rax, rdx
        sub     rax, rbx
        mov     rdi, rax
        call    print_int
        call    print_newline

        lea     rdi, [rel s_four]
        call    print_str
        rdtsc
        shl     rdx, 32
        or      rax, rdx
        mov     rbx, rax
        mov     r12d, 1000
.rep4:  lea     rdi, [rel array]
        lea     rdx, [rdi + 4096*8]
        xor     eax, eax
        xor     ecx, ecx
        xor     r8d, r8d
        xor     r9d, r9d
.four:  add     rax, [rdi]
        add     rcx, [rdi + 8]
        add     r8, [rdi + 16]
        add     r9, [rdi + 24]
        add     rdi, 32
        cmp     rdi, rdx
        jne     .four
        dec     r12d
        jnz     .rep4
        rdtsc
        shl     rdx, 32
        or      rax, rdx
        sub     rax, rbx
        mov     rdi, rax
        call    print_int
        call    print_newline
        mov     eax, 60
        xor     edi, edi
        syscall

The numbers are "ticks", and they change from run to run (the machine is shared, and its clock speed varies), but the second loop is usually clearly faster. Real measurements repeat many times and take the minimum. On Linux, perf stat counts cycles, cache misses and mispredicted branches for a whole program.

Rules of thumb

  1. Measure first. Find where the time goes before changing anything.
  2. Better algorithms beat better instructions. An O(n log n) sort in C beats a hand-tuned O(n²) one in assembly.
  3. Keep data together and in order. Arrays beat linked lists; walk memory forwards.
  4. Avoid unpredictable branches in hot loops: cmov, setcc and arithmetic (lesson 3.05).
  5. Avoid div when a shift, a mask or a multiplication will do.
  6. Break dependency chains with several accumulators.
  7. Use SIMD for doing the same thing to many values (next lesson).

Compilers already do most of this. Hand-written assembly wins mostly where you know something the compiler cannot: that arrays never overlap, that a value is always in range, or that a special instruction exists for the job.
