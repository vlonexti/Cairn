if, else and switch from C

lesson 3.044 of 5 in milestone 35 min1 practice task

Chains of if and else become a series of compares, each jumping to the next test. && jumps out at the first false part and || at the first true part. A switch over close-together values becomes a jump table - an array of addresses indexed by the value - after one unsigned compare that sends everything out of range to default.

else if chains

C
if (score >= 90)      grade = 'A';
else if (score >= 75) grade = 'B';
else if (score >= 50) grade = 'C';
else                  grade = 'F';

Each test jumps to the next test when it fails, and each body jumps to the end:

Assembly
        cmp     rdi, 90
        jl      .not_a
        mov     eax, 'A'
        jmp     .end
.not_a: cmp     rdi, 75
        jl      .not_b
        mov     eax, 'B'
        jmp     .end
.not_b: cmp     rdi, 50
        jl      .not_c
        mov     eax, 'C'
        jmp     .end
.not_c: mov     eax, 'F'
.end:

&& and ||

C's && and || stop as soon as the answer is known, and in assembly that is just where the jumps go:

C
if (x >= 1 && x <= 10) { ... }      // both must hold
if (c == ' ' || c == '\n') { ... }  // either is enough
Assembly
; x >= 1 && x <= 10: leave at the first part that fails
        cmp     rdi, 1
        jl      .skip
        cmp     rdi, 10
        jg      .skip
        ; ... body ...
.skip:

; c == ' ' || c == '\n': enter at the first part that holds
        cmp     dil, ' '
        je      .body
        cmp     dil, 10
        jne     .skip2
.body:
        ; ... body ...
.skip2:

switch and jump tables

A switch over a few values could be a chain of compares. Over many close-together values, compilers build a jump table: an array of label addresses, and one indirect jump that picks an entry with the value as the index.

Assembly
        global  _start

        section .data
s_zero: db      "zero", 10, 0
s_one:  db      "one", 10, 0
s_two:  db      "two", 10, 0
s_three: db     "three", 10, 0
s_many: db      "lots", 10, 0

        section .rodata
table:  dq      _start.case0, _start.case1, _start.case2, _start.case3   ; each case's address

        section .text
_start:
.next:
        call    read_int
        test    rdx, rdx
        jz      .exit
        cmp     rax, 3
        ja      .default                ; unsigned: catches negative numbers too
        lea     rcx, [rel table]
        jmp     [rcx + rax*8]           ; jump to the address stored in table[rax]
.case0: lea     rdi, [rel s_zero]
        jmp     .print
.case1: lea     rdi, [rel s_one]
        jmp     .print
.case2: lea     rdi, [rel s_two]
        jmp     .print
.case3: lea     rdi, [rel s_three]
        jmp     .print
.default:
        lea     rdi, [rel s_many]
.print: call    print_str
        jmp     .next
.exit:
        mov     eax, 60
        xor     edi, edi
        syscall

Run it with the input 2 0 7 -1 3.

  • dq _start.case0, ... stores the 8-byte addresses of the labels. The cases are local labels inside _start, and their full names are _start.case0 and so on. The table must spell them out, because inside the table a plain .case0 would belong to the label table.
  • jmp [rcx + rax*8] reads 8 bytes from the table and jumps there: an indirect jump.
  • The one ja check sends both too-big and negative values to the default, the unsigned trick from lesson 3.03. Without it, a bad value would jump to whatever address happened to be in memory past the table.

The table costs the same however many cases there are: one compare and one jump. Interpreters for languages like Python dispatch their instructions this way.
