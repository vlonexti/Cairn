Exceptions

lesson 4.033 of 5 in milestone 45 min1 practice task

Throwing and catching exceptions, the common exception types, catch order and exception filters, finally, rethrowing with throw versus throw ex, custom exception classes with inner exceptions, guard clauses and ArgumentException helpers, and when to use Try methods or result types instead.

throw and catch

When a method cannot do its job, it throws an exception. The exception travels up the call stack until a catch handles it; if nothing does, the program stops and prints the exception and its stack trace.

C#
foreach (string input in new[] { "42", "abc", "99999999999", "-5" })
{
    try
    {
        int age = ParseAge(input);
        Console.WriteLine($"age {age}");
    }
    catch (FormatException)
    {
        Console.WriteLine($"'{input}' is not a number");
    }
    catch (OverflowException)
    {
        Console.WriteLine($"'{input}' is far too big");
    }
    catch (ArgumentOutOfRangeException e)
    {
        Console.WriteLine(e.Message);
    }
}

static int ParseAge(string text)
{
    int age = int.Parse(text);           // throws FormatException or OverflowException
    if (age < 0) throw new ArgumentOutOfRangeException(nameof(text), age, "age cannot be negative");
    return age;
}

Catch blocks are tried in order; put specific types before general ones (Exception last).

Common exception types

Exception Thrown when
ArgumentException, ArgumentNullException, ArgumentOutOfRangeException A method was given a bad argument
InvalidOperationException The object is not in a state where this call makes sense
NullReferenceException A member of null was used (a bug: fix it, do not catch it)
IndexOutOfRangeException, KeyNotFoundException A missing index or key
FormatException, OverflowException Parsing failed
IOException, FileNotFoundException File and stream problems
NotSupportedException, NotImplementedException The operation is not supported / not written yet

Guard clauses

Check arguments at the start of public methods, so a mistake is reported where it happens:

C#
Console.WriteLine(Ratio(6, 3));
try { Ratio(1, 0); } catch (ArgumentException e) { Console.WriteLine(e.Message); }
try { Greet(null!); } catch (ArgumentNullException e) { Console.WriteLine(e.ParamName); }

static double Ratio(double part, double whole)
{
    ArgumentOutOfRangeException.ThrowIfZero(whole);
    return part / whole;
}

static string Greet(string name)
{
    ArgumentNullException.ThrowIfNull(name);
    ArgumentException.ThrowIfNullOrWhiteSpace(name);
    return $"Hello, {name}";
}

finally and filters

finally runs whether or not an exception happened: the place for clean-up (lesson 4.04 shows using, which does this for you). An exception filter when (...) catches only some exceptions of a type:

C#
int attempts = 0;
try
{
    attempts++;
    throw new HttpLikeException(503);
}
catch (HttpLikeException e) when (e.Status >= 500)
{
    Console.WriteLine($"server error {e.Status}, attempt {attempts}: worth retrying");
}
finally
{
    Console.WriteLine("finished");
}

public class HttpLikeException(int status) : Exception($"HTTP {status}")
{
    public int Status { get; } = status;
}

Custom exceptions

Define your own exception when callers need to tell your failure apart from others. Derive from Exception, end the name with Exception, and pass on the inner exception when wrapping another one:

C#
try
{
    LoadSettings("{ broken");
}
catch (ConfigException e)
{
    Console.WriteLine($"{e.Message} <- {e.InnerException?.GetType().Name}");
}

static Dictionary<string, string> LoadSettings(string json)
{
    try
    {
        return System.Text.Json.JsonSerializer.Deserialize<Dictionary<string, string>>(json)!;
    }
    catch (System.Text.Json.JsonException e)
    {
        throw new ConfigException("settings file is not valid JSON", e);
    }
}

public class ConfigException(string message, Exception? inner = null) : Exception(message, inner);

Rethrowing

To let an exception continue after logging it, write throw;. Writing throw e; restarts the stack trace at that line and hides where the problem really was.

C#
catch (IOException e)
{
    logger.Log(e);
    throw;            // not: throw e;
}

When not to throw

Exceptions are for exceptional situations: bugs, broken files, lost connections. They are slow-ish and make control flow hard to follow when used for ordinary outcomes. When failure is normal (the user typed something wrong, a key may be missing), prefer:

  • a Try method: bool TryParse(string s, out int value), dict.TryGetValue(...);
  • a nullable result: User? FindUser(string id);
  • a result type: record Result<T>(bool Ok, T? Value, string? Error).

Never catch an exception just to ignore it (catch { }): it hides bugs. Catch only what you can handle, at the level that knows what to do about it.
