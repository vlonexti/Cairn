Dates, Times and Culture

lesson 8.044 of 5 in milestone 85 min2 practice tasks

Getting time and formatting right in .NET - DateTime and its Kind, DateTimeOffset for moments, DateOnly and TimeOnly for calendar values, TimeSpan and date arithmetic, time zones with TimeZoneInfo, TimeProvider for testable code, and CultureInfo for numbers and dates that look right in every country and parse the same everywhere.

Which type?

You mean Use
an exact moment (a log entry, when an order was placed) DateTimeOffset (or DateTime in UTC)
a calendar date with no time (a birthday, a due date) DateOnly
a time of day (opening hours) TimeOnly
an amount of time (3 hours 20 minutes) TimeSpan

DateTime is the oldest type and the most confusing, because the same type can mean three things, shown by its Kind: Utc, Local (the computer's time zone) or Unspecified.

C#
var utc = new DateTime(2026, 11, 20, 9, 30, 0, DateTimeKind.Utc);
var unspecified = new DateTime(2026, 11, 20, 9, 30, 0);
Console.WriteLine($"{utc:O} {utc.Kind}");
Console.WriteLine($"{unspecified:O} {unspecified.Kind}");

The O format ("round-trip") writes ISO 8601 and keeps everything needed to read the value back.

DateTimeOffset: a moment with its offset

C#
var placed = new DateTimeOffset(2026, 11, 20, 18, 0, 0, TimeSpan.FromHours(1));   // 18:00 in a UTC+1 country
Console.WriteLine(placed);
Console.WriteLine(placed.UtcDateTime.ToString("u"));
Console.WriteLine(placed.ToOffset(TimeSpan.FromHours(-5)).ToString("yyyy-MM-dd HH:mm zzz"));
Console.WriteLine(placed == placed.ToUniversalTime());   // true: the same moment

Two DateTimeOffset values are equal when they are the same moment, whatever their offsets. Store and send moments as UTC (or with their offset), and convert to local time only to show them.

Calendar values: DateOnly and TimeOnly

C#
var due = new DateOnly(2026, 11, 30);
var today = new DateOnly(2026, 11, 20);
Console.WriteLine($"{due.DayNumber - today.DayNumber} days left, due on a {due.DayOfWeek}");
Console.WriteLine(due.AddMonths(3));          // the end of the month is kept sensible: 28/02/2027 in some cultures

var opens = new TimeOnly(9, 0);
var closes = new TimeOnly(17, 30);
var now = new TimeOnly(18, 15);
Console.WriteLine(now.IsBetween(opens, closes) ? "open" : "closed");
Console.WriteLine(closes - opens);           // 08:30:00

Arithmetic

C#
var start = new DateTime(2026, 1, 31, 0, 0, 0, DateTimeKind.Utc);
Console.WriteLine(start.AddMonths(1).ToString("yyyy-MM-dd"));      // 2026-02-28: no 31st, so the last day
Console.WriteLine(start.AddDays(30).ToString("yyyy-MM-dd"));       // 2026-03-02

TimeSpan t = TimeSpan.FromMinutes(200);
Console.WriteLine($"{t.Hours}h {t.Minutes}m, {t.TotalHours:F2} hours in total");
Console.WriteLine(new DateTime(2026, 12, 25) - new DateTime(2026, 11, 20));

Hours is the hours part (3); TotalHours is the whole length in hours (3.33). Mixing them up is a common bug.

Time zones

A time zone is more than an offset: it has rules for daylight saving time that change over the year and over history. TimeZoneInfo knows them:

C#
var london = TimeZoneInfo.FindSystemTimeZoneById("Europe/London");   // IANA ids work on every system in .NET 6+
var moment = new DateTimeOffset(2026, 7, 1, 12, 0, 0, TimeSpan.Zero);
var there = TimeZoneInfo.ConvertTime(moment, london);
Console.WriteLine(there);      // 01/07/2026 13:00:00 +01:00 (summer time)

Store the zone's id ("Europe/London") with a future appointment, not just an offset, because the offset of a future date can change if the rules change.

Code that asks for the time

DateTime.Now inside a method makes it impossible to test "what happens at midnight". .NET 8 added TimeProvider: pass one in, use TimeProvider.System in the program, and a fake in tests.

C#
Console.WriteLine(new Greeter(new FixedClock(new DateTimeOffset(2026, 11, 20, 8, 0, 0, TimeSpan.Zero))).Greet());
Console.WriteLine(new Greeter(TimeProvider.System).Greet().Length > 0);

class Greeter(TimeProvider clock)
{
    public string Greet() => clock.GetUtcNow().Hour < 12 ? "Good morning" : "Good afternoon";
}

class FixedClock(DateTimeOffset now) : TimeProvider
{
    public override DateTimeOffset GetUtcNow() => now;
}

Culture: how numbers and dates look

1234.5 is written 1,234.50 in the UK, 1.234,50 in Germany and 1 234,50 in France. Formatting and parsing use the current culture unless you say otherwise:

C#
using System.Globalization;

double price = 1234.5;
var date = new DateTime(2026, 11, 20);
foreach (var name in new[] { "en-GB", "de-DE", "fr-FR", "ja-JP" })
{
    var c = CultureInfo.GetCultureInfo(name);
    Console.WriteLine($"{name}: {price.ToString("N2", c)}  {date.ToString("d", c)}  {date.ToString("MMMM", c)}");
}

The rule that prevents the most bugs:

  • Show values to people with their culture (the default).
  • Store and exchange values (files, JSON, logs, URLs) with CultureInfo.InvariantCulture, or fixed formats like ISO 8601.
C#
using System.Globalization;

string saved = 3.75.ToString(CultureInfo.InvariantCulture);           // always "3.75"
double back = double.Parse(saved, CultureInfo.InvariantCulture);
Console.WriteLine($"{saved} {back}");
Console.WriteLine(double.TryParse("3,75", NumberStyles.Float, CultureInfo.InvariantCulture, out _));   // False

A program that saves 3,75 on a German computer and reads it back on an English one gets 375 or an error: that is the bug invariant culture prevents. String comparisons have the same choice: StringComparison.Ordinal for identifiers and keys, culture-aware comparison for sorting names for people.
