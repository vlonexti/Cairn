Unit Testing

lesson 6.022 of 5 in milestone 65 min1 practice task

Writing automated tests with xUnit - test projects, Facts and Theories with InlineData, Arrange-Act-Assert, asserting values, collections and exceptions, testing async code, fakes for dependencies, what makes code testable, test naming, and how a test framework finds and runs tests with attributes and reflection.

Why tests

A unit test is code that runs a small part of your program with known inputs and checks the result. A good test suite lets you change code without fear: if you break something, a test fails within seconds. Every practice task in this course has been checked this way.

xUnit

xUnit is the most common test framework for .NET. A test project references the code under test and contains classes of test methods:

C#
using Xunit;

public class LedgerTests
{
    [Fact]
    public void Deposit_increases_the_balance()
    {
        // Arrange
        var ledger = new Ledger(100m);

        // Act
        ledger.Deposit(25m);

        // Assert
        Assert.Equal(125m, ledger.Balance);
    }

    [Fact]
    public void Withdrawing_too_much_throws()
    {
        var ledger = new Ledger(10m);
        var ex = Assert.Throws<InvalidOperationException>(() => ledger.Withdraw(50m));
        Assert.Contains("not enough", ex.Message);
    }

    [Theory]
    [InlineData(2024, true)]
    [InlineData(1900, false)]
    [InlineData(2000, true)]
    public void Leap_years(int year, bool expected)
    {
        Assert.Equal(expected, Dates.IsLeapYear(year));
    }
}
  • [Fact] marks a test with no parameters; [Theory] with [InlineData(...)] runs the same test for each set of data.
  • Arrange, Act, Assert: set up, do the one thing being tested, check the result.
  • Name tests after the behaviour they check, so a failing name explains the problem.
  • dotnet test builds and runs every test, and reports failures with the expected and actual values.

Assertions

Assertion Checks
Assert.Equal(expected, actual) Values (records and collections compare by content)
Assert.True(cond), Assert.False(cond) Conditions
Assert.Null(x), Assert.NotNull(x) Null
Assert.Contains(item, collection), Assert.Empty(c), Assert.Single(c) Collections
Assert.Throws<T>(() => ...) An exception of exactly type T
await Assert.ThrowsAsync<T>(() => ...) The same for async code
Assert.InRange(x, low, high) Numbers in a range

Async tests return Task: public async Task Loads_settings() { var s = await store.LoadAsync(); Assert.Equal(...); }.

Testable code

Code is easy to test when its dependencies come in from outside. Code that reads DateTime.Now, the file system or the network directly can only be tested by changing the computer's clock or files. Code that receives an IClock, a TextReader or an IWeatherApi (lessons 3.04, 5.03, 5.05) can be given fakes:

C#
var clock = new FixedClock(new DateTime(2026, 3, 31));
var invoices = new InvoiceService(clock);
var invoice = invoices.Create("Ada", 120m);
Console.WriteLine($"{invoice.Due:yyyy-MM-dd} {invoice.Due == new DateTime(2026, 4, 30)}");

public interface IClock { DateTime Today { get; } }
public sealed class FixedClock(DateTime today) : IClock { public DateTime Today => today; }

public record Invoice(string Customer, decimal Amount, DateTime Due);

public class InvoiceService(IClock clock)
{
    public Invoice Create(string customer, decimal amount) => new(customer, amount, clock.Today.AddDays(30));
}

Fakes can be hand-written classes like FixedClock, or made with a mocking library such as NSubstitute or Moq. Hand-written fakes are often clearer for small interfaces.

What to test: the rules and calculations (the class library), the edge cases (empty lists, zero, the last day of a month, invalid input), and every bug you fix (a test that fails before the fix and passes after).

How a test framework works

There is no magic in [Fact]. An attribute is a class that attaches information to code. At run time, reflection lets a program inspect types and their methods, read their attributes, and call them. A test runner finds every public method with [Fact], creates the class, invokes the method, and records whether it threw:

C#
using System.Reflection;

foreach (var (name, passed, error) in MiniRunner.Run(typeof(MathTests)))
    Console.WriteLine($"{(passed ? "PASS" : "FAIL")} {name}{(error is null ? "" : ": " + error)}");

[AttributeUsage(AttributeTargets.Method)]
public sealed class FactAttribute : Attribute { }

public class MathTests
{
    [Fact] public void Adding() { if (2 + 2 != 4) throw new Exception("2 + 2 is not 4"); }
    [Fact] public void Dividing() { if (7 / 2 != 3.5) throw new Exception($"7 / 2 gave {7 / 2}"); }
    public void NotATest() { }
}

public static class MiniRunner
{
    public static IEnumerable<(string Name, bool Passed, string? Error)> Run(Type testClass)
    {
        foreach (MethodInfo method in testClass.GetMethods().Where(m => m.GetCustomAttribute<FactAttribute>() != null).OrderBy(m => m.Name))
        {
            object instance = Activator.CreateInstance(testClass)!;      // a fresh object for every test
            string? error = null;
            try { method.Invoke(instance, null); }
            catch (TargetInvocationException e) { error = e.InnerException?.Message; }
            yield return (method.Name, error is null, error);
        }
    }
}

xUnit does the same with many more features: theories, async tests, parallel runs, fixtures for shared setup. Practice 6.02 builds a fuller runner.
