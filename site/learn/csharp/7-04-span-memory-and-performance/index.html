Span, Memory and Performance

lesson 7.044 of 6 in milestone 75 min2 practice tasks

Writing fast C# without unsafe code - value types and the stack, Span<T> and ReadOnlySpan<T> as views over arrays and strings, slicing without copying, stackalloc, ArrayPool for reusing buffers, ref struct rules, and measuring before optimising.

Where allocations come from

Every new of a class, every string operation that produces a new string, every ToArray() and Substring() puts an object on the heap, and the garbage collector must later clean it up. In most code that cost is invisible. In code that runs millions of times (parsers, games, servers) it adds up. Modern C# gives tools to do the same work without allocating.

Span<T>: a view, not a copy

A Span<T> is a window onto a run of elements that already exist: part of an array, a block on the stack, or memory owned by someone else. Slicing a span makes a new window, not a copy:

C#
int[] numbers = [1, 2, 3, 4, 5, 6];
Span<int> middle = numbers.AsSpan(1, 4);      // 2, 3, 4, 5: no new array
middle[0] = 20;                               // writes into numbers
Console.WriteLine(string.Join(",", numbers)); // 1,20,3,4,5,6
Console.WriteLine(middle[^1]);                // 5
Console.WriteLine(middle.Slice(1, 2).Length); // 2

ReadOnlySpan<T> is the read-only version; a string gives one with AsSpan().

Parsing without Substring

C#
static int SumFields(ReadOnlySpan<char> line)
{
    int total = 0;
    while (true)
    {
        int comma = line.IndexOf(',');
        ReadOnlySpan<char> field = comma < 0 ? line : line[..comma];
        total += int.Parse(field);           // int.Parse accepts a span: no string made
        if (comma < 0) return total;
        line = line[(comma + 1)..];
    }
}

Console.WriteLine(SumFields("10,20,30,40"));    // 100

Split(',') would allocate an array and four strings; this allocates nothing. int.Parse, double.TryParse, string.Concat, StringBuilder.Append, Stream.Read and many more have span overloads.

stackalloc

A small temporary buffer can live on the stack, freed automatically when the method returns:

C#
static string Reverse(string text)
{
    Span<char> buffer = text.Length <= 256 ? stackalloc char[text.Length] : new char[text.Length];
    text.AsSpan().CopyTo(buffer);
    buffer.Reverse();
    return new string(buffer);
}

Console.WriteLine(Reverse("stressed"));    // desserts

Keep stack buffers small (a few hundred bytes to a few KB): the stack is about 1 MB in total.

The rules of ref struct

Span<T> is a ref struct: it may point into the stack, so the compiler makes sure it never outlives what it points at. It cannot be a field of a class, be boxed, be captured by a lambda, or cross an await. When you need a span-like thing that can be stored or used in async code, use Memory<T> / ReadOnlyMemory<T> and call .Span at the moment you work on it.

Reusing buffers: ArrayPool

For large buffers, rent from a pool instead of allocating a new array each time:

C#
using System.Buffers;

byte[] buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);   // may be larger than asked
try
{
    Console.WriteLine(buffer.Length >= 64 * 1024);
    // ... read a file or socket into buffer ...
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}

Structs and in parameters

Small value types (a readonly record struct Vec2) live inline in arrays and locals with no allocation. Passing a large struct copies it; in passes it by reference without allowing changes: static double Length(in Matrix4 m).

Measure first

Most code does not need any of this. Write it clearly, measure with a profiler or BenchmarkDotNet ([MemoryDiagnoser] shows allocations per call), and only then optimise the hot spot you found. Stopwatch is fine for a first look:

C#
using System.Diagnostics;

var watch = Stopwatch.StartNew();
long sum = 0;
for (int i = 0; i < 10_000_000; i++) sum += i;
Console.WriteLine($"{sum} in {watch.ElapsedMilliseconds} ms");
