Dependency Injection and Configuration

lesson 6.033 of 5 in milestone 65 min1 practice task

Building applications from small services - constructor injection, the composition root, Microsoft.Extensions.DependencyInjection with singleton, scoped and transient lifetimes, the generic host, configuration from appsettings.json, environment variables and user secrets bound to options classes, logging with ILogger, and how a container resolves constructors.

Constructor injection

Dependency injection means a class receives the services it needs through its constructor instead of creating them itself:

C#
// Wires everything together in one place: the "composition root".
IClock clock = new SystemClock();
INotifier notifier = new ConsoleNotifier();
var reminders = new ReminderService(clock, notifier);
reminders.Check(new[] { ("Pay rent", DateTime.Today.AddDays(-1)), ("Call Ada", DateTime.Today.AddDays(3)) });

public interface IClock { DateTime Now { get; } }
public interface INotifier { void Notify(string message); }

public sealed class SystemClock : IClock { public DateTime Now => DateTime.Now; }
public sealed class ConsoleNotifier : INotifier { public void Notify(string message) => Console.WriteLine($"[notice] {message}"); }

public class ReminderService(IClock clock, INotifier notifier)
{
    public void Check(IEnumerable<(string Task, DateTime Due)> items)
    {
        foreach (var (task, due) in items)
            if (due < clock.Now) notifier.Notify($"{task} is overdue");
    }
}

ReminderService does not know whether it prints to a console, sends an email or writes to a test list. Each class has one job, depends on interfaces, and is testable with fakes (lesson 6.02).

A container

In a big application, building every object by hand gets long. A DI container does it: you register which implementation goes with each interface, and it resolves a class by creating its constructor's arguments, and theirs, recursively.

C#
using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection();
services.AddSingleton<IClock, SystemClock>();          // one instance for the whole app
services.AddTransient<INotifier, ConsoleNotifier>();   // a new instance every time
services.AddScoped<IUnitOfWork, UnitOfWork>();          // one per scope (in a web app: per request)
services.AddTransient<ReminderService>();

using var provider = services.BuildServiceProvider();
var reminders = provider.GetRequiredService<ReminderService>();
Lifetime One instance Use for
Singleton For the whole application Stateless services, caches, HttpClient factories, configuration
Scoped Per scope (a web request) Database contexts, per-request state
Transient Per resolution Light services with no shared state

Never inject a scoped or transient service into a singleton: the singleton would keep it forever. Practice 6.03 builds a small container with reflection to show how resolution works.

The generic host

Microsoft.Extensions.Hosting combines DI, configuration and logging, and is how ASP.NET Core, worker services and well-structured console apps start:

C#
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

var builder = Host.CreateApplicationBuilder(args);
builder.Services.Configure<ReminderOptions>(builder.Configuration.GetSection("Reminders"));
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddSingleton<INotifier, ConsoleNotifier>();
builder.Services.AddHostedService<ReminderWorker>();       // a background service that runs until stopped
using IHost host = builder.Build();
await host.RunAsync();

Configuration

Settings should not be hard-coded. Configuration is read from several providers, later ones overriding earlier ones:

  1. appsettings.json
  2. appsettings.{Environment}.json (for example appsettings.Development.json)
  3. user secrets during development (kept outside the project folder, never committed)
  4. environment variables (Reminders__CheckEveryMinutes=5: a double underscore separates sections)
  5. command-line arguments (--Reminders:CheckEveryMinutes 5)
JSON
{
  "Reminders": { "CheckEveryMinutes": 15, "Channel": "email" },
  "Logging": { "LogLevel": { "Default": "Information" } }
}

Bind a section to a class with the options pattern, and inject IOptions<T>:

C#
public sealed class ReminderOptions
{
    public int CheckEveryMinutes { get; set; } = 10;
    public string Channel { get; set; } = "console";
}

public class ReminderWorker(IOptions<ReminderOptions> options, ILogger<ReminderWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var every = TimeSpan.FromMinutes(options.Value.CheckEveryMinutes);
        while (!stoppingToken.IsCancellationRequested)
        {
            logger.LogInformation("Checking reminders via {Channel}", options.Value.Channel);
            await Task.Delay(every, stoppingToken);
        }
    }
}

Secrets (API keys, connection strings with passwords) belong in user secrets during development and in environment variables or a secret store in production, never in appsettings.json in source control.

Logging

ILogger<T> is injected like any service. Use message templates with named placeholders rather than interpolated strings: logger.LogWarning("Order {OrderId} failed after {Attempts} attempts", id, n). Structured logging tools then store OrderId and Attempts as searchable fields.
