Desktop UI and MVVM

lesson 6.044 of 5 in milestone 65 min1 practice task

Building desktop applications with C# - the choices (WinForms, WPF, WinUI, Avalonia, .NET MAUI), event-driven UI and the UI thread, XAML and data binding, the MVVM pattern with INotifyPropertyChanged, ObservableCollection and ICommand, keeping the UI responsive with async, and testing view models without a window.

The choices

Framework Runs on Notes

WPF Windows XAML markup, data binding, rich styling; very widely used

Avalonia Windows, macOS, Linux WPF-like XAML that runs everywhere

This lesson's ideas apply to all of them. The practice sandbox has no screen, so UI code here is for reading; the view model logic below runs anywhere and is what the practice tests.

Event-driven code and the UI thread

A UI program waits for events: a click, a key, a timer. Each handler runs on the UI thread, the one thread allowed to touch the window. While a handler runs, the window cannot redraw or respond. So handlers must be quick, and slow work must be awaited (lesson 5.01):

C#
// WinForms: a button's Click event
private async void LoadButton_Click(object sender, EventArgs e)    // async void is right for event handlers
{
    loadButton.Enabled = false;
    statusLabel.Text = "Loading...";
    try
    {
        var report = await _service.LoadReportAsync();   // the window stays responsive while waiting
        reportGrid.DataSource = report.Rows;              // back on the UI thread after await
    }
    catch (HttpRequestException ex)
    {
        MessageBox.Show(this, ex.Message, "Could not load");
    }
    finally
    {
        loadButton.Enabled = true;
        statusLabel.Text = "";
    }
}

XAML and binding

WPF, WinUI, Avalonia and MAUI describe windows in XAML and connect them to data with bindings:

xml
<StackPanel Margin="12">
  <TextBox Text="{Binding NewTitle, UpdateSourceTrigger=PropertyChanged}" />
  <Button Content="Add" Command="{Binding AddCommand}" />
  <ListBox ItemsSource="{Binding Items}" />
  <TextBlock Text="{Binding Summary}" />
</StackPanel>

{Binding NewTitle} keeps the text box and the NewTitle property of the window's DataContext in sync, in both directions. The XAML contains no logic at all.

MVVM

Model-View-ViewModel separates a UI into three parts:

  • Model: the domain data and rules (your class library).
  • View: the XAML window: layout and looks only.
  • ViewModel: a plain class exposing what the view shows (properties) and does (commands). It knows nothing about controls.

For bindings to notice changes, the view model implements INotifyPropertyChanged, lists use ObservableCollection<T>, and actions are ICommands:

C#
using System.Collections.ObjectModel;
using System.ComponentModel;
using System.Runtime.CompilerServices;
using System.Windows.Input;

var vm = new TodoViewModel();
vm.PropertyChanged += (_, e) => Console.WriteLine($"changed: {e.PropertyName}");
Console.WriteLine(vm.AddCommand.CanExecute(null));
vm.NewTitle = "Buy tea";
Console.WriteLine(vm.AddCommand.CanExecute(null));
vm.AddCommand.Execute(null);
Console.WriteLine($"{vm.Items.Count} item, title now '{vm.NewTitle}', {vm.Summary}");

public abstract class ViewModelBase : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    protected bool Set<T>(ref T field, T value, [CallerMemberName] string? name = null)
    {
        if (EqualityComparer<T>.Default.Equals(field, value)) return false;
        field = value;
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
        return true;
    }

    protected void Raise(string name) => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
}

public sealed class RelayCommand(Action execute, Func<bool> canExecute) : ICommand
{
    public event EventHandler? CanExecuteChanged;
    public bool CanExecute(object? parameter) => canExecute();
    public void Execute(object? parameter) { if (CanExecute(parameter)) execute(); }
    public void NotifyCanExecuteChanged() => CanExecuteChanged?.Invoke(this, EventArgs.Empty);
}

public sealed class TodoViewModel : ViewModelBase
{
    private string _newTitle = "";
    public ObservableCollection<string> Items { get; } = new();
    public RelayCommand AddCommand { get; }

    public TodoViewModel()
    {
        AddCommand = new RelayCommand(Add, () => !string.IsNullOrWhiteSpace(NewTitle));
        Items.CollectionChanged += (_, _) => Raise(nameof(Summary));
    }

    public string NewTitle
    {
        get => _newTitle;
        set { if (Set(ref _newTitle, value)) AddCommand.NotifyCanExecuteChanged(); }
    }

    public string Summary => Items.Count == 1 ? "1 item" : $"{Items.Count} items";

    private void Add()
    {
        Items.Add(NewTitle.Trim());
        NewTitle = "";
    }
}

[CallerMemberName] fills in the property's name automatically. The CommunityToolkit.Mvvm package generates this plumbing from attributes ([ObservableProperty], [RelayCommand]), but it is worth knowing what it writes.

Why MVVM pays off

The whole behaviour of the screen (when Add is enabled, what the summary says, what happens after adding) is in TodoViewModel, an ordinary class. It is tested like any other code, without opening a window, which is exactly what practice 6.04 does. The view can be redesigned without touching the logic, and the same view model can serve a WPF and an Avalonia view.
