Solutions, Projects and NuGet

lesson 6.011 of 5 in milestone 65 min1 practice task

How real .NET code is organised - the .csproj file and its key settings, solutions with several projects, class libraries and project references, NuGet packages and versions, the dotnet CLI for building, testing, running and publishing, build configurations, and a sensible folder layout.

Projects

A project is a folder with a .csproj file and the source files under it. It builds into one assembly (a .dll, or an executable). The project file is short XML:

xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net9.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Spectre.Console" Version="0.49.1" />
    <ProjectReference Include="..\Budget.Core\Budget.Core.csproj" />
  </ItemGroup>
</Project>
Setting Meaning
OutputType Exe for a program; leave it out for a class library
TargetFramework The .NET version to build for: net9.0, net8.0
Nullable Turns on nullable reference warnings (lesson 2.05): always enable
ImplicitUsings Adds global usings for System, LINQ, collections and more
TreatWarningsAsErrors Makes every warning stop the build: a good habit

Every .cs file under the folder is compiled automatically; you do not list them.

Solutions and libraries

A solution (.sln or the newer .slnx) groups related projects. A typical application splits its code:

Text
Budget/
  Budget.sln
  src/
    Budget.Core/          class library: the domain and rules, no I/O
      Budget.Core.csproj
      Ledger.cs
      Transaction.cs
    Budget.Cli/           the console program: input, output, files
      Budget.Cli.csproj   (references Budget.Core)
      Program.cs
  tests/
    Budget.Core.Tests/    unit tests for the library (lesson 6.02)
      Budget.Core.Tests.csproj

Keeping the logic in a class library with no console or file code means a test project, a desktop UI and a web API can all reuse it. A ProjectReference makes one project use another; public types of the library are visible to it, internal ones are not.

The dotnet CLI

Terminal
dotnet new sln -n Budget
dotnet new classlib -o src/Budget.Core
dotnet new console -o src/Budget.Cli
dotnet new xunit -o tests/Budget.Core.Tests
dotnet sln add src/Budget.Core src/Budget.Cli tests/Budget.Core.Tests
dotnet add src/Budget.Cli reference src/Budget.Core
dotnet add tests/Budget.Core.Tests reference src/Budget.Core

dotnet build                  # compile everything
dotnet test                   # run all test projects
dotnet run --project src/Budget.Cli -- report 2026-03    # arguments after -- go to the program
dotnet publish src/Budget.Cli -c Release -r win-x64 --self-contained   # a folder you can ship

Builds come in configurations: Debug (the default, easy to debug) and Release (optimised, for shipping): dotnet build -c Release.

NuGet packages

NuGet is .NET's package manager. dotnet add package Name downloads a package and adds a PackageReference with its version:

Terminal
dotnet add src/Budget.Cli package Spectre.Console
dotnet list package --outdated      # newer versions available
dotnet list package --vulnerable    # known security problems

Versions follow semantic versioning (MAJOR.MINOR.PATCH); a plain version like 0.49.1 means "this version or higher, preferring the lowest that works". Packages that every .NET developer meets:

Package For
Microsoft.Extensions.Hosting Dependency injection, configuration and logging (lesson 6.03)
xunit, NUnit, MSTest Unit testing (lesson 6.02)
Spectre.Console Rich console output: tables, colours, prompts
CsvHelper Reading and writing CSV
Dapper, Microsoft.EntityFrameworkCore Databases
Serilog Structured logging

Every package is code from someone else that runs with your program's permissions. Prefer well-known packages, check how actively they are maintained, and keep them updated.

Reading a project file in code

Project files are XML, which System.Xml.Linq reads easily. Tools that report on many projects (which packages are used where, which projects target an old framework) do exactly this:

C#
using System.Xml.Linq;

var xml = XDocument.Parse("""
    <Project Sdk="Microsoft.NET.Sdk">
      <PropertyGroup><TargetFramework>net9.0</TargetFramework></PropertyGroup>
      <ItemGroup>
        <PackageReference Include="Serilog" Version="4.0.1" />
        <PackageReference Include="CsvHelper" Version="33.0.1" />
      </ItemGroup>
    </Project>
    """);
Console.WriteLine(xml.Descendants("TargetFramework").First().Value);
foreach (var p in xml.Descendants("PackageReference"))
    Console.WriteLine($"{p.Attribute("Include")?.Value} {p.Attribute("Version")?.Value}");
