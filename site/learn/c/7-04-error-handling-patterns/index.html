Error Handling Patterns

lesson 7.044 of 5 in milestone 75 min2 practice tasks

How C programs report and recover from failure - return codes and out-parameters, errno with strerror and perror, an error enum with messages, cleaning up with a single goto exit, assert for programmer mistakes, and setjmp and longjmp for jumping out of deep calls.

C has no exceptions

When a C function fails, it has to say so through its return value or through a variable the caller checks. The caller must check every call that can fail, and clean up whatever it already acquired. This lesson collects the patterns real C code uses.

Return codes and out-parameters

The common shape: the return value says whether it worked, and the actual result comes back through a pointer:

C
#include <errno.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>

/* Parses a whole decimal int. Returns 0 on success, -1 on failure; the value goes to *out. */
int parse_int(const char *text, int *out)
{
    char *end;
    errno = 0;
    long v = strtol(text, &end, 10);
    if (end == text || *end != '\0') return -1;          /* nothing read, or junk after the number */
    if (errno == ERANGE || v < INT_MIN || v > INT_MAX) return -1;
    *out = (int)v;
    return 0;
}

int main(void)
{
    const char *inputs[] = { "42", "-7", "12abc", "", "99999999999" };
    for (int i = 0; i < 5; i++)
    {
        int n;
        if (parse_int(inputs[i], &n) == 0) printf("\"%s\" -> %d\n", inputs[i], n);
        else printf("\"%s\" is not an int\n", inputs[i]);
    }
    return 0;
}

Conventions vary (0 for success in system APIs, a pointer that is NULL on failure, a count that is negative on failure), so read each function's documentation.

errno

Many library functions report why they failed by setting the global errno (lesson 5.03). strerror(errno) turns it into text and perror prints it with a prefix:

C
#include <errno.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    FILE *f = fopen("no/such/folder/file.txt", "r");
    if (f == NULL)
    {
        int saved = errno;                   /* save it before calling anything else */
        printf("could not open: %s\n", strerror(saved));
        printf("was it 'not found'? %s\n", saved == ENOENT ? "yes" : "no");
        return 0;                            /* a real program would return a non-zero code here */
    }
    fclose(f);
    return 0;
}

errno is only meaningful straight after a call that failed; a successful call may leave any value in it. Copy it at once, because the next library call (even printf) may change it.

An error enum with messages

For your own code, an enum of error codes and one function that names them reads better than magic numbers:

C
#include <stdio.h>

enum result { OK = 0, ERR_EMPTY, ERR_TOO_LONG, ERR_BAD_CHAR };

const char *result_text(enum result r)
{
    static const char *const text[] = { "ok", "the name is empty", "the name is too long", "the name has a bad character" };
    return (unsigned)r < sizeof text / sizeof text[0] ? text[r] : "unknown error";
}

enum result check_name(const char *name)
{
    if (name[0] == '\0') return ERR_EMPTY;
    int length = 0;
    for (const char *c = name; *c; c++, length++)
        if (!((*c >= 'a' && *c <= 'z') || *c == '_')) return ERR_BAD_CHAR;
    return length > 12 ? ERR_TOO_LONG : OK;
}

int main(void)
{
    const char *names[] = { "ada", "", "Ada", "a_very_long_name_indeed" };
    for (int i = 0; i < 4; i++) printf("%-24s %s\n", names[i], result_text(check_name(names[i])));
    return 0;
}

Clean up with one goto

A function that acquires several resources must release exactly those it got, whichever step fails. Nested ifs get deep quickly; the standard C idiom is a single cleanup section at the end, reached with goto:

C
#include <stdio.h>
#include <stdlib.h>

/* Copies the first line of src into a newly allocated string. Returns NULL on any failure. */
char *first_line_copy(const char *path)
{
    char *result = NULL;
    char *buffer = malloc(256);
    if (buffer == NULL) goto done;

    FILE *f = fopen(path, "r");
    if (f == NULL) goto free_buffer;

    if (fgets(buffer, 256, f) == NULL) goto close_file;
    result = buffer;
    buffer = NULL;                  /* ownership moved to result: do not free it below */

close_file:
    fclose(f);
free_buffer:
    free(buffer);
done:
    return result;
}

int main(void)
{
    char *line = first_line_copy("does-not-exist.txt");
    printf("%s\n", line ? line : "(nothing)");
    free(line);
    return 0;
}

The labels are in reverse order of acquiring, so each failure jumps to the point that releases what was acquired before it. This is the one place where goto is widely recommended in C; the Linux kernel is full of it.

assert is for bugs, not for input

assert(condition) (lesson 6.02's undefined behaviour lesson used it) stops the program when a condition the programmer guarantees turns out false. It is removed entirely when compiling with -DNDEBUG, so it must never be used to check user input, files or malloc results: those failures are expected and need real handling.

setjmp and longjmp

setjmp saves the current point of execution; longjmp jumps back to it from any depth of function calls, like a very crude exception:

C
#include <setjmp.h>
#include <stdio.h>

static jmp_buf on_error;

int parse_digit(char c)
{
    if (c < '0' || c > '9') longjmp(on_error, c);    /* never returns */
    return c - '0';
}

int sum_digits(const char *s)
{
    int total = 0;
    for (; *s; s++) total += parse_digit(*s);
    return total;
}

int main(void)
{
    const char *inputs[] = { "1234", "12x4" };
    for (int i = 0; i < 2; i++)
    {
        int bad = setjmp(on_error);                   /* 0 the first time; the longjmp value later */
        if (bad == 0) printf("%s -> %d\n", inputs[i], sum_digits(inputs[i]));
        else printf("%s has a bad character '%c'\n", inputs[i], bad);
    }
    return 0;
}

It skips every function in between without cleaning anything up: memory they allocated leaks and files stay open. It suits interpreters and parsers that allocate from an arena they can throw away; for ordinary code, return codes are clearer.
