Memory Bugs

lesson 4.066 of 6 in milestone 45 min1 practice task

Overflows, use after free, double frees, leaks and uninitialised reads often run without any visible problem - until they don't. AddressSanitizer adds checks around every memory access and reports the exact line, and Valgrind does it without rebuilding. Warnings and simple habits prevent most of them in the first place.

Silent bugs

C trusts you. When a program writes past the end of an array, nothing stops it: the write lands on whatever is next. It might crash at once, crash minutes later somewhere unrelated, print wrong results, or work perfectly on your computer and fail on someone else's. These bugs are the reason most serious security holes in C programs exist.

Bug Example
buffer overflow int a[4]; a[4] = 1;
use after free free(p); p->x = 1;
double free free(p); free(p);
memory leak malloc with no free
uninitialised read int x; if (x > 0) ...
returning a local's address return &local;

AddressSanitizer

AddressSanitizer (ASan) is built into GCC and Clang. Compiling with -fsanitize=address makes the compiler add a check before every memory access and keep a "shadow" map of which bytes may be touched. The moment a program steps out of bounds, it stops with a report showing the bad access, the line, and where the memory came from.

On this website, turn it on with Memory checks (AddressSanitizer) in the editor's menu, then run this:

C
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *scores = malloc(4 * sizeof *scores);
    if (scores == NULL) return 1;
    for (int i = 0; i <= 4; i++) {      // one too many
        scores[i] = i * 10;
    }
    printf("%d\n", scores[0]);
    free(scores);
    return 0;
}

Without memory checks, it probably prints 0 and looks fine. With them, it stops with heap-buffer-overflow and points at the line inside the loop: "0 bytes after 16-byte region", which is exactly the fifth int of a four-int block.

The website's memory checks also switch on UndefinedBehaviorSanitizer (-fsanitize=undefined), which catches things like signed integer overflow and shifts by too much (lesson 6.02).

Use it all the time while developing

Programs run about twice as slowly with ASan, which hardly matters while you are testing. Professional C projects run their whole test suite with sanitizers on.

Valgrind

On Linux, Valgrind runs an ordinary, unchanged program inside a simulated processor and checks every access. It is slower (20 to 50 times) but needs no recompiling, and its leak report at the end lists every block that was never freed:

Output
$ valgrind --leak-check=full ./program
==1234== 40 bytes in 1 blocks are definitely lost in loss record 1 of 1
==1234==    at 0x483B7F3: malloc
==1234==    by 0x109162: main (program.c:6)

ASan finds leaks too, when the program ends (on Linux).

Habits that prevent them

  • Compile with -Wall -Wextra and fix every warning: uninitialised variables and returned local addresses are warnings.
  • Give every variable a value when it is declared, pointers included (NULL if nothing else).
  • Keep the size next to the pointer, and use size_t and < for loops: for (size_t i = 0; i < count; i++).
  • Use the length-taking functions: snprintf and fgets, never gets (removed from C) or sprintf into a small buffer.
  • Decide who owns every heap block, and free it in one place. Set the pointer to NULL afterwards.
  • For every malloc, check NULL.

Why other languages exist

Every one of these bugs is impossible in safe Rust, which checks ownership at compile time, and in garbage-collected languages like Python and Java, which free memory for you and check every index. C gives up those checks for speed and control. That trade-off is why the C you write today should be tested with sanitizers, and why parts of Linux, Windows and Android are now being written in Rust.
