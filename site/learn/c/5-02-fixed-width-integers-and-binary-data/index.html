Fixed-Width Integers and Binary Data

lesson 5.022 of 5 in milestone 55 min2 practice tasks

The size of int and long depends on the system, so stdint.h gives types of exact sizes like uint8_t and int64_t, printed with the macros in inttypes.h. Writing a number's bytes in a fixed order with shifts makes data that every machine reads the same way, whatever its endianness.

How big is an int?

The C standard only promises minimums: int at least 16 bits, long at least 32. On 64-bit Linux and Mac long is 64 bits; on 64-bit Windows it is 32. When the exact size matters (file formats, network messages, hardware), use stdint.h:

Type Size Range
int8_t / uint8_t 8 bits −128 to 127 / 0 to 255
int16_t / uint16_t 16 bits −32,768 to 32,767 / 0 to 65,535
int32_t / uint32_t 32 bits about ±2.1 billion / 0 to 4.29 billion
int64_t / uint64_t 64 bits about ±9.2 × 10¹⁸ / 0 to 1.8 × 10¹⁹

Also size_t for sizes, intptr_t for an integer big enough to hold a pointer, and limits such as INT32_MAX and UINT8_MAX.

Printing them

printf has no letter for uint32_t, because its real type differs between systems. inttypes.h provides the right format as a macro that joins onto the string:

C
#include <inttypes.h>
#include <stdio.h>

int main(void)
{
    uint8_t small = 250;
    int64_t big = INT64_MAX;
    uint32_t hex = 0xDEADBEEF;
    small += 10;                                // wraps to 4
    printf("%" PRIu8 " %" PRId64 " %" PRIX32 "\n", small, big, hex);
    printf("sizes: %zu %zu %zu\n", sizeof(uint8_t), sizeof(int64_t), sizeof(long));
    return 0;
}

"%" PRIu8 becomes something like "%hhu"; adjacent strings in C are glued together by the compiler.

Bytes in memory: endianness

A uint32_t is 4 bytes, but which comes first? x86 and ARM computers are little-endian: the lowest byte is stored first.

Interactive demo. This part of the lesson is a working model you can step through in Xenon. Try it in Xenon
C
#include <stdint.h>
#include <stdio.h>

int main(void)
{
    uint32_t value = 0x11223344;
    const unsigned char *bytes = (const unsigned char *)&value;
    for (int i = 0; i < 4; i++) {
        printf("%02x ", bytes[i]);      // 44 33 22 11 on a little-endian machine
    }
    printf("\n");
    return 0;
}

Looking at any object's bytes through an unsigned char * is always allowed in C.

Writing a fixed order with shifts

If a program writes a number's raw bytes into a file, a big-endian machine would read them back wrongly. File formats and network protocols therefore fix the order. Shifts produce it on any machine:

C
#include <stdint.h>
#include <stdio.h>

void put_u32_be(unsigned char *out, uint32_t v)     // big-endian: most significant first
{
    out[0] = (unsigned char)(v >> 24);
    out[1] = (unsigned char)(v >> 16);
    out[2] = (unsigned char)(v >> 8);
    out[3] = (unsigned char)v;
}

uint32_t get_u32_be(const unsigned char *in)
{
    return (uint32_t)in[0] << 24 | (uint32_t)in[1] << 16 | (uint32_t)in[2] << 8 | in[3];
}

int main(void)
{
    unsigned char buffer[4];
    put_u32_be(buffer, 0xCAFEBABE);
    printf("%02x %02x %02x %02x\n", buffer[0], buffer[1], buffer[2], buffer[3]);
    printf("%08x\n", get_u32_be(buffer));
    return 0;
}

The shifts work on the value, not on memory, so this code gives the same bytes everywhere. Networks use big-endian ("network byte order"); most file formats today (PNG is an exception) use little-endian.

Cast before shifting up

in[0] << 24 first turns in[0] into a signed int; a byte of 0x80 or more then overflows into the sign bit. (uint32_t)in[0] << 24 is safe.

A hex dump

Programmers inspect binary data as hex: 16 bytes per line, with the printable characters at the side. Tools like xxd and hexdump do it, and you will write one:

Output
00000000  48 65 6c 6c 6f 2c 20 43 21 0a 00 ff              |Hello, C!...|
