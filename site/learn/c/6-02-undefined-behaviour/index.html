Undefined Behaviour

lesson 6.022 of 5 in milestone 65 min1 practice task

For some mistakes the C standard sets no rules at all - signed overflow, out-of-bounds access, using freed memory, dividing by zero. The optimiser assumes they never happen and builds on that assumption, so their effects can be strange and far away. Learn the list, compile with warnings, and test with sanitizers.

Three kinds of "it depends"

Kind Means Example
implementation-defined each compiler chooses and documents it the size of long, whether char is signed
unspecified one of several outcomes, not documented which argument of f(a(), b()) is worked out first
undefined the standard says nothing at all: anything may happen INT_MAX + 1, a[10] in an int a[10]

Undefined behaviour (UB) is not "a random value" or "a crash". The compiler is allowed to assume it never happens, and it optimises on that basis.

The usual suspects

  • signed integer overflow: INT_MAX + 1
  • reading or writing outside an object: arrays, strings without terminators
  • using a pointer after free, or to a local that has gone
  • dereferencing NULL
  • dividing by zero, or INT_MIN / -1
  • shifting by a negative amount or by the width of the type or more
  • reading an uninitialised local
  • changing a variable twice without a sequence point: i = i++ + 1;
  • modifying a string literal
  • a non-void function falling off its end when the caller uses the result

How the optimiser uses it

C
#include <limits.h>
#include <stdio.h>

int will_overflow(int x)
{
    int bigger = x + 1;
    return bigger < x;      // only true if x + 1 overflowed
}

int main(void)
{
    printf("%d\n", will_overflow(INT_MAX));
    return 0;
}

At -O0 (the website's normal build) this prints 1: the addition wraps and the test sees it. Switch the build to Release (click Debug in the editor's status bar), which compiles with -O2, and GCC prints 0, because it reasons: "signed overflow cannot happen, so x + 1 is always bigger than x", and replaces the whole function with return 0. (Written as one expression, return x + 1 < x;, GCC removes it even in a debug build.) Neither answer is a bug in GCC. The program had none to give.

Real damage happens the same way. In 2009 a Linux kernel driver read a field through a pointer before checking the pointer for NULL. Since dereferencing NULL is UB, the compiler concluded the pointer could not be NULL and deleted the check, which created a security hole.

Check before the operation, not after

To find out whether a + b would overflow, test first: if (b > 0 && a > INT_MAX - b). Or use the builtins: __builtin_add_overflow(a, b, &result) returns true on overflow (C23 adds ckd_add in stdckdint.h).

Unsigned arithmetic is safe

Unsigned types are defined to wrap around: UINT_MAX + 1u is 0, always. That is why hash functions and checksums use uint32_t or uint64_t.

Defending yourself

  • -Wall -Wextra catch many cases at compile time.
  • Memory checks in the editor's menu turn on AddressSanitizer and UndefinedBehaviorSanitizer, which report each overflow, bad shift or bad memory access as it happens, with a message such as runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'.
  • Prefer size_t for sizes and indexes, and unsigned types for bit work.
  • Keep functions small enough to check every path by eye.
