Building a Hash Table

lesson 6.055 of 5 in milestone 65 min1 practice task

A hash table finds a value by its key in about constant time. A hash function turns the key into a number, which picks a bucket in an array; keys that land in the same bucket are chained in a short linked list. When the table gets too full it grows and every entry moves to its new bucket. It is the structure behind Python's dict.

Looking things up fast

Finding a word in an unsorted array means checking every element: with a million words, a million comparisons. A sorted array with binary search needs about 20. A hash table needs about one.

The idea: turn the key into a number with a hash function, and use that number (modulo the table size) as an index into an array of buckets.

A hash function

A good hash function spreads keys evenly, so similar keys land far apart. FNV-1a is short and decent:

C
#include <stdint.h>
#include <stdio.h>

uint32_t hash_fnv1a(const char *key)
{
    uint32_t h = 2166136261u;            // the FNV offset basis
    for (const unsigned char *p = (const unsigned char *)key; *p; p++) {
        h ^= *p;
        h *= 16777619u;                  // the FNV prime; unsigned, so overflow wraps safely
    }
    return h;
}

int main(void)
{
    const char *words[] = {"cat", "cats", "act", "dog"};
    for (int i = 0; i < 4; i++) {
        uint32_t h = hash_fnv1a(words[i]);
        printf("%-5s %10u  bucket %u of 8\n", words[i], h, h % 8);
    }
    return 0;
}

cat and cats differ by one letter but get completely different hashes. That is what a good hash function does.

Collisions: chaining

Two keys can land in the same bucket: a collision. The simplest fix is separate chaining: each bucket holds a linked list (lesson 4.05) of the entries that landed there.

C
struct entry {
    char *key;              // our own copy of the text
    int value;
    struct entry *next;     // the next entry in the same bucket
};

struct table {
    struct entry **buckets; // an array of list heads
    size_t bucket_count;
    size_t size;            // entries stored
};
  • Find: hash the key, walk that bucket's list comparing keys with strcmp.
  • Insert: find first; if the key exists, update its value; otherwise push a new entry on the front of the bucket's list.
  • Remove: unlink from the bucket's list, with the pointer-to-link trick from lesson 4.05, and free the key and the entry.

Keeping it fast: the load factor

The load factor is entries ÷ buckets. While it stays below about 1, each list is short and every operation is about one step. When it passes a limit (often 0.75 or 1), the table grows: allocate twice as many buckets and move every entry to hash % new_count. Each entry moves only now and then, so on average insertion stays constant time, the same argument as the doubling array in lesson 4.02.

Ownership

The table should copy the keys it stores, because the caller's text may be a buffer that gets reused for the next line of input. That means the table also frees them: one table_free walks every bucket, frees each key and entry, then frees the bucket array.

Where they are

Python's dict and set, JavaScript objects and Map, C++'s unordered_map, Rust's HashMap, database indexes, compiler symbol tables, caches: hash tables everywhere. Many use open addressing instead of chaining (a collision tries the next free slot in the array itself), which keeps everything in one block of memory and suits caches better. The project at the end of this module is a word counter built on your own table.

Attacks on hash tables

If an attacker can choose keys that all hash to the same bucket, every lookup becomes a long list walk and a server slows to a crawl. Languages defend against this with seeded hash functions (SipHash in Python and Rust) whose results depend on a random secret chosen at startup.
