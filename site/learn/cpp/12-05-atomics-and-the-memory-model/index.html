Atomics and the Memory Model

lesson 12.055 of 7 in milestone 127 min2 practice tasks

std::atomic<T> makes individual operations on a variable indivisible, so counters and flags need no mutex. The memory model defines what other threads are guaranteed to observe: compilers and processors reorder work, and memory orders constrain that. The default, seq_cst, is the safest; weaken it only with proof.

std::atomic

An operation is atomic if no other thread can observe it half-done.

C++
#include <atomic>
#include <iostream>
#include <thread>

int main()
{
    std::atomic<int> counter{ 0 };
    auto increment{ [&]
    {
        for (int i{ 0 }; i < 1'000'000; ++i)
        {
            ++counter;
        }
    } };

    {
        std::jthread a{ increment };
        std::jthread b{ increment };
    }
    std::cout << counter << '\n';    // exactly 2000000
    return 0;
}

Compare with the lost updates in 12.02 Data Races, Mutexes and Locks. Here ++counter is a single indivisible read-modify-write. Access to an atomic object is never a data race.

Operation Meaning
x.load(), x.store(v) Read; write
x++, x += 5, x.fetch_add(5) Atomic read-modify-write
x.exchange(v) Store v and return the previous value
x.compare_exchange_weak(expected, desired) If x equals expected, store desired; otherwise copy x into expected
x.wait(old), x.notify_one() (C++20) Block until the value changes from old
std::atomic_flag A boolean flag guaranteed to be lock-free

For small types, atomics are implemented with single processor instructions and are lock-free: no thread ever blocks. For larger types the library may use a hidden lock; is_always_lock_free tells you which.

Atomic variables do not make atomic logic
C++
if (x == 0) { x = 1; }    // two operations: another thread can act in between

Each step is atomic and the sequence is not. Use a compare-exchange, or a mutex.

Compare-and-swap

compare_exchange is the building block of lock-free code: "change the value only if nobody else changed it first".

C++
std::atomic<int> maxSeen{ 0 };

void updateMax(int value)
{
    int current{ maxSeen.load() };
    while (value > current && !maxSeen.compare_exchange_weak(current, value))
    {
        // the exchange failed: current now holds the latest value, so the test is repeated
    }
}

The loop reads the current value, computes, and tries to install the result. If another thread got in first, the exchange fails, refreshes current, and the loop tries again. The weak form may fail spuriously and is meant for loops; compare_exchange_strong fails only when the values differ.

Why ordering matters

A compiler may reorder statements that do not depend on each other, and a processor may execute and commit them out of order. A single thread can never tell. Another thread can.

C++
int data{ 0 };
bool ready{ false };    // not atomic

// Thread A                    // Thread B
data = 42;                     while (!ready) {}
ready = true;                  std::cout << data << '\n';

Thread A's two writes are independent, so they may take effect as ready = true; data = 42;. Thread B might print 0. It might also loop for ever, because the compiler sees a loop that never modifies ready and reads it once. And all of it is a data race, so nothing is guaranteed at all.

The memory model is the part of the standard that says which orderings a program may rely on.

Memory orders

Every atomic operation takes an optional memory order describing how strongly it is ordered relative to other operations.

C++
std::atomic<bool> ready{ false };
int data{ 0 };

// Thread A: the producer
data = 42;
ready.store(true, std::memory_order_release);

// Thread B: the consumer
while (!ready.load(std::memory_order_acquire)) {}
std::cout << data << '\n';    // guaranteed to print 42
flowchart LR

    A2 -.->|"synchronizes with"| B1

A release store and an acquire load that reads the stored value form a pair. Everything thread A did before the store is visible to thread B after the load. That relationship is called happens-before: if A happens-before B, B sees A's effects. Here the plain variable data is safely handed over, with no data race.

Order Guarantee Typical use
memory_order_seq_cst (the default) All such operations appear in one global order that every thread agrees on Everything, unless measured otherwise
memory_order_release / memory_order_acquire The pairing described above Publishing data; implementing locks
memory_order_acq_rel Both, for a read-modify-write Lock-free data structures
memory_order_relaxed Atomicity only; no ordering Statistics counters read at the end

The weaker orders exist because the strongest costs more on some processors. On x86 the difference is small; on ARM it can be significant.

Lock-free programming is specialist work

Code using weak orders can be wrong in ways that appear once a month, on one processor family, under load. Use a mutex first. Move to atomics only when profiling shows the lock is the bottleneck, keep the default order unless you can argue the weaker one is correct, and test with ThreadSanitizer.

False sharing

Processors cache memory in blocks of typically 64 bytes, called cache lines. When two threads write to different variables that happen to share a cache line, each write invalidates the other core's copy of the whole line. The threads share no data, yet slow each other dramatically.

Output
 one cache line:   [ counterA | counterB | ............ ]
                       ▲            ▲
                    thread 1     thread 2        each write evicts the line from the other core

The remedy is to keep them on separate lines:

C++
struct alignas(std::hardware_destructive_interference_size) PaddedCounter
{
    std::atomic<long> value{};
};

More on caches in 13.04 Performance, Caches and Data-Oriented Design.

volatile is not for threads

volatile tells the compiler that reads and writes of a variable have effects it cannot see, so it must not remove or merge them. It exists for memory-mapped hardware. It provides neither atomicity nor ordering. Use std::atomic for anything shared between threads.

A spinlock

A mutex puts a waiting thread to sleep. A spinlock keeps retrying, which is faster when the wait is extremely short.

C++
class SpinLock
{
public:
    void lock()
    {
        while (m_flag.test_and_set(std::memory_order_acquire))
        {
            m_flag.wait(true);
        }
    }

    void unlock()
    {
        m_flag.clear(std::memory_order_release);
        m_flag.notify_one();
    }

private:
    std::atomic_flag m_flag{};
};

test_and_set atomically sets the flag and returns what it was. If it was already set, another thread holds the lock. This version waits efficiently with atomic_flag::wait instead of spinning hot. Because it has lock and unlock, it works with std::lock_guard<SpinLock>.
