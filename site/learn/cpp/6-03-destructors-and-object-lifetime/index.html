Destructors and Object Lifetime

lesson 6.033 of 9 in milestone 65 min3 practice tasks

A destructor, ~ClassName(), runs automatically when an object's life ends. Use it to release what the object holds: files, memory, locks. Objects are destroyed in the reverse order of their creation.

The other end of an object's life

A constructor runs when an object is created. A destructor runs when it is destroyed. Its name is the class name with a ~ in front; it takes no parameters and returns nothing.

C++
#include <iostream>
#include <string>
#include <string_view>

class Noisy
{
public:
    explicit Noisy(std::string_view name) : m_name{ name }
    {
        std::cout << "+ " << m_name << '\n';
    }

    ~Noisy()
    {
        std::cout << "- " << m_name << '\n';
    }

private:
    std::string m_name{};
};

int main()
{
    Noisy a{ "A" };
    {
        Noisy b{ "B" };
        Noisy c{ "C" };
    }
    Noisy d{ "D" };
    return 0;
}
Output
+ A
+ B
+ C
- C
- B
+ D
- D
- A

You never call a destructor. The compiler inserts the call at the exact point where the object's lifetime ends.

flowchart LR
    A["memory reserved"] --> B["constructor runs"] --> C["object in use"] --> D["destructor runs"] --> E["memory released"]

Reverse order

Objects are destroyed in the opposite order to their construction: last built, first destroyed.

Output
 built:      A, then B, then C
 destroyed:  C, then B, then A

The reason is dependency. Something built later may rely on something built earlier, so the later one has to go first.

The same holds inside an object. Members are constructed in declaration order and destroyed in reverse. The destructor's own body runs before the members are destroyed, so they are all still usable inside it.

What destructors are for

Releasing things. A resource is anything that must be given back after use.

C++
#include <cstdio>

class LogFile
{
public:
    explicit LogFile(const char* path) : m_file{ std::fopen(path, "w") } {}

    ~LogFile()
    {
        if (m_file)
        {
            std::fclose(m_file);
        }
    }

    void write(const char* text)
    {
        if (m_file)
        {
            std::fputs(text, m_file);
        }
    }

private:
    std::FILE* m_file{};
};

Whoever uses a LogFile cannot forget to close the file, on any path out of the scope, including early returns. The pattern "acquire in the constructor, release in the destructor" is called RAII. It is the most important idiom in C++, and it gets a full lesson: 7.04 RAII and the Rule of Three.

If a class holds no resources, it needs no destructor. The compiler supplies one that destroys the members, and that is enough.

When each kind of object dies

Kind of object Created Destroyed
Local variable At its definition At the closing brace of its scope
Global or static Before main, or on first use for a static local After main returns
Dynamic (made with new) At new At delete, when you decide: 7.02 new and delete — Dynamic Memory
Temporary Within an expression At the end of the full statement

For the first two, the language guarantees the destructor call. That guarantee is what makes RAII dependable.

Three rules
  • Do not call a destructor explicitly. Outside very specialised code it leads to the object being destroyed twice.
  • A destructor should never let an exception escape: 9.06 Exception Safety, noexcept and std::expected.
  • std::exit does not run the destructors of local objects, which is one more reason to prefer returning from main.
