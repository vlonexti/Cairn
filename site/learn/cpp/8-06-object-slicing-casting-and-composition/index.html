Object Slicing, Casting and Composition

lesson 8.066 of 7 in milestone 85 min3 practice tasks

Copying a derived object into a base value discards the derived part: that is slicing. dynamic_cast converts down a hierarchy safely, but needing it often points to a design problem. And the standing advice: favour composition over inheritance.

Object slicing

C++
#include <iostream>
#include <string>
#include <string_view>

class Animal
{
public:
    virtual ~Animal() = default;
    virtual std::string_view speak() const { return "..."; }
};

class Dog : public Animal
{
public:
    std::string_view speak() const override { return "Woof"; }

private:
    std::string m_trick{ "roll over" };
};

int main()
{
    const Dog dog{};
    const Animal animal{ dog };            // sliced
    std::cout << animal.speak() << '\n';   // ...
    return 0;
}
 Dog dog                          Animal animal{ dog }
 ┌──────────────────────┐         ┌──────────────┐
 │ Animal part          │ ──────▶ │ Animal part  │     an Animal, with Animal's vptr
 ├──────────────────────┤         └──────────────┘
 │ m_trick              │   not copied
 └──────────────────────┘

Animal animal{ dog } calls Animal's copy constructor, which knows only about Animal's members. The result is a complete, genuine Animal. It is not a Dog viewed as an Animal.

The same happens wherever a base is held by value:

Code Sliced?
Animal a{ dog }; Yes
void f(Animal a); called with a Dog Yes
std::vector<Animal> Yes, on every insertion
Animal& a{ dog };, Animal* p{ &dog }; No
std::vector<std::unique_ptr<Animal>> No

Many codebases make polymorphic base classes non-copyable so that slicing cannot compile:

C++
class Animal
{
public:
    Animal() = default;
    Animal(const Animal&) = delete;
    Animal& operator=(const Animal&) = delete;
    virtual ~Animal() = default;
};

When copies of polymorphic objects are needed, provide a virtual clone() that returns a std::unique_ptr<Animal>.

dynamic_cast

C++
void interact(Animal& animal)
{
    if (auto* dog{ dynamic_cast<Dog*>(&animal) })
    {
        dog->fetch();
    }
    else
    {
        std::cout << "not a dog\n";
    }
}
Form On failure
dynamic_cast<Dog*>(pointer) Returns nullptr
dynamic_cast<Dog&>(reference) Throws std::bad_cast

It checks the object's dynamic type at run time, using run-time type information (RTTI) stored alongside the vtable. Consequently it requires a polymorphic base class and has a real cost.

static_cast<Dog*>(&animal) also compiles and performs no check. If the object is not a Dog, the behaviour is undefined. Use it only when the type is guaranteed by other means.

[!tip] A chain of dynamic_cast tests is a missing virtual function

C++
if (dynamic_cast<Dog*>(a)) { ... } else if (dynamic_cast<Cat*>(a)) { ... }

This re-implements dynamic dispatch by hand, and breaks whenever a new derived class appears. Add a virtual function and let each class provide its own behaviour.

typeid

C++
#include <typeinfo>

std::cout << typeid(animal).name() << '\n';

typeid gives the dynamic type of a polymorphic object. The text of name() is implementation-defined, so it is useful for diagnostics and not for logic.

Inheritance Composition
Coupling Tight: the derived class depends on the base's details Loose: only on the part's public interface
Flexibility Fixed at compile time Parts can be replaced while running
Scaling Deep hierarchies become fragile Stays flat
Use it for A true is-a relationship that needs polymorphism Reusing behaviour

Where inheritance breaks down

Suppose enemies can walk, fly or swim, and attack by melee or by shooting. As a hierarchy:

Output
 FlyingEnemy, SwimmingEnemy, FlyingShootingEnemy, SwimmingShootingEnemy,
 FlyingSwimmingEnemy, FlyingSwimmingShootingEnemy ...

Every new ability multiplies the number of classes. With composition, an entity has behaviours:

C++
class Entity
{
public:
    void update()
    {
        m_movement->move(*this);
        m_attack->attack(*this);
    }

    void setMovement(std::unique_ptr<IMovement> movement) { m_movement = std::move(movement); }

private:
    std::unique_ptr<IMovement> m_movement{};    // Walk, Fly or Swim
    std::unique_ptr<IAttack> m_attack{};        // Melee, Shoot or None
};

Three movement classes and three attack classes give nine combinations, and an entity can change behaviour while the program runs. Inheritance is still used, but only for the small interfaces. This is the Strategy pattern, and the thinking behind entity-component systems in game engines.
