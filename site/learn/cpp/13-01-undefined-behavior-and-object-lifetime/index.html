Undefined Behavior and Object Lifetime

lesson 13.011 of 10 in milestone 137 min2 practice tasks

The compiler optimizes on the assumption that your program has no undefined behaviour. Break that assumption and it may delete checks, reorder code, or mis-compile something far from the fault. This lesson is the full catalogue, the rules of object lifetime, and the tools that keep you inside the lines.

Why it is worse than a crash

1.10 Compiler Settings, Build Configurations and Undefined Behavior described undefined behaviour as "the rules say nothing about what happens". The practical consequence is sharper: an optimizer is entitled to assume it never happens, and to reason from that.

C++
int table[4]{};

bool exists(int value)
{
    for (int i{ 0 }; i <= 4; ++i)      // off by one: reads table[4]
    {
        if (table[i] == value)
        {
            return true;
        }
    }
    return false;
}

Reading table[4] is undefined. So a conforming optimizer may conclude that the loop must return before i reaches 4, which means it always returns true, and compile the whole function to return true;. Real compilers have done exactly this.

C++
void check(int* p)
{
    const int x{ *p };      // dereferenced: so the compiler may assume p is not null
    if (p == nullptr)       // therefore this test is "always false" and is removed
    {
        return;
    }
    use(x);
}
flowchart LR
    A["The code contains<br/>undefined behaviour"] --> B["The optimizer assumes<br/>it cannot occur"]
    B --> C["It derives facts that<br/>are false at run time"]
    C --> D["Checks are deleted and code reordered,<br/>often far from the original fault"]

Two properties make it treacherous. The effect can appear before the offending operation executes, because the whole function was compiled under the false assumption. And it changes with optimization level, compiler version and unrelated edits.

Strict aliasing and type punning

The strict aliasing rule: an object may be accessed only through an expression of its own type (with a few allowances for const, signedness and base classes). It lets the compiler assume that a float* and an int* never refer to the same memory, which enables important optimizations.

C++
float f{ 1.0f };
std::uint32_t bad{ *reinterpret_cast<std::uint32_t*>(&f) };    // undefined: aliasing violation

std::uint32_t good{ std::bit_cast<std::uint32_t>(f) };         // defined, and constexpr

std::uint32_t older{};
std::memcpy(&older, &f, sizeof older);                         // the pre-C++20 way

Reinterpreting the bits of one type as another is type punning. std::bit_cast and std::memcpy both copy the representation into a fresh object of the target type, and compilers turn either into a single move instruction.

One exception is always allowed: any object's bytes may be examined through a pointer to char, unsigned char or std::byte.

Object lifetime

Memory existing is not the same as an object existing.

 storage obtained ─▶ [ lifetime: initialization complete ... destructor begins ] ─▶ storage released
                      ▲ the object may be used only inside this window ▲
Event Lifetime
Storage is obtained, and initialization finishes Begins
The destructor starts, or the storage is released or reused Ends

Using an object outside its lifetime is undefined, even when the bytes are still there and look intact. You can control the two halves separately:

C++
alignas(Widget) std::byte buffer[sizeof(Widget)];

Widget* w{ std::construct_at(reinterpret_cast<Widget*>(buffer), arguments) };    // lifetime begins
std::destroy_at(w);                                                              // lifetime ends
Facility Purpose
std::construct_at, std::destroy_at Begin and end a lifetime in existing storage: 13.03 Custom Memory: Placement new, Allocators and PMR
Implicit-lifetime types Simple types (scalars, trivial structs, arrays of them) come into existence in storage from malloc or after a memcpy without explicit construction
std::start_lifetime_as<T>(p) (C++23) Declares that bytes received from a file or the network are a T
std::launder Obtains a usable pointer in rare cases where storage is reused for an object with const or reference members

Temporaries

A temporary lives until the end of the full expression that created it. One rule extends that: binding a temporary directly to a const reference (or an rvalue reference) keeps it alive as long as the reference.

Code Result
const std::string& r{ std::string{ "hi" } }; Fine: the lifetime is extended to that of r
std::string_view sv{ std::string{ "temp" } }; Dangles at the end of the statement: a view is not a reference binding
auto& first{ std::vector{ 1, 2, 3 }[0] }; Dangles: the reference binds to an element, not to the temporary
const auto& n{ makePlayer().name() }; Dangles if name() returns a reference into the temporary

Extension applies only to the temporary itself, not to things reached through it.

Defences

Tool Catches

No tool finds everything. The durable defence is habit: prefer the constructs that cannot go wrong (std::vector::at, ranges, smart pointers, std::bit_cast, RAII), so that the dangerous ones are rare and visible.
