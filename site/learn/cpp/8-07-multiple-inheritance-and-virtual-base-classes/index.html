Multiple Inheritance and Virtual Base Classes

lesson 8.077 of 7 in milestone 85 min2 practice tasks

A class may inherit from several bases. That works well for combining interfaces. When two bases share a common base, the result is the diamond problem, which virtual inheritance solves. Use it sparingly.

Several base classes

C++
#include <iostream>

class IDrawable
{
public:
    virtual ~IDrawable() = default;
    virtual void draw() const = 0;
};

class IClickable
{
public:
    virtual ~IClickable() = default;
    virtual void onClick() = 0;
};

class Button : public IDrawable, public IClickable
{
public:
    void draw() const override { std::cout << "[ OK ]\n"; }
    void onClick() override { std::cout << "clicked\n"; }
};

void render(const IDrawable& item) { item.draw(); }
void press(IClickable& item) { item.onClick(); }

int main()
{
    Button button{};
    render(button);
    press(button);
    return 0;
}
classDiagram
    IDrawable <|-- Button
    IClickable <|-- Button

A Button is substitutable for either interface. Implementing several interfaces is the common, uncontroversial use of multiple inheritance.

Base subobjects are constructed in the order they are listed after the colon, and each has its own vptr.

Name clashes

Two bases may supply members with the same name.

C++
class USBDevice
{
public:
    int id() const { return 1; }
};

class NetworkDevice
{
public:
    int id() const { return 2; }
};

class WirelessAdapter : public USBDevice, public NetworkDevice
{
};

WirelessAdapter adapter{};
adapter.id();               // error: ambiguous
adapter.USBDevice::id();    // fine: qualified

The diamond problem

classDiagram
    PoweredDevice <|-- Scanner
    PoweredDevice <|-- Printer
    Scanner <|-- Copier
    Printer <|-- Copier

Scanner and Printer each contain a PoweredDevice. With ordinary inheritance, a Copier therefore contains two.

 Copier
 ┌──────────────────────────────┐
 │ Scanner                      │
 │   └─ PoweredDevice (first)   │
 │ Printer                      │
 │   └─ PoweredDevice (second)  │     two copies of the same base
 └──────────────────────────────┘

Any use of a PoweredDevice member through a Copier is ambiguous, and state stored in the base exists twice and can disagree.

Virtual inheritance

Declaring the inheritance virtual asks for one shared base subobject, however many paths lead to it.

C++
#include <iostream>

class PoweredDevice
{
public:
    explicit PoweredDevice(int watts) { std::cout << "PoweredDevice " << watts << "W\n"; }
};

class Scanner : virtual public PoweredDevice
{
public:
    Scanner(int, int watts) : PoweredDevice{ watts } {}
};

class Printer : virtual public PoweredDevice
{
public:
    Printer(int, int watts) : PoweredDevice{ watts } {}
};

class Copier : public Scanner, public Printer
{
public:
    Copier(int scanner, int printer, int watts)
        : PoweredDevice{ watts }, Scanner{ scanner, watts }, Printer{ printer, watts }
    {
    }
};

int main()
{
    Copier copier{ 1, 2, 300 };    // prints "PoweredDevice 300W" once
    return 0;
}
 Copier
 ┌──────────────────────────────────────────┐
 │ Scanner ─┐                               │
 │ Printer ─┴──▶ PoweredDevice (one, shared)│
 └──────────────────────────────────────────┘
Rule Detail
Who constructs the virtual base The most-derived class, here Copier
When Before every non-virtual base
The intermediate classes' initializers Scanner's and Printer's calls to PoweredDevice{ watts } are ignored when they are subobjects of a Copier

The price is extra indirection: because the shared base's position varies with the most-derived type, each object locates it through a stored offset. Access to virtual-base members is slightly slower, and objects are slightly larger.

Guidelines

Use Advice
Inheriting several interfaces with no data Fine and common
Inheriting several implementations with data Think hard, and prefer composition
A diamond Avoid if you can. If you cannot, use virtual inheritance.
Adding reusable behaviour to a class Consider template-based mixins: 11.05 CRTP, Mixins and Static Polymorphism
Design to avoid the question

Most diamonds arise because a base class carries both an interface and state. Split it: keep the interface free of data, and put shared state in a component the classes hold. The diamond then disappears, or becomes a harmless diamond of pure interfaces.
