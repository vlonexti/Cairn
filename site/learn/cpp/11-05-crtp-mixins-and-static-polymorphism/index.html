CRTP, Mixins and Static Polymorphism

lesson 11.055 of 7 in milestone 115 min2 practice tasks

The Curiously Recurring Template Pattern: class Derived : public Base<Derived>. The base knows the derived type at compile time, so it can call derived functions without virtual. That is static polymorphism. It suits mixins and interfaces with no run-time overhead. C++23's deducing this simplifies it.

The shape of the pattern

A class derives from a template and passes itself as the argument.

C++
#include <iostream>

template <typename Derived>
class Shape
{
public:
    double area() const
    {
        return static_cast<const Derived&>(*this).areaImpl();
    }
};

class Square : public Shape<Square>
{
public:
    double areaImpl() const { return m_side * m_side; }

private:
    double m_side{ 2.0 };
};

template <typename T>
void printArea(const Shape<T>& shape)
{
    std::cout << shape.area() << '\n';
}

int main()
{
    const Square square{};
    printArea(square);    // 4
    return 0;
}
flowchart LR
    S["Square"] -->|"derives from"| B["Shape&lt;Square&gt;"]
    B -->|"static_cast to Square,<br/>then calls areaImpl:<br/>resolved at COMPILE time"| S

This is the Curiously Recurring Template Pattern (CRTP). Inside Shape<Derived>, the object is known to be a Derived, so the static_cast down to it is valid, and the call to areaImpl is an ordinary direct call that the compiler can inline.

It is legal for Square to name itself as a template argument before it is complete, because the bodies of Shape<Square>'s member functions are not instantiated until they are used, and by then Square is complete.

Dynamic and static polymorphism

virtual (dynamic) CRTP and templates (static)
The call is resolved At run time, through the vtable At compile time
Inlining Usually not possible Yes
Per-object overhead A vptr None
Different types in one container Yes: std::vector<std::unique_ptr<Shape>> No: Shape<Square> and Shape<Circle> are unrelated types
New types without recompiling users Yes No
Code size One function body One instantiation per type

Use CRTP when the set of types is known at compile time and the call sits on a hot path. Use virtual when types must be chosen or mixed at run time. The mechanics of the virtual side are in 8.04 How Virtual Works — vtables.

Mixins

The more common use of CRTP is not polymorphism. It is to inject functionality into a class. A base class used this way is a mixin.

An object counter per class

C++
template <typename T>
class Counted
{
public:
    static int alive() { return s_alive; }

protected:
    Counted() { ++s_alive; }
    Counted(const Counted&) { ++s_alive; }
    ~Counted() { --s_alive; }

private:
    static inline int s_alive{ 0 };
};

class Enemy : public Counted<Enemy>
{
};

class Bullet : public Counted<Bullet>
{
};

Counted<Enemy> and Counted<Bullet> are different classes, so each has its own static counter. A non-template base would give one counter shared by everything. The protected destructor prevents deletion through a Counted<T>*, so no virtual destructor is needed.

Generating operators

C++
template <typename D>
struct EqualityComparable
{
    friend bool operator!=(const D& a, const D& b) { return !(a == b); }
};

struct Point : EqualityComparable<Point>
{
    int x{};
    int y{};
    friend bool operator==(const Point& a, const Point& b) { return a.x == b.x && a.y == b.y; }
};

The derived class supplies one operation and the mixin derives the rest. C++20's defaulted comparisons (6.07 Operator Overloading Basics) have made this particular example unnecessary, but the technique is everywhere in older libraries.

Removing clone boilerplate

C++
template <typename Base, typename Derived>
class Cloneable : public Base
{
public:
    std::unique_ptr<Base> clone() const override
    {
        return std::make_unique<Derived>(static_cast<const Derived&>(*this));
    }
};

class Circle : public Cloneable<Shape, Circle>
{
    // clone() is supplied
};

Here CRTP and virtual functions work together: the hierarchy is dynamic, and the repetitive override is generated statically.

Deducing this

C++23 lets a member function declare its object parameter explicitly, and deduce its type.

C++
struct Shape
{
    double area(this const auto& self) { return self.areaImpl(); }
};

struct Square : Shape
{
    double side{ 2.0 };
    double areaImpl() const { return side * side; }
};

self is deduced as the actual type of the object the function is called on, so no template base and no cast are required. The feature is called an explicit object parameter.

It also removes the duplication between const and non-const overloads (6.04 this, const Member Functions and Chaining):

C++
class Text
{
public:
    template <typename Self>
    auto&& at(this Self&& self, std::size_t i)
    {
        return std::forward<Self>(self).m_text[i];
    }

private:
    std::string m_text{};
};

One function serves const objects, non-const objects and temporaries, with the right return type for each.

Pitfalls

Pitfall Consequence Defence
Naming the wrong type: class Circle : public Shape<Square> Compiles; the static_cast is undefined behaviour Make the base constructor private and declare friend Derived; so only the named class can construct it
The derived class omits areaImpl A confusing error, or endless recursion if base and derived use the same name Use distinct names, or constrain with a concept
Expecting a common base type Shape<A> and Shape<B> share nothing Add a non-template base if run-time polymorphism is also needed
