Stack vs Heap

lesson 7.011 of 8 in milestone 75 min3 practice tasks

A program's memory has regions. The stack holds local variables: very fast and automatic, but small and tied to scope. The heap holds memory requested while running: large and flexible, but something has to manage it.

Where things live

So far "memory" has been one undifferentiated place. It has regions, and which region an object lives in decides how long it lasts and what it costs.

 high addresses
 ┌──────────────────────────────┐
 │  STACK   grows downwards     │  local variables and function calls
 │                              │
 │       (unused space)         │
 │                              │
 │  HEAP    grows upwards       │  memory requested while running
 ├──────────────────────────────┤
 │  Static data                 │  globals, static locals, string literals
 ├──────────────────────────────┤
 │  Code                        │  the compiled functions
 └──────────────────────────────┘
 low addresses

The stack

Each function call adds a stack frame holding that call's parameters and local variables. Returning removes it. You met this as the call stack in 5.09 Recursion.

C++
int square(int n)
{
    int result{ n * n };
    return result;
}

int main()
{
    int x{ 4 };
    int y{ square(x) };
    return y;
}
 while square runs:             after it returns:
 ┌──────────────────────┐
 │ square: n=4 result=16│ top
 ├──────────────────────┤       ┌──────────────────────┐
 │ main:   x=4  y=?     │       │ main:   x=4  y=16    │ top
 └──────────────────────┘       └──────────────────────┘

Allocating on the stack is nothing more than moving a marker, which is why it is so fast. The price is rigidity:

Property Consequence
Frames are removed in strict reverse order A local variable cannot outlive its function
Sizes are fixed at compile time You cannot have a local array whose length is decided while running
The whole stack is small, typically 1 MB on Windows Very deep recursion or a huge local array causes a stack overflow

The heap

The heap is a large pool from which memory can be requested at any moment, in any amount, and kept until it is explicitly given back. It is also called the free store.

C++
int* p{ new int{ 42 } };    // request an int from the heap
delete p;                   // give it back
 STACK                       HEAP
 ┌──────────────┐           ┌──────┐
 │ p: 0x5a20 ───┼──────────▶│  42  │   exists until it is deleted
 └──────────────┘           └──────┘

The pointer p is a local variable on the stack. The int it points at is on the heap, and its lifetime has nothing to do with any scope.

Side by side

Stack Heap
Speed of allocation Extremely fast Slower: a suitable free block has to be found
Total size Small (megabytes) Large (gigabytes)
Lifetime Automatic: ends at the closing brace Until it is released
Size must be known At compile time Any time
What goes wrong Overflow Leaks, dangling pointers, double release

When is the heap needed?

Situation Example
The size is only known while running A list of however many users log in
The data must outlive the function that creates it An object returned to and kept by the caller
The data is very large A 100 MB image
Objects of varying types behind one interface Polymorphism: 8.03 Virtual Functions and Polymorphism

You have been using the heap since Milestone 2 without seeing it:

 std::vector<int> v{ 1, 2, 3 };

 STACK                               HEAP
 ┌────────────────────────┐         ┌───┬───┬───┐
 │ v: pointer, size, cap ─┼────────▶│ 1 │ 2 │ 3 │
 └────────────────────────┘         └───┴───┴───┘

A vector object is three small values on the stack. Its elements live on the heap, which is how it can grow.

[!tip] You will rarely write new yourself std::vector, std::string and std::make_unique use the heap safely on your behalf. This milestone goes underneath them, because you cannot use those tools well, or debug them, without knowing what they are doing.
