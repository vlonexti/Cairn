Testing, Sanitizers, Static Analysis and Tooling

lesson 13.099 of 10 in milestone 138 min2 practice tasks

Professional C++ is supported by tools. Unit tests check behaviour. Sanitizers catch undefined behaviour as the program runs. Static analysis finds defects without running it. Formatters, fuzzers and continuous integration apply all of it to every change.

Layers of defence

No single technique finds every defect. Each layer catches what the previous ones missed, and the earlier a problem is caught, the cheaper it is to fix.

flowchart LR
    A["Write code"] --> B["Compiler warnings"]
    B --> C["Static analysis"]
    C --> D["Unit tests"]
    D --> E["Sanitizers"]
    E --> F["Fuzzing"]
    F --> G["Continuous integration:<br/>all of it, on every change"]
Layer Runs the code? Finds
Warnings, static analysis No Suspicious patterns on every path, including ones no test exercises
Unit tests Yes Wrong results, for the inputs you thought of
Sanitizers Yes Undefined behaviour on the paths the tests exercise
Fuzzing Yes Failures on inputs you did not think of

Unit testing

You have been on the receiving end of unit tests throughout this course: every Check in Xenon ran a set of them against your code. 3.08 Halts, goto, and Testing Your Code introduced the idea with a hand-written test function. A test framework supplies the infrastructure: registering tests, running them, reporting failures and summarizing.

With Catch2:

C++
#include <catch2/catch_test_macros.hpp>
#include "Fraction.h"

TEST_CASE("Fractions reduce automatically", "[fraction]")
{
    const Fraction f{ 2, 4 };
    REQUIRE(f.numerator() == 1);
    REQUIRE(f.denominator() == 2);
}

TEST_CASE("Adding fractions")
{
    SECTION("the same denominator")
    {
        CHECK(Fraction{ 1, 4 } + Fraction{ 2, 4 } == Fraction{ 3, 4 });
    }
    SECTION("a zero denominator throws")
    {
        REQUIRE_THROWS_AS(Fraction(1, 0), std::invalid_argument);
    }
}
Macro On failure
REQUIRE(expression) Reports and stops the current test case
CHECK(expression) Reports and continues
REQUIRE_THROWS_AS(expression, type) Fails unless the expression throws that type

GoogleTest is the other widely used framework: TEST(Fraction, Reduces) { EXPECT_EQ(f.numerator(), 1); }. The ideas are identical. Either is added to a CMake project with FetchContent (10.09 CMake, Libraries and Package Managers):

CMake
include(FetchContent)
FetchContent_Declare(Catch2
    GIT_REPOSITORY https://github.com/catchorg/Catch2.git
    GIT_TAG v3.7.1)
FetchContent_MakeAvailable(Catch2)

add_executable(tests tests/test_fraction.cpp)
target_link_libraries(tests PRIVATE fraction_lib Catch2::Catch2WithMain)

include(CTest)
include(Catch)
catch_discover_tests(tests)

What makes code testable

Property Why
Small, pure functions The same input always gives the same output, so a test is one line
Dependencies passed in A test can supply a fake clock, file system or network: 8.05 Abstract Classes and Interfaces
No hidden globals Tests do not interfere with each other: 13.08 C++ Idioms and Design Patterns
Logic separated from input and output The logic can be tested without a console or a file

Code that is hard to test is usually code with too many responsibilities or hidden dependencies. The difficulty is design feedback.

How good are the tests?

Measure Asks
Coverage Which lines and branches did the tests execute? Uncovered code is untested. Covered code is not necessarily tested well.
Mutation testing If a small bug is introduced deliberately, does any test fail? If not, the tests are not checking that behaviour.

Test-driven development reverses the usual order: write a failing test, write the least code that passes it, then tidy up. It guarantees that every piece of behaviour has a test and that the test can fail.

Sanitizers

A sanitizer is a compiler option that adds checks to the generated program. The program runs slower and reports errors precisely as they happen.

Sanitizer Flag (GCC, Clang) Microsoft Detects
AddressSanitizer -fsanitize=address /fsanitize=address Out-of-bounds access, use after free, double free, leaks
UndefinedBehaviorSanitizer -fsanitize=undefined Signed overflow, bad shifts, null dereference, misalignment
ThreadSanitizer -fsanitize=thread Data races, inconsistent lock ordering
MemorySanitizer (Clang) -fsanitize=memory Reads of uninitialized memory
Terminal
g++ -std=c++20 -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o app
Output
==12345==ERROR: AddressSanitizer: heap-use-after-free on address 0x602000000010
READ of size 4 at 0x602000000010 thread T0
    #0 0x4011a6 in main main.cpp:9

The report names the exact line, and where the memory was allocated and freed. A bug that might have surfaced weeks later as an unrelated crash is pinned down the first time it executes.

Limit Detail
Only executed code is checked A sanitizer is as good as the tests that drive it
Cost Two to three times slower for ASan; more for TSan
Combinations ASan and TSan cannot be used in the same build

The standard practice is to run the whole test suite under ASan and UBSan, and again under TSan for concurrent code. The beaker button above Xenon's editor ("Memory checks") builds your code with AddressSanitizer.

Static analysis

Static analysis examines source code without executing it, so it can reason about every path, including error handling that tests rarely reach.

Tool Notes
Compiler warnings The first and cheapest analyzer. Turn them up and treat them as errors.
clang-tidy Hundreds of checks in families: bugprone-*, modernize-*, performance-*, cppcoreguidelines-*. Many can fix the code automatically.
Microsoft Code Analysis /analyze, with a C++ Core Guidelines checker
cppcheck Free and standalone
YAML
# .clang-tidy
Checks: 'bugprone-*,modernize-*,performance-*,readability-*,-modernize-use-trailing-return-type'
WarningsAsErrors: 'bugprone-*'

Static analysis can report problems that are not real (false positives) and cannot find everything. It complements testing; it does not replace it.

Formatting

clang-format rewrites code to a style defined in a .clang-format file. Format on save, and arguments about brace placement end for good. Code reviews can then be about substance. The wand button above Xenon's editor (or Shift+Alt+F) runs it.

Fuzzing

A fuzzer calls a function with enormous numbers of generated inputs, guided by which code paths each one reaches, looking for crashes. Combined with sanitizers it is extremely effective on anything that parses untrusted input.

C++
extern "C" int LLVMFuzzerTestOneInput(const std::uint8_t* data, std::size_t size)
{
    parseConfig(std::string_view{ reinterpret_cast<const char*>(data), size });
    return 0;
}
Terminal
clang++ -fsanitize=fuzzer,address fuzz.cpp parser.cpp

You write the single function above; the fuzzer does the rest.

The debugger

A debugger pauses a running program and lets you inspect it.

Feature Use
Breakpoint Pause at a line
Conditional breakpoint Pause only when a condition holds, such as i == 9999
Data breakpoint (watchpoint) Pause when a variable's value changes: the fastest way to find who corrupted it
Call stack See the chain of calls that led here
Crash dump Examine a program's state after it has crashed, on another machine

Continuous integration

Continuous integration (CI) builds the project and runs every check automatically for each change pushed to the repository, on every platform you support.

YAML
jobs:
  build:
    strategy: { matrix: { os: [ubuntu-latest, windows-latest] } }
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - run: cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
      - run: cmake --build build
      - run: ctest --test-dir build --output-on-failure

The value is that the checks cannot be forgotten. A change that breaks a test, or the build on another platform, is caught within minutes and before it is merged.
