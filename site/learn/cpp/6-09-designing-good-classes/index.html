Designing Good Classes

lesson 6.099 of 9 in milestone 65 min3 practice tasks

A good class has one clear job, a small public interface that is hard to misuse, protects its invariants and is const-correct. Design it from the point of view of the code that will use it.

From syntax to judgement

You now know the mechanics of classes. This lesson is about using them well. None of it is enforced by the compiler; all of it decides whether your code is pleasant or painful to work with in six months.

One responsibility

Poor Better
A GameManager that loads files, draws, reads input and keeps scores FileLoader, Renderer, InputHandler, ScoreBoard

A class with one job is small enough to understand, test and reuse. A class with five jobs changes for five different reasons, and each change risks the other four.

The one-sentence test

Describe the class in one sentence. If you need the word "and", it is probably two classes.

Protect invariants for the object's whole life

C++
class Percentage
{
public:
    explicit Percentage(int value) : m_value{ std::clamp(value, 0, 100) } {}

    void add(int delta) { m_value = std::clamp(m_value + delta, 0, 100); }
    int value() const { return m_value; }

private:
    int m_value{};    // invariant: 0 <= m_value <= 100
};
Moment How the invariant is kept
Creation The constructor validates
Every modification Each member function that changes the data re-establishes the rule
Outside the class The data is private, so nothing else can touch it

Here invalid input is quietly brought into range. When invalid input should be reported as an error, the constructor throws an exception: 9.05 Exceptions.

Make the interface hard to misuse

The best interface is one where the wrong call does not compile.

Easy to get wrong Hard to get wrong Technique
Rectangle r{ 10, 20 }; Rectangle r{ Width{ 10 }, Height{ 20 } }; A small type for each kind of value
Date d{ 11, 12, 2026 }; Date::fromYmd(2026, 11, 12) A named factory function
run(5.0) accepted as a distance run(Meters{ 5.0 }) An explicit constructor

Tell, do not ask

C++
// Asking: pull the data out, decide outside, push it back.
if (account.balance() >= amount)
{
    account.setBalance(account.balance() - amount);
}

// Telling: ask the object to do it. The rule stays inside the class.
if (!account.withdraw(amount))
{
    std::cout << "Insufficient funds\n";
}

In the first version, every caller must remember to check the balance. One who forgets breaks the invariant. In the second, forgetting is impossible.

Const correctness

Check
Every member function that does not modify the object is const
Parameters that are only read are const T&, or by value for cheap types
Members are returned by const& when callers only need to read them

Struct or class?

Use a struct when Use a class when
The members are independent of each other The members must satisfy a rule together
Every combination of values is valid Some combinations are invalid
Point, Color, Config Fraction, BankAccount, Date

Do not wrap a plain bundle of data in getters and setters. It adds code without protecting anything.

Value semantics and the Rule of Zero

The easiest classes to use behave like int: they can be copied, assigned, compared and passed around freely, and each copy is independent. That behaviour is called value semantics.

You get it for free when a class's members are themselves well-behaved: std::string, std::vector, other value types. The compiler-generated copy operations and destructor then do the right thing, and you write none of them. That is the Rule of Zero, and the next milestone explains why it matters: 7.05 Move Semantics.

A design process

flowchart LR
    A["Write the code that<br/>USES the class first"] --> B["List its actions<br/>(the verbs)"] --> C["Decide the invariants"] --> D["Choose the private data"] --> E["Implement"] --> F["Test the edge cases"]

Starting from the calling code is the important step. It shows what the interface should feel like before any implementation detail has had the chance to shape it.
