RAII and the Rule of Three

lesson 7.044 of 8 in milestone 75 min3 practice tasks

RAII: tie every resource to an object's lifetime. Acquire it in the constructor and release it in the destructor, and clean-up becomes automatic on every path. Rule of Three: a class that needs a destructor, copy constructor or copy assignment operator almost certainly needs all three.

The most important idea in C++

The language guarantees that an object's destructor runs when its lifetime ends, however that comes about. RAII puts that guarantee to work: a resource is acquired in a constructor and released in the matching destructor.

flowchart LR
    C["Constructor<br/>open, allocate,<br/>lock, connect"] --> U["Use the object"] --> D["Destructor<br/>close, release,<br/>unlock, disconnect"]
    U -->|"early return"| D
    U -->|"exception"| D
    U -->|"end of scope"| D

The name stands for "Resource Acquisition Is Initialization". It is an awkward name for a simple idea: an object owns the resource, and the object's lifetime is the resource's lifetime.

Without RAII

C++
void save()
{
    std::FILE* file{ std::fopen("save.txt", "w") };
    if (!ready())
    {
        return;                 // the file is never closed
    }
    write(file);                // if this throws, the file is never closed
    std::fclose(file);
}

Every exit path needs its own clean-up, and every future edit to the function has to remember that.

With RAII

C++
class File
{
public:
    File(const char* path, const char* mode) : m_file{ std::fopen(path, mode) } {}

    ~File()
    {
        if (m_file)
        {
            std::fclose(m_file);
        }
    }

    File(const File&) = delete;
    File& operator=(const File&) = delete;

    std::FILE* get() const { return m_file; }

private:
    std::FILE* m_file{};
};

void save()
{
    File file{ "save.txt", "w" };
    if (!ready())
    {
        return;                 // closed automatically
    }
    write(file.get());          // closed even if this throws
}

The clean-up is written once, in the destructor, and cannot be skipped.

RAII is everywhere in the library

You have been relying on it throughout the course.

Resource RAII type
A block of heap memory std::vector, std::string
A single heap object std::unique_ptr, std::shared_ptr
A file std::ifstream, std::ofstream
A lock on a mutex std::lock_guard, std::scoped_lock
A thread std::jthread

A "resource" is anything that must be handed back: memory, files, locks, network connections, even a temporary change of state such as a console colour.

The Rule of Three

 If a class needs ONE of these, it almost certainly needs ALL THREE:

 ┌────────────────────┬────────────────────────┬──────────────────────────┐
 │ ~T()               │ T(const T&)            │ T& operator=(const T&)   │
 │ destructor         │ copy constructor       │ copy assignment          │
 └────────────────────┴────────────────────────┴──────────────────────────┘

The reasoning is short. Writing a destructor means the class manages a resource. If it manages a resource, the compiler-generated shallow copies are wrong (7.03 Copy Semantics — Shallow vs Deep). So you must either define the two copy operations or delete them, as File does.

You wrote And left the others to the compiler Result
A destructor only Shallow copy constructor and assignment Double delete on the first copy
Destructor and copy constructor Shallow assignment Double delete on the first b = a

These five special functions are together called the special member functions (the five here plus the two move operations in the next lesson, which turn this into the Rule of Five).

The Rule of Zero

The better rule is to need none of them.

C++
class Playlist
{
private:
    std::string m_name{};
    std::vector<Song> m_songs{};
    std::unique_ptr<Cover> m_cover{};
};

Every member already manages its own resource. The compiler-generated destructor, copies and moves are therefore correct, and Playlist declares no special member functions at all. That is the Rule of Zero.

flowchart TD
    Q{"Does this class directly manage<br/>a raw resource?"} -- "no (almost always)" --> Z["Rule of Zero:<br/>write no special members"]
    Q -- "yes: a small, dedicated<br/>wrapper class" --> F["Rule of Three / Five:<br/>write or delete all of them"]

The design this leads to: a handful of small classes whose only job is to wrap one raw resource, and everything else built from them with no manual management at all.
