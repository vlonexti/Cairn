Type Erasure

lesson 11.066 of 7 in milestone 115 min1 practice task

Type erasure hides many unrelated concrete types behind one non-template interface, without requiring them to share a base class. std::function, std::any and the deleter of std::shared_ptr all use it. The recipe: an internal abstract Concept, a templated Model that wraps any type, and an outer wrapper with value semantics.

The problem

You want a single container of "anything that can be drawn": your Circle, your Sprite and a Text class from a library you cannot modify. They share no base class.

Approach Limitation
A common base class with virtual functions Every type must inherit from it, which is impossible for types you do not own, and intrusive for those you do
A template std::vector<T> holds one type only
std::variant The set of types must be listed in advance

Type erasure gives run-time polymorphism over types that know nothing about each other or about the interface.

C++
#include <iostream>
#include <memory>
#include <string>
#include <utility>
#include <vector>

struct Circle
{
    double radius{};
};

struct Text
{
    std::string content{};
};

void drawIt(const Circle& c) { std::cout << "Circle " << c.radius << '\n'; }
void drawIt(const Text& t) { std::cout << "Text '" << t.content << "'\n"; }

class Drawable
{
public:
    template <typename T>
    Drawable(T value) : m_self{ std::make_unique<Model<T>>(std::move(value)) } {}

    Drawable(const Drawable& other) : m_self{ other.m_self->clone() } {}
    Drawable(Drawable&&) noexcept = default;

    Drawable& operator=(Drawable other) noexcept
    {
        std::swap(m_self, other.m_self);
        return *this;
    }

    void draw() const { m_self->draw(); }

private:
    struct Concept
    {
        virtual ~Concept() = default;
        virtual void draw() const = 0;
        virtual std::unique_ptr<Concept> clone() const = 0;
    };

    template <typename T>
    struct Model final : Concept
    {
        explicit Model(T value) : data{ std::move(value) } {}

        void draw() const override { drawIt(data); }
        std::unique_ptr<Concept> clone() const override { return std::make_unique<Model>(*this); }

        T data;
    };

    std::unique_ptr<Concept> m_self{};
};

int main()
{
    const std::vector<Drawable> scene{ Circle{ 2.0 }, Text{ "hi" }, Circle{ 5.0 } };
    for (const Drawable& item : scene)
    {
        item.draw();
    }
    return 0;
}
Piece Role
Concept A private abstract base listing the operations the wrapper needs
Model<T> A template that holds a T and implements Concept by forwarding to operations on T
Drawable The public, non-template class. Its constructor template builds the right Model<T>. 
 Drawable (a value, copyable)             heap
 ┌──────────────────┐        ┌────────────────────────────┐
 │ m_self ──────────┼──────▶ │ Model<Circle>              │
 └──────────────────┘        │   vptr to Model<Circle>'s  │
                             │   Circle{ 2.0 }            │
                             └────────────────────────────┘

 Outside the constructor, the type Circle no longer appears anywhere: it has been erased.

The inheritance and virtual dispatch are still there. They have moved inside the wrapper, where the compiler generates them per type. Circle and Text stay plain structs, and the requirement on them is purely structural: a drawIt overload must exist.

Because Drawable deep-copies through clone(), it has value semantics: it can be copied, assigned, returned and stored in containers like an int. This is polymorphism without pointers or ownership in the user's code.

In the standard library

Type Erases Requires of the wrapped type
std::function<R(Args...)> Any callable Callable with Args..., result convertible to R, copyable
std::move_only_function (C++23) Callables that cannot be copied The same, without copyability
std::any Any type Copy-constructible
The deleter of std::shared_ptr<T> The deleter's type Callable with a T*
std::pmr::memory_resource An allocation strategy 13.03 Custom Memory: Placement new, Allocators and PMR

This explains a detail from 7.06 Smart Pointers: a shared_ptr's deleter is not part of its type, while a unique_ptr's is. The shared_ptr erases it in the control block, at the cost of an indirect call.

Small buffer optimization

Allocating every wrapped object on the heap is the main cost. Real implementations reserve a small buffer inside the wrapper, typically 16 to 32 bytes, and construct small objects directly in it, falling back to the heap for large ones.

 small object:   [ wrapper: | the object lives here | ]             no allocation
 large object:   [ wrapper: | pointer ───────────────┼──▶ heap ]

std::function and std::any normally do this, which is why a std::function holding a lambda with one or two captures allocates nothing. The same idea applied to std::string is the small string optimization.

Trade-offs

Advantages Costs
Works with unrelated types, including ones you cannot change Boilerplate for each erased interface
Value semantics An indirect call, and possibly an allocation
A non-template interface: faster builds and a stable binary interface The concrete type is hidden from the debugger and from the optimiser
Mechanism Types Chosen
Templates and CRTP Any, known at compile time Compile time
std::variant A fixed list Run time
Virtual functions Anything derived from the base Run time
Type erasure Anything meeting the requirements Run time
