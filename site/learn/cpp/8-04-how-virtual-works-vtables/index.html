How Virtual Works — vtables

lesson 8.044 of 7 in milestone 85 min2 practice tasks

Ordinary calls are resolved at compile time (early binding). Virtual calls are resolved at run time (late binding) through a hidden pointer in each object, the vptr, to a per-class table of function addresses, the vtable. The cost is one pointer per object and one indirection per call.

Early and late binding

Binding Decided
Non-virtual call Early (static) By the compiler
Virtual call Late (dynamic) While the program runs

The standard does not say how virtual dispatch must be implemented. Every mainstream compiler uses the mechanism below.

The vtable

C++
class Animal
{
public:
    virtual ~Animal() = default;
    virtual void speak() const;
    virtual void move() const;
};

class Dog : public Animal
{
public:
    void speak() const override;    // move is not overridden
};

class Cat : public Animal
{
public:
    void speak() const override;
    void move() const override;
};
   OBJECTS                    VTABLES: one per CLASS, shared by all its objects

   ┌────────────┐            Dog's vtable
   │ rex (Dog)  │            ┌──────────────┬──────────────────┐
   │ vptr ──────┼──────────▶ │ slot 0 dtor  │ ~Dog             │
   │ members    │            │ slot 1 speak │ Dog::speak       │   overridden
   └────────────┘            │ slot 2 move  │ Animal::move     │   inherited
                             └──────────────┴──────────────────┘
   ┌────────────┐            Cat's vtable
   │ tom (Cat)  │            ┌──────────────┬──────────────────┐
   │ vptr ──────┼──────────▶ │ slot 0 dtor  │ ~Cat             │
   │ members    │            │ slot 1 speak │ Cat::speak       │
   └────────────┘            │ slot 2 move  │ Cat::move        │
                             └──────────────┴──────────────────┘
Piece Where Holds
vtable One per class with virtual functions The address of that class's version of each virtual function
vptr One hidden member in every object of such a class The address of its class's vtable

Every class in a hierarchy uses the same slot number for the same function. So animalRef.speak() compiles to three steps that work without knowing the dynamic type:

  1. Read the object's vptr.
  2. Read slot 1 of the table it points to.
  3. Call the address found there.

The cost

Cost
Memory per object One pointer, 8 bytes on a 64-bit system, plus any padding
Memory per class One table
Time per call Two extra memory reads and an indirect call
Lost optimisation The compiler generally cannot inline a virtual call, which is often the larger effect
C++
struct NoVirtual
{
    int x;
};    // sizeof is 4

struct HasVirtual
{
    int x;
    virtual ~HasVirtual() = default;
};    // sizeof is 16: an 8-byte vptr, the int, and 4 bytes of padding

In most code this is immaterial. It becomes measurable when a tiny virtual function is called millions of times in a tight loop over small objects. Alternatives for those cases:

Devirtualization

When the compiler can prove the dynamic type, it replaces the virtual call with a direct one, which can then be inlined. This is devirtualization.

Situation Why the type is known
A call on a local object by value Its type is exactly the declared one
The class or the function is final Nothing can override further
Whole-program optimisation shows a single implementation There is only one candidate

Marking leaf classes final is therefore a small, free optimisation.

Why virtual calls in constructors do not dispatch

The vptr is set by each constructor in turn.

Output
 constructing a Dog:

 Animal's constructor runs    vptr points at Animal's vtable
 Dog's constructor runs       vptr points at Dog's vtable

While Animal's constructor is running, the object is an Animal: the Dog members are not yet constructed. A virtual call at that moment reaches Animal's version, which is the only safe choice. Destruction mirrors it: by the time ~Animal runs, the Dog part has already been destroyed and the vptr has been set back.
