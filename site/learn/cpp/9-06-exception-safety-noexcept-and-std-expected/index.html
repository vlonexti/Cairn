Exception Safety, noexcept and std::expected

lesson 9.066 of 6 in milestone 96 min3 practice tasks

Code must leave objects in a sensible state when an exception passes through it. Know the three guarantees: basic, strong and nothrow. Mark functions that cannot throw noexcept. Destructors must not throw. For failures that are a normal outcome, consider std::optional or std::expected.

The exception-safety guarantees

Any statement that might throw is a possible exit from the function. Exception safety describes what a function promises about the program's state if that happens.

flowchart TD
    N["No guarantee<br/>leaks or corrupted state are possible"] --> B["Basic<br/>no leaks, every object still valid,<br/>but values may have changed"]
    B --> S["Strong<br/>commit or roll back:<br/>it succeeds, or nothing changed"]
    S --> T["Nothrow<br/>it never throws"]
Guarantee Promise Typical examples
Basic Invariants hold and nothing leaks The minimum for any correct code
Strong If it throws, the state is exactly as before the call std::vector::push_back
Nothrow It always succeeds Destructors, swap, move operations

Every function should give at least the basic guarantee. With RAII members, that comes almost free.

Getting the strong guarantee

Do all the work that might throw on the side, then commit with operations that cannot.

C++
void Inventory::replaceAll(const std::vector<Item>& items)
{
    std::vector<Item> fresh{ items };    // may throw: this object is untouched
    validate(fresh);                     // may throw: still untouched
    m_items.swap(fresh);                 // cannot throw: the commit
}

That is precisely why copy and swap (7.03 Copy Semantics — Shallow vs Deep) is exception-safe. The strong guarantee costs a copy, so it is not always worth having; choose it where a half-done operation would be harmful.

Where exceptions bite

Hazard Consequence Defence
A raw new with a throw before its delete A leak Hold resources in RAII objects
A destructor that throws during unwinding std::terminate Never let an exception escape a destructor
A constructor that throws part-way The destructor does not run Keep each resource in its own RAII member, which is destroyed automatically
Updating two pieces of state, with a throw between them Inconsistent object Prepare both first, then commit without throwing

noexcept

noexcept on a function declares that it does not throw.

C++
void swap(Buffer& a, Buffer& b) noexcept;
Buffer(Buffer&& other) noexcept;
Fact Detail
It is a promise, not a check If a noexcept function does throw, std::terminate is called
Callers and the compiler can rely on it Code can choose faster algorithms, and less unwinding machinery is generated
Destructors are noexcept implicitly You do not write it
It can be conditional noexcept(condition)
C++
template <typename T>
void relocate(T& from, T& to) noexcept(std::is_nothrow_move_constructible_v<T>);

static_assert(noexcept(swap(a, b)));    // the noexcept operator: a compile-time query

noexcept(expression) used as an operator asks whether an expression is declared not to throw. It does not evaluate the expression.

Why it matters for moves

flowchart LR
    V["a vector must grow"] --> Q{"Is T's move constructor<br/>noexcept?"}
    Q -- yes --> M["MOVE the elements<br/>the strong guarantee still holds"]
    Q -- no --> C{"Is T copyable?"}
    C -- yes --> CP["COPY the elements<br/>so it can roll back"]
    C -- no --> M2["move anyway<br/>basic guarantee only"]

push_back promises the strong guarantee. If moving an element could throw half-way through a reallocation, some elements would already have left the old block and the vector could not restore itself. So it moves only when the move is noexcept, through std::move_if_noexcept. This is the rule stated in 7.05 Move Semantics, and now you can see where it comes from.

[!tip] What to mark noexcept Move constructors, move assignment operators and swap: always, when true. Other functions: only when not throwing is a deliberate, permanent part of their contract, since removing noexcept later can break callers.

Reporting failure without exceptions

When failure is an ordinary result, encode it in the return type.

std::optional: maybe a value

C++
std::optional<int> parseAge(std::string_view text);

if (const auto age{ parseAge(input) })
{
    std::cout << *age << '\n';
}
else
{
    std::cout << "invalid\n";
}

std::expected: a value or an error

std::expected<T, E> (C++23) holds either a T or an E explaining why there is none.

C++
#include <charconv>
#include <expected>
#include <iostream>
#include <string_view>

enum class ParseError { empty, notANumber, outOfRange };

std::expected<int, ParseError> parseAge(std::string_view text)
{
    if (text.empty())
    {
        return std::unexpected{ ParseError::empty };
    }
    int value{};
    const auto [end, error]{ std::from_chars(text.data(), text.data() + text.size(), value) };
    if (error != std::errc{} || end != text.data() + text.size())
    {
        return std::unexpected{ ParseError::notANumber };
    }
    if (value < 0 || value > 150)
    {
        return std::unexpected{ ParseError::outOfRange };
    }
    return value;
}

int main()
{
    const auto result{ parseAge("42") };
    if (result)
    {
        std::cout << "age " << *result << '\n';
    }
    else
    {
        std::cout << "error " << static_cast<int>(result.error()) << '\n';
    }
    return 0;
}

std::from_chars is the non-throwing, locale-independent way to parse a number. It returns where it stopped and an error code.

Choosing a mechanism

Mechanism Use when
assert The condition can only be false if the code has a bug
std::optional "No result" is normal and needs no explanation
std::expected Failure is normal and the caller needs to know why
Exceptions Failure is rare, is handled far from where it occurs, or happens in a constructor
Error codes Interfacing with C, or environments that disable exceptions (some games and embedded systems) 
flowchart TD
    Q1{"Is it a bug in the program?"} -- yes --> A["assert"]
    Q1 -- no --> Q2{"Is failure a normal,<br/>frequent outcome?"}
    Q2 -- "yes, and the reason matters" --> E["std::expected"]
    Q2 -- "yes, no reason needed" --> O["std::optional"]
    Q2 -- "no: it is rare" --> X["exception"]
