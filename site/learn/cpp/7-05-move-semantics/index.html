Move Semantics

lesson 7.055 of 8 in milestone 76 min3 practice tasks

Copying a large object duplicates its data. Moving transfers the data out of an object that is about to disappear, by handing over a few pointers. Rvalue references, written T&&, bind to such objects, and std::move lets you mark one as movable.

Copying versus moving

A deep copy of a million-element vector allocates a new block and copies a million elements. Sometimes that is exactly what you need. Often the source is a temporary that is about to be destroyed anyway, and duplicating its data only to throw the original away is wasted work.

 COPY: build an identical house and furnish it identically

 ┌──────────────┐               ┌──────────────┐
 │  furniture   │   ── copy ──▶ │  furniture   │     both are full
 └──────────────┘               └──────────────┘

 MOVE: hand over the keys

 ┌──────────────┐               ┌──────────────┐
 │   (empty)    │   ── keys ──▶ │  furniture   │     the old one is left empty
 └──────────────┘               └──────────────┘
C++
std::vector<int> a(1'000'000, 7);
std::vector<int> b{ a };               // copy: allocate, then copy a million ints
std::vector<int> c{ std::move(a) };    // move: take over a's block. Instant. a is now empty.
 before the move:    a ──▶ [7 7 7 ... 7]
 after the move:     a ──▶ (nothing)         c ──▶ [7 7 7 ... 7]

A move transfers ownership of the resource. Nothing is duplicated.

Lvalues and rvalues

When is it safe to take an object's contents? When nothing else will use that object afterwards. The language captures this with two value categories, introduced briefly in 4.03 References.

lvalue rvalue
Has a name or a lasting location Yes: x, v[0], *p No: 5, x + 1, makeVector()
Can have its address taken Yes No
Exists after the expression ends Yes No: it is a temporary
Safe to take from No: other code may still use it Yes: nobody else can refer to it

The full picture has finer categories, covered in 11.01 Value Categories and Perfect Forwarding. This simpler view is enough to use move semantics correctly.

Rvalue references

An ordinary reference T& binds to lvalues. An rvalue reference T&& binds to rvalues. That gives overloading a way to tell them apart.

C++
#include <iostream>
#include <string>

void take(const std::string&) { std::cout << "lvalue: must leave it alone\n"; }
void take(std::string&&)      { std::cout << "rvalue: may take its contents\n"; }

int main()
{
    std::string name{ "Ada" };
    take(name);                    // lvalue
    take(std::string{ "Bo" });     // rvalue
    take(std::move(name));         // rvalue: you marked it
    return 0;
}

Writing the move operations

A class gets move semantics from two more special member functions, both taking T&&.

C++
class Buffer
{
public:
    // constructor, destructor and copy operations as in 7.03

    Buffer(Buffer&& other) noexcept
        : m_data{ std::exchange(other.m_data, nullptr) },
          m_size{ std::exchange(other.m_size, 0) }
    {
    }

    Buffer& operator=(Buffer&& other) noexcept
    {
        if (this != &other)
        {
            delete[] m_data;
            m_data = std::exchange(other.m_data, nullptr);
            m_size = std::exchange(other.m_size, 0);
        }
        return *this;
    }

private:
    int* m_data{};
    std::size_t m_size{};
};

std::exchange(a, b) stores b into a and returns the old value of a. Here it takes the pointer and leaves nullptr behind in one step.

flowchart LR
    S["source owns the data"] -->|"move constructor"| T["target owns the data<br/>source holds nullptr"]
    T --> D["source is destroyed:<br/>delete[] nullptr does nothing"]

Leaving the source empty is essential. Its destructor will still run, and it must not release what the target now owns.

Move constructor Move assignment
Signature T(T&& other) noexcept T& operator=(T&& other) noexcept
The target Is being created Already exists and must release its old resource first

[!important] Mark move operations noexcept When a std::vector reallocates, it moves its elements only if their move constructor is noexcept. Otherwise it copies them, to stay safe if something throws half-way. Forgetting noexcept silently makes vectors of your type slow.

std::move does not move

std::move(x) is a cast. It turns x into an rvalue reference and does nothing else. The actual transfer happens in whichever move constructor or move assignment operator that cast then selects.

After being moved from, an object is in a valid but unspecified state:

C++
std::string s{ "hello" };
std::string t{ std::move(s) };

s = "new value";    // fine: assigning gives it a known state again
With a moved-from object you may You should not
Destroy it Assume anything about its contents
Assign it a new value Use it as though it still held the old value

Where moves happen without being asked

Situation Example
Returning a local object return result;
Passing a temporary v.push_back(std::string{ "x" });
Inside library code std::sort, std::swap, vector reallocation

This is why returning a vector by value has been cheap all along.

[!warning] Do not write return std::move(local); Plain return local; lets the compiler construct the result directly in the caller, skipping even the move (6.02 Constructors). Adding std::move prevents that and makes the code slower.

The Rule of Five

The Rule of Three becomes the Rule of Five:

Output
 destructor · copy constructor · copy assignment · move constructor · move assignment

 If you declare any one of them, declare all five: define, = default or = delete each.

The compiler's own rules make this important:

If you declare The compiler no longer generates
A destructor or a copy operation The move operations: "moves" quietly become copies
A move operation The copy operations: the class becomes move-only

And the Rule of Zero still beats both: use members that already move correctly, and declare nothing.

Move-only types

Some types can be moved but not copied, because having two copies would make no sense: std::unique_ptr, std::thread, file streams.

C++
std::unique_ptr<int> a{ std::make_unique<int>(5) };
std::unique_ptr<int> b{ a };               // error: copying is deleted
std::unique_ptr<int> c{ std::move(a) };    // fine: ownership is transferred
