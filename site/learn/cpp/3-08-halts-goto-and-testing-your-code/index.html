Halts, goto, and Testing Your Code

lesson 3.088 of 8 in milestone 36 min3 practice tasks

std::exit ends the program from anywhere; std::abort ends it at once with no clean-up. goto exists and you almost never want it. Testing each function with known inputs as you write it is the cheapest way to catch bugs.

Ways a program ends

flowchart TD
    A["return from main"] -->|"normal: everything is cleaned up"| Z["program ends"]
    B["std::exit(code)"] -->|"globals cleaned up,<br/>local variables are not"| Z
    C["std::abort()"] -->|"immediate, no clean-up<br/>(what a failed assert does)"| Z
How Clean-up Use it when
return from main Complete Always, if you can
std::exit(code) Partial A fatal problem deep in the program with no sensible way back
std::abort() None Something is so wrong that continuing would do harm
C++
#include <cstdlib>
#include <iostream>
#include <string_view>

void fatal(std::string_view message)
{
    std::cerr << "Fatal: " << message << '\n';
    std::exit(EXIT_FAILURE);
}

The number handed to std::exit, like the one returned from main, is the program's exit code. EXIT_SUCCESS (0) means it worked. Anything else means it did not, and other programs can check that.

"Clean-up" will mean more in Milestones 6 and 7, when objects start releasing files and memory as they are destroyed. That is why returning from main is preferred: it is the only route on which everything is released properly.

goto

goto jumps to a labelled statement elsewhere in the same function.

C++
int attempts{ 0 };
retry:
    ++attempts;
    if (attempts < 3)
    {
        goto retry;
    }

It works, and a loop says the same thing more clearly. Code that jumps around freely becomes impossible to follow, which programmers call spaghetti code. Loops, break, continue and functions cover everything goto did, with structure a reader can see.

The one case people defend is leaving several nested loops at once. A function with return does that better:

C++
bool containsPair(int limit, int target)
{
    for (int a{ 1 }; a <= limit; ++a)
    {
        for (int b{ 1 }; b <= limit; ++b)
        {
            if (a * b == target)
            {
                return true;    // leaves both loops
            }
        }
    }
    return false;
}

Testing your code

This is the part of the lesson that will change how you work.

A test is code that calls your function with inputs whose correct answer you already know, and checks the result. Every Check button you have pressed in Xenon has run tests like that against your code.

flowchart LR
    W["Write a small function"] --> T["Test it with known cases"] --> P{"pass?"}
    P -- no --> F["Fix it now, while it is<br/>small and fresh"] --> T
    P -- yes --> N["Next function"]

Testing each function as you finish it means a failure can only be in the few lines you just wrote. Testing a whole program at the end means it could be anywhere.

A small test function

C++
#include <iostream>

bool isLeapYear(int year)
{
    return (year % 4 == 0 && year % 100 != 0) || year % 400 == 0;
}

int testIsLeapYear()
{
    if (isLeapYear(2024) != true)  { return 1; }
    if (isLeapYear(2023) != false) { return 2; }
    if (isLeapYear(1900) != false) { return 3; }    // divisible by 100
    if (isLeapYear(2000) != true)  { return 4; }    // divisible by 400
    return 0;
}

int main()
{
    const int failed{ testIsLeapYear() };
    if (failed != 0)
    {
        std::cout << "Test case " << failed << " FAILED\n";
    }
    else
    {
        std::cout << "All tests passed\n";
    }
    return 0;
}

Tests stay useful after they pass. Run them again whenever you change the function, and they tell you immediately if you broke something that used to work.

Choosing test cases

Typical values are the least likely to reveal a bug. Bugs gather at the edges. For clamp(value, 0, 10):

Kind of case Examples Why
Ordinary 5 gives 5 Does it work at all?
On the boundary 0 gives 0, 10 gives 10 Catches < written for <=
Just outside -1 gives 0, 11 gives 10 Catches off-by-one errors
Extremes The largest and smallest int Catches overflow
Odd input Low limit above high limit Did you decide what should happen?

Coverage

A test can only find a bug in code it actually runs. Coverage measures how much of your code the tests execute.

Level Meaning
Statement coverage Every line ran at least once
Branch coverage Every if went both ways at least once

If no test ever makes a condition false, the else branch is untested, however many tests you have.

Real projects use a testing framework

Libraries such as Catch2 and GoogleTest remove the repetitive parts and report failures clearly. The idea is exactly the one above. See 13.09 Testing, Sanitizers, Static Analysis and Tooling.

The usual suspects

When a test fails, check these first. They account for most logic errors in the first three milestones.

Error Example
Wrong comparison age > 18 where >= was meant
Off by one i <= size
Loop that never ends The step is missing
Precedence a + b / 2
Integer division 1 / 2 * x is always 0
Stray semicolon if (x); or for (...);
= for == if (x = 0)
