Smart Pointers

lesson 7.066 of 8 in milestone 75 min3 practice tasks

Smart pointers are RAII wrappers that delete a heap object automatically. std::unique_ptr has one owner and is the default. std::shared_ptr shares ownership by counting references. std::weak_ptr observes without owning. Create them with std::make_unique and std::make_shared.

Ownership, in the type

7.02 new and delete — Dynamic Memory ended on a problem: a raw pointer cannot say who is responsible for deleting. A smart pointer is a small class that owns a heap object and deletes it in its destructor. It is RAII for new.

flowchart TD
    Q{"Is a heap object<br/>needed at all?"} -- no --> S["Use a plain value<br/>or a std::vector"]
    Q -- yes --> O{"How many owners?"}
    O -- "exactly one" --> U["std::unique_ptr<br/>(the default)"]
    O -- "several, and no clear last one" --> SH["std::shared_ptr"]
    SH --> C{"Could the owners<br/>form a cycle?"}
    C -- yes --> W["Break it with std::weak_ptr"]

All three live in <memory>.

std::unique_ptr: one owner

C++
#include <iostream>
#include <memory>
#include <string>

struct Player
{
    std::string name{};
    int hp{ 100 };
};

int main()
{
    auto hero{ std::make_unique<Player>("Aria", 100) };
    hero->hp -= 10;
    std::cout << hero->name << ' ' << hero->hp << '\n';
    return 0;
}    // the Player is deleted here, automatically
 hero (unique_ptr) ──owns──▶ [ Player "Aria" ]

 hero goes out of scope: its destructor deletes the Player
Property Detail
Use Like a pointer: *p, p->member, if (p)
Cost The same size and speed as a raw pointer
Copying Not allowed: two owners would both delete
Moving Allowed: ownership is transferred
C++
auto a{ std::make_unique<int>(5) };
auto b{ std::move(a) };    // b now owns the int; a is null
if (!a)
{
    std::cout << "a is empty\n";
}

std::make_unique<T>(arguments) allocates and constructs in one step and returns the unique_ptr. There is no new in your code and no delete anywhere.

Passing smart pointers to functions

This is where people go wrong. Most functions should not mention the smart pointer at all.

The function wants to Parameter type Call
Use the object Player& or const Player& heal(*hero);
Use it, and it may be absent Player* inspect(hero.get());
Take over ownership std::unique_ptr<Player> by value adopt(std::move(hero));

A function that only uses a Player has no business knowing how its caller stores it. Taking a reference keeps it usable with objects on the stack too.

std::shared_ptr: shared ownership

Sometimes an object has several owners and no way to know which will finish with it last. A shared_ptr keeps a reference count of its owners and deletes the object when the count reaches zero.

C++
auto texture{ std::make_shared<Texture>("grass.png") };    // count is 1
{
    auto alias{ texture };                                  // count is 2
    std::cout << texture.use_count() << '\n';               // 2
}                                                           // count is 1
// when the last owner goes, the Texture is deleted
 sprite1 ─┐
 sprite2 ─┼──▶ [ control block: count 3 ] ──▶ [ Texture ]
 sprite3 ─┘

 each copy adds 1, each destruction subtracts 1, and at 0 the object is deleted

It is not free: there is a separate control block holding the count, and updating the count must be safe across threads. Use it only when ownership really is shared. If one clear owner exists, use unique_ptr and give everyone else a reference.

Cycles and std::weak_ptr

Reference counting has one failure mode.

C++
struct Person
{
    std::string name{};
    std::shared_ptr<Person> partner{};
};

auto ann{ std::make_shared<Person>("Ann") };
auto bob{ std::make_shared<Person>("Bob") };
ann->partner = bob;
bob->partner = ann;
// ann and bob go out of scope: each count drops to 1, never to 0. Both leak.
flowchart LR
    A["Ann (count 1)"] -->|shared_ptr| B["Bob (count 1)"]
    B -->|shared_ptr| A

Each keeps the other alive for ever. The fix is for one direction not to own. A std::weak_ptr refers to an object managed by shared_ptr without adding to the count.

C++
struct Person
{
    std::string name{};
    std::weak_ptr<Person> partner{};
};

if (auto p{ ann->partner.lock() })
{
    std::cout << p->name << '\n';
}

A weak_ptr cannot be dereferenced directly, because the object might already be gone. lock() returns a shared_ptr that is either valid or empty, so the check and the access cannot be separated.

The usual shape: a parent owns its children, and each child refers back to its parent with a weak_ptr or a plain pointer.

Summary

The modern rules
  • Do not write new or delete in ordinary code. Use std::make_unique and std::make_shared.
  • Raw pointers and references are fine, as non-owning observers.
  • Default to unique_ptr. Reach for shared_ptr only when you can explain why there are several owners.

A unique_ptr can also manage things other than memory, by giving it a function to call in place of delete. That function is a custom deleter:

C++
std::unique_ptr<std::FILE, int (*)(std::FILE*)> file{ std::fopen("data.txt", "r"), &std::fclose };
