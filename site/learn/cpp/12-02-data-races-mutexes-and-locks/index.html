Data Races, Mutexes and Locks

lesson 12.022 of 7 in milestone 125 min2 practice tasks

When two threads access the same data, at least one writes, and nothing synchronizes them, you have a data race: undefined behaviour. A mutex admits one thread at a time to a critical section. Lock it with RAII: std::lock_guard, std::scoped_lock, std::unique_lock. Beware deadlock.

A data race

C++
#include <iostream>
#include <thread>

int main()
{
    int counter{ 0 };
    auto increment{ [&]
    {
        for (int i{ 0 }; i < 1'000'000; ++i)
        {
            ++counter;
        }
    } };

    {
        std::jthread a{ increment };
        std::jthread b{ increment };
    }
    std::cout << counter << '\n';    // expected 2000000; typically something like 1374209
    return 0;
}

++counter is not one step. It reads, adds and writes back, and two threads can interleave those steps.

Output
 Thread A                  Thread B                  counter
 read counter (5)                                       5
                           read counter (5)             5
 add 1, giving 6                                        5
                           add 1, giving 6              5
 write 6                                                6
                           write 6                      6     one increment is lost
Term Meaning
Data race Two threads access the same memory location, at least one writes, and the accesses are not ordered by synchronization. It is undefined behaviour.
Race condition The correctness of the result depends on timing. A broader notion: it can exist without any data race.

Because a data race is undefined behaviour, the lost update is only the mildest possible outcome. The compiler may assume races do not happen and optimise accordingly.

std::mutex

A mutex ("mutual exclusion") can be locked by one thread at a time. A thread that tries to lock a locked mutex blocks until it is released. The code executed while holding it is a critical section.

C++
#include <mutex>

int counter{ 0 };
std::mutex mutex{};

auto increment{ [&]
{
    for (int i{ 0 }; i < 1'000'000; ++i)
    {
        std::lock_guard lock{ mutex };    // lock
        ++counter;
    }                                     // unlock, in the destructor
} };
sequenceDiagram
    participant A as Thread A
    participant M as the mutex
    participant B as Thread B
    A->>M: lock: acquired
    B->>M: lock: blocked
    A->>A: ++counter
    A->>M: unlock
    M-->>B: acquired
    B->>B: ++counter
    B->>M: unlock

[!danger] Never call lock() and unlock() yourself An early return or an exception between them leaves the mutex locked for ever, and every other thread that needs it stops. A lock object releases it on every path. This is RAII applied to locking (7.04 RAII and the Rule of Three).

The lock types

Lock Use it for
std::lock_guard The simple case: hold one mutex for a scope
std::scoped_lock Locking several mutexes together, without deadlock
std::unique_lock Flexibility: unlock early, lock later, move it, use it with a condition variable
std::shared_lock with std::shared_mutex Many readers at once, or one writer
C++
std::shared_mutex guard{};
std::map<std::string, int> cache{};

int read(const std::string& key)
{
    std::shared_lock lock{ guard };    // shared: other readers may enter
    return cache.at(key);
}

void write(const std::string& key, int value)
{
    std::unique_lock lock{ guard };    // exclusive
    cache[key] = value;
}

A reader-writer lock helps only when reads greatly outnumber writes and each takes long enough to matter. It is more expensive than a plain mutex, so measure.

Deadlock

 Thread A: holds m1, wants m2          Thread B: holds m2, wants m1

        ┌──── waits for m2 ────▶ held by B
   A ───┘                               │
   ▲                                    │
   └────── held by A ◀── waits for m1 ──┘        neither can ever proceed

A deadlock arises when each of a set of threads holds something another needs. With mutexes, it takes two threads acquiring the same two locks in opposite orders.

C++
void transfer(Account& from, Account& to, int amount)
{
    std::scoped_lock lock{ from.mutex, to.mutex };    // acquires both, in a safe manner
    from.balance -= amount;
    to.balance += amount;
}

std::scoped_lock given several mutexes acquires them with an algorithm that cannot deadlock, whatever order other threads name them in.

Rule Why
Acquire multiple mutexes with one std::scoped_lock It is deadlock-free by construction
Otherwise, always acquire in one agreed global order Opposite orders are what create the cycle
Never call unknown code while holding a lock A callback may try to take the same lock, or another
Keep critical sections short Less contention, and fewer chances to nest locks

Put the mutex with the data

The mutex and the data it protects belong in one class, with the data private. Then access without the lock is impossible to write.

C++
class ThreadSafeCounter
{
public:
    void increment()
    {
        std::lock_guard lock{ m_mutex };
        ++m_value;
    }

    int value() const
    {
        std::lock_guard lock{ m_mutex };
        return m_value;
    }

private:
    mutable std::mutex m_mutex{};
    int m_value{};
};

The mutex is mutable (6.04 this, const Member Functions and Chaining) so that a const function, which logically only reads, can still lock it.

Thread-safe operations do not compose

Each member function above is safe on its own. A sequence of them is not:

C++
if (counter.value() < 10) { counter.increment(); }    // another thread can run in between

The check and the action must happen under one lock, so the class needs a single operation that does both. Design the interface around whole operations.

Other tools

Tool Purpose
std::call_once with a std::once_flag Run an initialization exactly once, even with several threads racing to it
A function-local static variable Its initialization is guaranteed thread-safe
std::recursive_mutex May be locked repeatedly by the thread that holds it. Usually a sign the design needs rethinking.
