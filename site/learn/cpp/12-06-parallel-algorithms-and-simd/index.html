Parallel Algorithms and SIMD

lesson 12.066 of 7 in milestone 125 min1 practice task

Most standard algorithms accept an execution policy as their first argument, as in std::sort(std::execution::par, v.begin(), v.end()). The library then divides the work across cores, and SIMD lanes, for you. The functions you pass must be safe to run concurrently. The policies are in <execution>.

One argument, every core

The highest level of parallelism in the standard library asks for none of the machinery of the previous lessons.

C++
#include <algorithm>
#include <cmath>
#include <execution>
#include <iostream>
#include <numeric>
#include <vector>

int main()
{
    std::vector<double> v(2'000'000);
    std::iota(v.begin(), v.end(), 0.0);

    std::transform(std::execution::par, v.begin(), v.end(), v.begin(),
        [](double x) { return std::sqrt(x); });

    const double total{ std::reduce(std::execution::par, v.begin(), v.end()) };
    std::cout << total << '\n';
    return 0;
}

The algorithm decides how to split the range, how many threads to use and how to combine the partial results. Most implementations run on a shared thread pool.

Execution policies

Policy Threads Vectorized What your function may do
std::execution::seq One No Anything
std::execution::par Several No Must be free of data races; may lock a mutex
std::execution::par_unseq Several Yes Must not lock, allocate or otherwise synchronize
std::execution::unseq (C++20) One Yes The same restrictions as par_unseq

SIMD, "single instruction, multiple data", is parallelism inside one core. A vector register holds several values, and one instruction operates on all of them.

Output
 scalar:   a0+b0   then   a1+b1   then   a2+b2   then   a3+b3        four instructions
 SIMD:     [a0 a1 a2 a3] + [b0 b1 b2 b3]                              one instruction

 par_unseq: several cores, each using its SIMD lanes

A policy is permission, not a command. The library may run sequentially if it judges the input too small.

[!warning] Why the unseq policies forbid locking Vectorizing means several iterations are interleaved on the same thread: iteration 1 may begin before iteration 0 finishes. If the function locks a mutex, the second iteration tries to take a lock the same thread already holds, and deadlocks. The same reasoning excludes memory allocation, which usually takes a lock internally.

reduce and accumulate

Algorithm Order of operations Can run in parallel
std::accumulate Strictly left to right No
std::reduce Any grouping, any order Yes
std::transform_reduce Transform each element, then reduce Yes

accumulate is defined as ((a + b) + c) + d, which is inherently sequential. reduce is allowed to regroup, so two halves can be summed independently.

C++
const double dot{ std::transform_reduce(std::execution::par, a.begin(), a.end(), b.begin(), 0.0) };
The operation must be associative and commutative

reduce gives a well-defined answer only if regrouping and reordering do not change it. Subtraction fails that test. Floating-point addition nearly passes: it is not exactly associative, so reduce can differ from accumulate in the last digits, and from one run to the next.

Rules for the functions you pass

C++
int count{ 0 };
std::for_each(std::execution::par, v.begin(), v.end(),
    [&](double x) { if (x > 10) { ++count; } });    // DATA RACE on count

const auto n{ std::count_if(std::execution::par, v.begin(), v.end(),
    [](double x) { return x > 10; }) };             // correct: the algorithm combines the results
Rule Reason
Do not write to shared state It is a data race. An atomic would fix the race and make it slow.
Choose the algorithm that produces the result count_if, reduce, transform_reduce and any_of aggregate safely for you
Do not let an exception escape Under a parallel policy that calls std::terminate
Do not assume an order Elements are processed in no particular sequence

The ideal function is pure: its result depends only on its argument and it changes nothing else (10.03 Ranges and Views (C++20/23)).

When it helps

Parallelism has overheads: dividing the work, waking threads and combining results.

Situation Outcome
Millions of elements, real work per element Close to one speed-up per core
A cheap operation on a huge array Often limited by memory speed, not by the processor
A few thousand elements Frequently slower than sequential
The work is dominated by one sequential step Little gain, however many cores

The last row is Amdahl's law: if 10% of a job cannot be parallelized, no number of cores makes it more than ten times faster. Measure before and after, in a Release build (5.11 Sorting, Searching, Big-O and Timing Your Code).
