Exceptions

lesson 9.055 of 6 in milestone 95 min3 practice tasks

When a function cannot do its job, it throws an exception. Control leaves the function and travels up the call stack, running destructors on the way (stack unwinding), to the nearest matching catch. Throw by value, catch by const&, and derive your exception types from std::exception.

Why exceptions?

A function that cannot fulfil its purpose must tell its caller. The traditional way is a special return value.

C++
int result{ parse(text) };
if (result == -1)
{
    // an error? or is -1 a legitimate result?
}
Return codes Exceptions
Easy to ignore: forgetting the check compiles Cannot be ignored: unhandled, the program stops
Every caller at every level must check and pass it on Intermediate functions need no error-handling code
Compete with the real return value Travel on a separate channel
Impossible in constructors, which return nothing Work in constructors

throw, try, catch

C++
#include <iostream>
#include <stdexcept>

double safeDivide(double a, double b)
{
    if (b == 0.0)
    {
        throw std::invalid_argument{ "division by zero" };
    }
    return a / b;
}

int main()
{
    try
    {
        std::cout << safeDivide(10, 2) << '\n';    // 5
        std::cout << safeDivide(1, 0) << '\n';     // throws
        std::cout << "never printed\n";
    }
    catch (const std::invalid_argument& e)
    {
        std::cerr << "Error: " << e.what() << '\n';
    }
    std::cout << "the program continues\n";
    return 0;
}
Keyword Role
throw expression; Raises an exception. The current function stops immediately.
try { } Marks a block whose exceptions the following handlers may catch
catch (type) { } A handler: runs if an exception of a matching type arrives

Stack unwinding

After a throw, the runtime searches outwards through the active function calls for a matching handler. Each scope it leaves is cleaned up properly.

sequenceDiagram
    participant main
    participant load as loadLevel
    participant parse as parseFile
    main->>load: call (inside a try block)
    load->>parse: call
    parse--xparse: throw ParseError
    Note over parse: its local objects are destroyed
    parse--xload: no handler here
    Note over load: its local objects are destroyed
    load--xmain: caught by catch (const ParseError&)

This is stack unwinding. The destructor of every fully constructed local object runs, in reverse order, exactly as if each scope had ended normally. It is the reason RAII (7.04 RAII and the Rule of Three) makes code safe in the presence of exceptions without any extra effort: resources held by objects are released on the way out.

The standard hierarchy

 std::exception
 ├── std::logic_error                 errors in the program's logic
 │    ├── std::invalid_argument
 │    ├── std::out_of_range           v.at(i), std::stoi
 │    └── std::domain_error, std::length_error
 ├── std::runtime_error               failures detectable only while running
 │    ├── std::range_error, std::overflow_error
 │    └── std::system_error
 │         └── std::filesystem::filesystem_error
 ├── std::bad_alloc                   new could not obtain memory
 ├── std::bad_cast                    dynamic_cast to a reference failed
 └── std::bad_optional_access, std::bad_variant_access

A handler for a base class also catches every class derived from it.

C++
try
{
    process();
}
catch (const std::out_of_range& e)    // most specific first
{
}
catch (const std::logic_error& e)
{
}
catch (const std::exception& e)       // any standard exception
{
    std::cerr << e.what() << '\n';
}
catch (...)                           // anything at all
{
    std::cerr << "unknown error\n";
}
Order and reference

Handlers are tried from top to bottom and the first match wins, so derived types must come before their bases. And catch by const&: catching by value copies the exception and slices it to the handler's type (8.06 Object Slicing, Casting and Composition).

Your own exception types

Derive from a standard exception so that existing handlers for std::exception still work.

C++
class ParseError : public std::runtime_error
{
public:
    ParseError(const std::string& message, int line)
        : std::runtime_error{ message + " (line " + std::to_string(line) + ")" }, m_line{ line }
    {
    }

    int line() const { return m_line; }

private:
    int m_line{};
};

throw ParseError{ "unexpected '}'", 42 };

A dedicated type lets callers handle that failure specifically, and carry structured data such as the line number.

Rethrowing

A handler that cannot fully deal with an exception can pass it on.

C++
catch (const std::exception& e)
{
    log(e.what());
    throw;         // rethrows the original exception, with its real type
}

Write throw; with no operand. throw e; would throw a copy of e with the handler's declared type, slicing a derived exception down to std::exception.

Exceptions from constructors

A constructor that throws means the object never came into existence. Its destructor does not run. Members and base classes that were already constructed are destroyed.

To catch exceptions thrown by the member initializer list, use a function try block:

C++
class Widget
{
public:
    Widget() try : m_resource{ "config.txt" }
    {
    }
    catch (const std::exception& e)
    {
        std::cerr << "Widget failed: " << e.what() << '\n';
        // the exception is rethrown automatically: a half-built object cannot be rescued
    }

private:
    Resource m_resource;
};

Uncaught exceptions

If no handler matches anywhere, std::terminate is called and the program ends, possibly without unwinding. A top-level handler in main guarantees a clean exit and a readable message.

C++
#include <iostream>
#include <stdexcept>

void run()
{
    throw std::runtime_error{ "the settings file is missing" };
}

int main()
{
    try
    {
        run();
    }
    catch (const std::exception& e)
    {
        std::cerr << "Fatal: " << e.what() << '\n';
        return 1;
    }
    return 0;
}

When to use exceptions

Use them for Do not use them for
Failures that are rare: a missing file, malformed data, no memory Ordinary control flow, such as leaving a loop
Failures in constructors Outcomes that are expected: bad user input is asked for again
Errors detected far from the code able to handle them Bugs. Use assert: 3.07 Input Validation and assert

Throwing is slow, on the order of microseconds, while the non-throwing path costs essentially nothing. Exceptions suit failures that are rare. For failures that are a normal outcome, return a std::optional or std::expected: 9.06 Exception Safety, noexcept and std::expected.
