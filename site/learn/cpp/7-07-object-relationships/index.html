Object Relationships

lesson 7.077 of 8 in milestone 75 min3 practice tasks

Objects relate in a few standard ways. Composition: a part that is owned and dies with the whole. Aggregation: has it, but does not own it. Association: knows about it. Dependency: uses it briefly. Which one applies decides how you store the member.

Five relationships

Designing a program is largely deciding how its objects relate. Each relationship has a name, a meaning, and a natural way to write it in C++.

The middle column is the one that matters for this milestone. It is the ownership question from 7.02 new and delete — Dynamic Memory, asked about members.

Composition

The part belongs to the whole and has no life outside it.

C++
class Engine
{
public:
    void start() { std::cout << "vroom\n"; }
};

class Car
{
public:
    void drive() { m_engine.start(); }

private:
    Engine m_engine{};
    std::vector<Wheel> m_wheels{ 4 };
};
 ┌─────── Car ────────┐
 │ ┌──────┐ ┌──────┐  │     destroy the Car and the
 │ │Engine│ │Wheels│  │     Engine and Wheels go with it
 │ └──────┘ └──────┘  │
 └────────────────────┘

A value member is the simplest, fastest and safest form. Use a std::unique_ptr member only when you need what a pointer offers: the part may be absent, may be replaced, or is of a type chosen while running.

Aggregation

The whole refers to parts that exist on their own and may outlive it.

C++
class Department
{
public:
    void add(Teacher& teacher) { m_teachers.push_back(&teacher); }

private:
    std::vector<Teacher*> m_teachers{};    // not owned
};

Teacher bob{ "Bob" };
{
    Department maths{};
    maths.add(bob);
}    // the Department is gone. Bob is unaffected.

The raw pointers here are observers, which is a legitimate use. The obligation runs the other way: the teachers must outlive the department's use of them, or the pointers dangle.

A vector cannot hold references

std::vector<Teacher&> does not compile, because a reference cannot be reassigned and a vector must be able to move its elements. Use pointers, or std::vector<std::reference_wrapper<Teacher>>.

Association

Two independent objects that know about each other.

C++
class Patient;

class Doctor
{
public:
    void addPatient(Patient& patient);

private:
    std::vector<Patient*> m_patients{};
};

class Patient
{
private:
    std::vector<Doctor*> m_doctors{};
};

Links in both directions have to be kept consistent: adding a patient to a doctor must also add the doctor to the patient, and removal must undo both. Prefer a link in one direction, or store an identifier and look the object up when needed.

Dependency

The lightest relationship. One class uses another for the length of a function call and keeps nothing.

C++
class Printer
{
public:
    void print(const Document& document);
};

Choosing

flowchart TD
    Q1{"Is B a kind of A?"} -- yes --> I["Inheritance<br/>(Milestone 8)"]
    Q1 -- no --> Q2{"Is B a part of A that<br/>cannot exist without it?"}
    Q2 -- yes --> C["Composition<br/>value member or unique_ptr"]
    Q2 -- no --> Q3{"Does A keep a lasting<br/>link to B?"}
    Q3 -- yes --> A["Aggregation or association<br/>pointer, weak_ptr or identifier"]
    Q3 -- no --> D["Dependency<br/>function parameter"]
Prefer the weakest relationship that works

A dependency is easier to reason about than a stored link, and composition is easier than inheritance. The well-known advice "favour composition over inheritance" is explained in 8.06 Object Slicing, Casting and Composition.
