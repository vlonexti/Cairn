Performance, Caches and Data-Oriented Design

lesson 13.044 of 10 in milestone 137 min3 practice tasks

Modern processors are fast and memory is slow. Performance comes from keeping data in the cache: contiguous arrays, predictable access, small hot data. Measure first, optimize the hot spot, and measure again. Data-oriented design arranges data around how it is processed.

The memory hierarchy

A processor can execute several instructions in the time light travels a few centimetres. Fetching a value from main memory takes hundreds of times longer. Between the two sits a stack of caches: small, fast memories that hold recently used data.

              approximate time to read        size
 register     0.3 ns                          bytes
 L1 cache     1 ns      █                     32 to 64 KB per core
 L2 cache     4 ns      ████                  256 KB to 2 MB per core
 L3 cache     15 ns     ███████████████       8 to 64 MB, shared
 main memory  80 ns     ████████████████████████████████████████████████████████████████████████████████
 SSD          100,000 ns
Fact Consequence
Memory moves between levels in cache lines of 64 bytes Touching one byte brings its 63 neighbours with it at no extra cost
A request the cache cannot satisfy is a cache miss It costs roughly a hundred instructions' worth of time
The processor's prefetcher detects regular patterns Walking an array in order is fetched ahead of you; hopping around is not

For most programs, how the data is laid out in memory matters more than how many instructions are executed.

Access patterns

C++
// Rows are contiguous in memory.
for (int r{ 0 }; r < n; ++r)
{
    for (int c{ 0 }; c < n; ++c)
    {
        sum += grid[r][c];    // sequential: every byte of each cache line is used
    }
}

for (int c{ 0 }; c < n; ++c)
{
    for (int r{ 0 }; r < n; ++r)
    {
        sum += grid[r][c];    // jumps a whole row each step: a new cache line nearly every access
    }
}
Output
 row by row:        [■■■■■■■■][■■■■■■■■][■■■■■■■■]     every element fetched is used
 column by column:  [■·······][■·······][■·······]     one element used per line fetched

Same work, same Big-O, and the second can be five to ten times slower on a large grid.

The same reasoning explains 10.01 Choosing STL Containers. A std::list or std::map puts each node in its own allocation, so every step of a traversal may be a miss. A std::vector is one contiguous run.

Arrays of structs and structs of arrays

C++
// Array of structs
struct Particle
{
    Vec3 position{};
    Vec3 velocity{};
    Color color{};
    float age{};
    bool alive{};
    std::string name{};
};
std::vector<Particle> particles{};

// Struct of arrays
struct Particles
{
    std::vector<Vec3> positions{};
    std::vector<Vec3> velocities{};
    std::vector<float> ages{};
    // colours and names live elsewhere: they are not needed every frame
};
Output
 updating positions, array of structs:
   [pos vel color age alive name][pos vel color age alive name] ...     most of each line is not needed

 updating positions, struct of arrays:
   positions:   [p p p p p p p p ...]
   velocities:  [v v v v v v v v ...]                                   every byte loaded is used
Array of structs Struct of arrays
Natural to write Yes Less so
All fields of one object One line of cache One miss per field
One field across many objects Wastes most of each line Ideal
Automatic vectorization Harder Easy

Data-oriented design starts from the question "what transformations happen to this data, and how often?" and lays the data out to suit the common ones. Data read together is stored together; data used every frame (hot) is separated from data used rarely (cold).

Branch prediction

The processor guesses which way each branch will go and runs ahead. A wrong guess discards that work.

C++
for (int x : data)
{
    if (x >= 128)
    {
        sum += x;
    }
}

On random data, this branch is a coin toss and mispredicts half the time. On the same data sorted, it is false for a long run and then true for a long run, and the loop becomes several times faster. Removing the branch has the same effect:

C++
for (int x : data)
{
    sum += (x >= 128) * x;    // no branch to predict
}

[[likely]] and [[unlikely]] let you tell the compiler which path to lay out as the fast one.

Measure, do not guess

Intuition about performance is unreliable, including the intuition of experts. The method is empirical.

flowchart LR
    A["Write clear code"] --> B["Profile a Release build:<br/>find the hot few percent"] --> C["Form a hypothesis"] --> D["Change ONE thing"] --> E["Measure"] --> F{"faster?"}
    F -- yes --> G["keep it"] --> B
    F -- no --> H["revert it"] --> B
Tool For
A profiler (Visual Studio's, perf, VTune, Tracy) Finding where the time actually goes
A micro-benchmark library (Google Benchmark) Timing one small piece with proper statistics
Compiler Explorer (godbolt.org) Reading the machine code the compiler produced

A profiler samples the running program and reports which functions the time was spent in. Typically a few percent of the code accounts for most of the run time. Optimizing anything else achieves nothing.

Benchmarking has traps of its own. The optimizer deletes work whose result is unused, so benchmark libraries provide a way to mark a value as used. Run several times and distrust small differences. Always measure a Release build.

C++
#include <benchmark/benchmark.h>

static void BM_VectorPush(benchmark::State& state)
{
    for (auto _ : state)
    {
        std::vector<int> v{};
        for (int i{ 0 }; i < state.range(0); ++i)
        {
            v.push_back(i);
        }
        benchmark::DoNotOptimize(v.data());
    }
}
BENCHMARK(BM_VectorPush)->Range(8, 1 << 16);
BENCHMARK_MAIN();
Two opposite mistakes

Premature optimization: contorting code for speed before knowing where the time goes. It costs clarity and usually gains nothing. Premature pessimization: needless copies, a std::list by default, an allocation per loop iteration. That is not simplicity; it is carelessness. Write code that is efficient by default and clear. Optimize deeply only where measurement points.
