Compiler Settings, Build Configurations and Undefined Behavior

lesson 1.1010 of 10 in milestone 15 min3 practice tasks

Turn compiler warnings up and read them. Build in Debug while you work and Release when you finish. And meet the most important phrase in C++: undefined behaviour.

The compiler has settings

So far you have pressed Run and let the compiler get on with it. It has a few settings that matter, and Xenon has already chosen sensible ones. This lesson explains what they are, so they are not a mystery when you set up your own tools one day.

Warnings: the compiler's advice

An error means "I cannot build this". A warning means "I can build this, but it looks like a mistake".

C++
#include <iostream>

int main()
{
    int total{ 10 };
    int count{ 3 };
    int unused{ 5 };
    std::cout << total / count << '\n';
    return 0;
}

This builds and runs. With warnings turned up, the compiler also tells you that unused is never used. Perhaps you meant to use it and forgot.

Error Warning
Does the program build? No Yes
Should you fix it? You have to Yes, nearly always
Treat warnings as errors

Xenon compiles at a high warning level and shows warnings in the Problems tab. Some tasks are marked strict: they only pass when there are no warnings at all. That is how professional teams work, and it is a good habit to start now.

Debug and Release

The same source code can be built in two ways.

flowchart LR
    SRC["Your code"] --> DBG["Debug build<br/>extra safety checks<br/>slower"]
    SRC --> REL["Release build<br/>optimised<br/>fast"]
    DBG --> D1["Use while writing<br/>and fixing"]
    REL --> R1["Use for the<br/>finished program"]
Debug Release
Speed Slower Often many times faster
Extra checks for mistakes Yes No
Use it when You are still working You are finished, or measuring speed

In an optimised build the compiler rearranges your code to run faster while producing the same results. Xenon uses Debug unless you change it, because the extra checks catch mistakes. You can switch in Settings.

Which version of C++?

C++ is revised every three years, and a compiler has to be told which version to follow. Xenon uses the newest. If you copy code from an old tutorial and it looks different from what you learn here, a different version is usually the reason.

Undefined behaviour

This is the single most important idea in the lesson.

Most languages stop you when you do something senseless. C++ often does not. For certain mistakes, the rules of the language simply do not say what happens. That is called undefined behaviour, usually shortened to UB.

flowchart TD
    UB["Code with undefined behaviour"] --> A["Seems to work<br/>(the worst outcome:<br/>the mistake stays hidden)"]
    UB --> B["Wrong answer"]
    UB --> C["Crash"]
    UB --> D["Works today,<br/>breaks tomorrow"]

You have already met one example:

C++
int score;                  // never given a value
std::cout << score << '\n'; // undefined behaviour

This might print 0. It might print 32767. It might print something different on another computer or after an unrelated change. All of those are "allowed", because the rules promise nothing.

"It works on my machine" proves nothing

Code with undefined behaviour can pass every test you run and still be wrong. The only safe approach is to know the rules and not break them. The Debug build's extra checks catch some cases for you, which is one more reason to use it.

Words you cannot use as names

C++ reserves about ninety words for itself, called keywords. You have used several already: int, double, return, void, true, false. You cannot name a variable or a function with one of them. The editor shows keywords in their own colour, so if a name you chose changes colour, pick another.
