Custom Memory: Placement new, Allocators and PMR

lesson 13.033 of 10 in milestone 136 min2 practice tasks

new does two things: it obtains raw memory and constructs an object in it. The two can be separated. Placement new, or std::construct_at, constructs in memory you already have. Custom allocators and PMR (polymorphic memory resources) let containers draw their memory from arenas, pools or the stack.

new is two operations

flowchart LR
    N["new Widget(args)"] --> A["1. operator new(sizeof(Widget))<br/>obtain raw bytes"] --> C["2. construct a Widget<br/>in those bytes"]
    D["delete p"] --> X["1. run ~Widget()"] --> F["2. operator delete(p)<br/>release the bytes"]

Separating allocation from construction is what makes most of the standard library possible.

C++
#include <cstddef>
#include <iostream>
#include <memory>
#include <new>

struct Widget
{
    Widget(int a, int b) : sum{ a + b } { std::cout << "constructed\n"; }
    ~Widget() { std::cout << "destroyed\n"; }
    int sum{};
};

int main()
{
    alignas(Widget) std::byte storage[sizeof(Widget)];

    Widget* w{ ::new (static_cast<void*>(storage)) Widget{ 1, 2 } };    // construct only
    std::cout << w->sum << '\n';
    w->~Widget();                                                       // destroy only

    Widget* w2{ std::construct_at(reinterpret_cast<Widget*>(storage), 3, 4) };
    std::cout << w2->sum << '\n';
    std::destroy_at(w2);
    return 0;
}
Form Does
::new (address) T{ args } Placement new: constructs a T at address; allocates nothing
std::construct_at(pointer, args...) The same, as a function usable in constexpr code
p->~T(), std::destroy_at(p) Runs the destructor; releases nothing

The storage must be large enough and suitably aligned, hence alignas(Widget). The destructor call is the one place where invoking a destructor explicitly is correct: nothing else will do it.

Library type How it uses the separation
std::vector reserve obtains capacity without constructing elements; push_back constructs into it
std::optional Holds storage for a T inline and constructs it only when given a value
std::variant One buffer, re-used for whichever alternative is active

Replacing operator new

A class can supply its own allocation functions, which new and delete then use for that class.

C++
struct Particle
{
    static void* operator new(std::size_t size);
    static void operator delete(void* p) noexcept;
};

The global operator new can be replaced too, by defining it once in the program. That is how tools count or trace every allocation.

Why replace the allocator at all?

A general-purpose allocator must cope with any size, any lifetime and any thread. That generality costs time per call, and it scatters objects across memory. When you know more about the pattern of use, you can do far better.

The arena

Output
 arena:  [■■■■■■■■■■■■■■■■□□□□□□□□□□□□□□□□□□□□□□]
                           ▲ next

 allocate(n):   result = next;  next += n;         a pointer increment
 deallocate:    nothing
 reset:         next = start;                      everything released at once

An arena (also called a bump or monotonic allocator) hands out consecutive pieces of one large block. Individual deallocation does nothing; the whole arena is released or reset in one step. It is the fastest allocation strategy there is, and suits anything with a shared lifetime: the objects for one frame, one request or one parse.

Polymorphic memory resources

Since C++17, the containers in namespace std::pmr take a memory resource chosen at run time.

C++
#include <array>
#include <cstddef>
#include <iostream>
#include <memory_resource>
#include <string>
#include <vector>

int main()
{
    std::array<std::byte, 64 * 1024> buffer{};
    std::pmr::monotonic_buffer_resource arena{ buffer.data(), buffer.size() };

    std::pmr::vector<int> numbers{ &arena };
    for (int i{ 0 }; i < 1000; ++i)
    {
        numbers.push_back(i);    // no call to the heap
    }

    std::pmr::vector<std::pmr::string> names{ &arena };
    names.emplace_back("a string long enough to need an allocation of its own");

    std::cout << numbers.size() << ' ' << names.size() << '\n';
    return 0;
}    // the arena is released in one step

std::pmr::vector<T> is an alias for std::vector<T, std::pmr::polymorphic_allocator<T>>. The allocator holds a pointer to a std::pmr::memory_resource, an abstract base class, and forwards to it. Because the resource is not part of the container's type, two pmr vectors using different resources are the same type and can be passed to the same functions. It is type erasure applied to allocation (11.06 Type Erasure).

Note std::pmr::vector<std::pmr::string>: a pmr container passes its resource on to elements that are themselves pmr-aware, so the strings' characters come from the arena too. A plain std::string element would still use the heap.

flowchart TD

    MR --> M3["synchronized_pool_resource<br/>pools by size, thread-safe"]
    MR --> M4["new_delete_resource()<br/>the ordinary heap"]
    MR --> M5["a resource of your own"]
Resource Suits
monotonic_buffer_resource Short bursts with one shared lifetime: parsing, per-frame scratch data
unsynchronized_pool_resource Many small allocations and deallocations on one thread
synchronized_pool_resource The same, across threads
null_memory_resource() As the upstream of an arena: it throws, proving the buffer was never exceeded

Resources chain. Each has an upstream resource to fall back on when it runs out, the default being the heap.

Writing a resource

C++
class CountingResource : public std::pmr::memory_resource
{
public:
    std::size_t allocations{ 0 };

private:
    void* do_allocate(std::size_t bytes, std::size_t alignment) override
    {
        ++allocations;
        return m_upstream->allocate(bytes, alignment);
    }

    void do_deallocate(void* p, std::size_t bytes, std::size_t alignment) override
    {
        m_upstream->deallocate(p, bytes, alignment);
    }

    bool do_is_equal(const std::pmr::memory_resource& other) const noexcept override
    {
        return this == &other;
    }

    std::pmr::memory_resource* m_upstream{ std::pmr::get_default_resource() };
};

Three virtual functions define a resource. The public allocate and deallocate are non-virtual and call them: the non-virtual interface idiom from 8.05 Abstract Classes and Interfaces.

Classic allocators

The older mechanism makes the allocator a template parameter: std::vector<T, MyAllocator<T>>.

Template allocator PMR
The strategy is fixed At compile time, in the container's type At run time
Containers with different strategies Are different types Are the same type
Cost per allocation None beyond the allocation One virtual call
Effort to write Considerable Three functions

Prefer PMR unless the virtual call is shown to matter.

The resource must outlive the container

A pmr container stores a raw pointer to its resource. Destroy the arena first and every later allocation or deallocation touches a dead object. Declare the resource before the containers that use it, so it is destroyed after them.
