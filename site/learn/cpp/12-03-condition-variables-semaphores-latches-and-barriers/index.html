Condition Variables, Semaphores, Latches and Barriers

lesson 12.033 of 7 in milestone 125 min2 practice tasks

Mutexes protect data. These tools let threads wait for each other. A std::condition_variable sleeps until told that something changed. C++20 adds std::counting_semaphore (limit concurrent access), std::latch (a one-shot countdown) and std::barrier (a reusable meeting point).

Waiting without burning a core

A thread often has to wait for another: for work to arrive, for a result, for initialization to finish.

C++
while (!ready) {}    // spins at 100% of a core, and is a data race on ready

This is busy-waiting. What is wanted is for the thread to sleep and be woken when the situation changes.

std::condition_variable

A condition variable lets a thread sleep until another thread notifies it. It always works with a mutex protecting the state being waited on.

C++
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <queue>
#include <thread>

std::mutex mutex{};
std::condition_variable workAvailable{};
std::queue<int> jobs{};

void producer()
{
    for (int i{ 0 }; i < 5; ++i)
    {
        {
            std::lock_guard lock{ mutex };
            jobs.push(i);
        }
        workAvailable.notify_one();
    }
}

void consumer()
{
    for (int n{ 0 }; n < 5; ++n)
    {
        std::unique_lock lock{ mutex };
        workAvailable.wait(lock, [] { return !jobs.empty(); });
        const int job{ jobs.front() };
        jobs.pop();
        lock.unlock();                 // do not hold the lock while working
        std::cout << "processing " << job << '\n';
    }
}

int main()
{
    std::jthread c{ consumer };
    std::jthread p{ producer };
    return 0;
}

wait(lock, predicate) does this, atomically where it matters:

  1. If the predicate is already true, return at once.
  2. Otherwise release the lock and sleep, as one indivisible step.
  3. On waking, reacquire the lock and test the predicate again. If it is false, go back to step 2.

Always wait with a predicate

Two hazards make the bare wait(lock) wrong. Spurious wake-ups: a waiting thread may wake without any notification. Lost wake-ups: a notification sent before the thread starts waiting is not remembered. The predicate form handles both, because the condition is checked before sleeping and after every wake-up. The condition is the truth; the notification is only a hint to look again.

Detail Reason
wait needs a std::unique_lock It must unlock and relock, which a lock_guard cannot do
Modify the shared state under the mutex Otherwise a waiter can check, miss the change, and sleep for ever
Notify after releasing the lock The woken thread can then acquire it immediately
notify_one or notify_all One waiter can use the change; or all must re-examine it

std::condition_variable_any accepts a std::stop_token in wait, so a jthread blocked in a wait can be cancelled.

Semaphores

A semaphore holds a count of permits. acquire() takes one, blocking if none are left. release() returns one.

C++
#include <semaphore>

std::counting_semaphore<3> slots{ 3 };

void download(int id)
{
    slots.acquire();
    std::cout << "downloading " << id << '\n';
    std::this_thread::sleep_for(std::chrono::seconds{ 1 });
    slots.release();
}
// started on ten threads, at most three download at any moment

std::binary_semaphore is a semaphore with one permit, often used as a light signal from one thread to another.

std::latch

A latch is a counter that only goes down. Threads can block until it reaches zero. It is single-use.

C++
#include <latch>

std::latch ready{ 4 };
for (int i{ 0 }; i < 4; ++i)
{
    workers.emplace_back([&]
    {
        loadAssets();
        ready.count_down();
    });
}
ready.wait();    // continues only after all four have counted down

Use it for "wait until these N things have happened once", such as start-up.

std::barrier

A barrier is a reusable meeting point for a fixed number of threads. Each calls arrive_and_wait() and blocks until all have arrived. Then an optional completion function runs once, and all are released for the next phase.

C++
#include <barrier>

std::barrier sync{ 4, []() noexcept { std::cout << "--- step complete ---\n"; } };

auto worker{ [&](int id)
{
    for (int step{ 0 }; step < 3; ++step)
    {
        simulatePart(id, step);
        sync.arrive_and_wait();
    }
} };

It suits simulations that advance in lock-step: every thread computes its part of generation N, and no one starts N+1 until all have finished.
