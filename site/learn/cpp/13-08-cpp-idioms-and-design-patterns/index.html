C++ Idioms and Design Patterns

lesson 13.088 of 10 in milestone 138 min2 practice tasks

Idioms are solutions specific to C++: RAII, pImpl, copy and swap, the Rule of Zero, CRTP, type erasure. Design patterns are recipes that apply in any language: Strategy, Observer, Factory, Visitor. Knowing their names lets you design faster and talk to other programmers.

A shared vocabulary

Saying "use the Strategy pattern here" communicates a whole design in four words. That is the value of naming these things. This lesson collects the names, most of which you have already used.

pImpl

"Pointer to implementation". A class's private members are part of its definition, so they sit in the header. Every file that includes the header must be recompiled when they change, and must also include whatever headers those members need.

pImpl moves them out of sight.

C++
// Widget.h: all that users of the class ever see
#pragma once
#include <memory>

class Widget
{
public:
    Widget();
    ~Widget();
    Widget(Widget&&) noexcept;
    Widget& operator=(Widget&&) noexcept;

    void draw() const;

private:
    struct Impl;                     // declared, not defined
    std::unique_ptr<Impl> m_impl;
};
C++
// Widget.cpp
#include "Widget.h"
#include <string>
#include <vector>

struct Widget::Impl
{
    std::string name{};
    std::vector<int> data{};
};

Widget::Widget() : m_impl{ std::make_unique<Impl>() } {}
Widget::~Widget() = default;
Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;

void Widget::draw() const
{
    // uses m_impl->name and m_impl->data
}
flowchart LR
    U["user.cpp<br/>includes Widget.h"] --> H["Widget.h<br/>holds a unique_ptr to Impl"]
    H -.->|"an opaque pointer"| I["Widget::Impl, defined in Widget.cpp:<br/>change it freely, users do not recompile"]
Gain Cost
Changing private members recompiles one file One heap allocation per object
Heavy headers stay out of the public header One pointer indirection per access
The object's size and layout never change: a stable binary interface Copying must be written by hand if wanted
The destructor must be defined in the source file

std::unique_ptr<Impl> can only delete an Impl where Impl is a complete type. If the destructor were left implicit, it would be generated in the header, where Impl is only declared, and the code would not compile. The same applies to the move operations. Declare them in the header and define them as = default in the .cpp file, after Impl.

The classic patterns were described in terms of class hierarchies. Lambdas, std::function and std::variant often express the same intent with far less code.

Strategy: an interchangeable algorithm

C++
class Compressor
{
public:
    using Algorithm = std::function<std::string(std::string_view)>;

    explicit Compressor(Algorithm algorithm) : m_algorithm{ std::move(algorithm) } {}

    std::string run(std::string_view input) const { return m_algorithm(input); }

private:
    Algorithm m_algorithm{};
};

Compressor compressor{ runLengthEncode };

The classic form needs an abstract CompressionStrategy and a class per algorithm. A callable is enough.

Observer: notify whoever is listening

A subject keeps a list of callbacks and invokes them when something happens. The subject does not know who is listening.

C++
template <typename... Args>
class Signal
{
public:
    void connect(std::function<void(Args...)> listener) { m_listeners.push_back(std::move(listener)); }

    void emit(Args... args) const
    {
        for (const auto& listener : m_listeners)
        {
            listener(args...);
        }
    }

private:
    std::vector<std::function<void(Args...)>> m_listeners{};
};

The hazard is lifetime: a listener that captures an object must be disconnected before that object dies. Return a connection object that disconnects in its destructor, or hold listeners through std::weak_ptr.

Factory: create by name

C++
using Creator = std::function<std::unique_ptr<Shape>()>;

const std::unordered_map<std::string, Creator> registry{
    { "circle", [] { return std::make_unique<Circle>(); } },
    { "square", [] { return std::make_unique<Square>(); } },
};

auto shape{ registry.at("circle")() };

It decouples the code that needs an object from the knowledge of which concrete class to build, which is what loading objects from a file requires.

Builder: readable construction

C++
const auto request{ HttpRequest::Builder{}
    .url("https://example.com")
    .method("POST")
    .header("Accept", "json")
    .timeout(5s)
    .build() };

Each setter returns the builder (6.04 this, const Member Functions and Chaining). It replaces a constructor with eight parameters whose order nobody remembers. Designated initializers on a plain options struct are a lighter alternative.

Visitor and State

Pattern Classic form Modern form
Visitor: an operation over a closed set of types A Visitor interface with one visit overload per class, and an accept in each class std::variant with std::visit: 10.04 std::optional, std::variant, std::any and std::tuple
State: behaviour that changes with state A class per state behind a common interface std::variant<Idle, Running, Jumping>, with transitions written as visitors

With a variant, a forgotten state or type is a compile error.

Singleton, and why to avoid it

C++
Logger& logger()
{
    static Logger instance{};
    return instance;
}

A function-local static is initialized once, on first use, safely across threads. That is the correct way to write a singleton. Whether to write one is another matter:

Problem Why
It is a global variable Any code can reach and change it: 3.06 Global Variables, static and Linkage
It hides dependencies A function's signature no longer shows what it uses
It resists testing A test cannot substitute a fake

Prefer passing the dependency in (8.05 Abstract Classes and Interfaces).

The SOLID principles

Five guidelines for object-oriented design, widely quoted by their initials.

Principle In C++ terms
Single responsibility A class or function has one reason to change: 6.09 Designing Good Classes
Open/closed Extend behaviour by adding types or strategies, not by editing working code
Liskov substitution A derived class must honour everything the base class promises: 8.01 Inheritance Basics
Interface segregation Several small interfaces serve better than one large one
Dependency inversion Depend on abstractions (interfaces, concepts) and inject the concrete parts
Patterns are a vocabulary, not a goal

Reach for a pattern when you recognise the problem it solves. Code written to "use patterns" for their own sake acquires layers of indirection that no requirement asked for.
