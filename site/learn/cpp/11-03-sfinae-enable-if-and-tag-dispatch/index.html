SFINAE, enable_if and Tag Dispatch

lesson 11.033 of 7 in milestone 115 min2 practice tasks

SFINAE, "Substitution Failure Is Not An Error": if substituting a type into a template's declaration produces invalid code, that overload is silently removed instead of causing an error. Code before C++20 used it, through std::enable_if, void_t and tag dispatch, to constrain templates. Concepts do the job better now, but you must be able to read it.

The rule

When the compiler considers a function template for a call, it deduces the template arguments and substitutes them into the declaration. If that substitution produces an invalid type or expression, the template is dropped from the set of candidates. The program is not ill-formed.

flowchart TD
    C["the call f(42)"] --> O1["candidate 1:<br/>requires T::value_type"]
    C --> O2["candidate 2:<br/>requires T to be integral"]
    O1 -->|"substitute T = int:<br/>int::value_type is invalid"| D1["silently removed"]
    O2 -->|"substitute T = int: valid"| K["chosen"]

The rule exists so that an overload set may contain templates that are only meaningful for some types. Library authors turned it into a way of deliberately making a template vanish unless a condition holds.

Only the immediate context counts

SFINAE applies to failures in the function's declaration: its return type, its parameter types and its template parameter list. An error inside the function body is a hard error. This is why a constraint has to be expressed in the signature.

std::enable_if

enable_if is a trait built to fail on purpose.

C++
template <bool Condition, typename T = void>
struct enable_if {};                    // no member named type

template <typename T>
struct enable_if<true, T>
{
    using type = T;                     // present only when the condition is true
};

std::enable_if_t<false> names a member that does not exist. That is a substitution failure, so the overload disappears.

C++
#include <iostream>
#include <type_traits>

template <typename T, std::enable_if_t<std::is_integral_v<T>, int> = 0>
T half(T x)
{
    return x / 2;
}

template <typename T, std::enable_if_t<std::is_floating_point_v<T>, int> = 0>
T half(T x)
{
    return x * T{ 0.5 };
}

int main()
{
    std::cout << half(10) << ' ' << half(3.0) << '\n';    // 5 1.5
    // half("x");    error: no matching function, both overloads were removed
    return 0;
}

Read std::enable_if_t<condition, int> = 0 as "an unused template parameter of type int, defaulted to 0, which only exists when the condition is true".

The same device appears in three places:

Position Looks like
A defaulted template parameter template <typename T, std::enable_if_t<C, int> = 0>
The return type std::enable_if_t<C, T> half(T x);
An extra function parameter T half(T x, std::enable_if_t<C>* = nullptr);

The same thing with concepts

C++
auto half(std::integral auto x)       { return x / 2; }
auto half(std::floating_point auto x) { return x * 0.5; }

The requirement is stated, not encoded. That is why 9.04 Concepts (C++20) exist.

Detecting members

Two more tools make it possible to ask whether an expression is valid.

Tool Does
std::declval<T>() Yields a T&& without constructing anything. Usable only where nothing is evaluated, such as inside decltype.
std::void_t<Ts...> Is void if every Ts is a valid type; otherwise substitution fails
C++
template <typename, typename = void>
struct HasSize : std::false_type {};

template <typename T>
struct HasSize<T, std::void_t<decltype(std::declval<T>().size())>> : std::true_type {};

static_assert(HasSize<std::string>::value);
static_assert(!HasSize<int>::value);

How it works, for HasSize<X>:

  1. The primary template gives the second argument its default, void, so the lookup is for HasSize<X, void>.
  2. The partial specialization is tried. If X has .size(), the decltype is a valid type, void_t is void, and the specialization matches HasSize<X, void> and is preferred.
  3. If not, substitution fails, the specialization is discarded, and the primary template's false_type remains.

This is called the detection idiom. A trailing return type achieves a similar effect for functions:

C++
template <typename C>
auto printSize(const C& container) -> decltype(container.size(), void())
{
    std::cout << container.size() << '\n';
}

The comma expression requires container.size() to be valid and then yields void as the return type.

Tag dispatch

A different technique with the same purpose: choose an implementation by overloading on an empty tag type.

C++
template <typename It>
void advanceImpl(It& it, int n, std::random_access_iterator_tag)
{
    it += n;                        // O(1)
}

template <typename It>
void advanceImpl(It& it, int n, std::input_iterator_tag)
{
    while (n-- > 0)
    {
        ++it;                       // O(n)
    }
}

template <typename It>
void myAdvance(It& it, int n)
{
    advanceImpl(it, n, typename std::iterator_traits<It>::iterator_category{});
}

Each iterator type declares its category as a tag type. The tags form an inheritance hierarchy, so a random-access iterator's tag also converts to input_iterator_tag, and overload resolution picks the most specific implementation available. Nothing is removed; ordinary overloading does the selection.

The modern form needs no helper functions:

C++
template <typename It>
void myAdvance(It& it, int n)
{
    if constexpr (std::random_access_iterator<It>)
    {
        it += n;
    }
    else
    {
        while (n-- > 0)
        {
            ++it;
        }
    }
}

How the techniques evolved

Standard Tools for constraining and selecting
C++98 Tag dispatch, specialization of traits
C++11 enable_if, decltype, declval, SFINAE on expressions
C++17 void_t, if constexpr
C++20 Concepts and requires

Write concepts in new code. Read SFINAE in everything written before 2020, including most of the libraries you will use.
