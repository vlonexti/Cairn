Debugging Basics

lesson 1.099 of 10 in milestone 15 min4 practice tasks

A bug is a place where what the program does differs from what you expected. Debugging is finding that place. Do it with a method: read the message, look at the values, narrow it down.

Bugs are normal

Every programmer writes bugs all day. What separates a beginner from an expert is not how few bugs they write. It is how quickly they find them. That is a skill, and it has a method.

flowchart LR
    A["Something is wrong"] --> B["Make it happen<br/>again on demand"]
    B --> C["Narrow down<br/>where"]
    C --> D["Understand<br/>why"]
    D --> E["Fix it"]
    E --> F["Test again"]
    F -->|"still wrong"| C

The step people skip is the fourth. If you change things until it seems to work without knowing why, the bug is usually still there.

First, which kind of problem is it?

What you see Kind Where to look
It will not build Compile or linker error The Problems tab. Start with the first message.
It builds, then stops with an error Crash The message in the console, and the last thing printed before it
It runs and gives the wrong answer Logic error The values of your variables, step by step

Reading a compiler message

main.cpp(8,5): error C2146: missing ';' before identifier 'std'
   │      │ │                └── what the compiler got stuck on
   │      │ └── column
   │      └── line
   └── file

Go to that line. If it looks fine, look at the line above it. A missing ; is only noticed when the compiler reaches the next thing.

Technique 1: print the values

When the answer is wrong, some variable holds a value you did not expect. So look.

C++
#include <iostream>

int main()
{
    int price{ 4 };
    int quantity{ 3 };
    int total{ price + quantity };
    std::cerr << "DEBUG total=" << total << '\n';
    std::cout << "You owe " << total << '\n';
    return 0;
}

std::cerr works like std::cout. It is meant for messages to the programmer, not for the program's real output. The DEBUG label makes these lines easy to spot and delete when you have finished.

Here the debug line shows total=7. You expected 12, so the mistake is on the line that calculates total.

Technique 2: be the computer

Go through the program one line at a time and write down what every variable holds. This is called tracing, and it is the most reliable debugging tool there is.

C++
int a{ 4 };
int b{ 5 };
int c{ 6 };
int average{ a + b + c / 3 };
After the line a b c average
int a{ 4 }; 4
int b{ 5 }; 4 5
int c{ 6 }; 4 5 6
int average{ ... }; 4 5 6 4 + 5 + (6 / 3) = 11

The trace shows the problem. Division happens before addition, so only c is divided. The fix is brackets: (a + b + c) / 3.

Do what the code says, not what you meant

The difficult part of tracing is being honest. Your eyes see what you intended to write. Follow each symbol exactly as it is written.

Technique 3: cut the problem in half

When you have no idea where the mistake is, print a value in the middle of the program.

flowchart TD
    S["Print a value halfway through"] --> Q{"Is it what<br/>you expected?"}
    Q -->|"yes"| L["The mistake is in<br/>the second half"]
    Q -->|"no"| E["The mistake is in<br/>the first half"]
    L --> R["Repeat on that half"]
    E --> R

Each check halves the search. Even in a thousand lines you find the spot in about ten checks.

Technique 4: explain it out loud

Describe your code line by line to someone else, or to an object on your desk. Programmers call this rubber duck debugging. You will often stop mid-sentence because you have just heard yourself say something that is not true.

Writing fewer bugs

Habit Why it helps
Run after every few lines A new problem must be in the lines you just wrote
Read every warning A warning usually means "this is legal, and probably not what you meant"
Give every variable a starting value Removes a whole family of unpredictable behaviour
Keep functions small A small piece is easy to check on its own

Later: a debugger

Professional tools such as Visual Studio include a debugger. It pauses a running program on any line you choose, shows every variable, and lets you move forward one line at a time. It automates the tracing you just did by hand. Once you know how to trace, a debugger takes minutes to learn.
