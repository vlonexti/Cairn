Inheritance and Access

lesson 8.022 of 7 in milestone 85 min3 practice tasks

protected members are visible to derived classes but not to outside code. The kind of inheritance (public, protected, private) caps how inherited members appear. A derived class can add functions, hide base ones, extend them by calling the base version, or change their access.

Three access levels

A member that is Its own class Derived classes Outside code
public Yes Yes Yes
protected Yes Yes No
private Yes No No
C++
class Base
{
public:
    int pub{};

protected:
    int prot{};

private:
    int priv{};
};

class Derived : public Base
{
    void f()
    {
        pub = 1;     // fine
        prot = 2;    // fine
        priv = 3;    // error: private to Base
    }
};

A derived object still contains the private members of its base. It simply cannot name them.

Prefer private data with protected functions

Protected data lets every derived class depend on, and corrupt, the base's internals. The base can then no longer guarantee its own invariants or change its representation. Keep the data private and give derived classes a protected function that does what they need.

The kind of inheritance

The keyword after the colon sets an upper limit on the access of inherited members.

Declared as Base public members become Base protected members become
class D : public B public protected
class D : protected B protected protected
class D : private B private private

Only public inheritance models is-a, because only then can outside code treat a D as a B. Private inheritance means "implemented in terms of", for which a member is nearly always the better tool.

The default is private for a class and public for a struct. Write public explicitly every time.

What a derived class can do with base functions

C++
#include <iostream>
#include <string_view>

class Base
{
public:
    void greet() const { std::cout << "Hello from Base\n"; }
    void hello(int) {}
    void hello(double) {}
};

class Derived : public Base
{
public:
    void wave() const { std::cout << "waving\n"; }      // 1. add

    void greet() const                                  // 2. hide Base::greet
    {
        Base::greet();                                  // 3. extend: call the base version
        std::cout << "and from Derived\n";
    }

    using Base::hello;                                  // 4. keep the base overloads visible
    void hello(std::string_view) {}
};

int main()
{
    Derived d{};
    d.greet();
    d.hello(5);    // Base::hello(int), reachable thanks to the using-declaration
    return 0;
}
Action How
Add Declare a new function
Hide Declare a function with the same name
Extend Hide it, and call Base::function() inside
Change access using Base::name; in the section with the access you want
Remove void name() = delete;

Name hiding

flowchart TD
    C["d.hello(5)"] --> L{"Does Derived declare<br/>any function named hello?"}
    L -- yes --> D["Only Derived's overloads are considered.<br/>The search stops here."]
    L -- no --> B["Search Base"]

Name lookup works outwards one scope at a time and stops at the first scope that contains the name. Overload resolution happens afterwards, among what was found there. So declaring one hello in Derived hides every hello in Base, whatever their parameters.

One overload hides them all

using Base::hello; brings the base overloads into the derived scope so they take part in overload resolution alongside the new one.

Changing access

C++
class Derived : public Base
{
public:
    using Base::protectedFunction;    // now public in Derived

private:
    using Base::greet;                // no longer callable on a Derived
};

Restricting access this way is cosmetic: greet is still callable through a Base&.

This is not polymorphism yet

C++
Derived d{};
Base& b{ d };
b.greet();    // calls Base::greet

The function is chosen from the type of the reference, at compile time. Derived::greet hides the base function; it does not replace it. Making b.greet() call the derived version requires virtual, the subject of 8.03 Virtual Functions and Polymorphism.
