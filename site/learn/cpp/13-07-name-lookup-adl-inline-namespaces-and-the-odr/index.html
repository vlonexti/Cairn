Name Lookup, ADL, Inline Namespaces and the ODR

lesson 13.077 of 10 in milestone 137 min3 practice tasks

How does the compiler decide what a name refers to? Unqualified lookup searches outwards through scopes. ADL also searches the namespaces of the arguments' types, which is why std::cout << x finds std::operator<<. Inline namespaces version an interface. The One Definition Rule keeps definitions consistent across the program.

Lookup comes first

Before a call is resolved, three things happen in a fixed order.

flowchart LR
    A["1. Name lookup<br/>find candidate declarations"] --> B["2. Overload resolution<br/>choose the best match"] --> C["3. Access check<br/>is it public here?"]

A surprising amount of C++ behaviour follows from that order. A function that would be a perfect match is never considered if lookup does not find it, and a private function can win overload resolution and then be rejected.

Unqualified lookup

A name written without :: is searched for from the innermost scope outwards.

Output
 namespace app {
   int x;                         searched third
   namespace ui {
     int x;                       searched second
     void f() {
       int x;                     searched first: found, so the search stops
       use(x);
     }
   }
 }

The search stops at the first scope that contains the name. It does not go on to see whether an outer scope has a better candidate. That is the mechanism behind name hiding in derived classes (8.02 Inheritance and Access), where one function in the derived class hides every base overload of the same name.

A qualified name, such as app::x or ::x, is looked up only in the scope named.

Argument-dependent lookup

For an unqualified function call, there is a second search.

C++
#include <iostream>

namespace geo
{
    struct Point
    {
        int x{};
        int y{};
    };

    void print(const Point& p)
    {
        std::cout << p.x << ',' << p.y << '\n';
    }
}

int main()
{
    const geo::Point p{ 1, 2 };
    print(p);    // found without writing geo::
    return 0;
}
flowchart LR
    C["print(p)"] --> U["ordinary lookup:<br/>the enclosing scopes"]
    C --> A["ADL: the namespaces of<br/>the argument types.<br/>p is a geo::Point, so search geo"]
    U & A --> O["overload resolution over<br/>everything found"]

Argument-dependent lookup (ADL) adds, for each argument, the namespace in which its type is defined. The functions found both ways are combined into one set of candidates.

The motivation is operators. std::cout << text must find std::operator<<(std::ostream&, const std::string&). Nobody wants to write std::operator<<(std::cout, text). ADL makes a type's interface include the free functions in its namespace.

The two-step swap

Generic code that swaps should use a type's own swap if it provides one, and std::swap otherwise.

C++
template <typename T>
void exchange(T& a, T& b)
{
    using std::swap;    // makes std::swap a candidate
    swap(a, b);         // unqualified: ADL adds any swap in T's namespace
}
Written as Finds
std::swap(a, b) Only std::swap. A type's optimized swap is ignored.
swap(a, b) alone Only what ADL finds. Fails for int, which has no namespace.
using std::swap; swap(a, b); Both, and overload resolution prefers the more specific

std::ranges::swap performs this dance for you.

ADL works when you did not ask for it

An unqualified call can select a function from an argument's namespace that you have never heard of. In generic code, qualify calls that you do not intend to be customisable: write std::move, std::forward and std::addressof in full.

Hidden friends

A friend function defined inside a class is not visible to ordinary lookup at all. It can be found only by ADL, when one of the arguments has that class type.

C++
struct Vec2
{
    double x{};
    double y{};

    friend Vec2 operator+(Vec2 a, Vec2 b) { return { a.x + b.x, a.y + b.y }; }
};
Benefit Why
Smaller overload sets The operator is a candidate only when a Vec2 is involved
Fewer accidental conversions It cannot be selected through an implicit conversion of some unrelated type
Faster compilation, clearer errors The compiler has fewer candidates to consider and report

This is the recommended way to write operators, and what the examples in 6.07 Operator Overloading Basics were quietly doing.

Inline namespaces

The members of an inline namespace are treated as members of the enclosing namespace too.

C++
namespace lib
{
    namespace v1
    {
        void parse();
    }

    inline namespace v2
    {
        void parse();
    }
}

lib::parse();        // v2, the current version
lib::v1::parse();    // the old version, still reachable

Libraries use this for versioning. Callers write lib::parse and get whichever version is marked inline; the version name is still part of each symbol, so code built against different versions cannot be linked together by mistake. The standard library's literal suffixes live in inline namespaces, which is why using namespace std::chrono_literals; and using namespace std::literals; both work.

Unnamed namespaces

C++
namespace
{
    int helper() { return 1; }
}

Everything in an unnamed namespace has internal linkage: it is private to its source file (3.06 Global Variables, static and Linkage). Unlike static, it applies to types as well as to functions and variables, which matters for the next section.

The One Definition Rule

The One Definition Rule (ODR) has three parts.

Scope Rule
Within one translation unit An entity is defined at most once
Across the whole program A non-inline function or variable that is used is defined exactly once
Classes, templates, inline functions and inline variables May be defined in several translation units, but every definition must be identical, token for token and in meaning

A translation unit is one source file after all its #includes have been pasted in.

The third rule is the dangerous one.

Output
 a.cpp:   struct Config { int width; int height; };
 b.cpp:   struct Config { int width; int height; int depth; };

 Each file compiles. The program links. No error, no warning.
 Code in a.cpp and b.cpp now disagree about the size and layout of a Config.

A violation of this kind is "ill-formed, no diagnostic required". The linker sees two things called Config and assumes they are the same. The result is memory corruption that appears far from its cause.

How it happens Defence
Two source files each define a helper class with the same name Put file-local types in an unnamed namespace
Two libraries define the same name in the global namespace Give every library its own namespace
A header is included with different macros defined beforehand Avoid macros that alter definitions
Object files built with different settings that change layouts Build everything with the same options
An inline function in a header that behaves differently per file Keep headers free of dependence on file-local context

Modules (13.05 Modules (C++20) and import std (C++23)) remove much of this class of problem: a module's entities are attached to that module, so same-named entities in different modules do not collide.
