Type Traits

lesson 11.022 of 7 in milestone 115 min2 practice tasks

Type traits, in <type_traits>, are compile-time questions about types and transformations of them: "is T an integer?", "T without its const". Each is a template yielding a value or a type. With if constexpr and static_assert, they let code adapt to the types it is given.

Computing with types

A type trait is a class template whose result is a member: a value for a question, or a type for a transformation. They are functions from types to values or to other types, evaluated entirely by the compiler. Using them to shape code is metaprogramming.

Query traits

C++
#include <type_traits>

static_assert(std::is_integral_v<int>);
static_assert(std::is_floating_point_v<float>);
static_assert(std::is_pointer_v<int*>);
static_assert(std::is_same_v<int, signed int>);
Trait Asks
is_integral_v<T>, is_floating_point_v<T>, is_arithmetic_v<T> What kind of number?
is_pointer_v<T>, is_reference_v<T>, is_array_v<T>, is_enum_v<T>, is_class_v<T> What category of type?
is_const_v<T> Is it const-qualified?
is_same_v<T, U> Are they exactly the same type?
is_base_of_v<Base, Derived>, is_convertible_v<From, To> How are two types related?
is_trivially_copyable_v<T> Can it be copied as raw bytes?
is_nothrow_move_constructible_v<T> Is its move constructor noexcept?
is_invocable_v<F, Args...> Can F be called with these arguments?

trait_v<T> is a variable template, short for trait<T>::value.

Transformation traits

Trait Result
remove_const_t<const int> int
remove_reference_t<int&> int
remove_cvref_t<const int&> int
add_pointer_t<int> int*
decay_t<const int[5]> const int*: what passing by value does
make_unsigned_t<int> unsigned int
conditional_t<condition, A, B> A if true, otherwise B
common_type_t<int, double> double
underlying_type_t<Enum> The enum's integer type

trait_t<T> is an alias template, short for typename trait<T>::type.

flowchart LR
    A["const std::string&amp;"] -->|"remove_reference_t"| B["const std::string"] -->|"remove_const_t"| C["std::string"]
    A -->|"remove_cvref_t, in one step"| C

std::remove_cvref_t is the one you will reach for most. Inside a template with a forwarding reference, T may be Widget& or const Widget&, and most questions should be asked about plain Widget.

Using traits

static_assert: state a requirement

C++
template <typename T>
void writeBytes(std::ostream& out, const T& value)
{
    static_assert(std::is_trivially_copyable_v<T>, "writeBytes needs a trivially copyable type");
    out.write(reinterpret_cast<const char*>(&value), sizeof(T));
}

A violated requirement becomes a compile error with your message, in place of undefined behaviour at run time.

if constexpr: one function, a branch per type

C++
#include <iostream>
#include <string>
#include <type_traits>

template <typename T>
std::string toString(const T& value)
{
    if constexpr (std::is_same_v<T, std::string>)
    {
        return value;
    }
    else if constexpr (std::is_arithmetic_v<T>)
    {
        return std::to_string(value);
    }
    else if constexpr (std::is_pointer_v<T>)
    {
        return value ? toString(*value) : "null";
    }
    else
    {
        static_assert(false, "toString: unsupported type");
    }
}

int main()
{
    const int n{ 42 };
    std::cout << toString(n) << ' ' << toString(std::string{ "hi" }) << ' ' << toString(&n) << '\n';
    return 0;
}

The condition of if constexpr is evaluated at compile time, and the branches not taken are discarded: they are not instantiated for that T. That is the whole point. std::to_string(value) would not compile for a std::string, and here it is never asked to.

How traits are built

There is no compiler magic in most of them. A trait is a primary template giving the general answer and specializations giving the exceptions (9.02 Non-Type Parameters and Template Specialization).

C++
template <typename T>
struct IsPointer : std::false_type {};      // in general: no

template <typename T>
struct IsPointer<T*> : std::true_type {};   // for anything of the form T*: yes

template <typename T>
inline constexpr bool isPointer_v{ IsPointer<T>::value };

static_assert(isPointer_v<int*>);
static_assert(!isPointer_v<int>);

std::true_type and std::false_type are tiny classes with a static value of true or false. Inheriting from one is the conventional way to give a trait its result.

A transformation works the same way, with a nested type as the result:

C++
template <typename T>
struct RemoveConst
{
    using type = T;
};

template <typename T>
struct RemoveConst<const T>
{
    using type = T;
};

template <typename T>
using RemoveConst_t = typename RemoveConst<T>::type;

The typename keyword is required before RemoveConst<T>::type because it is a dependent name: until T is known, the compiler cannot tell whether ::type names a type or a value, and assumes a value unless told otherwise.

A few traits cannot be written in the language at all and are supplied by the compiler: is_trivially_copyable, is_class, is_enum and underlying_type among them.

Detecting capabilities

Asking "does T have a size() member?" used to need the machinery of the next lesson. With C++20 it is one requires-expression (9.04 Concepts (C++20)):

C++
template <typename T>
inline constexpr bool hasSize{ requires(const T& t) { t.size(); } };

static_assert(hasSize<std::vector<int>>);
static_assert(!hasSize<int>);

Traits or concepts?

Type traits Concepts
Produce A boolean or a type A named constraint
Constrain a template Through enable_if: awkward Directly
Take part in overload ordering No Yes, by subsumption
Transform types Yes No

Use concepts to constrain. Use traits to compute types, and inside if constexpr. Most standard concepts are defined in terms of traits.
