Project: A Complete Small Game

lesson 6.033 of 3 in milestone 65 min1 practice task

Put the whole course together into one finished game - choosing a scope you can finish, the order to build it in, data-driven waves and levels, the polish that makes it feel complete, and a checklist for release. The example is a top-down arena survival game.

Finishing is the skill

Most first games are never finished: the idea grows faster than the code. The goal of this project is a small game that is complete: a title screen, a game that starts, gets harder and ends, a game-over screen with a score, settings that are remembered, sound, and a build someone else can play.

The example here is an arena survival game: the player moves around a single arena with the keyboard or a gamepad and shoots in the direction they aim; enemies arrive in waves; each wave is harder; the score is the number of waves survived and enemies defeated. It uses almost every lesson, and is small enough to finish in a few weekends. Choose your own idea if you prefer, but keep it to one mechanic, one screen-sized world and one goal.

Waves as data

Hard-coding "wave 3 has five chargers" makes balancing slow. Describe waves as data in a text file that the game reads:

Output
# time  kind     count  interval
wave 1
0       walker   4      1.0
6       walker   4      0.5
wave 2
0       walker   6      0.6
3       charger  2      2.0

Each line is a spawn group: starting at time seconds into the wave, spawn count enemies of kind, one every interval seconds. The game asks "which enemies spawn between the last frame and this one?" and the answer comes straight from the data. You can rebalance without recompiling, and even reload the file while the game runs. The practice builds this spawner.

Difficulty should rise in steps with pauses between them: tension, then relief. After the hand-made waves, generate more by scaling counts and shortening intervals.

Order to build in

  1. The toy: a player that moves and shoots in an empty arena. Make it feel good before anything else: speed, acceleration, the bullet's speed, a sound and a particle burst for every shot.
  2. Something to shoot: one enemy type, collision, health, dying.
  3. A game: waves from the data file, a score, losing.
  4. Screens: title, pause, game over with the score, play again (reset everything, lesson 2.05).
  5. Variety: a second and a third enemy type with different behaviour.
  6. Polish: shake, hit flash, hit stop, death particles, music, a vignette.
  7. Remembering: settings and the high-score table.
  8. Release: icon, release build, clean-machine test, web build, itch.io page.

At every step the game runs, and you can stop and still have something to show.

The release checklist

  • It starts with a title screen and can be quit from the menu.
  • Every input has a keyboard and a gamepad binding, and the controls are shown somewhere.
  • Pause works and stops everything, including timers and spawns.
  • Play again resets everything.
  • Music and effects volumes are separate, saved, and applied at start-up.
  • Screen shake and flashes can be turned off.
  • The window can be resized or made fullscreen, and the game still fits.
  • Settings and scores are in %APPDATA%, saved safely.
  • It runs from a zip on a clean machine.
  • Someone who has never seen it played it without your help.

The last one matters most: watch a friend play without saying anything. Every place they hesitate is something to make clearer.
