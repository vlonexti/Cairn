Frame Time and Smooth Movement

lesson 1.044 of 5 in milestone 15 min1 practice task

Moving "4 pixels a frame" runs twice as fast on a 120 Hz screen. This lesson moves things in units per second using the frame time, adds velocity and acceleration, normalises diagonal movement, and keeps big frame-time spikes from breaking the game.

Pixels per frame is a trap

In lesson 1.02 the square moved 4 pixels a frame. With SetTargetFPS(60) that is 240 pixels a second, but on a slow computer at 30 frames a second it is 120, and with the frame rate unlocked on a fast one it could be 1000. The game's speed depends on the computer.

The fix is to measure time. GetFrameTime() returns the seconds the last frame took (about 0.0167 at 60 FPS), often called dt (delta time). Movement becomes units per second × dt:

C++
const float speed = 240.0f;                 // pixels per second
const float dt = GetFrameTime();
if (IsKeyDown(KEY_RIGHT)) x += speed * dt;

Now the square moves 240 pixels a second at any frame rate: smaller steps when frames are short, bigger when they are long.

Velocity and acceleration

Real movement has velocity (how fast, in pixels per second) and acceleration (how fast the velocity changes):

C++
struct Body { Vector2 pos; Vector2 vel; };

void step(Body& b, Vector2 accel, float dt)
{
    b.vel.x += accel.x * dt;    b.vel.y += accel.y * dt;
    b.pos.x += b.vel.x * dt;    b.pos.y += b.vel.y * dt;
}

This is semi-implicit Euler integration: change the velocity first, then move with the new velocity. It is simple and stable enough for almost every game. A car that speeds up while you hold a key, a ship that drifts, and a falling ball all come from these two lines.

Friction or drag slows things down. A simple version multiplies the velocity by a factor each second: vel *= pow(0.1f, dt) keeps 10 % of the speed per second regardless of the frame rate. Multiplying by a fixed 0.9f every frame would again depend on the frame rate.

Diagonals are too fast

Holding right and down adds speed on both axes: the length of (1, 1) is 1.41, so diagonal movement is 41 % faster. Normalise the input direction to length 1 before scaling it:

C++
Vector2 dir{ 0, 0 };
if (IsKeyDown(KEY_D)) dir.x += 1;
if (IsKeyDown(KEY_A)) dir.x -= 1;
if (IsKeyDown(KEY_S)) dir.y += 1;
if (IsKeyDown(KEY_W)) dir.y -= 1;
const float len = std::sqrt(dir.x * dir.x + dir.y * dir.y);
if (len > 0) { dir.x /= len; dir.y /= len; }
pos.x += dir.x * speed * dt;  pos.y += dir.y * speed * dt;

raylib's raymath.h has Vector2Normalize, Vector2Scale, Vector2Add and many more for exactly this.

Spikes

When you drag the window or the program pauses in the debugger, the next frame time can be a whole second. Objects then jump through walls. Clamp dt to a sensible maximum, such as 1/20 s: the game slows down briefly instead of breaking.

C++
const float dt = std::min(GetFrameTime(), 0.05f);

Milestone 3 goes further with fixed time steps, which make physics behave the same at every frame rate.

Timers

Many game rules are timers: a power-up lasting 5 seconds, a shot every 0.25 s. Keep a float that counts down by dt:

C++
cooldown -= dt;
if (IsKeyDown(KEY_SPACE) && cooldown <= 0) { shoot(); cooldown += 0.25f; }
if (cooldown < 0) cooldown = 0;

Adding the period back (+= 0.25f) instead of setting it keeps the average rate exact even when frames do not divide the period evenly.
