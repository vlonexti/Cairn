Fixed Time Steps

lesson 3.044 of 5 in milestone 35 min1 practice task

Physics that depends on the frame time behaves slightly differently at every frame rate. A fixed time step runs the simulation in equal steps whatever the frame rate - this lesson builds the accumulator loop, guards against the spiral of death, and interpolates between steps for smooth drawing.

Variable steps are not quite the same

Multiplying by dt (lesson 1.04) makes speeds right on average, but the results still differ with the frame rate. A jump simulated in steps of 1/30 s reaches a slightly different height from the same jump in steps of 1/144 s, and collision against thin objects depends on how far things move per step. For a puzzle or platformer where a jump must clear exactly three tiles, or for replays and networked games where every computer must compute the same thing, that is not good enough.

The accumulator

Run the simulation in fixed steps, such as 1/60 s, however long the frame took. Keep the left-over time for the next frame:

C++
const float step = 1.0f / 60.0f;
float accumulator = 0.0f;

while (!WindowShouldClose())
{
    accumulator += GetFrameTime();
    while (accumulator >= step)
    {
        updatePhysics(step);           // always the same dt
        accumulator -= step;
    }
    draw();
}

At 144 FPS most frames run zero steps or one; at 30 FPS each frame runs two. The simulation itself always sees exactly 60 steps a second.

The spiral of death

If one step takes longer to compute than step of real time, each frame adds more time to the accumulator than the steps remove, frames get slower, and the game freezes completely. Limit the number of steps per frame (or clamp the frame time), accepting that the game slows down instead:

C++
accumulator += std::min(GetFrameTime(), 0.25f);
int steps = 0;
while (accumulator >= step && steps < 5) { updatePhysics(step); accumulator -= step; ++steps; }

Smooth drawing with interpolation

With a 60 Hz simulation on a 144 Hz screen, some frames show the same physics state twice and the motion looks slightly jerky. After the loop, accumulator / step is how far (0 to 1) the real time is between the last step and the next one. Keep the previous state and draw between the two:

C++
const float alpha = accumulator / step;
const Vector2 drawPos = { prev.x + (curr.x - prev.x) * alpha, prev.y + (curr.y - prev.y) * alpha };

This draws up to one step behind the newest state, which is not noticeable, and every frame shows a slightly different position.

Input with fixed steps

Read input once per frame, but let the steps use it. One-off presses need care: if a frame runs zero steps, a jump press in that frame must not be lost; if it runs two, it must not jump twice. Store the press in a flag that the first step consumes.

Which approach to use

Approach Use when
Variable dt, clamped Simple games where small differences do not matter
Fixed step Platformers, physics puzzles, anything with replays or networking
Fixed step + interpolation The same, on high-refresh screens
