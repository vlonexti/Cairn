Enemies and State Machines

lesson 4.044 of 5 in milestone 45 min1 practice task

Enemies that patrol, notice the player, chase, attack and give up feel smart, but are a handful of states and the rules for moving between them. This lesson builds enemy behaviour as a finite state machine with enter and exit actions, timers, line of sight, and a little randomness.

States

Describe an enemy's behaviour as states, each with its own simple behaviour:

State Does Leaves when
Patrol Walks between two points Sees the player → Chase
Chase Runs towards the player Close enough → Attack; lost sight for 3 s → Return
Attack Plays the attack, damages on one frame Animation finished → Chase
Return Walks back to the patrol route Arrived → Patrol; sees the player → Chase
Hurt Knocked back, briefly helpless 0.3 s passed → Chase

Each state is easy to write and test on its own, and the diagram is something a designer can read and change.

In code

C++
enum class State { Patrol, Chase, Attack, Return, Hurt };

struct Enemy { State state{ State::Patrol }; float timer{ 0 }; Vector2 pos; /* ... */ };

void enter(Enemy& e, State s)
{
    e.state = s;
    e.timer = 0;                                    // time spent in the new state
    if (s == State::Attack) e.anim.play(attackAnim); // enter actions
}

void update(Enemy& e, const World& w, float dt)
{
    e.timer += dt;
    switch (e.state)
    {
    case State::Patrol:
        walkTowards(e, e.patrolPoints[e.nextPoint], dt);
        if (canSee(e, w.player)) enter(e, State::Chase);
        break;
    case State::Chase:
        walkTowards(e, w.player.pos, dt);
        if (distance(e.pos, w.player.pos) < 24) enter(e, State::Attack);
        else if (canSee(e, w.player)) e.lastSeen = e.timer;
        else if (e.timer - e.lastSeen > 3) enter(e, State::Return);
        break;
    // ...
    }
}

Going through enter for every change is what makes this robust: there is exactly one place where a state starts, so its timer is always reset and its animation always started. Changes from outside (the player hits the enemy) also go through enter(e, State::Hurt).

Seeing the player

"Sees the player" is usually three tests, cheapest first:

  1. Distance: within the sight range?
  2. Angle: within the field of view in front of the enemy? With the facing direction f and the direction to the player d (both normalised), dot(f, d) > cos(halfAngle).
  3. Line of sight: no wall in between? Walk along the line through the tile map, or test the segment against walls (practice 3.01).

Making it feel alive

  • Reaction time: wait 0.3 s after spotting the player before chasing, and show a "!" above the enemy. It is fairer and more readable.
  • Telegraphing: an attack has a wind-up the player can see and react to.
  • Variety: give each enemy slightly different speeds and timers, randomised at spawn, so a group does not move in lockstep.

Beyond state machines

When state machines grow to dozens of states, games move to hierarchical state machines (states inside states), behaviour trees or utility AI (score every possible action and pick the best). For most small games, a state machine like this one is all you need.
