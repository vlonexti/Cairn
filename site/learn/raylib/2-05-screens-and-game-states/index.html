Screens and Game States

lesson 2.055 of 5 in milestone 25 min1 practice task

A finished game has a title screen, the game itself, a pause menu, a game-over screen and transitions between them. This lesson organises a game into screens - first with an enum and a switch, then with screen objects on a stack - and fades smoothly from one to the next.

One loop, many screens

A whole game runs in the same loop, but what the loop does depends on which screen is showing:

C++
enum class Screen { Title, Playing, Paused, GameOver };
Screen screen = Screen::Title;

while (!WindowShouldClose())
{
    switch (screen)
    {
    case Screen::Title:    if (IsKeyPressed(KEY_ENTER)) { resetGame(); screen = Screen::Playing; } break;
    case Screen::Playing:  updateGame(); if (IsKeyPressed(KEY_P)) screen = Screen::Paused; if (lives == 0) screen = Screen::GameOver; break;
    case Screen::Paused:   if (IsKeyPressed(KEY_P)) screen = Screen::Playing; break;
    case Screen::GameOver: if (IsKeyPressed(KEY_ENTER)) screen = Screen::Title; break;
    }
    BeginDrawing();
    ClearBackground(BLACK);
    switch (screen) { /* draw each screen */ }
    EndDrawing();
}

This is a state machine: a set of states, one current state, and transitions triggered by events. For a small game an enum and two switches is perfectly fine.

Screens as objects

As screens grow, each switch case becomes a hundred lines. Give each screen its own class:

C++
class Scene
{
public:
    virtual ~Scene() = default;
    virtual void update(float dt) = 0;
    virtual void draw() const = 0;
    virtual bool coversBelow() const { return true; }   // a pause menu does not
};

A stack of screens

The pause menu shows the game behind it, frozen. A stack of scenes handles that naturally:

  • push: put a scene on top (open the pause menu).
  • pop: remove the top (close it, back to the game).
  • replace: swap the top for another (title to game).

Only the top scene is updated. Drawing starts from the highest scene that covers what is below it and goes up to the top, so the frozen game is drawn first and the menu over it.

C++
void drawStack(const std::vector<std::unique_ptr<Scene>>& stack)
{
    std::size_t first = stack.size() - 1;
    while (first > 0 && !stack[first]->coversBelow()) --first;
    for (std::size_t i = first; i < stack.size(); ++i) stack[i]->draw();
}

Changing the stack while a scene's update is running (the pause scene pops itself) would destroy the object whose function is running. Instead, scenes request changes, and the stack applies them after the update has finished; the practice builds exactly this.

Transitions

Cutting straight from one screen to the next is abrupt. A fade is simple: draw a black rectangle over everything with an alpha that rises from 0 to 255, switch the screen when it is fully black, and let it fall back to 0:

C++
// fade goes 0 -> 1 over 0.3 s, then the screen changes, then 1 -> 0 over 0.3 s
DrawRectangle(0, 0, GetScreenWidth(), GetScreenHeight(), Fade(BLACK, fade));

While a transition runs, ignore input, or a quick player can press Enter twice and skip two screens.

Resetting the game

"Play again" must reset everything: score, lives, level, timers, positions, enemies, particles. Keep all of a play-through's state in one struct and reset it by assigning a fresh one: game = Game{};. Leftover state from the previous round is a very common bug.
