Saving Progress and Settings

lesson 6.011 of 3 in milestone 65 min1 practice task

Players expect a game to remember their settings, their progress and their best scores. This lesson chooses what to save and where, writes simple versioned text formats, saves safely so a crash never destroys a save, and keeps a high-score table.

What to save

Kind Examples When
Settings Volumes, key bindings, window mode, screen shake on or off When changed
Progress Levels unlocked, items collected, the current level and checkpoint At checkpoints, level ends and on quit
Records High scores, best times, statistics When a record changes

Save data, not objects: the level number and the player's health, not the Player object with its texture handles and pointers. Loading then rebuilds the objects from the data.

Where

Never write next to the .exe: on Windows, a game installed in Program Files is not allowed to. Each user has a folder for this, %APPDATA% (for example C:\Users\Sam\AppData\Roaming\YourGame\):

C++
#include <cstdlib>
#include <filesystem>
std::filesystem::path saveFolder()
{
    const char* appData = std::getenv("APPDATA");               // Windows
    std::filesystem::path dir = appData ? appData : ".";
    dir /= "XenonQuest";
    std::filesystem::create_directories(dir);
    return dir;
}

On Linux the convention is ~/.local/share/<game>, on macOS ~/Library/Application Support/<game>.

A simple format

A text file of key=value lines is readable, easy to debug and easy to extend:

Output
version=2
music=70
effects=85
fullscreen=0
key.jump=32

Rules that keep it robust:

  • Defaults first: start from default settings and overwrite only the keys that are present and valid. A missing or damaged line then simply keeps its default, and new settings added in an update work with old files.
  • Validate and clamp every value: a volume of 900 or a key code of -5 must not reach the game.
  • Ignore unknown keys, so an older game can read a newer file.
  • Version the file, so a later version can convert old data (a migration).

Saving safely

If the game crashes or the power fails halfway through writing, the save file is cut off and the player loses everything. Write to a temporary file first, then replace the old one in a single step:

C++
void saveSafely(const std::filesystem::path& file, const std::string& text)
{
    const auto temp = file.string() + ".tmp";
    { std::ofstream out{ temp, std::ios::binary }; out << text; }       // closed (flushed) at the brace
    std::filesystem::rename(temp, file);                               // replaces the old file
}

A rename within one folder is atomic on Windows and Linux: afterwards there is either the complete old file or the complete new one. Keeping the previous save as save.bak adds another layer of protection.

Detecting damage

A checksum stored with the data detects files that were cut off or damaged: compute a number from the content (such as FNV-1a, a few lines of code), write it on the last line, and when loading, recompute it and compare. On a mismatch, fall back to the backup or to defaults, and tell the player rather than crashing.

A checksum is not protection against cheating: anyone can recompute it. For a single-player game that is fine; let players edit their saves if they want to.

High scores

A high-score table is a sorted list with a maximum length:

C++
struct Score { std::string name; int points; };
void addScore(std::vector<Score>& table, Score s)
{
    auto pos = std::find_if(table.begin(), table.end(), [&](const Score& t) { return s.points > t.points; });
    table.insert(pos, s);                     // after equal scores: earlier players keep their place
    if (table.size() > 10) table.pop_back();
}

Ask for the name (lesson 1.05's typed text) only when the score actually makes it into the table.
