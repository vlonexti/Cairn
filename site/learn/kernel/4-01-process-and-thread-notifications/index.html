Process and Thread Notifications

lesson 4.011 of 3 in milestone 45 min1 practice task

Windows lets drivers observe system events through documented callbacks - process creation and exit, thread creation and exit, and image loads. This lesson registers them, explains the context they run in and what information they carry, and keeps the course's log driver strictly an observer.

Documented observation points

Security products, monitoring tools and system utilities need to know what happens on the machine. Instead of guessing, Windows provides notification callbacks, documented functions that call a driver when:

Callback Registered with Called when
Process PsSetCreateProcessNotifyRoutineEx A process is created or exits
Thread PsSetCreateThreadNotifyRoutine A thread is created or exits
Image load PsSetLoadImageNotifyRoutine An executable or DLL is mapped into a process

They are the supported way to observe these events. The log driver in this milestone uses the process and thread callbacks to record events into project m03's ring buffer (with one more field, extra: the parent's id for a process start, the thread's id for thread events), and a user-mode viewer displays them. It observes only: it does not change, block or reach into any process.

The process callback

C++
void XenonProcessNotify(PEPROCESS process, HANDLE processId, PPS_CREATE_NOTIFY_INFO info)
{
    UNREFERENCED_PARAMETER(process);
    LARGE_INTEGER now;
    KeQuerySystemTimePrecise(&now);
    if (info)                                          // non-null: the process is being created
        g_ring.push(now.QuadPart, HandleToULong(processId), KindProcessStart, HandleToULong(info->ParentProcessId));
    else                                               // null: the process is exiting
        g_ring.push(now.QuadPart, HandleToULong(processId), KindProcessExit, 0);
}

// DriverEntry:
status = PsSetCreateProcessNotifyRoutineEx(XenonProcessNotify, FALSE);   // FALSE: register
// Unload:
PsSetCreateProcessNotifyRoutineEx(XenonProcessNotify, TRUE);             // TRUE: remove

PS_CREATE_NOTIFY_INFO describes the new process: its parent's id, the image file name, and the command line (as UNICODE_STRINGs that are only valid during the callback: copy what you keep). The Ex version requires the driver to be linked with /INTEGRITYCHECK, which the project settings provide.

The thread callback

C++
void XenonThreadNotify(HANDLE processId, HANDLE threadId, BOOLEAN create)
{
    g_ring.push(now(), HandleToULong(processId), create ? KindThreadStart : KindThreadExit, HandleToULong(threadId));
}

Where callbacks run

  • Process and thread callbacks run at PASSIVE_LEVEL (thread callbacks sometimes at APC_LEVEL), synchronously in the creating or exiting thread. Every process creation on the machine waits for your callback to return.
  • So callbacks must be fast: record a few numbers into a non-paged ring buffer under a spin lock (or interlocked operations) and return. No file writing, no waiting, no allocation if avoidable.
  • Many callbacks run at once on different processors: the ring buffer's lock (project m03) is essential.

The unload rule, again

A registered callback is a pointer the kernel will keep calling. Unload must remove every callback before anything else is freed; if removal fails (or is forgotten), the next process creation calls into unloaded memory and the machine bug-checks. Practice 1.04 and 3.04's checkers enforce exactly this order: unregister callbacks, then flush, then free.

Process ids and times

Process and thread ids are reused once a process has exited, so the viewer identifies processes by (id, start time) rather than id alone. KeQuerySystemTimePrecise returns a FILETIME-style UTC time (100 ns units since 1601, the Win32 course's lesson 2.03), which the viewer converts for display.
