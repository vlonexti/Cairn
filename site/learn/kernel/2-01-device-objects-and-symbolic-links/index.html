Device Objects and Symbolic Links

lesson 2.011 of 5 in milestone 25 min1 practice task

A driver is reached through a device object. This lesson creates one with IoCreateDevice, gives it a symbolic link so user mode can open it as \.\XenonEcho, secures it so only administrators can, and deletes both in Unload.

Drivers and devices

A driver object represents the loaded code. A device object represents something requests can be sent to. A user-mode program never talks to a driver directly: it opens a device, and the I/O manager routes its requests to the driver that owns that device.

flowchart LR
    C["Client: CreateFileW(\\\\.\\XenonEcho)"] --> L["\\??\\XenonEcho (symbolic link)"] --> D["\\Device\\XenonEcho (device object)"] --> R[Driver's dispatch routines]

Device objects live in the kernel's object namespace under \Device. User mode cannot see that directory directly; it sees \?? (shown to Win32 as \\.\), so the driver creates a symbolic link there pointing at its device. Project m01 built these names.

Creating them in DriverEntry

C++
UNICODE_STRING deviceName = RTL_CONSTANT_STRING(L"\\Device\\XenonEcho");
UNICODE_STRING linkName = RTL_CONSTANT_STRING(L"\\??\\XenonEcho");

extern "C" NTSTATUS DriverEntry(PDRIVER_OBJECT driver, PUNICODE_STRING)
{
    PDEVICE_OBJECT device = nullptr;
    NTSTATUS status = IoCreateDeviceSecure(driver, 0, &deviceName, FILE_DEVICE_UNKNOWN,
                                           FILE_DEVICE_SECURE_OPEN, FALSE,
                                           &SDDL_DEVOBJ_SYS_ALL_ADM_ALL, nullptr, &device);
    if (!NT_SUCCESS(status)) return status;

    status = IoCreateSymbolicLink(&linkName, &deviceName);
    if (!NT_SUCCESS(status)) { IoDeleteDevice(device); return status; }       // undo step 1

    device->Flags |= DO_BUFFERED_IO;                 // lesson 2.04
    device->Flags &= ~DO_DEVICE_INITIALIZING;        // ready for requests

    driver->DriverUnload = XenonUnload;
    // dispatch routines: lesson 2.02
    return STATUS_SUCCESS;
}

void XenonUnload(PDRIVER_OBJECT driver)
{
    IoDeleteSymbolicLink(&linkName);                 // reverse order
    IoDeleteDevice(driver->DeviceObject);
}

Note how practice 1.04's rule shows up: when the symbolic link fails, DriverEntry deletes the device it already created, and Unload deletes the link, then the device.

Who may open it

By default a device object can be opened by anyone. A driver that does something only administrators should be able to trigger must say so:

  • IoCreateDeviceSecure with an SDDL string sets the device's security descriptor: SDDL_DEVOBJ_SYS_ALL_ADM_ALL allows only SYSTEM and Administrators. Even for a teaching driver, this is the right habit.
  • FILE_DEVICE_SECURE_OPEN makes the I/O manager check that security for every open, including opens of names "under" the device (\\.\XenonEcho\anything), which otherwise skip the check.

Lesson 5.03 comes back to device security; an unprotected device is one of the most common driver vulnerabilities.

Exclusive and multiple devices

The Exclusive argument (FALSE above) allows several handles at once. A driver can create several device objects (they form a list starting at driver->DeviceObject), each with its own name, and use the device extension (the second argument, a size) to keep per-device data, reached later as device->DeviceExtension.

Seeing them

In the VM, the Sysinternals tool WinObj shows the object namespace: \Device\XenonEcho and the link \GLOBAL??\XenonEcho (where \?? resolves for most processes). In WinDbg, !devobj \Device\XenonEcho and !drvobj XenonEcho show the objects and their dispatch routines.
