IRPs and Dispatch Routines

lesson 2.022 of 5 in milestone 25 min1 practice task

Every request to a driver arrives as an IRP - an I/O request packet. This lesson explains what an IRP holds, the stack locations, dispatch routines for create, close, read and write, completing a request, and why every IRP must be completed exactly once.

The I/O request packet

When a user-mode program calls CreateFileW, ReadFile, WriteFile, DeviceIoControl or CloseHandle on a device, the I/O manager builds an IRP and passes it to the driver. An IRP carries:

Part What
Major function What kind of request: IRP_MJ_CREATE, IRP_MJ_CLOSE, IRP_MJ_READ, IRP_MJ_WRITE, IRP_MJ_DEVICE_CONTROL, IRP_MJ_CLEANUP, ...
Parameters Depending on the major function: the length to read, the control code, buffer lengths
Buffers The user's data, passed in one of three ways (lesson 2.04)
IoStatus The result to return: Status and Information (usually the number of bytes transferred)

Each driver in a stack of drivers (filters above a device driver) gets its own stack location in the IRP with its own parameters; IoGetCurrentIrpStackLocation(irp) returns the current driver's.

Dispatch routines

The driver object has a table of dispatch routines, one per major function, filled in DriverEntry:

C++
driver->MajorFunction[IRP_MJ_CREATE] = XenonCreateClose;
driver->MajorFunction[IRP_MJ_CLOSE] = XenonCreateClose;
driver->MajorFunction[IRP_MJ_READ] = XenonRead;
driver->MajorFunction[IRP_MJ_WRITE] = XenonWrite;
driver->MajorFunction[IRP_MJ_DEVICE_CONTROL] = XenonDeviceControl;

Unset entries point to a default that fails the request with STATUS_INVALID_DEVICE_REQUEST.

Completing a request

C++
NTSTATUS CompleteIrp(PIRP irp, NTSTATUS status, ULONG_PTR information)
{
    irp->IoStatus.Status = status;
    irp->IoStatus.Information = information;
    IoCompleteRequest(irp, IO_NO_INCREMENT);
    return status;                                  // the dispatch routine returns the same status
}

NTSTATUS XenonCreateClose(PDEVICE_OBJECT, PIRP irp)
{
    return CompleteIrp(irp, STATUS_SUCCESS, 0);    // opening and closing always succeed
}

NTSTATUS XenonWrite(PDEVICE_OBJECT device, PIRP irp)
{
    auto* stack = IoGetCurrentIrpStackLocation(irp);
    const ULONG length = stack->Parameters.Write.Length;
    // with buffered I/O, the data is in irp->AssociatedIrp.SystemBuffer (lesson 2.04)
    auto* ext = static_cast<XenonExtension*>(device->DeviceExtension);
    ext->bytesWritten += length;                   // a counter: this driver only counts
    return CompleteIrp(irp, STATUS_SUCCESS, length);
}

Information is what the user sees as "bytes written" or "bytes read". IoCompleteRequest hands the IRP back to the I/O manager, which copies results to user mode and wakes the waiting thread.

Exactly once

Every IRP a driver receives must be completed exactly once, or passed on to another driver, or marked pending and completed later:

  • Never completed: the user's thread waits forever, and the process cannot exit ("hangs in kill").
  • Completed twice: the IRP is freed and then used again, which crashes the system (Driver Verifier catches it, bug check 0xC4).
  • Touched after completing: the IRP may already be freed; read anything you need before calling IoCompleteRequest.

A driver that cannot finish a request at once (waiting for data, for example) calls IoMarkIrpPending(irp), returns STATUS_PENDING, and completes it later from another context. Pending IRPs must be cancellable (IoSetCancelRoutine, or better, cancel-safe queues IoCsqInitialize), and all of them must be completed before the driver unloads, or the system bug-checks with 0xCE.

Create, cleanup and close

  • IRP_MJ_CREATE: a handle is being opened. The driver can refuse it (return an error).
  • IRP_MJ_CLEANUP: the last handle to a file object was closed; cancel that file object's pending requests here.
  • IRP_MJ_CLOSE: the file object itself is going away (after all references are gone).

The practice simulates a dispatch table and checks the exactly-once rule.
