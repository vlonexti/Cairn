Building a Safe Lab

lesson 1.022 of 5 in milestone 15 min1 practice task

Setting up the virtual machine where every driver in this course runs - Hyper-V or VMware, snapshots, test signing inside the VM only, kernel debugging over the network with KDNET, and a routine that makes crashes cheap.

Two machines

Driver development uses two machines:

Machine Role
Host (your computer) Visual Studio, the WDK, WinDbg. Builds the driver and debugs the target. Never loads test drivers.
Target (a virtual machine) Runs Windows with test signing and a kernel debugger attached. Loads the driver. Crashes are expected.

Hyper-V (built into Windows 10/11 Pro and later) or VMware Workstation both work. Give the VM 2 processors (synchronisation bugs only show up with more than one), 4 GB of memory and a fresh Windows installation of the same version you target.

Snapshots

Take a snapshot (Hyper-V calls it a checkpoint) once the VM is set up: Windows installed, updated, debugging configured. Before each test session, you can go back to it in seconds. A driver that corrupts the system, or a VM that no longer boots, costs nothing.

Test signing, in the VM only

Windows only loads drivers signed by Microsoft (lesson 5.04). For development, Microsoft provides test signing: the WDK signs your driver with a test certificate, and a machine in test-signing mode accepts it.

Inside the VM, from an administrator command prompt:

C++
bcdedit /set testsigning on

and restart. Test signing requires Secure Boot to be off for that VM (in Hyper-V: the VM's Settings > Security > uncheck Enable Secure Boot). The desktop then shows "Test Mode" in a corner as a reminder. Never do this on your own computer: it is a development setting for a machine that exists to be crashed.

Kernel debugging with KDNET

A kernel debugger stops the whole target machine, lets you inspect it, and catches crashes before the blue screen. KDNET runs it over the network:

  1. On the host, find its IP address (ipconfig) and choose a port from 50000 to 50039.
  2. Copy kdnet.exe and VerifiedNICList.xml from the WDK (C:\Program Files (x86)\Windows Kits\10\Debuggers\x64) to the VM.
  3. In the VM, as administrator: kdnet.exe <host-ip> <port>. It enables debugging and prints a key like 1.2.3.4. Restart the VM.
  4. On the host: WinDbg > File > Attach to kernel > Net, enter the port and the key.

When the VM boots, WinDbg connects. Break (Ctrl+Break) freezes the whole VM at once, and g lets it run again. Lesson 1.05 uses this connection.

The routine

  1. Build the driver on the host (lesson 1.03).
  2. Copy the .sys file (and its .inf or .cat, if any) to the VM through a shared folder.
  3. Load it (lesson 1.04), with WinDbg attached and showing DbgPrint output.
  4. If it crashes, WinDbg stops at the bug check: run !analyze -v, read the call stack, fix the code.
  5. Restore the snapshot if the VM is in a bad state.

Why bother

Kernel bugs are expensive in the real world: a crashing driver can take down thousands of machines at once. The lab makes every one of your mistakes cheap and visible, and the debugger makes them understandable. Professionals work exactly this way.
