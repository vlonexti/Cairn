DPCs, Timers and Work Items

lesson 3.044 of 5 in milestone 35 min1 practice task

Deferring work in the kernel - DPCs run soon at DISPATCH_LEVEL, kernel timers fire DPCs once or periodically, and work items move work back to PASSIVE_LEVEL in a system thread. This lesson also covers making sure all of them are finished before Unload.

Why defer

Code at a high IRQL must be quick and may not wait. When it needs to do more (process data, allocate paged memory, write a file), it defers the work to a lower IRQL:

flowchart LR
    I[Interrupt / DIRQL] -->|queue| D[DPC at DISPATCH_LEVEL] -->|queue| W[Work item at PASSIVE_LEVEL]

DPCs

A deferred procedure call runs a function at DISPATCH_LEVEL soon, on some processor. Hardware drivers queue one from their interrupt routine; software drivers mostly meet DPCs through timers.

C++
KDPC dpc;
KeInitializeDpc(&dpc, XenonDpcRoutine, context);    // once
KeInsertQueueDpc(&dpc, nullptr, nullptr);            // run it soon; returns FALSE if already queued

A DPC runs at DISPATCH_LEVEL: the rules of lesson 3.02 apply, so only non-paged data, spin locks, no waiting.

Timers

A kernel timer queues a DPC when it expires, once or periodically:

C++
KTIMER timer;
KeInitializeTimerEx(&timer, NotificationTimer);
LARGE_INTEGER due;
due.QuadPart = -10'000'000LL;                        // NEGATIVE = relative, in 100 ns units: 1 second from now
KeSetTimerEx(&timer, due, 1000 /* period in ms, 0 for once */, &dpc);
// ...
KeCancelTimer(&timer);

Due times are in 100-nanosecond units: negative values are relative to now, positive values are absolute system times (the FILETIME of the Win32 course's lesson 2.03). Getting the sign or the unit wrong is a classic bug: a positive "10 seconds" means a date in January 1601, which has long passed, so the timer fires at once. The practice converts and checks these values.

Work items

To get back to PASSIVE_LEVEL (to allocate paged memory, write a file, call a registry function), queue a work item; a system worker thread runs it:

C++
PIO_WORKITEM item = IoAllocateWorkItem(deviceObject);
IoQueueWorkItem(item, XenonWorkRoutine, DelayedWorkQueue, context);
// in XenonWorkRoutine (PASSIVE_LEVEL): do the work, then IoFreeWorkItem(item)

IoAllocateWorkItem ties the work item to the device object, which keeps the driver loaded until the work item has finished: older APIs without that link let a driver unload while its work routine was still running.

Shutting down cleanly

Unload must guarantee that none of these will run again afterwards, or the kernel will call into unloaded code:

  1. Cancel periodic timers: KeCancelTimer.
  2. Wait for DPCs that may already be queued or running: KeFlushQueuedDpcs().
  3. Wait for outstanding work items: keep a count (or rundown protection, ExWaitForRundownProtectionRelease) and wait until it reaches zero.
  4. Only then free the memory they use.

This order matters: freeing a context before the last DPC has finished is a use-after-free in the kernel.

A periodic job

The log driver of milestone 4 uses all three: a periodic timer's DPC moves events from a non-paged buffer, counts them, and when there are enough, queues a work item that runs at PASSIVE_LEVEL. Project m03 builds the counting and buffering core.
