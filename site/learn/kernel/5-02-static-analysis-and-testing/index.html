Static Analysis and Testing

lesson 5.022 of 4 in milestone 55 min1 practice task

Finding driver bugs before they run - SAL annotations, Code Analysis for drivers, CodeQL with Microsoft's driver queries, the Static Driver Verifier idea, unit-testing driver logic in user mode, and fuzzing IOCTL handlers.

Annotations

SAL (source annotation language) tells the compiler's analysis what a function expects:

C++
_IRQL_requires_max_(DISPATCH_LEVEL)
NTSTATUS XenonPush(_Inout_ Ring* ring, _In_reads_bytes_(length) const void* data, _In_ ULONG length);

_IRQL_requires_(PASSIVE_LEVEL)
_Must_inspect_result_
NTSTATUS XenonLoadSettings(_In_ PUNICODE_STRING registryPath, _Out_ Settings* settings);

With annotations, analysis can report: a function called at a higher IRQL than it allows, a buffer read beyond its declared length, an _Out_ parameter not set on every success path, a result ignored. The WDK's headers are annotated throughout, which is why analysis finds so much in driver code.

Code Analysis and CodeQL

  • Code Analysis for drivers (/analyze with the driver rule sets, enabled by default in WDK projects): checks IRQL rules, annotation contracts, pool tagging, missing NT_SUCCESS checks, and common C mistakes on every build. Treat its warnings as errors.
  • CodeQL with Microsoft's Windows driver query suite: deeper, whole-program queries; required for drivers submitted for Windows certification. Run it from the command line or in CI on every change.
  • Static Driver Verifier (older WDK versions): model-checks the driver against rules for the use of kernel APIs, such as "a spin lock is always released" or "an IRP is completed once on every path". The ideas live on in CodeQL's rules.

Test the logic in user mode

Most of a driver is ordinary logic: parsing requests, validating, ring buffers, state machines. Writing it as plain, kernel-independent C++ with a thin kernel layer around it lets you unit-test it in user mode, quickly and with every tool available, which is exactly what every practice in this course has done. The kernel layer (dispatch routines that call the tested functions) stays small enough to review line by line.

Fuzzing

A fuzzer sends huge numbers of generated inputs to a handler and checks that nothing goes wrong. For an IOCTL handler, "wrong" means: a crash or exception, information larger than the output buffer, information not 0 on failure, an IRP not completed exactly once, or memory touched outside the buffers. Two kinds:

  • Generation: build inputs from the protocol's description with interesting values (0, 1, maximum, one less than the structure size, huge counts) in each field.
  • Mutation: start from valid requests and flip bits, change lengths, splice requests together.

Run the handler under the fuzzer in user mode first (with the address sanitizer, /fsanitize=address, which catches overruns like special pool), then against the real driver in the VM under Driver Verifier. The practice writes a deterministic fuzzer harness.

A test plan for a driver

  1. Unit tests for the logic, in user mode, on every build.
  2. Code Analysis on every build; CodeQL in CI.
  3. Fuzz every IOCTL in user mode with the sanitizer.
  4. In the VM with Verifier: load and unload loops, the real workload, the fuzzer against the device, low-resources simulation.
  5. Multiple processors in the VM, and many threads in the tests.
