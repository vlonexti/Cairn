Buffered, Direct and Neither I/O

lesson 2.044 of 5 in milestone 25 min1 practice task

The three ways user buffers reach a driver - the I/O manager copying through a system buffer, locking the user's pages with an MDL, or handing over raw user addresses - with their costs, their rules, and why METHOD_NEITHER is best avoided.

The problem

A user buffer lives at a user-mode address of one particular process. The driver may run in another thread's context, at a raised IRQL where paging is impossible, or later when that process is gone. So a raw user pointer is not something a driver can simply use. Windows offers three ways to hand data across.

Buffered I/O

The I/O manager allocates a system buffer in kernel memory (non-paged), copies the user's input into it before calling the driver, and copies the output back to the user after the request completes:
Driver sees irp->AssociatedIrp.SystemBuffer
For IOCTLs One buffer of max(input length, output length): input at the start, output written over it
Cost Two copies
Safety Excellent: the driver never touches user memory

Use it for small requests (up to a few kilobytes), which is most IOCTLs. Its one trap: input and output share the buffer, so read all of the input you need before writing output.

Direct I/O

For large transfers, copying is wasteful. With direct I/O, the I/O manager locks the user's pages in memory and describes them with an MDL (memory descriptor list); the driver maps them into kernel space:

C++
PVOID data = MmGetSystemAddressForMdlSafe(irp->MdlAddress, NormalPagePriority | MdlMappingNoExecute);
if (!data) return CompleteIrp(irp, STATUS_INSUFFICIENT_RESOURCES, 0);

For METHOD_IN_DIRECT / OUT_DIRECT IOCTLs, the input buffer is still buffered (SystemBuffer) and the output buffer comes as the MDL. The data is not copied, but the user process can change it while the driver reads it (it is the user's memory), so the driver must not read a value twice and assume it is the same.

Neither I/O

METHOD_NEITHER gives the driver the raw user addresses (Parameters.DeviceIoControl.Type3InputBuffer and irp->UserBuffer) and does nothing else. The driver must then:

  • run in the requesting thread's context (be the top driver, called directly);
  • probe the addresses with ProbeForRead / ProbeForWrite inside __try / __except, because the user can pass any address, including kernel addresses;
  • capture (copy) the data into its own memory before using it, because another user thread can change it at any moment ("double fetch" bugs).

Many serious driver vulnerabilities come from METHOD_NEITHER handled carelessly. Use buffered I/O unless there is a measured reason not to; this course's drivers never use neither I/O.

Read and write

The device object's flags choose the method for IRP_MJ_READ and IRP_MJ_WRITE: DO_BUFFERED_IO or DO_DIRECT_IO (set in DriverEntry, lesson 2.01). IOCTLs choose per control code, in the method bits.

Summary

Method Input Output Use for
METHOD_BUFFERED SystemBuffer SystemBuffer (same) Small requests: almost all IOCTLs
METHOD_IN_DIRECT / OUT_DIRECT SystemBuffer MDL Large data transfers
METHOD_NEITHER raw user pointer raw user pointer Avoid
