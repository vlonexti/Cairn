Secure Driver Design

lesson 5.033 of 4 in milestone 55 min1 practice task

Drivers run with full kernel privilege, so a flaw in one is a flaw in the whole system. This lesson lists the classic driver vulnerabilities - unprotected devices, unchecked buffers, METHOD_NEITHER, arbitrary memory access interfaces, information leaks, missing access checks - and the design rules that prevent them.

Why driver security matters

A program that can talk to a driver talks to the kernel. If the driver can be made to do something it should not, any program that can open the device gains that power. Vulnerable drivers, including legitimately signed ones, are regularly abused to gain kernel privileges, which is why Windows now ships a vulnerable driver blocklist and why Microsoft's driver security guidance is long. Designing a driver securely is part of writing it at all.

The classic flaws

Flaw What goes wrong Prevention
Unprotected device Any user, even a low-privilege one, can open it and send requests IoCreateDeviceSecure with a strict SDDL; FILE_DEVICE_SECURE_OPEN (lesson 2.01)
Missing access bits in IOCTLs A read-only handle can trigger state changes FILE_WRITE_DATA (or FILE_READ_DATA) in each control code (lesson 2.03)
Unchecked lengths and counts Reads and writes beyond buffers, integer overflow Lesson 2.05's checks, every time
METHOD_NEITHER mistakes Unprobed user pointers, kernel addresses accepted, double fetches Use buffered I/O (lesson 2.04)
Generic "read/write memory" or "call function" interfaces Turns the driver into a tool for anyone to control the kernel Never offer them; each IOCTL does one specific, safe thing
Information leaks Uninitialised bytes, kernel addresses or other processes' data returned to user mode Zero buffers, return only what you wrote, never return pointers
Trusting the caller Acting on a process id, handle or path supplied by user mode without checking that caller's rights Check the requestor's rights, open objects with the caller's access mode
Race conditions State checked and then used after another thread changed it Locks around state; copy user input once

Design rules

  1. Minimise the interface. Every IOCTL is attack surface. Offer the fewest, narrowest operations that do the job. The log driver offers exactly one, and it only reads its own ring buffer.
  2. Least privilege. Only the accounts that need the device can open it; only the handles that need write access can change state.
  3. Validate everything, fail closed (lesson 2.05).
  4. Never expose kernel addresses or raw memory. No IOCTL should accept or return a kernel pointer, an arbitrary address, a physical address, or a port number to read and write.
  5. Do not act on other processes on a caller's behalf. A driver that opens, reads or modifies another process because a user-mode request asked it to is a privilege escalation waiting to happen. The drivers in this course never touch other processes at all.
  6. Keep it small and reviewed. Less kernel code is less risk: do the complex parts in a user-mode service and keep the driver minimal.
  7. Test as an attacker would (lesson 5.02), under Driver Verifier (lesson 5.01).

Reviewing a driver

A security review walks every entry point (each dispatch routine, each IOCTL, each callback) and asks: who can reach it? What can they control? What does the code assume about that input? What happens with the worst input at the worst time? The practice turns this checklist into a small audit tool for a driver's description.
