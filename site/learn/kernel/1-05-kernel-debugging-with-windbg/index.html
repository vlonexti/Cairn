Kernel Debugging with WinDbg

lesson 1.055 of 5 in milestone 15 min1 practice task

Using WinDbg on the VM - breaking in, symbols, breakpoints in your driver, inspecting structures, reading a bug check with !analyze, and the handful of commands you will use every day.

Symbols first

A debugger without symbols shows addresses; with them it shows function names, types and source lines. Set the symbol path once (in WinDbg's settings or with a command) to Microsoft's symbol server plus your build folder:

C++
.sympath srv*C:\Symbols*https://msdl.microsoft.com/download/symbols;C:\Projects\XenonHello\x64\Debug
.reload

Your driver's .pdb (built next to the .sys) gives your function names and source lines.

Everyday commands

Command Does
g Go: let the target run
Ctrl+Break Break in: freeze the whole target
lm / lm m Xenon* List loaded modules
bp XenonHello!XenonDispatch Breakpoint on a function
bu XenonHello!DriverEntry Breakpoint that waits for the module to load
bl, bc * List / clear breakpoints
p, t, gu Step over, step into, step out
k / kb Call stack
dv Local variables
dt nt!_UNICODE_STRING addr Show a structure at an address
dx Explore objects with the data model (dx @$curprocess)
!analyze -v Explain a bug check

Reading a crash

When the driver crashes, the target stops with a bug check and WinDbg shows something like:

C++
*** Fatal System Error: 0x000000d1 (0xFFFFA00012345678, 0x0000000000000002, 0x0000000000000000, 0xFFFFF80123456789)

!analyze -v explains it:

  • The bug check code: 0xD1 DRIVER_IRQL_NOT_LESS_OR_EQUAL (touched pageable or invalid memory at a high IRQL, lesson 3.02), 0x50 PAGE_FAULT_IN_NONPAGED_AREA (a bad pointer), 0x3B SYSTEM_SERVICE_EXCEPTION, 0xC4 DRIVER_VERIFIER_DETECTED_VIOLATION (lesson 5.01), 0xCE DRIVER_UNLOADED_WITHOUT_CANCELLING_PENDING_OPERATIONS.
  • The parameters: for 0xD1, the address that was touched, the IRQL, whether it was a read or a write, and the instruction's address.
  • The faulting module and stack: which driver, which function, which line.

Most crashes in your own driver are found in a minute this way: the stack ends in your function, the source line shows the bad pointer.

Crash dumps

Without a live debugger, Windows writes a dump on a bug check (C:\Windows\MEMORY.DMP or minidumps in C:\Windows\Minidump). Open it in WinDbg (File > Open dump file) and run the same !analyze -v. Configure "Kernel memory dump" in the VM's System Properties > Startup and Recovery.

Debugging habits

  • Put a DbgPrintEx at the start and end of every dispatch routine while developing; remove or quieten them later (lesson 4.02).
  • Set bu breakpoints before loading the driver, so DriverEntry can be stepped through.
  • When something "randomly" crashes, turn on Driver Verifier for your driver (lesson 5.01): it turns hidden bugs into immediate, explained crashes.
