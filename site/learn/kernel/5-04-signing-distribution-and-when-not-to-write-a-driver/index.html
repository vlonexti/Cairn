Signing, Distribution and When Not to Write a Driver

lesson 5.044 of 4 in milestone 55 min1 practice task

How real drivers reach users - driver packages, INF files and catalogs, Microsoft's attestation and HLK signing through the Partner Center, Windows Update - and the alternatives that make most drivers unnecessary: user-mode services, ETW, UMDF and existing system features.

Why everything must be signed

Since Windows 10 version 1607, new kernel drivers load only when signed by Microsoft. A developer's own certificate is not enough: the driver is submitted to Microsoft, which signs it. Test signing (lesson 1.02) exists only for development machines. This requirement is a cornerstone of Windows security: it means every driver on a normal machine is traceable to a registered company, and drivers found to be malicious or vulnerable can be revoked and blocked.

The driver package

A driver is shipped as a package:

File Purpose
XenonLog.sys The driver
XenonLog.inf Installation instructions: where files go, services and registry entries, version
XenonLog.cat A catalog: hashes of the package's files, signed

A minimal INF for a software driver:

C++
[Version]
Signature   = "$WINDOWS NT$"
Class       = System
ClassGuid   = {4d36e97d-e325-11ce-bfc1-08002be10318}
Provider    = %ProviderName%
DriverVer   = 11/15/2026,1.0.0.0
CatalogFile = XenonLog.cat
PnpLockdown = 1

[DestinationDirs]
DefaultDestDir = 13          ; the driver store

[DefaultInstall.NTamd64]
CopyFiles = XenonLog.Files

[DefaultInstall.NTamd64.Services]
AddService = XenonLog,, XenonLog.Service

[XenonLog.Service]
ServiceType   = 1            ; kernel driver
StartType     = 3            ; on demand
ErrorControl  = 1
ServiceBinary = %13%\XenonLog.sys
; ... [XenonLog.Files], [Strings]

DriverVer (date and four-part version) decides which of several packages Windows prefers; InfVerif (in the WDK) checks the INF for errors. The practice parses and checks the [Version] section.

Getting Microsoft's signature

Through the Partner Center (Windows Hardware Dev Center), with an EV code-signing certificate identifying your company:

  • Attestation signing: submit the package (signed with your EV certificate); Microsoft checks it and signs it. It loads on client Windows. Fast, no hardware tests.
  • HLK certification: run the Hardware Lab Kit tests and submit the results; required for Windows Server and for distribution through Windows Update with the "certified" status.

Drivers must also pass the driver CodeQL checks (lesson 5.02) and the HVCI (memory integrity) compatibility requirements: no writable-and-executable memory, for example.

Distribution

Signed packages are installed with pnputil /add-driver XenonLog.inf /install, an installer that calls DiInstallDriver, or published through Windows Update for hardware drivers. Updating a driver means a new package with a higher DriverVer.

When not to write a driver

Every driver adds risk to every machine it runs on, needs Microsoft's signature, and is much harder to write and update than user-mode code. Before writing one, check the alternatives:

Need Use instead
Watching process creation, file and registry activity ETW providers (Microsoft-Windows-Kernel-Process and others), Windows Defender's and Sysmon's existing logging
Talking to a USB device WinUSB or a UMDF user-mode driver
Background work with system rights A Windows service
Network filtering Windows Filtering Platform from user mode where possible
Performance data ETW, performance counters

This course's log driver is a teaching project: in practice, a user-mode program subscribing to the kernel's ETW process events gives the same information without any driver at all. Knowing how the kernel works is valuable for debugging, performance work and security; writing kernel code should be the last option, taken with everything this course has covered.
