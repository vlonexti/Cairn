A First Driver

lesson 1.044 of 5 in milestone 15 min1 practice task

The smallest driver - DriverEntry and an Unload routine that frees everything - printing with DbgPrintEx, loading and unloading it as a service with sc.exe, and what happens to each step inside the kernel.

DriverEntry

Every driver has an entry point, DriverEntry, called once when the driver is loaded. It receives the driver object the I/O manager created for it, and the path of its registry key:

C++
#include <ntddk.h>

void XenonUnload(PDRIVER_OBJECT driverObject)
{
    UNREFERENCED_PARAMETER(driverObject);
    DbgPrintEx(DPFLTR_IHVDRIVER_ID, DPFLTR_INFO_LEVEL, "XenonHello: unloaded\n");
}

extern "C" NTSTATUS DriverEntry(PDRIVER_OBJECT driverObject, PUNICODE_STRING registryPath)
{
    UNREFERENCED_PARAMETER(registryPath);
    driverObject->DriverUnload = XenonUnload;
    DbgPrintEx(DPFLTR_IHVDRIVER_ID, DPFLTR_INFO_LEVEL, "XenonHello: loaded\n");
    return STATUS_SUCCESS;
}
  • extern "C" because the kernel looks the function up by its plain name.
  • Setting DriverUnload makes the driver unloadable; without it, it stays until the machine restarts.
  • Returning a failure status from DriverEntry means the driver is not loaded at all, and the kernel will not call Unload, so DriverEntry must clean up everything it did before failing.

The golden rule of Unload

Everything the driver creates (device objects, symbolic links, memory, registered callbacks, timers, threads) must be undone in Unload, in reverse order. A driver that leaves a callback registered and is then unloaded leaves the kernel pointing at code that no longer exists: the next call crashes the machine. Milestone 2 onwards builds drivers whose Unload mirrors DriverEntry step by step.

Seeing DbgPrint output

DbgPrintEx messages go to the kernel debugger (WinDbg on the host, lesson 1.02). By default the INFO level is filtered out; enable it once in the VM's registry or from WinDbg:

C++
ed nt!Kd_IHVDRIVER_Mask 0xF

Without a debugger attached, the Sysinternals tool DebugView (run as administrator, Capture Kernel enabled) shows the same messages inside the VM.

Loading as a service

A software driver is installed as a kernel service. In the VM, as administrator:

C++
sc create XenonHello type= kernel binPath= C:\Drivers\XenonHello.sys
sc start XenonHello          :: DriverEntry runs: "XenonHello: loaded"
sc stop XenonHello           :: Unload runs: "XenonHello: unloaded"
sc delete XenonHello

(The space after each = is required by sc.) The service lives under HKLM\SYSTEM\CurrentControlSet\Services\XenonHello, which is the registryPath passed to DriverEntry: drivers keep their configuration there.

If sc start fails with error 577, the driver's signature was not accepted: check that test signing is on in the VM and the driver was test-signed by the build.

What happens inside

  1. sc start asks the Service Control Manager, which asks the kernel to load the driver.
  2. The I/O manager maps the .sys file into kernel memory, checks its signature, resolves its imports against ntoskrnl.exe, creates a DRIVER_OBJECT, and calls DriverEntry.
  3. sc stop makes the I/O manager call DriverUnload, then unmap the image.

In WinDbg, lm m XenonHello shows the loaded module, and bp XenonHello!DriverEntry (set before sc start) stops in your code so you can step through it.
