Validating Everything From User Mode

lesson 2.055 of 5 in milestone 25 min1 practice task

A driver is a door into the kernel, and everything coming through it must be treated as hostile. This lesson lists the checks every request needs - lengths, alignment, structure versions, counts and offsets, integer overflow - and how to write handlers that cannot be tricked.

The threat model

Any program that can open the device can send any bytes with any lengths, in any order, from many threads at once. A bug that a normal client would never trigger is still reachable by a program written to trigger it. In the kernel, such a bug is not a crash of one program: it can crash the machine or, worse, let a program gain kernel privileges. That is why device security (lesson 2.01) and validation go together.

The checks

For every request, in this order:

  1. Lengths: is the input at least the size of the header? Is the output large enough for the answer? Compare against sizeof the structure, never trust a length field inside the data alone.
  2. Version and size fields: if the structure has a size (lesson 2.03), it must be at least the oldest supported size and at most the buffer length.
  3. Counts and offsets inside the data: "an array of count entries follows" must satisfy header + count × entrySize <= length, computed without overflow.
  4. Enumerations and flags: unknown values are rejected, not ignored; reserved fields must be zero (so they can be used later).
  5. Strings: counted, not null-terminated (lesson 1.03); a length must be even for UTF-16 and within the buffer.

Only after all checks pass does the handler use the data.

Integer overflow

The classic mistake:

C++
// count comes from the user
if (sizeof(Header) + req->count * sizeof(Entry) > inputLength) return STATUS_INVALID_PARAMETER;   // WRONG

With a huge count, the multiplication wraps around to a small number, the check passes, and the loop reads far past the buffer. Check without overflowing:

C++
if (inputLength < sizeof(Header)) return STATUS_BUFFER_TOO_SMALL;
const SIZE_T room = inputLength - sizeof(Header);
if (req->count > room / sizeof(Entry)) return STATUS_INVALID_PARAMETER;    // division cannot overflow

The kernel's ntintsafe.h has RtlULongMult, RtlSizeTAdd and friends that report overflow; use them for any arithmetic on user-supplied values.

Read once

With direct or neither I/O, the user can change the buffer while the driver reads it. A value read twice can differ between the check and the use ("time of check to time of use"). Copy the header into a local variable once, validate the copy, and use only the copy. With buffered I/O this cannot happen, which is another reason to prefer it.

Fail closed

  • Return an error for anything unexpected, without partially doing the work.
  • Set Information to 0 on failure, so no uninitialised bytes are copied back to user mode. When returning data, never return more bytes than were written: copying back uninitialised kernel memory leaks information (zero output buffers first with RtlZeroMemory, or use pool allocations that zero memory, lesson 3.01).
  • Keep each handler small: one IOCTL, one function, with all checks at the top.

Testing like an attacker

Test every IOCTL with: zero lengths, lengths of 1, lengths one short of the structure, huge counts, counts that overflow, wrong versions, unknown flags, and many threads at once. Practice 2.05 and project m02 do exactly that against a request validator; lesson 5.01's Driver Verifier and lesson 5.02's tools check the real driver.
