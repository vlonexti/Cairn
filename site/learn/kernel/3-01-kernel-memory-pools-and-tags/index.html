Kernel Memory: Pools and Tags

lesson 3.011 of 5 in milestone 35 min1 practice task

Drivers allocate from the kernel's pools - paged and non-paged - with ExAllocatePool2, tag every allocation, free everything they allocate, and use tags and PoolMon to find leaks. This lesson also defines operator new and delete for kernel C++.

Two pools

The kernel's general-purpose heap is the pool, in two kinds:

Pool Can be paged out? Use when
Non-paged (POOL_FLAG_NON_PAGED) Never The memory is touched at DISPATCH_LEVEL or above (lesson 3.02), in DPCs, with spin locks held
Paged (POOL_FLAG_PAGED) Yes Only touched at PASSIVE_LEVEL / APC_LEVEL; most configuration and bookkeeping

Non-paged memory is a limited resource (it always occupies physical RAM), so use paged pool when the rules allow. Touching paged memory at a raised IRQL is the classic 0xD1 bug check: the page might not be in memory, and the page fault cannot be handled at that level.

Allocating

C++
constexpr ULONG XENON_TAG = 'nriC';      // shows as "Cirn" in tools (stored little-endian)

auto* entry = static_cast<LogEntry*>(ExAllocatePool2(POOL_FLAG_NON_PAGED, sizeof(LogEntry), XENON_TAG));
if (!entry) return STATUS_INSUFFICIENT_RESOURCES;   // allocations CAN fail: always check
// ... use it ...
ExFreePoolWithTag(entry, XENON_TAG);

ExAllocatePool2 (Windows 10 2004 and later) zeroes the memory by default, which prevents leaking old data to user mode (lesson 2.05). The older ExAllocatePoolWithTag does not zero; older code must call RtlZeroMemory itself.

Pool tags

Every allocation carries a 4-character tag. Written as a multi-character constant, it is stored in memory in reverse, so 'nriC' appears as Cirn in the tools; the practice converts between the two. Tags let you:

  • see how much memory your driver uses, with the Sysinternals-like PoolMon tool (in the WDK) or WinDbg's !poolused 2 Cirn;
  • find a leak: a tag whose count keeps growing;
  • find what owns a corrupted block: !pool <address> shows the tag of the allocation around an address.

Use distinct tags for different kinds of allocations (Cirn for log entries, CirB for buffers) so a leak points straight at its source.

Freeing everything

Pool memory is not freed when the driver unloads. Leaked memory stays allocated until the machine restarts, and Driver Verifier (lesson 5.01) bug-checks with 0xC4 when a driver unloads with allocations still outstanding. Pair every allocation with a free on every path, including error paths, which is what RAII classes are for.

C++ in the kernel

Kernel C++ has no default operator new. Define one that takes the pool and tag, and pair it with delete:

C++
void* __cdecl operator new(size_t size, POOL_FLAGS flags, ULONG tag)
{
    return ExAllocatePool2(flags, size, tag);           // returns nullptr on failure: callers must check
}
void __cdecl operator delete(void* p, size_t) { if (p) ExFreePool(p); }

auto* ctx = new (POOL_FLAG_PAGED, XENON_TAG) Context{};
if (!ctx) return STATUS_INSUFFICIENT_RESOURCES;
delete ctx;

A small UniquePool<T> class (a unique_ptr look-alike that frees with the tag) removes most leaks by construction. No exceptions exist in the kernel, so "out of memory" is always a null pointer to check, never an exception.

Stack space

Kernel threads have small stacks: about 12 KB on x64 (versus 1 MB in user mode). Never put large arrays or structures on the stack in a driver; allocate them from the pool. Deep recursion is out of the question.
