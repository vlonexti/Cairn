IOCTLs and a User-Mode Client

lesson 2.033 of 5 in milestone 25 min1 practice task

Device I/O controls are a driver's private API. This lesson defines control codes with CTL_CODE, shares them in a header between driver and client, handles IRP_MJ_DEVICE_CONTROL, and writes the user-mode client that calls DeviceIoControl.

Control codes

Read and write move bytes; anything else a driver offers ("give me your statistics", "reset the counter", "echo this back") is an I/O control (IOCTL). Each has a 32-bit control code built with the CTL_CODE macro:

C++
#define CTL_CODE(DeviceType, Function, Method, Access) \
    (((DeviceType) << 16) | ((Access) << 14) | ((Function) << 2) | (Method))
Field Bits Meaning
Device type 31-16 FILE_DEVICE_UNKNOWN (0x22) for software drivers; values from 0x8000 are for vendors
Required access 15-14 FILE_ANY_ACCESS (0), FILE_READ_DATA (1), FILE_WRITE_DATA (2), or both (3)
Function 13-2 Your number; 0x800 and up for your own codes
Method 1-0 How buffers are passed: METHOD_BUFFERED (0), METHOD_IN_DIRECT (1), METHOD_OUT_DIRECT (2), METHOD_NEITHER (3)

The access field matters for security: the I/O manager checks that the handle was opened with that access before the request reaches the driver. An IOCTL that changes state should require FILE_WRITE_DATA. The practice packs and unpacks these fields.

A shared header

Driver and client must agree on the codes and on the layout of the data, so they share one header:

C++
// XenonEchoIoctl.h - included by the driver and the client
#pragma once
#define XENON_DEVICE 0x8000

#define IOCTL_XENON_ECHO      CTL_CODE(XENON_DEVICE, 0x800, METHOD_BUFFERED, FILE_ANY_ACCESS)
#define IOCTL_XENON_GET_STATS CTL_CODE(XENON_DEVICE, 0x801, METHOD_BUFFERED, FILE_READ_DATA)
#define IOCTL_XENON_RESET     CTL_CODE(XENON_DEVICE, 0x802, METHOD_BUFFERED, FILE_WRITE_DATA)

struct XenonStats
{
    ULONG size;            // sizeof(XenonStats): lets the structure grow in later versions
    ULONG echoes;
    ULONGLONG bytesWritten;
};

The size field at the start is a common versioning trick: a newer driver can tell an older client's smaller structure apart and fill only what it knows.

The driver side

C++
NTSTATUS XenonDeviceControl(PDEVICE_OBJECT device, PIRP irp)
{
    auto* stack = IoGetCurrentIrpStackLocation(irp);
    auto& p = stack->Parameters.DeviceIoControl;
    auto* ext = static_cast<XenonExtension*>(device->DeviceExtension);
    void* buffer = irp->AssociatedIrp.SystemBuffer;          // METHOD_BUFFERED: one buffer for input and output

    switch (p.IoControlCode)
    {
    case IOCTL_XENON_ECHO:
        if (p.OutputBufferLength < p.InputBufferLength) return CompleteIrp(irp, STATUS_BUFFER_TOO_SMALL, 0);
        InterlockedIncrement(&ext->echoes);
        return CompleteIrp(irp, STATUS_SUCCESS, p.InputBufferLength);   // the data is already in place: echoed

    case IOCTL_XENON_GET_STATS:
    {
        if (p.OutputBufferLength < sizeof(XenonStats)) return CompleteIrp(irp, STATUS_BUFFER_TOO_SMALL, 0);
        auto* s = static_cast<XenonStats*>(buffer);
        s->size = sizeof(XenonStats);
        s->echoes = ext->echoes;
        s->bytesWritten = ext->bytesWritten;
        return CompleteIrp(irp, STATUS_SUCCESS, sizeof(XenonStats));
    }
    case IOCTL_XENON_RESET:
        ext->echoes = 0; ext->bytesWritten = 0;
        return CompleteIrp(irp, STATUS_SUCCESS, 0);
    }
    return CompleteIrp(irp, STATUS_INVALID_DEVICE_REQUEST, 0);
}

Every length is checked before the buffer is used. Lesson 2.05 explains why that check is the most important line in the function.

The client

C++
HANDLE device = CreateFileW(L"\\\\.\\XenonEcho", GENERIC_READ | GENERIC_WRITE, 0, nullptr, OPEN_EXISTING, 0, nullptr);
if (device == INVALID_HANDLE_VALUE) { /* 2: driver not loaded; 5: not an administrator */ }

char message[] = "hello, kernel";
char reply[64] = {};
DWORD returned = 0;
if (DeviceIoControl(device, IOCTL_XENON_ECHO, message, sizeof(message), reply, sizeof(reply), &returned, nullptr))
    printf("echoed %lu bytes: %s\n", returned, reply);

XenonStats stats{};
DeviceIoControl(device, IOCTL_XENON_GET_STATS, nullptr, 0, &stats, sizeof(stats), &returned, nullptr);
CloseHandle(device);

returned is the IRP's Information. When the driver fails a request, DeviceIoControl returns FALSE and GetLastError holds the Win32 translation of the NTSTATUS (practice 1.01: STATUS_BUFFER_TOO_SMALL becomes 122).
