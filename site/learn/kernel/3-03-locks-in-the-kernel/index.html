Locks in the Kernel

lesson 3.033 of 5 in milestone 35 min1 practice task

Protecting shared data in a driver - interlocked operations, spin locks and queued spin locks, fast mutexes, executive resources for many readers, and how IRQL decides which lock you may use. This lesson also covers deadlocks and lock ordering in the kernel.

Why drivers need locks

A driver's dispatch routines can run on several processors at once (several threads calling DeviceIoControl), and a DPC can run at the same time as a dispatch routine. Shared data, such as the echo driver's counters or the log driver's buffer, must be protected, exactly as in user mode (the Win32 course's lesson 5.04), but the choice of lock depends on the IRQL.

Interlocked operations

For a single number, interlocked functions are the cheapest and work at any IRQL on non-paged data:

C++
InterlockedIncrement(&ext->echoes);
InterlockedExchangeAdd64(&ext->bytesWritten, length);
LONG previous = InterlockedCompareExchange(&ext->state, Running, Idle);   // only if it was Idle

Spin locks

A spin lock protects data used at DISPATCH_LEVEL (or from both passive code and DPCs). Acquiring it raises the IRQL to DISPATCH_LEVEL and, if another processor holds it, spins (busy-waits) until it is free:

C++
KSPIN_LOCK lock;                       // in non-paged memory; KeInitializeSpinLock(&lock) once
KIRQL old;
KeAcquireSpinLock(&lock, &old);
// short, non-blocking work on non-paged data
KeReleaseSpinLock(&lock, old);

Because other processors may be spinning, hold spin locks for microseconds: no allocation of paged memory, no waiting, no calling out to unknown code. Queued spin locks (KeAcquireInStackQueuedSpinLock) are fairer and scale better on many processors; prefer them for anything contended.

Fast mutexes

At PASSIVE_LEVEL, a waiting thread can sleep instead of spinning. A fast mutex does that and raises to APC_LEVEL while held:

C++
FAST_MUTEX mutex;                      // ExInitializeFastMutex(&mutex)
ExAcquireFastMutex(&mutex);
// work that may touch paged memory and take a while
ExReleaseFastMutex(&mutex);

Fast mutexes are not recursive: acquiring one twice on the same thread deadlocks it.

Executive resources

When many threads read and few write, an ERESOURCE (ExAcquireResourceSharedLite / ExAcquireResourceExclusiveLite, inside KeEnterCriticalRegion) lets readers share. Push locks (FltAcquirePushLockShared in filter drivers) are a lighter alternative.

Choosing

Data is used at Lock
Any IRQL, single value Interlocked
DISPATCH_LEVEL (DPCs, timers) or mixed Spin lock (queued)
PASSIVE_LEVEL only, short sections Fast mutex
PASSIVE_LEVEL, mostly reads ERESOURCE or push lock

Deadlocks in the kernel

The user-mode rules hold, with harsher consequences: a deadlock freezes the system or bug-checks it. Take locks in a fixed order everywhere; never acquire a spin lock while holding another unless that order is documented and always the same; never wait for something while holding a spin lock. Driver Verifier's deadlock detection records the order in which your driver takes locks and reports any cycle, even one that has not deadlocked yet; the practice builds that detector.
