Designing a Log Driver

lesson 4.033 of 3 in milestone 45 min1 practice task

Putting milestones 2 to 4 together - the XenonLog driver records process and thread events into a ring buffer, a secured device offers one read IOCTL, and a user-mode viewer polls it, resumes where it stopped and shows what was lost. This lesson is the design, the protocol and the order to build it.

The protocol

One IOCTL does the work:

C++
#define IOCTL_LOG_READ CTL_CODE(0x8001, 0x800, METHOD_BUFFERED, FILE_READ_DATA)

struct LogReadRequest { ULONG size; ULONG reserved; ULONGLONG afterSeq; };       // input: 16 bytes
// output: { ULONG count; ULONG missed; ULONGLONG lastSeq; }
//       + count x { ULONGLONG seq; ULONGLONG time; ULONG pid; ULONG kind; ULONG extra; ULONG reserved; }   // 32 bytes

The viewer keeps lastSeq and passes it back as afterSeq each time, so it never sees an event twice and always learns how many it missed. Because the request carries the position, the driver keeps no per-reader state: two viewers can read independently, and a viewer that crashes leaves nothing behind. The input has a size and a reserved field that must be zero (lesson 2.05), so the request can grow later.

Design decisions

  • Fixed memory: the ring buffer is allocated once in DriverEntry (non-paged, for example 4096 events). Callbacks never allocate, so they cannot fail and are fast.
  • Losing events is acceptable, slowing the system is not: when the viewer reads too slowly, old events are overwritten and the viewer reports "N events lost". A design that blocked process creation until the viewer caught up would be unacceptable.
  • Short locks: the callback holds the spin lock only to copy 32 bytes into a slot. Serializing for the IOCTL copies the events out under the lock, then formats outside it.
  • Security: only administrators can open the device (lesson 2.01); the IOCTL requires read access; the driver reports only process and thread ids and times, not command lines or other data from inside processes.

Unload, in order

  1. Unregister the thread callback, then the process callback (no new events).
  2. Delete the symbolic link, then the device (no new requests; open handles keep the device until closed).
  3. Free the ring buffer.

Practice 3.04's checker, extended with the callbacks, describes exactly this order.

The viewer

The user-mode viewer (a console program or the Win32 course's list view) runs a loop: send IOCTL_LOG_READ with the last sequence number, parse the reply, append lines, sleep 200 ms (or wait for a notification event, project m03's stretch goal). It keeps a table of processes seen (id and start time to parent and first-seen time), formats times as local time, and shows "[N events lost]" when missed is not zero. Project m04 writes the viewer's logic.

Order to build in

  1. The driver with only the device and a stub IOCTL that returns an empty reply; the viewer connects and prints "0 events".
  2. The ring buffer with a test IOCTL that pushes fake events; the viewer shows them.
  3. The process callback; then the thread callback.
  4. Driver Verifier on (lesson 5.01) while starting and stopping many programs; fix everything it reports.
  5. The viewer's process table, filters and lost-event display.
