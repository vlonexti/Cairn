IRQL

lesson 3.022 of 5 in milestone 35 min1 practice task

The interrupt request level decides what kernel code may do at each moment. This lesson explains PASSIVE, APC, DISPATCH and device levels, what is forbidden at each, how the documentation states each function's IRQL, and how to raise and lower it correctly.

Levels, not threads

Every processor runs at an IRQL (interrupt request level) at every moment. Code running at a given IRQL can only be interrupted by something at a higher IRQL. The levels that matter to drivers:

IRQL Value Who runs there
PASSIVE_LEVEL 0 Normal threads, DriverEntry, most dispatch routines, work items
APC_LEVEL 1 Asynchronous procedure calls; code holding a fast mutex
DISPATCH_LEVEL 2 DPCs, timers' DPCs, code holding a spin lock; the thread scheduler itself
Device IRQLs (DIRQL) 3+ Hardware interrupt service routines

The two big rules

At DISPATCH_LEVEL and above, the scheduler cannot run on that processor. Therefore:

  1. No waiting. Anything that might block (waiting on an event with a timeout other than zero, acquiring a mutex, KeDelayExecutionThread) is forbidden: there is no one to switch to while waiting.
  2. No page faults. Touching pageable memory (paged pool, pageable code, user buffers) is forbidden: resolving a page fault needs to wait for the disk. This is bug check 0xD1 / 0x0A.

Breaking either rule does not always crash at once: if the page happens to be in memory, nothing goes wrong, until one day it is not. That is why Driver Verifier (lesson 5.01) forces pages out to make these bugs reproducible.

Reading the documentation

Every kernel function's documentation ends with a line such as IRQL: <= DISPATCH_LEVEL or IRQL: PASSIVE_LEVEL. That is the highest IRQL at which it may be called. Some examples:

Function Maximum IRQL
ExAllocatePool2 (non-paged) DISPATCH_LEVEL
ExAllocatePool2 (paged) APC_LEVEL
KeAcquireSpinLock DISPATCH_LEVEL
ExAcquireFastMutex APC_LEVEL
ZwCreateFile, registry functions PASSIVE_LEVEL
IoCompleteRequest DISPATCH_LEVEL
KeSetEvent (Wait = FALSE) DISPATCH_LEVEL

Static analysis (lesson 5.02) checks annotations such as _IRQL_requires_max_(DISPATCH_LEVEL) against your code paths. The practice writes a small checker for a call path.

Raising and lowering

C++
KIRQL old;
KeRaiseIrql(DISPATCH_LEVEL, &old);      // now nothing on this CPU can preempt us
// ... very short work on non-paged data ...
KeLowerIrql(old);                       // always back to exactly where we were

You may only raise with KeRaiseIrql and only lower with KeLowerIrql to the value you saved. Most drivers never call these directly: acquiring a spin lock raises to DISPATCH_LEVEL, and releasing it lowers back (lesson 3.03).

KeGetCurrentIrql() tells you where you are; NT_ASSERT(KeGetCurrentIrql() <= APC_LEVEL) at the top of a function documents and checks its requirement in debug builds. PAGED_CODE() does the same for functions placed in pageable sections.

Where dispatch routines run

Dispatch routines for a top-level software driver run at PASSIVE_LEVEL in the context of the calling thread, so they may wait and allocate paged memory. Completion routines, DPCs and timer callbacks run at DISPATCH_LEVEL. A function called from both kinds of places must obey the stricter rules.
