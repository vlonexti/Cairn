Lists in the Kernel

lesson 3.055 of 5 in milestone 35 min1 practice task

The kernel's own data structures - intrusive doubly linked lists with LIST_ENTRY and CONTAINING_RECORD, singly linked lists, interlocked lists, lookaside lists for fixed-size allocations, and ring buffers for logs.

Intrusive lists

The kernel has no std::list. Its lists are intrusive: the link lives inside the object, as a LIST_ENTRY member:

C++
typedef struct _LIST_ENTRY { struct _LIST_ENTRY* Flink; struct _LIST_ENTRY* Blink; } LIST_ENTRY;

struct LogItem
{
    LIST_ENTRY link;          // the list goes through here
    LARGE_INTEGER time;
    ULONG processId;
};

LIST_ENTRY head;               // the list itself: a LIST_ENTRY that points to itself when empty
InitializeListHead(&head);

InsertTailList(&head, &item->link);
if (!IsListEmpty(&head))
{
    PLIST_ENTRY e = RemoveHeadList(&head);
    LogItem* oldest = CONTAINING_RECORD(e, LogItem, link);   // from the link back to the object
}

The list is circular: the head's Flink is the first element, its Blink the last, and the last element's Flink points back to the head. An empty list is a head that points to itself. CONTAINING_RECORD subtracts the member's offset from the link's address to find the object around it. An object can be in several lists at once with several LIST_ENTRY members.

No allocation happens when inserting or removing: the object already contains its link. That is exactly what the kernel wants: inserting at DISPATCH_LEVEL under a spin lock never fails and never allocates. The practice implements these functions and checks the list's invariants.

Walking and removing

C++
for (PLIST_ENTRY e = head.Flink; e != &head; )
{
    LogItem* item = CONTAINING_RECORD(e, LogItem, link);
    e = e->Flink;                                // advance BEFORE removing
    if (tooOld(item)) { RemoveEntryList(&item->link); ExFreePoolWithTag(item, XENON_TAG); }
}

Lists are not thread-safe: protect them with a lock (lesson 3.03), or use ExInterlockedInsertTailList with a spin lock for simple queues.

Singly linked and interlocked lists

SINGLE_LIST_ENTRY is a one-way list (a stack: PushEntryList, PopEntryList). Interlocked singly linked lists (SLIST_HEADER, InterlockedPushEntrySList) are lock-free stacks that work at any IRQL, useful for passing items between a DPC and a worker.

Lookaside lists

Allocating many objects of the same size from the pool is relatively slow. A lookaside list keeps freed blocks of one size for reuse:

C++
LOOKASIDE_LIST_EX lookaside;
ExInitializeLookasideListEx(&lookaside, nullptr, nullptr, NonPagedPoolNx, 0, sizeof(LogItem), XENON_TAG, 0);
auto* item = static_cast<LogItem*>(ExAllocateFromLookasideListEx(&lookaside));
ExFreeToLookasideListEx(&lookaside, item);
ExDeleteLookasideListEx(&lookaside);           // in Unload, after freeing every item

Ring buffers

A log that must never grow without limit uses a ring buffer: a fixed array where new entries overwrite the oldest when it is full. Two indexes (where to write next, how many are stored) and a lock are all it needs, and it never allocates after start-up. The log driver of milestone 4 stores events this way and counts how many were dropped because nobody read them in time.
