Logging and Tracing from a Driver

lesson 4.022 of 3 in milestone 45 min1 practice task

Getting information out of a driver without slowing the system down - DbgPrintEx levels and filters, rate limiting, WPP software tracing, and TraceLogging with ETW, which lets tools like WPR and WPA record a driver's events alongside the rest of the system.

DbgPrintEx, carefully

DbgPrintEx (lesson 1.04) is the first tool, but it has costs:

  • It formats text in the kernel, which is slow compared with recording a few numbers.
  • Output is filtered by component and level: DbgPrintEx(DPFLTR_IHVDRIVER_ID, DPFLTR_ERROR_LEVEL, ...) is always shown, INFO_LEVEL only when the filter mask allows it.
  • A message in a hot path (a callback called for every thread creation) can flood the debugger and slow the whole VM to a crawl.

Use it for errors and rare events, and rate-limit anything that can repeat: at most a few messages per second, then one summary ("suppressed 1 204 similar messages"). The practice builds a token-bucket limiter.

Levels and keywords

Good driver logging distinguishes:

Level Use
Critical / Error Something failed and the driver cannot do its job
Warning Unexpected but handled (a request rejected by validation)
Information Important state changes (loaded, device created)
Verbose Detailed tracing for debugging, off by default

Keywords are bit flags for areas of the driver (0x1 I/O requests, 0x2 callbacks, 0x4 memory). A trace session enables a level and a keyword mask, and the driver checks both before formatting anything, so disabled events cost almost nothing.

WPP software tracing

WPP (Windows software trace preprocessor) turns DoTraceMessage(FLAG_IO, "length %d", len) calls into compact binary events at build time: only the arguments are recorded, and the format strings live in the .pdb. Tracing is enabled per driver from outside (tracelog, TraceView), and the cost when disabled is a single flag check. Many Microsoft drivers trace this way; the WDK templates set it up.

TraceLogging and ETW

ETW (Event Tracing for Windows) is the system-wide, high-speed tracing infrastructure that Windows itself uses. TraceLogging is the simplest way for a driver to write ETW events, with self-describing fields:

C++
#include <TraceLoggingProvider.h>
TRACELOGGING_DEFINE_PROVIDER(g_provider, "Xenon.Log",
    (0x5c1f0a8e, 0x9b0a, 0x4c1d, 0x8f, 0x3e, 0x1a, 0x2b, 0x3c, 0x4d, 0x5e, 0x6f));   // your own GUID

TraceLoggingRegister(g_provider);                 // DriverEntry
TraceLoggingWrite(g_provider, "ProcessStart",
    TraceLoggingLevel(TRACE_LEVEL_INFORMATION),
    TraceLoggingKeyword(0x2),
    TraceLoggingUInt32(pid, "ProcessId"),
    TraceLoggingUInt32(parentPid, "ParentId"));
TraceLoggingUnregister(g_provider);               // Unload

Record a session with WPR (Windows Performance Recorder) using a profile that enables Xenon.Log, and open the trace in WPA (Windows Performance Analyzer): your events appear on the same timeline as CPU usage, disk I/O and every other system event. That makes ETW far more powerful than a private log.

Which one when

Need Use
Errors you want to see while developing DbgPrintEx at error level
Detailed debugging traces WPP or TraceLogging at verbose level
Events other tools should see, with timing TraceLogging (ETW)
A product feature (the user sees the events) Your own channel: a ring buffer and an IOCTL (lesson 4.03)

The course's log driver uses its own ring buffer because the viewer is part of the "product"; it would also be good practice to emit the same events with TraceLogging.
