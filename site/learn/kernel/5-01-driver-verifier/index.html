Driver Verifier

lesson 5.011 of 4 in milestone 55 min1 practice task

Driver Verifier makes hidden driver bugs crash immediately and explain themselves - special pool for overruns and use-after-free, forced IRQL checking, pool tracking for leaks, I/O verification, deadlock detection and low-resources simulation. This lesson turns it on in the VM and reads what it reports.

Bugs that hide

Many driver bugs do not crash when they happen: an overrun writes into a neighbouring allocation that nobody reads for an hour; a paged buffer touched at DISPATCH_LEVEL happens to be resident; a leak grows slowly. Driver Verifier, built into Windows, watches selected drivers and makes those bugs fail immediately and loudly, with bug check 0xC4 and a parameter that says exactly what went wrong.

Turning it on (in the VM)

C++
verifier /standard /driver XenonLog.sys      :: the standard checks for one driver
verifier /query                               :: what is enabled and current counters
verifier /reset                               :: turn it off (takes effect after restart)

Restart the VM after enabling. From then on, every load of XenonLog.sys runs under Verifier. Only verify your own drivers: verifying system drivers slows the machine and is not your concern. And never leave it on outside the lab.

What the standard checks do

Check Catches
Special pool Each allocation on its own page, right against an inaccessible guard page: an overrun faults at the exact instruction; freed memory is made inaccessible, so use-after-free faults too
Force IRQL checking Pageable memory is made non-resident whenever the IRQL is raised, so touching it at DISPATCH_LEVEL crashes every time, not occasionally
Pool tracking Every allocation is recorded; unloading with allocations outstanding is a bug check listing them
I/O verification IRPs completed twice, completed with bad status, freed while in use, or left pending at unload
Deadlock detection Lock order violations (practice 3.03), even when no deadlock happened
Security checks User-mode addresses used without probing, kernel addresses passed from user mode
Miscellaneous checks Freeing memory that contains active timers, DPCs or locks

Optional: low resources simulation (/faults) makes random allocations fail, which tests every if (!p) return STATUS_INSUFFICIENT_RESOURCES; path that otherwise never runs.

Reading a Verifier bug check

C++
DRIVER_VERIFIER_DETECTED_VIOLATION (c4)
Arg1: 0000000000000062, A driver has forgotten to free its pool allocations prior to unloading.
Arg2: ffffd30a1c2e3f20, name of the driver having the issue.
Arg3: ffffd30a1d4b6010, verifier internal structure with driver information.
Arg4: 0000000000000003, total # of (paged+nonpaged) allocations that weren't freed.

!analyze -v decodes the first argument (the kind of violation), and !verifier 3 XenonLog.sys lists the outstanding allocations with their tags and the stacks that allocated them: the leak points straight at its source. For special-pool crashes, the call stack ends at the instruction that overran.

A testing routine

With Verifier on, exercise the driver hard: start and stop it repeatedly, run the viewer while starting and stopping hundreds of programs, send every IOCTL with bad inputs (practice 5.02's fuzzer), close handles while requests are pending. A driver that survives this under Verifier is in good shape. Project m05 builds a special-pool simulator to see exactly how overruns, use-after-free and leaks are caught.
