The Windows Driver Kit

lesson 1.033 of 5 in milestone 15 min1 practice task

Installing Visual Studio with the Windows Driver Kit, creating a driver project, what is different about building a driver, the kernel's types and calling conventions, and the kernel's string type UNICODE_STRING.

Installing

On the host:

  1. Visual Studio 2022 with the Desktop development with C++ workload, plus the individual components MSVC (latest) Spectre-mitigated libraries for x64.
  2. The Windows SDK and the Windows Driver Kit (WDK) of the same version, from Microsoft's "Download the WDK" page, including the Visual Studio extension.

After installation, Visual Studio has project templates such as Kernel Mode Driver, Empty (KMDF) and Empty WDM Driver.

KMDF and WDM

Model What it is
WDM (Windows Driver Model) The underlying model: you handle IRPs, device objects and power yourself
KMDF (Kernel-Mode Driver Framework) A framework on top of WDM that handles the boilerplate, power management and Plug and Play correctly
UMDF The same framework for drivers that run in user mode

Microsoft recommends KMDF (or UMDF) for new hardware drivers. This course uses small WDM drivers that are not tied to hardware ("software drivers"), because they show plainly how the kernel's I/O model works; everything you learn carries over to KMDF, which wraps the same objects.

What is different about the build

  • The output is a .sys file: a PE image like a DLL, loaded into kernel space.
  • No C runtime: the driver links against ntoskrnl.exe (and a few other kernel modules) instead. #include <ntddk.h> replaces <windows.h>.
  • Warnings are errors, and code analysis runs on every build (lesson 5.02).
  • The build signs the driver with a test certificate automatically (Driver Signing > Test Sign).
  • C++ is allowed, but without exceptions or RTTI, and with new only if you define it yourself on top of the pool allocator (lesson 3.01).

Kernel types

The kernel has its own type names, close to Win32's:

Type Meaning
NTSTATUS The result of almost every kernel function: STATUS_SUCCESS (0), or an error such as STATUS_INVALID_PARAMETER; check with NT_SUCCESS(status)
ULONG, USHORT, UCHAR, ULONG_PTR 32, 16, 8-bit unsigned, pointer-sized unsigned
PVOID, PCHAR Pointers
PDRIVER_OBJECT, PDEVICE_OBJECT, PIRP The kernel's objects (milestone 2)
UNICODE_STRING The kernel's string (below)

NTSTATUS values have a severity in the top two bits: 0 success, 1 informational, 2 warning, 3 error. So every error is negative as a 32-bit signed number, and NT_SUCCESS is just status >= 0.

UNICODE_STRING

The kernel does not use null-terminated strings. It uses a counted UTF-16 string:

C++
typedef struct _UNICODE_STRING {
    USHORT Length;          // bytes in use, NOT characters, NOT including any null
    USHORT MaximumLength;   // bytes in the buffer
    PWSTR  Buffer;          // may not be null-terminated!
} UNICODE_STRING;

UNICODE_STRING name = RTL_CONSTANT_STRING(L"\\Device\\XenonEcho");
UNICODE_STRING copy;
RtlInitUnicodeString(&copy, L"literal");           // only for null-terminated literals
if (RtlEqualUnicodeString(&a, &b, TRUE)) { ... }   // TRUE: ignore case

Three facts cause most bugs:

  1. Lengths are in bytes. A string of 5 characters has Length = 10.
  2. The buffer is not necessarily null-terminated. Passing Buffer to anything that expects a C string reads past the end. Always use Length.
  3. The maximum length is a USHORT, so a string is at most 32 767 characters.

Printing one uses the %wZ format, which reads the counted structure: DbgPrint("name: %wZ\n", &name);. The practice implements the copy, append, compare and prefix functions on this structure.
