User Mode, Kernel Mode and Why Drivers Are Different

lesson 1.011 of 5 in milestone 15 min1 practice task

What the kernel is, why the processor separates user mode from kernel mode, what drivers are for, and why a bug in a driver takes the whole machine down. This lesson also sets the rules for the course - everything happens in a virtual machine.

Two privilege levels

The processor runs code at different privilege levels. Windows uses two:

User mode Kernel mode
Who runs there Applications, services, most of Windows' own programs The kernel, the executive, the HAL and drivers
Memory Its own process's address space only All of memory, every process, the hardware
A crash Ends that one process Stops the whole machine: a bug check (blue screen)
Errors Exceptions, error codes Must be handled perfectly; there is no one to clean up

User-mode code cannot touch the hardware or another process's memory; when it needs something the system provides (reading a file, creating a window), it makes a system call, and the processor switches to kernel mode to run trusted code on its behalf, then switches back.

What lives in the kernel

flowchart TB
    A[Applications] --> S[System calls: ntdll.dll]
    S --> E[Executive: I/O manager, memory manager, object manager, process manager, security]
    E --> K[Kernel: scheduling, interrupts, synchronisation]
    E --> D[Drivers: file systems, networking, devices, filters]
    K --> H[HAL: hardware abstraction]
    D --> H

Drivers are modules that run in kernel mode, loaded by the system, to extend it: a driver for a graphics card or a USB device, a file system, a network filter, an antivirus filter. They follow the same rules as the rest of the kernel and have the same power.

Why drivers are different

Everything in the Win32 API course still applies in spirit, but a kernel driver adds rules that user-mode code never sees:

  • No safety net: dereferencing a bad pointer, leaking memory, or holding a lock too long affects the whole machine, and a crash stops everything with a bug check.
  • No C++ runtime as you know it: no exceptions, no new without care, no standard library containers, no printf. Drivers are written in C or a careful subset of C++.
  • Interrupt levels (IRQLs, lesson 3.02) decide what code may do at any moment: some code may not wait, may not touch pageable memory, may not even call most functions.
  • Everything coming from user mode is hostile until checked: a driver is a door into the kernel, and an unchecked buffer is a security hole for the whole system (lesson 2.05).

Most of the time, the right answer is not to write a driver: user-mode services, ETW, Windows' built-in APIs and user-mode driver frameworks cover far more than people expect (lesson 5.04). This course is about understanding the kernel and building drivers correctly when they are needed.

The rules of this course

  1. Everything runs in a virtual machine (lesson 1.02). Never load a test driver on the computer you work on.
  2. The drivers in this course echo, count and log: they talk to their own user-mode client and observe documented events. They never read or write other processes' memory, never hide anything, and never try to get around any of Windows' protections.
  3. Test drivers are loaded with test signing, Microsoft's documented mechanism for driver development, enabled only inside the virtual machine.

How the practice works

Compiler Explorer runs ordinary programs, not drivers. So the practice checks the logic that goes inside drivers in plain C++: the I/O control codes, the kernel's string type, buffer validation, linked lists, ring buffers, IRQL rules. Each practice declares the few kernel types it needs, exactly as the WDK headers do.
