Lifetimes

lesson 4.044 of 5 in milestone 45 min1 practice task

How the compiler makes sure references never outlive their data - what a lifetime is, lifetime annotations on functions like longest, the elision rules that let you leave most of them out, structs that hold references, lifetimes in impl blocks and methods, 'static, and practical ways out such as returning owned data.

What a lifetime is

Every reference is valid for some region of the program: its lifetime. The borrow checker makes sure no reference is used after the value it points to is gone:

Rust
let r;
{
    let x = 5;
    r = &x;            // error[E0597]: `x` does not live long enough
}
println!("{r}");       // x was dropped at the closing brace above

Usually the compiler works lifetimes out by itself. You need to write them when a function returns a reference and the compiler cannot tell which input it comes from.

Annotating a function

Rust
fn longest(a: &str, b: &str) -> &str {      // error[E0106]: missing lifetime specifier
    if a.len() >= b.len() { a } else { b }
}

The result could borrow from a or from b. A lifetime parameter says how they relate:

Rust
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let outer = String::from("a fairly long string");
    let result;
    {
        let inner = String::from("short");
        result = longest(&outer, &inner);
        println!("{result}");               // fine: both strings are alive here
    }
    // println!("{result}");                // would not compile: result may borrow from inner
}

<'a> declares a lifetime named a; &'a str means "a reference valid for at least 'a". The signature promises: the result lives as long as the shorter of the two inputs. Annotations do not change how long anything lives; they describe the relationship so the compiler can check every caller.

Elision: when you can leave them out

Most functions need no annotations, thanks to three elision rules:

  1. Each reference parameter gets its own lifetime.
  2. If there is exactly one input lifetime, the output gets it: fn first_word(s: &str) -> &str.
  3. In methods, if there is &self or &mut self, the output gets self's lifetime.

So fn trim_end(s: &str) -> &str and fn name(&self) -> &str just work. Annotations are needed only when there are several input references and the output borrows from one of them.

Structs that hold references

A struct holding a reference must say that it cannot outlive the data it borrows:

Rust
struct Highlight<'a> {
    text: &'a str,
    start: usize,
}

impl<'a> Highlight<'a> {
    fn word(&self) -> &'a str {                       // borrows from the original text, not from self
        let rest = &self.text[self.start..];
        rest.split_whitespace().next().unwrap_or("")
    }
}

fn find_highlights<'a>(text: &'a str, needle: &str) -> Vec<Highlight<'a>> {
    text.match_indices(needle).map(|(start, _)| Highlight { text, start }).collect()
}

fn main() {
    let book = String::from("call me Ishmael. some years ago, never mind how long");
    let hits = find_highlights(&book, "m");
    for h in &hits {
        println!("{} at {}", h.word(), h.start);
    }
}

Highlight<'a> cannot outlive book; the compiler checks every use. Such "view" structs are fast (no copying), and lifetimes are what make them safe.

'static

'static means "valid for the whole program". String literals are &'static str, because they are stored in the program itself. You will also see T: 'static bounds on threads (milestone 6): the thread may outlive the current function, so it cannot borrow local variables.

Practical advice

  • Start without annotations; add them only when the compiler asks, and read its suggestion.
  • If lifetimes get complicated, consider returning owned data (String, Vec<T>) instead of references. A small copy is often worth the simpler code.
  • Structs that own their data (String fields) need no lifetimes at all; reach for borrowed fields only when performance matters.
