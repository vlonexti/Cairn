Modules, Crates and Tests

lesson 3.055 of 5 in milestone 35 min1 practice task

Organising code with mod, pub and use, privacy rules for items and struct fields, splitting modules into files, packages, library and binary crates, adding dependencies from crates.io with Cargo.toml, and writing unit tests with #[test], assert macros and cargo test, plus integration tests and documentation tests.

Modules

A module groups related items and controls what is visible outside it. Everything is private by default; pub makes it visible to the parent module and beyond:

Rust
mod geometry {
    pub struct Point {
        pub x: f64,
        pub y: f64,
    }

    pub fn distance(a: &Point, b: &Point) -> f64 {
        (square(a.x - b.x) + square(a.y - b.y)).sqrt()
    }

    fn square(v: f64) -> f64 { v * v }          // private: only usable inside geometry

    pub mod shapes {
        use super::Point;                        // super: the parent module

        pub struct Circle { pub center: Point, pub radius: f64 }

        impl Circle {
            pub fn area(&self) -> f64 { std::f64::consts::PI * self.radius * self.radius }
        }
    }
}

use geometry::shapes::Circle;
use geometry::{distance, Point};

fn main() {
    let a = Point { x: 0.0, y: 0.0 };
    let b = Point { x: 3.0, y: 4.0 };
    println!("{}", distance(&a, &b));
    let c = Circle { center: b, radius: 1.0 };
    println!("{:.3} at ({}, {})", c.area(), c.center.x, c.center.y);
    // geometry::square(2.0);                    // error: function `square` is private
}
  • Paths use ::. crate:: starts at the crate's root, super:: at the parent, self:: at the current module.
  • use brings a path into scope so you can write the short name.
  • A pub struct can still have private fields: then code outside the module cannot build it directly and must use its constructor, which keeps its rules intact.

Files

In a real project each module usually has its own file:

Text
src/
  main.rs          mod geometry;  (tells Cargo to load src/geometry.rs)
  geometry.rs      pub mod shapes;
  geometry/
    shapes.rs

mod geometry; with a semicolon means "the module's code is in geometry.rs (or geometry/mod.rs)".

Packages and crates

  • A crate is a unit of compilation: a binary crate (with main, from src/main.rs) or a library crate (from src/lib.rs).
  • A package is a folder with Cargo.toml; it can contain a library and any number of binaries.

Dependencies come from crates.io:

TOML
[package]
name = "wordcount"
version = "0.1.0"
edition = "2024"

[dependencies]
clap = { version = "4", features = ["derive"] }
serde = { version = "1", features = ["derive"] }

cargo add clap --features derive edits the file for you. Cargo.lock records exact versions; commit it for applications.

Unit tests

Tests live next to the code, in a module that is only compiled for cargo test:

Rust
pub fn add(a: i32, b: i32) -> i32 { a + b }

pub fn divide(a: i32, b: i32) -> i32 {
    if b == 0 { panic!("division by zero"); }
    a / b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn adds_small_numbers() {
        assert_eq!(add(2, 3), 5);
    }

    #[test]
    fn negative_numbers() {
        assert!(add(-2, -3) < 0, "expected a negative sum");
        assert_ne!(add(-1, 1), 1);
    }

    #[test]
    #[should_panic(expected = "division by zero")]
    fn dividing_by_zero_panics() {
        divide(1, 0);
    }

    #[test]
    fn returns_result() -> Result<(), String> {
        let n: i32 = "42".parse().map_err(|e| format!("{e}"))?;
        assert_eq!(n, 42);
        Ok(())
    }
}
Terminal
cargo test                    # build and run every test
cargo test negative           # only tests whose name contains "negative"
cargo test -- --nocapture     # show println! output from passing tests

Because the tests module is a child of the module it tests, it can test private functions too.

Integration tests go in a tests/ folder next to src/ and use the crate only through its public API, like a user would. Documentation tests are code examples inside /// comments, which cargo test compiles and runs, so examples in the documentation never go stale.

The practice tasks in this course use the same idea with a small kit: test("name", || { check_eq(actual, expected); }).
