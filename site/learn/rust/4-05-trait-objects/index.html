Trait Objects

lesson 4.055 of 5 in milestone 45 min1 practice task

Dynamic dispatch with dyn Trait - storing different types in one collection with Box<dyn Trait> and &dyn Trait, how vtables work, static versus dynamic dispatch and when to choose each, dyn-compatibility (object safety) rules, downcasting with Any, and enums as the alternative when the set of types is closed.

Different types in one list

Generics fill in one concrete type at compile time. To keep circles and squares in the same Vec, use trait objects: values of different types behind a pointer, all used through one trait:

Rust
trait Shape {
    fn area(&self) -> f64;
    fn name(&self) -> String;
}

struct Circle { r: f64 }
struct Square { side: f64 }

impl Shape for Circle {
    fn area(&self) -> f64 { std::f64::consts::PI * self.r * self.r }
    fn name(&self) -> String { format!("circle r={}", self.r) }
}

impl Shape for Square {
    fn area(&self) -> f64 { self.side * self.side }
    fn name(&self) -> String { format!("square {}", self.side) }
}

fn total_area(shapes: &[Box<dyn Shape>]) -> f64 {
    shapes.iter().map(|s| s.area()).sum()
}

fn print_one(shape: &dyn Shape) {
    println!("{} -> {:.2}", shape.name(), shape.area());
}

fn main() {
    let shapes: Vec<Box<dyn Shape>> = vec![
        Box::new(Circle { r: 1.0 }),
        Box::new(Square { side: 2.0 }),
        Box::new(Circle { r: 0.5 }),
    ];
    for s in &shapes {
        print_one(s.as_ref());
    }
    println!("total {:.2}", total_area(&shapes));
}

dyn Shape is "some type that implements Shape", whose size is not known at compile time, so it always sits behind a pointer: Box<dyn Shape> (owned), &dyn Shape (borrowed), or Rc<dyn Shape>.

How it works

A trait object is a fat pointer: a pointer to the data plus a pointer to a vtable, a table of that type's method implementations. A call s.area() looks up the method in the vtable at run time: dynamic dispatch.

Generics (impl Trait, T: Trait) Trait objects (dyn Trait)
Dispatch Static: resolved at compile time, can be inlined Dynamic: a vtable lookup per call
Mixed types in one collection No Yes
Code size One copy per type One copy
Typical use Algorithms, performance-sensitive code Plugins, heterogeneous lists, callbacks

The vtable call costs a few nanoseconds; choose by design, not by fear of speed.

Plugins and strategies

Trait objects suit "pick behaviour at run time":

Rust
trait Discount {
    fn apply(&self, cents: u64) -> u64;
    fn label(&self) -> String;
}

struct PercentOff(u64);
struct FlatOff { cents: u64, minimum: u64 }

impl Discount for PercentOff {
    fn apply(&self, cents: u64) -> u64 { cents - cents * self.0 / 100 }
    fn label(&self) -> String { format!("{}% off", self.0) }
}

impl Discount for FlatOff {
    fn apply(&self, cents: u64) -> u64 { if cents >= self.minimum { cents.saturating_sub(self.cents) } else { cents } }
    fn label(&self) -> String { format!("{} off over {}", self.cents, self.minimum) }
}

fn best(cents: u64, offers: &[Box<dyn Discount>]) -> (String, u64) {
    offers.iter()
        .map(|d| (d.label(), d.apply(cents)))
        .min_by_key(|(_, price)| *price)
        .unwrap_or(("none".to_string(), cents))
}

fn main() {
    let offers: Vec<Box<dyn Discount>> = vec![Box::new(PercentOff(10)), Box::new(FlatOff { cents: 800, minimum: 5000 })];
    println!("{:?} {:?}", best(4000, &offers), best(9000, &offers));
}

Dyn compatibility

Not every trait can be used as dyn Trait. A trait is dyn-compatible (formerly "object safe") when the compiler can build a vtable for it, which rules out, among other things:

  • methods that return Self (the size of Self is unknown behind the pointer);
  • generic methods (fn convert<T>(&self)): there would be one per T, too many for a table.

Clone returns Self, so dyn Clone is not allowed. Methods that do not fit can be excluded with where Self: Sized.

Closed sets: use an enum

If you know every variant up front (the shapes your program supports), an enum with a match (lesson 2.05) is often simpler and faster than trait objects, and the compiler checks you handle every case. Use trait objects when the set is open: other modules, crates or plugins may add types later.
