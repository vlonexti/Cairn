Writing Parsers

lesson 8.055 of 5 in milestone 85 min2 practice tasks

Turning text into data structures by hand - a tokenizer over chars with Peekable, tokens as an enum with positions, a recursive-descent parser that follows a small grammar, operator precedence, good error messages with the column of the problem, and a look at parser libraries such as nom.

Why write a parser?

Configuration files, commands, small languages, file formats: turning text into structured data is everywhere. split and parse handle simple cases. For anything with nesting or precedence (2 + 3 * (4 - 1)), the clean way is two steps:

  1. A tokenizer (lexer) turns characters into tokens: numbers, names, symbols.
  2. A parser turns tokens into a tree, following a grammar.

Tokens

Rust
#[derive(Debug, Clone, PartialEq)]
enum Tok {
    Num(f64),
    Ident(String),
    Op(char),
    LParen,
    RParen,
}

fn tokenize(src: &str) -> Result<Vec<(usize, Tok)>, String> {
    let mut out = Vec::new();
    let mut chars = src.char_indices().peekable();
    while let Some(&(pos, c)) = chars.peek() {
        if c.is_whitespace() {
            chars.next();
        } else if c.is_ascii_digit() || c == '.' {
            let mut text = String::new();
            while let Some(&(_, d)) = chars.peek() {
                if d.is_ascii_digit() || d == '.' { text.push(d); chars.next(); } else { break; }
            }
            let n = text.parse().map_err(|_| format!("bad number {text:?} at {pos}"))?;
            out.push((pos, Tok::Num(n)));
        } else if c.is_alphabetic() {
            let mut name = String::new();
            while let Some(&(_, d)) = chars.peek() {
                if d.is_alphanumeric() || d == '_' { name.push(d); chars.next(); } else { break; }
            }
            out.push((pos, Tok::Ident(name)));
        } else {
            chars.next();
            out.push((pos, match c {
                '+' | '-' | '*' | '/' | '^' => Tok::Op(c),
                '(' => Tok::LParen,
                ')' => Tok::RParen,
                _ => return Err(format!("unexpected {c:?} at {pos}")),
            }));
        }
    }
    Ok(out)
}

fn main() {
    println!("{:?}", tokenize("2 * (x + 1.5)").unwrap());
    println!("{:?}", tokenize("3 $ 4"));
}

peekable() lets the loop look at the next character without taking it, which is how a number knows where it ends. Keeping each token's position pays off later, in error messages.

A grammar

A grammar describes the shapes the parser accepts. For arithmetic with the usual precedence:

Text
expr   = term   (("+" | "-") term)*
term   = factor (("*" | "/") factor)*
factor = "-" factor | atom
atom   = number | name | "(" expr ")"

Each rule becomes one function, and a rule that uses another calls its function: that is recursive descent. Precedence comes for free from the nesting: term binds tighter than expr, so * happens before +.

The parser

Rust
#[derive(Debug, Clone, PartialEq)]
enum Tok { Num(f64), Op(char), LParen, RParen }

#[derive(Debug)]
enum Expr {
    Num(f64),
    Neg(Box<Expr>),
    Bin(char, Box<Expr>, Box<Expr>),
}

struct Parser {
    toks: Vec<Tok>,
    pos: usize,
}

impl Parser {
    fn peek(&self) -> Option<&Tok> {
        self.toks.get(self.pos)
    }

    fn next(&mut self) -> Option<Tok> {
        let t = self.toks.get(self.pos).cloned();
        self.pos += 1;
        t
    }

    fn expr(&mut self) -> Result<Expr, String> {
        let mut left = self.term()?;
        while let Some(Tok::Op(op @ ('+' | '-'))) = self.peek().cloned() {
            self.next();
            left = Expr::Bin(op, Box::new(left), Box::new(self.term()?));
        }
        Ok(left)
    }

    fn term(&mut self) -> Result<Expr, String> {
        let mut left = self.factor()?;
        while let Some(Tok::Op(op @ ('*' | '/'))) = self.peek().cloned() {
            self.next();
            left = Expr::Bin(op, Box::new(left), Box::new(self.factor()?));
        }
        Ok(left)
    }

    fn factor(&mut self) -> Result<Expr, String> {
        match self.next() {
            Some(Tok::Op('-')) => Ok(Expr::Neg(Box::new(self.factor()?))),
            Some(Tok::Num(n)) => Ok(Expr::Num(n)),
            Some(Tok::LParen) => {
                let e = self.expr()?;
                match self.next() {
                    Some(Tok::RParen) => Ok(e),
                    other => Err(format!("expected ')' but found {other:?}")),
                }
            }
            other => Err(format!("expected a number or '(' but found {other:?}")),
        }
    }
}

fn eval(e: &Expr) -> f64 {
    match e {
        Expr::Num(n) => *n,
        Expr::Neg(x) => -eval(x),
        Expr::Bin(op, a, b) => {
            let (a, b) = (eval(a), eval(b));
            match op { '+' => a + b, '-' => a - b, '*' => a * b, _ => a / b }
        }
    }
}

fn main() {
    use Tok::*;
    // 2 + 3 * (4 - 1)
    let toks = vec![Num(2.0), Op('+'), Num(3.0), Op('*'), LParen, Num(4.0), Op('-'), Num(1.0), RParen];
    let mut p = Parser { toks, pos: 0 };
    let tree = p.expr().unwrap();
    println!("{tree:?}");
    println!("= {}", eval(&tree));

    let mut bad = Parser { toks: vec![Num(1.0), Op('*')], pos: 0 };
    println!("{:?}", bad.expr());
}

After parsing, check that every token was used (p.pos == p.toks.len()); otherwise 1 2 would quietly parse as 1.

The loop in expr builds (1 - 2) - 3 for 1 - 2 - 3, so operators of equal precedence group from the left, as they should.

Good error messages

The difference between a toy parser and a useful one is its errors. With positions on tokens, an error can point at the problem:

Text
2 * (3 + )
         ^ expected a number or '(' at column 10

Return a struct ParseError { pos: usize, message: String } (lesson 8.01), and print the source line with a ^ under the column.

Parser libraries

For larger formats, libraries help:

  • nom builds parsers from small functions ("parser combinators"): tuple((digit1, char(':'), digit1)).
  • pest and lalrpop generate a parser from a grammar file like the one above.
  • serde with serde_json, toml and friends already parses the common data formats into your structs.

Hand-written recursive descent remains common in real compilers (including rustc), because it is simple to follow and gives the best error messages.
