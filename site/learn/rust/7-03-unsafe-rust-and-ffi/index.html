Unsafe Rust and FFI

lesson 7.033 of 5 in milestone 75 min2 practice tasks

What the compiler cannot check - the five things unsafe allows, raw pointers, unsafe functions and their safety contracts, wrapping unsafe code in a safe API, calling C functions through extern "C", making Rust callable from C, and the tools that catch mistakes.

What unsafe means

The borrow checker proves your references are always valid. Some correct programs cannot be proved that way: talking to C libraries, writing a data structure with raw memory, using hardware. For those, an unsafe block lets you do five extra things:

  1. dereference a raw pointer;
  2. call an unsafe function (including C functions);
  3. access or change a mutable static;
  4. implement an unsafe trait (such as Send or Sync by hand);
  5. access the fields of a union.

Everything else (the borrow checker, type checks, bounds checks) still applies inside unsafe. The keyword does not turn checking off; it means "I promise these five operations are correct here".

Raw pointers

*const T and *mut T are pointers with no lifetime and no guarantee: they may be null, dangling or unaligned. Making one is safe; reading through it is not.

Rust
fn main() {
    let mut value = 10;
    let p = &mut value as *mut i32;     // safe: just an address
    unsafe {
        *p += 5;                        // unsafe: we promise p is valid and unaliased right now
        println!("{}", *p);
    }

    let numbers = [10, 20, 30];
    let first = numbers.as_ptr();
    let third = unsafe { *first.add(2) };    // pointer arithmetic, like C
    println!("{third}");
}

Unsafe functions and safety contracts

A function is marked unsafe fn when callers must uphold a condition the compiler cannot check. Its documentation states that condition in a Safety section:

Rust
/// Returns the element at `index` without checking bounds.
///
/// # Safety
/// `index` must be less than `slice.len()`.
unsafe fn get_fast(slice: &[i32], index: usize) -> i32 {
    unsafe { *slice.as_ptr().add(index) }
}

fn main() {
    let data = [4, 8, 15];
    // SAFETY: 1 < data.len()
    let x = unsafe { get_fast(&data, 1) };
    println!("{x}");
}

A // SAFETY: comment at each unsafe block explains why the promise holds there. Reviewers read those first.

Safe abstractions

The goal is to keep unsafe small and hidden behind a safe function that cannot be misused. split_at_mut in the standard library is the classic case: two mutable slices of one array cannot be expressed with references alone, but the function checks its input so callers never can do anything wrong:

Rust
fn split_halves(v: &mut [i32]) -> (&mut [i32], &mut [i32]) {
    let mid = v.len() / 2;
    let len = v.len();
    let p = v.as_mut_ptr();
    // SAFETY: the two ranges [0, mid) and [mid, len) do not overlap and lie inside v.
    unsafe { (std::slice::from_raw_parts_mut(p, mid), std::slice::from_raw_parts_mut(p.add(mid), len - mid)) }
}

fn main() {
    let mut data = [1, 2, 3, 4, 5];
    let (left, right) = split_halves(&mut data);
    left[0] = 100;
    right[0] = 300;
    println!("{data:?}");
}

(In real code, use the standard v.split_at_mut(mid), which is exactly this.)

Calling C: extern "C"

An extern "C" block declares functions that exist in a C library, using C's calling convention. Calling them is unsafe because Rust cannot check what the C code does:

Rust
use std::ffi::CStr;

unsafe extern "C" {
    fn abs(x: i32) -> i32;
    fn strlen(s: *const std::ffi::c_char) -> usize;
}

fn main() {
    let text = c"hello from C";                 // a C string literal: zero-terminated
    unsafe {
        println!("{} {}", abs(-42), strlen(text.as_ptr()));
    }
    let back: &CStr = text;
    println!("{}", back.to_str().unwrap());
}

C strings end with a zero byte, Rust strings do not: CString (owned) and CStr (borrowed) convert between them. Real projects generate these declarations with bindgen and link the library through build.rs.

Rust called from C

The other direction marks a Rust function so C can call it by name:

Rust
#[unsafe(no_mangle)]
pub extern "C" fn add_scores(a: i32, b: i32) -> i32 {
    a + b
}

Built as a cdylib crate, this becomes a .dll or .so that C, C++, C# and Python can load (the DLLs course shows the C++ side).

Catching mistakes

Undefined behaviour in Rust is as dangerous as in C. Run unsafe code under Miri (cargo +nightly miri test), an interpreter that detects invalid pointer use, data races and uninitialised reads, and keep unsafe blocks as small as possible.
