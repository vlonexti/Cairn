Type-State and PhantomData

lesson 7.055 of 5 in milestone 75 min2 practice tasks

Letting the compiler enforce the order of operations - states as types, consuming self to move between them, PhantomData for type parameters that hold no data, typed IDs and units, sealed traits, and when the pattern is worth it.

Mistakes the compiler can catch

Many APIs have rules about order: a connection must be opened before sending, a builder needs a URL before build, a file must not be written after closing. Usually such rules are checked at run time with a flag and an error. In Rust, they can often be checked at compile time by making each state a different type.

States as types

Rust
struct Draft;
struct Reviewed;
struct Published;

struct Post<State> {
    text: String,
    _state: State,
}

impl Post<Draft> {
    fn new(text: &str) -> Post<Draft> {
        Post { text: text.to_string(), _state: Draft }
    }
    fn edit(&mut self, more: &str) {
        self.text.push_str(more);
    }
    fn review(self) -> Post<Reviewed> {              // consumes the draft
        Post { text: self.text, _state: Reviewed }
    }
}

impl Post<Reviewed> {
    fn publish(self) -> Post<Published> {
        Post { text: self.text, _state: Published }
    }
}

impl Post<Published> {
    fn content(&self) -> &str {
        &self.text
    }
}

fn main() {
    let mut post = Post::new("Hello");
    post.edit(", world");
    let live = post.review().publish();
    println!("{}", live.content());
    // post.edit("!");        // error: post was moved by review()
    // Post::new("x").publish(); // error: no method publish on Post<Draft>
}

Each transition takes self by value, so the old state cannot be used again, and each state's impl block only offers what makes sense in that state. A whole class of bugs cannot compile.

PhantomData

Draft, Reviewed and Published above are empty structs stored in a field. Often a type parameter is needed only to tell types apart and there is nothing to store. Rust insists every type parameter is used, and std::marker::PhantomData<T> is the zero-size field that "uses" it:

Rust
use std::marker::PhantomData;

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
struct Id<T> {
    value: u32,
    _for: PhantomData<T>,
}

impl<T> Id<T> {
    fn new(value: u32) -> Id<T> {
        Id { value, _for: PhantomData }
    }
}

struct User;
struct Order;

fn find_user(id: Id<User>) -> String {
    format!("user #{}", id.value)
}

fn main() {
    let user: Id<User> = Id::new(7);
    let order: Id<Order> = Id::new(7);
    println!("{}", find_user(user));
    // find_user(order);     // error: expected Id<User>, found Id<Order>
    println!("{}", std::mem::size_of::<Id<Order>>());   // 4: PhantomData takes no space
    let _ = order;
}

Two IDs with the same number but for different things can no longer be mixed up, and it costs nothing at run time.

Units of measure

The same trick gives numbers a unit:

Rust
use std::marker::PhantomData;
use std::ops::Add;

#[derive(Debug, Clone, Copy)]
struct Length<U> { value: f64, unit: PhantomData<U> }
#[derive(Debug, Clone, Copy)]
struct Metres;
#[derive(Debug, Clone, Copy)]
struct Feet;

impl<U> Length<U> {
    fn new(value: f64) -> Self { Length { value, unit: PhantomData } }
}

impl<U> Add for Length<U> {
    type Output = Length<U>;
    fn add(self, other: Self) -> Self { Length::new(self.value + other.value) }   // only the same unit
}

impl From<Length<Feet>> for Length<Metres> {
    fn from(f: Length<Feet>) -> Self { Length::new(f.value * 0.3048) }
}

fn main() {
    let run = Length::<Metres>::new(400.0) + Length::new(100.0);
    let climb: Length<Metres> = Length::<Feet>::new(1000.0).into();
    println!("{:.1} m, {:.1} m", run.value, climb.value);
}

Sealed traits

Sometimes the set of states should be closed, so nobody outside your crate can add one. A sealed trait requires a private supertrait that outside code cannot name:

Rust
mod private { pub trait Sealed {} }

pub trait State: private::Sealed {}
impl private::Sealed for Draft {}
impl State for Draft {}
// other crates cannot implement State, because they cannot implement private::Sealed

When it is worth it

Type-state shines when the rules are fixed and getting them wrong is costly: protocols, hardware drivers, builders with required fields, money and IDs. It adds types and generic code, so for rules that change at run time (a user can toggle a setting back and forth) a plain enum field and a check are simpler.
