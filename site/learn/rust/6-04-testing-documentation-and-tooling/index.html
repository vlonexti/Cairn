Testing, Documentation and Tooling

lesson 6.044 of 5 in milestone 65 min1 practice task

The Rust toolbox - cargo test with unit, integration and documentation tests, test organisation and fixtures, rustfmt and clippy, cargo doc and writing good doc comments, features and profiles, benchmarking, cargo workspaces, and publishing a crate.

Tests

cargo test builds and runs three kinds of tests:

  • Unit tests in a #[cfg(test)] mod tests next to the code (lesson 3.05). They can test private functions.
  • Integration tests in the tests/ folder. Each file is a separate crate that uses your library only through its public API.
  • Documentation tests: code examples in /// comments are compiled and run, so the docs never go stale.
Rust
/// Splits a duration like "1h30m" into seconds.
///
/// # Examples
///
/// ```
/// use timeparse::parse;
/// assert_eq!(parse("1h30m"), Ok(5400));
/// assert!(parse("soon").is_err());
/// ```
///
/// # Errors
///
/// Returns an error for empty input or unknown units.
pub fn parse(text: &str) -> Result<u64, ParseError> { /* ... */ }
Text
mycrate/
  Cargo.toml
  src/lib.rs           (unit tests inside)
  tests/
    parsing.rs         (integration tests)
    common/mod.rs      (shared helpers for integration tests)

Helpful patterns:

  • Name tests after the behaviour: fn rejects_negative_amounts().
  • assert_eq!(left, right, "message with {}", context) adds context to failures.
  • Tests that return Result<(), E> can use ?.
  • #[ignore] marks slow tests; run them with cargo test -- --ignored.
  • Property-based testing (the proptest crate) generates many random inputs and checks that a property always holds.

Formatting and linting

Terminal
cargo fmt              # rustfmt: formats the whole project in the standard style
cargo clippy           # hundreds of lints: bugs, slow code, unidiomatic code
cargo clippy -- -D warnings    # treat every lint as an error (good in CI)

Clippy catches things like if x == true, needless clone()s, len() == 0 instead of is_empty(), and loops that should be iterators. Its explanations link to the reasoning, which is a good way to learn idiomatic Rust.

Documentation

cargo doc --open builds HTML documentation for your crate and all its dependencies. Write doc comments with /// for items and //! for the crate or module itself. The conventional sections are # Examples, # Errors, # Panics and # Safety. docs.rs builds the documentation of every crate published on crates.io.

Cargo features and profiles

TOML
[features]
default = ["json"]
json = ["dep:serde_json"]        # optional dependency enabled by a feature

[dependencies]
serde_json = { version = "1", optional = true }

[profile.release]
lto = true                       # link-time optimisation: smaller, faster binaries
codegen-units = 1

cargo build --release uses the release profile: optimised, without debug checks such as integer-overflow panics. Measure performance with release builds only. For benchmarks, the criterion crate runs code many times and reports statistically meaningful timings.

Workspaces

A workspace groups several crates that are developed together and share one Cargo.lock and target folder:

TOML
# Cargo.toml at the top
[workspace]
members = ["core", "cli", "server"]
resolver = "3"

Typical layout: a library crate with the logic (core), and thin binary crates (cli, server) that depend on it, the same separation as the C# and Java courses recommend.

Publishing

cargo publish uploads a library to crates.io after cargo login. Version numbers follow semantic versioning; Cargo treats 0.x minor versions as breaking. Before publishing, fill in description, license and repository in Cargo.toml, and run cargo package to check what will be uploaded.
