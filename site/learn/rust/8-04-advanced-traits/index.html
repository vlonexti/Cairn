Advanced Traits

lesson 8.044 of 5 in milestone 85 min2 practice tasks

The trait features behind Rust's standard library - associated types and how they differ from generic parameters, default type parameters, supertraits, blanket implementations, const generics for array sizes, implementing Sum and FromIterator so collect and sum work with your types, and extension traits.

Associated types

Iterator has type Item; rather than a generic parameter. An associated type is chosen once by each implementation:

Rust
trait Container {
    type Item;
    fn get(&self, i: usize) -> Option<&Self::Item>;
    fn first(&self) -> Option<&Self::Item> {
        self.get(0)
    }
}

struct Shelf {
    books: Vec<String>,
}

impl Container for Shelf {
    type Item = String;
    fn get(&self, i: usize) -> Option<&String> {
        self.books.get(i)
    }
}

fn main() {
    let s = Shelf { books: vec!["Dune".into(), "Emma".into()] };
    println!("{:?} {:?}", s.first(), s.get(5));
}

With a generic parameter (trait Container<T>), one type could implement it many times (Container<String> and Container<i32>), and callers would have to say which. With an associated type, there is exactly one Item per implementing type, so shelf.first() needs no annotation. Use an associated type when each type has one natural answer.

Default type parameters

Add<Rhs = Self> means "add to the same type unless told otherwise", which is why impl Add for V2 (lesson 8.02) needed no parameter. You can give your own traits defaults the same way:

Rust
trait Scale<By = f64> {
    fn scale(&self, by: By) -> Self;
}

Supertraits

A trait can require another: trait Shape: Display means every Shape must also be Display, so Shape methods can use {}:

Rust
use std::fmt;

trait Shape: fmt::Display {
    fn area(&self) -> f64;
    fn describe(&self) -> String {
        format!("{self} with area {:.2}", self.area())
    }
}

struct Square(f64);

impl fmt::Display for Square {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "a square of side {}", self.0)
    }
}

impl Shape for Square {
    fn area(&self) -> f64 {
        self.0 * self.0
    }
}

fn main() {
    println!("{}", Square(3.0).describe());
}

Blanket implementations

An impl can cover every type that meets a bound. The standard library does this a lot: every type that implements Display gets to_string() through impl<T: Display> ToString for T. Yours work the same way:

Rust
use std::fmt::Display;

trait Shout {
    fn shout(&self) -> String;
}

impl<T: Display> Shout for T {
    fn shout(&self) -> String {
        format!("{}!", self.to_string().to_uppercase())
    }
}

fn main() {
    println!("{} {} {}", "hello".shout(), 42.shout(), 'x'.shout());
}

This also shows an extension trait: a trait that adds methods to types you did not write. Only code that imports the trait sees the methods.

Const generics

Types can take values as parameters, most often array sizes:

Rust
#[derive(Debug)]
struct Matrix<const R: usize, const C: usize> {
    data: [[i32; C]; R],
}

impl<const R: usize, const C: usize> Matrix<R, C> {
    fn transpose(&self) -> Matrix<C, R> {
        let mut data = [[0; R]; C];
        for r in 0..R {
            for c in 0..C {
                data[c][r] = self.data[r][c];
            }
        }
        Matrix { data }
    }
}

fn sum<const N: usize>(xs: [i32; N]) -> i32 {
    xs.iter().sum()
}

fn main() {
    let m = Matrix { data: [[1, 2, 3], [4, 5, 6]] };
    println!("{:?}", m.transpose());
    println!("{} {}", sum([1, 2, 3]), sum([10; 5]));
}

The sizes are checked at compile time: a 2×3 matrix's transpose is a 3×2 matrix, and mixing them up is a type error.

Making sum and collect work with your types

iter.sum() needs the item type to implement Sum, and collect() needs the target to implement FromIterator:

Rust
use std::iter::{FromIterator, Sum};
use std::ops::Add;

#[derive(Debug, Clone, Copy, Default, PartialEq)]
struct Money(i64);

impl Add for Money {
    type Output = Money;
    fn add(self, o: Money) -> Money {
        Money(self.0 + o.0)
    }
}

impl Sum for Money {
    fn sum<I: Iterator<Item = Money>>(iter: I) -> Money {
        iter.fold(Money::default(), |a, b| a + b)
    }
}

#[derive(Debug)]
struct Basket(Vec<String>);

impl FromIterator<String> for Basket {
    fn from_iter<I: IntoIterator<Item = String>>(iter: I) -> Self {
        let mut items: Vec<String> = iter.into_iter().collect();
        items.sort();
        Basket(items)
    }
}

fn main() {
    let total: Money = [Money(250), Money(120), Money(30)].into_iter().sum();
    println!("{total:?}");
    let b: Basket = ["tea", "bread", "milk"].iter().map(|s| s.to_string()).collect();
    println!("{} items: {:?}", b.0.len(), b.0);
}

Implementing these few traits makes your types fit into iterator chains as smoothly as the built-in ones.
