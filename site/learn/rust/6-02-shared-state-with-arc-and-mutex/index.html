Shared State with Arc and Mutex

lesson 6.022 of 5 in milestone 65 min1 practice task

Sharing data between threads safely - Arc for shared ownership across threads, Mutex for exclusive access with lock guards, RwLock for many readers, atomics for counters and flags, avoiding deadlocks and holding locks briefly, poisoning, and choosing between message passing and shared state.

Arc: shared ownership across threads

Rc is single-threaded. Arc<T> (atomically reference counted) is the thread-safe version: cloning it gives another owner, and the value is freed when the last owner is gone. On its own, Arc gives read-only sharing:

Rust
use std::sync::Arc;
use std::thread;

fn main() {
    let config = Arc::new(vec!["fast".to_string(), "safe".to_string()]);
    let handles: Vec<_> = (0..3).map(|i| {
        let config = Arc::clone(&config);
        thread::spawn(move || format!("thread {i} sees {}", config.join("+")))
    }).collect();
    for h in handles {
        println!("{}", h.join().unwrap());
    }
    println!("owners now: {}", Arc::strong_count(&config));
}

Mutex: one writer at a time

To change shared data, wrap it in a Mutex (mutual exclusion). lock() waits until no other thread holds the lock and returns a guard that gives access; the lock is released when the guard is dropped:

Rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0u64));
    let mut handles = Vec::new();
    for _ in 0..8 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                *counter.lock().unwrap() += 1;       // lock, change, guard dropped at the end of the statement
            }
        }));
    }
    for h in handles { h.join().unwrap(); }
    println!("{}", *counter.lock().unwrap());       // always 8000
}

Arc<Mutex<T>> is the thread-safe counterpart of Rc<RefCell<T>>. The data lives inside the mutex, so it is impossible to touch it without locking: forgetting the lock, the classic C bug, cannot be written.

If a thread panics while holding a lock, the mutex becomes poisoned and later lock() calls return Err. unwrap() then propagates the panic, which is usually right; into_inner() on the error recovers the data if you know it is still valid.

RwLock and atomics

Tool Use when
Mutex<T> Any shared data that changes
RwLock<T> Data that is read often and written rarely: many read() guards at once, or one write()
AtomicUsize, AtomicBool, AtomicU64... A single number or flag: no lock at all
OnceLock<T> / LazyLock<T> A value initialised once and then shared read-only
Rust
use std::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
use std::sync::{Arc, RwLock};
use std::thread;

fn main() {
    let hits = Arc::new(AtomicUsize::new(0));
    let stop = Arc::new(AtomicBool::new(false));
    let settings = Arc::new(RwLock::new(String::from("v1")));

    thread::scope(|s| {
        for _ in 0..4 {
            let (hits, settings) = (Arc::clone(&hits), Arc::clone(&settings));
            s.spawn(move || {
                for _ in 0..250 {
                    let _version = settings.read().unwrap();      // many readers at once
                    hits.fetch_add(1, Ordering::Relaxed);
                }
            });
        }
        s.spawn(|| {
            *settings.write().unwrap() = String::from("v2");      // one writer
            stop.store(true, Ordering::Release);
        });
    });
    println!("{} {} {}", hits.load(Ordering::Relaxed), stop.load(Ordering::Acquire), settings.read().unwrap());
}

For simple counters, Ordering::Relaxed is enough; flags that publish other data use Release when storing and Acquire when loading. When unsure, SeqCst is the strongest and simplest.

Deadlocks and lock hygiene

The compiler prevents data races, but not deadlocks: thread A holds lock 1 and waits for lock 2 while thread B holds lock 2 and waits for lock 1. Avoid them by:

  • holding locks briefly: copy what you need out of the guard, drop it, then do the slow work;
  • always taking several locks in the same order;
  • never calling unknown code (callbacks) while holding a lock.
Rust
let snapshot = { data.lock().unwrap().clone() };    // the guard is dropped at the end of the block
expensive_report(&snapshot);                        // the lock is free while this runs

Message passing or shared state?

Both are safe in Rust. Prefer message passing (channels) or splitting the work (scoped threads, each with its own data) when it fits naturally: there is nothing to lock. Use shared state for data many threads read and update, such as a cache or a counter. Libraries like rayon (data.par_iter().map(...).sum()) parallelise iterator chains with almost no code.
