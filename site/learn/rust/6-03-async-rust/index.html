Async Rust

lesson 6.033 of 5 in milestone 65 min1 practice task

An overview of asynchronous Rust - why async exists, futures and async fn, .await, why a runtime such as Tokio is needed, spawning tasks, running futures concurrently with join and select, async I/O, channels and timeouts, Send and 'static bounds on tasks, and choosing between threads and async.

Why async

Threads are a fine way to do several things at once, but each one costs memory and switching between thousands of them is expensive. A web server waiting on ten thousand slow network connections spends almost all its time waiting. Async code lets one thread juggle many waiting tasks: when a task would block, it yields, and the thread runs another task that is ready.

Futures and .await

An async fn does not run when called. It returns a future: a value that represents work which can be driven to completion later. .await drives a future, pausing the current async function until the result is ready:

Rust
async fn fetch_price(item: &str) -> u32 {
    // imagine a network request here
    tokio::time::sleep(std::time::Duration::from_millis(100)).await;
    if item == "tea" { 250 } else { 400 }
}

async fn total(items: &[&str]) -> u32 {
    let mut sum = 0;
    for item in items {
        sum += fetch_price(item).await;          // one after another
    }
    sum
}

Futures are lazy: if nobody awaits (or spawns) them, nothing happens. The compiler warns about unused futures.

A runtime

The standard library defines futures but does not include the machinery that runs them. A runtime does: it polls futures, parks them while they wait for I/O or timers, and wakes them up. Tokio is the most used one:

TOML
[dependencies]
tokio = { version = "1", features = ["full"] }
Rust
#[tokio::main]
async fn main() {
    let a = fetch_price("tea");
    let b = fetch_price("cake");
    let (pa, pb) = tokio::join!(a, b);            // both at the same time: about 100 ms, not 200
    println!("{pa} {pb}");

    let handle = tokio::spawn(async { fetch_price("mug").await * 2 });   // a separate task
    println!("{}", handle.await.unwrap());

    match tokio::time::timeout(std::time::Duration::from_millis(50), fetch_price("slow")).await {
        Ok(price) => println!("{price}"),
        Err(_) => println!("gave up after 50 ms"),
    }
}
Tool Does
x.await Wait for one future inside an async function
tokio::join!(a, b) Run several futures concurrently, wait for all
tokio::select! Wait for whichever finishes first
tokio::spawn(fut) Run a future as an independent task (like a lightweight thread)
tokio::sync::mpsc, Mutex Async versions of channels and locks
tokio::time::sleep, timeout Timers that do not block the thread

Rules that trip people up

  • Never block inside async code. std::thread::sleep, a long CPU loop or a blocking file read stops the whole runtime thread, and every task on it. Use the async versions (tokio::time::sleep, tokio::fs), or move blocking work to tokio::task::spawn_blocking.
  • Spawned tasks may run on other threads and outlive the caller, so their futures must be Send + 'static: own their data (move), and use Arc for sharing. Holding a std::sync::MutexGuard across an .await makes the future non-Send; release it before awaiting, or use tokio::sync::Mutex.
  • Async functions in traits work directly in modern Rust; returning boxed futures (Pin<Box<dyn Future>>) is still needed in some generic code.

Threads or async?

Use threads when Use async when
The work is CPU-bound (computing, compressing) The work is mostly waiting (network, many connections)
There are a handful of concurrent jobs There are thousands of concurrent tasks
You want the simplest code You are writing servers or clients with a runtime anyway

Many programs use both: an async web server that hands heavy computations to a thread pool. The practice sandbox has no Tokio, so this lesson's code is for reading and for your own projects.
