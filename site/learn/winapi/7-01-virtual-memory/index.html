Virtual Memory

lesson 7.011 of 6 in milestone 75 min1 practice task

Managing memory a page at a time - reserving address space and committing pages with VirtualAlloc, page size and allocation granularity, protection flags and VirtualProtect, asking about memory with VirtualQuery, decommitting and releasing with VirtualFree, guard pages, and a buffer that grows without moving.

Below new and malloc

new, malloc and the C++ containers get their memory from a heap, which in turn gets it from the operating system in big pieces. VirtualAlloc is that lower layer: it hands out memory in whole pages, with control over two things the heap hides:

  • Reserving address space (claiming a range of addresses, with no memory behind it yet) is separate from committing it (backing pages with real memory or the page file).
  • Each page has a protection: readable, writable, executable, or none.

The Pointers and Memory course covers the ideas; this lesson is the Windows API for them.

Sizes

C++
SYSTEM_INFO info{};
GetSystemInfo(&info);
// info.dwPageSize                 4096 on x64: the unit of commit and protection
// info.dwAllocationGranularity    65536: reservations start at multiples of 64 KB

A reservation's base address is always a multiple of the allocation granularity (64 KB), and its size is rounded up to whole pages. Committing, decommitting and protecting work on whole pages: a call covering part of a page affects all of it.

Reserve, then commit

C++
constexpr SIZE_T reserveSize{ 1ull << 30 };                       // 1 GB of addresses, no memory used yet
auto* base{ static_cast<std::byte*>(VirtualAlloc(nullptr, reserveSize, MEM_RESERVE, PAGE_NOACCESS)) };
if (!base) return GetLastError();

// Later, when the first 64 KB are needed:
if (!VirtualAlloc(base, 64 * 1024, MEM_COMMIT, PAGE_READWRITE)) return GetLastError();
base[0] = std::byte{ 1 };                                        // fine: committed and writable
// base[64 * 1024] = ...;                                        // access violation: reserved only

MEM_RESERVE | MEM_COMMIT does both at once, which is what most callers want for a plain block. Committed pages read as zero until written.

Reserving a large range and committing as you go gives a buffer that grows without ever moving: pointers into it stay valid, unlike a std::vector that reallocates. Large arrays, arenas and the stack of every thread work this way.

Protection

Constant Access
PAGE_NOACCESS none: any access faults
PAGE_READONLY read
PAGE_READWRITE read and write
PAGE_EXECUTE_READ read and run code
PAGE_EXECUTE_READWRITE all three (avoid: it defeats a basic security protection)
PAGE_GUARD (combined with one of the above) the first access raises a one-time STATUS_GUARD_PAGE_VIOLATION, then the page behaves normally

VirtualProtect(address, size, newProtect, &oldProtect) changes the protection of committed pages and must be given a place for the old value. Making data read-only after setting it up catches stray writes immediately, as an access violation at the bug instead of corruption found later.

Asking about memory

VirtualQuery(address, &mbi, sizeof mbi) describes the run of pages starting at the page containing address that all share the same state and protection:

Field Meaning
BaseAddress, RegionSize where this run starts and how long it is
AllocationBase, AllocationProtect the reservation it belongs to, and that reservation's original protection
State MEM_COMMIT, MEM_RESERVE or MEM_FREE
Protect the protection of committed pages

Walking a process's memory with repeated VirtualQuery calls (address = previous base + size) lists every region; debuggers and memory profilers do exactly this, and practice 7.01 simulates it.

Giving memory back

C++
VirtualFree(base, 64 * 1024, MEM_DECOMMIT);        // the pages go back to reserved
VirtualFree(base, 0, MEM_RELEASE);                 // the whole reservation; size MUST be 0

MEM_RELEASE takes the base address the reservation started at and a size of 0; anything else fails with ERROR_INVALID_PARAMETER.
