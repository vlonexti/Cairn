Strings on Windows

lesson 1.022 of 5 in milestone 15 min1 practice task

Windows uses UTF-16 internally, while files and the web mostly use UTF-8. This lesson explains the W and A versions of functions, wchar_t and L"" literals, surrogate pairs, converting between UTF-8 and UTF-16, and the UTF-8 code page option.

W and A

Most API functions that take text come in two versions:

  • CreateFileW, MessageBoxW, SetWindowTextW: W for wide, taking UTF-16 strings (const wchar_t*).
  • CreateFileA, MessageBoxA: A for ANSI, taking 8-bit strings in the system's legacy code page.

CreateFile without a letter is a macro that picks one depending on whether UNICODE is defined. Modern code calls the W functions explicitly: the A versions convert to UTF-16 internally anyway, and with a legacy code page they lose every character that page cannot represent (try a Japanese file name on an English system).

wchar_t and L"..."

On Windows, wchar_t is 16 bits and holds one UTF-16 code unit. String literals with an L prefix are wide: L"Grüße". std::wstring is the matching string class.

UTF-16 and surrogate pairs

Unicode has more than a million possible code points; 16 bits hold 65 536 values. UTF-16 encodes:

  • code points up to U+FFFF (all common scripts) as one 16-bit unit;
  • code points above U+FFFF (emoji, rare scripts) as two units, a surrogate pair: a high surrogate 0xD800-0xDBFF followed by a low surrogate 0xDC00-0xDFFF.
Output
U+1F600 (😀):  subtract 0x10000 → 0xF600, 20 bits: 0000 1111 0110 0000 0000
high = 0xD800 + (top 10 bits)  = 0xD83D
low  = 0xDC00 + (low 10 bits)  = 0xDE00

So wcslen counts code units, not characters: an emoji has length 2. Cursor movement in a text editor must skip both halves of a pair.

UTF-8

UTF-8 encodes each code point in 1 to 4 bytes:

Code points Bytes
U+0000 - U+007F 0xxxxxxx
U+0080 - U+07FF 110xxxxx 10xxxxxx
U+0800 - U+FFFF 1110xxxx 10xxxxxx 10xxxxxx
U+10000 - U+10FFFF 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx

ASCII text is unchanged, which is why UTF-8 is the standard for files, the web and most libraries.

Converting

MultiByteToWideChar and WideCharToMultiByte convert, called twice: once to get the size, once to convert:

C++
std::wstring widen(std::string_view utf8)
{
    if (utf8.empty()) return {};
    const int n = MultiByteToWideChar(CP_UTF8, MB_ERR_INVALID_CHARS, utf8.data(), (int)utf8.size(), nullptr, 0);
    if (n == 0) throw std::runtime_error("invalid UTF-8");
    std::wstring out(n, L'\0');
    MultiByteToWideChar(CP_UTF8, MB_ERR_INVALID_CHARS, utf8.data(), (int)utf8.size(), out.data(), n);
    return out;
}

std::string narrow(std::wstring_view utf16)
{
    if (utf16.empty()) return {};
    const int n = WideCharToMultiByte(CP_UTF8, WC_ERR_INVALID_CHARS, utf16.data(), (int)utf16.size(), nullptr, 0, nullptr, nullptr);
    std::string out(n, '\0');
    WideCharToMultiByte(CP_UTF8, WC_ERR_INVALID_CHARS, utf16.data(), (int)utf16.size(), out.data(), n, nullptr, nullptr);
    return out;
}

A good rule for a program: keep strings in UTF-8 (std::string) inside the program and in files, and convert to UTF-16 at the boundary, right where you call a W function. The practice writes these conversions by hand, to understand exactly what happens to every byte, including invalid input.

Invalid input

Not every byte sequence is valid UTF-8, and not every wchar_t sequence is valid UTF-16 (a lone surrogate is invalid, and Windows file names can contain them). The usual answer is to replace each invalid part with U+FFFD (�, the replacement character) rather than fail or, worse, silently drop data.

The UTF-8 code page

Since Windows 10 version 1903, an application manifest (lesson 6.02) can set activeCodePage to UTF-8. The A functions then take UTF-8, and fopen, std::ifstream and the console understand UTF-8 paths. It is a good option for porting code from Linux; for new Windows code, the W functions remain the clearest choice.
