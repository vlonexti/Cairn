Mouse Input and Capture

lesson 2.022 of 5 in milestone 25 min1 practice task

Handling clicks, double-clicks, movement and the wheel, the modifier flags that come with them, capturing the mouse during a drag, knowing when the mouse leaves, setting the cursor, and hit-testing your own shapes.

Mouse messages

Message When
WM_LBUTTONDOWN / UP, WM_RBUTTON..., WM_MBUTTON..., WM_XBUTTON... A button changes
WM_LBUTTONDBLCLK A second click soon after the first (only if the class has CS_DBLCLKS)
WM_MOUSEMOVE The mouse moved over the client area
WM_MOUSEWHEEL, WM_MOUSEHWHEEL The wheel turned (vertically, horizontally)
WM_MOUSELEAVE The mouse left the window (after you asked for it)

The position is in lParam, in client coordinates, read with GET_X_LPARAM / GET_Y_LPARAM (lesson 1.04). wParam holds flags for what else is down: MK_LBUTTON, MK_RBUTTON, MK_SHIFT, MK_CONTROL, MK_MBUTTON.

A double-click arrives as down, up, double-click, up: the first click is delivered as an ordinary click first. Design double-click actions so the single click before them does no harm (select on click, open on double-click).

The wheel

WM_MOUSEWHEEL is different from the others: its position is in screen coordinates (convert with ScreenToClient), and the amount is in the high word of wParam, signed, in multiples of WHEEL_DELTA (120) per notch:

C++
case WM_MOUSEWHEEL:
{
    m_wheelRemainder += GET_WHEEL_DELTA_WPARAM(wParam);
    const int notches = m_wheelRemainder / WHEEL_DELTA;
    m_wheelRemainder -= notches * WHEEL_DELTA;
    scrollLines(-notches * 3);
    return 0;
}

Precision touchpads send small values such as 15 or 30. Accumulating the remainder, as above, keeps slow scrolling working instead of throwing every small movement away. The practice writes this accumulator.

Capturing the mouse

When the user presses the button inside your window and drags outside it, WM_MOUSEMOVE and the button-up go to whatever window is under the mouse, not yours. A drag (moving a slider, selecting text, drawing a line) needs capture:

C++
case WM_LBUTTONDOWN: SetCapture(hwnd); m_dragging = true; m_start = pointFrom(lParam); return 0;
case WM_MOUSEMOVE:   if (m_dragging) { m_end = pointFrom(lParam); InvalidateRect(hwnd, nullptr, FALSE); } return 0;
case WM_LBUTTONUP:   if (m_dragging) { ReleaseCapture(); } return 0;
case WM_CAPTURECHANGED: m_dragging = false; return 0;       // capture lost, for any reason

While captured, every mouse message comes to your window, even from outside it, with positions that can be negative or beyond the client size. Handle WM_CAPTURECHANGED to end the drag cleanly: the system can take capture away (an Alt+Tab, a pop-up), and then no button-up will ever arrive.

Knowing when the mouse leaves

To highlight something on hover, you need to know when the mouse leaves. Ask for one WM_MOUSELEAVE with TrackMouseEvent, and ask again after each one:

C++
case WM_MOUSEMOVE:
    if (!m_tracking) { TRACKMOUSEEVENT t{ sizeof(t), TME_LEAVE, hwnd, 0 }; TrackMouseEvent(&t); m_tracking = true; }
    updateHover(pointFrom(lParam));
    return 0;
case WM_MOUSELEAVE: m_tracking = false; clearHover(); return 0;

The cursor

The class's cursor (wc.hCursor) is shown by default. To change it depending on what is under the mouse (a resize arrow over a splitter, a hand over a link), handle WM_SETCURSOR:

C++
case WM_SETCURSOR:
    if (LOWORD(lParam) == HTCLIENT && overSplitter()) { SetCursor(LoadCursorW(nullptr, IDC_SIZEWE)); return TRUE; }
    break;   // let DefWindowProcW set the normal cursor

Hit-testing

The window only tells you a point; deciding what is under it is your job: test the point against your shapes from the topmost down, and the first hit wins. Rectangles use lesson 1.05's exclusive right and bottom edges; circles compare squared distances.
