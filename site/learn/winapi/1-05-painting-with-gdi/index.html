Painting with GDI

lesson 1.055 of 5 in milestone 15 min1 practice task

Windows asks a window to paint itself with WM_PAINT. This lesson handles it with BeginPaint and EndPaint, draws lines, shapes and text with GDI, manages pens, brushes and fonts without leaking them, and invalidates just the part of the window that changed.

Windows does not remember your pixels

When a window is uncovered, restored or resized, the system does not keep a copy of what was in it. It marks the area as invalid and sends WM_PAINT: the window must draw itself again. So every program keeps its state (the text, the shapes, the score) and paints from it, exactly like a game draws each frame from its data.

WM_PAINT

C++
case WM_PAINT:
{
    PAINTSTRUCT ps;
    HDC dc = BeginPaint(hwnd, &ps);          // ps.rcPaint: the invalid rectangle
    RECT client;
    GetClientRect(hwnd, &client);
    DrawTextW(dc, L"Hello, GDI", -1, &client, DT_CENTER | DT_VCENTER | DT_SINGLELINE);
    EndPaint(hwnd, &ps);                     // validates the area
    return 0;
}

Always pair BeginPaint with EndPaint, even if you draw nothing: EndPaint marks the area valid. Without it, Windows keeps sending WM_PAINT forever and the program uses a whole CPU core.

HDC is a device context: a drawing surface with its current pen, brush, font and colours. Outside WM_PAINT you can get one with GetDC / ReleaseDC, but painting belongs in WM_PAINT.

Drawing

Function Draws
MoveToEx(dc, x, y, nullptr), LineTo(dc, x, y) Lines with the current pen
Rectangle(dc, l, t, r, b), Ellipse, RoundRect, Polygon Outlined with the pen, filled with the brush
FillRect(dc, &rect, brush) A filled rectangle, no outline
TextOutW(dc, x, y, text, len), DrawTextW(...) Text; DrawTextW can wrap and align in a rectangle
SetTextColor, SetBkMode(dc, TRANSPARENT) Text colour, and no background box behind text

Colours are COLORREF values made with RGB(r, g, b). Note the byte order: RGB stores red in the lowest byte (0x00BBGGRR), the opposite of the #RRGGBB order in HTML. The practice packs and unpacks them.

Coordinates are in pixels from the client area's top-left corner. A RECT's right and bottom are exclusive: {0, 0, 10, 10} covers pixels 0 to 9.

Pens, brushes and fonts

GDI objects are selected into the device context, and the previous object must be put back before you delete yours:

C++
HPEN pen = CreatePen(PS_SOLID, 3, RGB(200, 40, 40));
HBRUSH brush = CreateSolidBrush(RGB(250, 230, 120));
HGDIOBJ oldPen = SelectObject(dc, pen);
HGDIOBJ oldBrush = SelectObject(dc, brush);
Ellipse(dc, 50, 50, 200, 150);
SelectObject(dc, oldBrush);            // put the originals back
SelectObject(dc, oldPen);
DeleteObject(brush);                   // now safe to delete
DeleteObject(pen);

Deleting an object while it is still selected fails silently, and the object leaks. A program that leaks a brush per paint eventually reaches the per-process limit of 10 000 GDI objects and stops drawing altogether. GetStockObject(BLACK_PEN), WHITE_BRUSH and friends are system objects that never need deleting. Creating the pens and brushes you use often once, in WM_CREATE, is both faster and safer.

Repainting what changed

When the program's state changes, it does not paint directly. It invalidates the affected area and lets the next WM_PAINT do the work:

C++
InvalidateRect(hwnd, &changedRect, TRUE);   // TRUE: erase the background first
InvalidateRect(hwnd, nullptr, TRUE);        // the whole client area

Several invalidations before the next paint are combined into one region, and the paint's ps.rcPaint is the bounding rectangle of all of them; a careful program draws only what intersects it. UpdateWindow(hwnd) paints immediately instead of waiting for the queue to empty.

Background erasing before each paint causes flicker on resizing; lesson 4.01 removes it with double buffering.
