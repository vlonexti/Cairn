Threads and Synchronisation

lesson 5.044 of 5 in milestone 55 min1 practice task

Keeping the interface responsive while long work runs - worker threads, posting results back to the UI thread, protecting shared data with SRW locks and critical sections, events and condition variables, cancellation, and the thread pool.

The UI thread must not block

All of a window's messages are processed on the thread that created it. While a message handler runs, that thread cannot paint, react to input or even be moved. Anything slower than about 50 ms (reading a big file, searching a folder, a network request, waiting for a process) belongs on another thread.

Starting a worker

std::thread (or std::jthread, which joins automatically and supports stop requests) works on Windows; CreateThread is the raw API underneath.

C++
std::jthread m_worker;

void startSearch(HWND hwnd, std::wstring folder, std::wstring pattern)
{
    m_worker = std::jthread([hwnd, folder, pattern](std::stop_token stop) {
        std::vector<std::wstring> found;
        searchFolder(folder, pattern, found, stop);                     // checks stop.stop_requested() often
        auto* result = new std::vector<std::wstring>(std::move(found));
        if (!PostMessageW(hwnd, WM_APP_SEARCH_DONE, 0, reinterpret_cast<LPARAM>(result)))
            delete result;                                              // the window is gone
    });
}

case WM_APP_SEARCH_DONE:
{
    std::unique_ptr<std::vector<std::wstring>> result{ reinterpret_cast<std::vector<std::wstring>*>(lParam) };
    showResults(*result);
    return 0;
}

The rules:

  • A worker never touches windows directly (no SetWindowTextW, no drawing). It posts a message, and the UI thread updates the window. PostMessageW is safe from any thread; SendMessageW to the UI thread can deadlock if the UI thread is waiting for the worker.
  • Data passed with the message must outlive the worker: allocate it, pass the pointer, and let the receiver own it. If PostMessageW fails (the window was destroyed), free it yourself.
  • Before the window is destroyed, stop and join the worker, so it does not post to a dead window or use freed data.

Progress and cancellation

Long work should report progress and be cancellable. Post a progress message now and then (at most every 50-100 ms, or the queue fills with thousands), and check a stop flag (std::stop_token, or an std::atomic<bool>) between steps. Cancellation is cooperative: the worker must look at the flag; nothing stops a thread safely from outside.

Shared data

When two threads use the same data and at least one writes, the access must be synchronised, or the result is a data race: torn values, corrupted containers, crashes that appear once a week.

Tool Use
std::mutex / SRWLOCK Mutual exclusion: one thread at a time in a critical section
SRWLOCK shared mode Many readers at once, or one writer
CRITICAL_SECTION Older recursive lock; still common in existing code
std::atomic<T> A single value: flags, counters
std::condition_variable / CONDITION_VARIABLE Wait until something becomes true
Event (CreateEventW) A signal that can be waited on together with other handles
C++
SRWLOCK m_lock = SRWLOCK_INIT;
std::vector<Result> m_results;

void add(Result r) { AcquireSRWLockExclusive(&m_lock); m_results.push_back(std::move(r)); ReleaseSRWLockExclusive(&m_lock); }

In C++, std::mutex with std::lock_guard (or std::scoped_lock) does the same and cannot forget to unlock. Hold locks briefly, never call out to unknown code (or SendMessageW) while holding one, and always take several locks in the same order, or two threads can deadlock each holding what the other needs.

A work queue

A common structure is one or more workers taking jobs from a queue: the UI thread pushes jobs, the workers pop them, and a condition variable wakes a worker when a job arrives. Stopping it cleanly means: set a "closing" flag, wake everyone, let the workers finish (or abandon) the queue, and join them. The practice builds such a queue; the file finder of milestone 6 uses it.

The thread pool

Starting a thread costs some time and memory (1 MB of stack reserved by default). For many small jobs, use the system thread pool: TrySubmitThreadpoolCallback, or the full CreateThreadpoolWork API, which runs callbacks on a set of threads Windows manages. std::async on MSVC also uses the pool.

Waiting on several things

WaitForMultipleObjects waits until one (or all) of several handles is signalled: processes ending, events set, timers expiring. In a UI thread, MsgWaitForMultipleObjectsEx waits for handles or new messages, so the window stays responsive while waiting.
