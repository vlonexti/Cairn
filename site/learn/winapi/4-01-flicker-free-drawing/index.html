Flicker-Free Drawing

lesson 4.011 of 4 in milestone 45 min1 practice task

Why windows flicker when they repaint, and the fixes - not erasing the background, drawing into an off-screen bitmap first, the buffered-paint API, painting only what changed, and scrolling content efficiently.

Where flicker comes from

Flicker is the screen briefly showing a half-finished picture. With GDI it happens in two ways:

  1. Erasing: before WM_PAINT, Windows sends WM_ERASEBKGND, and the default handling fills the area with the class background. For a moment the screen shows an empty window, then your drawing appears on top.
  2. Overdraw: your own paint code fills a rectangle, then draws over it. Each step is visible for a moment.

Resizing makes both happen dozens of times a second.

Step 1: do not erase

If your WM_PAINT covers the whole area anyway, tell Windows not to erase:

C++
case WM_ERASEBKGND:
    return 1;          // "done", without doing anything

(and pass FALSE as the last argument of InvalidateRect). A class with no background brush (hbrBackground = nullptr) has the same effect.

Step 2: draw off-screen

Double buffering draws the whole frame into a bitmap in memory, then copies it to the window in one operation. Nobody ever sees the intermediate steps:

C++
case WM_PAINT:
{
    PAINTSTRUCT ps;
    HDC dc = BeginPaint(hwnd, &ps);
    RECT rc; GetClientRect(hwnd, &rc);

    HDC mem = CreateCompatibleDC(dc);
    HBITMAP bmp = CreateCompatibleBitmap(dc, rc.right, rc.bottom);
    HGDIOBJ old = SelectObject(mem, bmp);

    FillRect(mem, &rc, m_background);
    drawEverything(mem);                                  // all drawing goes to the memory DC

    BitBlt(dc, 0, 0, rc.right, rc.bottom, mem, 0, 0, SRCCOPY);   // one copy to the screen
    SelectObject(mem, old);
    DeleteObject(bmp);
    DeleteDC(mem);
    EndPaint(hwnd, &ps);
    return 0;
}

Creating the bitmap on every paint is fine for small windows; for large ones, keep it between paints and re-create it only when the window becomes larger than the bitmap.

The buffered-paint API

Windows has this pattern built in, with the bitmap cached for you:

C++
BufferedPaintInit();                                         // once, at start-up (uxtheme.h, uxtheme.lib)

PAINTSTRUCT ps;
HDC dc = BeginPaint(hwnd, &ps);
HDC mem = nullptr;
HPAINTBUFFER buffer = BeginBufferedPaint(dc, &ps.rcPaint, BPBF_COMPATIBLEBITMAP, nullptr, &mem);
if (buffer)
{
    drawEverything(mem);
    EndBufferedPaint(buffer, TRUE);                          // TRUE: copy to the screen
}
EndPaint(hwnd, &ps);

It buffers only rcPaint, the area that actually needs painting.

Step 3: paint less

Two habits make painting cheaper and smoother:

  • Invalidate precisely: when one item changes, invalidate its rectangle, not the whole window.
  • Skip what is outside rcPaint: test each item's rectangle against it (IntersectRect) and do not draw items that do not intersect. A list of 10 000 rows then draws only the 30 that are visible and changed.

Scrolling

To scroll content up by 40 pixels, there is no need to redraw everything: the window can move the existing pixels and repaint only the strip that became visible:

C++
ScrollWindowEx(hwnd, 0, -40, nullptr, nullptr, nullptr, nullptr, SW_INVALIDATE);   // move pixels, invalidate the new strip
UpdateWindow(hwnd);

Combined with scroll bars (SetScrollInfo, WM_VSCROLL), this is how long documents scroll smoothly even with GDI. Working out exactly which strip needs repainting after a scroll is the practice.

When GDI is not enough

GDI has no antialiasing (jagged diagonal lines and circles), no transparency in most operations, and runs mostly on the CPU. For anything more than simple controls and text, use Direct2D (lesson 4.02), which draws on the GPU with antialiasing and is flicker-free by design.
