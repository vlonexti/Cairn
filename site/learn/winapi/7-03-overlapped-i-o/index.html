Overlapped I/O

lesson 7.033 of 6 in milestone 75 min1 practice task

Reading and writing without waiting - opening files with FILE_FLAG_OVERLAPPED, the OVERLAPPED structure and its 64-bit offset, ERROR_IO_PENDING and operations that finish at once, waiting with events and GetOverlappedResult, I/O completion ports for many operations, cancellation, and keeping buffers alive.

Why not just use a thread?

A blocking ReadFile stops its thread until the data arrives. For one file, a worker thread (lesson 5.04) is fine. A program with hundreds of files or sockets in flight cannot have a thread each. Overlapped I/O starts an operation, returns at once, and tells you later when it finished, so a few threads can keep many operations going. It is how high-performance Windows servers, and the pipes of the Processes and Communication course, work.

Starting an operation

C++
HANDLE file{ CreateFileW(path, GENERIC_READ, FILE_SHARE_READ, nullptr, OPEN_EXISTING,
                         FILE_FLAG_OVERLAPPED, nullptr) };

OVERLAPPED ov{};                                  // must be zeroed
ov.Offset     = static_cast<DWORD>(position);     // low 32 bits of the file position
ov.OffsetHigh = static_cast<DWORD>(position >> 32);
ov.hEvent     = CreateEventW(nullptr, TRUE, FALSE, nullptr);

if (!ReadFile(file, buffer, size, nullptr, &ov))
{
    if (GetLastError() != ERROR_IO_PENDING) { /* a real failure */ }
    // otherwise: it is running; buffer and ov must stay alive until it finishes
}
  • With an overlapped handle there is no current file position: every operation states its offset in the OVERLAPPED, split into two 32-bit halves.
  • ReadFile returning FALSE with ERROR_IO_PENDING means started, not failed.
  • It may also return TRUE: the operation completed at once (cached data). Your code must handle both paths.
  • Reading at or past the end of the file fails with ERROR_HANDLE_EOF.

Waiting for one: GetOverlappedResult

C++
DWORD transferred{ 0 };
if (GetOverlappedResult(file, &ov, &transferred, TRUE))      // TRUE: wait for it
    process(buffer, transferred);

Each operation can have its own event in hEvent, and WaitForMultipleObjects can wait for up to 64 of them. Beyond that, use a completion port.

Many at once: I/O completion ports

An I/O completion port is a queue the system puts a completion packet on whenever an operation on an associated handle finishes:

C++
HANDLE port{ CreateIoCompletionPort(INVALID_HANDLE_VALUE, nullptr, 0, 0) };   // make the port
CreateIoCompletionPort(file, port, /*key*/ 1, 0);                              // associate a handle

// start several reads at different offsets ...

for (;;)
{
    DWORD bytes{ 0 };
    ULONG_PTR key{ 0 };
    OVERLAPPED* done{ nullptr };
    BOOL ok{ GetQueuedCompletionStatus(port, &bytes, &key, &done, INFINITE) };
    // 'done' tells you which operation finished (put OVERLAPPED inside your own struct to find its data);
    // ok == FALSE with done != nullptr: that operation failed (GetLastError says why)
}
  • Completions arrive in the order operations finish, not the order they started. Reads of chunks 3, 1 and 2 may complete as 2, 3, 1: keep track by offset (practice 7.03 does this).
  • A few worker threads calling GetQueuedCompletionStatus on one port share the work; the port limits how many run at once.
  • PostQueuedCompletionStatus puts your own packet in the queue, the usual way to tell workers to stop.
  • An operation that completes at once still queues a packet, unless you opt out with SetFileCompletionNotificationModes(file, FILE_SKIP_COMPLETION_PORT_ON_SUCCESS) and handle the TRUE return yourself.

Cancelling and lifetimes

CancelIoEx(file, &ov) cancels one operation (or all of the handle's with nullptr). A cancelled operation still completes, with ERROR_OPERATION_ABORTED. Until its completion arrives, the operation may still write into its buffer and OVERLAPPED: freeing them earlier, for example by letting a stack variable go out of scope, corrupts memory. Track every operation in flight, and free its memory only when its completion has been seen.
