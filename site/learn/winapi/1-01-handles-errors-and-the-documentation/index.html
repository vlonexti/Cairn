Handles, Errors and the Documentation

lesson 1.011 of 5 in milestone 15 min1 practice task

The Win32 API is thousands of C functions with their own conventions. This lesson explains handles, the Windows type names, how functions report errors through return values and GetLastError, turning error codes into messages, and how to read the documentation.

A C API for everything

The Win32 API (or Windows API) is how every Windows program talks to the system: windows, files, processes, threads, the registry, the clipboard. It is a C interface, so it works from C, C++, Rust, C# and anything else that can call C functions. It has been extended for thirty years and is still how Windows itself is built.

Everything comes from one header:

C++
#define WIN32_LEAN_AND_MEAN     // leave out rarely used parts, compiles faster
#define NOMINMAX                // stop windows.h from defining min and max macros
#include <windows.h>

NOMINMAX matters in C++: without it, std::min and std::max collide with macros of the same name and produce baffling errors.

The type names

Windows has its own names for types, from a time before standard sized integers:

Windows Meaning Standard C++
BYTE, WORD, DWORD 8, 16, 32-bit unsigned uint8_t, uint16_t, uint32_t
BOOL An int used as true/false (not bool) int
UINT, LONG, ULONGLONG Unsigned int, 32-bit signed, 64-bit unsigned
WPARAM, LPARAM, LRESULT Pointer-sized message parameters and results uintptr_t, intptr_t
WCHAR, LPCWSTR, LPWSTR UTF-16 character, const and mutable string pointers wchar_t, const wchar_t*
HANDLE, HWND, HDC, HINSTANCE Handles (below)

The LP prefix means "long pointer", a leftover from 16-bit Windows; C means const and W means wide (UTF-16).

Handles

A handle is an opaque value that refers to an object the system owns: a window (HWND), a file (HANDLE), a brush (HBRUSH), a module (HMODULE). You never look inside it; you pass it back to functions. Each kind is closed with its own function:

Handle Created by Closed by
File, thread, process, event CreateFileW, CreateThread, CreateEventW ... CloseHandle
Window CreateWindowExW DestroyWindow
GDI objects (pens, brushes, fonts, bitmaps) CreatePen, CreateSolidBrush ... DeleteObject
Device context from GetDC GetDC ReleaseDC
Loaded DLL LoadLibraryW FreeLibrary

Forgetting to close handles is a leak: Task Manager's "Handles" and "GDI objects" columns show it growing. In C++, wrap each handle in a small RAII class (or std::unique_ptr with a custom deleter), so it is closed automatically:

C++
struct HandleCloser { void operator()(HANDLE h) const { if (h && h != INVALID_HANDLE_VALUE) CloseHandle(h); } };
using UniqueHandle = std::unique_ptr<void, HandleCloser>;
UniqueHandle file{ CreateFileW(L"notes.txt", GENERIC_READ, FILE_SHARE_READ, nullptr, OPEN_EXISTING, 0, nullptr) };

Note the trap in that deleter: some functions return nullptr on failure, but CreateFileW returns INVALID_HANDLE_VALUE (-1). Always check the documentation's "Return value" section.

Errors

Most functions report failure in their return value (FALSE, nullptr, INVALID_HANDLE_VALUE) and store a detailed error code for the calling thread, which GetLastError() returns. Call it immediately: any later API call may overwrite it.

C++
HANDLE h = CreateFileW(L"missing.txt", GENERIC_READ, 0, nullptr, OPEN_EXISTING, 0, nullptr);
if (h == INVALID_HANDLE_VALUE)
{
    const DWORD error = GetLastError();          // 2 = ERROR_FILE_NOT_FOUND
    // ...
}

Common codes: 2 file not found, 3 path not found, 5 access denied, 32 sharing violation (another program has the file open), 87 invalid parameter, 183 already exists.

Error codes to messages

FormatMessageW turns a code into the system's text, in the user's language:

C++
std::wstring errorText(DWORD code)
{
    wchar_t* buffer = nullptr;
    const DWORD n = FormatMessageW(FORMAT_MESSAGE_ALLOCATE_BUFFER | FORMAT_MESSAGE_FROM_SYSTEM | FORMAT_MESSAGE_IGNORE_INSERTS,
                                   nullptr, code, 0, reinterpret_cast<wchar_t*>(&buffer), 0, nullptr);
    std::wstring text = n ? std::wstring(buffer, n) : L"Unknown error";
    LocalFree(buffer);
    while (!text.empty() && (text.back() == L'\r' || text.back() == L'\n')) text.pop_back();   // it ends in a line break
    return text;
}

COM-based APIs (lesson 3.02 onwards) return an HRESULT instead: negative means failure (FAILED(hr)), and HRESULT_FROM_WIN32(code) converts a Win32 error into one. The practice decodes both.

Reading the documentation

Every function has a page on Microsoft Learn with the same sections: the syntax (with [in], [out] and [in, optional] on each parameter), return value (what failure looks like and whether GetLastError is set), remarks (the details that matter), and requirements (the header, the library to link, and the minimum Windows version). Read the remarks: they hold most of the surprises.
