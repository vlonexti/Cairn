Threading the search

The search runs on a worker; the UI thread only displays. The tricky part is how results travel:

  • Posting a message per file floods the queue with tens of thousands of messages and the UI stutters.
  • Collect results in a vector protected by a lock (or a work queue, practice 5.04), and post one "new results" message at most every 100 ms. The UI thread swaps the batch out, appends it to the list's model, and calls ListView_SetItemCountEx once.
  • The status bar shows the folder currently being searched, also throttled. The practice writes the throttle.
C++
case WM_APP_RESULTS:
{
    std::vector<Item> batch;
    { std::lock_guard lock{ m_shared.mutex }; batch.swap(m_shared.pending); m_shared.posted = false; }
    m_model.append(std::move(batch));                       // project m03's ResultList, extended with append
    ListView_SetItemCountEx(m_list, m_model.count(), LVSICF_NOINVALIDATEALL | LVSICF_NOSCROLL);
    updateStatus();
    return 0;
}

A new search, closing the window, or the Stop button sets the stop flag and joins the old worker before anything else (with std::jthread, assigning a new thread does this). Never let two searches write into the same results.

Sorting while results arrive

Sorting a list that keeps growing must not make rows jump under the user's mouse. A simple rule: while searching, append in arrival order; when the search finishes (or the user clicks a column), sort once. Selection is kept by id (project m03), so it survives.

Actions on results

  • Enter or double-click: open with the default program (ShellExecuteExW, lesson 5.03).
  • Ctrl+Enter or the context menu's "Show in folder": SHOpenFolderAndSelectItems, or explorer.exe /select,"path" (quoted with practice 5.03's rules).
  • Ctrl+C: copy the selected paths, one per line with CRLF (lesson 5.05).
  • Delete: move to the Recycle Bin with IFileOperation (FOFX_RECYCLEONDELETE), never a permanent delete, and remove the rows.

Speed

FindFirstFileExW with FindExInfoBasic (no short 8.3 names) and FIND_FIRST_EX_LARGE_FETCH is noticeably faster than plain FindFirstFileW. Skipping folders you cannot open (error 5) silently, rather than reporting each one, keeps the search going through protected system folders. For whole-drive searches, real tools read the NTFS change journal or the Windows Search index; walking folders is fast enough for a few hundred thousand files.

Order to build in

  1. Window with the controls and layout; the folder picker.
  2. A search on the UI thread into a plain list: correct results first.
  3. Move it to a worker; post batches; Stop button.
  4. Virtual list view with the model from project m03; sorting and status text.
  5. Actions: open, show in folder, copy, delete to the Recycle Bin.
  6. Settings, high DPI, keyboard navigation everywhere.
