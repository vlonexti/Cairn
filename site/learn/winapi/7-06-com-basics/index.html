COM Basics

lesson 7.066 of 6 in milestone 75 min1 practice task

The object model behind much of the Windows API - initialising COM and apartments, interfaces and IUnknown with QueryInterface, AddRef and Release, creating objects with CoCreateInstance, HRESULTs, ComPtr to manage reference counts, memory COM hands you, and creating a shortcut with IShellLinkW as a complete example.

Why COM

Many Windows features are not plain C functions but COM objects: the file dialogs (lesson 3.02), Direct2D, DirectWrite and WIC (milestone 4), shortcuts, the taskbar, the Windows Runtime underneath WinRT. COM (the Component Object Model) is a binary standard for objects: any language that can call through a table of function pointers can use them, which is why the same objects work from C++, C#, Python and scripting languages.

Initialising

Every thread that uses COM initialises it first and uninitialises it at the end:

C++
HRESULT hr{ CoInitializeEx(nullptr, COINIT_APARTMENTTHREADED) };    // UI threads: a single-threaded apartment
if (FAILED(hr)) return hr;                                           // S_FALSE means "already initialised": still call CoUninitialize
// ... use COM ...
CoUninitialize();

The apartment says how objects may be called across threads: COINIT_APARTMENTTHREADED (STA) for threads with windows, where calls are delivered through the message loop; COINIT_MULTITHREADED (MTA) for worker threads. A thread cannot switch: a second call with the other model fails with RPC_E_CHANGED_MODE.

Interfaces and IUnknown

A COM object is used only through interfaces: tables of functions, each identified by a GUID (an IID). Every interface starts with the three methods of IUnknown:

Method Does
QueryInterface(iid, &ptr) asks the object for another interface; E_NOINTERFACE if it has none
AddRef() adds one to the object's reference count
Release() subtracts one; at zero, the object deletes itself

The rules: every interface pointer you receive (from CoCreateInstance, QueryInterface or an out parameter) has already been AddRefed for you, so you must Release it exactly once. Forgetting leaks the object; releasing twice destroys it while something still uses it. Practice 7.06 implements these rules and the smart pointer that follows them for you.

ComPtr

Nobody calls AddRef and Release by hand in modern code. Microsoft::WRL::ComPtr (in <wrl/client.h>, or winrt::com_ptr and the WIL library's wil::com_ptr) does it automatically:

C++
#include <wrl/client.h>
using Microsoft::WRL::ComPtr;

ComPtr<IShellLinkW> link;
HRESULT hr{ CoCreateInstance(CLSID_ShellLink, nullptr, CLSCTX_INPROC_SERVER, IID_PPV_ARGS(&link)) };
if (FAILED(hr)) return hr;

link->SetPath(LR"(C:\Program Files\Xenon\Xenon.exe)");
link->SetDescription(L"Learn to program");

ComPtr<IPersistFile> file;
hr = link.As(&file);                                     // QueryInterface for IPersistFile
if (SUCCEEDED(hr))
    hr = file->Save(LR"(C:\Users\Public\Desktop\Xenon.lnk)", TRUE);
// both pointers are released automatically here
  • IID_PPV_ARGS(&p) passes the interface's IID and the address of the pointer together, so they can never mismatch.
  • ComPtr copies AddRef, destruction and reassignment Release, .As() is a checked QueryInterface, .Get() gives the raw pointer for a call, and &p (or .ReleaseAndGetAddressOf()) for an out parameter.

Errors and memory

  • COM methods return **HRESULT**s: test with SUCCEEDED and FAILED (lesson 3.03 of Reading Documentation), and remember S_FALSE is a success.
  • Strings and buffers that a COM method allocates for you are freed with CoTaskMemFree (for example the path from IShellItem::GetDisplayName). BSTR strings, used by automation interfaces, are freed with SysFreeString. The method's documentation says which.
