Timers and the Clock

lesson 2.033 of 5 in milestone 25 min1 practice task

Doing things later or repeatedly with SetTimer and WM_TIMER, why timers are not precise, measuring time with QueryPerformanceCounter, the system clock and time zones, and running animation without freezing the interface.

SetTimer

A timer sends WM_TIMER to a window repeatedly:

C++
constexpr UINT_PTR TIMER_BLINK = 1;
SetTimer(hwnd, TIMER_BLINK, 500, nullptr);       // every 500 ms
// ...
case WM_TIMER:
    if (wParam == TIMER_BLINK) { m_caretVisible = !m_caretVisible; invalidateCaret(); }
    return 0;
// ...
KillTimer(hwnd, TIMER_BLINK);                    // e.g. in WM_DESTROY

Calling SetTimer again with the same window and id restarts that timer with the new period. A one-shot "do this in two seconds" is a timer that kills itself in its first WM_TIMER.

Timers are not precise

WM_TIMER is a low-priority message, generated only when the queue has nothing else (like WM_PAINT, lesson 1.04's practice model):

  • The default resolution is about 15.6 ms: a 10 ms timer fires roughly every 15.6 ms.
  • If the program is busy, ticks are combined: after a 2-second pause, a 100 ms timer fires once, not twenty times.
  • So never count ticks to measure time. A countdown that does remaining -= 100 on each tick runs slow; one that checks the real clock is always right.

Measuring time

For measuring durations, use the high-resolution counter:

C++
LARGE_INTEGER frequency, start, now;
QueryPerformanceFrequency(&frequency);        // counts per second, fixed at boot
QueryPerformanceCounter(&start);
// ... work ...
QueryPerformanceCounter(&now);
const double seconds = double(now.QuadPart - start.QuadPart) / double(frequency.QuadPart);

It is monotonic (never jumps backwards) and has sub-microsecond resolution. std::chrono::steady_clock is the portable way to the same counter. To convert counts to milliseconds without overflow or loss of precision, split into whole seconds and the remainder; the practice does exactly that.

GetTickCount64() gives milliseconds since boot at the 15.6 ms resolution: fine for timeouts, too coarse for measuring.

Wall-clock time

The time of day is a different thing: it can jump when the user changes the clock, the computer syncs with a time server, or daylight saving changes.

  • GetSystemTimeAsFileTime gives the current time in UTC as a FILETIME: 100-nanosecond intervals since 1 January 1601.
  • FileTimeToSystemTime breaks it into year, month, day, hour ...; SystemTimeToTzSpecificLocalTime converts UTC to local time.
  • Store and compare times in UTC, and convert to local time only to show them.

Converting between FILETIME and Unix time (seconds since 1970) is a fixed offset: 11 644 473 600 seconds between 1601 and 1970.

Animation

Animating with a timer: on each WM_TIMER, compute the animation's state from the elapsed real time, not from the number of ticks, and invalidate. Then it runs at the right speed whatever the timer actually does:

C++
case WM_TIMER:
{
    const double t = secondsSince(m_animStart);
    m_offset = easeOut(std::min(t / 0.25, 1.0)) * m_distance;
    if (t >= 0.25) KillTimer(hwnd, TIMER_ANIM);
    InvalidateRect(hwnd, nullptr, FALSE);
    return 0;
}

For smooth animation at the display's refresh rate, draw with Direct2D (milestone 4) and use DwmFlush or the swap chain's frame timing rather than WM_TIMER.

Never block the loop

Sleep(2000) in a window procedure freezes the whole window for two seconds: no painting, no input, and after about five seconds Windows marks it "Not responding". Anything that takes time goes to a timer (if it can be split into small steps) or a worker thread (lesson 5.04).
