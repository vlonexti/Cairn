A Property Inspector

lesson 5.033 of 4 in milestone 55 min1 practice task

An inspector shows and edits the properties of whatever is selected. Writing one widget call per field for every type gets tedious; describing each type's fields once, as data, lets one function draw an inspector for anything. This lesson builds that property table, handles editing several selected objects at once, and shows "mixed" values.

By hand first

C++
void inspect(Light& l)
{
    ImGui::DragFloat3("Position", &l.pos.x, 0.1f);
    ImGui::ColorEdit3("Colour", &l.color.x);
    ImGui::SliderFloat("Intensity", &l.intensity, 0.0f, 100.0f, "%.1f", ImGuiSliderFlags_Logarithmic);
    ImGui::Checkbox("Casts shadows", &l.shadows);
}

Perfectly fine for three types. With forty component types, and the same fields needing undo, saving and copy-paste, a description of the fields pays off.

Describing fields as data

C++
enum class Kind { Float, Int, Bool, Color3, Vec3, String };

struct Field
{
    const char* name;
    Kind kind;
    std::size_t offset;       // where the field is inside the object (offsetof)
    float min = 0, max = 0;   // for sliders; 0, 0 means "a drag with no limits"
};

static const Field lightFields[] = {
    { "Position",      Kind::Vec3,   offsetof(Light, pos) },
    { "Colour",        Kind::Color3, offsetof(Light, color) },
    { "Intensity",     Kind::Float,  offsetof(Light, intensity), 0.0f, 100.0f },
    { "Casts shadows", Kind::Bool,   offsetof(Light, shadows) },
};

One function then draws any object described this way:

C++
bool inspect(void* object, std::span<const Field> fields)
{
    bool changed = false;
    for (const Field& f : fields)
    {
        void* p = static_cast<char*>(object) + f.offset;
        switch (f.kind)
        {
        case Kind::Float:  changed |= f.max > f.min ? ImGui::SliderFloat(f.name, (float*)p, f.min, f.max) : ImGui::DragFloat(f.name, (float*)p, 0.1f); break;
        case Kind::Int:    changed |= ImGui::DragInt(f.name, (int*)p); break;
        case Kind::Bool:   changed |= ImGui::Checkbox(f.name, (bool*)p); break;
        case Kind::Color3: changed |= ImGui::ColorEdit3(f.name, (float*)p); break;
        case Kind::Vec3:   changed |= ImGui::DragFloat3(f.name, (float*)p, 0.1f); break;
        case Kind::String: changed |= ImGui::InputText(f.name, (std::string*)p); break;
        }
    }
    return changed;
}

The same table drives saving (write each field by name), loading, copy and paste, and undo (record which field changed and its old value). That is a small reflection system; big engines generate these tables from their source code.

offsetof is only guaranteed for standard-layout types (plain structs without virtual functions or mixed access); keep component data like that.

Editing several objects at once

When the user selects five lights and changes the intensity, all five should change. Show each field once:

  • if all selected objects have the same value, show it normally;
  • if they differ, show it as mixed (ImGui's ImGuiItemFlags_MixedValue draws a dash in a checkbox, and you can display "--" in a number field);
  • when the user edits it, write the new value to every selected object.

For drags, the most useful behaviour is often relative: dragging position by +2 moves every object by +2, keeping their arrangement. The practice computes the shown values for a multi-selection.

Common mistakes

Editing only the first selected object

Users expect the change to apply to everything selected.

Using offsetof on a class with virtual functions

It is not guaranteed to work. Keep inspectable data in plain structs.
