Immediate Mode versus Retained Mode

lesson 1.011 of 6 in milestone 15 min1 practice task

Most user-interface toolkits keep a tree of widget objects that you create once and update. Dear ImGui does the opposite - you describe the whole interface again every frame, as ordinary code, and it draws it. This lesson explains the idea, why it suits tools and debug views so well, and where its limits are.

Two ways to build an interface

Retained mode is what Windows Forms, Qt, HTML and Unity's UI Toolkit do. You create objects once - a window, a slider, a label - and the toolkit keeps them. To change what the user sees, you change the objects; to react to the user, you register callbacks:

C++
// retained mode (pseudo-code)
auto* slider = new Slider(window, "Speed", 0.0f, 10.0f);
slider->setValue(player.speed);
slider->onChanged([&](float v) { player.speed = v; });   // keep the copy and the real value in sync

There are now two copies of the speed: player.speed and the slider's value. Keeping them in sync is your job, and most UI bugs live in that gap.

Immediate mode is what Dear ImGui does. There are no widget objects for you to keep. Every frame, you call functions that describe the interface as it should be right now, and each call returns what the user did:

C++
// immediate mode: this runs every frame
ImGui::Begin("Player");
ImGui::SliderFloat("Speed", &player.speed, 0.0f, 10.0f);   // shows player.speed, writes to it if dragged
if (ImGui::Button("Reset")) player.speed = 4.0f;          // true on the frame it was clicked
ImGui::End();

The slider reads player.speed directly and writes to it directly. There is no second copy, no callback, no "update the UI when the data changes". If the game changes the speed, the slider shows it next frame because it is drawn from the data again.

Why tools love it

  • Interfaces are just code. Loops and ifs produce lists and optional parts: for (auto& enemy : enemies) ImGui::Text(...). When an enemy dies, it disappears from the list with no extra work.
  • Fast to write. A debug window for a new system is often ten lines, written in the system's own file.
  • Always in sync with the data, because it is drawn from it.
  • Drops into any engine. ImGui only produces triangles and textures to draw; a small back end feeds them to DirectX, OpenGL, Vulkan or Metal, and passes mouse and keyboard input in.

That is why game studios use it for editors, debug overlays, profilers and in-house tools: those are exactly the interfaces where speed of writing matters more than polish.

But ImGui does keep some state

"Immediate mode" describes the API, not the library's insides. ImGui remembers what it must between frames: window positions and sizes, which tree nodes are open, which widget is being dragged, scroll positions, text being edited. It finds that state by each widget's ID, which it computes from the label you pass (lesson 1.05). That is the one rule you have to learn early.

It also means the cost is real: building the UI runs your code every frame. For tools, that is a few hundred microseconds; for a game's main menu shown to players, a retained toolkit or a hand-made UI is often a better fit (lesson 6.03).

Where immediate mode is not the best choice

  • Player-facing game UI with animation, art direction and controller navigation everywhere.
  • Large text documents or anything needing rich text layout.
  • Accessibility: screen readers and similar tools rely on a widget tree that ImGui does not expose.

For the tools this course builds - inspectors, editors, profilers, consoles - it is excellent.

Common mistakes

Copying values into the UI and back

Pass pointers to the real data. SliderFloat("Speed", &player.speed, ...) needs no copy.

Trying to store widget objects

There are none to store. If something should appear, call its function this frame; if not, don't.
