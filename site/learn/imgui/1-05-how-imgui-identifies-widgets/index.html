How ImGui Identifies Widgets

lesson 1.055 of 6 in milestone 15 min1 practice task

ImGui remembers a widget between frames by its ID, a number computed from the widget's label and the ID stack. Two widgets with the same ID in the same place behave as one, which is the classic "my second button does not work" bug. This lesson explains IDs, the ## and ### label rules, and PushID.

The problem

C++
for (Stone& stone : stones)
{
    ImGui::Text("%s", stone.name.c_str());
    ImGui::SameLine();
    if (ImGui::Button("Delete")) remove(stone);   // only the first one works!
}

Every button has the label "Delete". ImGui computes each widget's ID from its label, so all the buttons get the same ID. When you press the third one, ImGui thinks the widget with that ID is active, but the first button with that ID claims it. The result: only the first button works, or the wrong one reacts.

How an ID is made

An ID is a 32-bit hash. ImGui keeps an ID stack: a stack of seed values. Each widget's ID is the hash of its label, seeded with the value on top of the stack. Every window pushes its own seed (from its name), so a "Delete" button in window A and one in window B already differ.

Output
ID = hash(label, seed = top of the ID stack)

To make widgets in a loop differ, push something unique onto the stack around each iteration:

C++
for (int i = 0; i < (int)stones.size(); ++i)
{
    ImGui::PushID(i);                            // changes the seed for everything inside
    ImGui::Text("%s", stones[i].name.c_str());
    ImGui::SameLine();
    if (ImGui::Button("Delete")) toDelete = i;   // now each has a different ID
    ImGui::PopID();
}

PushID accepts an integer, a string, or a pointer (PushID(&stone) is a good choice: the stone's address is unique and stable). Every PushID needs a PopID.

Label tricks: ## and

Labels do two jobs: the text shown and the source of the ID. Two markers separate them:

  • ##: everything after it is part of the ID but not shown. "Delete##3" shows "Delete" and hashes the whole string. "##speed" shows nothing (a slider with no label).
  • ###: only the part from ### onward is used for the ID. "Score: 120###score" shows "Score: 120" and hashes just "###score", so the ID stays the same when the score changes. Useful for window titles that show changing text: Begin("Level 3 - 12 enemies###LevelWindow") keeps its position and size even though the title changes.
Label Shown Hashed for the ID
"Delete" Delete Delete
"Delete##3" Delete Delete##3
"##speed" (nothing) ##speed
"HP: 87###hp" HP: 87 ###hp

The practice has you implement exactly this table, plus the stack, with a simple hash.

When IDs matter

IDs are how ImGui finds a widget's remembered state: whether it is hot (hovered) or active (being clicked or dragged), whether a tree node is open, a text box's cursor, a window's position. If two widgets share an ID, they share that state. If a widget's ID changes every frame (say its label contains a timer), it loses its state every frame: a tree node never stays open, a drag stops immediately.

Debugging IDs

  • Tools, ID Stack Tool in the demo window, or ImGui::ShowIDStackToolWindow(), shows the ID stack under the mouse.
  • Recent versions of ImGui detect duplicate IDs in the same window and draw a warning over them (io.ConfigDebugHighlightIdConflicts, on by default in debug builds).

Common mistakes

Buttons with the same label in a loop

Wrap each iteration in PushID / PopID, or add ## and a unique suffix.

A label that changes every frame

The widget gets a new ID each frame and forgets its state. Use ### with a fixed part.

Forgetting PopID

Every widget after it gets a different ID than intended. ImGui asserts at the end of the window.
