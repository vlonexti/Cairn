Undo and Redo for Tools

lesson 5.044 of 4 in milestone 55 min1 practice task

No one trusts an editor without undo. This lesson builds the classic command pattern undo stack, explains why redo history is cleared by a new edit, shows how to merge the sixty small changes of one drag into one step using ImGui's item queries, and how to mark a document as saved.

Commands

Every change to the document is an object that knows how to do and undo itself:

C++
struct Change
{
    virtual ~Change() = default;
    virtual void apply(Level& level) = 0;
    virtual void revert(Level& level) = 0;
    virtual std::string label() const = 0;     // shown in Edit > Undo "Move rock"
};

struct SetIntensity final : Change
{
    int lightId; float before, after;
    void apply(Level& l) override  { l.light(lightId).intensity = after; }
    void revert(Level& l) override { l.light(lightId).intensity = before; }
    std::string label() const override { return "Change intensity"; }
};

Two stacks

Output
undo stack:  [create rock] [move rock] [change colour]     <- top: the most recent change
redo stack:  []
  • Do a change: apply it, push it on the undo stack, and clear the redo stack.
  • Undo: pop from the undo stack, revert it, push it on the redo stack.
  • Redo: pop from the redo stack, apply it, push it back on the undo stack.

Why clear redo on a new change? After undoing "change colour", the redo stack holds it. If the user now moves a tree, the colour change belonged to a history that no longer exists: redoing it on top of the new state could make no sense. Every editor you know behaves this way.

One drag, one undo step

A slider drag changes the value every frame. Recording each frame would make one drag sixty undo steps. Use ImGui's item queries (lesson 2.01):

C++
static float before;
if (ImGui::IsItemActivated()) before = light.intensity;            // the drag started: remember the old value
ImGui::SliderFloat("Intensity", &light.intensity, 0, 100);          // edits live, for immediate feedback
if (ImGui::IsItemDeactivatedAfterEdit())                            // the drag ended with a change
    undo.record(std::make_unique<SetIntensity>(light.id, before, light.intensity));   // record, do not re-apply

Note record, not apply: the value is already set. Another approach is merging: when a new change has the same target as the top of the stack and arrives within a short time, combine them into one (keeping the oldest before and the newest after). Text editors use merging for typing.

Saved and dirty

The document is dirty (has unsaved changes) when the undo stack differs from what it was at the last save. Remember a saved marker: the size of the undo stack at save time (or a pointer to the top change).

  • After saving, the marker equals the current position: not dirty.
  • Undoing back to the saved point makes it clean again, which a simple dirty = true flag cannot do.
  • If a new change clears redo history that included the saved point, the saved state can never be reached again: always dirty until saved.

The practice builds the whole stack with labels, the saved marker and a limit on how many steps are kept.

Groups

"Delete 40 selected objects" is 40 changes but one action for the user. Put several changes into a group that applies them in order and reverts them in reverse order, and push the group as one step.

Common mistakes

Forgetting to clear redo after a new change

Redo then applies a change from an abandoned history.

A change that stores pointers to objects

Deleting and undoing recreates the object at a new address. Store ids.

Reverting a group in the same order it was applied

Later changes may depend on earlier ones. Revert in reverse.
