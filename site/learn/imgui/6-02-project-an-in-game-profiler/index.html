Project: An In-Game Profiler

lesson 6.022 of 3 in milestone 65 min1 practice task

Build a profiler that runs inside your game - scoped timers you sprinkle through the code, a per-frame tree of where the time went with total and self times, a frame-time graph with the budget line, and a flame view drawn with the draw list. This lesson covers measuring, collecting, aggregating and showing the data.

Measuring with scopes

A zone is a named span of time. Mark zones with a small RAII object that records a begin event when constructed and an end event when destroyed:

C++
class Zone
{
public:
    explicit Zone(const char* name) : m_name{ name } { Profiler::get().begin(m_name, now()); }
    ~Zone() { Profiler::get().end(m_name, now()); }
private:
    const char* m_name;
};
// Two steps, so __LINE__ is replaced by the number before the names are joined.
#define PROFILE_JOIN2(a, b) a##b
#define PROFILE_JOIN(a, b) PROFILE_JOIN2(a, b)
#define PROFILE_ZONE(name) Zone PROFILE_JOIN(profileZone, __LINE__){ name }

void updateEnemies()
{
    PROFILE_ZONE("updateEnemies");
    for (auto& e : enemies) { PROFILE_ZONE("think"); e.think(); }
}

now() should be a high-resolution clock: QueryPerformanceCounter on Windows, or std::chrono::steady_clock. The string is a literal, so storing the pointer is fine and cheap.

Zones nest naturally: "think" begins and ends inside "updateEnemies". Recording only begin and end events, in order, captures the whole tree.

From events to a tree

At the end of a frame, the events of that frame form a list like:

Output
begin frame 0      begin update 10    begin physics 12   end physics 40
begin think 41     end think 52       begin think 52     end think 60    end update 61
begin render 61    end render 150     end frame 152

Walk them with a stack: a begin pushes a new node as a child of the top of the stack; an end pops it and stores its duration. Each node's total time is its own duration; its self time is the total minus its children's totals: the time spent in that zone's own code. Zones with the same name under the same parent (the two "think" zones) are usually merged into one row with a call count. The practice builds exactly this.

Output
frame          152.0 ms   self 12.0
  update        51.0      self 4.0
    physics     28.0
    think       19.0  (2 calls)
  render        89.0

Showing it

  • A table tree (lessons 3.03 and 3.04): name, total, self, calls, with tree nodes in the first column and sorting by total or self.
  • A frame graph (lesson 5.01): the last few hundred frame times with the 16.6 ms line; clicking a bar pauses on that frame to inspect its tree.
  • A flame view: each zone as a bar whose x position and width are its start and duration in the frame, and whose row is its nesting depth. Draw it with AddRectFilled and AddText, coloured by name (the golden-ratio hue trick from lesson 2.04 keeps colours stable per name). Hover a bar for a tooltip with the exact numbers.

Threads

Zones on other threads (loading, audio, job workers) need their own event lists: give each thread its own buffer (thread_local) and merge them at the end of the frame, showing one lane per thread in the flame view.

Keep the profiler cheap

  • Two clock reads and two small writes per zone: keep zones out of loops that run millions of times, or profile a sample of them.
  • No memory allocation per event: pre-allocate the event buffer.
  • Compile zones out of shipping builds: #define PROFILE_ZONE(name) to nothing (lesson 6.03).

Professional tools such as Tracy and Optick follow this design and add network streaming, GPU timing and much more; after this project you will know how to read them.
