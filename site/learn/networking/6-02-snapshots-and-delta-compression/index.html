Snapshots and Delta Compression

lesson 6.022 of 5 in milestone 65 min1 practice task

Sending the world to clients efficiently - what goes in a snapshot, quantising floats into a few bits, sending only what changed against a baseline the client has acknowledged, change masks, and what happens when packets are lost.

A snapshot

A snapshot is the server's world state at one tick, as one client needs to see it: for each relevant entity, an id and the fields that matter (position, angle, health, animation). Sending it all, every time, is simple and robust: each snapshot stands alone, so a lost one does not matter. It is also big. Thirty players with 20 bytes each is 600 bytes, times 60 snapshots a second, times 30 clients: over 8 Mbit/s of upload for one server.

Two techniques shrink it dramatically.

Quantisation

A float is 4 bytes with far more precision than a game needs. If the map is 0 to 1 000 units wide, storing the position as a 16-bit integer gives steps of 1 000 / 65 535 ≈ 0.015 units, invisible on screen:

C++
std::uint16_t quantize(float v, float min, float max)
{
    const float t{ (std::clamp(v, min, max) - min) / (max - min) };
    return static_cast<std::uint16_t>(std::lround(t * 65535.0f));
}

float dequantize(std::uint16_t q, float min, float max)
{
    return min + (max - min) * (q / 65535.0f);
}

The same idea everywhere: an angle in 8 or 10 bits, health as a byte, a boolean as a single bit. The error is at most half a step. Crucially, the server simulates with the quantised values too (or rounds its state the same way), so client and server agree exactly on what was sent.

Delta compression

Most of the world does not change from one snapshot to the next: a player standing still, a door that is closed. So send only the difference against a snapshot the client already has:

  • The client acknowledges the snapshots it receives (milestone 5's acks).
  • The server keeps the last few dozen snapshots per client and encodes each new one against the latest one the client acknowledged, the baseline.
  • For each entity it writes the id and a change mask, one bit per field, followed by only the fields whose bit is set. Unchanged entities are left out entirely; new entities have every bit set; removed ones get a "removed" marker.

The client reconstructs the new snapshot by copying the baseline and applying the changes. A typical scene shrinks from hundreds of bytes to tens.

When packets are lost

Delta compression against an acknowledged baseline stays correct under loss: if snapshots 101 to 103 are lost, the server simply keeps encoding against 100 (the last one acknowledged) until a newer one is acknowledged. Deltas grow a little while packets are being lost, and shrink again once acks get through.

What must never happen is encoding against a snapshot the client might not have. Then the client applies changes to the wrong base and its world is silently wrong. If there is no usable baseline (a new client, or a baseline too old to keep), send a full snapshot.
