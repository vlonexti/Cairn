Serving Many Connections

lesson 2.044 of 5 in milestone 25 min1 practice task

Moving beyond one client at a time - thread per connection and its limits, non-blocking sockets and WSAEWOULDBLOCK, an event loop built on select or WSAPoll, per-connection buffers for reading and writing, and when to reach for I/O completion ports.

The problem

Lesson 2.02's server serves one client at a time: while it waits in recv for client A, client B is stuck in the accept queue. There are two classic ways out.

Thread per connection

Accept, then hand each client socket to a new thread running blocking code. Simple, and fine for dozens of clients. With thousands, the threads' memory (each has a stack) and context switching dominate, and shared state needs locks everywhere.

Non-blocking sockets and an event loop

A socket can be put in non-blocking mode:

C++
u_long nonBlocking{ 1 };
ioctlsocket(s, FIONBIO, &nonBlocking);

Then recv, send, accept and connect never wait. If they cannot do anything right now, they fail with WSAEWOULDBLOCK, which is not an error, just "nothing yet". On its own that turns waiting into busy polling; combined with a call that waits until any socket is ready, it gives an efficient single-threaded server: an event loop.

C++
std::vector<WSAPOLLFD> fds;                          // the listener, then one entry per client
for (;;)
{
    WSAPoll(fds.data(), static_cast<ULONG>(fds.size()), 1000);   // wait up to 1 s for anything
    for (WSAPOLLFD& f : fds)
    {
        if (f.revents & POLLRDNORM) { /* readable: accept (listener) or recv (client) */ }
        if (f.revents & POLLWRNORM) { /* writable: send queued data */ }
        if (f.revents & (POLLERR | POLLHUP)) { /* close it */ }
    }
}

select is the older, more widespread form of the same idea (on Windows it handles 64 sockets per call unless you raise FD_SETSIZE); WSAPoll is the Windows version of Unix's poll.

Per-connection state

In an event loop no function can wait for "the rest of the message", so each connection keeps its own state:

  • an input buffer: bytes received so far; after each recv, take out every complete message and handle it, leaving any partial one;
  • an output queue: bytes waiting to be sent. Never call send in a loop until everything goes: when it returns WSAEWOULDBLOCK or sends only part, keep the rest and ask to be told when the socket is writable (POLLWRNORM), then send more.
Text
recv -> append to input -> extract messages -> handle -> append replies to output
writable -> send as much of output as the socket takes -> keep the rest

The output queue also needs a limit: a client that never reads would otherwise make the server buffer replies for ever. When a queue grows too large, stop reading from that client, or disconnect it.

Fairness

One busy client must not starve the others. Read a bounded amount per client per loop iteration, handle a bounded number of messages, then move on. The same applies to expensive work: an event loop must never do anything slow (a disk read, a heavy computation) inline, or every client waits. Push slow work to worker threads and post the result back to the loop.

Scaling further

For thousands of busy connections on Windows, I/O completion ports (the IPC course, lesson 2.05) are the high-performance model: overlapped WSARecv/WSASend on every socket, completions collected by a few worker threads. Libraries such as Asio (C++), libuv (behind Node.js) and the Windows thread pool hide most of the detail.
