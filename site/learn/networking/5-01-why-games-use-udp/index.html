Why Games Use UDP

lesson 5.011 of 5 in milestone 55 min1 practice task

Why real-time games build their own protocol on UDP instead of using TCP - head-of-line blocking, the newest state making old data worthless - what a game protocol adds on top, virtual connections with timeouts, and testing under simulated loss and delay.

TCP's promise is the problem

TCP delivers every byte, in order. For a web page that is exactly right. For a game sending the player positions 30 or 60 times a second, it is a trap:

  • When one segment is lost, every later byte waits until the lost one is retransmitted, at least one round trip later, often more. Positions that arrived perfectly well sit in the receive buffer, unusable. This is head-of-line blocking, and it turns a single lost packet into a visible freeze.
  • The data being waited for is already out of date. By the time the position from 100 ms ago is resent, three newer positions exist. Nobody wants the old one.
  • TCP also slows down on loss (congestion control) and may combine small writes (Nagle's algorithm, disabled with TCP_NODELAY), both of which add delay a game would rather not have.

UDP delivers each datagram independently: some are lost, some are duplicated, some arrive out of order, but nothing waits for anything else. A game takes that and adds only what it needs.

What a game protocol adds

The key idea: most data is unreliable and newest-wins (positions, inputs, animation state), and only some messages need to be reliable. A game protocol lets each kind travel the way it needs.

A virtual connection

UDP has no connections, so the protocol makes its own:

  • Every packet starts with a protocol id (a fixed number such as a hash of the game name and version). Packets without it are dropped at once: stray traffic, port scanners, an old version of the game.
  • A connection is just "the address and port I hear from". The server keeps a table keyed by address and port.
  • Connecting uses a small handshake, often with a random salt from each side, so a forged source address cannot create a connection. Real games add encryption and a token from a login server.
  • Both sides send something at a steady rate (even an empty packet), and a connection that has heard nothing for a few seconds is timed out. There is no FIN: silence is how a UDP connection ends.

Testing on a bad network

A protocol that works on 127.0.0.1 with no loss proves nothing. Test with simulated conditions:

  • Latency: hold each packet for, say, 100 ms before delivering it.
  • Jitter: vary that delay, which also reorders packets.
  • Loss: drop a share of packets, 1 % to 10 % (and sometimes bursts).
  • Duplication: occasionally deliver a packet twice.

You can put a simulator inside your own code between "send" and the socket, which makes the tests repeatable, or use tools such as clumsy on Windows or tc netem on Linux to degrade real traffic. Make the simulator deterministic (a fixed pattern or a seeded generator), so a failure can be repeated.
