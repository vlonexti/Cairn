The Authoritative Server

lesson 6.011 of 5 in milestone 65 min1 practice task

How multiplayer games are organised - the server owns the truth and clients send only inputs, why that is the basis of fair play, the fixed tick with an accumulator, tick numbers as the shared clock, and choosing tick and send rates.

Who decides what happened?

In a multiplayer game, several machines each run a copy of the world, and their copies drift apart: messages take time, packets are lost, clocks differ. Someone has to decide what really happened. Almost every modern action game uses an authoritative server:

  • The server runs the real simulation. Its state is the truth.
  • Clients send only their inputs ("move left, jump, fire at this angle"), never results ("I am now here", "I hit him for 100").
  • The server applies the inputs, simulates, and sends the resulting state back to every client, which shows it.

This is also the foundation of fair play: a modified client can send odd inputs, but it cannot declare that it teleported or that its shot hit. The server validates every input: movement is limited to what the rules allow (a move vector longer than 1 is clamped, not trusted), a player cannot fire faster than the weapon allows, and actions are checked against the server's own state.

The alternatives have their places: peer-to-peer lockstep (every machine runs the same deterministic simulation from everyone's inputs, common in strategy games with thousands of units) and client authority for casual cooperative games where cheating does not matter. This milestone builds the server-authoritative model.

The tick

The server simulates in fixed steps called ticks, for example 60 per second (a step of 16.67 ms) or 20 to 30 for slower games. Fixed steps make physics stable and the simulation reproducible: the same inputs give the same results.

Real time does not arrive in neat steps, so a loop accumulates elapsed time and runs as many ticks as fit:

C++
accumulator += elapsed;
while (accumulator >= step)
{
    simulateOneTick();
    accumulator -= step;
}
alpha = accumulator / step;   // how far we are towards the next tick, for smooth drawing

If the machine falls far behind (a long pause, a debugger stop), running hundreds of ticks to catch up makes things worse: each slow frame causes even more ticks the next frame. Cap the ticks per frame and drop the rest of the backlog.

Clients run the same loop, drawing with alpha to blend between the last two simulated states, so motion is smooth on a 144 Hz screen while the simulation runs at 60.

Tick numbers are the clock

Every snapshot the server sends carries its tick number, and every input a client sends carries a sequence number (and often the tick it was made for). These numbers, not wall-clock times, are how the two sides talk about time:

  • "This snapshot is the world at tick 4 512."
  • "The last input of yours I applied was number 917."
  • "When you fired, you were seeing the world at tick 4 505." (lesson 6.05)

Tick rate and send rate

The server need not send a snapshot every tick. Typical choices: simulate at 60, send snapshots at 20 to 60, and clients send inputs every tick (often several inputs per packet, for redundancy against loss, as in milestone 5). Higher rates feel more responsive and cost bandwidth and server CPU per player; many games pick 30 or 64 and tune from there.
