UDP Sockets

lesson 2.055 of 5 in milestone 25 min1 practice task

Sending and receiving datagrams - sendto and recvfrom, connected UDP sockets, size limits, coping with loss, duplication and reordering, a request with timeouts and retries, checking who an answer came from, Windows' connection-reset quirk, and broadcast.

Datagrams

A UDP socket sends and receives whole datagrams, each with its own destination:

C++
SOCKET s{ socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP) };

sockaddr_in to{};
to.sin_family = AF_INET;
to.sin_port = htons(9000);
inet_pton(AF_INET, "192.168.1.50", &to.sin_addr);
sendto(s, packet, packetLength, 0, reinterpret_cast<sockaddr*>(&to), sizeof(to));

char buffer[1500];
sockaddr_in from{};
int fromLength{ sizeof(from) };
const int got{ recvfrom(s, buffer, sizeof(buffer), 0, reinterpret_cast<sockaddr*>(&from), &fromLength) };
// `got` bytes from address `from`: exactly one datagram

No listen, no accept, no connection: a server just binds a port and receives datagrams from anyone. Each recvfrom returns exactly one datagram, never part of one and never two. If your buffer is too small, the rest of that datagram is discarded (WSAEMSGSIZE).

A UDP socket can also be connected with connect: no packets are exchanged, but send and recv then go to and come only from that one peer, which is convenient for clients.

Size

A datagram can in theory be 65 507 bytes, but anything larger than the path's MTU is fragmented at the IP level, and losing any fragment loses the whole datagram. Keep datagrams under about 1200 bytes of payload to be safe on almost every path (QUIC uses this limit). Larger data is split by your own protocol (milestone 5).

Loss, duplication and reordering

Every datagram may be lost, may arrive twice, or may arrive after one sent later. Code using UDP must handle all three:

  • Loss: anything that must arrive needs a timeout and a resend (and so an acknowledgement).
  • Duplicates: give each datagram a sequence number and ignore numbers already seen.
  • Reordering: use the sequence numbers to discard stale data or to put things back in order.

On a quiet local network losses are rare, which makes untested UDP code look correct. Test with simulated loss (Windows tools such as clumsy drop and delay packets on purpose).

A request with retries

The simplest reliable pattern over UDP is a query: send a request, wait for the answer, resend if it does not come. DNS works this way:

  1. Send the request, with a random id.
  2. Wait up to a timeout (say 500 ms).
  3. If nothing arrives, resend, doubling the timeout each time, up to a few attempts.
  4. Accept an answer only if it comes from the address and port you sent to and carries your id. Anything else is ignored: a stray packet, a late answer to an earlier attempt, or an attacker trying to slip in a forged reply.

A Windows quirk

When a datagram is sent to a port where nothing listens, the target replies with an ICMP "port unreachable". On Windows, the next recvfrom on your socket then fails with WSAECONNRESET, even though UDP has no connections. A server receiving from many clients must ignore that error (or disable the behaviour with the SIO_UDP_CONNRESET ioctl) instead of treating it as fatal.

Broadcast

A datagram to 255.255.255.255 (or the subnet's broadcast address, lesson 1.02) reaches every device on the local network, after enabling SO_BROADCAST on the socket. Games use this to find servers on a LAN: the client broadcasts "any servers?" and each server answers with its name and port. Routers do not forward broadcasts, so it only works locally; multicast groups extend the idea in a more controlled way.
