Byte Order and Packet Layouts

lesson 2.033 of 5 in milestone 25 min1 practice task

Network byte order is big-endian - htons, htonl and their inverses, writing and reading binary headers field by field, fields smaller than a byte packed into bit fields, why a C++ struct is the wrong tool for a wire format, and the Internet checksum.

Big-endian on the wire

Internet protocols write multi-byte numbers big-endian: most significant byte first. This is network byte order. A port number 7777 (0x1E61) goes on the wire as 1E 61. Your x86 or ARM processor stores it little-endian, as 61 1E. Every number in a protocol header must be converted.

The socket API provides the conversions:

Function Converts
htons 16-bit, host to network
htonl 32-bit, host to network
ntohs, ntohl network to host

That is why lesson 2.02 wrote addr.sin_port = htons(7777): the sockaddr_in structure holds the port in network order. Forgetting the conversion is a classic bug: the server listens on port 24862 (0x611E) instead of 7777.

Writing headers field by field

The portable way to write a binary format is byte by byte, with shifts, which gives the same result on every machine whatever its own byte order:

C++
void put16(std::vector<std::uint8_t>& out, std::uint16_t v)
{
    out.push_back(static_cast<std::uint8_t>(v >> 8));       // big-endian: high byte first
    out.push_back(static_cast<std::uint8_t>(v));
}

std::uint16_t get16(const std::uint8_t* p) { return static_cast<std::uint16_t>((p[0] << 8) | p[1]); }

Your own protocols can choose little-endian (the IPC course did); when you implement a standard protocol, follow its specification, which for internet protocols almost always says big-endian.

Bit fields

Some header fields are smaller than a byte. The first byte of an IPv4 header holds two 4-bit numbers: the version (4) in the high half and the header length in 32-bit words in the low half:

Text
byte 0:  0100 0101   -> version 4, header length 5 words (20 bytes)  = 0x45

Read and write them with shifts and masks:

C++
const int version{ p[0] >> 4 };
const int headerLength{ (p[0] & 0x0F) * 4 };
const std::uint8_t first{ static_cast<std::uint8_t>((4 << 4) | 5) };

TCP's flags (SYN, ACK, FIN...) are single bits of one byte, tested with masks such as flags & 0x02 for SYN.

Why not a struct?

It is tempting to declare a C++ struct matching a header and memcpy or cast the packet to it. Every one of these breaks it:

  • Padding: the compiler may insert bytes between fields to align them.
  • Byte order: the struct's integers are in host order.
  • C++ bit fields: their order within a byte is implementation-defined.
  • Alignment: casting a packet buffer to a struct pointer can read misaligned data, and is an aliasing violation.

Real network code does use structs with #pragma pack(1) and careful conversions, but reading and writing fields explicitly, as above, is clearer and always correct.

The Internet checksum

IPv4, TCP, UDP and ICMP headers carry a 16-bit checksum so that corrupted packets can be detected. It is computed the same way everywhere (RFC 1071):

  1. Treat the data as a sequence of 16-bit big-endian words (pad an odd final byte with a zero).
  2. Add them all up using one's complement addition: whenever the sum overflows 16 bits, add the carry back into the low 16 bits.
  3. The checksum is the bitwise NOT of the result.

To verify, run the same sum over the data including the checksum field: a correct packet gives 0xFFFF before the final NOT (zero after it). It is a weak checksum, catching most single errors but not reordered words; TLS and application-level hashes protect data properly.
