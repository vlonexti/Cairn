Parsing HTTP Messages

lesson 3.022 of 5 in milestone 35 min1 practice task

Reading HTTP from a byte stream - finding the end of the headers, splitting the start line and headers, case-insensitive names, finding the body's length from Content-Length or chunked transfer encoding, and the limits and strictness that keep a parser safe.

In two stages

An HTTP message arrives on a TCP stream in arbitrary chunks (lesson 2.02), so a parser works in two stages:

  1. The head: collect bytes until the first \r\n\r\n. Everything before it is the start line and headers.
  2. The body: decide from the headers how many bytes the body has, and collect exactly that many.

Anything after the end of the body belongs to the next message on the connection.

The start line and headers

Split the head into lines at \r\n. The first line is the request line (METHOD TARGET VERSION, separated by single spaces) or, in a response, the status line (VERSION CODE REASON). Each following line is a header:

Text
Content-Type:   text/plain   ->  name "Content-Type", value "text/plain"
  • The name is everything before the first :. It must not be empty or contain spaces.
  • The value is everything after it, with spaces and tabs trimmed from both ends.
  • Names are case-insensitive: store them in lower case and look them up that way.
  • A header can appear more than once (Set-Cookie often does). For most headers repeats are combined with commas; keep them all and let each use decide.

How long is the body?

The rules, in order:

  1. Responses to HEAD, and 1xx, 204 and 304 responses never have a body.
  2. If Transfer-Encoding: chunked is present, the body is chunked (below).
  3. Otherwise, if Content-Length is present, the body is exactly that many bytes.
  4. Otherwise a request has no body, and a response body runs until the server closes the connection.

A message with both Transfer-Encoding and Content-Length, or with two different Content-Length values, is ambiguous and must be rejected: front-end proxies and back-end servers that resolve such ambiguity differently are the cause of request smuggling attacks.

Chunked transfer encoding

When a server does not know the length in advance (a page generated as it goes), it sends the body in chunks, each preceded by its size in hexadecimal, ending with a zero-size chunk:

Text
4\r\n
Wiki\r\n
6\r\n
pedia \r\n
D\r\n
in\r\n\r\nchunks.\r\n
0\r\n
\r\n

That body is Wikipedia in\r\n\r\nchunks.: 4 + 6 + 13 bytes. Each size line may carry extensions after a ;, which you ignore. After the zero chunk come optional trailer headers and a final empty line.

Limits and strictness

An HTTP parser takes input from anyone on the internet, so it must be strict and bounded:

  • Limit the head (8 KB is common) and the number of headers; reply 431 or close beyond that.
  • Limit the body you will accept; reply 413 Payload Too Large.
  • Reject malformed lines, a Content-Length that is not a plain decimal number, negative or absurd sizes, and the ambiguous combinations above, with 400 Bad Request.
  • Do not "fix" bad input; a lenient parser behind a strict one (or the other way round) is exactly how smuggling works.

For real servers, use a well-tested parser library (llhttp, the one inside Node.js, or your framework's); writing one, as the practice does, teaches what they check and why.
