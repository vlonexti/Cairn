Fragmentation and Bandwidth

lesson 5.055 of 5 in milestone 55 min1 practice task

Keeping packets under the path MTU, why IP fragmentation is avoided, splitting large blocks into fragments and reassembling them with ids, counts and timeouts, budgeting bandwidth per connection, and choosing what to send when it does not all fit.

How big can a packet be?

An Ethernet frame carries 1 500 bytes of IP packet (lesson 1.01). Paths through tunnels, VPNs and mobile networks carry less. If a UDP datagram is too big, IP fragments it, and then:

  • losing any fragment loses the whole datagram, so the loss rate multiplies;
  • some routers and firewalls drop fragments altogether;
  • with IPv6, routers do not fragment at all.

So games keep every datagram under a safe size, typically 1 200 bytes of payload (the same limit QUIC uses), and split large data themselves.

Your own fragments

To send a block larger than one packet (a map, a full snapshot, a file), split it into fragments, each sent in its own packet with a small header:

Field Size Meaning
block id 16 bits which block this belongs to
fragment index 8 bits 0 to count - 1
fragment count 8 bits how many fragments the block has

The receiver keeps a reassembly buffer per block id: which fragments have arrived and their bytes. When all count are there, the block is complete. Rules that make it robust:

  • Check everything: index below count, count above zero, the same count in every fragment of a block, a fragment size within limits. A wrong value is a dropped packet, never an out-of-range write.
  • Ignore duplicates of fragments already present.
  • Time out incomplete blocks, and limit how many are in progress, so a lost fragment or a malicious sender cannot use up memory.
  • If the block must arrive, either resend the missing fragments (using acks) or resend the whole block reliably. A neat scheme is to make each fragment a reliable message.

A bandwidth budget

A connection cannot send as much as it likes: the player's upload may be a few hundred kilobits per second, and a server sends to many players. Decide a budget per connection, for example 256 kbit/s, which at 60 packets a second is about 530 bytes per packet.

When everything does not fit:

  • Give each kind of data a priority. Things that have not been sent for a while gain priority (an accumulator: each tick, add each object's priority to its score; send the highest scores; reset the score of what was sent). Far-away objects get a lower priority, so they update less often but are never starved.
  • Send reliable messages first, but cap them so they cannot crowd out state entirely.
  • Watch round-trip time and loss: when they climb, the path is congested. Sending less (fewer packets a second, or smaller ones) is kinder to the network and usually improves the game, too.
