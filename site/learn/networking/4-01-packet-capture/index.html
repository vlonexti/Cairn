Packet Capture

lesson 4.011 of 5 in milestone 45 min1 practice task

Seeing the actual packets - capturing with Wireshark and Npcap, capture filters versus display filters, the pcap file format with its global and per-packet headers, and the rules about what you may capture.

Seeing what is really sent

Everything in this course so far has been described from the program's point of view. A packet capture shows what actually crossed the wire: every header, every retransmission, every byte. When a networked program misbehaves, a capture is usually the fastest way to find out whether the bug is in the client, the server, or the network.

Tools

  • Wireshark: the standard graphical capture and analysis tool. It decodes thousands of protocols, shows each packet's layers as a tree, and can follow whole conversations.
  • Npcap: the capture driver Wireshark installs on Windows. Enable its "loopback" support to capture traffic to 127.0.0.1, which never touches a real network card.
  • tshark and dumpcap: Wireshark's command-line tools, for capturing on servers and scripting.
  • pktmon: built into Windows 10 and later (pktmon start --capture), writing captures that Wireshark can open after conversion (pktmon etl2pcap).

Two kinds of filter

Capture filters decide what is recorded at all, in the BPF syntax of libpcap. They keep files small on busy networks:

Text
host 192.168.1.50
tcp port 7777
udp and port 53
not port 3389

Display filters decide what Wireshark shows from a capture, using its own field names, and can be changed freely afterwards:

Text
ip.addr == 192.168.1.50
tcp.port == 7777 && tcp.flags.syn == 1
dns.qry.name contains "justloofy"
http.request.method == "POST"
tcp.analysis.retransmission
tls.handshake.extensions_server_name

Capture broadly, filter the display narrowly: you cannot recover packets a capture filter dropped.

The pcap file format

Captures are saved as pcap files (or the newer pcapng, which Wireshark uses by default and can convert). The classic pcap format is simple, which is why every tool supports it:

A 24-byte global header:

Offset Size Field
0 4 magic number: 0xA1B2C3D4 (microsecond timestamps) or 0xA1B23C4D (nanoseconds)
4 2 + 2 version, 2.4
8 4 time zone correction (always 0)
12 4 timestamp accuracy (always 0)
16 4 snapshot length: the most bytes stored per packet
20 4 link type: 1 means Ethernet frames

The magic number also tells you the byte order of the file: read as little-endian it is 0xA1B2C3D4 on files written by little-endian machines; if it reads as 0xD4C3B2A1, every field in the file is big-endian.

Then, for each packet, a 16-byte record header and the packet bytes:

Offset Size Field
0 4 timestamp, seconds
4 4 timestamp, microseconds (or nanoseconds)
8 4 captured length: bytes stored in the file
12 4 original length: bytes the packet really had

When a packet was longer than the snapshot length, only the first bytes are stored and the captured length is smaller than the original. Decoders must cope with truncated packets.

What you may capture

Capturing traffic is reading other people's communication when it is not yours. Capture only on networks and machines you own or are explicitly authorised to examine, only the traffic you need, and treat captures as sensitive data: they can contain passwords sent without encryption, cookies, and private messages. Deleting a capture you no longer need is good practice.
