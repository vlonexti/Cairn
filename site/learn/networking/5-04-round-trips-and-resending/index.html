Round Trips and Resending

lesson 5.044 of 5 in milestone 55 min1 practice task

Measuring how long a round trip takes and smoothing it, the retransmission timeout from RFC 6298 with backoff and Karn's rule, and building reliable ordered messages on top of unreliable packets - message ids, resending until acknowledged, and delivering in order.

Measuring the round trip

The time from sending a packet to receiving its acknowledgement is a round-trip time (RTT) sample. Single samples are noisy (the other side may wait a few milliseconds before sending its next packet), so protocols keep a smoothed estimate. TCP's method, from RFC 6298, works well for games too:

Text
first sample R:     srtt = R              rttvar = R / 2
each later R:       rttvar = 3/4 · rttvar + 1/4 · |srtt - R|
                    srtt   = 7/8 · srtt   + 1/8 · R
timeout:            rto = srtt + 4 · rttvar     (clamped to a minimum and maximum)

srtt is the smoothed RTT, the number to show the player as "ping". rttvar measures how much it varies; adding four times it to the timeout means a slow-but-normal round trip is not mistaken for a loss.

  • Before any sample, use a safe initial timeout (TCP uses 1 second).
  • When a timeout fires and you resend, double the timeout (exponential backoff), up to the maximum, so a broken connection is not flooded. The next real sample resets it.
  • Karn's rule: never take a sample from something that was resent, because you cannot tell whether the ack is for the first copy or the second. With per-packet acks (lesson 5.03) this is easy: each packet is sent once, and only resent messages travel in new packets.

Reliable messages

Some things must arrive: chat, "you picked up the key", a match result. On top of unreliable packets:

  1. Give each reliable message an increasing message id (16 bits, compared as in lesson 5.02).
  2. Keep it in a send queue until it is acknowledged.
  3. Each time you build a packet, include queued messages that were never sent, or were sent longer ago than the timeout. Remember which message ids went into which packet.
  4. When the packet is acknowledged (lesson 5.03), the messages in it are done: remove them from the queue.

On the receiving side:

  • Messages may arrive out of order (a resent message overtakes nothing, but a later one may arrive first) and more than once.
  • Keep the id of the next message to deliver. A message with that id is delivered at once, followed by any buffered ones that now follow it. A later id is buffered. An earlier id is a duplicate and is dropped.

If order does not matter (each message independent), deliver immediately and only drop duplicates: that avoids one lost message holding back the others, the same head-of-line problem as TCP but chosen only where it is needed. Many games run several channels: unreliable, reliable unordered and reliable ordered.

Resending is expensive

Every resend uses bandwidth that newer data could have used. Keep reliable messages small and rare, send state (positions) unreliably, and if something important is large, send it once reliably and then send changes. The next lesson deals with sizes.
