Following a TCP Conversation

lesson 4.044 of 5 in milestone 45 min1 practice task

Turning a list of captured segments into the conversation they carry - identifying a connection by its addresses and ports, relative sequence numbers, the handshake, data in both directions, retransmissions and duplicates, and how connections end with FIN or RST.

One connection among many

A capture interleaves packets from every connection on the machine. A single TCP connection is identified by its four-tuple: the two IP addresses and the two ports. Packets in one direction have it as (A, portA, B, portB); replies have it reversed. A tracker uses a canonical key (the lower endpoint first, say) so both directions land in the same conversation.

Relative sequence numbers

Each side's initial sequence number (ISN) is random, so raw numbers like 3141592653 are hard to read. Wireshark shows relative numbers by default: the sequence number minus that side's ISN. The SYN is relative 0, the first data byte relative 1 (the SYN used up one number), and the relative number of any byte is its position in the stream plus one. Do the same in your own tools.

Reading a conversation

Text
 #  direction       flags     rel seq   rel ack   len
 1  client->server  SYN       0                   0
 2  server->client  SYN,ACK   0         1         0
 3  client->server  ACK       1         1         0
 4  client->server  PSH,ACK   1         1         75     request
 5  server->client  ACK       1         76        1448   response, part 1
 6  server->client  ACK       1449      76        1448   part 2
 7  client->server  ACK       76        2897      0
 8  server->client  FIN,ACK   2897      76        0
 9  client->server  FIN,ACK   76        2898      0
10  server->client  ACK       2898      77        0
  • Packets 1 to 3 are the handshake.
  • The client sent 75 bytes (4); the server acknowledged them (ack 76 in packet 5) and sent 2 896 bytes in two segments.
  • Each FIN takes one sequence number, so the final acknowledgements are one more than the data.

Retransmissions and duplicates

When a segment is lost, the sender sends the same bytes again later. In a capture this appears as a segment whose sequence range has already been seen. Wireshark flags these as [TCP Retransmission]; duplicate acknowledgements (the same ack number repeated, often three times before a fast retransmit) as [TCP Dup ACK].

To reassemble the byte stream, as "Follow TCP Stream" does, take each direction's segments in sequence order, keep only bytes not already placed, and stop at any gap (a segment never captured). The result is exactly what each program read with recv, which makes reading application protocols (next lesson) possible.

How connections end

  • FIN in both directions, each acknowledged: an orderly close (lesson 2.02).
  • RST: an abort. A RST in reply to a SYN means connection refused: nothing listens on that port. A RST in the middle of a conversation usually means a program crashed or closed with unread data, or a firewall killed the connection.
  • Nothing: a connection that simply stops, often because one side vanished; it is eventually timed out by keep-alives or by the application.

Counting how each connection in a capture ended is often the quickest diagnosis of "it sometimes disconnects".
