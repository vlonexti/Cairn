TCP and UDP Headers

lesson 4.033 of 5 in milestone 45 min1 practice task

The transport headers byte by byte - UDP's eight bytes, TCP's ports, sequence and acknowledgement numbers, data offset, flags, window and options such as MSS and window scaling - and the pseudo-header both checksums cover.

UDP

The UDP header is 8 bytes, all big-endian:

Offset Size Field
0 2 source port
2 2 destination port
4 2 length: header plus data
6 2 checksum (0 in IPv4 means "not computed")

That is everything UDP adds to IP (lesson 1.04).

TCP

The TCP header is 20 bytes plus options:

Offset Size Field
0 2 source port
2 2 destination port
4 4 sequence number: the number of the first data byte (or of the SYN)
8 4 acknowledgement number: the next byte expected, valid when ACK is set
12 4 bits data offset: header length in 32-bit words (5 to 15)
13 8 bits flags
14 2 window: free receive buffer space
16 2 checksum
18 2 urgent pointer (almost never used)
20 ... options, up to data offset × 4

The flags byte, from the most significant bit:

Bit Value Flag Means
7 0x80 CWR congestion window reduced
6 0x40 ECE congestion seen (ECN)
5 0x20 URG urgent pointer valid
4 0x10 ACK the acknowledgement number is valid
3 0x08 PSH push this data to the application now
2 0x04 RST reset: abort the connection
1 0x02 SYN synchronise: open a connection
0 0x01 FIN finished sending

The payload starts at data offset × 4, and its length is the IP data length minus that. A SYN or FIN with no data still uses up one sequence number, which is why the handshake's acknowledgements are "seq + 1".

Options

Options are type-length-value records (type 0 ends the list, type 1 is a one-byte padding "no-op"):

Kind Name Purpose
2 MSS the largest segment this side will accept (lesson 1.01)
3 window scale multiply the 16-bit window by 2^n, for fast networks
4 SACK permitted selective acknowledgements may be used
5 SACK which ranges beyond a gap have arrived
8 timestamps for measuring round trips and protecting against wrapped sequence numbers

Most appear only in the SYN and SYN-ACK, where the two sides negotiate them.

The checksum and the pseudo-header

TCP and UDP checksums use the Internet checksum (lesson 2.03), computed over:

  1. a pseudo-header: source address, destination address, a zero byte, the protocol number, and the TCP or UDP length (for IPv4: 4 + 4 + 1 + 1 + 2 bytes);
  2. the TCP or UDP header (with the checksum field as zero when computing it);
  3. the data, padded with a zero byte if its length is odd.

Including the addresses means a packet delivered to the wrong machine or port fails its checksum. To verify a received segment, run the sum over the pseudo-header and the whole segment including its checksum: a correct one comes out as zero.

In captures taken on the sending machine, Wireshark often reports TCP checksums as wrong: modern network cards compute them in hardware (checksum offloading) after the capture point, so the captured packet still has a blank or partial checksum. Wireshark's "Validate TCP checksum" option is off by default for this reason.
