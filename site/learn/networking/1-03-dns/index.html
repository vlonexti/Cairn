DNS

lesson 1.033 of 5 in milestone 15 min1 practice task

How names become addresses - the hierarchy of domains, resolvers and authoritative servers, the record types you will meet, caching and TTLs, the wire format of a DNS query with its length-prefixed labels, and why your program should call getaddrinfo instead of doing it itself.

Names for addresses

People use names (xenon.justloofy.dev); packets need addresses. The Domain Name System translates between them. It is a worldwide distributed database, organised as a tree:

Text
                      . (root)
            /           |          \
          com          dev          org
         /             |
     example        justloofy
                       |
                     xenon

Each level is a zone managed by someone: the root servers know who runs dev; the dev servers know who runs justloofy.dev; that domain's own authoritative servers know the address of xenon.justloofy.dev.

Asking

Your program does not walk the tree itself. It asks the operating system, which asks a recursive resolver (usually your router or your internet provider's, or a public one such as 1.1.1.1 or 8.8.8.8). The resolver walks the tree if needed, caches the answers, and replies. Most queries are answered from a cache in a few milliseconds.

Record types

Type Holds
A an IPv4 address
AAAA an IPv6 address
CNAME "this name is an alias for that name"
MX the mail servers for a domain
TXT free text (domain ownership proofs, email policies)
NS the name servers for a zone
SRV host and port of a service (_minecraft._tcp.example.com)

A name can have several A or AAAA records; clients usually try them in turn, which gives simple load balancing and failover.

Caching and TTL

Every record carries a time to live (TTL) in seconds: how long resolvers may cache it. A TTL of 3600 means a change can take up to an hour to be seen everywhere, which is why people lower TTLs before moving a server. Caching is also why DNS is fast and scales.

The wire format

A DNS query is a small UDP packet to port 53 (TCP is used for large answers). After a 12-byte header (an id, flags, and counts of questions and answers), the question holds the name in a special format: each label (the parts between dots) preceded by its length, ending with a zero byte:

Text
xenon.justloofy.dev  ->  05 'x' 'e' 'n' 'o' 'n'  08 'j' 'u' 's' 't' 'l' 'o' 'o' 'f' 'y'  03 'd' 'e' 'v'  00

then a 2-byte type (1 for A, 28 for AAAA) and a 2-byte class (1 for internet), all big-endian (lesson 2.03). Labels are at most 63 bytes, whole names at most 255.

Answers repeat names a lot, so DNS compresses them: instead of a label, two bytes whose top two bits are 11 give an offset, earlier in the packet, where the rest of the name continues. A parser must follow these pointers, and must guard against pointers that loop.

In your program

Do not build DNS packets to look up addresses; call the operating system:

C++
addrinfo hints{};
hints.ai_family = AF_UNSPEC;          // IPv4 or IPv6, whichever exists
hints.ai_socktype = SOCK_STREAM;      // for TCP
addrinfo* results{};
if (getaddrinfo("xenon.justloofy.dev", "443", &hints, &results) == 0)
{
    for (addrinfo* r{ results }; r; r = r->ai_next) { /* try to connect to r->ai_addr */ }
    freeaddrinfo(results);
}

getaddrinfo uses the system's resolver and cache, the hosts file, and handles IPv4 and IPv6. Building and parsing DNS messages yourself is for writing DNS tools, or for reading them in packet captures (milestone 4), which is what the practice prepares you for.
