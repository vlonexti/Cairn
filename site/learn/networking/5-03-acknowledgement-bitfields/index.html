Acknowledgement Bitfields

lesson 5.033 of 5 in milestone 55 min1 practice task

Telling the sender which packets arrived without sending a packet per acknowledgement - the latest received number plus a 32-bit field for the ones before it, why the redundancy survives loss, and how the sender turns acks into "delivered" events.

Acknowledging cheaply

TCP acknowledges bytes cumulatively and retransmits itself. A game protocol wants something different: the sender should simply learn which packets arrived, so it can decide what, if anything, to resend. And since both sides are sending packets all the time anyway, acknowledgements ride along in the header of every packet (piggybacking) instead of getting packets of their own.

The usual header:

Field Size Meaning
sequence 16 bits this packet's number
ack 16 bits the most recent sequence number received from the other side
ackBits 32 bits bit i set means packet ack - 1 - i was also received

So every packet acknowledges 33 packets at once.

Redundancy beats loss

Suppose the other side receives packets 100 to 140 except 137. Its next packets all say:

Text
ack = 140, ackBits: bit 2 clear (137 missing), every other bit of the 32 set

It sends this many times a second. Even if most of its packets are lost, any one that gets through tells you the whole story of the last 33 packets. An acknowledgement is lost for good only if the other side's packets are lost for more than about half a second in a row at 60 packets a second, and by then the connection is in trouble anyway.

The receiving side

Keep latest and bits. When a packet with sequence s arrives (using d = sequenceDifference(s, latest) from lesson 5.02):

  • d > 0: the new latest is s. The old latest becomes bit d - 1, and every old bit moves up by d (bits shifted past 31 are forgotten). If d > 32, the old history is gone completely.
  • d < 0: set bit -d - 1, if it is below 32.
  • d == 0: a duplicate; nothing changes.

Watch out for shifting a 32-bit value by 32 or more: in C++ that is undefined behaviour, so handle d >= 32 separately or shift a 64-bit value.

The sending side

The sender remembers what it put in each packet it sent (a ring buffer of the last few hundred, indexed by sequence % size). When an ack and ackBits arrive, it walks the 33 numbers they cover. Each that is marked received and was not acknowledged before becomes a "delivered" event:

  • reliable messages in that packet are done and need no resending;
  • the time between sending and the ack is a round-trip sample (next lesson);
  • a packet still unacknowledged long after newer ones were acked was almost certainly lost.

Each packet must produce its "delivered" event once, though it will be acknowledged by dozens of incoming packets.
