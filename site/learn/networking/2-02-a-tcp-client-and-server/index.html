A TCP Client and Server

lesson 2.022 of 5 in milestone 25 min1 practice task

The server side - bind, listen and accept - a complete echo server and client, sending everything with a loop, reading until a whole message has arrived, closing gracefully with shutdown, and the TIME_WAIT state that sometimes stops a server restarting.

The server's calls

C++
SOCKET listener{ socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) };

sockaddr_in addr{};
addr.sin_family = AF_INET;
addr.sin_addr.s_addr = htonl(INADDR_ANY);        // every interface (127.0.0.1 for local only)
addr.sin_port = htons(7777);                     // htons: byte order, lesson 2.03
if (bind(listener, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) == SOCKET_ERROR) { /* port in use? */ }

listen(listener, SOMAXCONN);                     // start accepting; queue pending connections

for (;;)
{
    sockaddr_in from{};
    int fromLength{ sizeof(from) };
    SOCKET client{ accept(listener, reinterpret_cast<sockaddr*>(&from), &fromLength) };
    if (client == INVALID_SOCKET) break;
    serve(client);                               // one client at a time, for now
    closesocket(client);
}
  • bind claims an address and port.
  • listen turns the socket into a listening socket. The operating system completes handshakes on its own and queues the new connections.
  • accept takes the next connection from the queue and returns a new socket for it. The listening socket keeps listening.

This server handles one client at a time; lesson 2.04 fixes that.

Sending everything

send may accept fewer bytes than you gave it, so real code always loops:

C++
bool sendAll(SOCKET s, const char* data, int length)
{
    while (length > 0)
    {
        const int sent{ send(s, data, length, 0) };
        if (sent == SOCKET_ERROR) return false;
        data += sent;
        length -= sent;
    }
    return true;
}

Receiving whole messages

Likewise, one recv returns whatever has arrived. A line-based protocol reads into a buffer and takes out complete lines:

C++
std::string buffer;
char chunk[4096];
for (;;)
{
    const int got{ recv(s, chunk, sizeof(chunk), 0) };
    if (got <= 0) break;                                    // closed (0) or error
    buffer.append(chunk, static_cast<std::size_t>(got));
    for (std::size_t end{ buffer.find('\n') }; end != std::string::npos; end = buffer.find('\n'))
    {
        handleLine(buffer.substr(0, end));
        buffer.erase(0, end + 1);
    }
}

The same shape with a length prefix instead of \n handles binary messages. A test that sends one short message over loopback will seem to work without the loop, because small messages usually arrive in one piece locally; across a real network, they do not.

Closing gracefully

Closing a TCP connection properly is a small dance:

  1. The side that has finished sending calls shutdown(s, SD_SEND): a FIN goes out.
  2. The other side's recv returns 0 after it has read everything. It sends whatever it still has, then shuts down its own sending.
  3. The first side's recv returns 0. Both call closesocket.

Calling closesocket while data from the peer is still unread makes Windows send a reset instead, and the peer may lose the last data it sent you. A client that sends a request and then shutdown(SD_SEND) to say "that is all" (as many simple protocols do) gets the full reply reliably.

TIME_WAIT

After a connection closes, the side that closed first keeps a record of it for a while (up to a few minutes) in the TIME_WAIT state, so that stray delayed packets of the old connection are not mistaken for a new one. A consequence: a server that is stopped and immediately restarted can fail to bind its port with WSAEADDRINUSE, because old connections are still in TIME_WAIT.

On Windows, SO_REUSEADDR has dangerous semantics (it allows another program to bind the same port too); use SO_EXCLUSIVEADDRUSE to protect a server's port, and design restarts to tolerate a short wait.
