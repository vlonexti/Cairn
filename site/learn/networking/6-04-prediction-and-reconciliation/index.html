Prediction and Reconciliation

lesson 6.044 of 5 in milestone 65 min1 practice task

Hiding latency for your own player - running your inputs immediately with the same simulation code as the server, keeping the inputs not yet confirmed, and when the server's state arrives, resetting to it and replaying the rest; plus smoothing corrections and what cannot be predicted.

The delay you feel

With a pure authoritative server, pressing a key does nothing until the input reaches the server, is simulated, and the result comes back: a full round trip, 50 to 150 ms. Movement feels like wading through syrup.

Client-side prediction

The client already knows its own inputs and has the same movement code as the server. So it applies each input immediately to its own player and shows the result, without waiting:

  1. Make an input, give it the next sequence number, and send it to the server.
  2. Simulate it locally at once, exactly as the server will.
  3. Keep it in a list of pending inputs: sent, but not yet confirmed.

When nothing unexpected happens, the server computes exactly the same positions a round trip later, and the prediction was perfect.

Reconciliation

Each snapshot tells the client its player's authoritative state and the sequence number of the last input the server applied. That state is in the past: inputs sent since then are still on their way. So the client:

  1. Drops pending inputs with sequence numbers up to the last applied one: they are confirmed.
  2. Resets its player to the authoritative state.
  3. Replays the remaining pending inputs on top of it, with the same simulation.

The result is the present again, now based on the truth. If the prediction was right, nothing visibly changes. If something the client could not know happened (another player pushed it, the server rejected a move, an explosion knocked it back), the replay starts from the corrected state and the player ends up where they really are.

Text
client predicted:   inputs 1..10 applied, at x = 100
snapshot arrives:   server applied up to 7, x = 70 (no surprises)
reconcile:          drop 1..7, reset to 70, replay 8, 9, 10 → x = 100   (no change)

snapshot arrives:   server applied up to 7, x = 40 (hit by something at input 5)
reconcile:          drop 1..7, reset to 40, replay 8, 9, 10 → x = 70    (correction of -30)

Making it work well

  • Same code, same results. The client must run exactly the server's movement code with the same inputs and tick length, and ideally the same quantisation (lesson 6.02). Any difference shows as constant small corrections.
  • Smooth the corrections. Instead of snapping the camera, move the displayed position towards the corrected one over a few frames, while the simulated position snaps at once.
  • Ignore old snapshots. A snapshot that confirms fewer inputs than one already applied arrived out of order: drop it.
  • Predict only what is yours. Your movement and your weapon's animation are predicted. Other players are interpolated (lesson 6.03), and anything that decides the game, such as hits, damage and pickups, waits for the server.
