TCP and UDP

lesson 1.044 of 5 in milestone 15 min1 practice task

The two transport protocols and what each promises - TCP's connections, three-way handshake, sequence numbers, acknowledgements, retransmission, flow and congestion control and orderly close; UDP's independent datagrams with no promises at all - and how to choose.

Two very different promises

IP delivers packets best effort: they can be lost, duplicated, delayed or arrive in a different order. The transport layer decides what to promise on top of that.

TCP UDP
Model a connection carrying a byte stream independent datagrams (messages)
Delivery every byte, exactly once maybe
Order always in order any order
Boundaries none: a stream each datagram arrives whole or not at all
Setup a handshake before data none
Speed when packets are lost waits for the lost data carries on

TCP: the handshake

A connection starts with three packets, the three-way handshake:

Text
client                         server
  | --- SYN  seq=1000 -------->  |     "I want to connect; my bytes start at 1000"
  | <-- SYN+ACK seq=5000 ack=1001|     "OK; mine start at 5000; I expect your 1001 next"
  | --- ACK  ack=5001 -------->  |     "I expect your 5001 next"

Each side picks a random starting sequence number. From then on every byte has a number, and that is what makes everything else possible.

Sequence numbers and acknowledgements

Each data packet (a segment) carries the sequence number of its first byte. The receiver replies with an acknowledgement: "I have every byte up to N; send N next". If a segment is lost, the receiver keeps acknowledging the byte before the gap; the sender notices (by a timeout, or by several duplicate acknowledgements) and retransmits. Segments that arrive early, beyond a gap, are held and delivered to the program once the gap is filled. So the program always reads every byte, in order, even though the network did not deliver them that way.

The price is head-of-line blocking: when one segment is lost, all the data after it waits, even if it already arrived, until the retransmission comes, typically a round trip or more later.

Flow and congestion control

  • Flow control: each acknowledgement carries a window, the free space in the receiver's buffer. The sender never sends more unacknowledged data than that, so a slow receiver is never flooded.
  • Congestion control: the sender also estimates how much the network can take. It starts slowly, increases its rate while all goes well, and cuts it sharply when packets are lost (loss usually means a full queue somewhere). This is what keeps the internet working when millions of connections share it, and why a new connection takes a little while to reach full speed.

Closing

Each side sends a FIN when it has finished sending, and the other acknowledges it. A side can finish sending but keep receiving (a half-close). An abrupt RST aborts the connection, for example when a program crashes or connects to a port where nothing listens ("connection refused").

UDP: just datagrams

UDP adds only ports, a length and a checksum to IP. Each sendto is one datagram that arrives whole, once, in some order relative to others, or never. There is no connection, no handshake, no retransmission, no congestion control.

That sounds worse, and for most data it is. But it means no head-of-line blocking and no waiting: a game that sends the player's position 60 times a second does not want a lost update from 50 ms ago to delay the newer ones that make it obsolete. DNS uses UDP because one question and one answer do not need a connection. Voice and video use it because late data is useless data.

Programs using UDP build exactly the reliability they need themselves; milestone 5 does that.

Choosing

  • TCP for anything where every byte matters and a little latency does not: files, web pages, chat, commands, most APIs.
  • UDP for real-time data where only the newest matters and late is as bad as lost: game state, voice, video, sensor streams; and for simple request-response such as DNS.
  • QUIC (the protocol under HTTP/3) runs over UDP and provides TCP-like reliability per stream, so one lost packet only delays its own stream. It is what new protocols increasingly use.
