Reading Protocols in Captures

lesson 4.055 of 5 in milestone 45 min1 practice task

Going up the stack in a capture - DNS queries and answers over UDP, plain HTTP in a reassembled TCP stream, and TLS, where only the handshake is readable - the record layer, the ClientHello, and the server name in its SNI extension.

DNS

DNS messages travel in single UDP datagrams to and from port 53 (lesson 1.03). The 12-byte header:

Offset Size Field
0 2 id: matches answers to questions
2 2 flags: the top bit (QR) is 0 for a query, 1 for a response; the low 4 bits are the response code (0 OK, 3 no such name)
4 2 number of questions
6 2 number of answers
8 2 number of authority records
10 2 number of additional records

The question follows: a name in label format, a 2-byte type and a 2-byte class. Answers repeat the name (usually as a compression pointer back to the question), then type, class, a 4-byte TTL, a 2-byte data length and the data (4 bytes for an A record). In a capture, DNS tells you which names a program looked up and what it was told, often the first clue to what it is doing.

HTTP

Plain HTTP (port 80, or your own local server) is readable once the TCP stream is reassembled: the request line, headers and body of lesson 3.01, in clear text. That is also why it should not be used for anything private.

TLS: only the handshake

Almost all web traffic is HTTPS, and a capture shows its content only as encrypted application data. But the start of the handshake is readable, and it says a lot.

TLS sends records:

Offset Size Field
0 1 content type: 22 handshake, 23 application data, 21 alert
1 2 legacy version (03 01 or 03 03)
3 2 length of the record's data

The first record from the client is a handshake record containing a ClientHello:

Field Size
handshake type 1 (1 = ClientHello)
length 3
client version 2
random 32
session id 1-byte length, then that many bytes
cipher suites 2-byte length, then 2 bytes per suite
compression methods 1-byte length, then the methods
extensions 2-byte length, then extensions: each a 2-byte type, 2-byte length, and data

Extension type 0 is server name indication (lesson 3.05). Its data is a 2-byte list length, then entries of a 1-byte name type (0 = host name), a 2-byte length and the name.

So from a capture you can learn, for each TLS connection, which hostname it was for, which versions and cipher suites the client offered, and the certificate the server sent (in TLS 1.2; TLS 1.3 encrypts it). This is how network monitoring tools label encrypted traffic, and why Encrypted Client Hello is being introduced.

When it does not decode

Real traffic is messier than tables: a ClientHello split across two TCP segments, records that span segments, protocols on unusual ports, QUIC traffic over UDP 443 that Wireshark decodes only partly. A robust decoder checks every length against the bytes actually available and reports "truncated" or "not this protocol" rather than reading past the end. The practice holds you to that.
