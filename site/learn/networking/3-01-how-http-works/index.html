How HTTP Works

lesson 3.011 of 5 in milestone 35 min1 practice task

The protocol of the web as plain text over TCP - a request line, headers and an optional body; a status line, headers and a body in reply - methods, status codes, the headers that matter, persistent connections, and where HTTP/2 and HTTP/3 differ.

Text over a connection

HTTP/1.1 is a text protocol on top of TCP. A client opens a connection (to port 80, or 443 for HTTPS) and sends a request:

Text
GET /courses/networking HTTP/1.1\r\n
Host: xenon.justloofy.dev\r\n
User-Agent: my-client/1.0\r\n
Accept: text/html\r\n
\r\n
  • The request line: a method, the target (path and query), and the version.
  • Headers: Name: value lines.
  • A blank line (\r\n alone) ends the headers.
  • Then an optional body, for methods that send data.

The server answers with a response in the same shape:

Text
HTTP/1.1 200 OK\r\n
Content-Type: text/html; charset=utf-8\r\n
Content-Length: 1532\r\n
\r\n
<!doctype html>... (exactly 1532 bytes)

You can speak it by hand: curl -v https://example.com shows both sides, and over plain HTTP even telnet example.com 80 and typing the request works.

Methods

Method Means Body Safe to repeat?
GET fetch a resource no yes
HEAD like GET, headers only no yes
POST submit data, create something, run an action yes no
PUT replace a resource with this body yes yes (idempotent)
PATCH change part of a resource yes not necessarily
DELETE remove a resource usually no yes (idempotent)
OPTIONS ask what is allowed (used by browsers' CORS checks) no yes

"Safe to repeat" is the idempotency of the IPC course's lesson 5.04: browsers and proxies retry GETs freely, but never a POST without asking.

Status codes

The first digit says the class:

Class Meaning Common codes
1xx information 101 Switching Protocols (WebSockets)
2xx success 200 OK, 201 Created, 204 No Content
3xx go elsewhere 301 Moved Permanently, 302 Found, 304 Not Modified
4xx the client's fault 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests
5xx the server's fault 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable

Clients should handle a code by its class when they do not know it specifically: an unknown 4xx is treated like 400.

Headers that matter

Header Purpose
Host which website on this server (required in HTTP/1.1: one IP serves many sites)
Content-Length the body's size in bytes
Transfer-Encoding: chunked the body comes in pieces of announced size (lesson 3.02)
Content-Type what the body is: text/html, application/json, image/png
Connection: close close the connection after this response
Location where a 3xx redirect points; where a 201 created something
Cache-Control, ETag, If-None-Match caching and conditional requests (304)
Authorization credentials, such as Bearer <token>
Cookie / Set-Cookie state the browser keeps for a site

Header names are case-insensitive (content-length is the same header); values are not.

Connections

HTTP/1.1 connections are persistent by default: after a response, the same connection carries the next request, saving a TCP (and TLS) handshake each time. That only works if each side knows exactly where every message ends, which is why every response needs a Content-Length or chunked encoding, or must close the connection to mark its end.

On one HTTP/1.1 connection requests are answered in order, one at a time, so browsers open several connections per site to load pages in parallel.

HTTP/2 and HTTP/3

HTTP/2 keeps the same methods, status codes and headers but sends them as binary frames, compresses headers, and multiplexes many requests over one connection at once. HTTP/3 does the same over QUIC (UDP), so a lost packet delays only its own request (lesson 1.04). Programs usually get both from a library; the meaning of requests and responses is the HTTP/1.1 you see here.
