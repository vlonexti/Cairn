HTTPS and TLS

lesson 3.055 of 5 in milestone 35 min1 practice task

What TLS adds to a connection - encryption, integrity and server authentication - certificates and the chain of trust, how hostnames are matched including wildcards, the handshake in outline, SNI, and why you always use a library for it.

Three promises

Plain HTTP travels as readable text: anyone on the path (the café's Wi-Fi, an internet provider, a compromised router) can read it and change it. TLS (Transport Layer Security, the successor of SSL) wraps a TCP connection and adds three guarantees:

  • Confidentiality: the data is encrypted; observers see only sizes and timing.
  • Integrity: any change in transit is detected and the connection fails.
  • Authentication: the client knows it is talking to the real server for that name, not an impostor.

HTTPS is simply HTTP inside TLS, on port 443. Everything in this milestone applies unchanged inside the encrypted channel.

Certificates

Authentication rests on certificates. A server's certificate contains its public key and the names it is valid for, signed by a certificate authority (CA). The client checks:

  1. The signature chain: the server's certificate is signed by an intermediate CA, which is signed by a root CA that the operating system or browser trusts.
  2. The certificate is within its validity dates and not revoked.
  3. The name: the host the client meant to reach is listed in the certificate's subject alternative names.

Then, during the handshake, the server proves it holds the private key matching the certificate's public key. An attacker can copy a certificate (it is public) but not the private key.

Free, automated certificates from Let's Encrypt made HTTPS the norm; there is no reason to serve anything public over plain HTTP.

Matching names

Name checking is where many home-made implementations fail. The rules (RFC 6125) for each name in the certificate:

  • Compare case-insensitively.
  • An exact name matches only itself: xenon.justloofy.dev matches xenon.justloofy.dev.
  • A wildcard *.justloofy.dev matches exactly one label in its place: xenon.justloofy.dev yes; justloofy.dev no (no label); a.b.justloofy.dev no (two labels).
  • The wildcard must be the entire leftmost label: *.dev style names that cover a whole public suffix are refused by clients, and partial wildcards like x*.example.com should be refused too.
  • IP addresses are matched against IP entries, never against wildcards.

The handshake in outline

TLS 1.3, the current version, needs one round trip:

  1. ClientHello: supported versions and ciphers, a key share, and the server name it wants (SNI, below).
  2. ServerHello with the server's key share; from both shares each side computes the same secret keys. Then, already encrypted, the certificate, a signature proving key ownership, and "finished".
  3. The client checks the certificate and signature, sends its own "finished", and application data flows.

Resumed connections can even send data in the first flight (0-RTT), with care about replays.

SNI

One IP address often hosts many HTTPS sites, but the certificate must be chosen before any HTTP is exchanged. So the ClientHello carries the hostname in the Server Name Indication extension. It is sent in clear text (Encrypted Client Hello is being deployed to fix that), which is why packet captures, and network filters, can see which site a TLS connection is for even though they cannot see the pages. Milestone 4's practice extracts it.

Use a library

TLS involves careful cryptography, certificate parsing, chain building, revocation, and dozens of past attacks that implementations must avoid. Never write your own. On Windows:

  • WinHTTP or WinINet: HTTPS requests with one API, using the system's certificate store.
  • SChannel: the system TLS implementation for your own sockets.
  • OpenSSL, BoringSSL or mbedTLS: cross-platform libraries.
  • Higher-level HTTP libraries (libcurl, cpp-httplib with OpenSSL) handle it for you.

And never "fix" a certificate error by turning verification off. That removes the authentication guarantee entirely and leaves the encryption protecting your traffic for an attacker.
