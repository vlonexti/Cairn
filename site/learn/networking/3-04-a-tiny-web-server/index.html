A Tiny Web Server

lesson 3.044 of 5 in milestone 35 min1 practice task

Putting the milestone together - routing requests by method and path with parameters, serving static files with the right Content-Type, building correct responses, and the path traversal attack that a naive file server falls for and how to stop it.

The loop

A web server is the event loop of lesson 2.04 with HTTP as its protocol:

  1. Accept connections; read bytes into each connection's buffer.
  2. When a whole request has arrived (lesson 3.02), route it to a handler.
  3. The handler produces a response: status, headers, body.
  4. Serialise the response into the connection's output queue.
  5. Keep the connection for the next request, unless either side asked to close.

Routing

A router maps a method and a path pattern to a handler. Patterns often contain parameters:

Text
GET  /                      -> home page
GET  /courses/{id}          -> one course; id from the path
GET  /courses/{id}/lessons/{lesson}
POST /api/progress          -> save progress

Matching splits the path at /, compares segment by segment, and collects {name} segments as parameters (percent-decoded, lesson 3.03). Useful rules:

  • If a path matches a route but not with this method, reply 405 Method Not Allowed with an Allow header listing the methods that would work, rather than 404.
  • Prefer exact segments over parameters when both match (/courses/new before /courses/{id}), or order routes so the specific one is tried first.
  • Unknown paths get 404.

Responses

A correct response always includes a status line, a Content-Length (or chunked encoding), and a Content-Type when there is a body:

C++
std::string response{ "HTTP/1.1 " + std::to_string(status) + " " + reason(status) + "\r\n" };
response += "Content-Type: " + type + "\r\n";
response += "Content-Length: " + std::to_string(body.size()) + "\r\n";
response += "\r\n";
response += body;

Content-Type for files comes from the extension: .html is text/html; charset=utf-8, .css text/css, .js text/javascript, .json application/json, .png image/png, .svg image/svg+xml, and unknown types application/octet-stream. Also send X-Content-Type-Options: nosniff so browsers trust that type instead of guessing.

Path traversal

A naive static file server maps a URL path straight onto a folder: GET /images/logo.png serves C:\site\public\images\logo.png. Now someone requests:

Text
GET /../../Windows/win.ini
GET /images/..%2F..%2F..%2Fsecret.txt
GET /images/..\..\config.json

If the server joins those to its folder without care, it serves files outside the public folder: configuration, source code, keys. This is path traversal, one of the oldest web vulnerabilities. Defend in layers:

  1. Percent-decode the path once, then reject anything containing \, a NUL byte, or a : (drive letters and Windows alternate data streams).
  2. Split at / and resolve . and .. yourself; reject any request whose .. would climb above the root, rather than silently clamping it.
  3. Reject segments Windows treats specially: names ending in . or a space, and device names such as CON, NUL or COM1.
  4. As a last check, compute the final absolute path and verify it is still inside the public folder (with std::filesystem::weakly_canonical on the real path).
  5. Never serve hidden or dot files (.env, .git) unless intended.

The practice builds exactly this check.

What a tiny server is for

A small server like this is useful for local tools (a dashboard for your game's stats, a documentation viewer) and for learning. For anything facing the internet, use a mature server or framework, and put TLS in front (next lesson): they have already handled the thousands of edge cases this milestone only touches.
