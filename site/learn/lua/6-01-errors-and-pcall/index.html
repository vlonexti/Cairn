Errors and pcall

lesson 6.011 of 5 in milestone 65 min1 practice task

Raising errors with error and assert, the level argument that says whose fault it is, catching errors with pcall, error values that are tables, xpcall with a traceback, and the nil-plus-message convention for errors that are expected.

Raising an error

error(message) stops the current function and every caller, all the way up, unless something catches it:

Lua
local function withdraw(balance, amount)
    if amount > balance then
        error("not enough money")
    end
    return balance - amount
end

print(withdraw(100, 30))
print(withdraw(100, 300))
print("not reached")
Output
70
lua: main.lua:3: not enough money
stack traceback:
	[C]: in function 'error'
	main.lua:3: in local 'withdraw'
	main.lua:9: in main chunk

Lua adds the position to a string message. The second argument, the level, says which position: 1 (the default) is the line with error, 2 is the line that called this function. For a function that checks its arguments, level 2 is right, because the mistake is the caller's:

Lua
local function sqrt_of(n)
    if type(n) ~= "number" then error("sqrt_of needs a number, got " .. type(n), 2) end
    return math.sqrt(n)
end
print(pcall(sqrt_of, "nine"))
print(pcall(function()
    local root = sqrt_of("nine")
    return root
end))
Output
false	sqrt_of needs a number, got string
false	main.lua:7: sqrt_of needs a number, got string

The first call came straight from pcall, which is C code with no line number, so there was no position to add. The second came from line 7. (Had that line been return sqrt_of("nine"), a tail call, the caller's frame would already be gone, and again no position would be added.)

assert

assert(value, message) raises an error when the value is false or nil, and otherwise returns all its arguments. That makes it perfect for wrapping calls that return nil, message on failure:

Lua
local n = assert(tonumber("42"), "not a number")
print(n + 1)
local f = assert(io.open("settings.txt", "w"))
f:write("volume=11\n")
f:close()
print(assert(io.open("settings.txt")):read("a"))
print(pcall(assert, false, "it was false"))
Output
43
volume=11

false	it was false

Catching errors with pcall

pcall(f, args...) ("protected call") calls f and catches any error in it. It returns true followed by f's results, or false and the error:

Lua
local function parse_age(text)
    local n = tonumber(text)
    if not n then error("'" .. text .. "' is not a number", 0) end
    if n < 0 or n > 150 then error("age out of range: " .. n, 0) end
    return math.floor(n)
end

for _, input in ipairs({ "42", "abc", "-5", "33.9" }) do
    local ok, result = pcall(parse_age, input)
    if ok then
        print("age", result)
    else
        print("error", result)
    end
end
Output
age	42
error	'abc' is not a number
error	age out of range: -5
age	33

Level 0 means "add no position", which suits messages meant for a user. Catch errors where you can do something about them (ask again, skip a line, show a message), not everywhere.

Errors as tables

error accepts any value, not just strings. A table can carry a kind, a code, or the bad input, and the catcher can look at it. Lua adds no position to a table:

Lua
local function load_level(n)
    if n > 3 then
        error({ kind = "missing", level = n })
    end
    return "level " .. n .. " loaded"
end

for _, n in ipairs({ 2, 7 }) do
    local ok, err = pcall(load_level, n)
    if ok then
        print(err)
    elseif type(err) == "table" and err.kind == "missing" then
        print("no level " .. err.level .. ", starting level 1")
    else
        error(err, 0)    -- not ours: pass it on
    end
end
Output
level 2 loaded
no level 7, starting level 1

xpcall and tracebacks

pcall throws away the call stack, so you lose where the error happened. xpcall(f, handler, args...) calls the handler at the point of the error, before the stack unwinds, which is where debug.traceback can still see it:

Lua
local function inner() local t = nil; return t.field end
local function outer() local v = inner(); return v end

local ok, report = xpcall(outer, function(err)
    return debug.traceback("caught: " .. tostring(err), 2)
end)
print(ok)
print(report)
Output
false
caught: main.lua:1: attempt to index a nil value (local 't')
stack traceback:
	main.lua:1: in upvalue 'inner'
	main.lua:2: in function <main.lua:2>
	[C]: in function 'xpcall'
	main.lua:4: in main chunk

Programs that embed Lua run scripts this way, so a crashing script shows a useful report instead of taking the whole application down.

Two kinds of failure

Lua's own libraries use two conventions, and your code should too:

Situation Convention Example
A bug (wrong type, impossible state) raise an error string.rep(nil), error("...")
An expected failure (missing file, bad user input) return nil and a message io.open, tonumber, utf8.len
Lua
local function find_user(users, name)
    for _, u in ipairs(users) do
        if u.name == name then return u end
    end
    return nil, "no user called " .. name
end

local users = { { name = "ada", admin = true } }
local u, err = find_user(users, "bob")
print(u, err)
print(find_user(users, "ada").admin)
Output
nil	no user called bob
true

The caller decides: check the nil, or wrap the call in assert to turn the failure into an error.
