Weak Tables and the Garbage Collector

lesson 7.022 of 3 in milestone 75 min2 practice tasks

How Lua frees memory and how to work with it - reachability, collectgarbage, weak keys and weak values with __mode, caches that do not leak, attaching data to objects without keeping them alive, __gc finalizers, and to-be-closed variables for resources that must be released on time.

Reachable means alive

Lua frees memory automatically. An object (a table, a function, a coroutine, a long string) stays alive while it is reachable: from a global, a local that is still in scope, a field of another reachable table, or an upvalue of a reachable function. Once nothing reaches it, the garbage collector may free it at any later moment.

Lua
local before = collectgarbage("count")         -- memory in use, in kilobytes
do
    local big = {}
    for i = 1, 100000 do big[i] = { i } end
end                                             -- big is out of scope: unreachable
collectgarbage()                                -- run a full collection now
print(collectgarbage("count") - before < 100)   --> true: the memory came back

You rarely need to call collectgarbage() yourself; it is useful in tests and for measuring.

The problem with ordinary tables

A table holds its keys and values strongly: anything stored in it stays reachable. A cache or a registry built from an ordinary table therefore keeps every object it has ever seen alive forever, which is a memory leak.

Weak tables

The __mode field of a table's metatable makes its references weak: they do not count for reachability.

__mode Weak part Entry disappears when
"k" keys the key object is no longer reachable elsewhere
"v" values the value object is no longer reachable elsewhere
"kv" both either is unreachable

Only objects can disappear; numbers, booleans and short strings are values, never collected out of a weak table.

Lua
local cache = setmetatable({}, { __mode = "v" })

local function load_image(name)
    local image = cache[name]
    if not image then
        image = { name = name, pixels = string.rep("x", 1000) }   -- stands in for slow loading
        cache[name] = image
    end
    return image
end

local hero = load_image("hero.png")
load_image("tree.png")                    -- nobody keeps this one
collectgarbage()
print(cache["hero.png"] ~= nil, cache["tree.png"] ~= nil)   --> true false
print(hero.name)

The cache gives the same image to everyone who asks while someone still uses it, and lets it go when nobody does.

Extra data for objects you do not own

Weak keys let you attach information to objects without changing them and without keeping them alive:

Lua
local visits = setmetatable({}, { __mode = "k" })

local function visit(node)
    visits[node] = (visits[node] or 0) + 1
end

local a = { id = "a" }
visit(a); visit(a)
print(visits[a])          --> 2
a = nil
collectgarbage()
print(next(visits))       --> nil: the entry went with the node

Lua's weak-keyed tables are ephemerons: a value that refers back to its own key does not keep the key alive.

Finalizers: __gc

A __gc metamethod runs when the collector frees a table. It is the hook for releasing something outside Lua, such as a file handle or a C library resource:

Lua
local log = {}
local function make_resource(name)
    return setmetatable({ name = name }, { __gc = function(r) table.insert(log, "freed " .. r.name) end })
end

do
    local r = make_resource("socket")
end
collectgarbage()
print(log[1])             --> freed socket

The __gc field must be in the metatable when setmetatable is called, or the finalizer is never registered. And when it runs is up to the collector: never rely on a finalizer to release something that must be released promptly.

To-be-closed variables

For resources that must be released at a known moment (closing a file, unlocking, ending a transaction), Lua 5.4 has to-be-closed variables. Declared with <close>, a variable's __close metamethod runs as soon as it goes out of scope, by any path, errors included:

Lua
local function open_resource(name, log)
    table.insert(log, "open " .. name)
    return setmetatable({ name = name }, { __close = function(r) table.insert(log, "close " .. r.name) end })
end

local log = {}
local ok = pcall(function()
    local db <close> = open_resource("db", log)
    local file <close> = open_resource("file", log)
    error("something failed")
end)
print(ok, table.concat(log, ", "))   --> false open db, open file, close file, close db

Like C++ destructors and Python's with, they close in reverse order of opening (lesson 3.05 introduced <close>).
