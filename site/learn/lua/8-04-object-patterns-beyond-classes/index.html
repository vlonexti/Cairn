Object Patterns Beyond Classes

lesson 8.044 of 5 in milestone 85 min2 practice tasks

Other ways to build objects in Lua - closures as objects with truly private state, constructors called like functions with __call, mixins that copy behaviour into a class, composition instead of inheritance, an event emitter, and validated objects with a proxy; with the trade-offs of each against the class pattern.

More than one way

Lesson 5.03's class pattern (a metatable whose __index is the class) is the most common way to write objects in Lua. It is not the only one, and some problems fit other patterns better.

Closures as objects

An object can be a table of functions that share local variables. The variables are completely private: no code outside can reach them.

Lua
local function newAccount(owner, balance)
    balance = balance or 0
    local history = {}

    local self = {}
    function self.deposit(amount)
        if amount <= 0 then error("amount must be positive", 2) end
        balance = balance + amount
        history[#history + 1] = "+" .. amount
    end
    function self.withdraw(amount)
        if amount > balance then return false, "insufficient funds" end
        balance = balance - amount
        history[#history + 1] = "-" .. amount
        return true
    end
    function self.balance() return balance end
    function self.statement() return owner .. ": " .. table.concat(history, " ") end
    return self
end

local a = newAccount("Ada", 100)
a.deposit(50)
print(a.withdraw(500))
a.withdraw(30)
print(a.balance(), a.statement(), a.history)       --> 120  Ada: +50 -30  nil

Methods are called with a dot (a.deposit), not a colon, because they do not need self: they reach the data through the closure. The cost is memory: each object has its own copy of every function, where class objects share one. For a few hundred objects that does not matter; for a million particles it does.

Constructors with __call

A metatable's __call lets a table be called like a function, which makes Point(1, 2) work instead of Point.new(1, 2):

Lua
local Point = {}
Point.__index = Point
setmetatable(Point, { __call = function(cls, x, y) return setmetatable({ x = x, y = y }, cls) end })

function Point:length() return math.sqrt(self.x ^ 2 + self.y ^ 2) end
Point.__tostring = function(p) return "(" .. p.x .. ", " .. p.y .. ")" end

local p = Point(3, 4)
print(tostring(p), p:length())

Mixins

A mixin is a table of methods copied into a class, so unrelated classes can share behaviour without inheriting from each other:

Lua
local Comparable = {
    __lt = function(a, b) return a:compareKey() < b:compareKey() end,
    __le = function(a, b) return a:compareKey() <= b:compareKey() end,
    max = function(self, other) if self < other then return other end return self end,
}

local Serialisable = {
    toText = function(self)
        local keys = {}
        for k in pairs(self) do keys[#keys + 1] = k end
        table.sort(keys)
        local parts = {}
        for _, k in ipairs(keys) do parts[#parts + 1] = k .. "=" .. tostring(self[k]) end
        return "{" .. table.concat(parts, ", ") .. "}"
    end,
}

local function include(class, mixin)
    for k, v in pairs(mixin) do class[k] = v end
    return class
end

local Card = { __index = nil }
Card.__index = Card
include(Card, Comparable)
include(Card, Serialisable)
function Card.new(rank, suit) return setmetatable({ rank = rank, suit = suit }, Card) end
function Card:compareKey() return self.rank end

local a, b = Card.new(10, "hearts"), Card.new(3, "spades")
print(b < a, a:max(b):toText())

Copying works for metamethods like __lt too, because they are just fields of the metatable.

Composition

Instead of a Player that inherits from Movable, which inherits from Drawable, give the player parts:

Lua
local function newPosition(x, y)
    return { x = x, y = y, move = function(self, dx, dy) self.x, self.y = self.x + dx, self.y + dy end }
end

local function newHealth(max)
    return { hp = max, max = max, hurt = function(self, n) self.hp = math.max(0, self.hp - n) end }
end

local player = { name = "Ada", pos = newPosition(0, 0), health = newHealth(20) }
player.pos:move(3, 1)
player.health:hurt(5)
print(player.name, player.pos.x, player.pos.y, player.health.hp)

Parts can be mixed freely (a chest has a position but no health), which is exactly why many game engines use components (the game development course's entity systems).

An event emitter

Objects that tell others when something happens:

Lua
local function newEmitter()
    local listeners = {}
    local e = {}
    function e.on(name, fn)
        listeners[name] = listeners[name] or {}
        table.insert(listeners[name], fn)
        return function()                    -- call this to unsubscribe
            for i, f in ipairs(listeners[name]) do
                if f == fn then table.remove(listeners[name], i) return end
            end
        end
    end
    function e.emit(name, ...)
        for _, fn in ipairs({ table.unpack(listeners[name] or {}) }) do fn(...) end
    end
    return e
end

local door = newEmitter()
local off = door.on("open", function(who) print(who .. " opened the door") end)
door.on("open", function() print("a bell rings") end)
door.emit("open", "Ada")
off()
door.emit("open", "Bob")

emit loops over a copy of the list, so a listener that unsubscribes while being called does not upset the loop.

Validated objects with a proxy

A proxy (lesson 5.02) can check every assignment:

Lua
local function validated(rules)
    local data = {}
    return setmetatable({}, {
        __index = data,
        __newindex = function(_, k, v)
            local rule = rules[k]
            if not rule then error("unknown field " .. tostring(k), 2) end
            local ok, msg = rule(v)
            if not ok then error(k .. ": " .. msg, 2) end
            data[k] = v
        end,
    })
end

local settings = validated({
    volume = function(v) return type(v) == "number" and v >= 0 and v <= 1, "must be from 0 to 1" end,
    name = function(v) return type(v) == "string" and #v > 0, "must be a non-empty string" end,
})
settings.volume = 0.5
print(settings.volume, pcall(function() settings.volume = 3 end))
print(pcall(function() settings.colour = "red" end))

Choosing

pattern good for
class with metatable many objects of one kind; shared methods; inheritance
closures truly private state; few objects
mixins sharing behaviour between unrelated classes
composition objects made of optional parts, like game entities
proxy checking or watching every change
