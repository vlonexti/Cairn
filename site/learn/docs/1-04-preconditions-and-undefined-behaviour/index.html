Preconditions and Undefined Behaviour

lesson 1.044 of 4 in milestone 15 min1 practice task

The contract a reference page describes - preconditions you must meet, what the function guarantees in return, what happens on failure - half-open ranges, the difference between checked and unchecked functions, exception guarantees, and why "the behaviour is undefined" is the most important sentence on a page.

A contract

Every reference page describes a contract between you and the function:

  • Preconditions: what must be true when you call it. Your responsibility.
  • Postconditions: what will be true afterwards, if you met the preconditions. The function's responsibility.
  • Failure behaviour: what happens when it cannot do its job even though you called it correctly (out of memory, file missing).

Preconditions are often written as "must", "shall", "requires", "expects", or as a list of allowed values: "count must not exceed size()", "first and last must form a valid range", "the pointer must not be null".

Undefined behaviour

When a page says "the behaviour is undefined if ...", it means breaking that precondition voids the contract completely. The program may crash, return garbage, corrupt something far away, or work perfectly on your machine and fail on another. The compiler is even allowed to assume it never happens and optimise accordingly.

C++
std::vector<int> v;
int x{ v[0] };        // operator[]: undefined if the index is not less than size()
int y{ v.at(0) };     // at(): checks, and throws std::out_of_range
v.front();            // undefined on an empty vector

Many libraries offer such pairs: an unchecked fast version whose misuse is undefined, and a checked version that reports misuse. The reference page tells you which one you are calling. (Debug builds of the Microsoft library add checks to many unchecked functions, which helps while testing but is not a guarantee.)

So, for every function you call, ask: what are its preconditions, and how do I know they hold? Either they are guaranteed by the code around the call (you just checked !v.empty()), or you check them first.

Half-open ranges

Almost every C++ library function that takes a range uses the half-open convention [first, last): first is included, last is not. So:

  • the number of elements is last - first;
  • an empty range has first == last;
  • "not found" is usually returned as last.

The same idea appears as "position and count" (substr(pos, count)) and in Python's slices s[start:stop]. When a page says "the range [pos, pos + count)", read it exactly that way.

What happens on failure

Reference pages describe failure in one of a few ways (lesson 2.02 goes deeper):

Style You see You do
exception "Throws std::out_of_range if ..." catch it where you can handle it, or let it propagate
error value "Returns -1 / nullptr / end() / an error code" check the result every time
error state "sets errno", "call GetLastError" read it immediately after the call
precondition only "the behaviour is undefined if ..." make sure it never happens

Exception guarantees

Pages for C++ functions that can throw often say what state things are left in:

  • No-throw guarantee (noexcept): it never throws.
  • Strong guarantee: if it throws, nothing changed, as if it was never called. std::vector::push_back gives this (for most element types).
  • Basic guarantee: if it throws, everything is still valid, but may have changed.
  • No guarantee: the page will say so, or say nothing; assume the worst.
