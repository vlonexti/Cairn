JavaScript, MDN and Node

lesson 4.022 of 4 in milestone 45 min1 practice task

Reading MDN Web Docs - syntax lines with optional parameters, return values and exceptions, the specification links and the browser compatibility tables - the ECMAScript specification behind them, and Node.js documentation with its stability index, callback and promise signatures and error codes.

MDN Web Docs

For JavaScript in the browser, the reference is MDN Web Docs (developer.mozilla.org), maintained by Mozilla with the other browser makers. Each page for a method follows a fixed layout:

Section Contains
Syntax every form of the call, one per line
Parameters each parameter; optional ones marked
Return value what comes back
Exceptions TypeError, RangeError ... and when
Description the behaviour in detail, including conversions
Examples runnable snippets, often with live output
Specifications a link to the exact section of the standard
Browser compatibility a table of which browser version supports what

The Syntax section lists each form separately instead of using brackets:

JavaScript
parseInt(string)
parseInt(string, radix)

The traps are in the Description

JavaScript converts types freely, and the Description section is where each method says how. Two famous examples, both clearly documented:

  • parseInt(string, radix) skips leading whitespace, reads an optional sign, and then as many valid digits as it can, ignoring the rest: parseInt("42px") is 42 and parseInt("1e3") is 1. Without a radix, a string starting with 0x is read as hexadecimal; with radix 10 it is not, so parseInt("0x1A", 10) is 0. A radix outside 2 to 36 gives NaN, and so does a string with no digits. Practice 4.02 implements these rules.
  • Array.prototype.sort() without a compare function converts the elements to strings and sorts them as text, so [10, 9, 1].sort() gives [1, 10, 9]. The page says so in its first paragraph, and recommends passing (a, b) => a - b for numbers.

Compatibility and Baseline

The Browser compatibility table shows, per browser, the first version supporting each feature, with notes for partial support. Newer pages also show a Baseline badge: "widely available" means it has worked in all major browsers for a long time; "newly available" means only recent versions. Check it before using a new API in a site people visit with older browsers.

The specification

Behind MDN is the ECMAScript specification (tc39.es/ecma262) for the language and the WHATWG and W3C specifications for browser APIs. They are written as step-by-step algorithms ("1. Let S be ? ToString(string). 2. Let R be ..."), which makes them precise and readable once you get used to them. MDN's Specifications section links straight to the right step list when you need the final word.

Node.js documentation

For JavaScript outside the browser, nodejs.org/docs has one page per module (fs, http, path ...). Things to read for:

  • The Stability index next to each API: 0 Deprecated, 1 Experimental (may change or vanish), 2 Stable, 3 Legacy (kept, but there is a better way). Production code should stay on 2.
  • Signatures with types in a bulleted list: fs.readFile(path[, options], callback), where options can be a string or an object, and callback receives (err, data).
  • Many modules come in three styles: callbacks (fs.readFile), promises (fs/promises, await readFile(...)), and synchronous (fs.readFileSync, which blocks the whole program while it runs).
  • Errors carry a code such as ENOENT (no such file) or ERR_INVALID_ARG_TYPE, documented on the Errors page; check err.code, not the message text, which may change.
  • "Added in: v18.0.0" and History tables, like Python's version notes.
