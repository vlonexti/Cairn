Man Pages, RFCs and Specifications

lesson 4.044 of 4 in milestone 45 min1 practice task

Reading the most precise documents you will meet - Unix man pages with their sections and ERRORS lists, RFCs with the MUST, SHOULD and MAY keywords of RFC 2119, ABNF grammars, errata, and turning one section of a specification into code and tests.

Man pages

On Linux and macOS, man shows the manual for commands and C functions. The manual is split into numbered sections, and the same name can exist in several:

Section Contains Example
1 commands man 1 ls
2 system calls man 2 open
3 C library functions man 3 printf
5 file formats man 5 passwd
7 overviews and conventions man 7 signal

A function's page has standard headings: NAME, SYNOPSIS (the #include and prototype), DESCRIPTION, RETURN VALUE, ERRORS, NOTES, BUGS, SEE ALSO. The ERRORS section lists every errno value the call can set and why (ENOENT: a component of the path does not exist; EACCES: permission denied), which is exactly the list your error handling has to consider. The same pages are online at man7.org, and many describe behaviour that Windows' C runtime copies.

RFCs

Internet protocols and formats are specified in RFCs (Requests for Comments) at rfc-editor.org: HTTP, TLS, JSON (RFC 8259), Base64 (RFC 4648), URIs (RFC 3986). An RFC never changes once published; corrections are listed as errata, and a newer RFC obsoletes or updates an older one (the header of each says which). Always check you are reading the current one.

Requirement keywords

Almost every RFC uses the keywords of RFC 2119, in capitals, with exact meanings:

Keyword Means
MUST, REQUIRED, SHALL an absolute requirement
MUST NOT, SHALL NOT an absolute prohibition
SHOULD, RECOMMENDED do it unless you have a good, understood reason not to
SHOULD NOT avoid unless you have a good reason
MAY, OPTIONAL truly optional; others must cope either way

A "MAY" for the sender becomes a "must handle" for the receiver: if a sender MAY add whitespace, every parser must accept it. Reading a spec well means sorting its sentences into these buckets.

ABNF grammars

Syntax in RFCs is written in ABNF (RFC 5234):

Text
version     = 1*DIGIT "." 1*DIGIT        ; one or more digits, a dot, one or more digits
DIGIT       = %x30-39                    ; the characters 0 to 9
hex-pair    = 2HEXDIG                    ; exactly two hex digits
header      = name ":" *WSP value        ; *WSP: zero or more spaces or tabs
flag        = "on" / "off"               ; / is "or"
option      = [ "-" ] name               ; [ ] is optional

* means "any number", 1* "at least one", n "exactly n", [ ] optional, / alternatives, "..." a literal (case-insensitive in ABNF), and %x41 a character by code. A grammar like this is a ready-made checklist for a parser and its tests.

Turning a section into code

The method that works for specifications of any size:

  1. Read the section twice: once for the idea, once for the rules.
  2. List every MUST and MUST NOT as a test case, including what to do with input that breaks them (reject? ignore?).
  3. Collect the spec's own examples and test vectors; many RFCs have an appendix of them (RFC 4648 section 10 lists Base64 test vectors).
  4. Write the code, then run it against both lists.
  5. Note every SHOULD and MAY you chose to follow or not, in a comment, so the next reader knows it was a decision.

Practice 4.04 does this for Base64, and the milestone project for Semantic Versioning, a short specification with famously precise ordering rules.
