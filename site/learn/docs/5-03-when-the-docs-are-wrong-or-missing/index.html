When the Docs Are Wrong or Missing

lesson 5.033 of 4 in milestone 55 min1 practice task

What to do when documentation and behaviour disagree - checking the version first, reading changelogs and migration guides, errata and known issues, weighing community answers and AI suggestions, reporting documentation bugs well, and protecting your code against behaviour that is not documented.

First suspect: the version

Most "the documentation is wrong" moments are really "I am reading the documentation for a different version". Check, in this order:

  1. Which version of the library, language or OS are you actually using? (--version, the package file, _MSC_VER, sys.version.)
  2. Which version is the page about? Look for a version selector, "Added in", "(since C++20)", "Changed in version" notes.
  3. Is there a changelog or release notes entry between the two?

Changelogs and migration guides

A changelog lists what changed in each release, usually grouped as Added, Changed, Deprecated, Removed, Fixed and Security. Many projects follow Semantic Versioning (the milestone 4 project), so the version number already warns you: a new major version may break your code, minor and patch versions should not.

When you upgrade across several versions, read every entry in between, not only the latest: a key renamed in version 2 and a default changed in version 3 both affect you. Larger projects publish a migration guide ("Upgrading from 2.x to 3.0") that lists breaking changes with before-and-after code. Practice 5.03 is a migration written from a changelog.

Things a changelog entry tells you that a reference page often does not:

  • what the old behaviour was, so you can recognise it in existing code;
  • whether a change is breaking or only a fix;
  • the deprecation timeline: a function marked deprecated in 2.3 may be removed in 3.0.

When the page really is wrong

Documentation is written by people and has mistakes, especially in corners: a wrong default, a missing error case, an example that no longer compiles. Signs you have found one:

  • your experiment (lesson 5.02) contradicts the page, on the version the page describes;
  • the implementation (lesson 4.03) clearly does something else;
  • the issue tracker or errata list mentions it.

Then:

  1. Trust the behaviour you can test, but write a learning test for it, since a fix might change it.
  2. Check errata and issues: RFCs have errata pages; libraries have issue trackers; cppreference pages have discussion pages and are corrected quickly.
  3. Report it, briefly and concretely: the page and section, what it says, what actually happens (with a minimal program), and the version. Most documentation is open to contributions: cppreference is a wiki, Microsoft Learn pages have an "Edit" link to GitHub, MDN is on GitHub too.

Community answers and AI suggestions

Answers from forums, Q&A sites, blog posts and AI assistants are often the fastest way to find which function to use. They are also often out of date, written for another platform or version, or simply wrong in a detail, and an AI suggestion can name a function or parameter that does not exist at all. Treat them as leads:

  • Look up every function they use on its reference page.
  • Check the date and version they were written for.
  • Prefer answers that link to documentation, and be suspicious of ones that only say "this works for me".
  • Run the experiment yourself.

Building on undocumented behaviour

Sometimes you must rely on something no page promises: an undocumented message format, the order of results, a timing. If you do:

  • Isolate it in one function, so there is one place to change.
  • Write a test that fails loudly if the behaviour changes.
  • Leave a comment saying it is undocumented and how you found out.
  • Prefer a documented alternative the moment one exists.
