Return Values and Error Reporting

lesson 2.022 of 4 in milestone 25 min1 practice task

The many ways standard library functions report their results - end iterators, npos, pairs with a bool, optional, error codes, exceptions and the paired throwing and non-throwing overloads of std::filesystem - and how to read each from the reference page and handle it correctly.

Read the Return value section every time

Two functions that look alike can report results in completely different ways. The Return value and Exceptions sections are where you find out. The common patterns in the standard library:

Pattern Example "Not found" or failure looks like
end iterator std::find, map::find the last / end() you passed or own
npos std::string::find std::string::npos, the largest size_t
pair with a bool map::insert, set::insert .second == false: already there; .first points to the existing one
std::optional your own APIs, many libraries empty optional
result struct std::from_chars ec != std::errc{}; ptr says where it stopped
exception vector::at, std::stoi, std::filesystem std::out_of_range, std::invalid_argument, filesystem_error
bool std::filesystem::remove false: there was nothing to remove (not an error!)

Insert, and what "inserted" means

Maps have several ways to add an element, and their pages differ in one crucial detail: what happens when the key already exists.

Call Key missing Key present
m[key] = value inserts overwrites
m.insert({key, value}) inserts does nothing; returns {it, false}
m.try_emplace(key, args...) inserts does nothing, and does not even build the value
m.insert_or_assign(key, value) inserts, returns {it, true} overwrites, returns {it, false}
m.at(key) throws std::out_of_range returns a reference

A common bug: using insert to update a value. It compiles, runs, and silently keeps the old value; the page said so.

Two overloads: throwing and not throwing

std::filesystem offers most functions twice:

C++
std::uintmax_t file_size(const std::filesystem::path& p);                                   // (1)
std::uintmax_t file_size(const std::filesystem::path& p, std::error_code& ec) noexcept;     // (2)

(1) throws std::filesystem::filesystem_error on failure. (2) never throws: it sets ec and returns a documented value, here static_cast<std::uintmax_t>(-1). Use (2) where failure is expected and normal (a file that may not exist), (1) where failure means something is really wrong.

Results that need two answers

std::from_chars reports where it stopped and whether it worked:

C++
#include <charconv>
#include <iostream>
#include <string_view>

void show(std::string_view text)
{
    int value{ -1 };
    const auto result{ std::from_chars(text.data(), text.data() + text.size(), value) };
    std::cout << '"' << text << "\": ";
    if (result.ec == std::errc::invalid_argument) std::cout << "no number";
    else if (result.ec == std::errc::result_out_of_range) std::cout << "too big";
    else std::cout << value << ", stopped after " << (result.ptr - text.data()) << " chars";
    std::cout << '\n';
}

int main()
{
    show("42");
    show("42px");
    show("px");
    show("99999999999");
}

To accept only a whole string, you must check both: no error, and ptr reached the end. The page tells you this indirectly ("on success, ptr points at the first character not matching the pattern"); turning such sentences into checks is the skill.

Errors you can ignore and errors you cannot

Some outcomes look like failures but are normal: std::filesystem::remove returning false for a missing file, map::insert finding the key. Others look harmless but are bugs: discarding the result of a [[nodiscard]] function, or an std::stoi that read "12abc" as 12 when you expected an error. The page decides which is which, not your intuition.
