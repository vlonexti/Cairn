Checking Your Understanding with Experiments

lesson 5.022 of 4 in milestone 55 min1 practice task

Confirming what you think a page says with small, focused programs - one question per experiment, predicting the result first, trying the edge cases, using Compiler Explorer, turning experiments into learning tests that keep checking the behaviour - and the limits of experiments when behaviour is undefined or unspecified.

Reading is not knowing

After reading a reference page you have a belief about how a function behaves. A two-minute experiment turns it into knowledge, or shows you misread. Experienced programmers do this constantly, especially for anything with edge cases: rounding, string splitting, time zones, encodings, regular expressions.

How to run an experiment

  1. One question. "What does std::round(-2.5) return?" not "how does rounding work?".
  2. Predict first. Write down what you expect before running it. A surprise is the whole point; without a prediction you will not notice one.
  3. Smallest program. No framework, no project: a main with a few prints, or a test.
  4. Cover the edges. Zero, negative, empty, the boundary value, one past it, the largest value.
  5. Compare with the page. If the result disagrees with your reading, re-read. If it disagrees with the page itself, see lesson 5.03.
C++
#include <cmath>
#include <iostream>

int main()
{
    // Question: how do the rounding functions treat halves?
    // Prediction: round goes away from zero; nearbyint goes to even.
    for (double x : { 0.5, 1.5, 2.5, -0.5, -2.5, 2.4999 })
        std::cout << x << ": round " << std::round(x) << ", nearbyint " << std::nearbyint(x)
                  << ", trunc " << std::trunc(x) << ", cast " << static_cast<int>(x) << '\n';
}

The pages explain the results: std::round rounds halves away from zero; std::nearbyint uses the current rounding mode, which is round-half-to-even by default (so 0.5 and 2.5 both go to the even neighbour); std::trunc and the cast drop the fraction towards zero. Seeing all four side by side fixes it in memory better than reading four pages.

Compiler Explorer

godbolt.org compiles and runs small programs in the browser with many compilers and versions. It is ideal for experiments: you can check whether the behaviour differs between MSVC, GCC and Clang, or between C++17 and C++20, in seconds, and share a link to the result with a colleague.

Learning tests

An experiment you run once is forgotten; an experiment written as a test keeps checking:

C++
TEST("std::round rounds halves away from zero") {
    CHECK_EQ(std::round(2.5), 3.0);
    CHECK_EQ(std::round(-2.5), -3.0);
}
TEST("our JSON library keeps the order of object keys") {
    CHECK_EQ(json::parse(R"({"b":1,"a":2})").keys(), (std::vector<std::string>{ "b", "a" }));
}

Tests like the second one are called learning tests: they pin down behaviour of a library that your code relies on, especially behaviour the documentation is vague about. When you upgrade the library and one fails, you know immediately which assumption broke, instead of finding out from a bug report.

What experiments cannot tell you

An experiment shows what this compiler, library and machine did this time. That is the documented behaviour only when the page promises it:

  • Undefined behaviour can "work" in an experiment and fail elsewhere: reading past the end of an array may print plausible numbers. Never take a successful run as proof that something is allowed.
  • Unspecified and implementation-defined results (the order of iteration of an unordered_map, the size of long, the text of what()) may differ between compilers or versions.
  • Timing and threads: a race condition may hide in a hundred runs and appear in the hundred-and-first.

So the rule is: the page says what you may rely on; the experiment confirms you read it correctly.
