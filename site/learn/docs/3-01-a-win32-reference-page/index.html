A Win32 Reference Page

lesson 3.011 of 4 in milestone 35 min1 practice task

Reading a Microsoft Learn page for a Windows API function from top to bottom - the syntax block and its types, parameter directions, the exact wording of the return value, the remarks where the surprises live, and the requirements table with header, library, DLL and minimum Windows version - using GetModuleFileNameW as the example.

Where Windows documents itself

Every Windows API function has a page on Microsoft Learn (learn.microsoft.com), under "Windows App Development > Win32 API" or by searching the function name. The pages share one layout, and once you know it you can use functions you have never seen before. The Win32 course uses these functions; this milestone is about reading their pages precisely.

We will read the page for GetModuleFileNameW, which gives the full path of an executable or DLL. What follows describes the page in our own words, section by section.

Syntax

C++
DWORD GetModuleFileNameW(
  [in, optional] HMODULE hModule,
  [out]          LPWSTR  lpFilename,
  [in]           DWORD   nSize
);
  • Types are Windows typedefs: DWORD is a 32-bit unsigned integer, LPWSTR a pointer to a wide (UTF-16) string, HMODULE a handle to a loaded module. The "Windows Data Types" page lists them all.
  • Directions in brackets: [in] you provide, [out] the function fills, [in, out] both, and optional means you may pass null. (In headers these appear as SAL annotations; lesson 3.02.)
  • Names use the old Hungarian prefixes, which are worth decoding: lp long pointer, n or cch a count of characters, cb a count of bytes, h a handle, dw a DWORD, b a BOOL.

Parameters

The page describes each parameter. For this function:

  • hModule: the module whose path you want; null means the executable of the current process.
  • lpFilename: the buffer that receives the path.
  • nSize: the size of that buffer in characters (WCHARs), not bytes.

"Characters, not bytes" is the kind of detail that causes buffer overruns when missed: a buffer of MAX_PATH wchar_ts is 520 bytes, and passing sizeof(buffer) would claim twice the real size.

Return value

This section must be read word by word. Paraphrased, it says:

  • On success, the return value is the length of the string copied, in characters, not including the terminating null.
  • If the buffer is too small, the path is truncated to nSize characters including the null, the function returns nSize, and the last error is set to ERROR_INSUFFICIENT_BUFFER.
  • On failure, the return value is 0; call GetLastError for the reason.

So a return value equal to nSize is not success; it is a truncated result. Code that only checks for 0 silently uses a cut-off path. The correct pattern, a loop that grows the buffer, is the first practice task.

Remarks

The remarks hold the surprises: which module handle to use for a DLL, what happens when the module was loaded from a long path, and an old Windows XP note that the result may not be null-terminated when truncated. Older pages often keep notes like this about past versions; check whether they apply to the systems you support.

Requirements

A table at the bottom:

Requirement Value (summarised)
Minimum supported client / server the first Windows version that has the function
Header libloaderapi.h (include windows.h)
Library Kernel32.lib, to link against
DLL Kernel32.dll, where it lives at run time

There is also the line "Unicode and ANSI names: GetModuleFileNameW (Unicode) and GetModuleFileNameA (ANSI)". The plain name GetModuleFileName is a macro that picks one depending on whether UNICODE is defined. Call the W versions explicitly with wide strings: the A versions convert through the current code page and lose characters.
