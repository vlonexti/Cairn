Reading Headers and Source Code

lesson 4.033 of 4 in milestone 45 min1 practice task

What to do when the documentation is thin or missing - reading a library's header for its real declarations, defaults and doc comments, Doxygen tags, finding the implementation with Go to Definition, using a project's tests as examples, and reading the source of the standard library itself.

When the docs are not enough

Many libraries, especially small open-source ones, have a README and little else. Even good documentation has gaps. Then the code is the documentation, and it has one great advantage: it is exactly the version you are using.

The usual order to look:

  1. The header (or the module's public file): every declaration, with its exact types and defaults.
  2. Doc comments in that header.
  3. The project's tests: they show how the authors expect the API to be called, including edge cases.
  4. The examples folder, if there is one.
  5. The implementation, for what is still unclear.
  6. The issue tracker: someone may have hit the same question; the answer may be "that is a bug".

Reading a header

A header is a contract summary. From this one you can learn a lot without seeing any code behind it:

C++
namespace tinyini {

/// A parsed configuration file.
class Config
{
public:
    /// Parses `text`. Returns std::nullopt on a malformed line and, if `errorLine`
    /// is not null, stores that line's number (1-based) there.
    static std::optional<Config> parse(std::string_view text, int* errorLine = nullptr);

    /// @return the value, or nullptr if the section or key does not exist.
    /// @note The pointer is valid until this Config is modified or destroyed.
    const std::string* find(std::string_view section, std::string_view key) const;

    /// @return the value as an integer; std::nullopt if it is missing
    ///         **or** is not a complete integer.
    std::optional<long long> findInt(std::string_view section, std::string_view key) const;
};

} // namespace tinyini
  • static + std::optional<Config>: you create one by parsing, and parsing can fail.
  • int* errorLine = nullptr: optional out-parameter; pass a pointer to get the line.
  • const std::string* returned from a const function: you read it but do not own it, and the note tells you how long it lives.
  • findInt's comment reveals a design decision: "missing" and "not a number" give the same result. If your program must tell them apart, use find first. Practice 4.03 depends on noticing exactly this.

Doc comments and Doxygen

Most C and C++ libraries write doc comments in the Doxygen style (/// or /** */), which tools turn into web pages:

Tag Means
@brief one-line summary
@param name a parameter; @param[out] name for outputs
@return / @returns the return value
@throws / @exception exceptions
@pre, @post preconditions and postconditions
@note, @warning remarks you should not skip
@deprecated do not use in new code

Editors show these comments when you hover over a call, so the habit of hovering often answers the question without opening a browser.

Into the implementation

In Visual Studio or VS Code, Go to Definition (F12) jumps from a call to its declaration, and again to the implementation if the source is available. Read with a question in mind ("what happens if the key is empty?") and follow only the code paths that answer it; reading a library front to back is rarely worth it.

Two cautions:

  • Behaviour you find in the implementation but not in the documentation is not a promise. It may change in the next version. If you rely on it, write a test (lesson 5.02) so you notice.
  • Check you are reading the same version you build with: the main branch on GitHub may be ahead of your release.

The standard library's own source

Microsoft's C++ standard library is open source (github.com/microsoft/STL), as are libstdc++ (GCC) and libc++ (LLVM). It is dense code, with names like _Myfirst and _Mylast to avoid clashing with your macros, but stepping into std::vector::push_back in the debugger and seeing the growth and the debug checks for yourself is a good way to understand what the reference pages describe.
