SAL Annotations and Buffer Sizes

lesson 3.022 of 4 in milestone 35 min1 practice task

The source annotation language in Windows headers - In, Out, Inout, opt, Out_writes and friends - what each promises about a parameter, characters versus bytes, and the three patterns Windows uses for buffers whose size you do not know in advance.

Annotations in the headers

Open a Windows header and the declarations look like this:

C++
DWORD GetEnvironmentVariableW(
    _In_opt_ LPCWSTR lpName,
    _Out_writes_to_opt_(nSize, return + 1) LPWSTR lpBuffer,
    _In_ DWORD nSize);

The _In_, _Out_writes_... markers are SAL, the Source Annotation Language. They compile to nothing, but they document the contract precisely, and the compiler's code analysis (/analyze) checks calls against them. The documentation's [in], [out] and optional come from the same information.

Annotation Means
_In_ read only; must not be null
_In_opt_ read only; may be null
_Out_ the function writes it; must not be null
_Inout_ read and then written
_In_reads_(n) reads n elements
_In_reads_bytes_(n) reads n bytes
_Out_writes_(n) writes up to n elements (the buffer must hold n)
_Out_writes_to_(n, count) buffer holds n, the function writes count
_Outptr_ receives a pointer the function allocates or returns
_Ret_maybenull_ the return value may be null
_Success_(expr) the out parameters are valid only when expr is true

_Out_writes_to_opt_(nSize, return + 1) above reads: the buffer may be null; it holds nSize characters; on success the function writes "return value + 1" characters (the string plus its null).

Characters or bytes

Windows counts in two units, and the names and annotations tell you which:

  • cch..., nSize "in characters", _Out_writes_(n) on a WCHAR*: count wchar_ts.
  • cb..., "in bytes", _Out_writes_bytes_(n): count bytes. A wide string of 10 characters plus its null is 22 bytes.

Mixing them is one of the most common Windows bugs, either an overrun (bytes passed where characters were expected) or a truncation (the other way round).

Three patterns for unknown sizes

Often you cannot know how big the result will be. Windows functions use one of three patterns, and the Return value section tells you which:

1. Ask for the size first. Call with a null buffer (or too small a one); the function returns the size needed, then you allocate and call again. GetEnvironmentVariableW: if the buffer is too small, it returns the size required including the null; on success it returns the length excluding the null. Those two different meanings of the return value are how you tell the cases apart.

2. Grow until it fits. Some functions never tell you the size; they truncate. GetModuleFileNameW (lesson 3.01) returns nSize when truncated, so you double the buffer and try again.

3. Size in, size out. A pointer parameter holds the buffer size going in and receives the size needed or used coming out, often with the error ERROR_MORE_DATA (234) when the buffer was too small. The registry function RegQueryValueExW works this way with lpcbData, in bytes. Passing a null data pointer with a valid size pointer asks only for the size.

In all three, the value can change between the calls: an environment variable or a registry value may be rewritten by another thread or process. Robust code loops: query, allocate, fetch, and if it is still too small, go round again.
