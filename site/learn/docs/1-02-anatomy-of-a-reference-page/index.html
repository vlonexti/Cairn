Anatomy of a Reference Page

lesson 1.022 of 4 in milestone 15 min1 practice task

The sections nearly every reference page has - synopsis, description, parameters, return value, errors, complexity, notes, requirements, examples and see also - what each one tells you, and the order to read them in when you have a question.

The same shape everywhere

Reference pages from cppreference, Microsoft, Python, MDN and man pages look different, but they share a structure. Once you know it, you can read any of them quickly. Here is a reference page for an imaginary function, written in the usual style.

trim_left (sample page)

Declared in header <textutil.h>

C++
std::string trim_left(std::string_view s, std::string_view chars = " \t\n");   // (1)
std::string trim_left(std::string_view s, char c);                              // (2)

Removes leading characters from s.

  1. Removes every leading character that appears in chars.
  2. Removes every leading character equal to c.

Parameters

  • s: the text to trim
  • chars: the set of characters to remove; if empty, nothing is removed
  • c: the character to remove

Return value

A copy of s without the removed characters. If every character is removed, an empty string.

Exceptions

May throw std::bad_alloc if allocation fails.

Complexity

Linear in the size of s times the size of chars.

Notes

Characters are compared as bytes; multi-byte UTF-8 sequences in chars are treated as separate bytes.

Example

trim_left(" hello ") returns "hello ".

See also

trim_right, trim

The sections

Section Tells you Read it for
Name and header / module what to #include or import getting it to compile
Synopsis / syntax every overload with exact types which version you are calling
Description what it does, often per overload the main behaviour
Parameters meaning and allowed values of each what you may pass
Return value what comes back, in every case handling the result
Errors / exceptions how failure is reported handling failure
Complexity how cost grows choosing between options
Notes / remarks surprises, edge cases, history the bugs you have not had yet
Requirements / availability version, platform, library to link will it work where you ship
Example the function in use a starting point (not production code)
See also related functions finding a better fit

Reading order

Do not read a reference page top to bottom like a story. Go to the section that answers your question, then check the ones that could change the answer:

  1. Synopsis: find the overload you are calling. With default arguments and overloads, trim_left(s, 'x') calls (2), not (1) with a one-character string.
  2. Description and Parameters: what it does with your arguments, including the edge values (empty, zero, null, negative, too large).
  3. Return value and Errors: every outcome you must handle.
  4. Notes: always skim them. This is where pages hide "not thread-safe", "the result is not null-terminated", "deprecated", and "behaviour changed in version 3".
  5. Requirements: once, before you rely on it.

Words that matter

Reference pages are written carefully, so small words carry meaning:

  • "must", "shall": a rule for you; breaking it is an error, often undefined behaviour (lesson 1.04).
  • "may": the function is allowed to do this. "May throw" means you must be ready for it even if you have never seen it happen.
  • "unspecified": one of several results, with no promise which. "implementation-defined": the compiler or library chooses and documents it.
  • "if ... otherwise": two cases; check which applies.
  • "the behaviour is undefined": anything can happen, including appearing to work.
