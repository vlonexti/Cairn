Kinds of Documentation

lesson 1.011 of 4 in milestone 15 min1 practice task

Why reading documentation is a core programming skill, the four kinds of documentation (tutorials, how-to guides, reference and explanation) and what each is for, the other sources you will meet, and how to pick the right one for the question you have.

The skill under every other skill

Nobody remembers every function. Working programmers spend a large part of each day reading: a reference page to check what a function returns on failure, a guide to set up a library, a specification to see what a file format allows. The difference between a beginner and an experienced programmer is often not what they know, but how quickly and precisely they can find out.

Reading documentation well means three things:

  1. Knowing which kind of document answers your question.
  2. Reading it precisely: every word on a reference page is there for a reason.
  3. Turning what it says into code that handles every case it describes.

This course trains all three, mostly with C++, then with Windows, Python, JavaScript and specifications.

Four kinds of documentation

Good documentation sets are usually split into four kinds, because each answers a different need. (This division is often called the Diátaxis framework.)

Kind Answers Reads like Example
Tutorial "I'm new, show me" a lesson: do this, then this "Your first window with raylib"
How-to guide "How do I do X?" a recipe with steps "How to read a file asynchronously"
Reference "What exactly does this do?" a dry, complete description the page for std::vector::insert
Explanation "Why is it like this?" an essay or background article "About processes and threads"

They mix badly. A tutorial that stops to list every parameter loses the learner; a reference page that tells a story hides the one fact you need. So when you search, decide first which one you want:

  • Learning something new: a tutorial, then explanation.
  • Trying to get a task done: a how-to, then the reference for each function it uses.
  • Debugging, or checking an edge case: the reference, always.

Other sources you will meet

Source Good for Watch out for
Specifications and standards (the C++ standard, RFCs, file format specs) the final word on what is allowed dense, precise language (milestone 4)
Header files and source code what really exists, in the version you have no explanations, easy to misread (lesson 4.03)
Doc comments in code (///, docstrings) quick help in your editor may be short or out of date
Release notes and changelogs what changed between versions easy to skip, costly when you do (lesson 5.03)
Examples and samples seeing the pieces used together usually skip error handling (lesson 5.01)
Q&A sites, forums, blog posts, AI answers quick pointers to the right function may be old, wrong, or for another version; confirm against the reference

Treat the last row as leads, not facts: they tell you where to look, and the reference page tells you whether it is true.

Where documentation lives

For the languages and platforms in this course:

  • C++ standard library: cppreference.com (community reference), the standard itself for the final word.
  • Windows: Microsoft Learn (learn.microsoft.com), the Win32 and C runtime references.
  • Python: docs.python.org, the library reference and the language reference.
  • JavaScript: MDN Web Docs for the language and browser APIs, nodejs.org/docs for Node.
  • Unix-like systems: man pages (man 2 open).
  • Libraries: their own site, README, and headers.

Bookmark the reference for each language you use. Searching the web for every question costs time and often lands on an old forum answer instead of the reference.
