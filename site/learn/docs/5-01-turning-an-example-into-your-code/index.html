Turning an Example into Your Code

lesson 5.011 of 4 in milestone 55 min1 practice task

Why documentation examples are not production code - what they leave out on purpose - and a dependable routine for adapting one - run it unchanged, understand every line against the reference, make it a function, add every error path the reference describes, release resources on every path, and test the edges.

Examples are written to teach

The example on a reference page exists to show one idea as clearly as possible. To stay short it usually leaves out exactly what your program needs:

Left out Why it matters
error handling the failure cases are on the page, just not in the example
cleanup on error paths a handle or allocation leaks when something fails halfway
loops for partial results a single read or send may do only part of the work
buffer sizing fixed buffers like char buf[256] that are too small for real data
real inputs hard-coded names, paths and values
thread safety, encoding, limits outside the example's one idea

Copying an example straight into a program is the most common way documentation causes bugs. The fix is a routine.

The routine

  1. Run it unchanged. In a scratch project, or Compiler Explorer. If it does not work as shown, you have learned something about your setup (version, platform, missing library) before mixing it with your own code.
  2. Explain every line. For each call, open its reference page and check: what does each argument mean here? What can it return? This is where you find the cases the example ignores.
  3. Make it a function with real parameters instead of hard-coded values, and a return type that can express failure (std::optional, an error code, an exception, matching the rest of your program).
  4. Add every error path the reference pages list. For each call: what happens if it fails, and what must already-acquired resources do then?
  5. Release resources on every path. Wrap handles in RAII types (a small class whose destructor closes them, or std::unique_ptr with a custom deleter), so early returns cannot leak.
  6. Handle partial results. Anything that reads, writes, sends or receives in pieces needs a loop (the Networking course's sendAll is the classic case).
  7. Test the edges the reference describes: empty input, the largest input, the failure of each call (practice 5.01 fakes them).

An example, adapted

A typical example for a file API looks like this:

C++
Handle h = fakeOpen("notes.txt");
char buffer[256];
long n = fakeRead(h, buffer, sizeof buffer);
std::cout << std::string(buffer, n);
fakeClose(h);

Reading the three reference pages shows five problems: fakeOpen can fail and return INVALID; fakeRead may return fewer bytes than the file has, so one call does not read the whole file; it returns -1 on an error, which std::string(buffer, n) would turn into a huge length; a file longer than 256 bytes is cut off; and if anything throws between open and close, the handle leaks.

The adapted version:

C++
class File
{
public:
    explicit File(Handle h) : h_{ h } {}
    ~File() { if (h_ != INVALID) fakeClose(h_); }
    File(const File&) = delete;
    File& operator=(const File&) = delete;
    Handle get() const { return h_; }
private:
    Handle h_;
};

std::optional<std::string> readWholeFile(const std::string& name)
{
    File file{ fakeOpen(name) };
    if (file.get() == INVALID) return std::nullopt;
    std::string contents;
    char buffer[4096];
    for (;;)
    {
        const long n{ fakeRead(file.get(), buffer, sizeof buffer) };
        if (n < 0) return std::nullopt;          // error: the destructor still closes
        if (n == 0) return contents;             // end of file
        contents.append(buffer, static_cast<std::size_t>(n));
    }
}

Longer than the example, and every added line traces back to a sentence on a reference page.
