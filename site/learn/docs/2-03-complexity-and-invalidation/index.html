Complexity and Invalidation

lesson 2.033 of 4 in milestone 25 min1 practice task

Two promises every container page makes - how cost grows (constant, amortised constant, logarithmic, linear) and which iterators, pointers and references stay valid after each operation - how to read the invalidation rules, and the bugs that come from ignoring them.

Complexity is a guarantee

Every function page on cppreference ends its description with Complexity. It is not a hint, it is a promise the library must keep, and it decides which container and which function you choose:

Phrase Means Example
constant the same cost whatever the size vector::operator[], vector::size
amortised constant usually constant, occasionally expensive, constant on average vector::push_back (sometimes reallocates)
logarithmic grows slowly, like a binary search map::find, std::lower_bound
linear in n proportional to the size std::find, vector::insert in the middle
average constant, worst linear hash tables unordered_map::find
O(n log n) comparisons sorting std::sort

Read the exact wording: "linear in the distance between pos and the end" (inserting near the end of a vector is cheap), "exactly N applications of the predicate" (you can count on side effects happening exactly once each).

Invalidation: when your iterators go bad

Iterators, pointers and references into a container can become invalid when the container changes. Using an invalid one is undefined behaviour (lesson 1.04): it may read freed memory, read the wrong element, or crash. Each modifying function's page says what it invalidates, and the container pages have a summary table. For the containers you use most:

Container Operation Invalidated
vector, string push_back, insert, reserve if capacity changes all iterators, pointers, references
vector, string insert/push_back without reallocation those at or after the insertion point (and end())
vector erase those at or after the erased element
deque insert at either end all iterators, but not references
list, map, set insert nothing
list, map, set erase only the erased element
unordered_map insert causing a rehash all iterators, but not references

The classic bugs

C++
// 1. Growing a vector while iterating over it
for (int x : v)
    if (x % 2 == 0) v.push_back(x);       // push_back may reallocate: the loop's iterators dangle

// 2. Keeping a reference across a push_back
int& first{ v[0] };
v.push_back(7);                           // may reallocate
std::cout << first;                       // may read freed memory

// 3. Erasing in a loop the wrong way
for (auto it{ v.begin() }; it != v.end(); ++it)
    if (*it < 0) v.erase(it);             // 'it' is invalid after erase; ++it is undefined

The fixes come straight from the pages:

  • erase returns an iterator to the element after the erased one: it = v.erase(it); and only ++it when you did not erase.
  • Better still, std::erase_if(v, pred) (C++20) removes all matching elements in one linear pass.
  • For growing while reading, loop over indices up to the original size, or build the new elements in a separate vector and append them afterwards.
  • reserve before taking pointers, if the page's guarantee is what you need: "no reallocation takes place until the size exceeds the capacity".

Microsoft's debug library checks many of these and stops the program with a debug assertion about an invalid or incompatible iterator. The release build does not check: the bug is still there, just silent.
