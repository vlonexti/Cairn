Writing Documentation Others Can Use

lesson 5.044 of 4 in milestone 55 min1 practice task

Turning everything this course taught about reading documentation into writing it - doc comments that state the contract, what every function's documentation must answer, examples that are correct, READMEs that get someone started, changelogs, and keeping documentation true as the code changes.

Write the page you wished you had

Every frustration in this course came from documentation that left something out: the return value when the buffer is too small, the difference between missing and invalid, the version a feature arrived in. When you write code others use (including yourself in six months), write the documentation that would have saved you that time.

Doc comments that state the contract

For each public function, the comment should answer the questions of lesson 1.02, in a few lines:

C++
/// Reads a whole file into memory.
///
/// @param path  the file to read; may be relative to the current directory.
/// @return the file's contents, or std::nullopt if the file cannot be opened
///         or a read fails part way. An empty file gives an empty string.
/// @throws std::bad_alloc if the file does not fit in memory.
/// @note Not safe to call while another thread writes the same file.
std::optional<std::string> readWholeFile(const std::filesystem::path& path);

A checklist for each function:

  • What it does, in one sentence starting with a verb.
  • Each parameter: meaning, units (bytes or characters, seconds or milliseconds), allowed values, whether null or empty is allowed.
  • The result in every case, including the empty, missing and failed ones.
  • Errors: exceptions, error codes, what state things are left in.
  • Preconditions the caller must meet, and what happens if they do not.
  • Ownership and lifetime of anything returned by pointer or reference.
  • Thread safety and complexity, when they are not obvious.

Leave out what the signature already says ("count: the count"), and do not describe the implementation: say what, not how, so you can change the how.

Examples that are correct

An example in documentation is copied more than anything else you write (lesson 5.01), so:

  • make it compile and run, ideally by building it as part of your tests;
  • handle errors in it, or say plainly that it skips them for brevity;
  • show the most common use first, then the tricky ones.

README and the four kinds

A project's README is often the only page someone reads. It should say, in order: what the project does and for whom, how to install or build it, a minimal example that works, where the full documentation is, and the licence. Beyond that, keep the four kinds of documentation from lesson 1.01 apart: a tutorial for newcomers, how-to guides for tasks, the reference generated from your doc comments, and explanation for the design decisions.

Changelogs

Keep a CHANGELOG.md with one section per release and entries under Added, Changed, Deprecated, Removed, Fixed, Security. Write each entry for the person upgrading: what changed and what they must do about it. Mark breaking changes clearly, and match them to your version numbers (a breaking change means a new major version under Semantic Versioning).

Keeping it true

Documentation that is wrong is worse than none, because people trust it. Habits that keep it true:

  • Change the doc comment in the same commit as the behaviour.
  • Let tests check the claims you can test: every documented error case is a test case.
  • Compile the examples.
  • When someone asks a question the docs should have answered, fix the docs, not just the person's question.
