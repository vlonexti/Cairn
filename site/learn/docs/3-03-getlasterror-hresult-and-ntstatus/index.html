GetLastError, HRESULT and NTSTATUS

lesson 3.033 of 4 in milestone 35 min1 practice task

The three error systems you meet in Windows documentation - the per-thread last error, COM's HRESULT with its severity, facility and code bits, and the kernel's NTSTATUS - how a page tells you which one a function uses, how to decode each, and how to turn them into readable messages.

Which system does this function use?

The Return value section always names it. The common phrases:

The page says System
"If the function fails, the return value is zero (or NULL, INVALID_HANDLE_VALUE). To get extended error information, call GetLastError." last error
"Returns ERROR_SUCCESS if successful, or a system error code." (registry functions) the error code is the return value; GetLastError is not used
"If this function succeeds, it returns S_OK. Otherwise, it returns an HRESULT error code." HRESULT
"Returns STATUS_SUCCESS or an error status" (native and driver APIs) NTSTATUS

Note the second row: some functions return the error code directly, and calling GetLastError after them gives an unrelated value.

The last error

GetLastError returns a number kept per thread, set by the last function that chose to set it. Rules from the pages:

  • Read it immediately after the failed call; almost anything else may overwrite it.
  • Only read it when the page says the function failed. Many functions do not clear it on success, and some set it even on success (the page says so when it matters: CreateMutexW sets ERROR_ALREADY_EXISTS while succeeding, which is how you detect an existing mutex).
  • The values are the system error codes: 2 ERROR_FILE_NOT_FOUND, 5 ERROR_ACCESS_DENIED, 87 ERROR_INVALID_PARAMETER, 122 ERROR_INSUFFICIENT_BUFFER, 234 ERROR_MORE_DATA ... listed on the "System Error Codes" pages.

HRESULT

COM and many newer APIs return an HRESULT, a 32-bit value with fields:

Text
bit 31        severity: 0 success, 1 failure
bits 16-26    facility: which area produced it (7 = Win32, 4 = ITF ...)
bits 0-15     code

So negative means failure: test with SUCCEEDED(hr) (hr >= 0) and FAILED(hr) (hr < 0), never with hr == S_OK alone, because S_FALSE (1) is a success that means "it worked, but the answer is no".

Values you will see constantly:

Name Value Means
S_OK 0x00000000 success
S_FALSE 0x00000001 success, negative answer
E_FAIL 0x80004005 unspecified failure
E_INVALIDARG 0x80070057 an argument was invalid
E_OUTOFMEMORY 0x8007000E allocation failed
E_ACCESSDENIED 0x80070005 access denied

Notice E_INVALIDARG is 0x8007 followed by 0x0057: facility 7 (Win32) and code 87, ERROR_INVALID_PARAMETER. The macro HRESULT_FROM_WIN32(x) builds such values: for a positive error code it ORs in the failure bit and facility 7; zero and values that are already HRESULTs (zero or negative) pass through unchanged. So when you see 0x8007xxxx, the low 16 bits are a plain Win32 error code you can look up.

NTSTATUS

The kernel and ntdll use NTSTATUS, also 32 bits, but with two severity bits at the top:

Top two bits Severity Example
00 success STATUS_SUCCESS = 0
01 informational 0x40000000 and up
10 warning STATUS_BUFFER_OVERFLOW = 0x80000005
11 error STATUS_ACCESS_VIOLATION = 0xC0000005

That last one is familiar: a crashing program's exit code 0xC0000005 (lesson 1.03 of the Processes and Communication course) is an NTSTATUS.

Turning codes into messages

FormatMessageW with FORMAT_MESSAGE_FROM_SYSTEM turns a system error code (and many HRESULTs) into the text shown on the System Error Codes page. Log the number and the text: the number is searchable, the text is readable. Visual Studio's "Error Lookup" tool and the watch-window format @err,hr do the same while debugging.
