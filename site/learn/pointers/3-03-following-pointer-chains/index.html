Following Pointer Chains

lesson 3.033 of 5 in milestone 35 min1 practice task

Real programs reach data through several levels of pointers - a game reaches a player's health through the world, the level and the player. A chain can be written as a base address and a list of offsets, followed one read at a time with a null check at every step. Why chains survive restarts when single addresses do not.

Data at the end of a path

In a real program the value you care about is rarely in a variable you can name. A game's code might reach the local player's health like this:

C++
struct Stats  { int level; int health; int mana; };
struct Player { char name[16]; Stats* stats; };
struct World  { int tick; Player* players[8]; };
struct Game   { World* world; int localIndex; };

Game* game{ /* created at start-up */ };
int health{ game->world->players[game->localIndex]->stats->health };

Five arrows. Every object along the way lives on the heap, created at a different moment, so none of them is at a predictable address. What is predictable is the shape of the path: from a Game, the World* is at some offset; from the World, the player pointers start at another; from a Player, the Stats* is at another; and health is at offset 4 of Stats.

A chain as base and offsets

Write each step as "read the pointer stored at this offset", and the whole path becomes a base address and a list of numbers:

Text
base:  &game (the address of the variable holding the Game*)
step 1: read the pointer at base + 0        -> the Game
step 2: read the pointer at Game + 0x00     -> the World
step 3: read the pointer at World + 0x08    -> players[0]
step 4: read the pointer at Player + 0x10   -> the Stats
final:  Stats + 0x04                        -> the address of health

So base → 0x00 → 0x00 → 0x08 → 0x10 → 0x04. Every intermediate step reads 8 bytes and treats them as the next address; the last offset is added without reading, giving the address of the value itself. The offsets come straight from the struct layouts of lesson 3.01: offsetof(World, players) is 8 because tick and its padding come first.

Debuggers and memory tools display chains in exactly this form, often with brackets for each read: [[[[base + 0] + 0] + 8] + 0x10] + 4.

Following a chain in code

With real pointers, following a chain through byte offsets looks like this:

C++
// Follows base -> offsets[0] -> ... -> offsets[n-1]. Returns the final address, or nullptr.
const void* follow(const void* base, const std::vector<std::size_t>& offsets)
{
    const unsigned char* at{ static_cast<const unsigned char*>(base) };
    for (std::size_t i{ 0 }; i + 1 < offsets.size(); ++i)
    {
        const void* next;
        std::memcpy(&next, at + offsets[i], sizeof(next));   // read the pointer stored there
        if (!next) return nullptr;                            // a broken link: stop
        at = static_cast<const unsigned char*>(next);
    }
    return offsets.empty() ? at : at + offsets.back();
}

The memcpy reads 8 bytes as an address (lesson 2.05 explains why not a cast). The null check at every step is not optional: any object along the path may not exist yet (no level loaded, the player not spawned), and following its null pointer crashes.

Watch out

A chain is only valid while every object along it is alive. A level being unloaded frees the World; a pointer you read from it a moment ago now dangles. Code that caches a resolved address must resolve the chain again whenever the structure may have changed.

Why chains survive a restart

Run the program twice and every heap address changes, and ASLR moves the program itself. So the address of health is different every time. The offsets never change, because they come from the struct layouts compiled into the program. And the first link can be anchored to something stable: a global variable inside the program's own image, whose address is "where the program was loaded" plus a fixed number.

Text
run 1: module at 0x7FF6_1000_0000, global Game* at module + 0x51A8, health at 0x0000_01F3_2C40_9A14
run 2: module at 0x7FF7_A230_0000, global Game* at module + 0x51A8, health at 0x0000_0229_0E11_3374
        the chain module + 0x51A8 -> 0 -> 0 -> 8 -> 0x10 -> 4 finds health both times

This is how debuggers, profilers, save-game editors and the inspection tools you build for your own programs find the same data run after run: not by remembering an address, but by remembering a path.

Where you will use this

  • Your own debug tools. A debug overlay or an external inspector for your own game (the Game Development course builds one) reaches its data through chains like this.
  • Reading crash dumps. A dump holds raw memory; you follow pointers from a known global by hand or with the debugger's dx command.
  • File formats and packets. Many binary formats store offsets to other parts of the file, which you follow exactly the same way, with "offset into the file" in place of "address".
