Leaks and How to Find Them

lesson 4.055 of 5 in milestone 45 min1 practice task

A leak is memory nobody frees. Why leaks matter in programs that run for hours, how the MSVC debug heap reports them at exit with an allocation number you can break on, heap snapshots in Visual Studio, AddressSanitizer for leaks and use-after-free, and counting your own allocations.

What a leak is

A leak is heap memory whose owner is gone: the last pointer to it went out of scope or was overwritten, so nothing can ever free it.

C++
void loadLevel(const char* path)
{
    char* data{ new char[1'000'000] };
    if (!readFile(path, data)) return;     // early return: data is never freed
    parse(data);
    delete[] data;
}

When a program exits, Windows takes back all its memory, so a leak in a tool that runs for a second does no harm. A leak in a game, an editor or a server that runs for hours does: a small leak every frame grows to gigabytes, the program slows as it pages to disk, and eventually allocation fails. Leaks are also the visible symptom of unclear ownership (lesson 4.04), which causes the more dangerous bugs too.

The debug heap's leak report

In a Debug build, the MSVC C runtime can list every block still allocated when the program ends. Turn it on at the start of main:

C++
#define _CRTDBG_MAP_ALLOC
#include <crtdbg.h>

int main()
{
    _CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF);
    // ...
}

When the program exits, the Output window shows a report:

Text
Detected memory leaks!
Dumping objects ->
C:\src\level.cpp(14) : {157} normal block at 0x000001C4B2E8F0A0, 40 bytes long.
 Data: <                > CD CD CD CD CD CD CD CD CD CD CD CD CD CD CD CD
{156} normal block at 0x000001C4B2E91230, 8 bytes long.
 Data: <*       > 2A 00 00 00 00 00 00 00
Object dump complete.

Each entry gives the allocation number in braces, the address, the size and the first bytes. The file and line appear only for malloc-family calls when _CRTDBG_MAP_ALLOC is defined; new shows just the number. The number is the key: allocations are counted in order, so if the program runs the same way again, allocation 157 is the same allocation. Add

C++
_CrtSetBreakAlloc(157);

at the top of main, run again, and the debugger stops at the moment the leaked block is allocated, with the call stack showing exactly who made it. The first bytes help too: CD CD CD means it was never written at all; 2A 00 00 00 is the int 42.

Heap snapshots

For a program that keeps running, Visual Studio's Diagnostic Tools window (Debug > Windows > Show Diagnostic Tools, Memory Usage tab) can take heap snapshots. Take one, play the game for a minute, take another, and view the difference: it lists the types and call stacks of everything allocated in between and not freed. Growth that should not be there is your leak.

AddressSanitizer

AddressSanitizer (ASan) is a compiler feature that adds checks around every memory access. Turn it on in Visual Studio with Project Properties > C/C++ > General > Enable Address Sanitizer (/fsanitize=address). It reports, at the instant they happen:

  • reads or writes past the end of heap, stack and global arrays;
  • use after free, and use after return;
  • double frees and mismatched new[]/delete.

Each report names the bad access, the call stack, and where the memory was allocated and freed. A program under ASan runs about twice as slow, so it is for testing, not shipping. On Linux and with Clang, ASan also reports leaks at exit (LeakSanitizer).

Tip

Run your tests and a play session under ASan regularly. Bugs that "work" in a normal build, such as reading one past the end, show up immediately.

Counting your own allocations

When tools are not available, count. A class can track how many of its objects are alive with a static counter:

C++
struct Tracked
{
    static inline int alive{ 0 };
    Tracked() { ++alive; }
    Tracked(const Tracked&) { ++alive; }
    ~Tracked() { --alive; }
};

If Tracked::alive keeps growing during a level that should be steady, something is creating them without destroying them. Tests can check it: create a level, destroy it, and check the count is back to where it started. Games often keep counters like this per system and show them on a debug overlay.

Fixing leaks for good

Finding one leak is debugging; not writing the next one is design. The real fix is to make freeing automatic so an early return or an exception cannot skip it. That is RAII, the first lesson of the next milestone:

C++
void loadLevel(const char* path)
{
    std::vector<char> data(1'000'000);     // freed automatically on every path out
    if (!readFile(path, data.data())) return;
    parse(data.data());
}
