Rows, Columns and Strides

lesson 2.044 of 5 in milestone 25 min1 practice task

Two-dimensional data is stored as one long row of memory, row after row. The index of (x, y) is y times the row length plus x, and the row length in memory, the stride, can be longer than the visible width. Sub-images that share memory, and why walking along rows is faster than down columns.

Flattening a grid

Memory is one-dimensional, so a grid, a screen of pixels, a tile map, a spreadsheet, has to be flattened. C and C++ store it row by row (row-major order):

Text
grid (3 rows, 4 columns)          in memory
  a b c d                          a b c d e f g h i j k l
  e f g h                          |row 0 ||row 1 ||row 2 |
  i j k l

So the cell in column x of row y sits at:

index = y × width + x

C++
#include <iostream>
#include <vector>

int main()
{
    const int width{ 4 }, height{ 3 };
    std::vector<char> grid(width * height);
    for (int i{ 0 }; i < width * height; ++i) grid[i] = static_cast<char>('a' + i);

    const int x{ 1 }, y{ 2 };
    std::cout << grid[y * width + x] << '\n';   // j
}

A built-in 2D array, int cells[3][4], is laid out exactly the same way; cells[y][x] is the formula above done by the compiler. Many programs skip the 2D array and use a flat std::vector with the formula, because the size can then be chosen at run time.

Stride: the real row length

Images, screen buffers and textures often have rows that are longer in memory than the visible width. A graphics card might want every row to start at a multiple of 64 or 256 bytes, so a 100-pixel row is stored in 128 pixels' worth of memory and the last 28 are unused padding.

The distance from the start of one row to the start of the next is the stride (also called the pitch):

address of (x, y) = start + y × stride + x

Text
width 5, stride 8
row 0:  P P P P P . . .
row 1:  P P P P P . . .
row 2:  P P P P P . . .

Code that uses width where it should use stride produces the most recognisable bug in graphics: the image comes out sheared diagonally, each row starting a little further off than the last. When you see that, check the stride.

Watch out

Some APIs give the stride in bytes, others in pixels. Direct3D's RowPitch and Windows bitmaps are in bytes. Know which one you have, and convert through a byte pointer when it is in bytes.

Views that share memory

Stride makes sub-images free. A rectangle inside a larger image is just a new start pointer with the same stride and a smaller width and height:

C++
struct View
{
    std::uint32_t* pixels;   // the top-left pixel of this view
    int width, height;
    int stride;              // pixels from one row start to the next
};

View sub{ full.pixels + y0 * full.stride + x0, w, h, full.stride };

Writing to sub writes into full's memory; nothing is copied. This is how editors draw into one part of a window and how sprite sheets hand out single frames.

Rows fast, columns slow

The processor does not read memory one byte at a time. It loads a whole cache line (64 bytes) at once and keeps recently used lines in a small fast cache. Walking along a row uses every byte of each line it loads. Walking down a column jumps stride bytes each step and uses 4 bytes of each 64-byte line it pulls in.

C++
// fast: the inner loop walks along a row
for (int y{ 0 }; y < h; ++y) for (int x{ 0 }; x < w; ++x) sum += at(x, y);

// slow on big images: the inner loop walks down a column
for (int x{ 0 }; x < w; ++x) for (int y{ 0 }; y < h; ++y) sum += at(x, y);

On a large grid the second loop can be several times slower while doing exactly the same arithmetic. Put x in the inner loop.

Row pointers

A loop that works a row at a time can compute each row's start once:

C++
for (int y{ 0 }; y < view.height; ++y)
{
    std::uint32_t* row{ view.pixels + y * view.stride };
    for (int x{ 0 }; x < view.width; ++x) row[x] = colour;
}

and copying a whole row is one std::memcpy(dst, src, width * sizeof(std::uint32_t)), because inside a row the pixels are consecutive even when the rows are not.
