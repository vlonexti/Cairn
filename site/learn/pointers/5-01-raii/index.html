RAII

lesson 5.011 of 5 in milestone 55 min1 practice task

Resource Acquisition Is Initialisation - tie every resource to an object whose destructor releases it, and C++ frees it on every path out of a scope, early returns and exceptions included. Writing small owning wrappers, scope guards, and why this one idea removes most leaks.

The problem with "remember to free"

Every resource that must be given back, heap memory, a file, a lock, a Windows HANDLE, a texture on the graphics card, needs its release code to run on every path out of the code that acquired it:

C++
bool saveGame(const char* path, const Game& game)
{
    char* buffer{ new char[game.saveSize()] };
    std::FILE* file{ std::fopen(path, "wb") };
    if (!file) { delete[] buffer; return false; }
    if (!game.serialise(buffer)) { std::fclose(file); delete[] buffer; return false; }
    std::fwrite(buffer, 1, game.saveSize(), file);
    std::fclose(file);
    delete[] buffer;
    return true;
}

Three exits, three copies of the clean-up, and if serialise throws an exception, none of them run. Add a fourth exit next month and forget one line, and you have a leak.

Let the destructor do it

C++ guarantees one thing absolutely: when an object goes out of scope, by reaching the closing brace, by return, by break, or because an exception passes through, its destructor runs. So put the release in a destructor:

C++
class File
{
public:
    File(const char* path, const char* mode) : handle{ std::fopen(path, mode) } {}
    ~File() { if (handle) std::fclose(handle); }
    File(const File&) = delete;
    File& operator=(const File&) = delete;

    std::FILE* get() const { return handle; }
    explicit operator bool() const { return handle != nullptr; }

private:
    std::FILE* handle;
};

bool saveGame(const char* path, const Game& game)
{
    std::vector<char> buffer(game.saveSize());   // RAII for memory
    File file{ path, "wb" };                     // RAII for the file
    if (!file) return false;
    if (!game.serialise(buffer.data())) return false;
    std::fwrite(buffer.data(), 1, buffer.size(), file.get());
    return true;
}                                                // both released here, on every path

This is RAII: Resource Acquisition Is Initialisation. The name is clumsy; the idea is simple: acquire in the constructor, release in the destructor, and let scope decide when.

RAII is everywhere in the standard library

You already use it constantly:

Class Owns Releases with
std::vector, std::string heap memory delete[] inside
std::unique_ptr one heap object delete (next lesson)
std::fstream a file closing it
std::lock_guard, std::scoped_lock a mutex lock unlocking
std::jthread a thread joining it

The rule of thumb for modern C++: ordinary code never calls delete, free, fclose or CloseHandle directly. Those calls belong inside a destructor, written once.

Destruction order

Objects in a scope are destroyed in the reverse order they were created. That is usually exactly right: things created later may depend on things created earlier.

C++
{
    Device device{};            // created first
    Texture texture{ device };  // uses device
}                               // texture destroyed first, then device

Members of a class are destroyed in reverse order of declaration, after the class's own destructor body runs.

Copying an RAII object

The File class deletes its copy constructor and copy assignment. If it did not, copying a File would copy the FILE*, and both copies would close it (lesson 4.04's double owner). An RAII class must decide what copying means: forbid it (most handles), do a deep copy (std::vector copies its elements), or share with reference counting (std::shared_ptr). Lesson 5.05 shows how to let it be moved instead.

Scope guards

Sometimes the "resource" is just an action that must happen at the end: restore a setting, pop a state, log an exit. A tiny class that runs a lambda in its destructor covers every such case:

C++
template <typename F>
class ScopeExit
{
public:
    explicit ScopeExit(F f) : action{ std::move(f) } {}
    ~ScopeExit() { if (active) action(); }
    void dismiss() { active = false; }
    ScopeExit(const ScopeExit&) = delete;
    ScopeExit& operator=(const ScopeExit&) = delete;
private:
    F action;
    bool active{ true };
};

void drawDebug(Renderer& r)
{
    r.pushState();
    ScopeExit restore{ [&] { r.popState(); } };   // runs however we leave
    // ... draw, possibly returning early ...
}

dismiss() cancels it, which is how "commit or roll back" code works: set up a guard that undoes a change, do the work, and dismiss the guard only once everything has succeeded.
