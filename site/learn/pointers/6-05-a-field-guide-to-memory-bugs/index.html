A Field Guide to Memory Bugs

lesson 6.055 of 5 in milestone 67 min1 practice task

Everything in this course turned into a way of working - reading a crash's address, recognising the debug fill patterns, the symptom-to-cause table, data breakpoints, AddressSanitizer and page heap, and the habits that stop the bugs being written in the first place.

Read the address first

When a program crashes with an access violation, the most useful single fact is the address it tried to use. The debugger shows it in the exception message and, for a pointer, in the Locals or Watch window. Many bad addresses identify themselves:

Address looks like Usually means
0x0000000000000000 to a few thousand a null pointer; the small number is the offset of the member being reached
0xCCCCCCCCCCCCCCCC (plus a small offset) a pointer read from uninitialised stack memory (MSVC debug)
0xCDCDCDCDCDCDCDCD a pointer read from heap memory never written after new or malloc
0xDDDDDDDDDDDDDDDD a pointer read from freed heap memory: the object holding it was already deleted
0xFEEEFEEEFEEEFEEE a pointer read from memory freed back to the Windows heap
0xFDFDFDFD in your data you are reading the guard bytes around a heap block: past an end
a valid-looking heap address, but the data is garbage a dangling pointer to memory that has been reused

The first three patterns only appear in Debug builds, which is a good reason to reproduce crashes in one.

Data breakpoints

When a value changes and you do not know who changed it, set a data breakpoint on it. In Visual Studio, stop somewhere the variable exists, right-click it in the Locals or Watch window and choose Break When Value Changes (or Debug > New Breakpoint > Data Breakpoint with an address). The processor's debug registers watch that address, and the debugger stops at the exact instruction that writes to it, however indirect the pointer was. There are only four such registers, so only a few bytes at a time can be watched.

This is the tool for "something is overwriting my health with garbage": the write that should not happen stops in the debugger with its call stack.

Make the bug happen at the bug

Memory bugs are hard because the damage shows up later than the mistake. Every tool here moves the failure back to the moment of the mistake:

  • AddressSanitizer (/fsanitize=address) checks every access and reports overruns, use after free and double frees as they happen (lesson 4.05).
  • Page heap (gflags /p /enable game.exe /full) puts every heap block against an inaccessible page, so an overrun faults on the exact instruction (lesson 6.04). It uses a lot of memory; enable it for one program at a time.
  • The debug heap checks guard bytes when blocks are freed and fills memory with recognisable patterns. _CrtCheckMemory() called at points in your code checks every block immediately, narrowing down when the corruption happened.
  • Debug fill on free in your own allocators: fill freed memory with a pattern (as your debug heap in milestone 4 did) so a use after free reads obvious garbage instead of plausible old data.

A way of working

  1. Reproduce it reliably, in a Debug build if possible.
  2. Read the crash: the faulting address, the instruction, the call stack. Match the address against the patterns above.
  3. Turn on the tools: ASan first; page heap or data breakpoints if needed.
  4. Find the owner: for the object involved, who created it, who frees it, and who still held a pointer. Most memory bugs are ownership bugs (lesson 4.04).
  5. Fix the design, not just the line: a raw owning pointer that should be a unique_ptr, a cached pointer that should be a handle, a stored view that should be a copy.

The habits that prevent them

  • Initialise every variable, pointers above all.
  • One owner per object, written in the type: values, containers and unique_ptr; shared_ptr only for real sharing.
  • No new/delete in ordinary code; RAII for every resource.
  • Pass views (span, string_view, references) down, never store them casually.
  • Indices or handles instead of long-lived pointers into containers.
  • Bounds-checked access (at(), spans with known sizes) wherever speed does not demand otherwise.
  • Run tests under AddressSanitizer regularly.

You now know what every one of those habits protects against, byte by byte.
