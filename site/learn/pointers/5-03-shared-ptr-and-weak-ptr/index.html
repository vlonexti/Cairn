shared_ptr and weak_ptr

lesson 5.033 of 5 in milestone 55 min1 practice task

std::shared_ptr shares ownership through a reference count kept in a control block, and deletes the object when the last owner goes. What it costs, the cycles that make it leak, std::weak_ptr for observing without owning, and when shared ownership is really the right answer.

Several owners

Sometimes an object really has no single owner: a texture used by several materials, where whichever material is destroyed last should free it. std::shared_ptr<T> handles that case. It keeps a reference count, the number of shared_ptrs currently pointing at the object, and deletes the object when the count reaches zero.

C++
std::shared_ptr<Texture> stone{ std::make_shared<Texture>("stone.png") };   // count 1
{
    std::shared_ptr<Texture> copy{ stone };     // copying is allowed: count 2
    std::cout << stone.use_count() << '\n';     // 2
}                                               // copy destroyed: count 1
stone.reset();                                  // count 0: the texture is deleted

The control block

The count has to live somewhere every copy can reach, so a shared_ptr is two pointers: one to the object and one to a control block holding the counts.

Text
 shared_ptr a ---+--> [ control block: strong 2, weak 1 ]
                 |
 shared_ptr b ---+--> [ Texture object ]

std::make_shared allocates the control block and the object in one heap block, which is faster and uses less memory than std::shared_ptr<T>(new T). Always use it.

What it costs

  • Every shared_ptr is 16 bytes, twice a raw pointer.
  • Copying one changes the count with an atomic instruction (it must be safe across threads), which is noticeably slower than copying a pointer. Pass a shared_ptr by const&, or pass the object by reference, when the function does not need to keep a share.
  • It hides who really controls the object's lifetime. When anyone can keep it alive, nobody knows when it dies.

So unique_ptr is the default, and shared_ptr is for when ownership is genuinely shared.

Cycles leak

Reference counting has one blind spot. If two objects hold shared_ptrs to each other, each keeps the other's count above zero for ever:

C++
struct Player;
struct Team   { std::vector<std::shared_ptr<Player>> members; };
struct Player { std::shared_ptr<Team> team; };

{
    auto team{ std::make_shared<Team>() };
    auto ada{ std::make_shared<Player>() };
    team->members.push_back(ada);   // team owns ada
    ada->team = team;               // ada owns team
}   // the locals are gone, but team's count is 1 (from ada) and ada's is 1 (from team): both leak

No leak checker running over the heap sees anything wrong while the program runs; the memory is still "owned". Cycles of shared_ptr are the most common leak in modern C++ code.

weak_ptr: observe without owning

std::weak_ptr<T> points at an object managed by shared_ptrs without adding to its strong count. It cannot be dereferenced directly. To use the object you call lock(), which gives a shared_ptr if the object still exists and an empty one if it has gone:

C++
struct Player { std::weak_ptr<Team> team; };    // a back-reference that does not own

if (std::shared_ptr<Team> t{ ada->team.lock() })   // still alive?
    t->announce("Ada scored");
else
    /* the team was disbanded */;

The rule for any parent and child: the parent owns the child (shared_ptr or, better, unique_ptr), and the child observes the parent (weak_ptr, or a raw pointer when the child can never outlive the parent).

weak_ptr also solves lesson 1.05's dangling pointer problem for shared objects: a cache, a list of listeners or a target reference can hold weak_ptrs and find out cleanly that the object is gone, rather than following a dangling address. The control block stays alive while any weak_ptr refers to it, so lock() can always answer, even though the object itself was destroyed.

When shared ownership is right

  • Resources used by several independent owners with no natural single parent: textures, sounds, fonts in a cache.
  • Objects handed to work running on other threads, where the caller may finish first.
  • Graphs where nodes are added and removed from many places.

Even then, ask first whether one central owner (a TextureCache holding unique_ptrs and handing out raw pointers or handles) would be simpler. It usually is.
