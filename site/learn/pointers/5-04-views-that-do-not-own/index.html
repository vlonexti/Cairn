Views That Do Not Own

lesson 5.044 of 5 in milestone 55 min1 practice task

std::span and std::string_view are a pointer and a length bundled together - a cheap, safe way to borrow a sequence without copying or owning it. Passing them to functions, slicing them, and the one way they go wrong - outliving what they view.

A pointer and a length

C-style functions take a pointer and a count as two separate parameters, and getting the count wrong is a classic bug (lesson 2.01). C++20's std::span<T> bundles the two into one small value:

C++
#include <span>

int sum(std::span<const int> values)
{
    int total{ 0 };
    for (int v : values) total += v;      // range-for works: it knows its length
    return total;
}

int a[]{ 1, 2, 3 };
std::vector<int> v{ 4, 5, 6, 7 };
std::array<int, 2> s{ 8, 9 };

sum(a);          // a C array: length taken from the type
sum(v);          // a vector
sum(s);          // an array
sum({ v.data() + 1, 2 });   // any pointer and count: 5 + 6

One function serves every container whose elements sit consecutively in memory, without templates and without copying. std::span<const int> borrows read-only; std::span<int> lets the function change the elements.

A span is 16 bytes: a pointer and a size. Passing it by value is the right way, as cheap as passing two integers.

Slicing for free

Taking part of a span makes a new span over the same memory:

Call Gives
s.first(n) the first n elements
s.last(n) the last n
s.subspan(offset, count) count elements starting at offset
s.size(), s.empty(), s.data() length, emptiness, the pointer

Parsing a packet or a file becomes a matter of slicing: read a header from buffer.first(8), then carry on with buffer.subspan(8).

C++
std::span<const std::byte> rest{ packet };
const auto header{ rest.first(8) };
rest = rest.subspan(8);

string_view

std::string_view is the same idea for text: a pointer to characters and a length, with no ownership and no zero terminator required. Every function that only reads a string should take one:

C++
bool startsWithHash(std::string_view line) { return !line.empty() && line.front() == '#'; }

startsWithHash("# comment");                 // a literal: no std::string is built
startsWithHash(someStdString);               // a std::string: no copy
startsWithHash(std::string_view{ buf, 12 }); // twelve chars from the middle of a buffer

substr on a string_view returns another view, not a new string, so splitting a line into words allocates nothing.

Watch out

A string_view is not necessarily followed by a zero. Never pass view.data() to a C function that expects a C string; build a std::string first.

The one way views go wrong

A view borrows. It must not outlive what it views, and nothing checks that it does not:

C++
std::string_view name()
{
    std::string full{ "Ada Lovelace" };
    return full;                     // the view points into full, which dies here
}

std::string_view first{ std::string("temporary") };   // dangles at the end of the line

std::vector<int> v{ 1, 2, 3 };
std::span<int> view{ v };
v.push_back(4);                       // may reallocate: view now points at freed memory

These are lesson 1.05's dangling pointers wearing a nicer type. The rules that avoid them:

  • Use views as function parameters, where the caller's object is guaranteed to outlive the call. This is their main job and is always safe.
  • Be careful storing views in members or returning them. Only do it when the viewed data clearly lives longer, such as string literals or a buffer owned by the same object.
  • Do not keep a view into a container that may grow.

Choosing parameter types

Parameter When
std::span<const T> read a sequence of any length
std::span<T> change elements in place (but not the length)
std::string_view read text
const std::vector<T>& you specifically need vector features
std::vector<T> by value you keep your own copy (move into it)
std::string by value you keep your own copy of the text
