The Stack Up Close

lesson 4.022 of 5 in milestone 45 min1 practice task

Each function call pushes a frame holding the return address and the function's locals; returning pops it. The stack pointer moves down as frames are added. Why a pointer to a local dangles after the return, what a stack overflow is, and how writing past a local array can overwrite a return address.

A stack of frames

Every thread has one stack: a block of memory used last-in, first-out. A processor register, the stack pointer (rsp on x64), holds the address of its current top. On x86 and ARM the stack grows downwards: adding something moves the stack pointer to a lower address.

When a function is called:

  1. The call instruction pushes the return address, where execution continues afterwards, and jumps to the function.
  2. The function subtracts from the stack pointer to make room for its locals. That block, return address included, is its frame.
  3. When it returns, it adds the same amount back and the ret instruction pops the return address and jumps there.

Step through the demo and watch the addresses: each new frame sits below its caller's, and returning just moves the stack pointer back. Nothing is erased. The old bytes stay where they were until the next call overwrites them.

Why a pointer to a local dangles

That last fact explains the classic bug exactly:

C++
int* makeScore()
{
    int score{ 42 };
    return &score;            // the address of a byte range in makeScore's frame
}

void other() { int junk[16]{}; (void)junk; }

int main()
{
    int* p{ makeScore() };    // the frame is gone, but 42 is still sitting there
    std::printf("%d\n", *p);  // may print 42
    other();                  // other's frame is put in the same place
    std::printf("%d\n", *p);  // now prints 0, or anything
}

The first print often "works", because nothing has reused that memory yet. The next call reuses it. The compiler warns about this (C4172: returning address of local variable); treat that warning as an error.

The rule: never let a pointer or reference to a local escape its function. Return the value itself; it is copied out (or moved, or built straight into the caller's variable) before the frame goes away.

Stack overflow

A thread's stack has a fixed size, 1 MB by default on Windows (set by the linker's /STACK option, or per thread in CreateThread). Every active call uses some of it. Two things run it out:

  • Deep recursion: each call adds a frame, and a recursion 100 000 deep with 64-byte frames needs over 6 MB.
  • Big locals: char buffer[2'000'000]; in a function is 2 MB of stack in one frame.

Below the stack is a guard page; touching it raises EXCEPTION_STACK_OVERFLOW (0xC00000FD) and the program ends. The fix is never a bigger stack. It is to put big data on the heap (std::vector) and to turn very deep recursion into a loop with an explicit std::vector used as a stack.

Writing past a local array

Locals sit in the frame next to each other and, higher up, next to the saved return address. Writing past the end of a local array walks upwards over whatever is there:

Text
 higher addresses
   [ return address  ]   <- where the function goes when it returns
   [ saved registers ]
   [ int count       ]
   [ char name[16]   ]   <- strcpy(name, longInput) writes upward from here
 lower addresses

Copy 40 bytes into name and you overwrite count, the saved registers and the return address. When the function returns, it jumps to whatever the overwritten bytes say. That is a stack buffer overflow: at best a crash with a nonsense address, and historically the most exploited bug in software. It is why lesson 2.03 warned about strcpy.

Modern compilers defend against it. MSVC's /GS option (on by default) places a random security cookie between the locals and the return address and checks it before returning; if it changed, the program is stopped at once with STATUS_STACK_BUFFER_OVERRUN. Debug builds' /RTC checks catch overruns of individual locals. Neither is a licence to overrun; they turn silent corruption into a clear crash.
