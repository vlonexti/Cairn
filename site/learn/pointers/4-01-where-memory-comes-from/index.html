Where Memory Comes From

lesson 4.011 of 5 in milestone 45 min1 practice task

A running program's address space holds its code, its static data, one stack per thread and the heap. Each object gets one of four lifetimes - static, automatic, dynamic or thread - and the lifetime decides where it lives, when it starts and when its address stops being valid.

The map of a process

When Windows starts your program it gives it a private address space: a huge range of addresses (128 TB on 64-bit Windows) of which only a few small areas are actually backed by memory. The areas you will meet are:

Text
high addresses
  +-----------------------------+
  | stack of thread 1           |  grows down; 1 MB reserved by default
  | stack of thread 2           |
  |            ...              |
  | heap blocks                 |  new / malloc, anywhere the heap finds room
  |            ...              |
  | DLLs: kernel32, ucrtbase... |
  | your .exe image:            |
  |   .text    machine code     |  read + execute
  |   .rdata   constants, text  |  read only
  |   .data    initialised globals
  |   .bss     zeroed globals   |
  +-----------------------------+
low addresses

ASLR shuffles where each area starts, but every program has these pieces. When you look at a pointer's value in a debugger, its rough size already says which area it is in: an address near the .exe's load address is a global, a high address near the stack pointer is a local, anything else is probably heap.

Four lifetimes

C++ gives every object a storage duration, and that decides where it lives:

Duration Example Lives Starts Ends
static globals, static variables, string literals in the image (.data, .bss, .rdata) before main, or at the first call for a static local when the program exits
automatic ordinary local variables, parameters on the stack when execution reaches the declaration at the closing brace of its block
dynamic new, malloc, the inside of std::vector on the heap when you allocate it when you free it, and only then
thread thread_local variables per-thread storage when the thread starts or first uses it when the thread ends

A pointer is valid only during its object's lifetime. Almost every memory bug is a pointer that outlived what it pointed at.

Static storage

C++
int frames{ 0 };                    // .data: the whole program sees one frames
static int hits{ 0 };               // the same storage; static here limits it to this file
const char* title{ "Xenon" };       // the pointer is in .data, the text in .rdata

int nextTicket()
{
    static int next{ 1 };           // initialised once, the first time the function runs
    return next++;                  // keeps its value between calls
}

Static objects exist for the whole run, so a pointer to one is always safe to return or keep. That includes string literals: returning "January" from a function is fine, because the text lives in the image, not on the stack.

Writing to a string literal is not fine: it is in read-only memory, and char* s = "abc"; s[0] = 'x'; crashes with an access violation (modern C++ does not even let that first line compile).

Automatic storage

Locals live in the current function's stack frame, created on entry and discarded on return. That is fast (allocating a frame is subtracting from one register) and automatic, and it is why a pointer to a local is valid only until the function returns. The next lesson looks at frames byte by byte.

Dynamic storage

The heap is for objects whose lifetime does not match a function call: created in one place, used across many calls, freed later, possibly by someone else. You get it with new (or malloc), and it stays until you give it back. The heap does not know when you have finished with something; you must say so. Lessons 4.03 to 4.05 are about getting that right, and milestone 5 is about making C++ do it for you.

Choosing

  • Default to automatic. A local std::vector or std::string is itself on the stack and manages its own heap memory for you.
  • Use static for things that genuinely exist once for the whole program, and keep it rare: global state makes code hard to test and to run on several threads.
  • Use dynamic when the size is only known at run time, when the object must outlive the function that creates it, or when it is too big for the stack (1 MB in total, by default, for everything on a thread's stack).
