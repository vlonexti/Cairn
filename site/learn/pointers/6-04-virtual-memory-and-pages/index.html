Virtual Memory and Pages

lesson 6.044 of 5 in milestone 65 min1 practice task

Every address a program uses is virtual. The processor translates it, one 4 KB page at a time, through page tables the operating system maintains. Pages that are reserved, committed or free, page protection, page faults, guard pages, and what an access violation really is.

Addresses are not where the bytes are

Every address in this course so far has been a virtual address. When your program reads 0x000001C4B2E8F0A0, there is no memory chip at that number. The processor translates the virtual address into a physical address in RAM, using tables that the operating system maintains for each process.

This is why two programs can both use address 0x140001000 without clashing: each process has its own translation, its own address space. And it is why one program cannot read another's memory by accident: there is simply no translation from its addresses to the other's RAM.

Pages

Translating every byte separately would need impossibly large tables, so memory is managed in pages: blocks of 4096 bytes (4 KB) on x86 and ARM Windows. A virtual address splits into a page number and an offset within the page:

Text
virtual address 0x0000_0001_C4B2_E8F0
                ^^^^^^^^^^^^^^^^^^^ ^^^
                page number         offset (low 12 bits, 0 to 4095)

page  = address >> 12      (address / 4096)
offset = address & 0xFFF   (address % 4096)

The page table maps each virtual page number to a physical frame number. The physical address is the frame's start plus the same offset. The bytes within a page stay in the same order; only whole pages are moved around.

Translations are cached in the processor's TLB (translation lookaside buffer), so most accesses cost nothing extra. Code that jumps around huge areas of memory pays for TLB misses, another reason scattered linked structures are slow.

Reserved, committed, free

In Windows each page of an address space is in one of three states:

State Meaning
free nothing there; any access faults
reserved the address range is set aside so nothing else will use it, but it has no memory behind it; any access faults
committed backed by memory (RAM or the page file); accessible according to its protection

VirtualAlloc does both steps:

C++
// Reserve 1 GB of addresses: costs no memory, just address space.
void* base{ VirtualAlloc(nullptr, 1ull << 30, MEM_RESERVE, PAGE_NOACCESS) };
// Commit the first 64 KB of it when you actually need it.
VirtualAlloc(base, 64 * 1024, MEM_COMMIT, PAGE_READWRITE);

This is how a growable array can be built that never moves: reserve a huge range once, commit pages at the end as it grows. Thread stacks work this way too: 1 MB reserved, a little committed, more committed as the stack grows.

Committed memory is also only given real RAM when first touched. Committing guarantees it can be provided; the operating system supplies a zero-filled page at the first access.

Protection

Each committed page has a protection: PAGE_READONLY, PAGE_READWRITE, PAGE_EXECUTE_READ, PAGE_NOACCESS, and a few more. The program image is mapped with its code read+execute and its constants read-only, which is why writing to a string literal crashes. VirtualProtect changes a page's protection, and VirtualQuery reports the state and protection of any address (the Game Development course explores your own process with it).

Page faults and access violations

When the processor cannot translate an address, or the access breaks the page's protection, it raises a page fault and hands control to the operating system, which decides what it means:

  • The page is committed but not in RAM yet (first touch, or it was paged out to disk): the OS loads it and the program continues, never knowing. This is a normal, soft or hard page fault.
  • The page is free or reserved, or the access breaks the protection: the OS raises an access violation (0xC0000005) in the program. Unhandled, that ends it.

So "access violation reading location 0x0000000000000018" is the processor saying: page 0 is not committed, so this address has no translation. Windows deliberately never maps the first 64 KB of the address space, so every null pointer access, plus a small offset, faults immediately.

Guard pages

A page committed with PAGE_GUARD faults once on first access, and the OS then removes the guard. The stack uses one to grow: touching the guard page below the committed stack commits another page and moves the guard down. Debugging tools use the same idea to catch overruns: page heap (enabled with the gflags tool) places each allocation at the end of a page followed by an inaccessible page, so the first byte written past the end faults at that exact instruction.
