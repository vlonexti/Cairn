Looking at Raw Bytes

lesson 2.055 of 5 in milestone 25 min1 practice task

Any object's bytes can be read through an unsigned char pointer. Reading them as a different type is a different matter - the strict aliasing rule forbids most pointer casts, so memcpy and std::bit_cast are the correct tools. Byte order, swapping it, and the casts C++ offers.

The bytes of anything

Lesson 1.01 printed an int's bytes through an unsigned char*. C++ guarantees this works for every object: char, unsigned char and std::byte are allowed to look at the bytes of any type.

C++
#include <cstdio>

struct Point { float x, y; };

int main()
{
    Point p{ 1.0f, -2.5f };
    const unsigned char* b{ reinterpret_cast<const unsigned char*>(&p) };
    for (unsigned i{ 0 }; i < sizeof(p); ++i) std::printf("%02X ", b[i]);
    std::printf("\n");   // 00 00 80 3F 00 00 20 C0
}

That is how a hex viewer, a network packet writer, a save file and a hash function all see your data: as bytes.

Reading bytes as another type: not with a cast

The tempting next step is to read a float's bits as an integer by casting the pointer:

C++
float f{ 1.0f };
std::uint32_t bits{ *reinterpret_cast<std::uint32_t*>(&f) };   // undefined behaviour

This breaks the strict aliasing rule: apart from the char types, you may only read an object through a pointer to its own type (or a signed/unsigned twin of it). The compiler relies on that rule to optimise: it assumes a float* and a std::uint32_t* never point at the same memory, and may reorder or drop reads accordingly. The code above often "works", and then a release build or a new compiler version quietly gives the wrong answer.

The correct tools copy the bytes instead of pretending:

C++
#include <bit>
#include <cstring>

float f{ 1.0f };

std::uint32_t a;
std::memcpy(&a, &f, sizeof(a));               // works in every C++ version

std::uint32_t b{ std::bit_cast<std::uint32_t>(f) };   // C++20, clearer, sizes checked

Both compile to a single register move. No copying happens in the machine code; the memcpy is only how you tell the compiler what you mean.

The same goes for reading a number out of the middle of a byte buffer, such as a 4-byte length field at offset 6 of a packet. Casting buffer + 6 to std::uint32_t* is also a misaligned read on top of the aliasing problem. memcpy from buffer + 6 into a std::uint32_t is always correct.

The four casts

C++ has four named casts, and choosing the right one documents what you are doing:

Cast For
static_cast<T>(x) ordinary conversions: int to double, void* back to the T* it came from, base to derived when you know it is safe
reinterpret_cast<T>(x) reading memory as something else: pointer to unsigned char*, pointer to integer and back
const_cast<T>(x) removing const (only safe if the object was not really const)
dynamic_cast<T>(x) checked downcasts between classes with virtual functions

The old C-style cast, (int*)p, tries several of these in turn and so can quietly do something you did not mean. Prefer the named ones; reinterpret_cast in particular is easy to search for in a code review.

A pointer can be turned into a plain number with reinterpret_cast<std::uintptr_t>(p), the integer type guaranteed to hold any address. That is how you print an address in your own format or check its alignment: (reinterpret_cast<std::uintptr_t>(p) % alignof(double)) == 0.

Byte order, revisited

When bytes cross between machines (a file, a network packet) the order matters. Network protocols traditionally use big-endian order, most significant byte first, the opposite of x86. Converting is a byte swap:

C++
std::uint32_t swap32(std::uint32_t v)
{
    return (v >> 24) | ((v >> 8) & 0x0000FF00) | ((v << 8) & 0x00FF0000) | (v << 24);
}

C++23 has std::byteswap, and Windows has _byteswap_ulong; both become one bswap instruction. The most portable way to read a number in a known byte order is to assemble it from bytes with shifts, as you did in lesson 1.01: that code gives the same answer on any machine.

To check the machine's own order: std::endian::native == std::endian::little (C++20), or look at the first byte of the int 1.
