The Heap

lesson 4.033 of 5 in milestone 45 min1 practice task

new and delete, new[] and delete[], malloc and free - what each does, why they must be paired exactly, what the allocator keeps next to every block, and the bugs that come from getting a pair wrong - double frees, mismatched frees, and memory that was never initialised.

Asking for memory

The heap gives out blocks of memory that live until you give them back. C++ asks for them with new:

C++
int* one{ new int{ 42 } };            // one int, initialised to 42
Enemy* boss{ new Enemy{ "Golem", 500 } };   // one object; its constructor runs
int* many{ new int[1000]{} };          // an array of 1000 ints, all zero

delete one;                            // the destructor runs, then the memory is returned
delete boss;
delete[] many;                         // arrays use delete[]

Each new does two things: get raw memory from the allocator, then construct the object in it. Each delete does the reverse: run the destructor, then return the memory.

The pairs must match

You allocated with Free with
new T delete p
new T[n] delete[] p
std::malloc, std::calloc, std::realloc std::free(p)
a library's CreateX / AllocX that library's DestroyX / FreeX
HeapAlloc, VirtualAlloc, LocalAlloc HeapFree, VirtualFree, LocalFree

Mixing them is undefined. delete on an array runs only the first element's destructor and may hand the allocator a pointer it does not recognise; free on something from new skips the destructor. Memory from a DLL that uses a different C runtime must go back to that DLL's free function, because its heap is not yours (the DLLs course covers this boundary).

malloc is not new

std::malloc(bytes) returns raw memory, or nullptr if there is none. It constructs nothing, so it is only for plain data such as int, char and simple structs, and its contents start as garbage. std::calloc zeroes the block; std::realloc resizes it, possibly moving it to a new address (so every old pointer into it dangles).

new never returns nullptr on failure; it throws std::bad_alloc. In C++ code you use new (or, far better, a container or a smart pointer). You meet malloc in C code and C APIs.

What the allocator keeps

The heap is not magic. It is ordinary code (on Windows, the C runtime on top of the Windows heap) managing big regions of memory. For every block it hands out it keeps a little bookkeeping: at least the block's size, usually stored in a header just before the address you receive.

Text
           your pointer
               |
               v
 [ header: size, flags ][ your 24 bytes ................ ][ next block's header ]

That is why delete p needs no size: the allocator looks just below p. It is also why heap bugs are so destructive. Writing a few bytes past the end of your block overwrites the next block's header. Nothing happens immediately; the crash comes much later, when the allocator next reads that header, in an unrelated new or delete, with a message such as HEAP CORRUPTION DETECTED or a crash inside ntdll.dll.

Each block also costs more than you asked for: alignment (blocks are 16-byte aligned on 64-bit Windows) plus the header. A million new int calls use far more than 4 MB.

The classic heap bugs

C++
int* p{ new int{ 1 } };
delete p;
delete p;            // double free: the allocator's lists are corrupted

int* q{ new int[10] };
q[10] = 5;           // one past the end: overwrites the next block's header

int* r{ new int[10] };
delete r;            // wrong form: should be delete[]

int* s{ static_cast<int*>(std::malloc(40)) };
int sum{ s[0] };     // reading uninitialised memory: 0xCDCDCDCD in a debug build

The debug heap in an MSVC Debug build checks a lot of this for you: it fills new blocks with 0xCD, freed blocks with 0xDD, surrounds every block with 0xFD guard bytes and checks them when the block is freed. That turns many silent corruptions into an assertion at the delete that found them. This milestone's project builds a small debug heap of your own.

Setting pointers to nullptr after delete

delete p; does not change p; it still holds the old address. If p lives on (a member variable, say), set it to nullptr straight away. A second delete nullptr is harmless by definition, and a later use crashes cleanly at address 0 instead of quietly reading freed memory.
