How an Allocator Works

lesson 6.011 of 5 in milestone 65 min1 practice task

Inside malloc and new - big regions carved into blocks, headers that record each block's size, free lists, first fit, splitting and joining blocks, alignment, fragmentation, and the size classes that make modern allocators fast.

Carving up a region

An allocator starts with a large region of memory it got from the operating system, and hands out pieces of it. The simplest possible design keeps the region as a sequence of blocks, each with a small header in front of it:

Text
[ hdr 32 used ][ 32 bytes ][ hdr 64 free ][ 64 bytes ][ hdr 48 used ][ 48 bytes ][ hdr 880 free ] ...

Each header records the block's size and whether it is in use. Because the next header is right after this block, the headers form an implicit list that walks the whole region: from any header, add its size to find the next.

Allocating: find a free block

To allocate n bytes:

  1. Round n up so the block keeps the alignment the allocator promises (16 bytes on 64-bit Windows).
  2. Find a free block that is big enough. First fit takes the first one found; best fit searches for the smallest that fits.
  3. If the block is much bigger than needed, split it: the front part becomes the allocation, the rest becomes a new, smaller free block with its own header.
  4. Mark it used and return the address just after its header.

Freeing: join neighbours

To free a pointer, step back to its header (pointer minus header size) and mark the block free. Then coalesce: if the next block, or the previous one, is free too, merge them into one larger free block. Without coalescing, a region that has been fully freed would still be chopped into small pieces, and a large request would fail even though all the memory is free.

Fragmentation

Even with coalescing, a long-running program can end up with plenty of free memory in total but no single free block large enough:

Text
[used 16][free 16][used 16][free 16][used 16][free 16] ...   1 MB free in total, largest block 16 bytes

This is fragmentation: free space scattered between blocks still in use. A request for 64 bytes now fails, or forces the allocator to ask the operating system for more. Games that allocate and free many differently sized objects every frame suffer from it, which is one reason they use the arena and pool allocators of the next two lessons for their per-frame and per-object memory.

Free lists and size classes

Walking every block to find a free one gets slow with millions of blocks. Real allocators keep free lists: linked lists of only the free blocks, with the next pointers stored inside the free blocks themselves (their memory is unused, so it costs nothing).

Modern allocators go further and keep separate free lists per size class: one for 16-byte blocks, one for 32, 48, 64, and so on. A request is rounded up to its class and served from that list's head in a few instructions, with no searching at all. Only large requests fall back to the slow general path. The Windows heap's Low Fragmentation Heap, which is switched on automatically for frequently used sizes, works this way, as do jemalloc, mimalloc and tcmalloc.

Design Allocate Free Fragmentation
implicit list, first fit walk until a fit mark and coalesce moderate
explicit free list walk free blocks only push on the list moderate
size classes pop from the class's list push on the class's list low for small sizes, some wasted space from rounding

Alignment

Every pointer the allocator returns must be aligned for any type (alignof(std::max_align_t), 16 on 64-bit Windows). So block sizes and header sizes are kept multiples of 16, and the arithmetic is "round up to a multiple":

C++
std::uintptr_t alignUp(std::uintptr_t value, std::uintptr_t align)   // align is a power of two
{
    return (value + align - 1) & ~(align - 1);
}

Adding align - 1 and then clearing the low bits rounds up. It only works when align is a power of two, which alignments always are; checking that is (align & (align - 1)) == 0.

Where the region comes from

Allocators get their big regions from the operating system: on Windows with VirtualAlloc (raw pages, lesson 6.04) or HeapCreate; malloc in the C runtime sits on the process heap, which sits on VirtualAlloc. Large requests (around 512 KB and up on Windows) are usually served directly from fresh pages instead of the block list.
