Null, Dangling and Wild Pointers

lesson 1.055 of 5 in milestone 15 min1 practice task

The three kinds of bad pointer - null, dangling and wild - what each one is, what happens when you follow it, why the crash often appears far from the bug, and the habits that keep pointers valid.

A pointer is only as good as its address

A pointer can hold any 64-bit number. Only some of those numbers are the address of an object that exists right now. Following any other is undefined behaviour: the C++ standard says nothing about what happens, and in practice the result ranges from an immediate crash to silently wrong data a minute later.

There are three ways a pointer goes bad.

1. Null pointers

A pointer holding nullptr says honestly "I point at nothing". Following it is still a bug, but the friendliest one: address 0 and the pages around it are never mapped on Windows, so the processor stops the program at once.

Text
Exception thrown: read access violation.
p was nullptr.

A crash at the bad line, naming the variable, is the best case. Small addresses near zero, like 0x0000000000000018, mean the same thing: something did p->member with p null, and 0x18 was that member's offset.

2. Dangling pointers

A dangling pointer holds the address of an object that used to exist:

C++
int* makeScore()
{
    int score{ 42 };
    return &score;         // score dies when the function returns
}

int* p{ makeScore() };     // p dangles: the memory is still there, the object is not
C++
int* data{ new int{ 7 } };
delete data;               // the object is gone
*data = 8;                 // use after free: data still holds the old address
C++
std::vector<int> v{ 1, 2, 3 };
int* first{ &v[0] };
v.push_back(4);            // the vector may move its elements to a bigger block
*first = 10;               // first may now point into freed memory

Dangling pointers are the worst kind, because the address is plausible. The memory is still mapped, often still holds the old value, so reading through it seems to work, until something else reuses that memory. Then you read someone else's data, or write into it, and the crash happens later, somewhere unrelated.

Danger

"It printed the right value" does not prove a pointer is valid. A dangling pointer often reads the old value for a while. Tools like AddressSanitizer (lesson 4.05) catch these at the moment they happen.

3. Wild pointers

A wild pointer was never given a valid value at all:

C++
int* p;          // uninitialised: holds whatever bytes were on the stack
*p = 5;          // writes to a random address

In a debug build MSVC fills uninitialised stack memory with 0xCC bytes, so the pointer is 0xCCCCCCCCCCCCCCCC and the crash is immediate and recognisable. Learn the debug fill patterns; they tell you what went wrong at a glance:

Value MSVC debug meaning
0xCCCCCCCC uninitialised stack memory
0xCDCDCDCD heap memory from new/malloc, never written
0xDDDDDDDD heap memory that was freed
0xFDFDFDFD the guard bytes just before and after a heap block
0xFEEEFEEE memory freed back to the Windows heap

A pointer value of 0xDDDDDDDDDDDDDDDD means "this pointer was read out of freed memory": a use after free one step removed.

Out of bounds is the fourth way

A pointer can also start valid and be moved off the end of its object, which is the subject of the next milestone. Reading one element past an array reads whatever is next in memory; writing there corrupts it.

Habits that keep pointers valid

  • Initialise every pointer, to an object or nullptr. Never int* p;.
  • Check pointers that may be null before following them, and document which ones may be.
  • Never return the address of a local variable. Return the value, or memory that outlives the function.
  • Set a pointer to nullptr after delete if the variable lives on, so a later mistake is a clean null crash instead of a use after free.
  • Do not keep pointers into a vector across operations that grow it. Keep an index instead.
  • Know who owns the object a pointer points at, and how long it lives (milestone 4).
