Pool Allocators

lesson 6.033 of 5 in milestone 65 min1 practice task

A pool hands out blocks of one fixed size from a single region. Free blocks are linked into a list through their own memory, so allocating and freeing are a couple of pointer moves, with no headers and no fragmentation. Building one, and where games use them.

Many objects of one size

Games create and destroy huge numbers of identical objects: bullets, particles, sound voices, network messages. Each one is the same size. A pool allocator exploits that: it divides one region into equal blocks, and handing one out is just taking any free block.

Text
[ block 0 ][ block 1 ][ block 2 ][ block 3 ][ block 4 ][ block 5 ] ...   every block 64 bytes

Because every block is the same size, there is no searching for a fit, no splitting, no headers to record sizes, and no fragmentation: any free block is as good as any other.

The free list lives in the free blocks

The pool needs to know which blocks are free. It keeps them on a linked list, and the clever part is where the next pointers go: inside the free blocks themselves. A free block's memory is unused anyway, so its first 8 bytes can hold the address of the next free block.

Text
free --> [ next: &block 3 | .... ] --> [ next: &block 5 | .... ] --> [ next: nullptr | .... ]
          block 1                       block 3                        block 5
C++
class Pool
{
public:
    Pool(std::size_t blockSize, std::size_t count)
        : size{ std::max(blockSize, sizeof(void*)) }, memory(size * count)
    {
        for (std::size_t i{ count }; i-- > 0;)            // push every block onto the list
            push(memory.data() + i * size);
    }

    void* allocate()
    {
        if (!head) return nullptr;                         // pool exhausted
        void* block{ head };
        std::memcpy(&head, block, sizeof(head));           // head = the next pointer stored in the block
        return block;
    }

    void release(void* block) { push(static_cast<std::byte*>(block)); }

private:
    void push(std::byte* block)
    {
        std::memcpy(block, &head, sizeof(head));           // the block's first bytes point at the old head
        head = block;
    }

    std::size_t size;
    std::vector<std::byte> memory;
    void* head{ nullptr };
};

Allocating pops the head of the list; freeing pushes the block back on. Both are a handful of instructions, always the same speed however full the pool is. Blocks must be at least as big as a pointer, which the constructor makes sure of.

LIFO reuse

The most recently freed block is the next one handed out. That is good for the cache: memory just touched is likely still in it. It also means a use-after-free bug in pooled objects shows up quickly and strangely, because the freed object's memory is immediately reused by the next allocation of the same type, and its first 8 bytes are overwritten by the free-list pointer as soon as it is freed.

Pools in practice

  • Particle systems and bullets: thousands created and destroyed per second, all the same size.
  • Network messages and events: fixed-size records queued and processed.
  • Nodes of linked structures: a pool of Nodes makes a linked list or tree far faster than one new per node, and keeps the nodes close together in memory.
  • Size-class allocators (lesson 6.01) are just one pool per size.

A pool can also hand out indices instead of pointers: block numbers from 0 to count - 1. Indices are 4 bytes instead of 8, stay valid if the pool is moved or saved to disk, and combine naturally with the generation counters of lesson 1.05's handles, which catch use-after-free on the spot.

Growing

A fixed pool can run out. Either treat that as a design limit ("at most 4096 bullets", and refuse more), or let the pool allocate another region when it is exhausted and add its blocks to the free list. Growing never moves existing blocks, so pointers into the pool stay valid, which a std::vector of objects cannot promise.
