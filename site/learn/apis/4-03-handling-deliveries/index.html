Handling Deliveries

lesson 4.033 of 5 in milestone 45 min1 practice task

What a webhook endpoint must assume about deliveries - they are retried, so they arrive more than once; they arrive out of order; and they must be answered quickly - and the techniques that cope - acknowledge fast and queue, idempotent processing by event id with bounded memory, and versions or fetching current state for ordering.

At least once, in any order

Services promise at-least-once delivery: every event is delivered, possibly more than once. And they do not promise order: a retried order.created can arrive after the order.shipped that followed it. Your handler must be correct anyway.

Answer quickly

The service waits only a few seconds for your answer; after that it counts the delivery as failed and retries. So:

  1. Verify the signature.
  2. Store the event (in a database table or a queue).
  3. Answer 2xx immediately.
  4. Process it afterwards, in a background worker.

A handler that does the real work (sending emails, calling three other APIs) before answering will time out under load, causing retries, causing more load.

What to answer:

Situation Answer Effect
verified and stored (or already seen) 200 done
signature invalid 400 or 401 the service may retry, but it will keep failing: that is fine
event type you do not handle 200 otherwise it is retried for days
your own temporary failure (database down) 500 or 503 the service retries later: exactly what you want

Duplicates: idempotent processing

Because of retries, the same event id will arrive again. Make processing idempotent: record the ids you have processed, and skip ones already recorded.

  • Record the id after processing succeeds, in the same database transaction as the effect if possible. Recording first and then failing would drop the event forever.
  • Memory is not infinite: keep ids for longer than the service's retry window (a few days), and drop older ones. In memory, a bounded structure that forgets the oldest ids is enough (practice 4.03).

Order: versions or fresh state

Two common ways to stop an old event from overwriting newer data:

  • Versions or timestamps. If events carry the object's version (or updated_at), remember the latest version applied per object and ignore anything older.
  • Fetch the current state. Treat the event only as a notification ("order 42 changed") and fetch order 42 from the API before acting. Whatever order events arrive in, you always act on the current truth. This costs a request per event but is the simplest correct approach, and some services send "thin" events for exactly this reason.
