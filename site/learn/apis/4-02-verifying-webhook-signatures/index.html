Verifying Webhook Signatures

lesson 4.022 of 5 in milestone 45 min1 practice task

Making sure a webhook really came from the service - why a public endpoint must verify every request, the common signature scheme of timestamp plus HMAC of the raw body, signature headers with several values during secret rotation, tolerance windows, and the mistakes that break verification.

Anyone can POST to your URL

A webhook endpoint is a public URL. Anyone who finds it can send it a request that looks like a "payment succeeded" event. If your code believes it, someone gets goods for free. So every webhook must be verified before you act on it.

Services sign their deliveries with a secret shared with you when you set up the subscription (the signing secret, often starting whsec_). The scheme most services use, in slightly different spellings:

Text
Webhook-Signature: t=1793523600,v1=a3f19c...c09e
  • t is the time the service signed it.
  • v1 is the hex HMAC-SHA256, keyed with the signing secret, of the signed payload: the timestamp, a dot, and the raw request body: "1793523600." + body.

To verify:

  1. Parse the header into t and the list of v1 values.
  2. Reject if t is too far from your clock (5 minutes is typical): this stops replays of old captured deliveries.
  3. Compute the HMAC of f"{t}.".encode() + raw_body with your secret.
  4. Accept if it equals any of the v1 values, compared with hmac.compare_digest.

Use the raw body

The signature covers the exact bytes that were sent. If you parse the JSON and dump it again, spaces, key order and escapes change, and the signature no longer matches. Verify before parsing, on the body exactly as received. Web frameworks that parse bodies for you usually have a way to get the raw bytes; use it.

Several signatures: secret rotation

When you (or the service) rotate the signing secret, there is a period when deliveries may be signed with the old or the new one. Services handle this by sending several v1 values, one per active secret, and your verifier may also hold several secrets. Accept the delivery if any of your secrets matches any of the signatures; this is why step 4 says "any".

Other schemes

  • Some services sign only the body, with the result in a header such as X-Hub-Signature-256: sha256=<hex> (GitHub). No timestamp, so no replay protection beyond event ids.
  • Some send the signature base64-encoded instead of hex.
  • The Standard Webhooks specification uses webhook-id, webhook-timestamp and webhook-signature headers and signs id.timestamp.body.

Each provider's documentation states exactly which bytes are signed and how the result is encoded. Implement it exactly, and test it with the example payload and signature from their documentation.
