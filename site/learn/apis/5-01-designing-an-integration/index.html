Designing an Integration

lesson 5.011 of 5 in milestone 55 min1 practice task

The decisions to make before writing code that connects two services - which system owns which data, one-way or two-way, triggered by webhooks, schedules or users, how records in one system find their partners in the other, and writing it all down on one page.

Two systems, one picture

Most real API work is integration: making two services that were not designed for each other work together. An online shop and an accounting package; a form tool and a CRM; an issue tracker and a chat app. The code is rarely the hard part. The hard part is the decisions, and they are best made before the first request.

The running example for this milestone: paid orders in a shop become invoices in an accounting system.

Who owns what?

For every kind of data, decide which system is the source of truth:

Data Owner The other system
orders, customers, prices shop receives copies
invoice numbers, payment status in the books accounting never writes these back into the shop

Copies are never edited by hand in the receiving system, or the next sync overwrites the edit (or worse, sometimes does and sometimes does not). If both systems must edit the same data, you need conflict rules (lesson 5.03), and it is worth trying hard to avoid that.

Which direction, triggered how?

  • One-way (shop to accounting) is far simpler than two-way. Choose it whenever you can.
  • Triggers: a webhook from the shop (fast, lesson 4.01); a schedule (every 10 minutes, simple and robust); or a user action ("send to accounting" button). Many integrations combine a webhook for speed with a scheduled sync to catch anything missed.

Finding partners: the id map

The shop's order 1001 becomes the accounting system's invoice INV-2026-0042. The integration must remember that pair, so that a later change to the order updates the invoice instead of creating a second one. Two ways:

  • Store the other system's id in a field of the record, if the API allows custom fields or an external reference ("external_ref": "shop-1001"), and look it up there.
  • Keep your own id map: a small table of (shop id, accounting id) pairs (practice 5.01).

An external reference in the target system also makes your integration recoverable: if your id map is lost, it can be rebuilt by searching.

Write it down

Before coding, write one page: the systems and versions; what flows where and who owns it; the triggers; the field mapping (next lesson); what happens on deletes, on errors, and on the first run with existing data; and how someone will know it is working (lesson 5.05). It is the document the next person (often you, months later) needs, and writing it surfaces the questions the business must answer: "should refunds void the invoice or create a credit note?"
