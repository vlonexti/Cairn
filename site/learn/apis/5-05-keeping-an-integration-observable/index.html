Keeping an Integration Observable

lesson 5.055 of 5 in milestone 55 min1 practice task

Knowing an integration works without watching it - structured log lines with correlation ids, a summary per run, the few numbers worth tracking (processed, failed, dead letters, lag), alerts that fire on the right things, health checks, and scheduling runs with cron or Windows Task Scheduler.

Silent failure

Integrations fail quietly. Nobody looks at a sync until the accountant asks why no invoices arrived for three weeks. Building in observability (being able to tell from the outside what it is doing) is part of the job, not an extra.

Structured logs

Log events, one JSON object per line, with fixed fields, rather than free text:

Text
{"ts": "2026-11-19T10:00:03Z", "level": "info", "msg": "invoice created", "run": "r-0193", "order": "1001", "invoice": "INV-42"}
{"ts": "2026-11-19T10:00:04Z", "level": "error", "msg": "dead letter", "run": "r-0193", "order": "1017", "reason": "422 invalid email"}
  • Machines can search and count them: "all errors for order 1017", "invoices created per day".
  • Every line of one run shares a run id; lines about one record share its id; requests carry the API's request id (lesson 1.02). These correlation ids let you follow one record through the whole system.
  • Redact secrets before writing (lesson 2.05).

A summary per run

At the end of each run, write one summary line: when it started, how long it took, how many records were created, updated, skipped and dead-lettered, and the new checkpoint. Most questions ("is it running?", "did yesterday's run do anything?") are answered by the last few summaries.

The numbers that matter

Metric Tells you
records processed per run it is doing work
errors and dead letters something needs attention
lag: now minus the checkpoint (or the oldest unprocessed change) how far behind it is
time since the last successful run whether it is running at all
API error rates and 429s the other side is struggling, or you are calling too fast

Lag and time since the last success catch the failures that produce no errors at all: a scheduler that stopped, a webhook subscription that was deleted.

Alerts

Alert on things a person must act on, rarely enough that alerts are not ignored:

  • no successful run for N intervals;
  • lag above a threshold;
  • new dead letters (or the count above zero for a day);
  • the error rate far above normal.

Scheduling and health

A scheduled sync runs from cron on Linux and macOS, Task Scheduler on Windows, or a cloud scheduler. Make each run safe to run twice at once (or prevent it with a lock), since schedulers sometimes overlap runs. A webhook receiver should expose a health check URL that a monitor can call, returning 200 only if it can reach what it depends on.
