Idempotency Keys and Timeouts

lesson 3.044 of 5 in milestone 35 min1 practice task

Making non-idempotent requests safe to retry - the Idempotency-Key header, one key per logical operation, what the server stores and replays, conflicts when the same key comes with a different request - and timeouts, unknown outcomes and deadlines that span several calls.

The unknown outcome

You send POST /payments and the connection drops before the response arrives. Did the payment happen? You cannot know. Retrying might pay twice; not retrying might not pay at all. Timeouts create the same uncertainty: a timeout says you stopped waiting, not that the server did nothing.

Idempotency keys

Many APIs that create things (payments, orders, messages) solve this with an idempotency key: a unique value the client generates for each logical operation and sends as a header:

Text
POST /v1/payments
Idempotency-Key: 6f1c2b7e-4a5d-4c3e-9b8a-1d2e3f4a5b6c
Content-Type: application/json

{"amount": 1999, "currency": "EUR"}

The server remembers the key with the response it gave. If the same key arrives again:

  • with the same request: it does not repeat the operation; it replays the stored response. Your retry is now safe.
  • with a different request (another amount): it refuses, typically with 409 or 422, because reusing a key for a different operation is a client bug.

Rules for the client:

  • Generate the key once per operation (uuid.uuid4()), before the first attempt, and reuse it for every retry of that operation.
  • A new operation (the user clicks "pay" again for a second item) gets a new key.
  • Keys expire on the server after some time (often 24 hours); retries happen within seconds or minutes, so this does not matter for them.

Practice 3.04 builds the server side of this, which is the best way to understand what the client relies on.

Timeouts and deadlines

Every request needs a timeout (lesson 1.02). When an operation makes several requests, with retries, also give it a deadline: a total time budget. Each attempt gets the smaller of its usual timeout and the time left, and the operation stops when the budget is spent:

Python
deadline = clock() + 30
for attempt in range(1, 5):
    remaining = deadline - clock()
    if remaining <= 0:
        raise TimeoutError("gave up after 30 s")
    response = send(timeout=min(10, remaining))
    ...

Deadlines keep a slow dependency from making your whole program slow: a web page that must answer in 2 s cannot spend 40 s retrying.
