Webhooks versus Polling

lesson 4.011 of 5 in milestone 45 min1 practice task

Two ways to learn that something changed at another service - asking repeatedly (polling) and being told (webhooks) - what each costs, polling done carefully with an updated-since cursor and adaptive intervals, and how webhook subscriptions, events and deliveries work.

"Has anything changed?"

Integrations constantly need to know when something happens elsewhere: a payment succeeded, an issue was closed, a file was uploaded. There are two ways to find out.

Polling

Ask, again and again:

Python
since = load_checkpoint()
while True:
    changes = client.request("GET", "/orders", {"updated_since": since})
    for order in changes["items"]:
        handle(order)
        since = max(since, order["updated_at"])
    save_checkpoint(since)
    sleep(interval)

Polling is simple and works with any API, but:

  • Most polls find nothing, and each one costs a request and some of your rate limit.
  • Changes are noticed up to one interval late. Shorter intervals cost more requests.
  • "Updated since" has an edge case: several items updated in the same second as your checkpoint. Asking for updated_at > since can miss some; asking for >= since returns ones you have already seen. The usual fix is >= plus remembering which ids you saw at exactly that timestamp (practice 4.01).

An adaptive interval reduces the cost: poll more often while things are happening, back off when they are quiet (halve the interval after finding changes, double it after an empty poll, within limits).

Webhooks

With a webhook, the service calls you: when an event happens, it sends an HTTP POST to a URL you registered, with the event as JSON.

Text
POST /webhooks/payments HTTP/1.1
Content-Type: application/json
Webhook-Id: evt_01HX9F...
Webhook-Signature: t=1793523600,v1=a3f19c...c09e

{"id": "evt_01HX9F", "type": "payment.succeeded", "created": 1793523600, "data": {"object": {"id": "pay_42", "amount": 1999}}}
  • You subscribe in the service's dashboard or through its API: the URL, and which event types you want.
  • Each event has an id, a type and the data (sometimes the whole object, sometimes only its id, so you fetch the current state yourself).
  • Each attempt to send it is a delivery. If your endpoint does not answer with a 2xx in time, the service retries later, with backoff, for hours or days.

Webhooks are near-instant and cost nothing when nothing happens. In exchange your program must run a public HTTP endpoint, check that requests really come from the service (lesson 4.02), and cope with deliveries that arrive late, twice or out of order (lesson 4.03).

Use both

Webhooks can be missed: your server was down for longer than the retry window, or the subscription was misconfigured. Robust integrations use webhooks for speed and a slow reconciliation poll (every hour or night) to catch anything missed.
