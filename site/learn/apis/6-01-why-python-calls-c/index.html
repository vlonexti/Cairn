Why Python Calls C

lesson 6.011 of 5 in milestone 65 min1 practice task

The other kind of API - a native library's functions - why C's calling convention is the common language every other language can speak, what you gain by calling into C from Python, the tools available (ctypes, cffi, extension modules), and the new kind of failure it brings - crashes instead of exceptions.

A different kind of API

Web APIs connect programs over a network. A native library (a .dll on Windows, .so on Linux, .dylib on macOS) offers its API as functions in the same process: no HTTP, no JSON, just a call with arguments in registers and memory. The Windows API, SQLite, zlib, OpenSSL, graphics drivers and countless vendor SDKs are all native libraries with C interfaces.

C as the common language

Almost every language can call functions that follow the C calling convention (the ABI: how arguments are passed, who cleans up the stack, how structures are laid out in memory), and most libraries offer a C interface even when written in C++ or Rust. So C is the lingua franca: a library with a C API can be used from Python, C#, JavaScript, Go, Java and more.

Reasons to call C from Python:

  • Use something only available natively: an operating system function, a hardware vendor's SDK, a library with no Python package.
  • Speed: a hot loop moved into C (NumPy, Pillow and most of the scientific stack do this).
  • Reuse: a company's existing C or C++ code, without rewriting it.

The tools

Tool How it works Good for
ctypes (standard library) describe the C types in Python, load the library, call quick bindings, no compiler needed
cffi (package) paste the C declarations; it works out the types larger APIs, written from the header
C extension modules write C against Python's own C API, compile it maximum speed and control
pybind11, nanobind C++ templates generate the extension wrapping C++ classes
Cython Python-like language compiled to C speeding up Python code, calling C

This milestone uses ctypes, because it needs nothing installed and shows exactly what every binding tool must do underneath: describe each type, each function's arguments and result, and who owns which memory.

A new kind of failure

Inside Python, a mistake raises an exception you can catch and read. Across the boundary into C, Python cannot check anything: if you describe a function wrongly (an int where the library expects a pointer, a buffer that is too short, a structure laid out differently), the program crashes with an access violation, or worse, keeps running with corrupted memory. So binding code is written carefully, from the header file, with every type spelled out (lesson 6.02), and tested.
