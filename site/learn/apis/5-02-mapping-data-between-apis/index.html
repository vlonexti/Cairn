Mapping Data Between APIs

lesson 5.022 of 5 in milestone 55 min1 practice task

Turning one API's records into another's - a field mapping table, money as integers or decimals rather than floats, enumerations mapped explicitly with a decision for unknown values, names and emails, missing versus null, and dates and times across time zones with ISO 8601, datetime and zoneinfo.

The mapping table

Write the mapping as a table first, with a row for every target field and where its value comes from:

Invoice field From the order Rule
external_ref id "shop-" + id
date created_at the local date in the company's time zone
customer_name customer.first_name, customer.last_name joined with a space, trimmed
email customer.email lower case
amount total_cents "19.99": a decimal string
state status paid to open, refunded to void; anything else is an error

Each row hides a decision; the rest of this lesson is about the common ones.

Money

Never use binary floating point for money: 0.1 + 0.2 is 0.30000000000000004. APIs send money as an integer of the smallest unit (1999 cents) or a decimal string ("19.99"). Convert with integer arithmetic or decimal.Decimal:

Python
from decimal import Decimal

cents = 1999
print(f"{cents // 100}.{cents % 100:02d}")
print(Decimal(cents) / 100, Decimal("19.99") * 3)
print(0.1 + 0.2)
Output
19.99
19.99 59.97
0.30000000000000004

Also check the currency: not every currency has two decimal places (yen has none), so cents / 100 is only right for the ones that do.

Enumerations

Status fields are the most common source of silent bugs. Map them with an explicit table, and decide what happens to a value not in it: raise an error, skip the record, or use a documented default. Never let an unknown status fall through as some default by accident; the day the shop adds partially_refunded, you want to know.

Missing, null and empty

{"phone": null}, {"phone": ""} and {} may mean different things: "known to have none", "entered blank", "not sent in this partial update". In particular, a PATCH-style partial update must not turn "not sent" into "erase the value". Decide per field, and write it in the mapping table.

Dates and times

Timestamps travel as ISO 8601 strings (2026-11-19T23:30:00Z, where Z means UTC, or with an offset like +01:00) or as seconds since 1970. Rules that avoid nearly every time bug:

  • Keep everything in UTC internally, as timezone-aware datetime objects.
  • Convert to local time only at the edge where a human-facing date is needed, such as an invoice date.
  • An order paid at 23:30 UTC on 19 November is dated 20 November in Amsterdam (UTC+1). Using the UTC date puts it in the wrong day, and at month end in the wrong month and the wrong tax period.
Python
from datetime import datetime
from zoneinfo import ZoneInfo          # on Windows: pip install tzdata

created = datetime.fromisoformat("2026-11-19T23:30:00+00:00")
local = created.astimezone(ZoneInfo("Europe/Amsterdam"))
print(local.date().isoformat())         # 2026-11-20

Prefer named time zones (Europe/Amsterdam) over fixed offsets in real code: they know about daylight saving time. (The practice uses fixed offsets so it runs anywhere.)

Keep the mapping testable

Write the mapping as a pure function, record in, record out, with no requests inside. It is then trivial to test with sample records, including the awkward ones: a missing last name, an unknown status, a timestamp just before midnight.
