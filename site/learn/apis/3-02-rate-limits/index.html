Rate Limits

lesson 3.022 of 5 in milestone 35 min1 practice task

How APIs limit how fast you call them - per-second, per-minute and daily limits, the 429 status, Retry-After in seconds or as a date, rate-limit headers - and staying under the limit on your side with a token bucket instead of waiting to be told off.

Why limits exist

Every public API limits how many requests a client may make: "100 requests per minute per key", "10 per second", "5,000 per hour". The limits protect the service from overload and from one customer starving the others. Your integration will hit them, most often while backfilling data or paging through everything.

Being told to slow down

When you go over, the API answers 429 Too Many Requests (some old APIs use 403 or 503), usually with headers saying when to come back:

Text
HTTP/1.1 429 Too Many Requests
Retry-After: 12
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1793523612
  • Retry-After is standard HTTP, and comes in two forms: a number of seconds (12) or an HTTP date (Wed, 21 Oct 2026 07:28:00 GMT). Handle both (practice 3.02); email.utils.parsedate_to_datetime reads the date form.
  • X-RateLimit-* headers are a common convention, not a standard: limit, remaining in the window, and when the window resets (often seconds since 1970, sometimes seconds from now: read the documentation). A newer standard spells them RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset.

Waiting at least as long as Retry-After says, then retrying, is the minimum. Ignoring it and retrying at once gets keys blocked.

Staying under the limit yourself

Better than hitting the limit is not hitting it. A token bucket paces requests on the client:

  • The bucket holds up to capacity tokens and starts full.
  • It refills continuously at rate tokens per second.
  • Each request takes one token; with none available, wait until one has refilled.
Python
class TokenBucket:
    def __init__(self, rate, capacity, clock):
        self.rate, self.capacity, self.clock = rate, capacity, clock
        self.tokens, self.updated = capacity, clock()

    def _refill(self):
        now = self.clock()
        self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
        self.updated = now

    def try_take(self):
        self._refill()
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

The capacity allows short bursts, the rate keeps the average under the limit. Set the rate a little below the documented limit, since other programs using the same key share it.

Other ways to need fewer requests

  • Use bulk endpoints when they exist (fetch 100 ids in one call).
  • Use the largest page size.
  • Cache what does not change (lesson 3.05).
  • Use webhooks (milestone 4) instead of polling for changes.
