Pagination

lesson 3.011 of 5 in milestone 35 min1 practice task

Getting long lists from an API one page at a time - offset and limit, page numbers, cursors and Link headers - how each behaves when data changes while you read, loop protection, and Python generators that make paging invisible to the rest of your code.

Lists come in pages

An endpoint that lists things (GET /books) never returns a million rows at once. It returns a page and a way to ask for the next one. The documentation's "Pagination" section says which style it uses.

Style Request Response tells you
offset and limit ?offset=40&limit=20 maybe a total
page number ?page=3&per_page=20 maybe total_pages
cursor ?cursor=eyJpZCI6MTAyfQ&limit=20 next_cursor (or has_more)
Link header follow the URL given Link: <https://api.example.com/books?cursor=abc>; rel="next"

Why cursors win

Offsets break when the list changes while you read it. Suppose you read page 1 (items 1 to 20), and someone deletes item 5 before you ask for offset=20: everything shifts left by one, and you skip the item that moved from position 21 to 20. An insert at the front makes you see an item twice.

A cursor is an opaque marker of "where I got to" (often the last id or sort key, encoded). The next page starts after that point regardless of inserts and deletes before it. Treat a cursor as an opaque string: do not decode or build it yourself, just pass back what you were given.

With any style:

  • Keep the sort order fixed (the API's default, or an explicit sort=id); paging over an unstable order is meaningless.
  • Ask for the largest page the API allows when you want everything: fewer requests, fewer rate-limit problems.
  • Deduplicate by id when the API only offers offsets.

Link headers

GitHub and many others put the next URL in a Link header (RFC 8288):

Text
Link: <https://api.example.com/books?page=3>; rel="next", <https://api.example.com/books?page=9>; rel="last"

Follow rel="next" exactly as given (it already contains every parameter), and stop when there is none. Parsing this header properly is practice 3.01.

Generators hide the paging

In Python, a generator turns "fetch page, process, fetch next page" into a plain loop for the rest of your code, and fetches lazily, only as far as the caller reads:

Python
def all_books(client):
    cursor = None
    seen = set()
    while True:
        page = client.request("GET", "/books", {"limit": 100, "cursor": cursor})
        yield from page["items"]
        cursor = page.get("next_cursor")
        if not cursor:
            return
        if cursor in seen:
            raise RuntimeError("the API returned the same cursor twice")
        seen.add(cursor)

for book in all_books(client):        # pages are fetched as the loop needs them
    if book["year"] < 1950:
        print(book["title"])

The seen check is loop protection: a server bug that returns the same cursor forever would otherwise make your program run, and spend your rate limit, forever.
