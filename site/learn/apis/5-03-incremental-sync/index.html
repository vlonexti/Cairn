Incremental Sync

lesson 5.033 of 5 in milestone 55 min1 practice task

Copying only what changed since last time - checkpoints and updated-since queries, upserting by external id so that reruns are safe, deletes through tombstones or periodic reconciliation, the first run over existing data, and the extra problems of two-way sync - conflicts and echo loops.

Not everything, every time

Copying all records on every run works for ten records and fails at ten thousand. An incremental sync asks only for what changed since the last run:

  1. Load the checkpoint: the largest updated_at processed last time.
  2. Fetch changes updated_since the checkpoint (paging through them, lesson 3.01).
  3. For each change, in order, upsert it into the target.
  4. Save the new checkpoint after the changes are safely applied.

If the program crashes between steps 3 and 4, the next run processes some changes again. That is fine, as long as step 3 is idempotent.

Upsert by external id

Upsert means "update if it exists, otherwise insert". With the id map (lesson 5.01), or an external reference in the target, reapplying the same change finds the existing record and updates it to the same values: nothing is duplicated. Never write a sync whose correctness depends on running each change exactly once.

The boundary problem from lesson 4.01 appears here too: ask for updated_at >= checkpoint and skip records already applied at exactly that timestamp, or a record updated in the same second as the checkpoint can be lost.

Deletes

A deleted record does not show up in "what changed" unless the source tells you:

  • Tombstones: the API returns deleted records in the change feed, marked "deleted": true (or has a separate deleted-records endpoint). Apply them as deletes, voids or archives.
  • Reconciliation: otherwise, periodically fetch the full list of ids from the source, compare with your id map, and handle the missing ones. Slower, but catches everything.

Decide what a delete means in the target: in accounting, you never delete an invoice; you void it or issue a credit note.

The first run

On the first run there is no checkpoint, and the target may already contain records created by hand before the integration existed. Plan the backfill: fetch everything (respecting rate limits), match existing target records by a natural key (an order number, an email) before creating new ones, and set the checkpoint at the end.

Two-way sync

When both systems may change the same records, two new problems appear:

  • Conflicts: the record changed on both sides since the last sync. Common rules: last writer wins by updated_at (simple, can lose an edit), field ownership (the shop owns the address, the CRM owns the notes), or flagging the conflict for a person.
  • Echo loops: you write a change into B; B reports it as a change; you copy it back into A; A reports it... Prevent it by remembering what you wrote (and ignoring the echo), comparing values before writing (no change, no write), or marking records with the integration as their last editor.
