Retries with Backoff

lesson 3.033 of 5 in milestone 35 min1 practice task

Recovering from the failures that go away by themselves - which errors and statuses are worth retrying, why only idempotent requests are safe to repeat, exponential backoff with a cap, full jitter, honouring Retry-After, and limiting attempts and total time.

Transient failures

Networks drop connections, servers restart, load balancers time out, and rate limits fill up. These transient failures often succeed a moment later, so robust clients retry. But retrying the wrong thing, or retrying too eagerly, makes problems worse.

What to retry

Outcome Retry?
connection refused or reset, DNS failure, timeout yes (the request may not have arrived)
408 Request Timeout, 429 Too Many Requests yes, after waiting
500, 502, 503, 504 yes
501 Not Implemented no (it will never be implemented by retrying)
any other 4xx no: the request is wrong
2xx, 3xx no: done

Only if it is safe to repeat

A retry may happen after the first attempt did reach the server and did take effect: the response was lost, not the request. So only repeat requests that are idempotent, meaning doing them twice has the same effect as once:

  • GET, HEAD, OPTIONS: read only.
  • PUT: replaces with the same content.
  • DELETE: the second delete finds nothing to delete.
  • POST and PATCH are not idempotent in general: a repeated "create order" creates two orders. Retry them only with an idempotency key (lesson 3.04).

Backoff and jitter

Retrying immediately hits a struggling server when it is weakest. Wait longer after each failure, exponential backoff:

Text
attempt 1 fails: wait up to 0.5 s
attempt 2 fails: wait up to 1 s
attempt 3 fails: wait up to 2 s     ... base × 2^(n-1), capped (for example at 8 s)

If a thousand clients failed at the same moment and all wait exactly 0.5 s, 1 s, 2 s, they all come back at the same moments, in synchronised waves. Jitter spreads them out. The simplest and very effective form, full jitter, waits a random time between 0 and the backoff value:

Python
delay = rng.uniform(0, min(cap, base * 2 ** (attempt - 1)))

When the response carries Retry-After, it overrides the computed delay: the server knows best.

Knowing when to stop

Always limit retries, by number of attempts (3 to 5 is common) and ideally by a total deadline ("this whole operation may take at most 30 s"). After the last attempt, report the last error with how many attempts were made. Endless retrying hides outages and burns your rate limit.

Pass the clock, the sleep function and the random number generator into your retry code: production passes time.monotonic, time.sleep and random.Random(), tests pass fakes, and a test of "retries four times with these delays" runs in a millisecond. Practice 3.03 is built that way.
