Partial Failure and Dead Letters

lesson 5.044 of 5 in milestone 55 min1 practice task

What to do when some records fail and others succeed - never letting one bad record stop the rest, sorting failures into transient and permanent, retrying the transient ones, keeping the permanent ones in a dead-letter list with the reason, replaying them after a fix, and the outbox pattern for keeping a database and an API in step.

One bad record

A sync processes a thousand orders and order 417 has an email address the accounting API rejects. The worst possible behaviour is the most common one: an exception stops the run, the checkpoint is not saved, and the next run fails on order 417 again, forever. Nothing after it is ever synced.

Transient or permanent?

Sort every failure into one of two kinds:

Kind Examples Action
transient timeout, connection reset, 429, 5xx retry (lesson 3.03); usually works soon
permanent 400 or 422 validation errors, an unmapped status, a missing required field retrying cannot help; set the record aside

Make the distinction explicit in code, with your own exception classes, so the processing loop can act on it:

Python
class TransientError(Exception): ...
class PermanentError(Exception): ...

for record in records:
    try:
        with_retries(lambda: handle(record))          # retries TransientError a few times
    except (TransientError, PermanentError) as e:
        dead_letters.append({"record": record, "reason": str(e)})
        continue                                       # the rest still get processed

Dead letters

A dead-letter queue (or list, or table) holds the records that could not be processed, each with:

  • the record (or its id),
  • the reason, as specific as possible ("accounting rejected email: invalid format"),
  • how many attempts were made and when.

The run continues past them and its checkpoint advances: the dead letters, not the checkpoint, remember what still needs doing. Someone (or an alert, lesson 5.05) looks at them, the cause is fixed (the mapping, the data in the shop, a bug), and the dead letters are replayed: processed again, and removed when they succeed. Practice 5.04 builds both halves.

A dead-letter list that only grows is a sign nobody is looking. Count it, alert on it.

Keeping a database and an API in step: the outbox

A common shape: your program saves an order in its own database and must tell another API about it. Doing both directly fails awkwardly: save succeeds and the API call fails, and the API never hears; or the API call succeeds and the save fails, and you told it about something that does not exist.

The outbox pattern fixes this: in the same database transaction as the order, insert a row "send order 42 to accounting" into an outbox table. A separate worker reads the outbox, makes the API call (with retries and an idempotency key, lesson 3.04), and marks the row done. The database transaction makes "order saved" and "message queued" happen together or not at all; the worker makes delivery eventually happen.
