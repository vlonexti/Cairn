Callbacks and Errors

lesson 6.044 of 5 in milestone 65 min1 practice task

When C calls back into Python - CFUNCTYPE and WINFUNCTYPE, keeping callbacks alive, exceptions inside callbacks - and how C reports errors - return codes, errno with use_errno, GetLastError with use_last_error and WinError, and errcheck to turn return codes into Python exceptions automatically.

Functions as arguments

Many C APIs take a function pointer: qsort takes a comparison function, Windows' EnumWindows calls you once per window, libraries call you with progress or log messages. In ctypes, describe the function type with CFUNCTYPE(restype, *argtypes) (WINFUNCTYPE for Windows API callbacks), and wrap a Python function with it:

Python
import ctypes

BINARY = ctypes.CFUNCTYPE(ctypes.c_int, ctypes.c_int, ctypes.c_int)

def add(a, b):
    return a + b

c_add = BINARY(add)          # a real C function pointer that runs the Python code
print(c_add(2, 3))
Output
5

A classic use, sorting a C array with the C library's qsort:

Python
CMP = ctypes.CFUNCTYPE(ctypes.c_int, ctypes.POINTER(ctypes.c_int), ctypes.POINTER(ctypes.c_int))

def compare(a, b):
    return (a[0] > b[0]) - (a[0] < b[0])

values = (ctypes.c_int * 5)(5, 1, 4, 2, 3)
libc.qsort.argtypes = [ctypes.c_void_p, ctypes.c_size_t, ctypes.c_size_t, CMP]
libc.qsort.restype = None
libc.qsort(values, len(values), ctypes.sizeof(ctypes.c_int), CMP(compare))
print(list(values))                 # [1, 2, 3, 4, 5]

Keep the callback alive

The C function pointer only exists while the Python wrapper object exists. If C stores the callback to call later (an event handler, a timer), and your code keeps no reference to the CFUNCTYPE object, Python frees it and C later jumps into freed memory: a crash, possibly minutes later. Store such callbacks somewhere long-lived (an attribute of the object that registered them) until you unregister them.

Exceptions cannot cross

An exception raised inside a callback cannot travel up through C frames. ctypes prints it, and C receives a meaningless result. So catch everything inside the callback, store the error, and check it after the C function returns:

Python
errors = []
def safe_compare(a, b):
    try:
        return compare(a, b)
    except Exception as e:
        errors.append(e)
        return 0

How C reports errors

C has no exceptions. Libraries report failure in the ways the Reading Documentation course described:

  • a return code (0 for success, negative for errors) or a special value (NULL, -1);
  • errno: load with CDLL(name, use_errno=True) and read ctypes.get_errno() right after the call;
  • on Windows, GetLastError: load with WinDLL(name, use_last_error=True), read ctypes.get_last_error(), and ctypes.WinError(code) turns it into an OSError with the system's message.

ctypes saves errno and the last error immediately after each call when asked to, which matters because Python itself may make system calls (and change them) before your next line runs.

errcheck

Checking every return value by hand is repetitive and easy to forget. A function's errcheck attribute runs after every call and may raise:

Python
def check_zero(result, func, args):
    if result != 0:
        raise OSError(result, f"{func.__name__} failed with {result}")
    return result

lib.open_device.argtypes = [ctypes.c_char_p, ctypes.POINTER(DeviceHandle)]
lib.open_device.restype = ctypes.c_int
lib.open_device.errcheck = check_zero          # now a failure raises like normal Python

Wrapping a C library this way, with types declared, errors turned into exceptions and resources freed in __del__ or context managers, gives the rest of the program an API that feels like ordinary Python.
