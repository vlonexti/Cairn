Reading an API Reference

lesson 1.044 of 5 in milestone 15 min1 practice task

Getting everything you need from a web API's documentation - base URL and versions, the endpoint list, path and query parameters, request and response bodies, error codes, authentication and limits - and the OpenAPI description many APIs publish, which you can read and even generate clients from.

What the reference must tell you

Before writing code against a web API, collect these from its documentation (the Reading Documentation course is about doing this precisely):

Question Where it usually is
Base URL, and per region or sandbox? "Getting started", "Environments"
How do I authenticate? "Authentication" (milestone 2)
Which version, and how is it chosen? "Versioning": in the path (/v2/), a header, or a date
What endpoints exist? the reference, one page per endpoint
What may I send, what will I get? each endpoint's parameters, request body and response schemas
How do errors look? "Errors": status codes and the error body shape
How much may I call? "Rate limits" (lesson 3.02)
How do lists work? "Pagination" (lesson 3.01)
What changed? "Changelog"

A sandbox or test mode environment, if the API has one, is where you develop: same API, fake money, fake messages.

One endpoint, read fully

A typical endpoint page, summarised:

Create a book - POST /v1/books

Body (JSON): title string, required, 1 to 200 characters; year integer, optional; tags array of strings, optional, at most 10.

Query: notify boolean, default false.

Responses: 201 the created book, with a Location header; 400 invalid JSON; 409 a book with that ISBN exists; 422 a field fails validation, with error.field naming it.

From that alone you know which fields to send, which to check, and four outcomes your code must handle differently.

Kinds of parameter you will see:

  • Path parameters are part of the path: GET /books/{id}. They must be escaped (lesson 1.05): an id of a/b must not create a new path segment.
  • Query parameters filter or shape results: GET /books?author=Herbert&limit=20.
  • Header parameters: authentication, versions, idempotency keys.
  • Body fields, described by a schema with types, required fields and limits.

OpenAPI

Many APIs publish their reference as an OpenAPI document (formerly Swagger): a YAML or JSON file describing every endpoint, parameter and schema. The pretty documentation pages are often generated from it. An excerpt:

Text
paths:
  /books/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer }
      responses:
        "200":
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Book" }
        "404":
          description: no such book

Because it is machine-readable, tools can generate client code, mock servers and request validators from it, and you can search it for facts the prose pages leave out. When the pretty page and the OpenAPI file disagree, check against the live sandbox (lesson 5.03 of Reading Documentation).

Versions and deprecation

APIs change while your code runs. Read how the provider versions it: a new path (/v2/), a header (Accept: application/vnd.example.v2+json), or a dated version you choose per request (Api-Version: 2026-10-01). Pin the version explicitly, read the changelog before moving, and watch for deprecation notices, sometimes sent as a Deprecation or Sunset response header.
