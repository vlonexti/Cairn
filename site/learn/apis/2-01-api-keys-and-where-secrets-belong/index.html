API Keys and Where Secrets Belong

lesson 2.011 of 5 in milestone 25 min1 practice task

The simplest way APIs identify a caller - the API key - how to send it, why never in the URL, where secrets live (environment variables, untracked files, secret managers, never in code), keeping keys narrow in what they can do, and what to do the day one leaks.

Who is calling?

Almost every API needs to know who is calling: to bill them, to limit them, to decide what they may see. The simplest answer is an API key: a long random string the provider gives you, which you send with every request.

Python
headers = {"Authorization": "Bearer sk_live_51Hx...", "Accept": "application/json"}
# or, depending on the API:
headers = {"X-Api-Key": "sk_live_51Hx..."}

The documentation says which header. Some old APIs accept the key in the query string (?api_key=...): avoid that whenever there is a choice. URLs end up in server logs, proxy logs, browser history and error reports; headers usually do not.

A key is a password

Anyone who has the key is you, as far as the API knows. So:

  • Never put it in code. Code is committed, shared, pasted into questions, and published. Keys pushed to a public repository are found by automated scanners within minutes.
  • Read it from the environment, or a configuration file that is not tracked by git (add it to .gitignore), or a secret manager (Windows Credential Manager, macOS Keychain, cloud secret stores) in production.
  • Fail clearly when it is missing, without printing it when it is present.
Python
import os

api_key = os.environ.get("BOOKS_API_KEY", "").strip()
if not api_key:
    raise SystemExit("Set the BOOKS_API_KEY environment variable (see README).")

On Windows, set it for the current terminal with set BOOKS_API_KEY=... (cmd) or $env:BOOKS_API_KEY="..." (PowerShell); .env files loaded by a library such as python-dotenv are a common convenience for development, and they too stay out of git.

Narrow keys

Most providers let you create several keys with different powers. Use that:

  • Test and live keys separately (sk_test_... and sk_live_... are a common naming): development never touches real data.
  • Restricted keys with only the permissions the program needs: a reporting script gets read-only access.
  • One key per program or server, so one can be revoked without breaking the others, and logs show which one did what.

When a key leaks

It will happen eventually: a commit, a screenshot, a log file. The response is always the same:

  1. Revoke (or "roll") the key at the provider immediately. Deleting the commit is not enough: it is already copied.
  2. Create a new key and put it where your programs read it.
  3. Check the provider's logs for use you did not make.
  4. Find how it leaked and close that path (lesson 2.05).
