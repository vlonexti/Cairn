Requests and Responses

lesson 1.022 of 5 in milestone 15 min1 practice task

The parts of an HTTP request and response as an API client sees them - method, URL with path and query, headers such as Content-Type, Accept and Authorization, the body, status codes and their families, response headers worth reading, and timeouts.

The request

Every call you make is an HTTP request with four parts:

Text
POST /v1/books?notify=true HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json
Authorization: Bearer abc123

{"title": "Dune", "year": 1965}
  • The method and the URL: scheme and host (https://api.example.com), path (/v1/books) and query string (?notify=true), name-value pairs after the ?, separated by &.
  • Headers: metadata. Content-Type says what the body is; Accept says what you want back; Authorization carries your credentials (milestone 2); User-Agent names your program; Idempotency-Key (milestone 3) makes a retry safe.
  • The body: the data you send, for POST, PUT and PATCH. For JSON APIs, a JSON document.

The response

Text
HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/books/77
X-Request-Id: 9f2c1e

{"id": 77, "title": "Dune", "year": 1965}

The status code is the first thing to check. Its first digit is its family:

Family Meaning Common codes
2xx success 200 OK, 201 Created, 202 Accepted, 204 No Content
3xx go elsewhere 301 Moved Permanently, 304 Not Modified (lesson 3.05)
4xx your request is wrong 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Too Many Requests
5xx the server failed 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout

The distinction between 4xx and 5xx drives your error handling: repeating a 4xx request unchanged gives the same error (fix the request), while a 5xx or a 429 may succeed if you retry later (milestone 3).

Response headers worth reading: Content-Type (is it really JSON?), Location (where a created resource lives), Retry-After (how long to wait), ETag (lesson 3.05), rate-limit headers, and a request id such as X-Request-Id, which you should log: it is what the API's support team asks for.

Error bodies

Most APIs also put details of an error in the body, often in a documented shape:

JSON
{"error": {"code": "invalid_year", "message": "year must be between 0 and 2100", "field": "year"}}

Your client should surface the status, the API's error code and message, and the request id, rather than a bare "request failed".

Timeouts

A request without a timeout can hang forever if the server or network stalls. Always pass one: urlopen(url, timeout=10) or requests.get(url, timeout=(3, 10)) (connect and read timeouts). Choose it from what your program can afford to wait, and treat a timeout like a 5xx: maybe retry, maybe give up.
