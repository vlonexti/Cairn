OAuth 2.0 and PKCE

lesson 2.033 of 5 in milestone 25 min1 practice task

Acting on behalf of a user without ever seeing their password - the OAuth 2.0 roles, the authorization code flow step by step with PKCE and the state parameter, scopes and redirect URIs, the client credentials flow for server-to-server calls, and why you use a well-tested library.

The problem OAuth solves

Your program wants to read a user's calendar at another service. The bad solution is to ask for their password. OAuth 2.0 lets the user sign in at the service itself and grant your program limited access, which it receives as tokens. The user's password never reaches you, and they can revoke your access at any time.

The roles: the resource owner (the user), the client (your program), the authorization server (where the user signs in and tokens come from) and the resource server (the API).

The authorization code flow with PKCE

The flow used by apps, websites and command-line tools today:

  1. Make a code verifier: a random secret string (43 to 128 characters of A-Z a-z 0-9 - . _ ~), and its code challenge: base64url(SHA-256(verifier)) without = padding. This is PKCE (Proof Key for Code Exchange, RFC 7636).
  2. Make a state: another random string, remembered for this attempt.
  3. Send the user's browser to the authorization URL:
Text
https://auth.example.com/authorize?response_type=code&client_id=myapp
    &redirect_uri=http%3A%2F%2F127.0.0.1%3A8765%2Fcallback&scope=calendar.read
    &state=Xy7...&code_challenge=E9Mel...&code_challenge_method=S256
  1. The user signs in there and approves the scopes you asked for.
  2. The service redirects the browser to your redirect URI with ?code=...&state=... (or ?error=access_denied).
  3. Check the state equals the one you made; otherwise reject: it protects against a forged callback.
  4. Exchange the code at the token endpoint: POST with grant_type=authorization_code, the code, the redirect_uri, your client_id and the code verifier. The server hashes the verifier and checks it matches the challenge from step 3.
  5. You receive the access token (and usually a refresh token).

Why PKCE? A code intercepted on its way to your redirect URI (by another app on the device, for example) is useless without the verifier, which never left your program. It replaces the older "client secret" for apps that cannot keep a secret, and is recommended for every client now.

Python
import base64, hashlib

verifier = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"         # the example from RFC 7636
digest = hashlib.sha256(verifier.encode("ascii")).digest()
print(base64.urlsafe_b64encode(digest).rstrip(b"=").decode())
Output
E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM

Scopes and redirect URIs

  • Scopes name what you may do: calendar.read, repo, offline_access (for a refresh token). Ask for the fewest you need; users are more likely to approve, and a leaked token can do less.
  • The redirect URI must be registered with the service in advance and match exactly. Desktop and command-line programs use a loopback address such as http://127.0.0.1:8765/callback, running a tiny local server for the moment of the callback.

Client credentials: no user involved

For server-to-server calls, where your program acts as itself, the client credentials flow is a single request:

Text
POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=myservice&client_secret=...&scope=reports.read

The answer is an access token as in lesson 2.02. Note the body is form-encoded, not JSON: token endpoints follow the OAuth specification, not the API's usual style.

Use a library

The flows are simple to describe and easy to get subtly wrong (state checks, redirect matching, token storage). In real programs use a maintained library (authlib, requests-oauthlib, or the provider's SDK) and read its documentation. Building the pieces once, as the practice does, is how you learn what the library is doing for you, and how to debug it when a sign-in fails.
